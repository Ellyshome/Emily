# 规格→概要设计计划（req-plan）

> **最高约束**：本 skill 的产出必须符合 [项目宪法](../_shared/constitution.md)。冲突时以宪法为准——本技能的"硬约束"章节直接引用宪法 §2，不自行发明铁律。

> **产出级别：SD（System Design / 概要设计）**
>
> 本技能产出**概要设计**级别的开发计划，聚焦于：
> - 系统架构与模块划分
> - 模块间接口契约
> - 数据模型设计（表结构/字段级）
> - 数据流与时序设计
> - 关键算法/策略选型
>
> **不产出**具体实现代码、完整复制粘贴代码块——那些属于 DD（详细设计）范畴，由 AI 执行者在编码阶段自行落地。
>
> **你的角色**：
>
> | 角色 | 固定/自适应 | 说明 |
> |------|------------|------|
> | **作为Emily开发者资深架构师** | 🔒 固定 | 深刻理解Emily项目架构（双容器+Session主线+LangGraph 5节点执行引擎）、53表数据模型、分层约束。所有设计必须建立在真实架构基础上，不允许架空设计 |
> | **{AI根据需求自行判断}** | 🔄 自适应 | 根据具体需求的内容和领域，自行判断需要叠加哪些专业角色（如系统设计师、数据库架构师、安全工程师等），在计划开头声明 |
>
> **"作为Emily开发者资深架构师"是不可跳过的根基角色**，确保计划始终根植于Emily真实架构。在此基础上，根据需求自行判断并声明额外角色。

## 1. 核心原则

| # | 原则 | 说明 |
|---|------|------|
| 1 | **SD 级抽象** | 设计做"做什么、接什么、出什么"，不做"怎么写"。产出接口契约、数据模型、流程设计，不是具体代码 |
| 2 | **接口契约明确** | 模块间交互通过明确定义的接口契约（函数签名、数据格式、协议），契约中注明输入/输出/异常 |
| 3 | **模块化设计** | 以"模块"为组织单元，非"阶段"。每个模块有独立职责、独立接口、独立验收标准，最后组装 |
| 4 | **验收嵌入模块** | 每个模块有独立的验收检测命令。不是在全部完成后集中验证——那太晚了 |
| 5 | **深嵌项目现状** | 必须先探查现有架构再写设计。所有分层位置、现有接口、数据表必须来自真实架构，不是假设 |
| 6 | **参照已有模式** | 新模块的分层、命名、交互模式必须与项目现有架构一致。每个模块标注参照源 |
| 7 | **硬约束前置** | 计划开头列出的硬约束**直接引用宪法 §2（C0~C11）**，不自行发明铁律。执行者绝对不能违反的铁律前置声明 |
| 8 | **依赖图显式** | 模块间依赖关系必须用 ASCII 图表达，据此决定构建顺序 |
| 9 | **数据模型完整** | 涉及数据持久化的模块，必须给出完整表结构（表名、字段、类型、约束、索引），但不产出 ORM 代码 |
| 10 | **独立脚本架构** | 每个功能设计为独立可执行脚本，聚合薄壳仅串联各脚本入口不含业务逻辑。独立脚本提供双通道：CLI + 可 import 核心函数 |
| 11 | **追溯闭合** | 每个模块必须声明它实现的 `US-xx`；每个 `US` 必须被至少一个模块覆盖。产出 US↔模块映射表，不闭合即不合格（宪法 §1.3） |
| 12 | **不私自扩需** | 计划只回答"怎么实现"。若发现规格缺陷，**回退 req-review 改 PRD**，不在计划里新增/改写需求（宪法 §1.2） |

## 2. 触发条件

### 使用此 skill 的场景

- 需求规格已完成（PRD 由 `req-review` 产出），需要转化为概要设计计划
- 用户说"帮我制定实施计划"、"根据这个需求生成开发计划"、"create implementation plan"
- 用户使用 `/req-plan` 命令
- 用户说"这个需求怎么落地"、"分几个模块做"

### 不使用此 skill 的场景

- 需求尚未明确，还在讨论阶段 —— 先让用户用 `req-review` 产出规格
- 需求太简单（单文件、<50 行改动）—— 直接写代码，不需要计划
- 纯调研/分析任务 —— 不需要分模块编码
- 已有实施计划，需要审核计划本身 —— 用 `req-review`
- 已实施完毕，需要验收 —— 用 `req-verify`

## 3. 统一命名与追溯约定

本项目需求流水线（需求→规格→计划→测试报告）使用统一文件命名规则：

**命名格式**：`{模块标识}_{阶段}_V{版本号}.md`

| 阶段标记 | 含义 | 产出方 |
|---------|------|--------|
| `需求` | 原始需求文档 | 人工编写 |
| `PRD` | **规格（Spec）**——含 `US-xx` / `AC-xx` | req-review |
| `计划` | 概要设计计划（SD，Plan） | req-plan（本技能） |
| `测试报告` | 验证结果 + 规格符合度 | req-verify |

**版本号规则**：每份文档独立版本，从 V1 起始。同一模块同阶段产出新版时自动递增。

**模块标识提取**：
1. 若输入文档遵循命名约定（如 `全景节点图V2_需求_V1.md`），提取 `_需求_` 之前的模块标识
2. 若为旧格式文件名，以文档所在目录名作为模块标识
3. 模块标识在整个流水线中保持稳定

**追溯约定（本技能的责任）**：计划必须消费 PRD 的 `US-xx`，产出 US↔模块映射：

| 追溯项 | 本技能须产出 | 校验规则（宪法 §1.3） |
|--------|-------------|---------------------|
| US → 模块 | 每个模块声明它实现的 `US-xx` | 每个 US 至少被一个模块覆盖 |
| 模块 → US | 每个模块标注对应的 `US-xx` 列表 | 无对应 US 的模块 = 越界，须删除或回退补规格 |
| 缺失清单 | "未覆盖的 US"清单 | 有 US 未被任何模块实现时，必须显式列出并说明 |

> **模块编号由本技能分配**：PRD 阶段只用**功能域名**（如"世界书裁剪层"），`M1`/`M2` 等编号在本技能首次出现。追溯矩阵中应标注 **功能域 → `Mx`** 的对应，便于回查 PRD。

**文件版本声明**：计划头部必须声明 `基于 PRD：{文件名}`（含版本号），否则视为失效。

**文件名示例**：
```
全景节点图V2_需求_V1.md    全景节点图V2_PRD_V1.md    全景节点图V2_计划_V1.md
```

## 4. 概要设计编制流程

### Step 1：读取并理解规格（PRD）

- 读取用户指定的规格文档。按统一命名约定查找 `{模块标识}_PRD_V*.md`（取最新版本）
- **必须提取 PRD 中的 `US-xx` 清单与各自的验收标准 `AC`**——这是本技能追溯的基准
- **必须提取 PRD 的两类约束**，作为设计输入：
  - §4.1 触碰的宪法铁律 → 计入计划的"硬约束"
  - §4.4 约束型技术决策（必须/不得类）→ 逐条落实，写入"PRD 约束落实"表（见 §5 模板）
- 若存在旧格式的审核意见（`*_审核意见.md` / `*-架构师完善版.md`），一并参考
- 如果用户未指定路径但提到了文档名，用 Glob 在 `需求/` 下搜索
- **若找不到 PRD**：向用户报告搜索路径与结果，提示先用 `req-review` 产出规格；**不凭一段需求概述直接设计**（否则 US→模块追溯链无法建立，宪法 §1.3 不满足）

### Step 2：深度探查项目现状

> **这是最关键的一步**。设计必须建立在"真正了解现状"的基础上。不能凭记忆或假设。

按以下顺序探查：

```
1. 宪法 §2（_shared/constitution.md）← 确认铁律 C0~C11，作为本次设计的硬约束
2. CLAUDE.md           ← 已加载，确认当前架构版本、技术栈、分层约束
3. docs/数据库设计.md    ← 了解现有表 schema，避免重复或冲突
4. docs/业务模块与运转全景.md ← 了解现有模块，确认集成点
5. 相关现有代码          ← Read 关键源文件，了解现有接口、数据模型、分层结构
6. 相关需求文档目录       ← Glob 同模块已有需求/PRD/计划/报告
```

**必须探查的具体内容**：

| 探查目标 | 方法 | 产出 |
|----------|------|------|
| 分层位置确认 | Read 对应 Service/Repository/Application 文件 | 确定新模块在分层链中的插入点 |
| 可复用接口 | Read 同层已有代码 | 列出可直接复用/扩展的现有接口和类（精确到方法签名） |
| 已有模式参照 | Read 相似模块的完整实现 | 确定状态模式、Repo 模式、Service 模式、ORM 风格 |
| 数据库现状 | Read `models.py` 相关 ORM 类 | 确认不会创建重复表，确认 FK 关系，确认列命名风格 |
| 配置现状 | Read `config.py` | 确认新增配置 key 的命名一致性 |
| 已有 API 风格 | Read 已有路由文件 | 确认 URL 前缀、响应格式、错误处理风格 |

### Step 3：设计模块拆分与系统架构

基于需求+现状探查结果，将需求拆解为**独立可设计、可验收的模块**。

**模块拆分原则**：

| 原则 | 说明 | 反例 |
|------|------|------|
| **单一职责** | 每个模块负责一个清晰的领域/功能 | ❌ M1 包含 schema + parser + registry |
| **独立可验** | 每个模块有独立的验收检测命令 | ❌ "数据层设计好了但没法验证" |
| **依赖显式** | 模块间依赖用 ASCII 图表达 | ❌ 模块间有隐式耦合 |
| **无循环依赖** | 依赖图必须是 DAG | ❌ M1→M2→M1 |
| **新增包不影响已有分层** | 新模块在分层链中的位置必须明确 | ❌ 新模块跨越 Service/Repository 层 |
| **独立脚本架构** | 每个功能设计为独立脚本，流程用薄聚合脚本串联 | ❌ 所有逻辑内嵌到 EmilyCore，无法独立验证 |
| **追溯可闭合** | 每个模块声明的 `US-xx` 合起来覆盖 PRD 全部 US | ❌ 某 US 无人实现却未列出缺失 |
| **不越界** | 模块不得引入 PRD 之外的需求 | ❌ 模块"顺手"实现了未登记的功能 |

**模块粒度参考**：

| 粒度 | 适用场景 | 示例 |
|------|----------|------|
| 细粒度（单一职能） | 纯数据结构/独立解析器/校验器 | 告警规则定义、数据格式解析 |
| 中粒度（协同子模块） | 带状态的注册表/引擎/编排器 | 告警引擎、调度器、导出器 |
| 粗粒度（跨模块集成） | 需要改造已有模块的集成设计 | Pipeline 集成、API 路由扩展 |

**产出追溯映射**：拆完模块后，先建立 US↔模块映射再写设计：

```markdown
| US-ID | 由哪些模块实现 | 覆盖状态 |
|-------|---------------|---------|
| US-01 | M1, M3        | ✅ 已覆盖 |
| US-02 | —             | ❌ 未覆盖（须说明原因或回退 req-review） |
```

> 此映射表将原样写入设计文档（见 §5 追溯矩阵）。**映射不闭合不许进入 Step 4**。

### Step 4：输出概要设计文档

用 Write 保存到需求文档同目录。

**文件命名规则**——遵循统一命名约定（见第 3 节）：
1. **提取模块标识**：从输入文件名中提取；旧格式用目录名
2. **确定版本号**：Glob 搜索 `{模块标识}_计划_V*.md`，取最大版本号 +1；无已有文件则用 V1
3. **最终文件名**：`{模块标识}_计划_V{版本号}.md`

例如：为 `全景节点图V2_需求_V1.md` 制定计划 → 输出 `全景节点图V2_计划_V1.md`

> 项目铁律直接引用 [宪法 §2](../_shared/constitution.md)，**不自行发明**。

5. **不私自扩需**：发现规格缺陷**回退 req-review**，不在本设计里新增/改写需求

## 独立脚本架构设计

> 涉及数据处理/业务流程的模块，按"独立脚本+聚合薄壳"模式设计。

## 阶段反思指令

每完成一个模块的设计，在进入下一个模块之前，执行以下反思：

1. **检查设计完整性**：本模块的接口契约、数据模型、验收检测是否完整
2. **检查追溯闭合**：本模块声明的 US 是否都有接口/验收覆盖；对照追溯矩阵有无遗漏
3. **检查设计偏差**：是否有与规格（PRD）不符的设计？如发现规格缺陷，**回退 req-review**，不在计划内扩需
4. **判断是否继续**：
   - 如果偏差 ≤ 1 个接口调整 → 直接修改设计文档对应模块，继续
   - 如果偏差 2-4 个接口或模块职责调整 → 在设计文档末尾追加 "v1.1 修订记录"，继续
   - 如果偏差 > 4 个接口或架构方向变化 → **停止**，报告给用户，等用户决定是否重新生成设计

---

## 7. 反模式（不要做的事）

| # | ❌ 不要做 | ✅ 应该做 |
|---|----------|----------|
| 1 | 不探查项目就写设计 | 先 Read 相关源文件、已有模块实现、数据库 models.py |
| 2 | 用"Phase"分阶段 | 用"Module"分模块（M1/M2/M3...），每模块独立可设计可验收 |
| 3 | 写模糊接口描述 | 给出精确的方法签名、字段类型、API 端点路径 |
| 4 | 验收标准写"功能正常" | 写具体验证命令+预期输出 |
| 5 | 沿用已废弃的模式 | 确认参照源是当前有效代码 |
| 6 | 设计脱离分层约束 | 新模块必须遵守项目的实际分层链 |
| 7 | 产出完整实现代码 | SD 级别不写复制粘贴代码——给接口契约和数据模型即可 |
| 8 | 设计写得像需求文档 | 设计文档用接口、表结构、流程图表达，不是用户故事 |
| 9 | 不给替代方案 | 核心算法/策略选型注明为什么选此方案 |
| 10 | 模板结构自己发挥 | 严格按第 5 节模板——这是设计产出的约定格式 |
| 11 | 模块间有隐式耦合 | 依赖图必须显式，接口契约必须声明 |
| 12 | 只有最终验收没有模块验收 | 每个模块必须有独立验收检测 |
| 13 | 不标注对现有代码的改动 | "现有模块改动清单"必须逐一标注每个受影响模块 |
| 14 | 设计过于抽象无法验证 | 接口签名、数据表结构、验收命令必须是具体可执行的 |
| 15 | **模块不声明实现的 US / 追溯不闭合** | 每个模块标注"实现的需求：US-xx"，产出完整追溯矩阵，缺失项显式列出 |
| 16 | **在计划里私自扩需** | 只回答"怎么实现"；发现规格缺陷回退 req-review 改 PRD |
| 17 | **自行发明硬约束** | 直接引用[宪法 §2](../_shared/constitution.md)的铁律，不另起炉灶 |
| 18 | **找不到 PRD 就凭需求概述直接设计** | 先让 req-review 产出规格，否则 US→模块追溯链无法建立 |
| 19 | **沉默跳过 PRD 的约束型技术决策** | 逐条在"PRD 约束落实"表回应（如何遵守/落在哪个模块）；确实无法遵守的回退 req-review，不装作没看见 |
