# 需求→AI执行计划（req-plan）

> **你的角色**：你是**实施计划编制专家**。你产出的不是传统软件设计文档——而是给 AI 编码 agent 看的**操作指令序列**。接收这份计划的 agent 应当能逐行执行，无需额外澄清、无需二次探查。

---

## 1. 核心原则

| # | 原则 | 说明 |
|---|------|------|
| 1 | **指令式，非描述式** | "打开 X 文件，在第 N 行后追加 Y 代码"——不是"应该在 X 模块下新建文件"。AI agent 需要具体的动作动词 |
| 2 | **代码完整可复制** | 计划中的代码块是最终产物的直接模板，不允许 `...` 省略关键逻辑。AI agent 的职责是复制→适配→验证，不是从零设计 |
| 3 | **验证嵌入步骤** | 每个步骤后紧跟一条可执行的验证命令。不是在阶段末尾集中验证——那太晚了 |
| 4 | **深嵌项目现状** | 必须先探查现有代码再写计划。所有参照的文件路径、方法签名、模式必须来自真实代码，不是假设 |
| 5 | **参照已有模式** | 新代码风格、命名、分层必须与项目现有代码一致。每个新建文件标注参照源 |
| 6 | **纵向切片** | 每阶段交付一个可独立验证的端到端功能。不是"先做所有 Model，再做所有 Service" |
| 7 | **硬约束前置** | 计划开头列出 AI 执行者绝对不能违反的铁律（不改已有方法签名、不跳过验证等） |

---

## 2. 触发条件

### 使用此 skill 的场景

- 需求文档已完成（可能经过 `req-review` 审核），需要转化为开发计划
- 用户说"帮我制定实施计划"、"根据这个需求生成开发计划"、"create implementation plan"
- 用户使用 `/req-plan` 命令
- 用户说"这个需求怎么落地"、"分几个阶段做"

### 不使用此 skill 的场景

- 需求尚未明确，还在讨论阶段 —— 先让用户用 `req-review` 审核需求
- 需求太简单（单文件、<50 行改动）—— 直接写代码，不需要计划
- 纯调研/分析任务 —— 不需要分阶段编码
- 已有实施计划，需要审核计划本身 —— 用 `req-review`

---

## 3. 统一命名约定

本项目需求流水线（需求→审核→计划→测试报告）使用统一文件命名规则：

**命名格式**：`{模块标识}_{阶段}_V{版本号}.md`

| 阶段标记 | 含义 | 产出方 |
|---------|------|--------|
| `需求` | 原始需求文档 | 人工编写 |
| `审核` | 需求审核报告 | req-review |
| `计划` | AI 实施计划 | req-plan |
| `测试报告` | 验证测试报告 | emy-verify |

**版本号规则**：每份文档独立版本，从 V1 起始。同一模块同阶段产出新版时自动递增。

**模块标识提取**：
1. 若输入文档遵循命名约定（如 `全景节点图V2_需求_V1.md`），提取 `_需求_` 之前的模块标识
2. 若为旧格式文件名，以文档所在目录名作为模块标识
3. 模块标识在整个流水线中保持稳定

**文件名示例**：
```
全景节点图V2_需求_V1.md    全景节点图V2_审核_V1.md    全景节点图V2_计划_V1.md
```

## 4. 实施计划编制流程

### Step 1：读取并理解需求

- 读取用户指定的需求文档
- 如果存在对应的审核报告，必读。按统一命名约定查找：`{模块标识}_审核_V*.md`（取最新版本）。旧格式可能为 `xxx_审核意见.md` 或 `xxx-架构师完善版.md`
- 如果用户未指定路径但提到了文档名，用 Glob 在 `需求文件/` 下搜索

### Step 2：深度探查项目现状

> **这是最关键的一步**。计划必须建立在"真正了解现状"的基础上。不能凭记忆或假设。

按以下顺序探查：

```
1. CLAUDE.md           ← 已加载，确认当前架构版本、技术栈、分层约束
2. docs/数据库设计.md    ← 了解现有表 schema，避免重复或冲突
3. docs/业务模块与运转全景.md ← 了解现有模块，确认集成点
4. 相关现有代码          ← Read 关键源文件，了解现有实现、可复用组件、真实方法签名
5. 相关需求文档目录       ← Glob 同模块已有需求/计划/报告
```

**必须探查的具体内容**：

| 探查目标 | 方法 | 产出 |
|----------|------|------|
| 分层位置确认 | Read 对应 Service/Repository/Application 文件 | 确定新模块在分层链中的插入点 |
| 可复用组件 | Read 同层已有代码 | 列出可直接复用的类、函数、枚举、Mixin（精确到方法签名） |
| 已有模式参照 | Read 相似模块的完整实现 | 确定状态机模式、Repo 模式、Service 模式、ORM 列风格 |
| 数据库现状 | Read `models.py` 相关 ORM 类 | 确认不会创建重复表，确认 FK 关系，确认列类型风格 |
| 配置现状 | Read `config.py` | 确认新增配置 key 的命名一致性 |
| 已有 API 风格 | Read 已有路由文件 | 确认 URL 前缀、响应格式、错误处理风格 |

### Step 3：设计架构方案

基于需求+现状探查结果，设计模块架构。**注意：这一步是编制者自己的思考过程，不必全部写入最终计划**。最终计划只需要：

1. **模块定位**：在分层架构中的位置（一句话 + ASCII 图）
2. **数据模型**：新表/字段的完整定义
3. **代码模式参照**：每层参照哪个现有文件
4. **架构决策**：如果有多种路线可选，简述选择理由（1-2 句）

### Step 4：划分实施阶段

按**增量交付**原则划分阶段。每阶段一个可独立验证的端到端功能切片。

| 原则 | 说明 | 反例 |
|------|------|------|
| **纵向切片** | 每阶段交付可独立验证的端到端功能 | ❌ Phase 1 只做所有 Model 类 |
| **自底向上** | 先基础设施，再逻辑，再暴露，再集成 | ❌ Phase 1 先写 API 路由 |
| **每阶段可验收** | 阶段结束时有一条端到端路径可跑 | ❌ "数据层写好了但没法测试" |
| **风险前置** | 把技术风险最高的放在早期阶段 | ❌ 未验证的技术选型放在最后 |

### Step 5：输出 AI 执行计划文档

用 Write 保存到需求文档同目录。

**文件命名规则**——遵循统一命名约定（见第 3 节）：
1. **提取模块标识**：从输入文件名中提取；旧格式用目录名
2. **确定版本号**：Glob 搜索 `{模块标识}_计划_V*.md`，取最大版本号 +1；无已有文件则用 V1
3. **最终文件名**：`{模块标识}_计划_V{版本号}.md`

例如：为 `全景节点图V2_需求_V1.md` 制定计划 → 输出 `全景节点图V2_计划_V1.md`

**这是最关键的一步**。按照下方模板（第 4 节）输出——模板结构不可偏离，因为它是 AI 执行者解析计划时的约定格式。

## 7. 反模式（不要做的事）

| # | ❌ 不要做 | ✅ 应该做 |
|---|----------|----------|
| 1 | 不探查代码就写计划 | 先 Read 相关源文件、已有模块实现、数据库 models.py |
| 2 | 横向切分阶段（"先做所有 Model"） | 纵向切片，每阶段交付端到端可验证功能 |
| 3 | 写模糊的文件描述（"在 services 下建文件"） | 给出精确路径和插入位置：`emily-core/emily_core/services/xxx_service.py` 末尾 |
| 4 | 验收标准写"功能正常" | 写具体验证命令+预期输出：`grep "class Xxx" path/to/file.py` → 应返回一行匹配 |
| 5 | 沿用已废弃的模式 | 确认参照源是当前有效代码（不是 M15 WorkOrder、不是 EmyBot 旧架构） |
| 6 | 计划脱离分层约束 | 新模块必须遵守项目的实际分层链 |
| 7 | 代码块用 `...` 省略 | 代码必须完整。如果某段逻辑确实太长，拆成多个步骤 |
| 8 | 计划写得像需求文档 | 指令式动词（"打开/追加/替换/运行"），不是描述式（"应该/需要/建议"） |
| 9 | 不给替代方案 | 在"架构决策"中 1-2 句简述为什么选此方案 |
| 10 | 模板结构自己发挥 | 严格按第 4 节模板——这是 AI 执行者解析计划的约定格式 |
