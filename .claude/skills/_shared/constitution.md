# Emily 项目宪法（Constitution）

> **定位**：需求流水线（req-review → req-plan → req-verify）与全部开发的最高约束。任何 skill 的内部约定与本文冲突时，**以本文为准**。
> **权威来源**：架构铁律源自 [`CLAUDE.md §6 开发约束`](../../../CLAUDE.md)；流水线规则由本文件定义。
> **版本**：v1.1（2026-09-11）

---

## 0. 三技能如何引用本宪法

| 技能 | 引用点 |
|------|--------|
| **req-review** | 生成规格前，对照 §2 判断需求是否触碰架构铁律；在 PRD"边界与约束"章节声明触及的铁律编号与影响 |
| **req-plan** | 计划的"硬约束"章节**直接引用 §2**，不得自行发明铁律；每个模块设计须声明它遵守/不违反哪些铁律；产出"接线矩阵"满足 §3 Q6 |
| **req-verify** | 测试报告中增加"宪法合规"判定，逐条核对 §2 / §3 是否被违反；**Q6 接线闭合须用静态可达性扫描实测**（定义 vs 使用），不得只看运行时行为 |

> **原则**：铁律不被"绕过"。若需求确实与某条铁律冲突，必须显式提出并走变更（见 §1.3），不允许沉默迁就。

## 1. 流水线与追溯宪法（SDD 核心）

### 1.1 流水线与文档（铁律）

```
需求 → [req-review] PRD（规格/Spec）→ [req-plan] 计划（概要设计/Plan）→ 编码 → [req-verify] 测试报告
```

命名统一为 `{模块标识}_{阶段}_V{版本号}.md`：

| 阶段标记 | 含义 | 产出方 |
|---------|------|--------|
| `需求` | 原始需求文档 | 人工编写 |
| `PRD` | **规格（Spec）**：What / Why + 可验收标准 | req-review |
| `计划` | **概要设计（Plan）**：How | req-plan |
| `测试报告` | 验证结果 + 规格符合度 | req-verify |

### 1.2 Spec / Plan 边界（铁律）

| 文档 | 只回答 | 禁止出现 |
|------|--------|---------|
| **PRD（Spec）** | 做什么、为什么、怎样算做完 | 见下方「PRD 禁 / 许清单」 |
| **计划（Plan）** | 怎么实现 | 新增或改写需求。若发现需求缺陷，**回退到 req-review** 改 PRD，不在计划里私自扩需 |

**PRD 禁 / 许清单**

| 类别 | ❌ 禁止（属计划 / DD） | ✅ 允许（属规格） |
|------|---------------------|-----------------|
| 数据 | 表名、字段类型、DDL、JSON schema 定义 | 对数据的**业务要求**（可见范围、保留期、一致性、审计） |
| 接口 | 函数签名、类名、API 路径与请求体 | 对外的**可感知行为**（输入/输出/失败时用户看到什么） |
| 位置 | 文件路径、目录结构 | — |
| 模块 | **模块编号 `M1`/`M2`**，以及"某模块放某文件"的归属声明 | 用**功能域名称**描述边界（如"世界书裁剪层""会话编排"） |
| 技术决策 | **方案型**：选哪张表 / 哪个类 / 哪个库 / 放哪个文件 | **约束型**：必须复用现有能力、不得引入新依赖、必须经注册通道接入、必须兼容既有协议 |
| 可视化 | 系统架构图、数据流向图、模块依赖图 | 业务流程图、业务状态图 |

> **判断法则**：一句话若描述"用户能看到的行为"或"必须遵守的约束"→ 属 PRD；若描述"代码怎么组织"或"用哪个方案实现"→ 属计划 / DD。
>
> **模块编号归属**：`Mx` 由 req-plan 统一分配；PRD 阶段只按**功能域**命名，不预设编号。
>
> **约束的传递**：PRD §4.4 的约束型技术决策属规格，**必须被下游消费**——
> - req-plan：逐条落实，并在"PRD 约束落实"表中回应（遵守方式 / 是否需变更）
> - req-verify：逐条核对是否被遵守（如"不得引入新依赖"→ 检查依赖清单；"必须复用 X"→ 检查是否确用了 X）

### 1.3 稳定 ID 与三向追溯（铁律）

| ID | 含义 | 分配方 | 规则 |
|----|------|--------|------|
| `US-{NN}` | 需求条目（用户故事） | req-review | **一旦分配永久稳定**，不复用、不重编号 |
| `AC-{US-NN}.{M}` | 验收标准 | req-review | 挂在所属 US 下，可执行、可判定 |
| `M{N}` | 实现模块 | req-plan | 每个模块须声明它实现哪些 US |
| `TC{NN}` | 测试用例 | req-verify | 每条用例须声明它回验哪些 US |

**追溯链：`US-xx → Mx → TCxx`，三向必须闭合。**

| 校验点 | 规则 | 校验方 |
|--------|------|--------|
| 计划阶段 | 每个 US 至少被一个 M 实现 | req-plan |
| 测试阶段 | 每个 US 至少被一个 TC 回验 | req-verify |
| 越界检查 | 无对应 US 的 M / TC 视为越界，必须删除或补规格 | req-plan / req-verify |
| 缺失检查 | 无对应 M 的 US = 未设计；无对应 TC 的 US = 未验证 | 各自输出"未覆盖清单" |

### 1.4 规格变更（铁律）

需求变更时，遵循单向传播：

```
改 PRD（版本号 +1，登记变更记录） → 改计划 → 改测试报告
```

- 计划与测试报告头部**必须声明"基于 PRD 版本"**（如 `基于 PRD：XX_PRD_V2.md`）
- 基于旧版 PRD 而未同步的下游文档**视为失效**
- ID 只增不改：作废的需求标 `US-xx（已废弃）`，不回收编号

### 1.5 生效范围（新老划断）

- 本宪法约束**此后新产出**的 PRD / 计划 / 测试报告
- **存量文档不回填、不判违规**：已产出的 PRD（如含系统架构 / 模块职责表 / 文件路径的历史件）保持原样继续有效；确需修订时，按新规重出下一版（版本号 +1）
- 新老文档可共存；追溯链只要求**同一版本内**闭合

## 2. 架构铁律（违反即失败）

> 权威来源：[`CLAUDE.md §6 开发约束`](../../../CLAUDE.md)。此处为流水线校验用速查版；如与 CLAUDE.md 冲突，以 CLAUDE.md 为准。

| # | 铁律 | 一句话 |
|---|------|--------|
| C0 | **根治而非迁就** | 优先系统性解决根因，不做凑合/绕过方案 |
| C1 | **业务内核独立** | `emily_core` 不 import 任何 `astrbot.*` 包 |
| C2 | **分层不可跳** | `API → EmilyCore → Session → WorkItem → Application → Service → Repository → DB` |
| C3 | **SOP 即路由** | 新增 SOP = 放 `.md` 到 `emily-data/sops/` → 重启生效 |
| C4 | **Hook 声明式 JSON** | 新 Hook 编辑 `hook_config.json` 注册 → 实现类 → 重启生效 |
| C5 | **结构化输出优先** | 命中 SOP → chat_json → `{tool, params}` → 框架直调，不暴露为 function-calling |
| C6 | **Sync repo + to_thread** | Repository 全 sync，async Service 用 `asyncio.to_thread()` 包裹 |
| C7 | **Hook 三态 deny-wins** | before 异常 = BLOCK；after 异常不阻断 |
| C8 | **唯一执行引擎** | LangGraph StateGraph（5 节点含 error_analysis）；PipelineBUS 已废弃 |
| C9 | **ToolManager / ScriptManager 边界** | 进程内 LLM 工具 vs subprocess 脚本，共享 service 层但互不调用 |
| C10 | **工具必须带参数 schema** | 三步缺一不可：源文件 `_XXX_SCHEMA` → 注册 `params=` → 一致性映射 `TOOL_SCHEMA_MAP` |
| C11 | **功能注册接入（元原则）** | 新功能必须经注册通道接入（tools/scheduler/hook/sop/scripts/provider），禁止裸文件/硬编码接线；出现孤儿代码须**停下提醒用户** |
| C12 | **Session 主循环冻结（元原则）** | ⚠️ 最高优先级架构纪律：Session 主循环只因对话机制本身而改，**永不因业务功能增长而改**；功能增长一律落能力层（新工具/新 SOP 能力/协作封装为新能力）。**腐化判据：业务功能的 PR diff 到主循环文件即违反本条** |

## 3. 质量红线

| # | 红线 | 说明 |
|---|------|------|
| Q1 | **验收可执行** | 任何"验收标准/验收检测"必须给出可执行命令 + 预期输出。禁止"功能正常"类描述 |
| Q2 | **证据驱动** | 测试结论必须有回复文本 / API 响应 / DB 记录 / 日志行支撑。禁止编造 PASS |
| Q3 | **真实用户测试** | emy-test 的 `--sender-id` 必须取自 `users` 表真实 UUID，禁止伪造（否则测的是降级路径） |
| Q4 | **无残留** | 临时脚本 / 桩数据 / 配置变更必须清理，或显式标注保留原因 |
| Q5 | **无越界** | 不引入未经评估的新依赖；不顺带重构无关代码 |
| Q6 | **接线闭合** | 任何产出物必须有消费者，任何开关必须有读取方。**仅定义无使用**（死开关/死代码）、**仅写入无读取**、**仅注册无调用**（孤儿代码）＝未完成，不得判"通过"。核验用**静态可达性扫描**（定义处 vs 使用处），不依赖运行时行为——运行时"看起来正常"不能证明已接线（默认值巧合正确尤其危险） |

## 4. 修订约定

- 修订本宪法后，**必须同步检查三个技能的一致性**（命名、ID 规则、引用点）
- 铁律的增删改须与 [`CLAUDE.md §6`](../../../CLAUDE.md) 保持一致，不得只改其一
- 版本号递增记录在文首 `版本` 行
