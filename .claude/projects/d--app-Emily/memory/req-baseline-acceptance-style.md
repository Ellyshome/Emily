  type: project

- **规则**：需求基线的「验收方向」章节，必须以**用户视角**表达，用「**修改前 → 修改后**」的差异呈现；不得写成"场景 → 预期结果"的功能清单式罗列。
- **写法**：
  - 三列表：`场景（用户动作）` / `修改前（现状）` / `修改后`。
  - 「场景」用用户会做的动作来写（"上传一份完工单""想让某个节点退出管控"），不写内部机制名。
  - 「修改前」必须按**实测代码现状**写，且用**中性、事实性**的陈述：现状是什么就写什么，**不刻意负面、不写成抱怨或价值评判**。例：写"该资料按普通文件归档，不触发全景节点的创建或调整"，而不是"系统完全不处理，节点树要靠人逐条录入"。不得按旧文档口径、设计意图或设想写。
  - 不体现前后差异的条款（工程约束类：注册通道、只读性、静态可达性、C12/C13、编号规则、权限边界等）**另立一张表**（如"边界与工程约束核对（不体现为前后差异）"），不要塞进差异表硬造一个"修改前"。
  - 仍须满足宪法 Q1：落地为测试时给出可执行命令 + 预期输出。
- **示例**：`Issues/全景节点/全景节点_需求基线_V1.md` §九——9.1 用户可见差异（14 条前后对照）+ 9.2 边界与工程约束核对。
- **反例**：`| 5 | 归档一份无任何归属的文件 | 落临时节点并标注「无归属」；L4 用户可见并认领 |`——只给了预期，读者无法判断"以前是什么样、这次变了什么"。

**Why:** 需求基线的读者是评审者与业务方，他们判断"这个需求值不值得做"的依据是"用户实际体验会发生什么变化"，而不是系统内部新增了哪些行为。只写预期结果时，未实现的旧能力与新增能力在表格里长得一模一样，评审者无法分辨改动价值，也无法判断某条验收是否本该早已满足。
