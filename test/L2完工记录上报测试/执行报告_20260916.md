## 三、逐用例证据

### T1 正解-模糊表达（3 轮）+ T7 确认

| 轮次 | 用户输入 | Emily 回复（要点） | 漏斗档 |
|---|---|---|---|

| 3 | 帮我记录一下：景观工程铺装本日施工完成铺装面层10平方米 | 拟录入单：事件「景观铺装面层完成」／**归属节点：硬质铺装与园路**／内容回显 | F1→F2→F3 ✅ |
| 4 | 确认 | 已记录，事件编号 EVT-20260916-0005 | F4 ✅ |

**归属证据**：`project_events` PE-20260916-0005 → `EMR-SG-01-05-02`；`events` EVT-20260916-0005 `status=confirmed`。

**缺陷（P1）**：第 2 轮 LLM 触发"追问中断"（Scheduler interrupt），用户却只收到占位串「请补充信息」。归档可见：
```
⏸ 1. 能力: SOP-002-REC　待用户补充（29714ms）
  成果: 请补充信息
```
该占位串还会**残留到下一轮**（第 3 轮归档中重复出现同一工作项），存在上下文污染风险。

**根因已定位并复现（模型无过错，是取值的管道 bug）**：

`llm_trace.jsonl` 中该轮 LLM 实际生成的 `ask_user` 参数**质量很高**，明确追问了两个缺口：

```json
{"question": "黄工，收到，这是景观铺装施工…1）归属节点：你负责的节点里，「硬质铺装与园路」（下有\"园路面层铺装\"成果）和「水景石材铺装」都涉及铺装。你说的\"景观那边铺砖\"是园路/广场的面层铺装，还是水景池壁的石材铺装？2）工作量：今天大概铺了多少平方米？具体在哪个位置…"}
```

但这段文本在传递途中丢失，落到了 `emily_core/workitem/scheduler.py:470 _extract_interrupt_question()` 的兜底返回值。该函数：

```python
tasks = getattr(snap, "tasks", {}) or {}
for t in tasks.values():          # ← 问题在这里
```

而 langgraph 的 `langgraph.types.StateSnapshot.tasks` 声明为 **`tuple[PregelTask, ...]`**（元组），元组没有 `.values()`，抛出的 `AttributeError` 被紧随其后的 `except Exception: pass` 静默吞掉，于是返回 `"请补充信息"`。

实测复现（容器内注入同名假快照）：
```
tasks as tuple -> '请补充信息'                    ← 与线上实际类型一致
tasks as dict  -> '黄工，是园路面层铺装还是水景池壁石材铺装？…'   ← 修复后即正确
```

**附带确认**：`loop.py` 的 `_ask_user` 在 `interrupt()` 之后才 `return {..., "patch": {"waiting_question": question}}`，而 `interrupt()` 会即刻挂起、函数体不再执行，因此 `waiting_question` **从未写入状态**——这解释了为何 `scheduler.py:429` 的 `snap.values.get("waiting_question")` 取到空值、只能退化到上面那个坏掉的兜底函数。两处叠加才导致占位串外泄。

**一行修复**：`for t in tasks.values():` → `for t in (tasks.values() if isinstance(tasks, dict) else tasks):`（或直接 `for t in tasks:`，langgraph 的元组语义即可）。
