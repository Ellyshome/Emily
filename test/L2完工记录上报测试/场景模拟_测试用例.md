# 场景模拟 测试用例 —— L2 施工员信息上报的节点归属引导（导向漏斗）

> **场景来源**：`场景模拟.md`（模拟 L2 用户进行施工完工确认录入）
> **被测能力**：SOP-002-REC 事件记录 + 节点归属引导（四档判定）+ 参与节点的成果承接识别
> **执行通道**：A（IM 对话，emy-test）+ E（库核对）
> **数据布置**：`场景模拟_布置_景观任务链.sql`　**回滚**：`场景模拟_回滚_景观任务链.sql`
> **用例数**：7（T1~T7）　**观察维度**：7（D1~D7）
> **本次重点**：不是"能不能录进去"，而是**引导过程如何逐级收敛到具体节点**——即漏斗的每一档有没有被正确走到。

## 三、导向漏斗模型（观察骨架）

引导应沿下列档位**自上而下**收敛（判定顺序与 SOP-002 §3.5 一致）：

```
F0 意图识别        「我今天干活了」→ 是否进入事件记录并开始启发式引导
      ↓
F1 承接关系识别    是否找到"承接本次成果的任务节点"（靠 query_my_nodes 的 deliverables 名称匹配）
      ↓               命中 → F2；未命中 → F5
F2 归属确定        node_id 是否 = 承接节点（正解 EMR-SG-01-05-02）；不得越级落到临时节点
      ↓
F3 确认交互        拟录入单是否展示归属（节点名）并等用户确认；不得索要节点编号
      ↓
F4 落库留痕        写入后 project_events.node_id 是否正确、可追溯
      ↓
F5 降级兜底        无承接/用户明确不知道 → 列候选（本人负责→企业参与）→ 最后才临时节点
```

每档的判定标准见第五节 D1~D7。

## 四、测试用例

> 每轮之间保持同一 `--sender "黄志强"`（服务端会话池按 sender 归并），才能观察到"多轮收敛"。

| 编号 | 输入（按轮次） | 期望漏斗路径 | 判定标准（通过条件） |
|---|---|---|---|
| **T1 正解-模糊表达**（场景原文） | ①「喂，那个...我今天干活了」<br>②「啊...就是铺装，景观那边的铺砖，我今天弄了些，想报上去」<br>③「帮我记录一下：景观工程铺装本日施工完成铺装面层10平方米」 | F0→F1→F2→F3→F4 | ①②轮逐级追问且问题有指向性（部位/部位工序/工程量），不重复问同一件事；③轮给出的归属为**硬质铺装与园路**（或该节点下的「园路面层铺装」）；拟录入单含归属行；不出现"节点编号是多少" |
| **T2 正解-一次说全** | 一条消息：「景观工程铺装，今天完成面层铺装10平方米，挂到硬质铺装与园路」 | F1→F2→F3 | 不再重复追问已有信息；直接给拟录入单+归属确认 |
| **T3 干扰项-同企业不同工序** | 「今天在景观那种树，乔木灌木，种了30株」 | F1→F2 | 归属为**绿化种植**（或「乔木灌木种植」），**不得**落到硬质铺装/铺装类节点 |
| **T4 高干扰项-同名"铺装"** | 「水景池壁的石材铺装，今天做了20平方」 | F1→F2 | 归属为**水景石材铺装**（EMR-SG-01-11-01），**不得**被"铺装"关键词带到园路铺装 |
| **T5 无承接** | 「景观那边土方回填，今天填了100方」 | F1（未命中）→F5 | 不得编造 node_id；应列出候选节点名让用户选，或说明暂存待归类；回执中说明"暂未归类"之类的业务语言 |
| **T6 用户明确不知道** | 接 T5：「我也不知道该算哪个节点」 | F5→最后档 | 不再反复追问；落临时节点；回执说明后续可改挂；**不得**自行挑一个节点填上 |
| **T7 拟录入确认闭环** | 接 T1：「确认」 | F4 | 落库成功；`project_events.node_id` = 所确认的归属节点；事件可被后续查询还原 |

> T1/T2 验"主链路"，T3/T4 验"匹配精度"，T5/T6 验"兜底与不臆造"，T7 验"留痕闭环"。

## 五、分维度观察表

执行时逐条记录（"记录"列填 观察到的原话/现象 或 证据 SQL 结果）。

| 维度 | 观察点 | 合格判定 | 不合格信号（卡点） | 记录 |
|---|---|---|---|---|
| **D1 引导收敛** | 每轮追问是否比上一轮更具体；是否把用户零散信息整理成拟录入单 | 轮数与信息缺口同步减少；每次追问只问 1~2 个缺口 | 反复问同一字段；连续 3 轮原地打转；一次抛 5 个问题 | |
| **D2 承接识别** | 是否主动查"有没有承接本次成果的任务节点"（而不是直接让用户从节点清单里挑） | T1/T2 直接命中铺装成果；T3/T4 不失真 | 完全不查承接关系，一上来就罗列候选节点 | |
| **D3 归属精度** | 正解/干扰项的落点是否正确 | T1→05-02、T3→05-01、T4→11-01 | 被关键词带偏（T4 落到园路铺装）；或一律落到父节点 05 | |

| **D5 交互口径** | 是否用业务语言、给节点**名称**而非编号；是否暴露内部概念 | 全程无"节点编号""UNASSIGNED""状态机"等词 | 索要节点编号；把"临时节点"直白告诉用户 | |

## 七、已知卡点（布置阶段实测得出，执行时重点确认）

| # | 卡点 | 说明 | 与本场景的关系 |
|---|---|---|---|
| 1 | **成果名不含工序/部位** | 现网景观链成果全是"施工方案（份）"，无法承接"完工量"上报 | 布置脚本已补 4 条完工量成果。若未布置，T1 必然走不到 F2 |
| 2 | **层级深度上限 = 3** | `node_service.MAX_PARENT_DEPTH=3`，`EMR-SG-01-05-02` 已有 2 级祖先，**无法再挂工序级子任务** | "整条任务链"到"具体任务"为止；若业务需要工序级任务包，需先决策调深度或改挂法 |
| 3 | **父节点状态滞后** | `EMR-SG-01-05` 子节点已 IN_PROGRESS，但父状态仍是 `CONDITIONS_NOT_MET`（未重算） | 布置脚本已显式补正；这也是一个可复现的治理缺陷 |
| 4 | **L2 权限边界** | `submit_node_deliverable` 已放开到 L2（`write_l2`，**需重启 emily-core 生效**）；`create_task_node`（L3+）、`update_node_progress`（L5+）仍锁 | 一线只能"上报"，不能建任务/改进度；成果提交还需节点先 IN_PROGRESS |
| 5 | **query_my_nodes 状态口径** | 参与人口径只返回 `IN_PROGRESS`；责任人口径已改为不限状态 | 若节点未启动，候选里只剩责任人口径能兜住 |
| 6 | **记录能力的可见性来源** | L2 的 `record_event` 不经级别层（write=L3+），而是靠已授权 SOP-002-REC（`min_level=2`）在 SOP 授权层放行 | 若某角色 `sop_allow` 不含 SOP-002-REC，则连记录都调不起 |
| 7 | **超时风险** | 历史上 SOP-002-REC 出现过 120s 超时 | 超时轮次不计入 D1~D4 评分，但计入 D7 |
