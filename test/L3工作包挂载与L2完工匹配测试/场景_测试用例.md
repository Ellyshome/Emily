# 场景 测试用例 —— L3 工作包挂载录入 + L2 完工上报匹配

> **参考**：`Issues/测试用例/L2完工记录上报测试/`（同结构、同口径）
> **被测能力**：① L3 在工作包层级的「挂载录入」能力；② L2 完工上报时对工作包成果的**承接匹配**与归属引导
> **执行通道**：A（IM 对话，emy-test）+ E（库核对）
> **数据布置**：`场景_布置_大区景观工作包.sql`　**回滚**：`场景_回滚_大区景观工作包.sql`
> **用例数**：6（U1~U6）　**观察维度**：7（E1~E7）
> **本次重点**：分两段——**上半场**看 L3 能不能把工作包挂上去；**下半场**看 L2 上报 100 ㎡铺装面层能否**准确落到「铺装面层」工作包**。

## 三、观察骨架

### 段 A：L3 挂载录入能力（可达性）

```
A1 诉求识别     「在大区景观工程下分解三个工作包…」→ 是否识别为"建节点/挂工作包"意图
     ↓
A2 能力可达     是否真的调到了节点挂载类能力（create_task_node / create_node / mount_child_node）
     ↓              可达 → A3；不可达 → 记录卡点（走 SOP 能力？还是被拒？还是误走了"记任务"）
A3 结构正确     父节点 = 大区景观工程；3 个包；类型正确（均为叶子节点 → TASK）
     ↓
A4 量化承载     建出的包能否带成果与目标量（500/300/200 ㎡）
```

### 段 B：L2 完工上报的匹配漏斗（沿用四档口径）

```
B1 承接匹配     100㎡铺装面层 → 是否命中「铺装面层」工作包的成果（而非两个垫层包）
     ↓             命中 → B2；未命中 → B4
B2 归属确定     node_id 是否 = EMR-LG-01-01（铺装面层）
     ↓
B3 确认与留痕   拟录入单是否展示归属、用户确认后 project_events.node_id 是否正确
     ↓
B4 降级兜底     无承接/用户不知道 → 本人负责节点 → 企业参与节点 → 最后才临时节点
```

| 编号 | 段 | 输入 | 期望 | 判定标准 |
|---|---|---|---|---|

| **U2** | B | L2：「景观铺装面层今天完工 100 平方米」 | 匹配到铺装面层 | 归属 = **铺装面层**（EMR-LG-01-01）；拟录入单含归属展示；不得落到父节点「大区景观工程」或临时节点 |

| **U5** | B | L2：「大区景观那边绿化种了点草，大概 200 平」 | 无承接降级 | 三个工作包都无"绿化"成果 → 走 B4 降级（列候选/暂存待归类），**不得**硬塞给铺装或垫层包 |
| **U6** | B | L2：「把铺装面层这 100 平方正式报上去（提交成果）」 | 成果提交边界 | 观察 `submit_node_deliverable` 是否可达、是否让用户确认；**并核对成果量是否更新**（预期：`current_amount` 仍为 0，见卡点③） |

## 七、已知卡点（代码级预判，执行时重点验证）

| # | 卡点 | 依据 | 预期表现 |
|---|---|---|---|
| ① | **L3 的写能力不进会话能力目录** | `CapabilityCatalog.list_capabilities` 对兜底档位为 BASIC 的用户（L2/L3）按 `FallbackPolicy.resolve(tier, with_write=True)` 过滤写工具，该白名单只含 `knowledge_search / chat_archive / meta_cognition_read`；而 `create_task_node` 虽在级别层可见（business/write → L3+），却没有 L3 可访问的 SOP 声明它（SOP-011 `min_level=5`，且其 §3.3 章节标题不匹配解析器） | **U1 预期走不通**：L3 大概率被告知无权限/无法执行，或退化为"记任务"。这就是本包要暴露的核心缺口 |
| ② | **`create_task_node` 无成果参数** | 该工具 schema 只有 project_id/title/executor_id/deadline/parent_node_id/description | 即使 U1 能建包，包上**没有成果与目标量** → 下半场无法量化匹配 |
| ③ | **完工量无法通过上报落地** | `submit_node_deliverable` 只改 `submission_status` 与附件，**不写 `current_amount`**；量只在 `confirm_deliverable`（current=target）或 `update_node_progress`（L5+）时变更 | U6 上报后仍是 `0/500`；"100 平方米"只留在事件描述里 |
| ④ | **成果提交同样无 SOP 入口** | `submit_node_deliverable` 的 SOP 声明只在 SOP-011（L2/L3 不可见） | U6 大概率不可达；L2 现实可用的上报路径是 **SOP-002 事件记录**（`min_level=2`）——U2~U5 因此按事件记录口径判定 |
| ⑤ | **层级深度上限 = 3** | `node_service.MAX_PARENT_DEPTH=3` | 本布置只用 2 层（大区 → 工作包），若要在工作包下再挂工序级子任务，只剩 1 层余量 |
| ⑥ | **父节点状态依赖子节点重算** | `determine_node_status`：有子节点时由子节点集体决定 | 若上半场/布置后父状态未刷新，需留意「大区景观工程」状态是否与子节点一致 |

> ①②③④ 是"能力/模型缺口"，⑤⑥ 是"约束与一致性"；前者建议立需求，后者建议补自检。
