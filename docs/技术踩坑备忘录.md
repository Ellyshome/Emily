## 1. 容器与部署

### 1.1 `__pycache__` 不会自动刷新

| 项 | 内容 |
|----|------|
| **现象** | 修改 Python 代码后重启容器，旧逻辑仍在运行 |
| **原因** | Docker bind-mount 不触发 Python 重编译，`.pyc` 缓存仍是旧字节码 |
| **解决** | 每次代码变更后执行：`docker exec astrbot find /AstrBot/data/plugins/emily_agent -name '__pycache__' -type d -exec rm -rf {} +` |
| **相关** | Windows 宿主机 + Docker Desktop bind-mount 特有问题 |

### 1.2 Git Bash 路径污染 SOP 目录解析

| 项 | 内容 |
|----|------|
| **现象** | `SOPIntentRegistry` 加载 0 份 SOP，全部走 fallback |
| **原因** | `Path(__file__).resolve().parents[2]` 在容器内路径为 `C:/Program Files/Git/app/sops`（Windows PowerShell Git Bash 路径注入）；容器内期望 `/app/sops` |
| **解决** | SOP 目录解析加回退顺序：`/app/sops` → 环境变量 `EMILY_SOP_REPOSITORY_DIR` → dev 路径 `emily-data/sops` |
| **文件** | `agent/intent_registry.py` |

### 1.3 Docker 服务名在宿主机不可达

| 项 | 内容 |
|----|------|
| **现象** | `emys_tester` 连接 `maxkb` 失败 |
| **原因** | `emys_tester` 在宿主机执行，`maxkb` 是 Docker Compose 内部服务名 |
| **解决** | tester 自动替换 `maxkb`→`localhost`（RAG provider URL）；`emily-postgres`→`localhost`（DB 直连） |
| **文件** | `.claude/skills/emy-test/emys_tester.py` |

### 1.4 Windows PowerShell 默认 GBK 中文乱码

| 项 | 内容 |
|----|------|
| **现象** | emy-test 输出中文显示为乱码 |
| **原因** | PowerShell 默认 GBK 编码 |
| **解决** | 预先设置 `$env:PYTHONIOENCODING="utf-8"`；emy-test daemon 模式自行设置编码 |
| **文件** | `.claude/skills/emy-test/cli.py` |

### 1.5 `bootstrap._config_from_env` 缺少 env 映射

| 项 | 内容 |
|----|------|
| **现象** | Docker 设 `EMILY_EXECUTOR_MODE=real` 但 Config 仍为 `mock`；MaxKB RAG 未初始化 |
| **原因** | `_config_from_env()` 的 `env_map` 缺失 10 个 `EMILY_*_MODE` 和 `EMILY_MAXKB_*` 映射 |
| **解决** | 补全 10 个 env 映射（PLANNER/EXECUTOR/GUARDIAN/AUTH/RISK_MODE + MAXKB_*） |
| **文件** | `bootstrap.py` |

## 2. 数据库

### 2.1 FK 列语义陷阱：`conversation_id` 是 UUID 非业务串

| 项 | 内容 |
|----|------|
| **现象** | `create_outbound()` 和 `AgentReasoningRepository` 写入消息报 FK 违规 |
| **原因** | `messages.conversation_id` 列是 FK→`conversations.id`（UUID string），但业务层用的是 `conversation_id` 字符串（如 "group_888"）。需要先通过 `_resolve_conversation_id()` 把业务 ID 转为 UUID。 |
| **解决** | `MessageRepository.create_from_standard()` 已正确（它通过 `conv.id` 访问 UUID）；`create_outbound()` 和 `AgentReasoningLog` 写入前需显式解析 |
| **安全模式** | 始终用 `from_standard()` 路径（正确处理 FK），避免直接构造 ID |
| **文件** | `repositories/message_repo.py`, `agent_reasoning_repo.py` |

### 2.2 `Base.metadata.create_all()` 不给已有表加索引/列

| 项 | 内容 |
|----|------|
| **现象** | 新增列和索引在已有环境上不生效 |
| **原因** | `create_all()` 只建不存在的表和列——对已存在表的新增字段和索引无效 |
| **解决** | 首次部署（全新空 DB）无问题；已有环境需手动执行 DDL。无 Alembic 迁移工具 |
| **文件** | `infrastructure/database/session.py:init_db()` |

### 2.3 PostgreSQL advisory lock 是 session 级

| 项 | 内容 |
|----|------|
| **现象** | `PlanTaskScheduler._tick()` 的 advisory lock 未阻止并发执行 |
| **原因** | PG advisory lock 绑定到 session；`_acquire()` 返回后 session 关闭，lock 自动释放，`_tick()` 失去保护 |
| **解决** | 使用 `get_session_raw()` 手动管理 session 生命周期，保持 session 在 `_tick()` 期间不关闭 |
| **文件** | `services/plan_task_scheduler.py`, `infrastructure/database/session.py` |

### 2.4 `expire_on_commit=False` 避 DetachedInstanceError

| 项 | 内容 |
|----|------|
| **现象** | ORM 对象在 session 外访问属性报 `DetachedInstanceError` |
| **原因** | SQLAlchemy 默认在 commit 后 expire 所有属性 |
| **解决** | `sessionmaker(expire_on_commit=False)` —— 全局禁用 expire，对象可在 session 外安全访问 |
| **文件** | `infrastructure/database/session.py` |

### 2.5 时间戳为 ISO8601 字符串（非 DB datetime）

| 项 | 内容 |
|----|------|
| **现象** | 应用层比较时间戳行为与 DB 原生 datetime 不同 |
| **原因** | 所有时间戳列定义为 `String` 类型，存储 ISO8601 字符串（如 `"2026-06-26T09:30:00+08:00"`），由 `_utc_now()` / `_beijing_now()` 生成 |
| **解决** | 应用层字符串比较需注意时区（UTC vs Beijing +08:00）；字符串排序与 ISO8601 字典序一致 |

### 2.6 `instance_no` vs `instance_id` 混淆

| 项 | 内容 |
|----|------|
| **现象** | 计划任务工具 handler 收到 `instance_no`（如 `PTI-20260625-0001`），但传给 Service 时 `instance_id=""` → 核心功能断裂 |
| **原因** | 工具参数名为 `instance_no`，但 Service 按 `instance_id`（UUID）查找 |
| **解决** | handler 先调用 `get_by_instance_no(instance_no)` 解析出 UUID，再传给 Service |
| **文件** | `tools/plan_task_tool.py`, `services/plan_task_service.py`, `repositories/plan_task_repo.py` |

### 2.7 缺失 UniqueConstraint 致无幂等

| 项 | 内容 |
|----|------|
| **现象** | 同一周期重复创建计划任务实例 |
| **原因** | `PlanTaskInstance` 缺 `__table_args__` → 无唯一约束 → `(template_id, period_key)` 可重复 |
| **解决** | 加 partial unique index：`uq_pti_period(template_id, period_key) WHERE status != 'CANCELLED'`（PostgreSQL `postgresql_where`） |
| **文件** | `infrastructure/database/models.py:PlanTaskInstance` |

### 2.8 User 模型缺 `permission_level` 字段

| 项 | 内容 |
|----|------|
| **现象** | 反委派检测（`getattr(user, "permission_level", 0)`）始终返回 0，从未触发 |
| **原因** | `users` 表定义时遗漏 `permission_level` 列 |
| **解决** | 新增 `permission_level` Integer 字段（0访客..4系统管理员）；存量数据默认为 0 |
| **文件** | `infrastructure/database/models.py:User` |

### 2.9 事务边界：instance + log 跨 session

| 项 | 内容 |
|----|------|
| **现象** | log 写入失败但 instance 已提交（脏数据） |
| **原因** | `PlanTaskService` 创建 instance 和写入 log 用了两个不同 session → instance 已 commit，log 失败不回滚 |
| **解决** | 合并到同一事务中（统一 session 管理），确保原子性 |
| **文件** | `services/plan_task_service.py` |

### 2.10 LLM failure 标志位位置错误

| 项 | 内容 |
|----|------|
| **现象** | 计划任务 LLM 周期计算失败但未检测到 |
| **原因** | `llm_calculation_failed` 标志在 `PlanTaskInstance` 上（从未被设为 True），实际应在 `PlanTaskTemplate` 上标记 |
| **解决** | 将标志位从 Instance 移回 Template；Template 上有对应检查和通知逻辑 |
| **文件** | `services/plan_task_scheduler.py`, `infrastructure/database/models.py` |

## 3. AstrBot / IM

### 3.1 `event.plain_result()` 不是 awaitable

| 项 | 内容 |
|----|------|
| **现象** | `await event.plain_result(text)` 报错 |
| **原因** | `plain_result()` 返回 `Result` 对象，非 coroutine |
| **正确** | `result = event.plain_result(text); event.set_result(result); event.stop_event()` |

### 3.2 `set_result()` 被后续 `send()` 覆盖

| 项 | 内容 |
|----|------|
| **现象** | 前导消息（"处理中…"）丢失 |
| **原因** | AstrBot 的 `event.set_result()` 同事件多次调用只保留最后一次。RespondStage 在所有 handler 执行完毕后统一发送。中间消息必须用 `event.send()` 直发。 |
| **解决** | `send_progress()` 改用 `event.send()` 直发（M8b）；`send_file` 同理（M13） |
| **文件** | `data/plugins/emily_agent/adapters/astrbot/outbound_sender.py` |

### 3.3 插件 `__init__` 必须接收 `config` 参数

| 项 | 内容 |
|----|------|
| **现象** | AstrBot 加载插件失败 |
| **原因** | AstrBot 通过 `Star(config=plugin_config)` 传入配置，插件 `__init__` 签名必须为 `__init__(self, context, config=None)` |
| **文件** | `data/plugins/emily_agent/main.py` |

### 3.4 消息去重指纹不含 sender_id

| 项 | 内容 |
|----|------|
| **现象** | 同一消息不同 pipeline 阶段 sender_id 可能不同，去重失效 |
| **原因** | 去重 fingerprint 不含 sender_id 字段 |
| **解决** | fingerprint = SHA-256(session_id \| message_text)，不含 sender_id |
| **文件** | `data/plugins/emily_agent/main.py` |

### 3.5 NapCat 端口

| 项 | 内容 |
|----|------|
| **现象** | 连接失败 |
| **原因** | NapCat 端口为 `6199`，地址 `ws://astrbot:6199/ws`（Docker 内部用 service name，非 `host.docker.internal`） |
| **文件** | `napcat/config/onebot11.json` |

## 4. 异步与并发

### 4.1 Sync repo + async service 阻塞事件循环

| 项 | 内容 |
|----|------|
| **现象** | Event loop blocked 警告 |
| **原因** | Repository 全 sync（`with get_session()`），async Service 直接调用 → 阻塞事件循环 |
| **解决** | 用 `asyncio.to_thread()` 包裹 sync repo 调用（项目级模式） |
| **文件** | 所有 `services/*.py`，模式定义在 `plan_task_service.py` |

## 7. 模式切换

### 7.1 `EMILY_*_MODE` 默认值

| 项 | 内容 |
|----|------|
| **现象** | 更改 Docker env 不生效 |
| **原因** | `_resolve_mode()` 有回退逻辑：real 模式但无 LLM client → 自动回退 mock。也是一种安全机制 |
| **注意** | 所有模式默认 `mock`（Phase 0 起始状态）；`real` 需同时有 LLM client 才生效 |
| **文件** | `workitem/workitem_agent.py:_resolve_mode()`, `bootstrap.py:_config_from_env()` |

### 7.2 Mock 模式下 `[Mock 模式]` 前缀

| 项 | 内容 |
|----|------|
| **现象** | Mock 模式下回复前缀 `[Mock 模式]` |
| **说明** | 这是设计意图——提醒用户当前为 Mock 模式，数据不真实 |
| **文件** | `workitem/pipeline/mocks/mock_execution.py` |
