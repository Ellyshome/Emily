## 1. 容器与部署

### 1.1 `__pycache__` 不会自动刷新

| 项 | 内容 |
|----|------|
| **现象** | 修改 Python 代码后重启容器，旧逻辑仍在运行 |
| **原因** | Docker bind-mount 不触发 Python 重编译，`.pyc` 缓存仍是旧字节码 |
| **解决** | 每次代码变更后执行：`docker exec astrbot find /AstrBot/data/plugins/emily_agent -name '__pycache__' -type d -exec rm -rf {} +` |
| **相关** | Windows 宿主机 + Docker Desktop bind-mount 特有问题 |

### 1.2 Git Bash 路径污染 SOP 目录解析

| 项 | 内容 |
|----|------|
| **现象** | `SOPIntentRegistry` 加载 0 份 SOP，全部走 fallback |
| **原因** | `Path(__file__).resolve().parents[2]` 在容器内路径为 `C:/Program Files/Git/app/sops`（Windows PowerShell Git Bash 路径注入）；容器内期望 `/app/sops` |
| **解决** | SOP 目录解析加回退顺序：`/app/sops` → 环境变量 `EMILY_SOP_REPOSITORY_DIR` → dev 路径 `emily-data/sops` |
| **文件** | `agent/intent_registry.py` |

### 1.3 Docker 服务名在宿主机不可达

| 项 | 内容 |
|----|------|
| **现象** | `emys_tester` 连接 `maxkb` 失败 |
| **原因** | `emys_tester` 在宿主机执行，`maxkb` 是 Docker Compose 内部服务名 |
| **解决** | tester 自动替换 `maxkb`→`localhost`（RAG provider URL）；`emily-postgres`→`localhost`（DB 直连） |
| **文件** | `.claude/skills/emy-test/emys_tester.py` |

### 1.4 Windows PowerShell 默认 GBK 中文乱码

| 项 | 内容 |
|----|------|

| **原因** | PowerShell 默认 GBK 编码 |
| **解决** | 预先设置 `$env:PYTHONIOENCODING="utf-8"`；emy-test daemon 模式自行设置编码 |
| **文件** | `.claude/skills/emy-test/cli.py` |

### 1.5 `bootstrap._config_from_env` 缺少 env 映射

| 项 | 内容 |
|----|------|
| **现象** | Docker 设 `EMILY_EXECUTOR_MODE=real` 但 Config 仍为 `mock`；MaxKB RAG 未初始化 |
| **原因** | `_config_from_env()` 的 `env_map` 缺失 10 个 `EMILY_*_MODE` 和 `EMILY_MAXKB_*` 映射 |
| **解决** | 补全 10 个 env 映射（PLANNER/EXECUTOR/GUARDIAN/AUTH/RISK_MODE + MAXKB_*） |
| **文件** | `bootstrap.py` |

### 1.6 新增 Core 写入目录须在 docker-compose 挂载；`restart` 不应用 compose 变更

| 项 | 内容 |
|----|------|
| **现象** | Session 归档 md 文件「没生成」——`emily-data/session_archives/` 空空如也；但日志显示 `SessionArchive header created: /app/session_archives/xxx.md`，容器内 `ls` 也能看到文件 |
| **原因** | ① 新写入路径 `/app/session_archives` 未在 `docker-compose-napcat.yml` 的 emily-core `volumes` 挂载到宿主（对比 `/app/journal` 已挂载所以项目日志可见）。`resolve_data_path` 优先返回容器路径 `/app/session_archives`（父目录 `/app` 存在），文件写进容器可写层，宿主看不到。② `docker compose restart` 不重新读取 compose 文件，volume 变更不生效 |
| **解决** | 在 emily-core `volumes` 增 `- ./emily-data/session_archives:/app/session_archives`，用 `docker compose up -d emily-core`（而非 `restart`）重建容器使挂载生效 |
| **文件** | `docker-compose-napcat.yml`；参照 `infrastructure/paths.py` `resolve_data_path` 的三级探测 |

### 1.7 PowerShell 5.1 读取无 BOM 的 UTF-8 中文 .ps1 脚本报语法错误

| 项 | 内容 |
|----|------|
| **现象** | 执行含中文的 .ps1 脚本（如 `setup_test_env.ps1`）报一堆解析错误：`表达式或语句中包含意外的标记`、`此语言版本中不支持"from"关键字`、`数组索引表达式丢失`、`语句块中缺少右"}"` 等，错误信息里中文显示为乱码（如 `鍏ㄦ櫙鑺傜偣鏍?`）。用 VSCode/Read 工具看文件内容却完全正常 |
| **原因** | PowerShell 5.1 读取**无 BOM** 的 .ps1 文件时默认用系统 ANSI（GBK/CP936）解码。文件实际是 UTF-8，中文字节被 GBK 误读成乱码，乱码中某些字节恰好是 ASCII 语法字符（`(` `)` `?` 等），破坏脚本解析。脚本内 `[Console]::OutputEncoding=UTF8` 只管运行时输出编码，**不影响 PS 读取 .ps1 文件本身的编码** |
| **解决** | 给 .ps1 文件加 UTF-8 BOM（`EF BB BF`）：`[System.IO.File]::WriteAllText($p, $c, [System.Text.UTF8Encoding]::new($true))`。PS 5.1 见 BOM 即按 UTF-8 解码；PowerShell 7+ 默认 UTF-8 无此问题。纯 ASCII 的 .ps1 无 BOM 也能正常读（GBK 与 UTF-8 对 ASCII 字节一致），仅含中文/非 ASCII 的脚本需要 BOM |
| **文件** | `需求/env-test/setup_test_env.ps1`；`scripts/backup.ps1`；`需求/环境布置/scripts/reset_emerald.ps1` |

### 1.8 Git Bash 路径转换污染 docker exec 容器内路径

| 项 | 内容 |
|----|------|
| **现象** | `docker exec maxkb python /opt/maxkb-app/apps/manage.py shell -c "..."` 报 `can't open file '/opt/maxkb-app/C:/Program Files/Git/opt/maxkb-app/apps/manage.py': [Errno 2] No such file or directory` |
| **原因** | Windows Git Bash（MSYS2）自动将以 `/` 开头的命令参数转换为 Windows 路径（path mangling），容器内 Linux 绝对路径被破坏成 `C:/Program Files/Git/opt/...` |
| **解决** | 命令前加 `MSYS_NO_PATHCONV=1` 环境变量禁用路径转换：`MSYS_NO_PATHCONV=1 docker exec maxkb python /opt/maxkb-app/apps/manage.py ...` |
| **对比** | 1.2 是容器内 Python `Path(__file__).resolve().parents[N]` 被 Git Bash 注入；本条是宿主机 `docker exec` 传参时被转换。两者根因相同（MSYS2 path mangling），表现不同 |

## 2. 数据库

### 2.1 FK 列语义陷阱：`conversation_id` 是 UUID 非业务串

| 项 | 内容 |
|----|------|
| **现象** | `create_outbound()` 和 `AgentReasoningRepository` 写入消息报 FK 违规 |
| **原因** | `messages.conversation_id` 列是 FK→`conversations.id`（UUID string），但业务层用的是 `conversation_id` 字符串（如 "group_888"）。需要先通过 `_resolve_conversation_id()` 把业务 ID 转为 UUID。 |
| **解决** | `MessageRepository.create_from_standard()` 已正确（它通过 `conv.id` 访问 UUID）；`create_outbound()` 和 `AgentReasoningLog` 写入前需显式解析 |
| **安全模式** | 始终用 `from_standard()` 路径（正确处理 FK），避免直接构造 ID |
| **文件** | `repositories/message_repo.py`, `agent_reasoning_repo.py` |

### 2.2 `Base.metadata.create_all()` 不给已有表加索引/列

| 项 | 内容 |
|----|------|
| **现象** | 新增列和索引在已有环境上不生效 |
| **原因** | `create_all()` 只建不存在的表和列——对已存在表的新增字段和索引无效 |
| **解决** | `init_db()` 现已内置 `_ensure_columns()` 自动补齐已有表的缺失列（启动时检测 information_schema，缺失列自动 ALTER TABLE ADD COLUMN）。如遇特殊情况仍需手动 DDL |
| **文件** | `infrastructure/database/session.py:init_db()` → `_ensure_columns()` |

### 2.3 PostgreSQL advisory lock 是 session 级

| 项 | 内容 |
|----|------|
| **现象** | `PlanTaskScheduler._tick()` 的 advisory lock 未阻止并发执行 |
| **原因** | PG advisory lock 绑定到 session；`_acquire()` 返回后 session 关闭，lock 自动释放，`_tick()` 失去保护 |
| **解决** | 使用 `get_session_raw()` 手动管理 session 生命周期，保持 session 在 `_tick()` 期间不关闭 |
| **文件** | `services/plan_task_scheduler.py`, `infrastructure/database/session.py` |

### 2.4 `expire_on_commit=False` 避 DetachedInstanceError

| 项 | 内容 |
|----|------|
| **现象** | ORM 对象在 session 外访问属性报 `DetachedInstanceError` |
| **原因** | SQLAlchemy 默认在 commit 后 expire 所有属性 |
| **解决** | `sessionmaker(expire_on_commit=False)` —— 全局禁用 expire，对象可在 session 外安全访问 |
| **文件** | `infrastructure/database/session.py` |

### 2.5 时间戳为 ISO8601 字符串（非 DB datetime）

| 项 | 内容 |
|----|------|
| **现象** | 应用层比较时间戳行为与 DB 原生 datetime 不同 |
| **原因** | 所有时间戳列定义为 `String` 类型，存储 ISO8601 字符串（如 `"2026-06-26T09:30:00+08:00"`），由 `_utc_now()` / `_beijing_now()` 生成 |
| **解决** | 应用层字符串比较需注意时区（UTC vs Beijing +08:00）；字符串排序与 ISO8601 字典序一致 |

### 2.13 时间戳 aware/naive 混用致 `TypeError: can't compare offset-naive and offset-aware datetimes`

| 项 | 内容 |
|----|------|
| **现象** | `SchedulerEngine` 每个 tick 报 `TypeError: can't compare offset-naive and offset-aware datetimes`，调度器完全停摆 |
| **原因** | `engine._is_due` 中 `now = datetime.now(timezone.utc)`（aware），而 `next_execution_at` 由 [db_seeds](../需求/env-test/010_seed_runtime_data.sql) 存成无 offset 的北京时间字符串（如 `2026-07-21T09:00:00`），`datetime.fromisoformat()` 解析得 naive；aware 与 naive 直接 `>=` 比较即抛 TypeError |
| **解决** | 解析后若 `next_dt.tzinfo is None`，按北京时间 `_BEIJING_TZ` 补 tzinfo 再与 UTC `now` 比；同时接入既有 `has_period_execution` 幂等（`_execute_job` 起始检查同周期已有执行记录则跳过），避免 `next_execution_at` 不更新时每 tick 重复触发 |
| **文件** | `scheduler/engine.py`（`_is_due` + `_execute_job`）、`repositories/scheduler_repo.py`（`has_period_execution` 改任意状态）、`scheduler/service.py`（`has_executed_in_period`） |
| **延伸** | 该 TypeError 实际掩盖了调度器三处半接线（已修复，见 `需求/0722调度器半接线修复计划.md`）：①`_execute_job` 不更新 execution 状态（停留 PENDING）→ 现走 PENDING→RUNNING→SUCCESS/FAILED 状态流转，No-handler 从静默 return 改为抛错落 FAILED；②无 reschedule（`next_execution_at` 永不更新）→ 新增 `scheduler/next_execution.py`（croniter + 极简兜底）按北京时间解释 cron 重算 next_execution_at，写入 UTC-aware ISO；③3 个种子作业 action_type 旧残留无 handler → 种子 SQL + 迁移脚本 `需求/env-test/012_fix_scheduler_jobs.sql` 对齐，JOB-003 因 files 表无过期字段先 INACTIVE。`has_period_execution` 随之改回 SUCCESS-only（reschedule 为主闸门，幂等仅兜底失败重试） |
| **Reload 坑** | `docker compose restart` 在本机 `:ro` bind-mount 下未可靠重载代码（uvicorn 仍跑旧字节码，`python -c` 单跑却已是新码）；改用 `docker compose up -d emily-core --force-recreate` 重建容器才生效 |

### 2.14 PeriodicNodeHandler 误用 CreateTaskNodeCommand 致 `create_node` 报 `no attribute 'node_id'`

| 项 | 内容 |
|----|------|
| **现象** | 调度器 JOB-001 执行报 `'CreateTaskNodeCommand' object has no attribute 'node_id'`，节点未创建 |

| **文件** | `scheduler/jobs/periodic_node.py`、`services/node_batch.py`（`_generate_node_id`→公开 `generate_node_id`）、`emily_core/__init__.py`（初始化顺序：node 先于 scheduler） |

### 3.4 消息去重指纹不含 sender_id

|----|------|
| **现象** | 日志有 `ProgressHook[progress.processing] sent: 收到，正在为你处理...`，但 IM 端/插件 SSEListener 始终收不到该前导消息，且无任何报错 |
| **原因** | `_progress_sender` 是 `EmilyCore._collect_injected_services` 注入的全局闭包，只接收 `text`，发布 `{"content": text}` **缺 `conversation_id`**。插件 `SSEListener._handle_progress` 用 `data.get("conversation_id", "")`（得到 `""`）查 `_event_registry`（key 是真实 conv_id）→ 返回 `None` → `if event is not None and text:` 不成立 → **静默跳过**，既不发也不报错。`reply`/`session_closed` 事件因带了 `conversation_id` 不受影响 |
| **解决** | `PipelineBUS.run` 开头为每个 `BusContext` 注入 per-message `progress_sender` 闭包到 `context.baggage`（捕获 `context.message.conversation_id`，发布 `{"content": text, "conversation_id": cid}`）。ProgressHook 原设计就支持 `baggage.get("progress_sender", 实例属性)` 优先取 baggage，全局闭包退为兜底。`PipelineBUS` 需在构造时持有 `outbound_bus`（`build_default(outbound_bus=...)`） |
| **文件** | `workitem/pipeline/bus.py`, `workitem/pipeline/hook.py`, `emily_core/__init__.py` |

### 6.3 MaxKB 登录验证码机制（fail_count 触发）

| 项 | 内容 |
|----|------|
| **现象** | `maxkb_provider.py` 的 `_login()` 登录 MaxKB 返回 `{"code": 1005, "message": "验证码是必填项", "data": null}`，RAG 检索链路在登录阶段即失败 |
| **原因** | MaxKB v2.10.2 登录验证码机制：失败登录次数 `fail_count >= max_attempts`（默认 1）时强制要求验证码。`maxkb_provider.py:_login()` 只传 `{username, password}`，未传 `captcha` 字段。只要有过 1 次失败登录（密码错/网络抖动/token 过期重试），`fail_count` 累积，后续所有登录都被验证码卡住。失败计数 10 分钟过期（`record_login_fail` expire=600） |
| **解决** | ① 保持密码正确 + `fail_count=0`（登录成功不增计数，不触发验证码）；② 清除失败计数：`MSYS_NO_PATHCONV=1 docker exec maxkb python /opt/maxkb-app/apps/manage.py shell -c "from django.core.cache import cache; from common.constants.cache_version import Cache_Version; sv,gk=Cache_Version.SYSTEM.value; [cache.delete(gk(k),version=sv) for k in ['system_admin','system_admin_lock','system_admin_lock_count']]"`；③ 永久关闭验证码：设 `auth_setting.max_attempts=-1`（但 auth_setting 模型默认未启用，需 MaxKB 企业版许可） |
| **长期风险** | maxkb_provider.py 处理不了验证码——任何一次失败登录都会让 RAG 检索卡死直到计数过期（10 分钟）。建议改造 `_login()` 传 `captcha` 字段或增加验证码检测容错 |
| **文件** | `providers/rag/maxkb_provider.py:_login()`；MaxKB 验证码逻辑在容器内 `/opt/maxkb-app/apps/users/serializers/login.py:_need_captcha` |

### 6.4 maxkb_provider.py `_login()` 对 `data: null` 崩溃

| 项 | 内容 |
|----|------|
| **现象** | `_login()` 在 MaxKB 返回错误响应时抛 `AttributeError`（异常消息可能为空，难排查） |
| **原因** | `data.get("data", {}).get("token")`——当 MaxKB 返回 `{"code": 1005, "data": null}` 时，`data.get("data", {})` 返回 `None`（key 存在但值为 None，`.get` 默认值不生效），随后 `None.get("token")` 抛 `AttributeError: 'NoneType' object has no attribute 'get'` |
| **解决** | 改为 `(data.get("data") or {}).get("token")`，或先检查 `data.get("code") == 200` 再取 token |
| **文件** | `providers/rag/maxkb_provider.py:_login()`（line 85-86） |

### 6.5 `LocalFileRagProvider.__init__` parents 索引越界

| 项 | 内容 |
|----|------|
| **现象** | `LocalFileRagProvider()` 实例化报 `IndexError: list index out of range`（`parents[7]` 越界） |
| **原因** | `Path(__file__).resolve().parents[7]` 越界——注释说路径链 5 层（rag→providers→emily_core→emily-core→Emily），对应 `parents[4]`，但代码写 `parents[7]`。且 `project_root` 无条件计算，即使传了 `search_dir` 也越界 |
| **解决** | 改为延迟计算：`if search_dir: self._search_dir = Path(search_dir) else: project_root = Path(__file__).resolve().parents[4]; self._search_dir = project_root / _DEFAULT_SEARCH_DIR` |
| **未暴露原因** | LocalFileRagProvider 在生产中从未被实例化（`bootstrap.py` 只创建 MaxKBRagProvider，`rag_provider=None` 时不回退到 LocalFile），死代码路径 bug 长期隐藏 |
| **文件** | `providers/rag/local_fallback.py:__init__` |

### 6.6 MaxKB 管理员密码重置

| 项 | 内容 |
|----|------|
| **现象** | `admin/maxkb123`（MaxKB 官方默认密码）登录失败，返回"用户名或密码不正确" |
| **原因** | MaxKB 部署时密码可能被修改，或该版本默认密码非 maxkb123 |
| **解决** | 用 Django manage.py 重置：`MSYS_NO_PATHCONV=1 docker exec maxkb python /opt/maxkb-app/apps/manage.py shell -c "from users.models import User; u=User.objects.get(username='admin'); u.set_password('maxkb123'); u.save()"`。重置后需清除失败计数（见 6.3），否则验证码仍触发 |

| **凭据** | MaxKB v2.10.2：用户名 `admin`（固定），密码重置后为 `maxkb123`；WebUI `http://localhost:8080` |
| **文件** | MaxKB 容器 `/opt/maxkb-app/apps/manage.py` |
