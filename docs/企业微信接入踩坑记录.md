# 企业微信自建应用接入踩坑记录

> Emily V1.0 通过 AstrBot 接入企业微信自建应用的完整调试过程。
> 时间：2026-08-05 | 操作人：Emily Team

---

## 架构链路

```
企业微信 App → AstrBot wecom 适配器 → emily_agent 插件 → emily-core → PostgreSQL
```

共涉及 3 个配置文件、4 个企业微信后台参数、7 个踩坑点。

---

## 一、配置清单

### 1.1 企微后台获取四个参数

| 参数 | 位置 | 说明 |
|------|------|------|
| `corpid` | 「我的企业」→ 企业信息 → 企业 ID | `ww` 开头 |
| `secret` | 「应用管理」→ 点击应用 → 顶部 AgentId 下方「查看」 | 注意：每个 Agent 有独立 secret |
| `token` | 应用详情页 →「接收消息」→「设置 API 接收」→ 随机获取 | 回调签名验证 |
| `encoding_aes_key` | 同上，另一个随机获取按钮 | 43 位，消息加解密 |

### 1.2 AstrBot 配置文件

**文件路径**：`/home/data/cmd_config.json`

在 `"platform": []` 数组中添加：

```json
{
  "type": "wecom",
  "id": "Emily服务系统",
  "enable": true,
  "corpid": "ww1994648105a74a7c",
  "secret": "你的应用Secret",
  "token": "你的回调Token",
  "encoding_aes_key": "你的EncodingAESKey",
  "port": 6199,
  "callback_server_host": "0.0.0.0",
  "unified_webhook_mode": true
}
```

**关键说明**：
- AstrBot v4 通过 `cmd_config.json` 管理平台配置，不需要 WebUI
- `unified_webhook_mode: true` 会将所有平台 webhook 收归 Dashboard 端口（6185），生成唯一 UUID 路径
- 修改配置后需重启 AstrBot：`docker compose restart astrbot`

## 二、踩坑全记录

### 坑 1：统一 Webhook 模式下的回调 URL 端口

**现象**：企微后台填入 `http://IP:6199/callback/command` 后验证失败。

**原因**：启用 `unified_webhook_mode` 后，回调 URL 不再是独立端口 6199，而是 Dashboard 端口 6185 带 UUID 路径。

**定位方法**：查看 AstrBot 启动日志：
```
🔗 机器人平台 Emily服务系统(企业微信) 已启用统一 Webhook 模式
📍 Webhook 回调地址: 
   ➜  http://<your-ip>:6185/api/platform/webhook/17dc2ce13b734abb
```

**解决**：使用日志中打印的实际 Webhook URL。

---

### 坑 2：域名 ICP 备案与回调 URL

**现象**：担心未备案域名无法用于企微回调验证。

**结论**：不影响。回调 URL 使用公网 IP 而非域名时，不需要 ICP 备案。企微可信域名验证（OAuth/JS-SDK 网页授权用）与消息回调是两个独立系统，消息机器人不需要配可信域名。

---

### 坑 3：ECS 安全组端口放行

**需要放行的端口**：

| 端口 | 用途 | 方向 |
|------|------|------|
| 6185 | AstrBot Dashboard + 统一 Webhook | 入方向 TCP |
| 6199 | AstrBot 独立 Webhook（备用） | 入方向 TCP |
| 80 | 域名验证文件 HTTP Server（如需要） | 入方向 TCP |

### 坑 4：emily_agent 插件加载失败 —— JSON 格式错误

**现象**：AstrBot 重启后日志报错：
```
ValueError: 插件配置 schema 不是有效的 JSON: .../_conf_schema.json (line 24, column 23)
```

**原因**：`_conf_schema.json` 第 24 行的 hint 字段中包含 ASCII 双引号 `"`（原意应为中文弯引号 `""`），导致 JSON 解析失败：
```json
"hint": "开启后用户会收到"正在查询知识库..."等进度提示"
```
此处 `"正在查询知识库..."` 的引号被 JSON 解析器当作字符串结束符。

**修复**：将内部引号改为中文书名号 `「」`：
```json
"hint": "开启后用户会收到「正在查询知识库...」等进度提示"
```

---

### 坑 5：emily-core 数据库初始化失败 —— pgvector 扩展未启用

**现象**：
- emily-core 接收消息后返回 HTTP 500
- 日志：`type "vector" does not exist` / `relation "users" does not exist`
- 数据库 0 张表

**原因**：PostgreSQL 容器（`pgvector/pgvector:pg16`）虽然镜像包含 pgvector，但扩展需要手动启用。`CREATE TABLE knowledge_chunks(...embedding VECTOR(1024)...)` 因找不到 `vector` 类型而失败，导致 `init_db()` 整个回滚，58 张表一张都没建。

**修复**：
```sql
CREATE EXTENSION IF NOT EXISTS vector;
```
然后重启 emily-core 触发数据库初始化。

**教训**：emily-core 启动后应检查 `docker logs emily-core | grep "Database initialized"` 确认表数量。

---

### 坑 6：自动注册用户失败 —— `creator_id` NOT NULL 无默认值

**现象**：消息到达 emily-core 后始终报 `ValueError: user_id 不能为空`，且日志中无 `user binding failed` 警告。

**定位过程**：
1. 发现企微消息成功到达 AstrBot（`解析成功: TextMessage`）✅
2. emily_agent 成功转发到 emily-core ✅
3. emily-core `handle_message()` 中 `user_id` 始终为空
4. 日志中没有任何 user binding 相关日志 —— 说明异常被 try/except 吞掉后 `logger.warning()` 没有正常输出（日志缓冲问题）

**根因**：`UserRepository.create_user_and_bind()` 创建 User 时只传了 `username`，但 `users` 表的 `creator_id` 字段为 `NOT NULL` 且**无默认值**。INSERT 失败导致自动注册异常，被上层 catch 后 `user_id` 保持空字符串。

**修复**（文件：`emily-core/emily_core/repositories/user_repo.py`）：
```python
# 修复前
user = User(username=im_display_name or im_user_id)

# 修复后
new_id = str(uuid.uuid4())
user = User(
    id=new_id,
    username=im_display_name or im_user_id,
    creator_id=new_id,  # 自注册用户：creator = 自身
)
```

**教训**：
- 绑定了 `:ro` 的 Docker bind-mount 下，修改代码需在宿主机进行
- 修改后需清除 `__pycache__` 再重启容器

### 坑 7：Docker 日志缓冲

**现象**：emily-core 处理请求返回 500，但 `docker logs` 查不到对应错误日志。

**原因**：Python 日志输出到 stderr 存在缓冲，高频率 scheduler 错误（每秒一次）可能加重缓冲延迟。

**排查技巧**：发请求后 `sleep 2-3` 再查日志，或使用 `docker logs --since 30s` 缩小范围。

---

### 坑 8：接管判断中的 `conversation_type` 字段

**现象**：不带 `conversation_type` 的测试消息返回 204（不接管），带 `"private"` 的返回 500（接管后处理失败）。

**原因**：`DomainTakeoverService.decide()` 中：
- `conversation_type == "private"` → `takeover=True` → 进入完整处理链路
- `conversation_type == ""` → 不走 `private` 分支 → `takeover=False` → 直接返回 204

这不是 bug，但调试时容易产生"为什么有时候 204 有时候 500"的困惑。

---

### 坑 9：企微 Secret 与 AgentID 不匹配

**现象**：emily-core 正常处理消息并返回回复，但企微端收不到消息。AstrBot 日志：
```
Error code: 301002, message: not allow operate another agent with this accesstoken
```

**原因**：`secret` 是每个自建应用独立的。消息从 AgentID `1000003` 发来，但 `cmd_config.json` 里的 `secret` 属于 AgentID `1000002`。企微 API 拒绝跨 Agent 操作。

**修复**：确认正确的 AgentID → 在企微后台获取对应的 secret → 更新 `cmd_config.json` → 重启 AstrBot。

---

### 坑 10：企微 IP 白名单

**现象**：更换正确 secret 后，发送消息仍失败：
```
Error code: 60020, message: not allow to access from your ip, from ip: 121.41.230.45
```

**原因**：企微自建应用的 API 调用（如发送消息）要求服务器 IP 在白名单中。

**修复**：企微管理后台 →「应用管理」→ 点进应用 →「企业可信 IP」→ 添加服务器公网 IP `121.41.230.45`。实时生效，无需重启。

## 三、问题速查表

| 错误码/现象 | 原因 | 解决 |
|------------|------|------|
| openapi 回调地址请求不通过 | 回调 URL 端口或路径错误（统一 Webhook 模式） | 查 AstrBot 日志获取正确 URL |
| type "vector" does not exist | pgvector 扩展未启用 | `CREATE EXTENSION vector;` |
| relation "users" does not exist | 数据库初始化失败（上一条原因） | 先修 pgvector，重启 emily-core |
| user_id 不能为空 | `creator_id` NOT NULL 导致自注册失败 | 修 `user_repo.py` 补全 `creator_id` |
| Error 301002 | Secret 与 AgentID 不匹配 | 核对 secret 所属 AgentID |
| Error 60020 | IP 未加入白名单 | 企微后台加「企业可信 IP」 |
| 回调 URL vs 可信域名混淆 | 两套独立系统 | 消息机器人只需回调 URL，不需要可信域名 |
| 域名未备案能否用 | 用 IP 直连即可 | 不影响消息回调 |

## 四、日常运维命令

```bash
# 重启 AstrBot（配置变更后）
docker compose -f /home/docker-compose.yml restart astrbot

# 重启 emily-core（代码变更后，记得先清 pycache）
docker exec emily-core find /app -name '__pycache__' -type d -exec rm -rf {} +
docker compose -f /home/docker-compose.yml restart emily-core

# 查看 AstrBot 启动后的 Webhook URL
docker logs astrbot 2>&1 | grep "Webhook 回调地址"

# 查看最近消息流转
docker logs astrbot --since 1m 2>&1 | grep -E "解析成功|返回|ERROR"
docker logs emily-core --since 1m 2>&1 | grep -E "ERROR|WARNING|user=|intent"

# 确认数据库状态
docker exec emily-postgres psql -U emily -d emily -c "SELECT count(*) FROM users;"
docker exec emily-postgres psql -U emily -d emily -c "SELECT * FROM user_im_bindings;"

# 验证配置文件 JSON 合法性
python3 -c "import json; json.load(open('/home/data/cmd_config.json')); print('OK')"
```
