## 1. 进化闭环（聚合壳：evolution.py）

**聚合壳**：[scripts/evolution.py](../scripts/evolution.py) — 按调度顺序串联各独立脚本的核心函数，不含业务逻辑，仅做编排。

**子命令**：`daily` / `weekly` / `morning` / `validate` / `full`

```bash
uv run python scripts/evolution.py daily --date 2026-07-21           # 日度进化闭环
uv run python scripts/evolution.py daily --date 2026-07-21 --days 7  # 7 天汇总模式
uv run python scripts/evolution.py weekly --end-date 2026-07-21      # 周度规则归纳+补丁
uv run python scripts/evolution.py morning --date 2026-07-21         # 生成晨报
uv run python scripts/evolution.py validate                          # 验证所有已应用的补丁
uv run python scripts/evolution.py full --date 2026-07-21            # daily + morning
```

> `daily` 内部流程：metrics → anomaly → insight  
> `weekly` 内部流程：rules → patch  
> `full` = daily + morning

### 1.1 evolution_metrics.py — 指标聚合

**职责**：从 10 个数据源采集指标，输出人类可读报告。

**调度归属**：双重 — ① 调度器 `DailyInsightHandler` → `InsightGenerator` import 调用；② CLI 手动执行

```bash
uv run python scripts/evolution_metrics.py --date 2026-07-21             # 单日指标
uv run python scripts/evolution_metrics.py --date 2026-07-21 --days 7    # 7 天汇总
uv run python scripts/evolution_metrics.py --date 2026-07-21 --preview   # 预览（不写 DB）
uv run python scripts/evolution_metrics.py --date 2026-07-21 --source pipeline  # 只看管道指标
uv run python scripts/evolution_metrics.py --date 2026-07-21 --json      # JSON 输出
```

| 参数 | 说明 |
|------|------|
| `--date/-d` | 日期（必需），YYYY-MM-DD |
| `--days` | 汇总天数，默认 1 |
| `--source/-s` | 限定数据源：pipeline / sop_routing / feedback / rag / business_events / session_lifecycle / agent_reasoning / tool_calls / project_nodes / cognition_drift |
| `--preview` | 预览模式（替代 `--dry-run`） |
| `--json` | JSON 格式输出 |
| `--db-url` | 数据库连接（可选，默认走环境变量） |

**10 个数据源**：pipeline、sop_routing、feedback、rag、business_events、session_lifecycle、agent_reasoning、tool_calls、project_nodes、cognition_drift

### 1.6 evolution_apply.py — 补丁审批/应用/回滚

**职责**：审核 + 应用进化补丁，支持回滚。

**调度归属**：纯手动

```bash
uv run python scripts/evolution_apply.py list --status DRAFT             # 列出草稿补丁
uv run python scripts/evolution_apply.py approve --patch-no EP-001       # 审批通过
uv run python scripts/evolution_apply.py reject --patch-no EP-001 --reason "风险过高"  # 驳回
uv run python scripts/evolution_apply.py apply --patch-no EP-001         # 应用补丁
uv run python scripts/evolution_apply.py apply --patch-no EP-001 --dry-run  # 预览应用
uv run python scripts/evolution_apply.py rollback --patch-no EP-001      # 回滚补丁
uv run python scripts/evolution_apply.py status --patch-no EP-001        # 查看补丁状态
```

| 子命令 | 说明 |
|--------|------|
| `list` | 列出补丁（`--status` 过滤：DRAFT / APPROVED / APPLIED / REJECTED / ROLLED_BACK） |
| `approve` | 审批通过（`--patch-no` 必需） |
| `reject` | 驳回（`--patch-no` + `--reason`） |
| `apply` | 应用补丁（支持 `--dry-run`） |
| `rollback` | 回滚（支持 `--dry-run`） |
| `status` | 查看补丁详情 |

## 4. 全景节点管理

### 4.1 manage_nodes.py — 全景节点管理 CLI

**职责**：全景节点图的增删改查 CLI 薄壳。核心逻辑在 [emily_core/services/node_batch.py](../emily-core/emily_core/services/node_batch.py) 和 `node_batch_update.py`。

**调度归属**：纯手动

**7 个子命令**：

```bash
# 创建节点（YAML 文件定义节点树）
uv run python scripts/manage_nodes.py create --file nodes.yaml --dry-run
uv run python scripts/manage_nodes.py create --file nodes.yaml

# 更新节点字段
uv run python scripts/manage_nodes.py update --file updates.yaml --dry-run
uv run python scripts/manage_nodes.py update --file updates.yaml

# 激活节点
uv run python scripts/manage_nodes.py activate --node-ids SG-001,SG-002 --operator-id <UUID>
uv run python scripts/manage_nodes.py activate --node-ids SG-001 --operator-id <UUID> --dry-run

# 废弃节点
uv run python scripts/manage_nodes.py discard --node-ids SG-001 --operator-id <UUID>
uv run python scripts/manage_nodes.py discard --node-ids SG-001 --operator-id <UUID> --dry-run

# 批量更新成果进度
uv run python scripts/manage_nodes.py progress --file progress.yaml --dry-run
uv run python scripts/manage_nodes.py progress --file progress.yaml

# 文件关联
uv run python scripts/manage_nodes.py link-files --file links.yaml --dry-run

# 查询节点
uv run python scripts/manage_nodes.py query --project-id ECOCITY-26
```

| 子命令 | 说明 | `--dry-run` |
|--------|------|-------------|
| `create` | YAML 文件批量创建节点树 | ✅ |
| `update` | YAML 文件批量更新节点字段 | ✅ |
| `activate` | 激活节点（--node-ids 逗号分隔） | ✅ |
| `discard` | 废弃节点 | ✅ |
| `progress` | YAML 文件批量更新成果进度 | ✅ |
| `link-files` | YAML 文件关联文件到节点 | ✅ |
| `query` | 按 project-id 查询节点树 | 无需（只读） |

### 6.4 rag_dry_run.py — RAG 基座 dry-run 测试

**职责**：直接调用生产入口 `handle_knowledge_search`，绕过 LLM 和 4 节点管道，打 MaxKB hit_test 输出原始检索结果。保证"手动能跑通 ⟹ 调用能跑通"。

**调度归属**：纯手动（调试/诊断用）

```bash
uv run python scripts/rag_dry_run.py "放线验收标准"                               # 默认检索
uv run python scripts/rag_dry_run.py "施工工艺" --top-k 8                        # 指定条数
uv run python scripts/rag_dry_run.py "钢筋间距" --stage 施工建设 --role 工程部经理 # 过滤
uv run python scripts/rag_dry_run.py --probe                                     # 仅检查配置+连通性
```

| 参数 | 说明 |
|------|------|
| `query`（位置参数） | 自然语言查询（`--probe` 模式可省略） |
| `--top-k` | 返回条数，默认 `config.kb_top_k`（5），handler 内限上限 10 |
| `--stage` | 按项目阶段过滤 |
| `--role` | 按岗位过滤 |
| `--probe` | 仅检查配置 + 连通性，不发检索请求 |
| `--config` | 指定 core_config.json 路径（默认多级回退） |

> **设计原则**：测试入口 = 生产入口。脚本调 `handle_knowledge_search(params, rag_provider)`——与 RealExecutor 框架直调同一个函数（[knowledge_search_tool.py:59](../emily-core/emily_core/tools/knowledge_search_tool.py#L59)）。不绕过 handler 直接调 Provider，保证测试路径与生产路径一致。配置加载复用 `bootstrap._config_from_env`，与 `bootstrap.init()` 路径完全一致。RAG 基座调用失败即反馈失败，不做本地回退兜底（与生产行为一致）。

### 6.5 check_tools_consistency.py — 工具一致性检查

**职责**：验证 BusinessFlowToolRegistry 与 Skill YAML / tool_registry 表的一致性。检查工具名存在性、参数 schema 匹配、空 schema、表同步。核心逻辑可 import，供 self_check 启动集成。

**调度归属**：纯手动（开发者改完 Skill YAML / 工具后验证）+ self_check 启动集成（快速检查）

```bash
uv run python scripts/check_tools_consistency.py              # 全量检查（含 tool_registry 表）
uv run python scripts/check_tools_consistency.py --json       # JSON 输出
uv run python scripts/check_tools_consistency.py --no-tool-registry  # 跳过 DB 检查
```

| 参数 | 说明 |
|------|------|
| `--skill-dir` | Skill YAML 目录（默认多级回退：/app/skills → emily-data/skills） |
| `--json` | JSON 格式输出 |
| `--no-tool-registry` | 跳过 tool_registry 表检查（不连 DB） |

退出码：0=无 fatal；1=有 fatal（便于 CI 集成）。

> **设计原则**：方案 B——独立脚本（全量）+ self_check 集成（启动快速检查），复用现有基础设施。砍掉语义级检查（V6/V7/V9）和独立启动自检。核心逻辑在 `emily_core/infrastructure/tools_consistency.py`，可被 self_check import 复用。
