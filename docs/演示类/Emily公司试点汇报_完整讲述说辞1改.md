Emily公司试点汇报——完整讲述说辞与演示流程
定位：轻松科普式叙事 + 现场产品演示 + 企业试点提案
目标听众：地产公司高层管理团队
建议时长：20～25分钟
核心目标：让听众理解“为什么需要企业自己的AI”，相信Emily已经具备试点基础，并愿意提供真实业务场景、数据规则和基础经费进行试点。

==================================================
一、整体叙事主线
==================================================

不要按照传统“背景—产品—技术—预算”的汇报方式展开，而采用一条逐渐深入的认知路径：

生活小场景
→ 通用AI为什么有时“不知道”
→ 企业真正需要的是进入业务环境的AI
→ Emily首次亮相：第一眼像“杭小东”，是装进企业信息的AI
→ 热梗一“养虾”：从“个人养虾”到“团队养虾”——Emily是团队共养的数字同事
→ 热梗二“蒸馏同事”：Emily能把做项目过程中积累的经验留下来
→ 项目记忆会随人走：上万张照片、群聊记录，别人接不了手
→ 现场问Emily一个真实地产项目
→ 从“会回答”到“记住项目”
→ 从个人助手到团队记忆中枢
→ 从知识沉淀到企业能力沉淀
→ 为什么它能做到：全景节点 + 企业规则/SOP + 工具/插件
→ Emily当前做到什么
→ 真正缺什么：公司的数据、规则和真实项目
→ 建议低成本试点
→ 请求公司提供试点条件

全程避免一开始堆砌“Agent、RAG、向量数据库、状态机”等技术名词。
技术只在听众已经产生兴趣之后，用来解释“为什么Emily不是普通聊天机器人”。

==================================================
二、开场：杭州东站出站口
预计2分钟
目的：用一个生活场景，让听众自己发现“通用AI也有不知道的东西”。
==================================================

【页面1：标题页】
说：
“今天不准备按照传统方式给大家汇报一个AI项目。
我想先从一个特别小的事情讲起。”

“而且这个事情可能大家都遇到过。”

切入下一页。

【页面2：去杭州东站接人】
说：
“前几天我去东站接朋友，他告诉我了车次，但东站有十几个出站站台，我不知道该去哪个口等人。我觉得这事可以问豆包试试”
“于是我问它：GXXXX这个车次，从杭州东站哪个站台出？“

“然后我得到了这样一个回复：

```
我无法回答这个问题，站台编号：动态不固定，调度会变更，纸质车票/12306看不到固定站台，必须到站看大屏、站台广播才知道实际站台。
 
> 提示：可以访问微信公众号‘杭小东’获取进一步服务信息。或直接看站内公告“大屏”，列车进站前几分钟才会刷新真实站台。
```
“
停顿。

“这就有点奇怪了。
现在的AI不是已经知道很多东西了吗？”

【页面3：为什么AI不知道】
说：
“后来你会发现，这其实不是它聪明不聪明的问题。”

“杭州东站有几个进站口、车站怎么走，这些都是公开信息。
但是某一个具体车次今天到底从哪个出站口出来，可能是车站内部根据当天实际情况实时调度的。”

“但具体一趟列车从哪个站台出，是车站内部调度信息，实时更新调整。
它存在于车站自己的业务系统和现场运营里面。不在固定可查的公开数据里”

“后来我扫码实用站内的‘杭小东’，进行同样的提问，不但查到了对应的站台，甚至根据我的位置给出了详细的电子路书引导我找到正确位置”

总结：
“这其实揭示了一个很重要的事情：

AI知道多少，和它有没有进入一个具体的业务环境，是两回事。”

==================================================
三、从车站切到地产
预计2分钟
目的：让听众理解“行业垂直AI”的必要性。
==================================================

【页面4：如果换成地产公司】
说：
“我们把这个场景换成地产公司，其实完全一样。”

“比如问AI：
‘大树移栽需要注意什么？’”

“豆包、ChatGPT这类通用AI，完全可以回答，而且可能回答得还不错。”

“但是我换一个问题。”

“‘蓝城对大乔木移栽的验收标准是什么？规范要求体现在哪个文件里？’”

停顿。

“这时候它就不知道了。”

继续：
“如果再问：
‘我们XX项目今年5月份那次乔木移栽出现问题，当时是怎么处理的？’”

“这个问题，通用AI更不可能知道。”

总结：
“所以企业真正缺的，很多时候不是一个更聪明的AI。”

“而是一个真正进入公司业务环境的AI。”

四、Emily首次亮相：它像“杭小东”，但不止是“杭小东”
预计2分钟
目的：让Emily在铺垫完成后立即登场；先让听众觉得“这不就是企业版杭小东吗”，再用两个热梗拉开它的两个重要方向。
==================================================

【页面5：Emily是什么】
说：
“其实，这个方向我们已经动手做了。
我们做了一个AI，叫Emily。”

“简单说，Emily把公司自己的信息装了进去：
制度、标准、历史项目、业务规则。”

“所以第一眼看过去，Emily和‘杭小东’有点像——”

停顿。
“只不过杭小东装的是杭州东站的信息，
Emily装的是我们公司自己的信息。”

“如果只是这样，那Emily顶多算一个‘企业版杭小东’。”

“但Emily真正重要的，还有两个方向。
这两个方向，正好可以用最近大家常说的两个热梗讲清楚：
一个叫‘团队养虾’，一个叫‘蒸馏同事’。”

切入下一页。

==================================================
五、热梗一：“养虾”——从“个人养虾”到“团队养虾”
预计2分钟
目的：先讲清流行的“养虾”本质是单用户行为、存在短板；再引出Emily用“团队养虾”增强能力、大幅降低短板。
==================================================

【页面6：大家都在“养虾”】
说：
“第一个热梗，叫‘养虾’。
这两年很多人突然开始‘养虾’，养的是OpenClaw这一类可以长期运行、持续调用工具的AI Agent。”

“为什么大家会觉得有意思？
因为它不是一个‘问完就结束’的搜索框，
而是可以放在身边长期运行——
今天记一点东西，明天调一个工具，后天完成一个任务。”

停顿。
“但大家注意，
现在流行的‘养虾’，其实是‘个人养虾’：
一个人养一个AI，它只服务于这一个人。”

“个人养虾有一个天然的短板：
它记住的，只是你一个人喂给它的东西。”

“你一个人学会的东西，别人看不到，也用不上。
每个人都各养各的，信息还是分散的。”

“Emily要做的，是把‘个人养虾’升级成‘团队养虾’。”

“不是每个人各养一个AI，
而是整个团队一起养一个AI。”

“团队养虾的核心价值是：
一个人攻克了一个功能，其他人、其他项目都可以复用。”

“举个例子。
比如有一个同事教会了Emily公司的报销流程：
报销单应该怎么填、需要哪些单据、怎么贴票。”

“那么以后新入职的同事，
直接问Emily就行，
完全不用再为这些基础工作去打扰老员工。”

“而且，如果哪里踩了坑、或者流程有了变化，
只要有人反馈给Emily，
就相当于所有人都避开了坑、或者都能按最新的要求来办。”

“这也正是论文里说的：
知识沉淀的主体，从‘个人’变成了‘团队’。”

“所以我把它叫做：
‘团队养虾’。”

切入下一页。

==================================================
六、热梗二：蒸馏同事——把“经验”留下来
预计2分钟
目的：用“蒸馏同事”热梗说明Emily能把做项目过程中形成的经验留下来，给后来做同类项目的同事复用。
==================================================

【页面7：把经验“蒸馏”成数字同事】
说：
“第二个热梗，叫‘蒸馏同事’。
我们地产行业其实特别需要它。”

“有些项目会遇到偏冷门的工程实例，
比如涉海工程、地铁沿线工程。
这些经验非常难得。”

“但一个人做完这样的项目，
他脑子里积累了大量处理问题的经验，
这些经验却很难留下来。”

“项目结束以后，复盘文件往往只有几十页：
当时具体遇到过什么问题、是怎么处理的，
大多只能记一个大概。”

“真正有价值的东西，其实藏在过程里：
过程文件、沟通群里的讨论、当时的判断和取舍。”

“Emily要做的，就是把过程记录下来，
很大程度上复现项目当时的推进过程，
让后来做类似项目的同事，能直接拿到这些宝贵经验。”

“这就是‘蒸馏同事’：
把人做项目过程中形成的经验，蒸馏成公司自己的知识。”

==================================================
七、团队记忆中枢：项目记忆不能跟着人走
预计2分钟
目的：讲清“项目记忆”会随人调动、离职而流失，Emily要成为团队记忆中枢。
==================================================

【页面8：项目记忆，不能只存在人脑子里】
说：
“刚才说的是‘经验’。
还有一种更基础的东西，叫‘项目记忆’。”

“项目记忆，会随人调动、离职一起流失。”

“举一个真实的例子。
年中汇报的时候，项目上的同事说，
他们在项目运作过程中拍摄了上万张过程照片，
几乎涵盖了工程的方方面面，
完全可以用于后续其他同类项目参考指导。”

“但问题是：
这套素材库的‘检索能力’，只在这位同事身上。”

“上万张照片，其他同事几乎无法接手——
太多了，看不过来；
检索，更无从谈起；
就算真的看完了，也不清楚某张照片
是在什么情况下、为了反映什么问题拍的。”

“类似的还有：
有些项目要查一份资料，
还得靠具体经办人去翻群聊记录、回忆当时在哪。”

“这些东西，一旦人走了，就断了。”

“所以Emily要做的，就是成为项目的‘记忆中枢’：
把项目过程中的记录、沟通、照片、事件都组织起来，
让它能被记住、被检索、被追溯。”

八、现场演示：不要先讲功能，直接问
预计5～7分钟
这是整个汇报的核心高潮。
==================================================

【页面9：现场演示——先问一个普通问题】
说：
“我们不先看系统架构。
直接问它几个问题。”

操作Emily：
“乔木移栽需要注意什么？”

说：
“这个问题普通AI也能回答。”

“所以如果Emily只做到这里，它没有什么特别的。”

切换问题。

【页面10：问公司标准】
操作：
“我们公司的乔木栽植验收标准是什么？”

说：
“现在问题就发生变化了。”

“它回答的已经不是网上的通用知识，而是我们企业自己的标准。”

“而且我们希望它不仅告诉你答案，还能告诉你依据来自哪里。”

【页面11：问项目】
操作：
“XX项目最近有没有发生乔木移栽相关问题？”

说：
“现在再往前走一步。”

“它开始从‘公司知识’进入‘项目记忆’。”

“我们真正希望它记住的，不只是一个文件，而是：
什么时候发生了什么，
谁发现的，
怎么处理的，
最后结果怎么样。”

【页面12：连续追问】
连续问：
“是谁发现的？”
“什么时候发生的？”
“当时怎么处理？”
“最后解决了吗？”

说：
“这时候它已经不是一个文档搜索框。”

“它开始形成一条项目事件链。”

“这也是我们做Emily时非常看重的一件事情：
让项目过程本身成为可以被查询、被追溯、被复用的记忆。”

【页面13：集团管理视角】
操作：
“现在XX项目整体处于什么状态？”
“最近有哪些风险？”
“景观工程最近有哪些未完成事项？”

说：
“如果我是项目负责人，我可以这么问。”

“如果我是集团领导，我还可以继续问：
‘最近所有项目有没有类似问题？’”

“这时候视角就从一个员工的问题，变成了团队和集团的管理信息。”

预计2分钟

【页面14：项目团队记忆中枢】
说：
“所以我后来给Emily一个定位：
项目团队的记忆中枢。”

“它记的不是简单的‘文件在哪里’。”

“而是：

怎么处理；

以后再遇到类似问题怎么办。”

“项目过程中的信息和经验，还可以继续为下一个项目服务。”

十、重新解释“蒸馏同事”
预计1分钟
==================================================

【页面15：个人经验 → 团队经验 → 企业能力】
说：
“这时候再回来看刚才说的‘蒸馏同事’，就比较容易理解了。”

“一个人做过的事情，
经过项目沉淀，
形成团队经验，
最后变成企业可以复用的能力。”

“也就是：

个人经验
→ 项目经验
→ 团队记忆
→ 企业能力。”

“Emily要做的，本质上就是帮助这个过程发生。”

十一、越用越强：不是AI自己偷偷训练自己
预计1分钟
==================================================

【页面16：越用越强】
说：
“这里我还想解释一下我说的‘越用越聪明’。”

“它不是说Emily自己偷偷训练自己。”

“真正的逻辑是：
每做一次项目，
就可能多留下一点数据；
每解决一个问题，
就可能多沉淀一条经验；
再把这些经验整理成规则、SOP或者新的工具能力。”

“于是下一次Emily就比上一次更懂公司。”

“所以我把它戏称为：
‘越用越强的团队养虾。’”

==================================================
十二、为什么Emily能够做到
预计3分钟
==================================================

【页面17：Emily为什么懂公司】
说：
“那么问题来了：
它凭什么知道这些？”

“其实不是因为我们用了一个特别神奇的模型。”

“真正重要的是，我们给它建立了三类东西。”

第一：
“第一类，是它知道‘现在发生了什么’。”

“比如项目、标段、节点、事件、人员、时间、状态。
我们把这些组织成项目的全景信息。”

“可以简单理解成：
让AI有一张‘项目地图’。”

第二：
“第二类，是它知道‘应该怎么做’。”

“这就是公司的制度、标准、规则和SOP。”

“比如什么情况下需要验收、谁负责、验收什么、出了问题怎么处理。”

第三：
“第三类，是它知道‘可以帮你做什么’。”

“例如查资料、查项目、填表、生成报告，甚至调用其他系统。”

“这些能力可以通过插件的方式不断增加。”

总结：
“所以真正让通用大模型变成公司AI的，不只是模型本身。”

“而是：

公司的数据
+
公司的规则
+
公司的业务能力。”

十三、价值：不要做传统功能清单
预计2分钟
==================================================

【页面18：如果Emily在公司里运行一年】
说：
“那么，如果Emily真的在公司里面运行一年，会发生什么？”

“我觉得可以看到四个变化。”

第一：
“对外，它可以成为一个新的企业服务入口。
客户、合作方、参建单位，不一定要知道系统在哪里，直接用自然语言问就可以。”

第二：
“对内，它可以成为一个新的知识入口。
过去是‘找文件、找人、问同事’，
以后逐渐变成‘直接问公司’。”

第三：
“对管理，它可以让项目过程更加透明。
领导不一定每次都要通过层层汇报才能了解项目状态，可以直接穿透到过程信息。”

第四：
“对组织，它最长期的价值，是让经验留下来。
人员变化以后，经验不至于全部跟着人一起消失。”

总结：
“所以我把它概括成四句话：

信息不丢失；
知识找得到；
管理看得见；
经验留得住。”

“基础的AI对话、知识检索、项目数据组织、权限控制、业务流和插件扩展这些底层能力已经具备。”

十五、真正需要公司提供什么
预计2分钟
==================================================

【页面20：Emily现在缺的不是代码】
说：
“它现在最缺的东西，其实不是代码。”

“它缺的是公司的真实业务内容。”

第一：
“第一，公司怎么做。
也就是制度、标准、SOP、验收规则。”

第二：
“第二，公司过去发生过什么。
也就是历史项目资料、项目记录和经验。”

第三：
“第三，让它进入一个真实项目。
因为只有真实项目，才能验证它到底有没有用。”

第四：
“最后才是服务器、模型Token、小程序等基本运行条件。”

强调：
“所以这个项目真正需要投入的，可能并不是大量软件开发经费。”

“真正有价值的投入，是把公司原来已经存在、但分散在不同地方的知识和经验组织起来。”

十六、建议怎么试
预计2分钟
==================================================

【页面21：不要一开始做大，先做一个真实试点】
说：
“所以我这次并不是想建议公司一开始就做一个很大的AI项目。”

==================================================
十七、现场问答备用话题
==================================================

1. “它和企业微信AI、普通知识库有什么区别？”
答：
“普通知识库解决的是‘把文件找出来’。Emily希望进一步解决‘理解项目、理解规则、理解过程，并参与业务动作’。知识库是其中一个基础能力，不是最终形态。”

2. “是不是需要把所有数据都给它？”
答：
“不需要，也不应该。按照业务、权限和用途逐步接入。不同角色看到不同范围的信息，这是企业AI必须具备的基础能力。”

3. “AI答错怎么办？”
答：
“关键业务不能把AI自由回答当成最终审批。重要回答要有来源、有依据；涉及流程执行时由规则和权限控制。AI负责理解、检索和辅助，企业制度负责约束。”

4. “会不会泄密？”
答：
“企业内部部署和权限体系是基础。Emily的设计不是让所有人看到所有信息，而是让AI在用户权限边界内工作。”

5. “最大的成本是什么？”
答：
“冷启动阶段最大成本不是Token，而是数据整理、规则梳理和业务人员参与。软件运行成本反而比较明确。”

6. “以后是不是还要不断投入开发？”
答：
“会，但应该是插件式、模块化迭代。新业务增加新Skill，新规则更新规则，新知识进入知识库，而不是每次都重做整个系统。”

7. “最终能不能替代人？”
答：
“不是这个目标。更现实的方向是替代大量低价值的信息查找、重复录入、过程整理工作，同时让人的经验更容易被组织复用。”

==================================================
十八、演示时的三个原则
==================================================

原则1：少讲技术，多让它现场工作。
技术架构最多用3分钟解释，不要成为主角。

原则2：故意先展示一个“普通问题”。
让听众先觉得“这不就是普通AI吗”，然后再通过企业标准和项目记忆逐层拉开差异。

原则3：最后一定落到“低成本试点”。
不要让高层感觉是在申请一个长期研发项目，而是申请一个可控、可验证的企业AI试验。
