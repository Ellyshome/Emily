## 1. 软件概述

### 1.1 软件名称
艾米地产项目人工智能调度管理系统（Emily）

### 1.2 版本号
V1.0

### 1.3 软件简介
Emily 是一款面向地产项目全生命周期的团队协作与智能调度管理系统。系统采用三层 Agent 架构设计，结合细粒度权限控制和全局状态机驱动，为项目各方提供精准、可控、可追溯的智能服务。

系统核心价值：
- **全面记录**：开发建设中的过程细节被完整记录，消除信息差
- **高效协作**：打破信息壁垒，大幅提升团队协作效率
- **知识沉淀**：行业经验不再随人走，永久沉淀为团队资产
- **模式升级**：信息管理告别"人盯人"的原始模式，AI 工具融入地产行业日常

### 1.4 技术栈

| 层级 | 技术选型 |
|------|---------|
| 后端框架 | Python AsyncIO + SQLAlchemy |
| 数据库 | PostgreSQL + JSONB |
| LLM 引擎 | 多模型支持（OpenAI 兼容接口） |
| 接入渠道 | 企业微信 / 微信 / Web 端 |
| 文件存储 | 本地存储 + 对象存储 |
| 日志系统 | Python logging + DB 审计日志 |

## 3. 核心功能设计

### 3.1 智能对话交互

#### 3.1.1 功能描述
用户通过自然语言与系统交互，系统自动识别意图并执行相应操作。支持群聊和私聊两种模式。

#### 3.1.2 核心流程
```
用户发送消息
    ↓
消息标准化处理（去重 / 格式统一）
    ↓
快速短路判断（问候 / 感谢 / 告别 → 直接回复）
    ↓
LLM 意图识别（基于 SOP 目录）
    ↓
意图匹配成功？
    ├─ 是 → 创建 WorkItem → Pipeline 执行
    └─ 否 → 兜底模式（工具自由调用 + RAG 检索）
    ↓
结果合成 + Guardian 审核
    ↓
回复用户
```

#### 3.1.3 关键特性
- **快速短路**：常见问候语无需 LLM 参与，毫秒级响应
- **上下文记忆**：支持多轮对话，历史消息自动注入 Prompt
- **意图消歧**：模糊意图时主动询问用户确认
- **群聊@机制**：群聊中仅 @机器人 的消息被处理

### 3.2 SOP 标准化作业流程

#### 3.2.1 功能描述
基于标准作业程序（SOP）模板，引导用户按规范完成业务操作，确保过程可追溯、结果可验收。

#### 3.2.2 SOP 结构
每份 SOP 包含以下章节：
```
§1 目的与适用范围
§2 定义与术语
§3 前置条件（权限 / 依赖 / 数据要求）
§4 操作步骤（Step 1 - Step N）
§5 验收标准
§6 异常处理
§7 相关工具与模板
```

#### 3.2.3 内置 SOP 清单
| SOP ID | 名称 | 适用场景 |
|--------|------|---------|
| REC-001 | 记录项目事件 | 质量/安全/进度/决策事件记录 |
| REC-002 | 创建任务 | 任务分配与追踪 |
| REC-003 | 会议纪要归档 | 会议记录与待办提取 |
| FILE-001 | 文件归档 | 工程文件上传与分类 |
| QUERY-001 | 数据查询 | 项目数据多维度检索 |
| SYS-001 | 待确认处理 | 待确认事项确认/取消 |

### 3.3 全景节点图状态机

#### 3.3.1 功能描述
将项目拆分为多层级节点（阶段 / 子阶段 / 任务 / 成果），每个节点独立状态流转，自动计算整体进度。

#### 3.3.2 节点状态定义
```
NOT_ACTIVATED    — 未激活（初始状态）
CONDITIONS_NOT_MET — 条件不满足（前置依赖未完成）
IN_PROGRESS      — 进行中（可提交成果）
BLOCKED          — 阻塞（异常/风险）
COMPLETED        — 已完成（验收通过）
```

#### 3.3.3 进度计算规则
```
节点进度 = Σ(子节点进度 × 子节点权重) / Σ(子节点权重)
当子节点全部 COMPLETED 时，父节点自动 COMPLETED
```

### 3.4 三维权限控制

#### 3.4.1 权限维度
```
维度 1：权限层级（L0-L5）
  L0 访客     — 仅公开信息查询
  L1 参建执行  — 个人任务 + 照片上传
  L2 参建管理  — 专业范围内任务管理
  L3 监理      — 质量/安全监督
  L4 建设主管  — 项目全量信息 + 报表导出
  L5 系统管理员 — 全系统功能可访问

维度 2：信息密级
  PUBLIC       — 公开信息
  INTERNAL     — 内部公开
  PRIVATE      — 项目内可见
  CONFIDENTIAL — 机密（仅授权人员）

维度 3：资源范围
  企业类型      — 建设/设计/总包/分包/监理/供应商
  部门范围      — 指定部门可见
  节点范围      — 指定项目节点可见
```

### 3.5 智能调度与巡检

#### 3.5.1 定时任务类型
| 类型 | 触发方式 | 用途 |
|------|---------|------|
| CRON | Cron 表达式 | 日报/周报/月报生成 |
| INTERVAL | 固定间隔（秒） | 卡滞节点巡检（5 分钟） |
| ONCE | 指定时间点 | 一次性任务提醒 |

#### 3.5.2 节点巡检规则
- 检查超过 7 天无进展的节点 → 自动标记为"关注"
- 检查即将到期（3 天内）的节点 → 自动提醒责任人
- 检查前置依赖已完成但未激活的节点 → 自动激活提示
- 检查成果超期未验收 → 提醒验收人

## 4. 关键算法与流程

### 4.1 SOP 意图识别算法

#### 4.1.1 算法描述
基于 LLM 语义理解，将用户自然语言请求匹配到最适合的 SOP 流程。

#### 4.1.2 匹配流程
```
1. 预处理
   - 去除无效字符
   - 提取关键实体（项目名 / 人名 / 时间）
   - 历史对话上下文注入

2. 构建 SOP 目录树
   - 按业务领域分类
   - 每个 SOP 包含：名称 / 描述 / 适用场景示例

3. LLM 分类判断
   Prompt 模板：
   """
   你是一个意图分类专家。根据以下 SOP 目录，判断用户请求最匹配的 SOP。

   SOP 目录：
   {sop_catalog}

   用户历史对话：
   {conversation_history}

   用户当前请求：{user_input}

   请输出 JSON 格式：
   {
     "sop_id": "匹配的 SOP ID 或 null",
     "confidence": "high/medium/low/none",
     "is_compound": true/false,  # 是否复合请求需拆分为多个子任务
     "sub_tasks": [{"sop_id": "", "user_input": ""}],  # 复合请求时必填
     "reasoning": "判断理由"
   }
   """

4. 后处理
   - confidence ≥ medium → 走对应 SOP 流程
   - confidence < medium → 走兜底模式
   - is_compound = true → 拆分为多个 WorkItem 并行执行
```

### 4.2 三维鉴权算法

#### 4.2.1 算法描述
按优先级短路求值，任何一步不通过即拒绝访问。

#### 4.2.2 鉴权流程
```
输入：用户权限对象（perms）+ 目标 SOP ID
输出：ALLOW / DENY + 原因

Step 1：检查 DENY 编码（最高优先级）
  IF sop_code IN perms.denied_codes → DENY

Step 2：检查单独授权
  IF sop_code IN perms.granted_codes → ALLOW

Step 3：检查 SOP 权限矩阵
  3.1 IF is_public = true → ALLOW
  3.2 IF 用户级别 < min_level → DENY
  3.3 IF 信息密级 > 用户可查看级别 → DENY
  3.4 IF 企业类型不匹配 → DENY
  3.5 IF 部门不匹配 → DENY
  3.6 IF 节点范围无交集 → DENY

Step 4：全部通过 → ALLOW
```

### 4.3 Pipeline 4 节点执行流程

#### 4.3.1 流程总图
```
WorkItem 创建
    ↓
┌─────────────────────────────────────────┐
│ Node 1：意图验证 + 知识注入            │
│  ├─ 检查 SOP 是否存在                  │
│  ├─ 检查用户是否有权限（Auth Hook）    │
│  └─ KnowledgeInjector 注入 SOP 全文    │
└─────────────────────────────────────────┘
    ↓  Before Hook（鉴权 / 审计 / 校验）
┌─────────────────────────────────────────┐
│ Node 2：计划生成                        │
│  ├─ Skill 定义优先（若有预定义步骤）   │
│  └─ LLM 动态生成执行计划               │
│     （风险等级 / 步骤列表 / 验收标准）│
└─────────────────────────────────────────┘
    ↓  Before Hook（计划校验 / 二次鉴权）
┌─────────────────────────────────────────┐
│ Node 3：执行 + 验收                     │
│  ├─ 遍历步骤调用工具 handler            │
│  ├─ Guardian 并进审核每步输出          │
│  └─ 失败即停止，返回错误信息            │
└─────────────────────────────────────────┘
    ↓  After Hook（执行审计 / 进度通知）
┌─────────────────────────────────────────┐
│ Node 4：成果总结（可选）               │
│  ├─ 合成执行结果摘要                   │
│  ├─ Guardian 出站内容审核              │
│  └─ 格式化为自然语言回复               │
└─────────────────────────────────────────┘
    ↓
执行完成 → 更新 WorkItem 状态 → 回复用户
```

### 4.4 节点状态机算法

#### 4.4.1 状态转移规则
```
NOT_ACTIVATED → CONDITIONS_NOT_MET （激活但依赖未完成）
             → IN_PROGRESS           （激活且无依赖）

CONDITIONS_NOT_MET → IN_PROGRESS    （所有前置依赖完成）

IN_PROGRESS → COMPLETED              （所有成果 100%）
           → BLOCKED                （标记阻塞）

BLOCKED → IN_PROGRESS               （解除阻塞）

任何状态 → NOT_ACTIVATED             （废弃节点）
```

#### 4.4.2 依赖满足度计算
```python
def calc_dependency_satisfaction(node):
    """计算节点前置依赖满足度（0.0 - 1.0）"""
    deps = get_dependencies(node.node_id)
    if not deps:
        return 1.0  # 无依赖 = 100% 满足

    completed_count = 0
    for dep in deps:
        dep_node = get_node(dep.depends_on_node_id)
        if dep_node.status == COMPLETED:
            completed_count += 1

    return completed_count / len(deps)
```
