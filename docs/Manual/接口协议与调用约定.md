## 1. 标准协议对象（`emily_core/adapters/standard/`）

这些 dataclass 构成 IM 适配器与 Emily Core 之间的跨平台合约。Core 只依赖这些对象，不依赖原始 IM 事件。

### 1.1 `StandardMessage` — 入站统一消息（`message.py`）

| 字段 | 类型 | 默认值 | 说明 |

| `conversation_id` | `str` | `""` | 群 ID 或私聊用户 ID |
| `sender_id` | `str` | `""` | 发送者 IM ID |
| `sender_name` | `str` | `""` | 发送者昵称 |
| `group_id` | `str\|None` | `None` | 群 ID（私聊为空） |
| `group_name` | `str\|None` | `None` | 群名称 |
| `content` | `str` | `""` | 消息文本（@bot 已剥离） |

### 2.3 ExecutionPlan / WorkAgent（`planning.py` + `execution.py`）

`PlanStep`：`step_id / description / tool_name / tool_params / expected_output / depends_on`

`ExecutionPlan`：`risk_level: "L1"|"L2"|"L3"` / `steps: list[PlanStep]` / `acceptance_criteria: list[str]` / `estimated_steps: int` / `_source`

`WorkAgent(ABC)`：
```python

async def execute(plan, context) -> list[StepResult]         # node3
```

### 2.4 Guardian（`guardian.py`）

```python
class Guardian(ABC):

```

`GuardianVerdict`：PASS / FLAG / REJECT

### 2.5 RiskGrader（`risk.py`）

```python
class RiskGrader(ABC):
    def grade(route_decision, operation_type="") -> str  # "L1"|"L2"|"L3"
```

分级逻辑：快回/闲聊→L1；单意图高置信读取→L1；单意图中低置信或写入→L2；复合/兜底/删除→L3。

## 3. 工具定义协议

### 3.1 `ToolDefinition` — LLM 函数调用工具（`agent/tool_registry.py`）

```python
@dataclass
class ToolDefinition:
    name: str                                          # 唯一标识，如 "query_data"
    description: str                                   # 注入 LLM system prompt
    parameters: dict                                   # JSON Schema
    execute: Callable[[dict], Awaitable[dict]]         # async fn(args)→dict
    require_admin: bool = False                        # True=仅管理员
```

| `ToolRegistry` 方法 | 说明 |
|---------------------|------|
| `register(tool)` | 注册工具，重复名抛 ValueError |
| `get(name)` | 按名获取 |
| `list_all()` / `list_public()` | 列出全部 / 排除管理员工具 |
| `get_openai_tools(admin=False)` | 导出为 OpenAI function-calling 格式 `[{type:"function", function:{...}}]` |

### 3.2 `BusinessFlowTool` — 业务流工具（M14 框架直调，`tools/business_flow_tools.py`）

```python
@dataclass
class BusinessFlowTool:
    name: str                                          # 与 SOP §3.2 一致
    description: str                                   # 注入 LLM 结构化输出 prompt
    parameters: dict                                   # JSON Schema
    handler: Callable                                  # async fn(params: dict) -> dict
```

| `BusinessFlowToolRegistry` 方法 | 说明 |
|-------------------------------|------|
| `register(tool)` | 注册 |
| `get(name)` / `has(name)` | 查存在 / 获取 |
| `list_names()` | 列出全部工具名 |

**调用约定**：BusinessFlowTool **不暴露为 LLM function-calling**。Skill YAML 的 steps 声明 tool_name → SkillExecutor 按 tool_name 从 BusinessFlowToolRegistry 查找 → 调用 `handler(params)`。工具白名单由 Skill YAML tools 字段声明。

**特殊 tool_name 取值**：
- `null` / 空字符串：纯逻辑步骤，不调工具（如 SOP-999 step-01 LLM 选工具+推参）
- `__DYNAMIC__`：动态工具执行分支——从 prev_step 的 output_key 取 `{tool_name, params}`，校验白名单后直调 handler。写类工具（permission_flag != all）走 `confirm_callback` 拟执行确认，用户确认后才执行。审计标记 `trigger="sop999"`

### 3.3 M5 文件用途与附件链工具

以下 4 个工具为 M5 文件管理模块新增，操作 `files` 表的 `purpose` 与 `attachment_of` 字段。

#### `update_file_purpose`

```python
@dataclass
class UpdateFilePurposeParams:
    file_id: str          # 目标文件 UUID（必填）
    purpose: str          # 目标用途枚举值：EVIDENCE/RECORD/DESIGN/REFERENCE/CHAT（必填）
    confirmed: bool = True  # 是否人工确认（默认 True，写入 purpose_confirmed）
```

| 返回字段 | 类型 | 说明 |
|----------|------|------|
| `success` | `bool` | 操作是否成功 |
| `file_id` | `str` | 文件 ID |
| `purpose` | `str` | 更新后的用途 |
| `purpose_confirmed` | `bool` | 确认标志 |
| `previous_purpose` | `str` | 更新前的用途 |

#### `link_to_master`

```python
@dataclass
class LinkToMasterParams:
    attachment_id: str    # 附属文件 UUID（必填）
    master_id: str        # 主文件 UUID（必填）
```

| 规则 | 说明 |
|------|------|
| 循环检测 | 不允许 master 是自身或已挂载在 attachment 之下 |
| 多重挂载禁止 | 已挂载的附属文件先自动 `unlink_attachment` 再挂到新 master |
| 级联约束 | master 被删除时，其下所有附属文件的 `attachment_of` 置 NULL |

| 返回字段 | 类型 | 说明 |
|----------|------|------|
| `success` | `bool` | 操作是否成功 |
| `attachment_id` | `str` | 附属文件 ID |
| `master_id` | `str` | 主文件 ID |

#### `unlink_attachment`

```python
@dataclass
class UnlinkAttachmentParams:
    attachment_id: str    # 要解除挂载的附属文件 UUID（必填）
```

将 `attachment_of` 置 NULL，文件变为独立主文件。

| 返回字段 | 类型 | 说明 |
|----------|------|------|
| `success` | `bool` | 操作是否成功 |
| `attachment_id` | `str` | 文件 ID |
| `previous_master_id` | `str\|None` | 之前挂载的主文件 ID |

#### `list_attachments`

```python
@dataclass
class ListAttachmentsParams:
    file_id: str          # 主文件 UUID（必填）
    include_nested: bool = False  # 是否递归列出孙子附属
```

| 返回字段 | 类型 | 说明 |
|----------|------|------|
| `master_id` | `str` | 主文件 ID |
| `attachments` | `list[dict]` | 附属文件列表，每项含 `{file_id, file_no, filename, purpose, file_type}` |
| `count` | `int` | 附属文件数量 |

#### `record_file` 新增 `purpose` 字段

原有 `record_file` 工具新增可选参数：

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `purpose` | `str\|None` | `None` | 文件用途枚举值。不传则由 `file_rule_engine` 自动推断，写入后 `purpose_confirmed=False`；显式传入则 `purpose_confirmed=True` |

### 3.4 `ToolManager` — 聚合层（`tools/manager.py`）

[ToolManager](../emily-core/emily_core/tools/manager.py) 是 BusinessFlowToolRegistry 的轻量聚合层，补三件事：统一调用入口、自描述、CLI/HTTP 测试接口。**不替代 Registry**，注册仍走 `register_all`。

```python
class ToolManager:
    def __init__(self, registry: BusinessFlowToolRegistry)
    def list(self) -> list[dict]                           # 轻量元信息列表
    def describe(self, name: str | None = None) -> dict     # 完整描述（含 schema）
    def schema(self, name: str) -> dict                     # 单工具 JSON Schema
    def export(self) -> dict                                # 导出全部 schema
    async def call(self, name: str, params: dict | None) -> dict  # 统一调用入口
    def selfcheck(self) -> dict                             # 依赖就绪检查
```

| 调用约定 | 说明 |
|----------|------|
| **注册不侵入** | `register_all(core)` → Registry → ToolManager 只读包装。ToolManager 不参与注册。 |
| **运行时调用** | SkillExecutor 仍直查 Registry（性能路径，不变）。测试/自描述走 ToolManager。 |
| **call 绕过 SOP** | `ToolManager.call()` 直接调 `handler(params)`，不走 SkillExecutor 和 SOP 管线。 |
| **标准化返回** | `call()` 返回 `{"success": bool, "result": ..., "tool": str, "code": int}`；code 0/1/2 语义与 CLI 退出码一致。 |
| **selfcheck 策略** | 检查 handler 函数名是否含 `stub`（如 `_rag_stub`），含则 `ready=false`。 |

CLI 入口：[scripts/toolmgr.py](../scripts/toolmgr.py)。

### 3.5 `ScriptManager` — 脚本管理聚合层（`emily_core/scripts/manager.py`）

[ScriptManager](../emily-core/emily_core/scripts/manager.py) 与 ToolManager 平级，管理 `scripts/` 目录下的开发者/维护脚本。元信息从 `emily-data/config/scripts_registry.yaml` 声明式加载，不新建 DB 表。

```python
class ScriptManager:
    def __init__(self, registry: ScriptRegistry)
    def list(self) -> list[dict]                           # 轻量元信息列表
    def describe(self, name: str | None = None) -> dict     # 完整描述
    def check(self, name: str | None = None) -> dict         # 跑 check_arg 自检
    def run(self, name: str, args: list[str] | None, timeout: int | None) -> dict  # subprocess 执行
    def test(self, name: str | None = None) -> dict          # smoke 用例
    def export(self, format: str = "markdown") -> dict | str # 导出注册信息
```

| 调用约定 | 说明 |
|----------|------|
| **声明式注册** | 脚本元信息维护在 `emily-data/config/scripts_registry.yaml`，`load_registry()` 解析后 `ScriptManager` 只读包装。 |
| **subprocess 执行** | `run()` 默认使用 `subprocess.run([sys.executable, script_path, ...])`，与 bootstrap 一致。`entrypoint` 非空时可走 in-process 快路径。 |
| **check 契约** | 不重构脚本 argparse，用清单 `check_arg` 字段做适配器封装 `--check`/`--dry-run`/`--preview`/`--probe` 等。 |
| **标准化返回** | `run()` 返回 `{"success": bool, "returncode": int, "stdout": str, "stderr": str, "script": str, "code": int}`；code 0/1/2 语义与 ToolManager 一致。 |

CLI 入口：[scripts/scriptmgr.py](../scripts/scriptmgr.py)。

边界：ToolManager 管 LLM 运行时工具；ScriptManager 管开发者/维护脚本。两者共享 service 层，互不调用。

## 5. LLM Client 接口（`infrastructure/llm/client.py`）

`LLMClient` 封装 `openai.AsyncOpenAI`（DeepSeek/OpenAI 兼容）。所有方法 async。

| 方法 | 签名 | 返回 | 说明 |
|------|------|------|------|
| `chat` | `async (system_prompt, user_message) -> str` | 原始文本 | 单轮对话 |
| `chat_json` | `async (system_prompt, user_message) -> dict` | 解析后的 dict | `response_format=json_object`；失败回退 plain chat + markdown fence 提取；不可解析抛 ValueError |
| `chat_with_tools` | `async (messages, tools, temperature?, max_tokens?) -> dict` | `{type, content/tool_name, finish_reason, reasoning_content?}` | OpenAI function-calling；处理 DeepSeek thinking 模式 reasoning_content 往返；MVP 仅第一 tool_call |
| `set_trace_callback` | `(callback\|None) -> None` | None | M11 trace hook：回调收到 `{phase, call_type, model, message_count, tool_count, response_type, tokens, latency_ms}` |

**trace callback 与 Hook 的关系**：`set_trace_callback` 是 LLM 客户端级回调（每 LLM 调用触发）；`TraceHook` 是管道级 Hook（挂载在 node3 的 before/after）。TraceHook 调用 `AgentTraceService` 写追踪日志；`set_trace_callback` 用于非侵入式 LLM 调用观测。

## 6. 状态机合约

### 6.1 WorkItem 状态机（现行，`workitem/workitem_state.py`）

```
CREATED → PLANNING → EXECUTING → DONE (终态)
                 ↓           ↓
               FAILED    WAITING_CONFIRM → EXECUTING
               (终态)         ↓
                           FAILED (终态)
```

`TRANSITIONS`：CREATED→[PLANNING, FAILED] / PLANNING→[EXECUTING, FAILED] / EXECUTING→[DONE, WAITING_CONFIRM, FAILED] / WAITING_CONFIRM→[EXECUTING, FAILED]。`TERMINAL_STATES = {DONE, FAILED}`。

> ⚠ WAITING_CONFIRM 状态已定义但当前无节点驱动进入，`SessionAgent._collect_pending_confirms` 会检查此状态。

### 6.2 BusContext（现行，`workitem/pipeline/context.py`）

共享状态流经 4 节点，Hook 读/写。

| 字段 | 类型 | 说明 |
|------|------|------|
| `work_item` | `WorkItem` | 当前执行单元 |
| `message` | `StandardMessage` | 原始消息 |
| `intent` | SOPMatchDecision | 路由/意图匹配 |
| `agent_result` | `AgentResult` | Agent 执行结果 |
| `verified_reply` | `str` | 核验后的回复 |
| `baggage` | `dict` | 自由扩展字段（Node→Hook 传参，如 `send_progress_callback`） |
| `_session_context` | `SessionContext` (只读) | 含 PermissionSnapshot |

## 7. HTTP / SSE API

### 7.1 `POST /api/v1/message/send`

**请求** `MessageIn`（Pydantic，镜像 StandardMessage）：
```json
{
  "message_id": "msg-123",
  "platform": "napcat",
  "conversation_type": "group",
  "conversation_id": "group_888",
  "sender_id": "qq_12345",
  "sender_name": "张三",
  "content": "帮我创建事件：样板段放线完成",
  "is_at_bot": true,
  "msg_type": 1,
  "attachments": []
}
```

**响应**：
- `200` + `ReplyOut{conversation_id, content, reply_to_message_id}`：同步短路回复（快回）
- `204` No Content：已接管，异步回复将通过 SSE 推送

### 7.2 `POST /api/v1/session/terminate`

```json
{"conversation_id": "group_888"}
```
→ `{"terminated": true, "conversation_id": "group_888"}`

### 7.3 `GET /api/v1/health`

→ `{"status": "ok", "sessions": 1, "uptime": 3600, ...}`

### 7.4 `GET /api/v1/events/outbound` — SSE 出站事件流

```
event: reply
data: {"conversation_id":"group_888","content":"已创建事件 EVT-20260626-0001"}

event: progress
data: {"conversation_id":"group_888","content":"正在处理…"}

event: file_send
data: {"conversation_id":"group_888","file_paths":["/app/data/files/..."],"caption":"图纸"}

event: session_closed
data: {"conversation_id":"group_888"}

: keep-alive
```

**时序**：
- 同步快回：`POST /message/send` 直接 200（不走 SSE）
- 异步路径：POST 返回 204 → Core 通过 `OutboundEventBus` → SSE 推送事件
- `progress` 事件可多次推送（前导消息实时通知）
- `reply` 事件是最终回复（含 `reply_to_message_id` 引用）
- `session_closed` 标识会话终止（TTL 超时或主动关闭）
- 15s 无事件 → 发送 `: keep-alive` 注释行心跳

### 7.5 `GET /api/v1/config/inventory` — emy-config 配置总清单（只读）

页面：`http://127.0.0.1:18080/config/`。用于回答「这项配置现在是什么值、值从哪来、改了会不会生效」。

```json
{
  "code": 0, "message": "ok",
  "data": {
    "runtime":  {"config_source": "环境变量 → Config（bootstrap._config_from_env）", "dotenv_path": "/app/host/.env",
                 "dotenv_readable": true, "field_count": 79, "env_entry_count": 35, "generated_at": "..."},
    "sections": [{"key": "llm", "title": "LLM 模型与采样", "count": 10}],
    "fields":   [{"field": "llm_model", "type": "str", "note": "...", "env": "EMILY_LLM_MODEL", "has_env": true,
                  "sensitive": false, "source": "env", "default": {...}, "declared": {...}, "effective": {...}}],
    "files":    [{"name": "core_config.json", "exists": true, "read_by_runtime": false, "evidence": []}],
    "findings": [{"level": "warn", "kind": "file-conflict", "title": "...", "detail": "...", "action": "..."}],
    "unmapped_env": [...], "dotenv_declared": [...], "host_files": [...], "restart_hint": [...]
  }
}
```

约定：
- `source` ∈ `env`（容器环境变量生效） / `dotenv-uninjected`（`.env` 写了但容器没有，**改它不生效**） / `default`（代码默认值）。
- `sensitive: true` 的字段（`api_key`/`password`/`token`/`idkey` 等，`*_tokens` 结尾的配额除外）任何接口都不返回明文，只给「已配置（N 字符）」。
- `files[].read_by_runtime` 由**源码 AST 扫描**判定（跳过注释与 docstring，剔除扫描器自身），`evidence` 给出 `文件:行号`；不硬编码结论。
- `findings` 五类：`dotenv-uninjected` / `file-conflict` / `file-not-loaded` / `env-without-dotenv` / `env-unmapped`（另有 `env-type-unregistered`、`file-invalid-key` 两个 info 类），每条附 `action`（可执行的下一步）。

### 7.6 `GET /api/v1/config/file?name=` — 单个配置文件内容（只读）

- 文件名白名单：仅 `emily-data/config` 下已登记的 7 个文件；宿主机 `.env` **不在**白名单内，路径穿越被拒。
- 返回密钥类键值已掩码，超长（>200k 字符）截断。
- 失败返回 `{"code": 1, "message": "配置文件未登记：xxx", "data": null}`。

> 本模块**只读**：不提供任何写配置的接口，不自动重启、不做热重载；生效方式见清单返回的 `restart_hint`
> （`.env` 改动须 `docker compose up -d <service>` 重建容器，`docker restart` 不重读 `.env`；代码/配置文件改动只需 restart）。

## 8. 调用约定

| # | 约定 | 说明 |
|----|------|------|
| 1 | **分层不可跳** | `API → EmilyCore → Session → WorkItem → Application → Service → Repository → DB`。不跨层 import。 |
| 2 | **Sync repo + `asyncio.to_thread`** | Repository 全 sync（SQLAlchemy sync session），async Service 用 `asyncio.to_thread()` 包裹 repo 调用防阻塞事件循环。 |
| 3 | **M14 结构化输出优先** | 命中 SOP 路径：LLM `chat_json` → 提取参数 → 框架调用 `BusinessFlowTool.handler(params)`，不走 function-calling。未命中 unmatched 路径：ReAct + ToolRegistry function-calling。 |
| 4 | **Hook 三态 deny-wins** | before hook 异常视为 BLOCK（安全第一）；after hook 异常不阻断（fire-and-forget）。多个 hook 任一 BLOCK 即终止。 |
| 5 | **声明式 JSON 配置** | 新增 Hook / 新增 SOP 通过编辑 `hook_config.json` / 放 `.md` 到 `sops/` → 重启生效，不改 Python 代码。 |
| 6 | **每请求新建注册表** | 每消息新建 `ToolRegistry` + `BusinessFlowToolRegistry`，闭包注入 `user_id` / `is_admin` / `guardian_review` / `pending_issues`。 |
| 7 | **管理员工具隔离** | `require_admin=True` 的工具不暴露给普通用户的 LLM function-calling 列表。 |
| 8 | **核验注入** | 核心业务流工具统一接收 `guardian_review` + `pending_issues` 参数，handler 内部走核验三选一（修改重审/坚持录入标记/取消）。 |
| 9 | **FK 列语义陷阱** | `messages.conversation_id` 是 FK→`conversations.id`（UUID），非业务 `conversation_id` 字符串。`create_outbound()` 和 `AgentReasoningRepository` 写入前需调用 `_resolve_conversation_id()` 转换。`MessageRepository.create_from_standard()` 已正确处理。 |
| 10 | **Session 级串行锁** | 同一 `conversation_id` 内消息串行处理（asyncio.Lock），不同 `conversation_id` 间并行。 |
| 11 | **business_id 解析模式** | 工具 handler 收到业务编号（如 `PTI-20260625-0001`），需先通过 `get_by_xxx_no()` 解析为 UUID，再传给 Service 层。 |
| 12 | **无 LLM 时放行** | `return None`（HTTP 204），不硬编码回复。让 AstrBot 原生 Agent 兜底。 |
| 13 | **agent loop 不直接回复用户** | agent loop 的 LLM 只做工具决策，完成工作必须调 `complete_work` 返回成果，信息不足调 `ask_user` 挂起。type=text 兜底转为 StructuredResult。回复组织权在 SessionAgent。 |
| 14 | **留痕挂载点唯一** | 留痕只在 `service` 动作层产生（经 `@audited` 装饰器，见 §9）；入口层（`api/routes`、`application`、`scripts`）只注入上下文，**禁止直接写留痕**。 |

## 9. 留痕归因约定（操作留痕治理）

> 需求与设计见 `issues/操作留痕治理/`（需求基线 V1 / PRD V1 / 计划 V1）。

**9.1 挂载与写入**

| 组成 | 位置 | 说明 |
|------|------|------|
| 留痕门面 | `infrastructure/logging/audit.py` | 上下文（ContextVar）+ `@audited` 装饰器 + 三态判定 + 同步写入 + 失败计数 |
| 写入底层 | `infrastructure/logging/log_writer.py` | `EvolutionLogWriter.write_sync`（同步上下文）/ `write`（async） |

`@audited(category=..., action=..., target_type=..., actor_arg=..., target_arg=..., target_no_arg=..., target_result_attr=..., summary_arg=..., summary=...)`：
- 参数取值支持点号路径（如 `cmd.creator_id` / `doc_metadata.doc_id`），`target_result_attr` 用于建类动作从返回值取新对象 id；
- 取不到 actor 时回退上下文 actor，仍无则记 `unknown`（**不得因缺 actor 而不留痕**）；
- 同时支持 sync / async 方法；方法抛异常记 `failed` 后原样抛出。

**9.2 流量性质 `source`（`business_event_logs` / `messages` / `scheduler_job_logs`）**

| 取值 | 含义 | 注入点 |
|------|------|--------|
| `user` | 真实用户行为 | `EmilyCore.handle_message`（IM 四渠道，`channel` + `channel_account` 同时注入） |
| `ops` | 人发起的运维操作 | console 路由中间件（`AuditContextMiddleware`）；脚本 CLI 入口（ScriptManager 环境变量 / `declare_script_source`） |
| `auto` | 无人触发的系统行为 | 调度作业执行入口（`SchedulerEngine._execute_job`） |
| `test` | 测试流量（console 模拟对话） | `console_resources.chat_send` 显式覆盖（走真实 IM 入口但必须与真实流量可区分） |

- `channel`（QQ/企微/小程序/邮箱）为附属字段，仅 `source=user` 时必填；
- `channel_account` 记"来源标识"：渠道账号 / `cli` / `console` / 作业标识。

**9.3 三态 `result`**

`succeeded` / `failed` / `rejected`，判定见 `audit.classify_result`（兼容 `dict含success` / `NodeOperationResult` / `list[dict]` / `bool`）。
口径：**动作已开始**后的规则或权限拒绝记 `rejected`（拒绝码表 `REJECT_CODES`）；**请求尚未进入动作**的参数校验拒绝不留痕（校验位置 ≠ 留痕位置）。
局限：返回值只带中文文案、无机器码的动作点一律记 `failed`，需在该动作点补 `reason_code` 才能精确化。

**9.4 消费端**

- 统一分辨方法：`ConsoleLogRepo.is_test_record(row)`（读 `source`，**不 grep 前缀**）；
- 日志面板：`GET /api/v1/console/logs?exclude_sources=test`（逗号分隔，仅对带 `source` 列的模块生效；当前 16 个模块中 `business_event_logs` / `scheduler_job_logs` 支持）；
- 行为分析与进化闭环默认只取 `source=user`（如 `EvolutionRepo.get_user_recent_events`）。

**9.5 粒度语义**

- 动作边界 = service 的公开方法。**批量动作**（如 `node_batch_update.batch_*`）不单独记一条，而是由其内部逐项调用的 `NodeService` 动作方法各记一条 —— 因此一次批量 N 个节点产生 N 条记录（对审计更可用）；
- 委托型 Facade 只在最内层动作方法挂载（如 `FileManager.update_confidentiality` 不挂，避免与 `FileService.update_confidentiality` 重复）；
- 查询类动作默认不记，仅"高风险读"按需记（如 console 知识查库 `knowledge/searched`）。
