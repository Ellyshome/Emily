### 新纪元：Emily（2026-06-23 ~ 至今）

旧 EmyBot 架构痛点驱动重构：8 阶段铁序管道僵化、MasterAgent 职责过重（路由+执行+合成三重角色）、AstrBot 容器绑定无法独立、确认流内存 dict 重启丢失。

**核心变化**：
- 包名 `teambrain_core` → `emily_core`（内核独立）
- AstrBot 内嵌插件 → **双容器**（薄插件 `emily_agent` + 独立 `emily-core` FastAPI）
- 8 阶段 WorkOrder 管道 → **Session 主线 + WorkItem 4 节点 PipelineBUS**
- Agent 编排（M14 结构化输出优先、Hook 声明式）保留，逻辑从旧 `agent/` 提取到 `SessionAgent`/`WorkItemAgent`

## 3. 关键架构决策（ADR）

### ADR-E01：WorkOrder → WorkItem — 消息级处理上移 Session 层

| 项 | 内容 |
|----|------|
| **日期** | 2026-06-23 |
| **决策** | 旧 M15 WorkOrder（8 阶段单消息流程单）→ 新 WorkItem（4 节点单任务执行单元）；消息级处理（intake/绑定/路由）上移至 Session 层；一条消息可拆分为 0..N 个 WorkItem |
| **原因** | WorkOrder 是"消息→回复"的单通道处理；WorkItem 支持复合请求拆解 + 并行执行；Session 层管理对话状态与确认队列 |
| **后果** | 旧 WorkOrder/PipelineContext 已完全移除；新系统 `WorkItem` + `BusContext` 为唯一路径 |

### ADR-E02：旧 `agent/` 冷备不 import

| 项 | 内容 |
|----|------|
| **日期** | 2026-06-24 |
| **决策** | 原 `emily_core/agent/` 下 Agent 逻辑（MasterAgent/BusinessFlowAgent 等）提取到 `SessionAgent` / `WorkItemAgent`。当前 `agent/` 保留 SOPIntentRegistry / ToolRegistry / sop_parser 等工具模块，仍在热路径中 import。 |
| **原因** | (1) Agent 逻辑与工具注册表解耦；(2) SessionAgent/WorkItemAgent 提供更清晰的职责边界；(3) 新架构用更简洁的代码量表达同类概念 |
| **后果** | `agent/` 中 Agent 类已移除，保留工具注册表/SOP 解析等基础设施模块仍在活跃使用 |

### ADR-E03：M14 结构化输出优先于 ReAct

| 项 | 内容 |
|----|------|
| **日期** | 2026-06-24 |
| **决策** | SOP 命中路径：LLM `chat_json` 提取 `{tool, params}` → 框架直接调用 `BusinessFlowTool.handler(params)`，不走 ReAct + function-calling。Unmatched 兜底路径仍走 ToolRegistry function-calling 自由推理。 |
| **原因** | (1) SOP §3.2 已明确声明所需工具；(2) LLM 核心价值是自然语言→结构化参数提取；(3) 减少 LLM tool-calling 往返延迟和 token 消耗；(4) 框架直接执行消除调用错误工具的风险 |
| **后果** | 5 个核心业务工具（record_event/task/meeting/file + query_data）仅在 `BusinessFlowToolRegistry` 中注册，不暴露为 LLM function-calling |

### ADR-E04：Hook 声明式 JSON 配置

| 项 | 内容 |
|----|------|
| **日期** | 2026-06-23 |
| **决策** | Hook 通过 `emily-data/config/hook_config.json` 声明式挂载到管道节点，不改 Python 代码。三态决策 ALLOW/WARN/BLOCK。 |
| **原因** | 鉴权/审计/核验/追踪是横切关注点，应与业务逻辑分离；非开发人员可通过编辑 JSON 启用/禁用/调整 Hook |
| **后果** | Hook 子类在 Python 中实现（`pipeline/hook.py`），挂载配置在 JSON 中；`HOOK_TYPE_MAP` 实现 type 名→类映射 |

### ADR-E05：容器拆分 + 内核独立

| 项 | 内容 |
|----|------|
| **日期** | 2026-06-23 |
| **决策** | 从 AstrBot 内嵌插件拆为独立 `emily-core` 容器 + 薄 `emily_agent` 插件。Emily Core 不 import `astrbot.*`。 |
| **原因** | (1) 业务内核可独立部署/扩展/测试；(2) 不绑定 AstrBot 容器环境；(3) HTTP+SSE 协议比 Python import 更清晰的边界 |
| **后果** | 插件 `adapters/standard/` 下 DTO 副本（message/reply/command/result）是刻意设计，使插件不依赖 Core 包 |

### ADR-E06：PermissionSnapshot 一次性灌注 + 只读

| 项 | 内容 |
|----|------|
| **日期** | 2026-06-24 |
| **决策** | Session 创建时从 `User` 记录构建 `PermissionSnapshot`（grouping/company/project/SOP/DB 权限），注入 `SessionContext`，WorkItemAgent 通过 `BusContext` 只读访问。 |
| **原因** | (1) 权限在单次对话内不变，无需重复查询 DB；(2) 只读访问防止 AI Agent 越权篡改；(3) snapshot 模式符合 "权限在对话开始时确定" 的业务语义 |
| **后果** | 权限变更要新对话生效；长期运行 Session 可能需要 TTL 驱动的 re-auth |

### ADR-E07：Sync repo + `asyncio.to_thread` 妥协

| 项 | 内容 |
|----|------|
| **日期** | 2026-06-24 |
| **决策** | Repository 层全 sync（SQLAlchemy sync session），async Service 方法通过 `asyncio.to_thread()` 包裹 repo 调用 |
| **原因** | SQLAlchemy async 与 PostgreSQL `pool_size=5` 配合不佳；sync repo 更易调试和测试；项目规模（~15K LOC）可接受此妥协 |
| **后果** | 不是纯粹 async；高并发下 thread pool 可能成为瓶颈；未来可迁移到 SQLAlchemy async |

### ADR-E08：Prompt 文件集中管理 + 代码回退链

| 项 | 内容 |
|----|------|
| **日期** | 2026-07-01 |
| **决策** | 所有 Agent system prompt 从 Python 字符串常量提取到 `emily-data/prompts/*.md` 文件，通过 `prompt_loader.py` 多级回退加载（文件 → 硬编码兜底）。旧 `routing.md` + `planner.md` 合并入 `session.md` + `workitem.md`，旧 `master_agent.txt` 内容回收。 |
| **原因** | (1) Python 代码中的多行字符串难以浏览、比较、调优；(2) `.md` 文件支持 IDE Markdown 预览和语法高亮；(3) Docker bind-mount `:ro` 支持修改后即时生效无需重启；(4) 硬编码回退确保文件缺失时系统不崩溃 |
| **后果** | 5 份 .md prompt 文件：session / workitem / guardian_step / guardian_reply / project（预埋）。3 个消费者（SessionAgent / WorkItemAgent / RealGuardian）全部接线。向后兼容 `routing` → `session` 别名。 |

### ADR-E09：管理员创建节点自动激活（跳过审批）

| 项 | 内容 |
|----|------|
| **日期** | 2026-07-03 |
| **决策** | 全景节点创建时，若创建人 `permission_level >= 5`（管理员/系统管理员），节点直接以 `CONDITIONS_NOT_MET` 状态创建，跳过 `NOT_ACTIVATED → CONDITIONS_NOT_MET` 的审批环节。创建人同时记为 `approver_id`。普通用户创建节点仍走 `NOT_ACTIVATED` 待审批流程。 |
| **原因** | (1) 管理员本身具有审批权限，创建后再走审批是多余步骤；(2) 管理员通常批量录入节点，逐个审批严重影响效率；(3) 审批机制的目的是防止普通人员越权创建节点，管理员不受此约束 |
| **后果** | `NodeService.create_node` 新增 `is_admin` 检测分支；管理员创建的节点事件类型为 `node_created_auto_activated`（区别于 `node_created_pending_approval`）；`PermissionRepository` 作为 `user_repo` 注入到 `NodeService` |
