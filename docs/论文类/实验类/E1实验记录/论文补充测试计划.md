## 零、背景：为什么需要补充测试

Emily 项目已有 13 份测试报告（累计 60+ 用例，真实 LLM 驱动，通过率 >93%），覆盖了事件记录（SOP-002）、数据查询（SOP-005）、文件管理（SOP-004）、闲聊快速通道等核心路径。

但以下场景覆盖不足：会议纪要录入（SOP-001）、任务创建（SOP-003）、复合请求拆解（SessionAgent is_compound → 多 WorkItem）。本测试计划针对性地补上这些缺口，同时加入论文中最能展示 Emily 架构独特性的场景。

## 二、测试用例

### 测试约定

- **命令模板**：`uv run python .claude/skills/emy-test/cli.py --managed --llm --qq "<QQ号>" --sender "<用户名>" --message "<消息>"`
- **超时**：每个命令最多等待 120 秒。SSE 超时不算 FAIL，记录为 INCONCLUSIVE 并备注。
- **运行间隔**：两个测试命令之间至少间隔 10 秒（让服务端 Session 处理完成）。
- **PASS 条件**：回复符合预期 OR DB 验证通过。两者满足其一即 PASS。
- **FAIL 条件**：HTTP 500 且无合理回复 OR DB 验证结果与预期矛盾。
- **INCONCLUSIVE 条件**：SSE 超时但 Docker 日志显示代码路径正确。

### 多轮对话测试约定

- **同一 sender 的多轮消息**：使用相同 `--qq` + `--sender`，自动归属同一 Session。
- **多轮之间有上下文依赖**：第二轮可以说"确认"或"那帮我再看看..."，Emily 应能关联上下文。
- **多轮之间间隔**：至少 15 秒，让前一轮的 WorkItem 执行完毕。

### 组 B：复合请求与多 SOP 串联（B1-B2）

#### B1. 复合请求拆解 — 一条消息拆为 3 个 WorkItem ★ 亮点场景

**对应论文实验**：E1-13
**为什么需要**：这是论文中最能展示 Emily 核心架构特性（SessionAgent is_compound → N 个 WorkItem）的场景。**这是本次补测最重要的用例。**

**命令**（单轮——注意这是一条消息）：
```powershell
uv run python .claude/skills/emy-test/cli.py --managed --llm `
  --qq "123456001" --sender "王建国" `
  --message "今天周例会结束了，议了三件事：1. 样板段验收通过 2. 安排王工下周做外墙检查 3. 基坑东侧发现渗水已报监理。都帮我记一下"
```

**验收标准**：
1. CLI 输出非空
2. 回复中应体现处理了"多件事"（可能分条回复，或汇总各事项的处理结果）
3. DB 验证（关键——期望 3 张表各有新增）：
```sql
-- 事件：样板段验收 + 基坑渗水（可能 2 条事件）
SELECT no, title, event_type, created_at FROM events
WHERE created_at > '<测试前基线时间戳>'
ORDER BY created_at DESC;

-- 任务：外墙检查
SELECT no, title, assignee, due_date, created_at FROM tasks
WHERE created_at > '<测试前基线时间戳>'
ORDER BY created_at DESC;

-- 会议：周例会本身
SELECT no, title, created_at FROM meetings
WHERE created_at > '<测试前基线时间戳>'
ORDER BY created_at DESC;
```

**评分标准**：
- 3 张表各有新增 → ★★★ 完美（复合请求拆解完全生效）
- 2 张表有新增 → ★★ 良好（部分拆解生效）
- 1 张表有新增 → ★ 基础（LLM 理解了部分意图但未拆解）
- 0 张表新增 → 需排查

**PASS 条件**：至少 2 张表有符合预期的记录。

**Docker 日志验证（补充）**：
```
docker logs --tail 100 emily-core 2>&1 | Select-String "is_compound|WorkItem|sub_task"
```
期望：日志中出现 `is_compound=True` 或多个 WorkItem 创建的记录。

## 三、执行顺序与时间规划

建议按以下顺序执行（总耗时约 60-90 分钟）：

| 阶段 | 用例 | 耗时 | 说明 |
|------|------|------|------|
| 1. 环境检查 | 前置检查 | 5 min | Docker、健康检查、基线快照 |
| 2. 单轮用例 | A1, A2, A3, A4, A5, A6 | 30 min | 每个 3-5 min（含等待） |
| 3. B1 ★ | B1 | 5 min | 最重要用例，发 1 条消息 |
| 4. B2 | B2 | 5 min | |
| 5. 多轮 D | D1 (3步), D2 (2步) | 15 min | 有依赖，必须顺序执行 |
| 6. 多用户 C | C1 (3步) | 10 min | 有依赖，必须顺序执行 |
| 7. 权限 C | C2, C3 | 8 min | |
| 8. 结果验证 | 全量 DB 验证 | 10 min | 汇总所有 DB 新增记录 |

### 注意事项

1. **不要并行发送消息**：同一 sender 的多轮消息必须顺序执行，每轮等 15 秒以上。
2. **多用户测试可以用同一个 PowerShell 窗口**：不同 `--qq` 和 `--sender` 自动创建不同 Session，互不干扰。
3. **如果 SSE 超时**：记录为 INCONCLUSIVE，检查 Docker 日志中是否有 WorkItem 执行记录。
4. **如果回复质量差但 DB 写入了**：仍然可以 PASS（DB 验证优先于回复文本评价）。

## 五、服务端日志检索（辅助诊断）

如果某个用例 CLI 输出异常，执行以下命令辅助排查：

```powershell
# 查看最近 50 行 emily-core 日志
docker logs --tail 50 emily-core 2>&1

# 查看是否有 ERROR
docker logs --tail 100 emily-core 2>&1 | Select-String "ERROR|Traceback|Exception"

# 查看 SOP 路由日志
docker logs --tail 100 emily-core 2>&1 | Select-String "intent|sop=|SOP-"

# 查看 WorkItem 执行日志
docker logs --tail 100 emily-core 2>&1 | Select-String "WorkItem|BUS|langgraph|node"

# mitmproxy 流量分析（如果启用 LLM_TRACE_ENABLED=1）
docker exec mitmproxy tail -5 /app/logs/llm_trace.jsonl
```
