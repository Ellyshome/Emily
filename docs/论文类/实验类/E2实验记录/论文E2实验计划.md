## 一、实验目的与设计原则映射

### 1.1 E2 定位

E2 是 E1（功能正确性量化验证）之上的**定性深度层**。E1 证明"系统能正常工作"，E2 证明"设计原则在真实业务场景中交叉生效"。

E2 采用**一条叙事线 × 三个场景**的结构：以"景观管理经理"（李景利，L4）为主角，串起一个真实业务角色在 Emily 中的典型一天。三个场景不是独立实验，而是同一角色视角下的连续工作流。

### 1.2 场景→设计原则映射表（论文核心素材）

| 场景 | 验证原则 | 系统行为落点 |
|------|---------|-------------|
| 场景① 越级查询指令执行情况 | **P2 团队级训练主体 + P3 自然语言接入** | 集团领导（王建国 L6）无需经过中间层级，直接用自然语言追溯一线部署的执行状态。系统跨表关联会议部署（meetings）→ 任务执行（tasks）→ 完工确认（events），信息从一线透传到决策层 |
| 场景② 日报信息汇总 | **P5 陪跑式信息采集 + P3 自然语言接入** | 日报不是预配置报表模板，而是系统日常陪跑采集的事件/任务/待处理问题，由自然语言动态聚合 |
| 场景③ 特化专家 Agent 审核 | **P4 渐进式知识发现 + P1 ANI 工具化** | 通用 Agent 通过加载特化专家手册（职能手册+任务手册+8维度量化标准）切换为"苗木审核专家"角色，输出量化评分报告。最终决策权仍归人 |

### 1.3 叙事线

```
集团条线领导 王建国（L6 系统管理员）
    │
    │ 场景①：早上，通过 IM 直接询问一线部署执行情况（不需要中间员工汇报）
    ▼
景观管理经理 李景利（L4 工程部经理，本项目主角）
    │
    │ 场景②：上午，要一份昨日景观工作汇总日报
    ▼
李景利 收到设计院的植物设计方案
    │
    │ 场景③：下午，请系统调用苗木审核专家做量化评审
    ▼
得到 8 维度评分报告 + 问题清单 + 修改建议
```

## 三、场景设计

### 场景①：越级查询指令执行情况（验证 P2+P3）★ 核心场景

**业务叙事**：集团条线领导王建国在 7 月 28 日周例会上部署了"景观施工图苗木审核"工作。今天（测试执行日）他直接问 Emily："这项工作完成得怎么样了？"——在传统模式中，他需要打电话给项目经理 → 项目经理查台账 → 层层反馈。在 Emily 模式中，系统直接从会议记录追溯部署、从任务表查执行状态、从事件表找完工确认。

**技术链路预期**：
```
意图识别 → SOP-005-QRY 数据查询
  ↓
LLM 分步查询：
  ① meetings（追溯 7月28日周例会部署内容 + action_items）
  ② tasks（苗木审核任务的 owner/status）
  ③ events（完工确认事件）
  ↓
合成回复：部署内容 + 执行人 + 当前状态 + 完工证据
```

#### 验收标准（PASS/FAIL 判定）

**核心验收（满足任一即 PASS）**：
1. 回复中包含**苗木审核工作的执行状态**（如"已完成""done""8月2日完成"），且提及**张正宏**或**审核报告/评分**等执行细节
2. 回复追溯了**部署来源**（提及"周例会""7月28日""会议部署"之一）

**降级验收（若核心不满足）**：
- 回复至少包含 tasks 或 events 单表查询结果（证明查询链路部分工作）
- 记录实际行为到结果表的"备注"列：LLM 查了哪些表、跳过了哪些关联

**FAIL 条件**：回复与预埋数据无关（查不到苗木审核任务）或报错无回复。

**DB 佐证**（测试后执行，用于论文证据）：

SELECT event_no, title, status, confirmed_at FROM events WHERE event_no='EVT-PAPER-9001';

### 场景②：日报信息汇总（验证 P5+P3）

**业务叙事**：李景利早上到岗，需要一份"昨天景观干了什么、今天要处理什么"的汇总——传统模式靠管理员查台账人工汇总，Emily 模式一句话生成。

**技术链路预期**：
```
意图识别 → SOP-005-QRY
  ↓
query_data（event：最近事件 / summary：项目概览）
  ↓
manage_pending_issues（list_pending：待处理问题清单）
  ↓
LLM 合成日报式回复
```

**测试命令**：
```powershell
uv run python .claude/skills/emy-test/cli.py --managed --llm `
  --qq "123456002" --sender "李景利" `
  --message "帮我汇总一下昨天翠湖庭院的景观工作情况和今天要处理的事项"
```

**验收标准（PASS/FAIL 判定）**：

| 维度 | PASS 条件 | 备注 |
|------|----------|------|
| 昨日成果 | 回复包含事件类信息（如"样板段""铺装""验收"等场景①预埋的事件） | 若系统数据中"昨天"（测试日-1）恰有 EVT-PAPER-9002（event_date=2026-08-11）则命中 |
| 今日待办 | 回复包含任务/待办信息（tasks 或 pending_issues） | — |
| 汇总形态 | 回复是结构化汇总（分项列出），而非单条记录 dump | 宽松判断：出现两个以上信息板块 |

**PASS 条件**：上述 3 项中至少 2 项满足。
**FAIL 条件**：回复为空、报错、或与项目数据完全无关。

**文件佐证**（待处理问题清单是文件型服务，非 DB 表）：

**业务叙事**：设计院提交了星湖湿地公园植物设计说明。李景利请求系统"按公司苗木审核标准做专业评审"——系统自动匹配 EXP-001 苗木审核专家，加载职能手册（8 维度标准+红线）+ 任务手册（权重+评分分级），输出量化评分报告。**人做最终决策，AI 是增强工具（P1）。**

**技术链路预期**（已确认 SOP-012 全链路已实现）：
```

  ↓
ExpertManualLoader → 加载职能手册 + 任务手册 + 待审文件
  ↓
LLM chat_json（expert_model）→ 结构化审核
  ↓
结果归一化 → 8 维度评分报告
```

**验收标准（PASS/FAIL 判定）**：

| 验收项 | PASS 条件 |
|--------|----------|
| 路由正确 | Docker 日志出现 SOP-012 或 expert_review 或 EXP-001 相关记录 |
| 手册加载 | 日志出现 ExpertManualLoader 或"手册"加载记录（若日志不可见，跳过此项） |
| 量化评分 | 回复含 0-100 总分（或"分"字样数字） |
| 维度明细 | 回复含 ≥5 个审核维度得分（乔木密度/草灌比/换土与种植穴/土壤理化/种植间距/苗木规格/成活率/生物多样性 八选五） |
| 问题清单 | 回复含问题列表，且问题引用具体标准依据（如"CJJ 82-2012""红线""标准"等字样） |
| 结论分级 | 回复含结论（通过/修改后通过/重做 之一） |

**PASS 条件**：量化评分 + 结论分级 2 项必备，其余 4 项至少满足 2 项。
**FAIL 条件**：回复未触发专家审核（走普通对话或普通查询路径）。

**已知审核素材**（论文写作用，测试者无需关心）：
- 待审文件中的换土设计："乔木种植穴深度 0.8m，直径 1.2m" —— 低于职能手册红线（中小乔木换土深度 ≥1.0m、种植穴 ≥1.2m），审核应能发现此问题
- 若审核报告 score 落在 70-84 分区间 → 结论应为"修改后通过"

## 七、注意事项

1. **QQ 号必须真实**（123456001-007 系列），伪造 sender 会被自动创建为 level=1 用户，测试结果不可信
2. **预埋数据编号固定**（MTG-PAPER-9001 / TSK-PAPER-9001 / EVT-PAPER-900x），幂等可重复执行，测试完成后可清理（DELETE WHERE 编号 LIKE '%PAPER-90%'）
3. **场景②的"昨天"是相对日期**：EVT-PAPER-9002 的 event_date 固定为 2026-08-11，若测试执行日不是 2026-08-12，场景②"昨天"可能查不到该事件——此时以"最近事件"口径判定 PASS 即可
4. **场景③若走普通查询路径**（未触发 SOP-012）：检查 experts 表 status 是否 ACTIVE；日志查 `_match_expert` 是否被调用；必要时重发一次
5. **mitmproxy 日志**仅在 `LLM_TRACE_ENABLED=1` 时可用；若不可用，量化指标改为从 `llm_interaction_logs` 表查询：
   ```sql
   SELECT id, model, prompt_tokens, completion_tokens, created_at
   FROM llm_interaction_logs ORDER BY created_at DESC LIMIT 10;
   ```
6. **测试完成后数据清理**（可选，保留也可作为论文证据）：
   ```sql
   DELETE FROM events  WHERE event_no  LIKE 'EVT-PAPER-%';
   DELETE FROM tasks   WHERE task_no   LIKE 'TSK-PAPER-%';
   DELETE FROM meetings WHERE meeting_no LIKE 'MTG-PAPER-%';
   ```
