# 论文对比验证实验计划（轻量版）

> 版本：v1.0 | 日期：2026-08-12
> 目标：用 1-2 组可控对比数据，量化"传统人工汇总 vs Emily 自动汇总"的效率差异，直接支撑论文核心价值主张"重构团队信息流"
> 性质：轻量实验——复用已有数据、1 名计时人员、约 1 小时执行、无需改代码
> 产出：一张对比表 + 2-3 个有说服力的数字，写入论文第 5 章新增小节（5.3.5 或 5.4）

---

## 一、实验设计原则

1. **同数据、双路径**：两条路径处理的是**同一组已积累的项目运行数据**——对比的公平性建立在"输入相同"之上，差异仅在于"信息流路径"
2. **保守计测**：传统路径的执行者应尽量模拟真实场景（从原始聊天记录/台账中翻查），且执行者若为系统开发者本人，实际传统路径耗时只会被**低估**（他知道数据在哪）——结果偏向保守，审稿人无法质疑夸大
3. **诚实呈现**：论文中如实标注"基于同一组项目运行数据的两条汇总路径实测对比"，不宣称"长期生产观察"

## 二、对比一：日报汇总（主推，必做）

### 任务定义

生成一份"某项目昨日景观工作日报"，须包含三类内容：
- 昨日已确认成果
- 待认证事项
- 今日待办任务

### 路径 A：传统方式（模拟）

```
项目人员 → 微信群 → Excel/Word 台账 → 部门经理汇总 → 日报
```

**模拟方式**（利用现有数据）：
1. 执行者从数据库导出"昨日"的原始数据作为台账材料：
   ```powershell
   docker exec emily-postgres psql -U emily -d emily -c "SELECT created_at, title, status, description FROM events ORDER BY created_at DESC LIMIT 30;"
   docker exec emily-postgres psql -U emily -d emily -c "SELECT title, status, due_date, owner_text FROM tasks ORDER BY created_at DESC LIMIT 20;"
   ```
2. 将导出结果放入一个 Excel/Word 文档（模拟"项目人员汇总上来的台账"）
3. 同时准备"聊天记录"材料：从 messages 表导出最近的用户消息（模拟微信群翻查）：
   ```powershell
   docker exec emily-postgres psql -U emily -d emily -c "SELECT created_at, direction, content FROM messages WHERE direction='user_to_agent' ORDER BY created_at DESC LIMIT 40;"
   ```
4. 执行者计时开始：翻查上述两份材料 → 手工整理出日报 → 计时结束
5. 记录：**信息收集时间**（翻查聊天记录）、**人工整理时间**（写日报）、**参与人数**（几人参与此过程，模拟场景记为 2-3 人：一线人员+汇总人员）、**数据来源数量**（翻查了几份材料）

### 路径 B：Emily

```powershell
uv run python .claude/skills/emy-test/cli.py --managed --llm `
  --qq "123456002" --sender "李景利" `
  --message "帮我汇总一下昨天本项目的景观工作情况和今天要处理的事项"
```

1. 计时开始：发送消息
2. 计时结束：收到完整回复
3. 记录：耗时（秒）、参与人数（1 人）、数据来源数量（1 个对话入口）

### 信息完整度校验（关键，保证公平）

预定义 **6 个必报信息点**（从数据中选取昨日真实存在的记录，执行前由实验设计者确认存在）：

| # | 信息点 | 来源 |
|---|--------|------|
| 1 | 景观进场安全交底已完成（已确认） | events 表 |
| 2 | 样板段验收通过（待确认） | events 表 |
| 3 | C区滨水步道样板段施工完成约80平米（待监理验收） | events 表 |
| 4 | 苗木采购进场验收（待办，黄工） | tasks 表 |
| 5 | 硬质铺装与园路施工（待办，黄工） | tasks 表 |
| 6 | 审核景观绿化施工方案（进行中，李经理） | tasks 表 |

> 注意：具体信息点以执行日数据的实际情况为准，执行前先从 DB 确认"昨日"有哪些事件/任务，取 6 个真实存在的作为校验点。

**完整度 = 两条路径各自覆盖的信息点数 / 6**

## 六、注意事项

1. **执行者选择**：传统路径的执行者最好是**非 Emily 深度开发者**（如同事），避免"太熟悉系统"导致低估传统耗时——若只能作者自己做，结果仍保守可用
2. **材料真实性**：台账材料必须与 Emily 读取的数据完全一致（同一 DB 导出），保证"同数据"前提
3. **不刻意放水**：传统路径中执行者应真实翻查，不要刻意拖时间；Emily 路径若一次失败可重试，记录重试次数
4. **日期口径**：容器时钟与宿主机可能偏差 1 天（E2 报告 6.2 节已记录），"昨日"以 DB 中最近一天的完整数据为准，两条路径用同一日期口径
