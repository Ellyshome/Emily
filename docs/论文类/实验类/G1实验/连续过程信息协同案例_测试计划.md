## 1. 测试定位与范围

### 1.1 定位

- **层级**：E2 级（设计原则 / 路线闭环验证），非 E1 功能正确性。
- **目标**：验证 PRD 第 2 节的三问——信息能否低门槛进入、能否跨角色跨时间关联、未参与人能否回溯全程 + 溯源到人。
- **范围**：限定在 `docs/论文类/实验类/G1实验/` 的实验设计，**不改系统**（零代码约束）。

### 1.2 与现有验证的关系

| 现有验证 | 性质 | 本案例补足 |
|---------|------|-----------|
| 5.2 功能正确性 | "点"验证（单次闭环） | 不涉及 |
| 5.3 三场景 | "点"验证（原则落地） | 不涉及 |
| 5.4 溯源 / 遮阴网对比 | 预埋数据 + 单次查询演示 | **补足"信息在过程中逐步长出"的"线"验证** |

## 2. 环境与角色准备

### 2.1 测试框架

复用 emy-test 框架：

```powershell
uv run python .claude/skills/emy-test/cli.py --managed --llm `
  --message "<消息>" --sender "<真实用户名>"
```

### 2.2 前置检查

1. 确认 emily-core / emily-postgres 容器运行中：
   ```powershell
   docker compose -f docker-compose-napcat.yml ps emily-core
   ```
2. 确认 LLM 流量代理（mitmproxy）状态（用于三重证据法之③运行日志核查）：
   ```powershell
   docker compose -f docker-compose-napcat.yml ps mitmproxy
   ```

### 2.3 角色准备（遵循 CLAUDE.md emy-test 强制规则）

> **强制规则**：`--sender-id` 必须使用 `users` 表中真实存在的用户 UUID；推荐用 `--sender "用户名"` 自动从 users 表 + user_im_bindings 解析。随便编 ID 会污染 users 表并导致权限降级到 level 1，测试结果不可信。

从 `users` 表选取 4 个真实用户，权限级别 ≥ 3，分别扮演：

| 角色 | 职务定位 | 阶段 |
|------|---------|------|
| 项目经理 | 问题提出 + 最终决策确认 | 阶段 1、4 |
| 设计负责人 | 原因分析 | 阶段 2 |
| 工程负责人 | 处理方案 | 阶段 3 |
| 未参与人 | 回溯查询（全程未参与前 4 阶段） | 阶段 5 |

前置查询：

```powershell
docker exec emily-postgres psql -U emily -d emily -c "SELECT id, username, permission_level FROM users WHERE status = 'active' ORDER BY permission_level DESC LIMIT 10;"
```

### 2.4 目标项目

确认目标项目（如"翠湖庭院"）存在：

```powershell
docker exec emily-postgres psql -U emily -d emily -c "SELECT id, code, name, status FROM projects ORDER BY created_at DESC LIMIT 10;"
```

## 3. 测试脚本（逐阶段）

> 每阶段含：输入消息 → 期望行为 → DB 断言。项目名称与业务编号在论文呈现时做隐写处理（沿用 V2.0 5.1 节规则）。

### 阶段 0：基线快照

执行前记录 events 表当前最大时间戳 / 最新 event_no，作为"新增 4 条"的判定基线：

```powershell
docker exec emily-postgres psql -U emily -d emily -c "SELECT no, title, created_at FROM events ORDER BY created_at DESC LIMIT 3;"
```

### 阶段 1：问题发现（项目经理）

- **输入消息**：
  > "样板区东侧铺装颜色和效果图差异比较大，需要重新核一下，帮我记一下"
- **期望行为**：路由 SOP-002 → 创建事件（`quality_issue`），返回事件编号 EVT-1。
- **DB 断言**：
  ```sql
  SELECT no, event_type, related_event_ids, user_id, confirmed_by, status
  FROM events WHERE title LIKE '%铺装%' ORDER BY created_at DESC LIMIT 1;
  ```
  - 断言：`event_type = quality_issue`；`related_event_ids = []`（锚点事件，无前向关联）。

### 阶段 2：原因分析（设计负责人）

- **输入消息**（显式带锚点编号）：
  > "样板区东侧铺装（EVT-1）那个问题，主要是材料批次的问题，设计方案本身没有变化，帮我记一下"
- **期望行为**：创建事件（`design_change` 或 `general`），LLM 提取锚点编号填入 `related_event_ids = ["EVT-1"]`。
- **DB 断言**：
  ```sql
  SELECT no, event_type, related_event_ids, user_id FROM events
  WHERE title LIKE '%材料批次%' OR description LIKE '%材料批次%' ORDER BY created_at DESC LIMIT 1;
  ```
  - 断言：`related_event_ids` 含 `EVT-1`。
  - **风险点**：LLM 是否正确回填 `related_event_ids`——本案例最大不确定性，重点观察。

### 阶段 3：处理方案（工程负责人）

- **输入消息**（显式带锚点编号）：
  > "样板区东侧铺装（EVT-1）的问题，供应商会重新提供三组样品，下周一确认，帮我记一下"
- **期望行为**：创建事件（`general`），`related_event_ids = ["EVT-1"]`。
- **DB 断言**：同阶段 2，断言 `related_event_ids` 含 `EVT-1`。

### 阶段 4：结果确认（项目经理）

- **输入消息**（显式带锚点编号）：
  > "样板区东侧铺装（EVT-1）的问题已解决，新样品确认第二组，后面全部按这个执行，帮我记一下"
- **期望行为**：创建事件（`decision`），`related_event_ids = ["EVT-1"]`。
- **DB 断言**：同阶段 2，断言 `related_event_ids` 含 `EVT-1`，`event_type = decision`。

### 阶段 5：回溯查询（未参与人）

- **输入消息**：
  > "样板区东侧铺装的问题后来是怎么处理的？"
- **期望行为**：未参与人（全程未参与前 4 阶段）能通过自然语言查询，系统跨事件聚合出 Day 1 → Day 7 时间线。
- **验收断言**：
  - 回复含"问题发现 → 原因分析 → 处理方案 → 结果确认"的完整链路（或等价语义）。
  - 追问溯源：
    > "这个铺装问题是谁记录的？"
  - 断言：回复给出记录人（项目经理）+ 岗位，命中率 100%。

## 4. 关键验证点（零代码风险聚焦）

| # | 验证点 | 风险等级 | 说明 |
|---|--------|---------|------|
| 1 | **关联回填**：LLM 能否在录入时正确提取 `related_event_ids`（显式带编号时） | 高 | 最大不确定性，阶段 2/3/4 重点观察 |
| 2 | **回溯聚合**：阶段 5 能否跨事件正确聚合时间线 | 中 | 依赖 LLM 语义拼装；日报场景已证明可行但需复验 |
| 3 | **溯源命中**：`build_trace` 复验 | 低 | 5.4.1 已实证 100%，本案例再证 |

## 5. 数据采集与证据

采用**三重证据法**（沿用 V2.0 5.1 节）：

1. **回复文本**：观察系统回复是否满足预期语义。
2. **数据库直查**：验证 events 表 4 条记录真实落库 + `related_event_ids` 链正确 + 溯源字段完整。
3. **运行日志**：核查意图路由（SOP-002）、工具调用（`record_event`）、状态流转是否按设计路径执行。可用 mitmproxy jsonl 日志佐证 LLM 结构化输出内容：
   ```powershell
   docker exec mitmproxy tail -1 /app/logs/llm_trace.jsonl
   ```

## 7. 失败预案

| 失败情形 | 处理 |
|---------|------|
| `related_event_ids` 未被 LLM 回填 | 记录为诚实发现；改为"人工录入时 LLM 关联能力边界"分析，或降级为纯事件时间线演示（靠 `query_events` + 时间排序聚合，不依赖关联链） |
| 回溯聚合不稳定（时间线错乱/遗漏） | 诚实报告"关联链确定、语义聚合依赖 LLM"，反而强化论文克制立场 |
| 某阶段录入被守护核验拦截 | 按系统流程处理（确认或 force）；若产生 PND，作为 PRD 第 6 节"加分项"记录 |
| 目标项目不存在 | 换用真实存在的项目（如翠湖庭院），或先创建测试项目 |
