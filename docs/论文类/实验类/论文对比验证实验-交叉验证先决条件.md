> 版本：v1.1 | 日期：2026-08-14
> 定位：支撑论文核心价值主张"重构团队信息流"的对比实验
> 配套预埋：`seed_compare.sql`（同目录）
> 测试工具：emy-test CLI
> 触发背景：原对比实验计划（日报汇总效率）被否定——只体现"工具效率"，未体现 Emily 的核心价值

---

## 一、实验要论证的立论

论文核心价值主张：**Emily 提供完整的任务推进记录，这些记录构成一条证据链，可组合成完整的交叉验证。**

这一主张的精确边界（与 P1 原则"权威在人"一致）：

- Emily **不替代**交叉验证的判断本身（对比照片、核对日期仍由人完成）
- Emily 的价值是**提供完整的证据链**——从指令下达、任务下发、完工上报、认证到验收检查，每一环节由不同角色在不同时间留痕，使交叉验证第一次具备完整的素材

> ⚠️ 表述红线：写"提供完整的任务推进记录，作为证据链，可组合成交叉验证"，**不**写"Emily 自动完成交叉验证"。

## 二、实验设计

### 2.1 对比对象：同一指令、两个项目

**集团指令**（7 月 15 日，王建国下达）：
> 所有在建项目的地被苗木与重点点睛苗木，须在 7 月 20 日前完成遮阴网覆盖；遮阴网须满足遮光率 ≥ 70%、四周压实固定、无漏搭。

| | 项目 A（翠湖庭院，使用 Emily） | 项目 B（滨江府，未使用 Emily） |
|---|---|---|
| 呈现方式 | 预埋数据进 DB，系统自动汇聚 | 纯文字历史记录（工程实践真实形态） |

### 2.2 项目 B：传统模式的历史记录（素材，不进 DB）

传统模式下，各角色**其实都留了痕**，但散落在不同媒介、互不相通：

| 时间 | 角色 | 留下的"事件" | 存放位置 |
|------|------|-------------|---------|
| 7/15 | 领导 王建国 | 集团群下发指令 | 集团微信群（滚动淹没） |
| 7/16 | 项目经理 陈建华 | 项目群 @工长布置 | 项目内部微信群 |
| 7/18 | 工长 | 拍完工照片 + "弄完了" | 微信（图片 7 天过期） |
| 7/19 | 监理 | 巡检日志"已覆盖，基本符合" | 监理纸质日志 |
| 7/20 | 资料员 | 台账填一行 | 个人电脑 Excel |

**7/22 领导想核查落实情况的处境**：
- 五条记录散在五个地方、五个人手里，**没有任何一个视图能放一起**
- 唯一能问的人，链条上每个人都是"自己说自己那一环"
- 无法回答："工长说 7/18 完成、监理说 7/19 基本符合，中间差在哪？""遮光率真测了吗？"

**关键**：记录一样存在、一样是多人、一样有时间——**但它们是孤岛，散落各处、没有证据链，交叉验证无从谈起**。差异不在"有没有记录"，而在"记录能否串成一条完整的证据链"。

### 2.3 项目 A：Emily 下的多来源汇聚（预埋数据）

同一指令，Emily 下所有留痕进入**同一项目底座**，角色/时间/来源天然对齐：

| 留痕 | 来源人 | 角色 | 时间 |
|------|--------|------|------|
| 任务下发 TSK-CMP-9001 | 王建国 | 指令下达 | 7/15 |
| 全景节点 SG-CMP-9001 | 王建国 | 节点创建 | 7/15 |
| 完工上报 EVT-CMP-9001 | 张正宏 | 执行人（工长） | 7/18 |
| 认证 | 李景利 | 认证人 | 7/18 |
| 验收检查 EVT-CMP-9002 | 李景利 | 第二来源 | 7/19 |
| 照片存放地址 | 张正宏 | 完工照片 | 已关联（attachments 字段，不实际放图） |

**核心特征**：多人（王建国 ≠ 张正宏 ≠ 李景利）× 多时间（7/15/7/18/7/19）× 多渠道（任务/节点/事件×2）。

## 三、测试序列与验收

### 3.1 预埋执行

```powershell
docker exec -i emily-postgres psql -U emily -d emily < "docs\论文类\实验类\E2实验记录\seed_compare.sql"
```

**期望**：4 条记录（1 任务 + 1 节点 + 2 事件）。

### 3.2 场景①：跨来源自动汇聚（核心）

```powershell
uv run python .claude/skills/emy-test/cli.py --managed --llm `
  --message "7月15日部署的遮阴网覆盖工作，翠湖庭院落实得怎么样了？" --sender "王建国"
```

**验收标准**（PASS 判定）：
- 回复包含**任务下发来源**（"7月15日部署"/TSK 编号）
- 回复包含**完工上报**（7/18、执行人张正宏、遮光率 72%）
- 回复包含**验收检查**（7/19、第二来源李景利）
- 三者**日期/标准项交叉对应**（遮光率、固定方式、无漏搭在多来源中一致）

**实测已通过**（见附录对话原文）。

### 3.3 场景②：多留痕溯源（交叉验证的另一半）

```powershell
uv run python .claude/skills/emy-test/cli.py --managed --llm `
  --message "遮阴网覆盖完成这条是谁上报的？验收检查又是谁做的？" --sender "王建国"
```

**验收标准**：完工上报=张正宏、验收检查=李景利，且能区分"上报人≠验收人"，溯源到具体角色。

**实测已通过**。

## 四、对比结论（论文写作核心句）

| 维度 | 项目 B（无 Emily） | 项目 A（Emily） |
|------|-------------------|----------------|
| 记录是否产生 | 是（5 条） | 是（6 条） |
| 记录是否汇聚 | ❌ 散落 5 个媒介 | ✅ 汇聚一个底座 |
| 是否构成证据链 | ❌ 孤岛，无链条 | ✅ 指令→下发→上报→认证→验收，环环相扣 |
| 能否交叉验证 | ❌ 各说各话，无从对照 | ✅ 证据链完整，可组合交叉验证 |
| 领导核查方式 | 逐人电话/翻群 | 一次自然语言查询 |

**论文结论句（草拟）**：

> 传统模式下，指令的执行、记录、上报由同一套班子完成，信息虽多人产生，却散落各处、缺乏汇聚点，无法构成证据链，交叉验证无从谈起；Emily 并非替代校验本身，而是通过陪跑式信息采集，将指令下达、任务下发、完工上报、认证与验收检查各环节由不同角色在不同时间留痕，**提供完整的任务推进记录，作为证据链，可组合成完整的交叉验证**——这本身就是团队信息流的一次结构性改进。
