
# 一、4处我认为必须改

## 1. 摘要里的“研究表明”仍然偏强

现在摘要写：

> “研究表明，该框架能够……” 

但V5已经主动把第五章从“验证”降成了“应用说明”，所以这里再写“研究表明”会造成**证据等级不一致**。

你现在的逻辑实际上是：

> 框架设计 + 两个工程应用实例说明。

而不是：

> 实验验证框架有效。

### 建议改成：

> **“两个业务实例表明，在本文应用场景下，该框架能够……”**

或者更克制：

> **“工程应用实例说明，在本文场景下，该框架能够……”**

我更推荐第二种。

---

## 2. 第2章对“三书”的定义很好，但“Harness”需要稍微技术化处理

现在：

> “团队Harness需要持续获得项目运行过程中的公共上下文……” 

以及：

> “通用LLM/Agent向行业项目团队公共Harness特化……” 

这个概念是你文章比较有特色的部分，但对于工程管理期刊来说，**Harness不是天然通用术语**。

问题不是不能用，而是第一次出现时最好给出定义。

### 建议改成：

> **“团队级Agent Harness（即面向团队运行的Agent公共运行支撑环境）……”**

后面就可以简称：

> 团队Harness。

另外，我建议把：

> “通用LLM/Agent向行业项目团队公共Harness特化”

略改成：

> **“通用LLM/Agent向行业项目团队公共运行环境特化过程中形成的认知组织模型”**

这样学术味更强。

---

## 3. 图4现在仍然和图3有明显重叠

这个问题从当前文件看，**仍然存在**。

图3已经是：

> 用户 → IM → SessionAgent → WorkItemAgent → GuardianAgent → 人工确认/执行 + 三书/DB/RAG/Skill/Plugin。

而图4又是：

> 用户任务 → SessionAgent → WorkItem → 三书 → WorkItemAgent → Guardian → 人工确认 → 业务结果。

这两张图的**信息维度高度相同**。

所以前面我们讨论的结论仍然成立：

> **图4不要再画一次“执行链”。**

现在既然三书已经被你提升为论文核心概念，我建议最终把图4改成：

### **图4 三书驱动的信息协同运行闭环**

核心表达：

```text
团队日常业务活动
      ↓
IM / DB / 文件 / 事件记录
      ↓
项目过程信息进入系统
      ↓
项目态势书
      ↓
Agent任务
 ↙          ↘
组织规则书   系统能力书
 ↓            ↓
规则约束     能力调用
      ↓
   业务执行
      ↓
人工确认/业务结果
      ↓
产生新的过程事件
      ↓
回写项目态势书
      ↺
```

这样四张图各司其职：

> 图1：研究路线
> 图2：管理对象如何推导框架
> 图3：框架静态架构
> 图4：框架如何持续运行

**这一步我建议定稿时一定做。**

# 4. “三书”的第一次定义已经很好，但4.2还可以再补一个关键层次关系

当前3.2已经明确写：

> “三书属于框架的认知组织层……而不是Agent执行模块。” 

这是非常重要的，我建议保留。

但第4章的结构图3中，目前三书和Agent处在比较混合的视觉关系。

正式制图时建议明确画成：

```text
┌─────────────────────────────┐
│       团队公共认知层         │
│  项目态势书 / 规则书 / 能力书 │
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐
│         Agent执行层          │
│ Session / WorkItem / Guardian│
└──────────────┬──────────────┘
               ↓
        业务工具/人工
```

不要把“三书”画成和三个Agent并排的六个模块。

论文文字现在已经解决了这个概念问题，**图也必须体现出来**。

# 二、5处建议优化

## 5. 2.1中的“RAG与Memory分别支撑……”建议换一个更准确的说法

现在：

> “RAG与Memory分别支撑外部知识检索和长期信息组织……” 

这里虽然没错，但Memory不是一个单一技术机制，而是一个研究方向。

建议：

> **“RAG主要支持外部知识检索，Agent Memory研究则关注长期信息的组织与利用……”**

这样更严谨。

---

# 6. 表2里的“RAG+结构化DB”稍微容易让人误解

现在：

> RAG的对应机制：**三书+结构化DB**。

实际上三书不是RAG的技术补丁。

你的真正论点是：

> **RAG负责语义检索，DB负责结构化状态，三书负责认知对象组织。**

所以表2这一格我建议写：

> **“三书认知组织 + RAG/DB双路径”**

这样技术关系非常清楚。

# 7. 4.2.4出现了重复句

这一段：

下一段又：

> “三书采用‘共享地图、按需探索’的方式运行……”

合并即可：

> **“三书并不是三个独立数据库，而是三个逻辑认知对象，采用‘共享地图、按需探索’的方式运行，即‘任务识别→三书目录/摘要→按需深入→WorkItem执行与核验’。”**

然后继续：

> “这种组织方式……”。

# 8. “热记忆”这个词已经可以用，但最好给出你的专门含义

你现在把：

> “项目热记忆”

作为三书形成逻辑的核心。

这是有特色的，但“热记忆”容易被理解为：

> LLM上下文窗口里的短期记忆。

而你实际上说的是：

> **项目当前持续变化、与日常运行高度相关的活跃过程信息。**

所以可以第一次出现时写：

> **“项目运行过程中的热记忆，即持续变化并与当前业务状态高度相关的过程信息”**

后面再简称：

> 项目热记忆。

这样你的概念就不会飘。

---

# 9. 第5章现在已经够轻，但摘要/结论与第5章的证据等级要完全统一

第五章已经明确写：

> “不以应用案例进行统计意义上的性能验证，而以实际业务实例说明……” 

这是正确的。

因此全文建议统一使用：

> **说明、展示、表明在本文场景下**

而尽量避免：

> 验证有效性
> 证明可行
> 证明具有普适性

目前结论：

> “两个实际业务实例说明……” 

已经基本符合，不需要大改。

# 三、我认为现在“三书”已经成为全文真正站得住的概念

这一版有一个明显进步。

现在“三书”已经形成：

### 来源

> 团队公共认知问题 → 三类认知对象。

### 定义

> 项目态势 / 组织规则 / 系统能力。

### 层级

> 属于认知组织层，不属于Agent执行模块。

### 实现

> DB / RAG / Event / Skill / Plugin等底层能力。

### 运行方式

> 共享地图、按需探索。

这已经不是一个“好听的概念”，而是一个**完整的架构抽象**。

# 五、全文还有一个潜在的“创新性审稿问题”

这是我现在最需要提醒你的地方。

你现在已经明确：

> 不提出新基础模型；
> 三书、FSM、Skill、Multi-Agent都是成熟技术的领域化组合。

这很诚实，但也会带来一个问题：

> **“那么你的创新到底是什么？”**

目前你的答案是：

> **领域管理结构驱动的Agent框架设计方法。**

这基本够，但还可以进一步凝练成一句**可判定的研究命题**：

> **本文的创新不在于提出新的Agent基础组件，而在于提出一种由行业项目管理对象反向驱动Agent认知与执行结构的领域化框架设计方法。**

建议在1.4或者3.2最后再出现一次。

这样审稿人不会把你的工作理解成：

> 三书 + FSM + Skill + Multi-Agent = 简单拼装。

而会理解成：

> **管理结构 → 技术结构的映射方法**

才是你真正的贡献。
