# 一、基于全景节点的可见信息控制与鉴权模型

## 1.1 问题背景：地产项目信息共享的"最小可见"需求
- 地产项目涉及多专业、多参建单位，数据共享须遵循最小可见原则。
- 典型约束：成本预算、财务类数据仅对部门内部及特定管理层开放；特定工序施工日志仅对本专业条线开放。
- 由此形成"组织边界即信息边界"的领域特征，要求权限模型以组织单元而非单点角色为基本粒度。

## 1.2 模型设计：全景节点作为鉴权与可见性组织单元
- 以全景节点为基本组织单元，将项目资料按节点打包为专项信息包，节点参与者对对应信息包具备访问权。
- 人员以所在企业为元组（企业参与哪些节点，即对哪些节点信息可见），实现同一数据源下的差异化可见范围。
- 权限上下行均限定于节点内：节点参与者权限被约束在所属节点，信息上行（成果上报）与下行（资料下发）均在节点范围内。

## 1.3 节点治理：操盘企业分级员工的规则定义权
- 操盘企业对应级别员工依据权限细分，可创建节点、定义可见信息范围及节点闭合成果验收条件。
- 约束：可见信息范围不超过创建者自身可见信息范围，防止越权扩散。

## 1.4 与现有框架的关系
- 该模型将"权限与人工责任边界"从抽象原则具体化为"全景节点—信息包—企业元组—节点内上下行"的数据层可见性结构。
- 为 GuardianAgent 的权限核验提供结构化的可见性判定依据。

# 二、语义意图服务与固定页面服务的范式差异

## 2.1 核心定位论断
- Emily 与传统系统管理软件的最大区别在于服务范式：
  - 前者：基于语义理解的意图服务（用户表达意图，系统理解并组合能力达成）；
  - 后者：基于固定预设需求的页面服务（功能以固定页面/菜单承载）。

## 2.2 能力组织方式转变：从独立 APP 到模组化能力
- 开发对象由独立 APP 转向一组可被发现、调用、组合协作的模组化能力。

## 2.3 三层能力组织原则
- 高频独立能力 → 封装为 Skill；
- 固定且复杂任务 → 制作为独立 Agent 负责规划；
- 保底业务流 → 由 Agent 基于基座功能自行临时组合规划（高权限用户特有）。

## 2.4 价值与定位
- 该原则是 Emily 作为协作平台能力扩展的重要路径，契合地产管理需求细碎、使用门槛低的行业特征，有助于降低培训与沟通成本。
- 是 AI 能力整合进入地产行业的重要原则。
