# 一、最重要的两个问题

## 1. 4.4.4“Emily系统目前实现”这一段，还是略微超出了现有证据

你现在写：

> “Emily系统目前实现的Skill执行遵循‘Skill Schema → 参数映射 → Tool Binding → Output Template → 核验’的链路。”

然后举SOP-032作为证据。

这个方向总体正确，因为实验原文确实明确记录了：

> WorkItemAgent加载 `SOP-032-DOC-rectification_notice`，将信息映射为结构化模板参数；之后生成《返工整改通知单》，再由Guardian核验。

所以**“参数映射—工具/模板—核验”是有证据的**。

但是：

> **“Skill Schema”**

这个术语在实验原文中并没有被明确展示。

也就是说，如果你真实系统里确实有正式的Skill Schema，那没问题；如果这个Schema只是我们前面从架构上抽象出来的，就不能把它写成“Emily目前实现”。

### 更稳的写法

改成：

> **从案例A可观察到，Emily系统中的Skill执行已经形成“Skill加载—参数映射—工具/模板调用—结果核验”的执行链。以整改通知Skill为例……**

这样完全落在现有实验事实之内。

# 二、4.5.1“权限快照”仍然需要谨慎

你现在写：

> “SessionAgent在会话启动时获取当前用户权限的只读快照……”

这个东西**不是实验记录直接证明的事实**。

实验A/B能够证明的是：

* 系统会查询用户权限；
* Guardian会进行权限核验；
* 具有副作用的执行前会再次核验；
* 权限不足时会采取限制或协作导航。 

但是：

> “会话启动时缓存权限只读快照”

属于更具体的架构实现细节。

### 如果真实代码就是这样

可以保留。

### 如果这是架构设计

建议改成：

> **“SessionAgent可在会话层获得当前用户权限信息，用于任务规划与路由；实际资源访问及具有副作用的操作仍在执行边界重新核验。”**

这样不会虚构一个你没有展示证据的“snapshot机制”。

# 三、4.3.2现在已经基本改对了，但4.3.3还有一个小风险

你现在写：

> “只有在节点要求的完工资料、现场验收或签认条件满足后，才允许状态进入相应的后续节点。”

这句话还是稍微有点绝对。

因为实验A实际上证明的是：

> `待签认 → 整改中`

在人工确认和Guardian核验后发生。

它并没有充分证明所有节点都严格采用：

> 完工资料 + 现场验收 + 签认

三者全部满足才允许状态转换。

### 建议改成：

> “只有在节点预设的相应成果条件、业务规则或人工确认条件满足后，才允许状态进入相应的后续节点。”

这样更准确，也更有普适性。
