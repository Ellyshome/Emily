## 1 引言

*定位：完成「行业困境 → AI缺口 → 技术本质 → 研究问题」的递进立题。*

### 1.1 研究背景：行业困境与AI缺口

- 困境一（信息跟人走）：现场信息、沟通记录、会议纪要和业务文件分散在人员、IM及不同系统中，大量过程信息难以持续沉淀并保留上下文；项目经验高度依赖具体人员，人员离岗后历史信息、判断依据与处理过程容易失去关联。
- 困境二（存量知识用不起来）：企业信息沉淀量巨大而精力有限，难以活化复用；传统数字化系统只擅长预设流程与结构化数据，对自然语言过程信息和非预设任务无力，且培训成本高、跨企业难复用、可参与人少。
- 与此同时，AI技术正加速渗透各行业并产生实际赋能，但在地产行业，其效能现状是「单人单任务」：通用AI应用集中于BIM、进度、质量等单点任务，或面向个人的问答与文书工具，以个人会话为中心，难以持续进入团队信息流并形成组织公共认知。
- 行业真正缺的不是「能回答问题的AI」，而是一个团队向的AI工具层：AI能否进入一个组织，拥有持续的公共上下文，并在明确的权责边界内参与工作协同。

### 1.2 技术本质与人机分工：落地关键在Harness

- 当前人工智能处于弱AI（ANI）阶段，本质是根据训练权重对输入信息做关联运算，无长期记忆、上下文窗口有限，单次会话难以承载项目级的持续认知。
- 由此推导出合理的人机分工：AI承担信息检索、关联与分析；任务发布、审核与决策等涉及责任归属的工作由人完成。
- 落地难点不在让模型更聪明，而在搭建一个使AI对项目态势、组织架构、项目记忆、集团规范等信息有组织地参与协同工作的运行环境（Harness）。

### 1.3 研究问题与总体技术路线

- 研究问题：如何针对地产项目管理结构，将通用AI Agent重构为能够持续组织团队公共信息、并在权责边界内支持受控业务协同的领域化框架？
- 总体路线：以地产项目团队的真实协同场景为观察对象，梳理其运行所依赖的信息、规则与责任边界；将管理要素工程化为AI可持续理解与执行的基础，构建面向团队的行业运行框架；以实际业务场景验证工程落地效果，并随实践反馈持续迭代完善。
- 本文贡献：一是建立地产管理要素向Agent技术对象的映射方法；二是据此构建信息协同型AI智能体框架并完成工程实践验证，为垂直领域团队级AI的落地与框架搭建提供借鉴。

## 2 框架设计：面向团队的地产行业智能体

*定位：按「差异需求 → 要素映射 → 总体架构」三步展开，回答框架「具备什么、从哪里来、长什么样」。*

### 2.1 与通用AI智能体的差异

- 通用AI智能体的组织方式可概括为「LLM → Context → Tool → Loop → Memory」，其上下文与记忆服务于当前用户的单人会话。
- 面向团队的地产行业垂直领域智能体则要求：团队级上下文（从「用户上下文」扩展到「项目—组织—角色—任务—长期项目记忆」）、多人协同与任务调度、项目状态感知、角色与权限控制、SOP流程执行、人机协作分工（AI检索梳理、人发布审核决策）与团队记忆中枢。
- 这七项需求将在2.3的六层架构中逐层承接，并经第3章的实现机制落地。

### 2.2 管理要素向Agent技术对象的映射

- 将地产项目管理中的主要信息对象抽象为：项目状态、过程事件、项目资料、组织规则、业务流程、人员关系和系统能力，并逐项映射为Agent技术对象（表1）。

表1 地产管理要素与Agent技术对象映射

| 地产管理要素 | Agent技术对象 | 核心机制 |
| --- | --- | --- |
| 项目状态/节点 | 状态空间 | LLM增强FSM |
| 过程事件/项目资料 | 公共上下文对象 | 项目态势摘要 |
| 组织制度/规则 | 约束知识 | 组织规则摘要 |
| 系统工具/接口 | 能力对象 | 系统能力目录 |
| 业务流程/SOP | 能力单元 | Skill化SOP |
| 复合请求/交互上下文 | 工作项/会话任务 | WorkItem/SessionAgent |
| 具体业务任务 | 执行任务 | WorkItemAgent |
| 组织参与关系/权限 | 可见性与核验对象 | GuardianAgent |

- 映射的基本逻辑：由地产管理对象反向决定Agent需要的技术对象——状态需要状态空间，过程信息需要聚合摘要，SOP需要能力单元，复合任务需要工作项，组织责任则要求执行与核验相分离。

### 2.3 「六层一闭环」Harness总体架构

- 定义：以项目组织和业务状态为上下文，以WorkItem为任务载体，以SOP/Skill为执行规则，以权限和人工确认保证管理边界，以证据链保证过程可追溯的Agent运行框架。
- 六层：
  - **组织层（Who）**：建立企业、项目、部门、专业、角色等组织关系，明确AI服务的团队边界；
  - **上下文层（Context）**：将项目、阶段、业务对象、历史决策、人员关系等组织为持续上下文，使AI理解「当前是什么项目、处于什么状态」；
  - **状态层（State）**：将地产管理过程抽象为可感知的业务状态/全景节点，使AI能判断「现在进行到哪里、下一步应该发生什么」；
  - **任务层（WorkItem）**：将自然语言需求转化为可创建、执行、暂停、恢复、交接和关闭的任务单元，实现多人多任务协同；
  - **能力层（Skill/Tool）**：将企业SOP、管理规则、专业方法和外部工具封装为可调用能力，使AI从「会回答」转向「会办事」；
  - **治理层（Permission & Audit）**：控制信息可见范围、操作权限、人工确认、责任归属和全过程证据。
- 业务执行闭环：感知 → 判断 → 任务 → 执行 → 协同 → 验证 → 留痕 → 更新状态，闭环持续沉淀项目记忆。

## 3 实现方法

*定位：给出支撑六层架构落地的七项关键机制，每项标注对应架构层次，顺序沿「认知 → 感知 → 能力 → 执行 → 边界 → 弹性 → 沉淀」展开。*

### 3.1 领域上下文工程：聚合摘要、渐进式发现与实时热重载（对应上下文层）

- **聚合摘要**：将分散于IM、文档、数据库与事件记录等载体的团队过程信息，按主题持续聚合并生成结构化摘要，作为会话建立时注入模型的轻量上下文起点；按主题形成项目态势摘要（项目正在发生什么）、组织规则摘要（应遵循什么规则）与系统能力目录（系统能做什么）三类上下文工件。
- **渐进式发现**：摘要之外不全文灌入，任务执行中经RAG、DB与事件日志按需检索细节，形成「先摘要、后按需深入」的探索路径，避免长上下文中间信息利用不足的问题。
- **实时热重载**：底层信息一旦变化（节点状态推进、新事件产生、能力目录调整），系统即经偏差检测即时重建对应摘要，使AI认知与项目实际保持同步。

### 3.2 全景节点与状态管理：LLM增强有限状态机（对应状态层）

- 以全景节点构建项目业务状态空间：将开发任务分解为有明确产出的子任务作为节点，以节点关联性组织项目全景图；节点按重要性分级（自竣工验收等里程碑节点至具体工序小任务节点），由操盘单位管理。
- 状态变化采用「人定义状态空间、系统维护状态关系、LLM辅助语义判断」的LLM增强有限状态机：LLM从自然语言中提取状态证据并提出候选转移，实际转移受成果条件、业务规则与人工确认约束。

### 3.3 SOP-Skill能力封装（对应能力层）

- 将标准化业务流程封装为含任务描述、输入参数、前置条件、工具绑定与权限要求等约束的Skill；企业以SOP规范业务动作，系统管理员对SOP认证负责。
- 经系统能力目录完成能力注册、语义发现与参数映射，使自然语言任务能够调用既定业务能力执行。
- 按业务稳定程度形成「Skill—专用Agent—既有能力组合」的分层能力组织，并随使用反馈迭代。

### 3.4 WorkItem驱动的任务编排：三智能体分工（对应任务层）

- 将复杂用户请求拆解为可独立执行的WorkItem，由三个智能体分工：SessionAgent负责会话组织与任务拆解，WorkItemAgent负责具体能力调用与业务执行，GuardianAgent负责责任核验，实现「任务组织、业务执行、责任核验」三者分离。
- 支撑多人同时使用、任务排队、交互焦点、任务交接与并行执行的团队级异步协作。

### 3.5 权限与执行边界控制（对应治理层）

- 以全景节点作为信息可见性的基本组织单元：人员经企业、角色与参与节点形成节点级可见关系，新授权不得超过授权者自身可见范围（V_new ⊆ V_creator）。
- 通过权限快照、执行前Hook、GuardianAgent二次校验及人工确认机制，对信息可见范围、业务规则和操作边界进行全过程约束；权限不足时选择拒绝、脱敏或协作导航。
- 责任认定、关键状态确认与流程变更由人完成最终确认。

### 3.6 非预设任务的能力组合（对应闭环的弹性扩展）

- 对缺少对应SOP的新型任务，若不涉及新增组织规则，可在权限边界内组合既有检索、数据库、事件记录与历史经验等基础能力完成。
- 严格区分「能力组合」与「新流程生成」：后者（新SOP、流程规则与状态空间变更）仍需人工审核，保证框架弹性不突破管理边界。

### 3.7 事件流与多源信息沉淀（对应项目记忆沉淀）

- 以IM作为低门槛自然语言入口（基本零培训、无需新装APP），将团队日常沟通中的过程信息经事件记录、结构化数据库与RAG检索持续沉淀为可追溯的项目过程记录。
- 使框架成为随项目推进持续更新的团队记忆中枢，项目记忆不随人员流动而流失——回应1.1的困境一。

## 4 案例验证

*定位：两个互补实例验证工程落点——实例一验证预设执行链，实例二验证非预设组合；开头声明：实例用于说明工程落点，不构成统计意义上的性能验证。*

### 4.1 实例一：园路铺装验收——预设执行链验证

- 场景：苏州某住宅项目景观工程阶段，园路铺装节点完成后，项目主管经IM提出验收咨询。
- 过程：SessionAgent将请求拆分为流程匹配与成果定位两个WorkItem，WorkItemAgent经能力目录语义匹配到验收Skill，并按需获取节点状态、成果与验收标准，GuardianAgent完成权限与规则二次核验；现场发现质量问题后，系统继续拆分规范比对、合同查询与材料溯源任务，经人工确认执行整改通知与节点变更。
- 验证归纳：该实例中三个智能体各司其职，且上下文摘要与执行智能体分属认知、执行两层被分别调用，验证了三智能体分工与「认知组织—任务执行分离」的分层架构成立；验收Skill的语义发现与按需信息加载、节点变更与整改全程经人工确认，验证了Skill化SOP、渐进式上下文与LLM增强FSM受控转移设计成立。

### 4.2 实例二：跨部门软装品质追溯——非预设组合验证

- 场景：苏州某已竣工住宅项目中，集团景观负责人追溯软装品质偏差；原项目主管离岗且无专属SOP。
- 过程：系统按权限完成跨源查询后，由WorkItemAgent组合RAG、DB、事件日志与历史经验，还原招标、交底、采购、进场与验收5个阶段，形成跨5个部门、8类信息来源的事件演进链；涉密信息采用权限控制与协作导航而非直接输出。
- 验证归纳：在无专属SOP条件下，系统组合基础能力完成任务且未生成新流程，验证了非预设能力组合的边界设计与渐进式发现机制成立；涉密信息经节点级权限控制与协作导航输出，GuardianAgent识别出成本壁垒、界面不清、签认缺位等信息流转缺口，且原主管离岗后完整过程链仍可还原，验证了节点级鉴权（V_new ⊆ V_creator）、执行与核验分离、以及以团队为主体的公共认知沉淀设计成立。
- 本章收束（适用条件与局限）：框架运行依赖项目数据、可检索规则与人员权限等数字化基础；跨载体深层关联仍依赖RAG与DB；LLM状态证据解析存在不确定性，需通过人工定义状态空间、规则与责任边界限制Agent自由度。

## 5 结论

*定位：提炼方法贡献、点明框架本质、以实例支撑主张，一句带过展望。*

- 核心结论：本文从地产项目管理结构出发，提出领域管理结构驱动的AI Agent框架设计方法——将项目状态、过程信息、组织规则、业务流程、系统能力、复合任务与组织权责，映射为状态空间、项目级上下文工件（态势/规则摘要与能力目录）、Skill能力单元、WorkItem与职责核验机制，以「六层一闭环」Harness组织为「认知—感知—执行—核验」的信息协同型框架。
- 框架的本质：核心不是增加行业知识，而是将管理结构本身转化为Agent的上下文、状态、能力、可见性与责任边界。
- 实例支撑：两个业务实例表明，该框架能支持预设流程与非预设复合信息任务，并在受控边界内持续组织团队公共信息，缓解过程认知分散与经验随人流失的困境。
- 价值与展望：为传统行业由管理结构反向驱动Agent架构设计提供工程实践参考；后续可结合事件关系网络优化信息召回、支持上下文工件的分层增量更新，并以插件机制接入BIM、视觉多模态等专业能力。
