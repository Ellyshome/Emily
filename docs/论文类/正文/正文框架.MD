## 行业背景：
- 项目记忆与过程经验随人员流动而流失。一线过程信息（现场、会议、IM中的细节、问题处理过程、试错经验、情境判断）不进入正式留档，最终沉淀的只是加工后的结果性信息，形成「正式数据完整、过程认知分散」的现象，
- 企业信息沉淀量巨大，但精力有限、难以活化复用；传统数字化系统只擅长预设流程和结构化数据，对自然语言过程信息和非预设任务无力，且培训成本高、跨企业难复用、可参与人少。

## AI发展与在地产领域的现状：
- AI技术正深刻变革生产关系，在众多行业加速渗透并产生实际赋能。
- 但在地产行业中，其发挥效能的现状特征是"单人单任务"：通用AI工具以个人会话为中心，难以持续进入团队信息流并形成组织公共认知。
- 行业内现有的AI应用集中于BIM、进度、质量等单点任务，或面向个人的问答与文书工具。
- 行业真正缺的不是"能回答问题的AI"，而是缺少一个团队向的AI工具层：AI能否进入一个组织，拥有持续的公共上下文，并在明确的权责边界内参与工作协同。

## AI特性分析及其应有的效能模式：
- 当前处于弱人工智能（ANI）阶段，本质是根据训练权重对输入信息做关联运算，无长期记忆，上下文窗口有限，单次会话难以承载项目级的持续认知。
- 由此推导出人机分工的合理模式：适合AI做信息检索、关联与分析，人做任务发布、审核与决策。
- 落地的难点不在于让模型更聪明，而在于搭建一个让AI对项目态势、组织架构、项目记忆、集团规范要求等信息有组织地参与协同工作的运行环境（Harness）。

## 总路线：
以地产项目团队的真实协同场景为观察对象，梳理其运行所依赖的信息、规则与责任边界；将要素工程化为AI可持续理解与执行的基础，逐步构建面向团队的行业运行框架；以实际业务场景验证框架的工程落地效果，并随实践反馈持续迭代完善。

## 对比通用AI智能体。面向团队的地产行业垂直领域智能体，归纳提炼其需具备的功能与特性：
### 通用AI智能体特性：
LLM → Context → Tool → Loop → Memory。
### 面向团队的地产行业垂直领域智能体（7项基本特征）：
团队级上下文：从“用户上下文”扩展到“项目—组织—角色—任务-长期项目记忆”上下文。
多人协同与任务调度：支持多人同时使用、任务排队、交互焦点、任务交接与并行执行。
项目状态感知：持续感知项目阶段、全景节点、事项状态，而非每次从零理解。
角色与权限控制：按人员、组织、项目、专业、信息等级控制“谁能看、谁能做、谁能知道”。
业务流程/SOP执行：把企业标准、管理制度、验收标准逐步转化为 AI 可执行的规则与 Skill。按照企业标准流程主动推进工作。并随实践改进
人机协作机制：人与AI的协作机制，ai提供信息检索与梳理，人提供任务发布以及校审与决策。
团队记忆中枢：记住项目历史决策、问题、责任、变更和结果，形成持续性的“项目记忆”。关联原始文件、记录、节点和执行过程。

## 构建地产行业 Harness 的要点归纳（六层一闭环）：
围绕地产项目团队如何真实开展工作，构建 AI 的运行环境、协作机制与管理边界。

### 组织层（Who）
建立企业、项目、部门、专业、角色等组织关系，明确 AI 服务的团队边界。
### 上下文层（Context）
将项目、阶段、业务对象、历史决策、人员关系等形成持续上下文，让 AI 理解“当前是什么项目、处于什么状态”。
### 状态层（State）
将地产管理过程抽象为可感知的业务状态/全景节点，使 AI 能判断“现在进行到哪里、下一步应该发生什么”。
### 任务层（WorkItem）
将自然语言需求转化为可创建、执行、暂停、恢复、交接和关闭的任务单元，实现多人多任务协同。
### 能力层（Skill / Tool）
将企业 SOP、管理规则、专业方法和外部工具封装为可调用能力，让 AI 从“会回答”转向“会办事”。
治理层（Permission & Audit）
对信息可见范围、操作权限、人工确认、责任归属和全过程证据进行控制。
### 一闭环：业务执行闭环
感知 → 判断 → 任务 → 执行 → 协同 → 验证 → 留痕 → 更新状态
最终形成：
组织定义边界 → 上下文提供认知 → 状态决定时机 → WorkItem承载任务 → Skill完成执行 → 治理控制风险 → 闭环沉淀项目记忆。

## 具体实现方法
1. 全景节点与状态管理：以全景节点构建项目业务状态空间，并结合 LLM 增强型有限状态机，实现项目状态识别、节点转换与过程约束。
2. 领域上下文工程：通过结构化组织项目状态、组织规则、历史信息与系统能力等领域上下文，实现任务执行所需信息的按需加载与渐进式发现。
3. SOP-Skill 能力封装：将标准业务流程封装为可调用的 Skill，并通过能力注册、语义发现和参数映射，使自然语言任务能够调用既定业务能力执行。
4. 核心任务编排规划框架：将复杂用户请求拆解为可独立执行的 WorkItem，由 SessionAgent 负责任务组织、WorkItemAgent 负责具体执行，实现面向团队的异步任务协作。
5. 权限与执行边界控制：根据全景节点对可见信息范围进行隔离、执行前 Hook、GuardianAgent 二次校验及人工确认机制，对信息可见范围、业务规则和实际操作边界进行全过程约束。
7. 事件流与多源信息沉淀：通过 IM 信息采集、事件记录、结构化数据库与 RAG 检索等机制，将团队日常业务信息持续沉淀并形成可追溯的项目过程记录。

## 实践验证一：园路铺装验收（验证框架的预设执行链设计）
三智能体分工设计：SessionAgent 拆解、WorkItemAgent 执行、GuardianAgent 核验三层各司其职，验证了「任务组织 / 业务执行 / 责任核验」三者分离的框架分工成立。
三书认知基座设计：态势书供状态、规则书供标准、能力书供 Skill，验证了「按需加载、非全文灌入」的认知组织方式成立。
Skill 化 SOP 设计：能力书语义匹配到验收 Skill 并调用，验证了「业务能力单元化 + 可发现可调用」的设计成立。
LLM 增强 FSM 设计：节点变更与整改须经人工确认，验证了「人定义状态空间、系统维护关系、LLM 仅辅助判断」的受控转移设计成立。
分层架构设计：三书（认知层）与三 Agent（执行层）在实例中分属不同层次被调用，验证了「认知组织与任务执行分离」的总体架构设计成立。
## 实践验证二：跨部门软装品质追溯（验证框架的非预设组合设计）
非预设能力组合设计：无专属 SOP 时组合 RAG/DB/事件日志/历史经验，验证了「能力组合 ≠ 新流程生成」这一边界设计成立。
渐进式发现设计：在无专属 SOP 的场景下仍能按「任务识别→按需探索→执行核验」运行，验证了「共享地图、按需探索」的联动机制设计成立。
全景节点可见性设计：涉密信息走权限控制 + 协作导航而非直接输出，验证了「节点级信息可见范围 + V_new ⊆ V_creator」的鉴权设计成立。
Guardian 边界核验设计：识别出成本壁垒、界面不清、签认缺位等信息流转缺口，验证了「执行与核验相分离」的职责隔离设计成立。
团队公共认知沉淀设计：原主管离岗后仍能还原完整过程链，验证了「以团队而非个人为认知主体」这一框架设计目标成立。
