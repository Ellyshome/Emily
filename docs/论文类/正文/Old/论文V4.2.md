# 面向地产项目团队的信息协同型AI智能体架构设计与实践

## 摘要

随着大语言模型与AI Agent技术快速发展，人工智能开始由单点任务辅助向复杂业务过程渗透。然而，在地产项目团队中，AI应用仍主要表现为个人工具或单一业务功能，项目过程信息、组织规则与业务能力尚未形成统一的团队级认知环境。针对地产项目具有信息多源、状态动态变化、业务流程依赖标准化规则以及组织权限边界明确等特征，本文从地产项目管理要素出发，建立管理要素与Agent技术对象之间的映射关系，将项目过程信息、组织规则、系统能力、项目状态和业务流程分别转化为公共认知载体、状态空间与能力单元，并据此构建“项目态势书—组织规则书—系统能力书”三书认知基座、LLM增强有限状态机、Skill化SOP以及SessionAgent、WorkItemAgent和GuardianAgent组成的协同执行架构。在此基础上完成Emily系统的工程实现，通过真实地产项目中的业务任务执行与跨部门多源事件链重构两个案例，对信息持续接入、多源信息关联、任务执行和权限核验等机制进行验证。两个案例表明，在本文验证场景下，该架构能够将分散于人员、即时通讯、文档和业务系统中的过程信息组织为可检索、可关联和可核验的团队公共信息，并支持预设业务流程与非预设复合任务的受控执行。本文研究为AI Agent由个人工具向垂直行业团队信息基础设施转化提供了一种工程化实现路径。

**关键词：** 智能体；信息协同；工程项目管理；知识管理；大语言模型；地产项目

# 1 引言

## 1.1 问题背景

地产行业数字化建设持续推进，各类协同工具与项目管理系统逐步普及，企业已经积累了大量结构化业务数据与文档资料。然而，项目团队内部的信息流仍以人员为主要传递节点。一线现场产生的细节信息、问题处理过程、试错经验与隐性判断，往往通过会议、汇报和即时通讯逐级传递，最终进入正式系统的通常只是经过加工的结果性信息。大量过程性信息散落于个人经验、即时通讯记录和零散文件中，并可能随着人员流动而失去上下文。

与此同时，地产项目具有明显的动态性。项目由多个专业条线共同参与，状态随节点推进不断变化，业务过程既包含相对稳定的标准流程，也包含大量依赖现场情境的临时协调。传统数字化系统擅长处理结构化、预设性的业务流程，但对于自然语言沟通、跨来源过程信息以及非预设任务的关联处理能力有限；近年来快速发展的AI工具则具有较强的自然语言理解和知识处理能力，但多数仍以个人任务为中心，难以持续嵌入团队的信息流。

由此产生一个值得进一步研究的工程问题：**如何将AI Agent从面向个人的任务工具转化为能够持续进入项目团队日常信息流、形成公共认知并参与受控业务协同的团队级基础设施。**

## 1.2 地产项目团队的信息结构特征

从项目管理对象来看，地产项目的信息并非简单的文档集合，而是由项目状态、过程事件、组织规则、业务流程、人员关系和系统能力等多类要素共同构成。不同信息具有不同的生命周期和使用方式：项目状态随节点推进变化，过程事件持续产生，组织规则相对稳定但会随制度修订更新，业务流程具有明确的输入、步骤和结果约束，人员关系决定信息访问边界，而系统能力决定Agent可以采取哪些实际操作。

这意味着，单纯建立一个面向项目文档的RAG知识库，并不能完整表达项目团队运行所需要的公共认知。Agent不仅需要“知道资料在哪里”，还需要理解当前项目处于什么状态、哪些规则适用、当前有哪些能力可以调用，以及某项操作是否处于用户权限范围之内。

因此，本文将地产项目团队的信息协同问题进一步抽象为四类技术需求：

1. **公共认知构建**：将分散的项目过程信息、组织规则和系统能力组织为团队共享的信息环境；
2. **动态状态感知**：使Agent能够理解项目节点及其状态变化，而非仅对静态资料进行检索；
3. **受控业务执行**：将企业SOP转化为Agent可以发现、调用和执行的能力单元；
4. **组织化任务协同**：在自然语言交互、任务执行和结果核验之间建立清晰的职责边界。

## 1.3 研究问题与技术路线

围绕上述需求，本文重点研究以下三个问题：

**RQ1：如何将地产项目管理中的状态、信息、规则、流程和系统能力转化为Agent可处理的技术对象？**

**RQ2：如何构建团队级公共认知，使Agent能够持续利用项目过程信息、组织规则和业务能力？**

**RQ3：如何使Agent在执行复杂业务任务时保持明确的权限边界、流程约束和人工责任边界？**

针对上述问题，本文采用“问题识别—领域建模—技术映射—架构实现—工程验证”的研究路径。

**图1-1 总体技术路线（文字占位）**

> 地产项目管理问题 → 管理要素分析 → 管理要素与Agent技术对象映射 → 公共认知基座设计 → 动态状态感知 → 业务流程能力封装 → 多Agent任务协同 → 权限与人工核验 → 真实项目验证

其中，第三章重点解决“为什么这样设计以及如何进行领域建模”，第四章重点说明“具体如何设计并实现”，第五章重点验证“技术机制是否能够在真实业务场景中运行”。

## 1.4 研究贡献

本文不以提出新的基础模型或底层算法为目标，而关注通用AI Agent向垂直行业团队应用过程中所需要的领域化工程重构。本文的核心方法是**领域管理结构驱动的Agent架构重构方法**：以地产项目管理要素为出发点，建立其与Agent技术对象之间的映射关系，并由此导出若干具体技术实现机制。主要贡献包括三个方面。

第一，建立**地产管理要素向Agent技术对象的映射方法**。针对地产项目的状态、信息、规则、流程、人员和能力等要素，分别建立对应的状态空间、公共认知对象、能力单元和任务单元，使领域管理结构成为Agent架构设计的依据，这是本文方法的起点。

第二，在上述映射方法下形成若干**技术实现机制**，包括三书认知基座、LLM增强FSM、Skill化SOP以及三智能体协作。这些机制并非彼此独立的创新点，而是同一领域化重构方法在不同管理要素上的落地：项目状态对应LLM增强FSM，过程信息与规则对应三书，业务流程对应Skill，任务与权责分别对应WorkItem与Guardian。

第三，通过**真实项目案例进行工程机制验证**。分别以预设业务任务执行和非预设跨部门多源事件链重构作为验证场景，观察系统的信息持续接入、多源信息关联、任务执行、权限控制和结果核验能力。

# 2 技术基础与研究空白

## 2.1 组织知识管理研究

人工智能逐渐进入组织知识管理领域后，其作用已经不再局限于传统意义上的信息存储和检索。相关研究表明，AI正在参与组织知识的获取、整合、转化和应用，并开始影响组织知识创造的具体过程[9]。这为AI参与组织知识处理与流动提供了理论基础。

传统知识管理更多关注知识如何被保存、共享和利用，而项目团队日常产生的大量过程信息具有更强的动态性。这些信息可能出现在即时通讯、会议记录、业务文件和其他工作记录中，并不一定及时进入正式知识库。依赖人员主动录入和整理的传统机制，在面对持续产生的即时信息时容易出现采集不及时、上下文丢失等问题。

因此，本文将知识沉淀从“项目结束后的资料整理”扩展到“项目运行过程中的持续认知积累”，以团队而非个人作为知识沉淀主体，通过AI持续接收、整理和关联自然语言信息，并进一步将项目状态、组织规则和系统能力纳入统一的公共认知框架。

## 2.2 AI Agent工程研究

AI Agent工程技术已经由单轮问答逐步发展到工作流执行、状态管理、工具调用、记忆机制和多智能体协作等方向。StateFlow研究表明，可以将复杂LLM任务建模为状态驱动的工作流，并由LLM承担部分语义状态判断，从而兼顾自然语言适应能力与任务执行的可控性[1]。MetaGPT研究展示了将组织中的SOP编码到多Agent协作流程中的方法[2]。RAG为多源知识的组织与检索提供了成熟范式[7]，Agent Memory相关研究则从信息来源、记忆形式和操作机制等方面总结了Agent长期认知能力的构建方式[3]。

近期研究进一步开始关注多用户环境下的共享与持久记忆。有研究提出Memory Fabric框架，讨论私有记忆与共享/团队级记忆分层、多用户共享上下文、基于角色的访问控制和记忆来源追溯等机制[5]。这些研究说明Agent记忆正在从单用户个体记忆向多用户协作环境下的共享记忆发展。

但对于垂直行业团队而言，问题并不只是“如何共享记忆”，还包括**公共认知应包含哪些信息，以及这些信息如何按照真实业务管理结构组织**。地产项目中的状态、规则、流程和能力具有不同生命周期，因此需要对通用Agent的记忆、工作流和工具调用机制进行领域化组织。

**表2-1 AI Agent技术研究方向与本文研究空白**

| 技术方向 | 已解决问题 | 代表工作 | 面向地产团队的进一步问题 | 本文处理方式 |
|---|---|---|---|---|
| FSM/Workflow | 复杂任务状态管理 | StateFlow[1] | 通用状态机缺乏项目节点与成果约束 | LLM增强FSM |
| Multi-Agent | 角色分工与协作 | MetaGPT[2] | 缺乏真实组织权责映射 | Session/WorkItem/Guardian分工 |
| Memory | 长期记忆与信息组织 | Agent Memory综述[3] | 缺乏团队公共认知结构 | 三书认知基座 |
| Shared Memory | 多用户共享记忆与访问治理 | Memory Fabric[5] | 缺乏地产项目状态、规则、能力的领域化组织 | 三类动态信息载体 |
| RAG | 外部知识调用 | Lewis等[7] | 静态知识检索难以表达动态项目态势 | RAG+结构化DB |
| Tool/Skill | 工具调用 | Toolformer[10] | 通用工具调用缺少企业SOP约束 | Skill化SOP |

## 2.3 产业数字化与工程AI实践

产业数字化已经形成较为成熟的项目管理系统、BIM平台、协同办公系统及专业软件体系。传统数字化系统具有强流程、强结构和较弱自然语言交互的特点，其优势在于处理预设好的标准化业务，而对于非结构化、情境化的信息处理存在局限。

另一方面，当前工程领域AI应用多集中在专业任务效率提升。例如基于DeepSeek的BIM工程管理平台研究主要围绕特定工程业务场景进行AI能力探索[6]。这类应用证明了AI在工程专业任务中的应用价值，但多数仍属于“单点工具/场景探索型”应用。

由此形成“个人AI工具—组织数字化系统”之间的衔接问题：前者具备较强的自然语言理解和任务处理能力，后者具备组织化的数据和流程，但二者之间缺少一个能够持续进入团队日常信息流、组织多源信息并形成公共认知的工程化层。

## 2.4 技术空白与本文定位

综合上述研究，现有技术已经分别解决了知识管理、Agent任务执行和企业业务流程数字化中的部分问题，但三者在垂直行业团队环境中的组合仍存在以下空白：

1. **公共认知结构不足**：共享记忆研究关注记忆共享与治理，但较少回答垂直行业公共认知应如何按照业务结构组织；
2. **动态项目状态表达不足**：RAG适合文档语义检索，但难以独立表达项目节点、状态转移和成果约束；
3. **业务流程与Agent能力之间缺少标准化接口**：企业SOP通常以制度文件存在，尚未天然成为Agent可发现、可调用的能力单元；
4. **Agent职责与组织责任之间缺少工程映射**：多Agent协作通常关注任务分工，而地产项目还需要考虑权限、执行与核验之间的组织制衡关系。

因此，本文不试图重新发明RAG、FSM、Multi-Agent或Tool Calling等基础技术，而是研究这些成熟机制如何按照地产项目管理的结构进行重新组织，形成面向团队公共信息协同的领域化Agent架构。

# 3 地产管理要素的Agent化建模

## 3.1 地产项目管理的信息要素

地产项目管理可以进一步抽象为项目状态、过程事件、组织规则、业务流程、项目资料、人员关系和系统能力等基本信息要素。不同要素具有不同的生命周期、结构化程度和业务作用。

**表3-1 地产管理要素及其技术特征**

| 管理要素 | 主要内容 | 典型特征 | Agent处理需求 |
|---|---|---|---|
| 项目状态/节点 | 项目阶段、节点状态、成果条件 | 动态变化、具有转移条件 | 状态感知与状态转移 |
| 过程事件 | IM记录、会议、日志、现场信息 | 持续产生、多源异构 | 采集、关联与回放 |
| 项目资料 | 图纸、合同、照片、报告等 | 非结构化、多载体 | 检索与语义关联 |
| 组织规则 | 制度、规范、验收标准 | 相对稳定、具有约束性 | 规则检索与约束 |
| 业务流程 | SOP、标准作业程序 | 有步骤、有输入输出 | 能力封装与执行 |
| 人员关系 | 角色、部门、责任、在岗状态 | 权限相关、组织动态 | 权限判断与协作导航 |
| 系统能力 | DB、RAG、插件、业务接口 | 可调用、可扩展 | 能力发现与工具调用 |

这些要素不能简单地被压缩为同一种“知识”。例如，项目状态具有时间连续性，规则具有约束性，业务流程具有执行结构，系统能力则描述“系统可以做什么”。因此，本文采用分层组织而非单一知识库的方式构建Agent运行环境。

## 3.2 管理要素与Agent技术对象映射

基于上述分析，本文建立地产管理要素与Agent技术对象之间的映射关系。

**表3-2 地产管理要素与Agent技术对象映射**

| 地产管理要素 | Agent技术对象 | 核心实现机制 | 主要解决问题 |
|---|---|---|---|
| 项目状态/节点 | 状态空间 | LLM增强FSM | 动态项目态势感知 |
| 过程事件与项目资料 | 公共认知对象 | 项目态势书 | 信息持续沉淀与关联 |
| 组织制度与验收标准 | 约束知识 | 组织规则书 | 响应与执行边界控制 |
| 业务流程/SOP | 能力单元 | Skill化SOP | 流程发现、调用与执行 |
| 系统工具与接口 | 可调用能力 | 系统能力书 | 能力发现与组合 |
| 用户复合请求 | 工作项 | WorkItem | 复杂任务拆解与隔离 |
| 用户交互上下文 | 会话任务 | SessionAgent | 对话组织与任务调度 |
| 具体业务任务 | 执行任务 | WorkItemAgent | 受控业务执行 |
| 权限与结果约束 | 核验任务 | GuardianAgent | 权限、规则与结果核验 |

这一映射关系构成本文技术路线的核心。三书解决“Agent知道什么以及可以发现什么”的问题，LLM增强FSM解决“Agent如何理解项目处于什么状态”的问题，Skill化SOP解决“Agent如何按照业务流程执行”的问题，三智能体则解决“Agent如何组织、执行和核验任务”的问题。

## 3.3 设计约束

管理要素的技术化并不意味着AI获得独立的组织决策权。相反，地产项目的责任结构决定了Agent必须运行在明确的权限和人工责任边界内。因此，本文将四项原则作为系统设计约束，而非独立的算法创新。

**表3-3 问题、设计约束与工程要求**

| 核心问题 | 设计约束 | 工程要求 |
|---|---|---|
| AI与人的权责划分 | AI作为辅助工具而非责任主体 | 信息收集、关联、建议与受控执行；关键事项人工确认 |
| 团队知识沉淀 | 团队而非个人作为公共知识主体 | 公共认知基座与持续信息接入 |
| 信息采集门槛 | 不要求一线人员额外学习复杂录入系统 | IM自然语言持续接入 |
| 系统扩展 | 场景可以扩展，但规则不能失控 | Skill/Plugin模块化扩展，人审核规则和流程变更 |

四项约束共同形成一个边界：**人定义规则和责任边界，系统负责信息组织与受控执行，人完成关键判断与升级决策。**

## 3.4 总体技术路线

基于上述映射，本文形成“认知—感知—执行—核验”的技术路线。

**图3-1 地产管理要素Agent化总体模型（文字占位）**

> 组织制度/规范 → 组织规则书  
> SOP/工具/接口 → 系统能力书  
> 三书共同构成团队公共认知基座  
> ↓  
> LLM增强FSM负责项目状态感知与节点流转  
> ↓  
> Skill化SOP负责标准业务流程执行  
> ↓  
> SessionAgent负责自然语言任务组织

> ↓  
> 人工确认/业务结果

这一技术路线使地产项目管理的领域结构成为Agent架构的设计依据，而不是在通用Agent外部简单增加若干行业知识。

# 4 系统技术架构与实现

为区分架构设计、系统实现与案例证据的不同证据等级，本章统一采用以下三类表述：**“本文设计”**描述架构层面的机制设计；**“Emily系统目前实现”**描述已在系统中落地运行的机制；第五章则以**“案例中观察到/验证”**描述实验证据。对于尚处于架构设计层面、未在系统中完整实现的机制，本文明确标注为“设计”，避免将设计误述为实现。

## 4.1 总体架构

基于第三章的领域建模，本文设计并实现Emily系统。系统总体架构遵循“轻接入、重内核、分层解耦”的原则，由IM接入层、业务内核、三书认知基座、Agent执行层以及业务数据与工具层构成。

**图4-1 Emily系统总体技术架构（文字占位）**

> 用户/项目成员  
> ↓  
> IM插件接入层  
> ↓  
> SessionAgent：会话组织、意图识别、WorkItem拆解  
> ↓  
> WorkItemAgent：任务规划、RAG/DB/Skill/Plugin调用  
> ↓  
> GuardianAgent：权限、规则与结果约束二次核验  
> ↓  
> 人工确认/业务执行  
> ↑  
> 三书认知基座：项目态势书、组织规则书、系统能力书  
> ↑  
> 项目数据库、RAG知识库、业务插件、事件流

系统将用户交互与业务执行解耦，使IM仅承担轻量入口职责，核心业务逻辑由独立业务内核处理。不同Agent共享三书认知地图，但按照职责分别读取和使用信息；具有副作用的操作在执行边界再次进行权限核验，以降低会话级权限快照与实时权限状态不一致的风险。

## 4.2 三书认知基座

三书并非以物理存储划分的三个相互独立的数据库，而是面向Agent认知组织的三个逻辑对象，其底层由DB、RAG、事件流、规则文本、能力注册等不同存储和能力共同实现。三书按不同生命周期和业务作用组织，共同目标是建立Agent运行所需的团队公共认知环境。

**表4-1 三书逻辑对象及其主要底层实现**

| 逻辑对象 | 主要底层实现 |
|---|---|
| 项目态势书 | 结构化DB + 过程事件 + RAG语义索引 |
| 组织规则书 | 规则文本 + 规则元数据（版本/生效时间/适用范围） |
| 系统能力书 | 能力注册表 + Skill/Plugin 元数据 |

### 4.2.1 项目态势书

项目态势书是以项目全景节点为骨架的状态聚合载体。其主要内容包括节点当前状态、过程事件、成果文件索引、参建方关系以及与节点相关的结构化业务数据。

其核心不是复制所有项目资料，而是提供一张能够指导Agent进一步探索的信息地图。结构化状态信息通过DB保存，非结构化过程记录通过RAG索引；Agent首先获取节点概要和相关索引，再根据任务需要深入调取具体记录。

项目态势书随项目节点流转和事件发生而更新，其生命周期与项目运行过程直接相关。因此，它与面向个人的静态会话记忆不同，更接近项目团队共享的动态项目认知模型。

### 4.2.2 组织规则书

组织规则书用于组织企业管理制度、项目管理要求、验收标准、合同规则及相关规范条文。其作用不是让AI形成抽象的“道德规则”，而是让Agent能够在具体业务场景中检索适用的组织约束。

规则书主要通过语义检索结合规则元数据筛选提供适用规则，并在关键任务中作为核验依据。规则的版本、生效时间和适用范围应作为规则元数据保存，以避免过期制度或不适用项目规则进入执行链。

### 4.2.3 系统能力书

系统能力书描述当前系统能够调用的业务能力，包括RAG检索、数据库查询、业务插件以及Skill化SOP等。与硬编码工具清单不同，系统能力书使能力具有可描述、可发现和可扩展的特征。

每项能力至少包含能力标识、功能描述、输入参数、输出结构、适用条件和权限要求等信息。用户提出业务需求后，SessionAgent或WorkItemAgent可以通过语义检索发现相关能力，而不需要将所有工具描述一次性注入上下文。

### 4.2.4 三书联动与渐进式发现

三书采用“共享地图、角色化探索”的方式运行。三类信息并不全部进入每一次Agent上下文，而是首先提供目录索引、摘要和关联入口，在任务明确后再逐步深入读取详细资料。这样既可以降低无关上下文进入模型带来的干扰，也能够适应项目知识规模持续增长的情况。

三书的更新机制不同：项目态势书随事件和节点变化更新，组织规则书随制度修订更新，系统能力书随插件和Skill接入更新。三者共同形成Agent长期运行所需的公共认知环境。

## 4.3 LLM增强有限状态机

### 4.3.1 状态空间定义

地产项目节点具有明确的业务阶段和管理边界，因此状态空间不能由LLM自由生成。本文设计采用“人定义状态空间、系统执行状态管理、LLM辅助语义判断”的机制。

项目管理人员预先定义节点名称、允许状态、状态转移关系、成果要求以及相关验收规则。系统不允许LLM在运行过程中自行创造新的状态类别或修改状态空间。

### 4.3.2 LLM语义状态判定

传统FSM要求状态转移条件以确定性的布尔表达式实现，而地产项目中的信息大量来自自然语言。例如“现场已经做完了”“材料到了但还没签”“基本没问题，剩两处整改”等表述无法直接通过简单规则判断。

因此，本文将LLM置于状态机的语义条件边上。LLM负责将自然语言和事件信息解析为状态证据，并提出候选状态转移；实际状态变化仍受预定义FSM、成果条件、权限和必要的人工确认约束。FSM本身负责维护状态空间和合法转移关系。

**图4-2 LLM增强FSM状态判定机制（文字占位）**

> 新事件/用户输入  
> ↓  
> LLM语义解析（提取状态证据）  
> ↓  
> 提出候选状态转移  
> ↓  
> 预定义FSM + 成果要求/规则校验  
> ↓  
> 满足条件 → 状态转移  
> 不满足条件 → 保持当前状态/请求补充证据

### 4.3.3 成果约束驱动状态转移

节点状态变化不能仅由用户表达触发，而需要结合成果状态和预设验收标准。系统通过项目态势书获取节点已有成果，通过组织规则书获取相应标准，再由LLM对自然语言证据进行语义解析，以辅助判断是否满足转移条件。

例如，用户表示“园路铺装完成”，系统可以将其作为状态证据，但只有在节点预设的相应成果条件、业务规则或人工确认条件满足后，才允许状态进入相应的后续节点。这使项目状态管理从简单的“状态标记”转变为“状态+成果+约束”的联合判断。

### 4.3.4 人可定义的受控状态空间

项目节点的新增、修改和删除由具有相应权限的管理人员完成。系统可以提供节点定义工具和状态配置能力，但不允许Agent自行扩展状态空间。这样既利用LLM处理非结构化语义，又避免模型自行改变项目管理规则。

## 4.4 Skill化SOP

### 4.4.1 Skill作为业务能力单元

地产企业大量业务知识已经以SOP、制度和操作手册形式存在，但传统SOP通常面向人员阅读，而不是面向Agent执行。本文将标准化业务流程封装为Skill，使SOP由静态文档转化为可被Agent发现、调用和执行的能力单元。

**图4-3 Skill化SOP结构（文字占位）**

> Skill  
> ├── ID/名称  
> ├── 任务描述  
> ├── 输入参数  
> ├── 前置条件  
> ├── 执行步骤  
> ├── 工具绑定  
> ├── 输出结构  
> ├── 结果约束  
> └── 权限要求

### 4.4.2 能力发现与路由

系统不将所有SOP同时加载到Agent上下文，而是通过系统能力书进行语义匹配。用户以自然语言提出任务后，Agent首先判断任务类型，再在能力索引中检索候选Skill，获得其输入、前置条件和结果约束后进入执行阶段。

这种方式使业务能力与具体对话解耦。本文设计中，新增SOP按照统一协议注册后即可接入能力发现机制，从而避免修改核心Agent代码。

### 4.4.3 结构化执行

WorkItemAgent采用“自然语言→结构化参数→预定义能力”的执行模式。LLM主要负责将用户意图转换为结构化任务参数，具体业务动作由Skill、DB、RAG或插件执行。

这种设计减少了LLM自由选择工具和自由编排业务动作的空间，更适合地产领域“流程相对固定、参数具有变化”的业务特征。

### 4.4.4 从真实案例看Skill的执行边界

从案例A可观察到，Emily系统中的Skill执行已经形成“Skill加载—参数映射—工具/模板调用—结果核验”的执行链。以案例A中的整改通知Skill为例，WorkItemAgent加载对应SOP后，将问题编号、整改依据条款、承包单位、整改期限等自然语言信息映射为结构化模板参数，再绑定到具体工具执行，输出结构化通知单，最后由核验环节检查其格式与边界。这一案例表明，Skill化SOP已经在Emily系统的具体业务场景中形成可运行、可核验的实现形态。

### 4.4.5 非预设场景下的能力组合

当系统能力书没有匹配到某项专属SOP时，并不意味着系统必须拒绝任务。对于不需要创造新规则的复合信息任务，WorkItemAgent可以在权限允许的范围内组合已有基础能力，例如RAG检索、DB查询、事件日志查询和历史经验检索。

需要明确的是，“能力组合”与“系统自主生成新流程”不同。前者只是在既有能力范围内临时组织任务，后者会改变组织规则或业务流程。本文仅允许前者，任何新的SOP、流程规则和状态空间变更仍需人工审核。

## 4.5 三智能体协作架构

### 4.5.1 SessionAgent：会话组织与任务拆解

SessionAgent位于用户交互层，负责维护当前会话连续性、理解用户输入并组织任务。当消息仅涉及简单查询或信息记录时，可以直接从三书获取相关信息并完成响应；当输入包含多个业务诉求时，将其拆分为一个或多个WorkItem。

例如，用户提出“帮我查一下这个节点为什么延期，并告诉我应该怎么处理”，SessionAgent可以拆分为节点状态查询、延期事件检索、相关规则匹配和处理建议等工作项，再交由执行层分别处理。

SessionAgent在会话层获取当前用户权限信息，用于任务规划和路由；实际资源访问及具有副作用的操作仍必须在执行边界重新核验。

### 4.5.2 WorkItemAgent：任务隔离与执行

WorkItemAgent负责具体业务任务执行。每个WorkItem具有相对明确的输入、目标、所需能力和输出要求，Agent不掌握与当前任务无关的全局信息。

WorkItemAgent根据任务需要读取三书，发现相应Skill或工具，并将自然语言需求转换为结构化参数。任务完成后输出结构化结果，同时保留来源、执行过程和状态信息，供SessionAgent汇总和核验环节检查。

### 4.5.3 GuardianAgent：职责隔离的二次核验

GuardianAgent不承担具体业务决策，而负责在关键执行边界对权限、规则与结果约束进行检查。其核验内容包括用户是否具备资源访问权限、调用的规则是否有效、输出是否超出信息范围、任务是否产生未经授权的副作用以及结果是否满足预设约束等。

当核验不通过时，系统可以暂停后续执行并请求补充权限、信息或人工确认。这样，执行与核验被适当分离，避免同一个Agent同时完成理解、执行和自我确认。

需要说明的是，本文所称的“二次核验”是**架构职责层面的分离机制**，而非统计意义上相互独立的验证器。SessionAgent、WorkItemAgent与GuardianAgent在实现上可能共享同一大语言模型与同一组底层工具，因此其价值在于以职责隔离减少“执行者自证正确”的结构性问题，而不在于提供模型层面的独立证据。

### 4.5.4 三智能体协同链

**图4-4 三智能体端到端执行链（文字占位）**

> 用户自然语言输入  
> ↓  
> SessionAgent：意图识别/复合任务拆解  
> ↓  
> WorkItem  
> ↓  
> WorkItemAgent：能力发现/RAG/DB/Skill/Plugin  
> ↓  
> 执行结果  
> ↓  
> GuardianAgent：权限、规则与结果约束二次核验  
> ↓  
> 允许执行 / 请求人工确认 / 拦截  
> ↓  
> SessionAgent组织结果并反馈用户

三智能体的划分并非为了增加Agent数量，而是将地产项目中的“任务组织—业务执行—过程核验”进行技术映射，使Agent职责与组织责任边界保持一致。

## 4.6 权限、核验与人工确认机制

权限控制贯穿系统的不同执行阶段。会话层权限快照用于任务规划，执行层权限钩子用于实际资源访问，GuardianAgent负责对关键操作进行二次核验。对于涉密信息，系统根据用户角色和资源等级进行分级释放，而不是简单地采用“允许/拒绝”二元判断。

当用户无权直接访问目标信息时，系统并非简单终止请求，而是在不泄露受限信息的前提下，根据组织关系和权限规则提供合法的信息获取路径。例如，当用户询问其无权查看的涉密信息时，系统可以提示其向相应的责任人或主管部门申请权限或获取信息，从而将“权限拒绝”转化为“合法协作路径”，而非任务终止。

对于涉及责任认定、业务状态确认、规则升级或流程变更的事项，AI输出应明确标识为信息支持或参考建议，由具有相应职责的人员完成最终确认。系统记录人工确认行为，使关键业务过程具备可追溯性。

**图4-5 人机责任边界（文字占位）**

> AI：理解、检索、关联、提示、受控执行  
> 人：规则定义、权限授权、关键确认、责任承担、流程升级

## 4.7 端到端运行过程

以“B标段园路铺装节点完成后，主管需要进行验收”为例，系统的完整运行链如下：

1. 项目事件进入系统，项目态势书记录节点状态变化；
2. 用户通过IM自然语言提出验收请求；
3. SessionAgent识别任务并拆解为“匹配验收流程”和“定位节点成果要求”两个WorkItem；
4. WorkItemAgent通过系统能力书发现铺装面层验收Skill，并通过DB和RAG获取当前节点状态、成果文件和历史记录；
5. GuardianAgent核验用户权限、SOP版本和输出边界；
6. 系统向用户输出结构化验收指引；
7. 用户现场发现缺陷后继续自然语言反馈；
8. SessionAgent将缺陷处理拆分为规范比对、合同条款查询和历史经验检索等WorkItem；
9. WorkItemAgent调用组织规则书、合同DB和项目态势书获取证据；
10. GuardianAgent核验来源一致性、权限和责任边界；
11. 用户确认后，系统执行受控的整改通知、节点更新等动作，并保留过程记录。

这一运行过程体现了本文从“领域管理要素”到“Agent技术对象”再到“实际业务动作”的完整映射链。

# 5 工程验证

## 5.1 验证目标与方法

本文不以通用大模型的准确率、响应速度等纯性能指标作为主要评价目标，而关注所提出的技术路线能否在真实地产项目中形成完整的“信息接入—认知组织—任务执行—权限核验—结果输出”链路。

验证采用真实项目业务过程作为对象，设置两个具有不同特征的案例：

- **案例A：业务任务执行链验证。** 验证三书、LLM增强FSM、Skill化SOP及三智能体协作能否将项目知识、当前态势和组织规则转化为具体人员可执行的任务支持；
- **案例B：跨部门多源事件链重构验证。** 验证在无专属SOP的情况下，系统能否在权限约束下组合已有能力，跨部门、跨载体和跨阶段还原事件链并进行交叉验证。

观察维度包括：

1. 信息是否能够伴随业务过程持续进入系统；
2. 多来源信息能否形成关联；
3. 信息能否转化为面向任务的结构化支持；
4. 权限、规则与结果约束的二次核验能否通过职责隔离实现；
5. 关键过程能否被回溯和交叉验证。

本文案例属于工程可行性和机制有效性验证，而非统计意义上的大规模性能实验。项目名称、人员身份及部分业务数据均进行了脱敏处理。

## 5.2 案例A：业务任务执行链验证

### 5.2.1 场景与验证目标

案例A发生于苏州某商品住宅项目景观工程施工阶段。B标段园路花岗岩铺装节点完成后，系统主动推送节点状态提醒；新调入项目的景观工程主管在验收前向Emily询问验收要点，现场发现质量缺陷后继续通过自然语言交互获得处理指导。

本案例主要验证三书认知基座、LLM增强FSM、Skill化SOP和三智能体协作能否共同完成“节点状态感知—业务流程发现—项目资料获取—规则匹配—缺陷处理—人工确认”的业务执行链。

### 5.2.2 验收准备阶段

主管提出：“B标段园路铺装节点完成了，我要去现场验收，验收要注意什么？”

SessionAgent识别为“完工确认验收准备”请求，并拆解为两个WorkItem：

- WI-1：匹配验收业务流程；
- WI-2：定位本次验收的节点成果要求。

WorkItemAgent执行WI-1时，通过系统能力书语义检索发现“铺装面层验收流程”SOP；执行WI-2时，通过DB查询项目态势结构化数据，并进一步通过RAG检索节点相关成果文件和事件记录。

GuardianAgent随后核验主管的节点签认权限、SOP版本有效性以及输出是否超出信息层范围。核验通过后，系统输出包括验收业务流程、节点当前状态、关联成果文件以及企业验收标准在内的结构化指引。

**表5-1 案例A验收准备阶段的技术机制映射**

| 验证环节 | 输入 | 系统机制 | 输出 | 核验 |
|---|---|---|---|---|
| 节点状态识别 | 项目事件 | 项目态势书/DB | 节点已完成、待签认 | FSM状态约束 |
| 流程发现 | 自然语言任务 | 系统能力书/RAG | 铺装面层验收SOP | SOP版本核验 |
| 成果定位 | 节点标识 | DB+项目态势书 | 成果文件、历史事件 | 权限核验 |
| 验收指引 | 多源结果 | SessionAgent汇总 | 结构化验收清单 | Guardian核验 |

### 5.2.3 缺陷处理阶段

主管现场发现花岗岩存在明显色差、花筋以及板缝宽窄不均，并提出处理请求。

SessionAgent将请求拆解为规范比对、合同条款查询和历史经验检索三个WorkItem。WorkItemAgent分别调用组织规则书、合同DB和项目态势书，获取质量标准、违约条款以及历史同类问题处理记录。

随后GuardianAgent对三个WorkItem的来源一致性、历史经验来源和输出责任边界进行核验。系统没有直接替主管作出追责决定，而是将相关判断依据标识为供主管决策参考。

当主管进一步反馈材料质量问题后，系统追加材料进场溯源WorkItem，通过DB查询进场记录、报审人员和验收参与人员，并引导主管补充现场照片、实测数据以及进场验收记录等证据。

在信息充分后，系统基于节点进度约束、现场反馈的次品比例以及历史项目处理记录，形成部分退换货而非整批退货的参考建议，并给出责任追溯提示。主管确认执行后，GuardianAgent再次核验权限和状态合法性，系统才执行相应的整改通知、节点状态变更等受控操作。

### 5.2.4 验证结果

案例A表明，系统能够将项目当前状态、业务SOP、组织规则、合同信息和历史经验组合为面向具体任务的结构化支持。其技术价值不在于单次问答，而在于用户提出一个自然语言任务后，系统可以沿着“状态—能力—知识—规则—核验—执行”的链条持续组织信息。

同时，三智能体在验收准备、缺陷处理和执行确认等关键节点均承担不同职责，GuardianAgent对权限、规则与结果约束进行职责隔离的二次核验，使AI的建议和执行动作保持在明确的责任边界内。

**表5-1a 案例A真实执行链**

| 阶段 | 输入 | 调度 | 执行 | 核验 | 输出/动作 |
|---|---|---|---|---|---|
| 验收准备 | 自然语言验收请求 | SessionAgent拆分为2个WorkItem | WorkItemAgent：能力发现+RAG+DB | Guardian核验权限/SOP/边界 | 结构化验收清单 |
| 缺陷处理 | 现场质量缺陷反馈 | SessionAgent拆分为3个WorkItem | WorkItemAgent：规范+合同+历史经验 | Guardian核验来源/责任边界 | 判断依据（标识为参考） |
| 材料溯源 | 材料质量追问 | SessionAgent追加溯源WorkItem | WorkItemAgent：DB进场记录+报审/验收人员 | Guardian核验权限 | 取证引导 |
| 执行确认 | 主管确认 | SessionAgent组织确认 | 系统执行整改通知/节点变更 | Guardian再次核验权限/状态合法性 | 受控执行并留痕 |

因此，案例A主要验证了**预设业务场景下的Agent化任务执行链**，其验证性质属于机制/全链路验证，而非性能或准确率实验。

## 5.3 案例B：跨部门多源事件链重构验证

### 5.3.1 场景与验证目标

案例B发生于苏州某商品住宅项目景观工程竣工交付前。集团巡检发现景观软装呈现品质效果较差，集团景观高级经理希望了解从设计到施工的完整过程及品质偏差成因线索。查询时项目已经竣工，原项目景观主管已经离职，岗位随项目结束撤销，因此传统依赖关键人员访谈的回溯方式难以实施。

该案例涉及景观、成本、合约、工程和设计等5个部门，信息来源包括IM私聊、IM群聊、会议纪要、中标报价存档、节点签认记录、事件日志以及项目历史经验等8类信息来源/信息载体，覆盖招标至验收阶段的5个业务阶段。

本案例主要验证两个问题：

1. 在没有预设专属SOP的情况下，Agent能否组合已有能力完成复合信息任务；
2. 多来源信息能否被组织为跨部门、跨阶段的可回溯事件链，并识别其中的信息流转缺口。

### 5.3.2 任务发现与权限判断

集团经理提出跨部门复合查询请求后，SessionAgent首先在系统能力书中检索相关能力，但未匹配到“景观软装品质问题追溯”专属SOP。

系统并未因此拒绝任务，而是根据组织规则书进行权限判断，并通过DB确认用户具备跨源复合查询权限。随后，SessionAgent将任务拆解为多个信息检索WorkItem，由WorkItemAgent分别调用RAG、DB、事件日志和历史经验等已有能力。

GuardianAgent对跨部门信息访问权限、临时组合查询是否超出能力边界以及涉密信息的分级输出进行核验。

### 5.3.3 跨部门多源事件链重构

系统最终还原出从招标、交底、采购、进场到验收的事件演进链。其成因线索主要包括：

1. 合约规划阶段软装未独立列项，导致预算与深化设计责任界面不清；
2. 景观主管与成本部门之间存在成本信息壁垒，品质要求缺少明确的成本锚定；
3. 承包单位认为合同与价目清单未包含专业厂家二次深化设计，双方缺少明确依据；
4. 采购档次受零散报价约束，缺乏独立预算和品质锚定；
5. 工程节点时限压力导致软装材料在品质问题未完全解决前推进进场；
6. 完工确认过程中存在设计部门未签认即完成确认的程序缺口。

**图5-1 案例B跨部门多源事件链重构（文字占位）**

> 招标 → 预算/合约界面 → 交底 → 采购 → 进场 → 验收  
> 各阶段分别连接IM记录、会议纪要、DB存档、事件日志和历史经验，最终形成带来源标识的事件演进链。

系统不仅还原事件链，还识别出成本信息壁垒、合约界面缺口和程序缺位等信息流转缺口。需要说明的是，上述“成因线索”是基于多源事件记录的时间排序、关联与交叉印证形成的成因推断，而非严格的因果证明。改进建议均标注来源，并作为参考意见交由管理人员决定是否采纳。

### 5.3.4 权限分级与能力组合

案例中，系统遇到涉密成本信息时没有简单采用“拒绝访问”策略，而是根据用户角色和资源等级判断其是否具有查看权限，并在允许访问时进行相应的信息分级处理。

同时，系统没有因为缺少专属SOP而生成新的业务流程，而是在既有能力范围内临时组合RAG检索、DB查询、事件日志和历史经验等能力。该过程验证了“可扩展但不失控”的设计边界：系统能够应对未预设的信息任务，但不会自行修改组织规则或创建新的业务流程。

此外，本案例还体现了“权限拒绝→协作导航”的机制。当某查询者询问其无权直接访问的成本涉密信息时，系统并未直接返回受限数据，而是根据组织规则书查询相应成本主管的在岗状态，在不泄露受限信息的前提下建议其向该主管获取信息。后续群聊记录中确实出现了这一沟通，说明权限控制在这里不是任务终止，而是转化为合法的协作路径。

### 5.3.5 验证结果

案例B最终形成跨5个部门、8类信息载体/记录来源、5个业务阶段的事件演进链，并识别出3处具有组织层面意义的信息流转缺口。不同阶段由不同来源记录共同构成事件链，部分关键事件可由多个来源交叉印证。该结果说明，系统的价值并非单纯提高资料搜索速度，而是能够将分散在不同部门和信息载体中的同期记录组织为可回溯的事件链。

尤其是在原关键知情人已经离岗的情况下，系统仍可以依赖历史留痕进行事件回放，从而降低组织记忆对个人在岗状态的依赖。

因此，案例B主要验证了**非预设场景下的能力组合以及跨部门多源事件链重构机制**。

两个案例分别验证了“预设业务流程中的受控执行”和“非预设复合任务中的信息重构”，共同覆盖了本文从认知组织、状态感知、能力发现到任务执行和核验的主要技术链条。

## 5.5 局限性与讨论

首先，本文案例数量有限，当前验证主要属于工程可行性验证，尚不能据此推导不同企业、不同规模项目中的普遍效果。后续需要扩大项目样本，并引入不同业务条线进行重复验证。

其次，本文尚未设置与人工检索、传统协同系统或单Agent方案的系统性对照，因此目前无法对信息获取效率、错误率等指标进行严格的相对量化评价。本文选择机制验证而非性能对照，主要是因为研究目标是验证架构路线是否成立，而非比较某个基础模型的性能。

再次，当前认知基座主要采用RAG与结构化DB两种召回路径。RAG受文档切分和嵌入质量影响，跨文档、跨载体的关联能力仍有限；DB查询则依赖预设表结构，对过程信息中的弱关联发现能力不足。这是进一步提升团队公共认知深度的主要技术瓶颈。

最后，LLM参与项目状态语义判断仍然具有不确定性。因此本文通过人工定义状态空间、成果约束、权限核验和关键状态人工确认等机制限制其自由度。未来可以进一步研究事件图、知识图谱或Wiki式知识条目网络与三书机制的结合，以增强跨来源关联和证据追踪能力。

# 6 结论与展望

本文针对地产项目团队中过程信息持续沉淀困难、多源信息难以关联、组织经验复用不足以及传统管理链条难以进行全过程信息核验等问题，从地产项目管理要素出发，建立了管理要素与Agent技术对象之间的映射关系，并构建了面向团队公共认知的信息协同型AI智能体架构。本文的核心方法是领域管理结构驱动的Agent架构重构方法，三书、LLM增强FSM、Skill化SOP与三智能体是该方法在不同管理要素上的技术实现机制。

在技术路线方面，本文将项目过程信息、组织规则和系统能力组织为三书认知基座，将项目节点重构为LLM增强有限状态机，将标准业务流程封装为Skill化SOP，并通过SessionAgent、WorkItemAgent和GuardianAgent分别承担任务组织、业务执行和职责隔离的二次核验职责，从而形成“认知—感知—执行—核验”的完整技术链。

在工程验证方面，案例A表明，系统能够将项目态势、业务流程、组织规则和历史经验组合为面向具体人员的任务支持，并在关键执行节点进行权限和结果核验；案例B表明，在没有预设专属SOP的情况下，系统能够在权限约束下组合已有能力，跨5个部门、8类信息载体/记录来源和5个业务阶段还原事件演进链，并识别组织信息流转缺口。两个案例共同表明，在本文所验证的地产项目场景下，团队级Agent能够在不依赖特定人员持续在岗的情况下，对项目过程信息形成持续的公共认知，并在受控边界内为团队协同提供信息支持。

本文的主要认识是，垂直行业AI的工程价值不必然来自替代专业人员，也可以来自对组织信息流的重新组织。对于地产项目这类具有多角色、多阶段、多来源信息特征的业务环境，AI Agent如果能够同时具备公共认知、动态状态感知、业务能力调用和组织化核验能力，其角色可以从单点任务工具进一步转变为团队的信息基础设施。

本文仍存在案例规模有限、缺少基线对照以及跨来源知识关联能力不足等局限。后续将围绕三书认知基座的深化展开研究，重点探索Wiki式知识条目网络、事件关系网络与RAG/DB双路径召回的结合，以进一步提升项目公共认知的关联深度、证据可追溯性和跨项目经验复用能力。
