# 论文提纲指导：中级职称定位 + 是否浪费的考量

> 日期：2026-08-12
> 关联：配合 [论文提纲_导师点评.md](论文提纲_导师点评.md) 阅读，上一份点评偏学术期刊标准，本文件做两个调整：(1) 按中级职称实际要求降执行标准；(2) 讨论"只弄职称是否浪费"的问题。

---

## 一、中级职称论文 vs 学术期刊论文：评价标准完全不同

中级职称论文的核心逻辑不是"做出学术贡献"，而是**"证明你具备独立解决工程问题的专业能力"**。两者的评价标准：

| 维度 | 学术期刊审稿人看什么 | 职称评审专家看什么 |
|------|---------------------|-------------------|
| **创新性** | 理论/方法上有没有前人没做过的东西 | 有没有结合行业实际做有价值的工程实践 |
| **系统设计** | 设计决策的理论正当性 | 架构是否合理、技术选型是否有依据 |
| **实验** | 严格的定量对比、统计显著性 | **有真实数据支撑**即可，不要求对照实验 |
| **文献** | 全面覆盖、精确定位 gap | 有就行，证明你了解行业现状 |
| **写作** | 学术规范、英文表达 | **逻辑清晰、言之有物**，中文写作过关 |
| **核心问题** | "So what?"（你的贡献是什么） | "这个工程师能不能干活？"（专业能力展示） |

**上一份点评的框架完全可用，但执行标准要大幅下调。**

## 二、投稿定位：降两档，聚焦实用

| 原建议 | 修正建议 | 理由 |
|--------|---------|------|
| 投 *Automation in Construction* / *JSS* / ICSE SEIP | 投**省级或国家级工程技术类期刊**，如《土木建筑工程信息技术》《建筑施工》《工程质量》《建筑经济》《智能建筑》等 | 中级职称一般要求公开发表 1-2 篇，省级以上刊物即可，部分单位要求核心期刊 |
| 英文投稿 | **建议中文投稿** | 职称评审中文期刊认可度更高，写作成本低，审稿周期短 |
| 追求学术 novelty | **追求"工程实践价值 + 技术深度"** | 评审专家更看重你解决了什么实际问题、用了什么技术手段、效果怎么样 |

**首选目标**：《土木建筑工程信息技术》（住建部主管，BIM/信息化方向，非常对口）。备选：《建筑施工》《工程质量》《智能建筑》。

## 三、论文结构不变，内容密度大幅降低

### 3.1 题目（中文即可）

- **《面向房地产项目管理的团队级 AI Agent 系统设计与实践》**
- **《基于大语言模型的垂直领域智能助手架构设计——以房地产行业为例》**
- **《Emily：一种团队协作式的地产行业 AI 智能体系统》**

要点：出现"设计""实践""应用"等工程关键词。

### 3.2 摘要（中文，200-300 字）

标准三段式：
1. **问题**：房地产项目管理中存在信息层级损耗、经验随人流失、传统 MIS 使用门槛高等问题
2. **方案**：基于大语言模型设计了一套团队级垂直 AI Agent 系统，提出若干设计原则，采用 Session 主线 + WorkItem 执行单元的架构
3. **效果**：实际部署运行，覆盖 N 类业务场景，验证了方案的可行性

### 3.3 引言（精简到 1-1.5 页）

从提纲的论点 1-4 中，各取最精华的一段：
- 论点 1（ANI 本质）：1 段，说明为什么 AI 在行业中应定位为增强工具
- 论点 2（团队级训练优于个人）：1 段
- 论点 3（经验流失问题）：半段
- 论点 4（传统 MIS 的学习成本）：半段
- 最后半段：引出本文工作

不需要做学术论文式的详尽文献综述——更重要的是"让评审专家觉得这个问题确实存在、值得解决"。

### 3.4 相关工作（大幅简化）

不需要 6 条文献线索。**10-15 篇中文文献即可**，覆盖：
- 建筑业信息化/数字化的国内研究
- LLM 在垂直行业应用的相关论文
- RAG 技术应用的文献
- 企业知识管理的经典文献

写法从"carve out a niche"降为"概述行业现状 + 指出还有改进空间"。一段一个方向，三段收工。

### 3.5 设计原则（保留，加分项）

上一份点评的 5 条原则框架**保留**——评审专家看到你能从工程实践中提炼出方法论，比单纯描述系统加分得多。

但表述要接地气，不追求英文术语。例如：
- P1 → "弱人工智能定位：AI 作为增强工具而非替代工具"
- P2 → "以团队为主体的 AI 训练模式"
- P3 → "自然语言降低信息录入门槛"
- P4 → "渐进式知识发现与按需加载"
- P5 → "陪跑式信息采集与持续沉淀"

### 3.6 系统架构（核心章节，重点写）

**这是评审专家最看重的部分**——能不能把一个复杂系统讲清楚。你已有的材料足够写出很有分量的一章。

结构：
1. **整体架构图**（现有 Mermaid 图转论文配图）
2. **消息处理主流程**（IM → 薄插件 → FastAPI → SessionAgent → WorkItem → 回复）
3. **关键模块分述**（选 3-4 个最有特色的）：SessionAgent / WorkItemAgent / RAG 知识检索 / SOP 渐进式加载
4. **数据库设计简述**（核心表 ER 简图）

技巧：每个模块写三段——"为什么需要"→"怎么设计"→"用了什么技术"。

### 3.7 效果验证（不需要严格实验，但必须有数据）

职称论文对"实验"的要求远低于学术期刊。不需要对照组、统计显著性。但**必须有真实数据**。

**最低可行方案**（任选 2-3 项就够）：

| 数据类型 | 怎么获取 | 怎么写 |
|----------|---------|--------|
| 功能测试通过率 | emy-test 已有的 13/13 | "针对 13 个业务场景端到端测试，全部通过" |
| 业务覆盖范围 | SOP 数量 + 工具数量 | "系统覆盖 N 类业务 SOP、M 个业务工具" |
| 系统运行稳定性 | Docker 容器 uptime、消息处理量 | "系统已持续运行 X 天，处理消息 Y 条" |
| LLM 调用效率 | mitmproxy jsonl 日志 | "平均单次请求 token 消耗 X，响应延迟 Y 秒" |
| 典型场景演示 | 选 2-3 个有代表性的对话记录 | 文字 + 截图展示 Emily 处理复杂请求 |

**这可能是整篇论文最关键的 2-3 页**——评审专家看到有数据、有截图、有案例，就放心了。

### 3.8 结论（半页到一页）

四件事：本文做了什么 → 局限性（2-3 条）→ 未来改进方向（1-2 条）→ 对其他行业的参考意义（一句拔高）。

## 四、篇幅控制

| 章节 | 建议页数 | 说明 |
|------|---------|------|
| 摘要 | 0.5 页 | 中文摘要 + 关键词 |
| 引言 | 1-1.5 页 | 行业背景 + 问题提出 |
| 相关工作 | 1-1.5 页 | 简化的文献综述 |
| 设计原则 | 2-3 页 | 5 条原则，每条半页 |
| 系统架构 | 4-6 页 | **核心章节，写厚** |
| 效果验证 | 2-3 页 | 数据 + 案例 |
| 结论 | 0.5-1 页 | 总结 + 展望 |
| **总计** | **12-16 页** | 5000-8000 字，附图表 |

对中级职称来说非常合适——不会太薄显得没东西，也不会太厚让评审专家不耐烦。

## 五、"多拿点分"策略

### 加分项

| 加分点 | 怎么做 | 预估加分 |
|--------|--------|---------|
| **有实际部署** | 论文中明确写"系统已在 XX 项目实际部署运行" | 高 |
| **有数据支撑** | 测试结果、运行统计、token 消耗分析 | 高 |
| **有系统截图** | 对话截图、架构图、数据库设计图 | 中 |
| **技术栈规范** | Docker Compose、FastAPI、PostgreSQL、LangGraph——这些技术名词本身说明现代软件工程能力 | 中 |
| **有设计方法论** | 5 条设计原则——从实践中提炼方法论，区分"码农"和"工程师" | 高 |
| **有创新点** | "团队级 AI 训练主体"这个提法本身就有新意 | 中 |
| **文献引用规范** | 引用 10-15 篇，格式正确 | 低但必要 |

### 失分陷阱

| 陷阱 | 说明 |
|------|------|
| **只描述不分析** | 不能只写"系统有 A、B、C 模块"，要写"为什么需要 A，它解决什么问题" |
| **技术堆砌** | 不能像产品说明书一样罗列技术名词，要解释选择每项技术的原因 |
| **没有数据** | 纯文字描述系统，没有任何运行数据或测试结果——评审专家会怀疑系统是否真的跑起来了 |
| **标题太大内容太小** | "基于 AI 的房地产管理系统研究"这种题外行——题目与内容要匹配 |

## 六、时间线

总周期约 1.5 个月：

| 阶段 | 时间 | 产出 |
|------|------|------|
| 确定投稿期刊 | 第 1 周 | 选定 1-2 个目标期刊，下载 3-5 篇已发表论文看风格 |
| 写系统架构章节 | 第 1-2 周 | 初稿 4-6 页 |
| 补数据 + 写效果验证 | 第 2-3 周 | 收集运行数据、整理测试结果、截图 |
| 写设计原则 + 引言 + 相关工作 | 第 3-4 周 | 三章初稿 |
| 全文整合 + 摘要结论 | 第 4-5 周 | 完整初稿 |
| 修改打磨 | 第 5-6 周 | 2-3 轮修改 |
| 查重 + 投稿 | 第 6 周 | 查重过关后投出 |

---

## 七、总结：两份点评的分工

- **第一份点评**：提供方法论框架——论文结构、设计原则提炼、写作逻辑、学术深度方向。**全盘保留，作为"上限"。**
- **本文件**：提供执行标准下调——把"发顶刊"的标准降到"发省级期刊评职称"的标准，作为**"保底方案"**。

你现在有了一个完整的梯度：保底是写一篇够评中级职称的省级期刊论文，上限是写一篇有学术贡献的系统设计论文。两篇的核心素材完全相同（Emily 项目），差别只在于写作深度、实验强度、文献广度和投稿目标。
