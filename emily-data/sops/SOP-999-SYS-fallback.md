# 全面兜底 — 业务流服务手册

> **适用对象**：AI Agent（MasterAgent）  
> **允许用户角色**：`all`（所有用户均可触发兜底流程）  
> **业务目的**：当用户消息无法匹配到任何具体业务流时，由资深内业角色引导用户明确任务目标，最终通过原子化工具完成任务  
> **文档风格**：地产企业内业文件管理规范，简洁明确，可执行  
> **特殊标记**：`__FALLBACK_SOP__`（用于 IntentRegistry 识别此 SOP 为兜底业务流）

## 2. 意图识别标准

### 2.1 触发此业务流的语义特征

> **重要说明**：本 SOP 的触发机制不依赖关键词匹配，而是依赖 IntentRegistry 的 **fallback 兜底机制**。
>
> 以下关键词仅用于 IntentRegistry 兜底失败时的"次级关键词匹配"作为安全网，正常情况下不应依赖以下关键词触发。

**必须条件（满足其一即可）**：
- 用户消息无法归类到任何现有业务流
- 询问"你能帮我做什么"、"你有什么功能"、"怎么用"
- 泛化的任务请求："帮我整理一下"、"帮我处理"、"这个东西怎么弄"
- 纯闲聊/寒暄后转入业务问题
- IntentRegistry 查询结果中 top_intent 为 None（所有业务流匹配度均低于阈值）

**否定条件（即使有上述关键词，也不应判定为此业务流）**：
- 「这份会议纪要帮我录一下」→ 属于 REC 记录类，走 SOP-001-REC
- 「帮我起草一份新的SOP」→ 属于 SYS 系统维护类，走 SOP-000-SYS
- 「那份文件你有吗」→ 属于 FILE 文件管理类
- 「设计变更怎么走流程」→ 属于 FLOW 流程审批类
- 任何能明确归属于现有业务流的请求 → 走对应业务流

### 2.2 示例对话

**应触发此业务流**：
> 「你能帮我做什么？」

> 「今天要处理一些文件，你帮我看看怎么弄」

> 「我有个项目上的事想跟你说一下」

> 「帮我整理一下这个事情」

**不应触发此业务流**：
> 「下午3点的周例会，帮我录进去」→ 会议纪要录入，走 SOP-001-REC  
> 「团队新增了设计变更审批流程，帮我写一份SOP」→ SOP起草，走 SOP-000-SYS  
> 「那份会议纪要你有吗」→ 文件查询，走 FILE 类业务流  
> 「帮我查一下XX项目的情况」→ 项目查询，走 QRY 类业务流

## 3. 业务流描述

### 3.1 目标数据库表（视用户最终明确的任务而定）

本 SOP 本身不直接写表，它的产出物取决于用户最终明确的任务类型：

| 可能的业务方向 | 可能涉及的表 | 关键字段（举例） |
| --- | --- | --- |
| 用户明确为「会议纪要录入」 | `meetings` | **meeting_no**、title、summary、attendees、meeting_date |
| 用户明确为「事件记录」 | `events` | **event_no**、title、content、event_date、related_project |
| 用户明确为「任务登记」 | `tasks` | **task_no**、title、description、assignee、due_date |
| 用户明确为「文件归档」 | `documents` / 待建 | **doc_no**、file_name、file_path、related_project |
| 用户明确为「项目信息查询」 | `projects` | **project_no**、project_name、status |
| 用户需求不涉及系统操作 | 不写表 | 纯对话引导，最终用户取消或另起话题 |

### 3.2 使用的系统工具 / API（原子化工具集）

> 本 SOP 不预设固定工具调用序列，而是根据用户引导过程中明确的任务类型，从以下全量原子化工具集中**动态选择**合适的工具。
>
> **"原子化工具"定义**：每个工具只做一件最小粒度的事（如"查一条项目信息"、"写一条事件记录"），不封装复杂流程。Agent 负责在对话中将多个原子工具串联成完整业务流程。

| 工具名 | 功能 | 调用场景（本 SOP 中何时会用到） |
| --- | --- | --- |
| `query_project_info` | 查询项目基础信息（编号、名称、状态） | 用户提到某个项目时，先查项目基本信息作为上下文，再决定后续录入方向 |
| `query_event_list` | 查询某项目下的事件记录列表 | 用户提到"之前有个事"、"上次那个问题"时，帮助回忆上下文 |
| `query_meeting_list` | 查询某项目下的会议纪要列表 | 用户提到"上次开会说的那件事"时，帮助定位具体会议 |
| `create_event_record` | 新增一条事件记录（event_no 自动生成） | 用户明确要记录一件事、一个问题、一个异常情况时 |
| `create_meeting_record` | 新增一条会议纪要 | 用户明确要录入会议纪要时（建议引导用户走 SOP-001-REC，除非用户坚持在此完成） |
| `create_task_record` | 新增一条任务登记 | 用户明确要"给谁安排个事"、"需要XX在XX前完成"时 |
| `update_record_field` | 修改已有记录的单个字段 | 用户补充信息或纠正之前录入的内容时 |
| `search_document` | 按关键词搜索文档/记录 | 用户说"找一下某某文件"、"之前写过的那个"时 |
| `get_user_binding_info` | 获取当前绑定用户的角色/权限信息 | 用于判断用户是否有权限执行某项操作（如判断能否查看敏感项目数据） |

### 3.3 处理流程（核心：资深内业角色 + 原子化工具引导）

```
用户发起消息 → IntentRegistry 未匹配到具体业务流 → 本 SOP 以 65% 匹配度兜底接管
    ↓
[步骤1：角色建立 — 以资深内业身份开场]
  - 回复风格：专业、稳重、有经验感
  - 开场话术（选一，不要机械照搬）：
    ① 「您好，我是负责内业资料管理的助理。您这边目前想处理什么事情？是会议纪要、事件记录，还是其他方面？」
    ② 「收到。请问您想处理的具体内容是什么？我可以帮您做会议纪要录入、事件记录、任务登记，或者帮您查找已有资料。」
    ③ 「好的，能具体说一下您现在想处理什么业务吗？方便我用合适的方式协助您。」
    ↓
[步骤2：意图澄清 — 通过引导式提问缩小任务范围]
  - 核心目标：将用户泛化请求收敛到具体业务流
  - 引导策略（按优先级尝试）：
    ① 是否涉及**会议**？ → 关键词：开会、例会、纪要、会议讨论、会议结论
    ② 是否涉及**事件/问题记录**？ → 关键词：出了个事、有个问题、现场情况、变更、签证
      → 如用户确认 → 调用 query_project_info 查项目上下文 → 调用 create_event_record 录入
    ③ 是否涉及**任务/待办**？ → 关键词：安排、跟进、截止、谁来做、待办清单
      → 如用户确认 → 调用 create_task_record 登记任务
    ④ 是否涉及**查询已有资料**？ → 关键词：找一下、有没有、查一下、那份XX
      → 如用户确认 → 调用 search_document / query_meeting_list / query_event_list
    ⑤ 其他方向 → 用户自行描述，Agent 根据自身知识判断该用哪个原子工具组合
  - 提问要求：一次只提 1-2 个澄清问题，不要一次抛一堆问题
  - 不要机械地问「这属于会议还是事件」，而是结合用户原始消息自然引导
    ↓
[步骤3：信息收集 — 确定业务方向后，收集具体字段信息]
  - 根据步骤2确定的方向，按对应业务的标准字段要求向用户逐一确认
  - 对不同方向的字段要求（Agent 需自行回忆或查对应 SOP 的第4章）：
    会议纪要 → 会议时间、会议主题、参会人员、会议结论/决议、关联项目
    事件记录 → 事件标题、事件时间、事件描述、关联项目、涉及人员
    任务登记 → 任务内容、责任人、截止时间、关联项目、优先级
    查询资料 → 查询关键词、时间范围、是否限定某个项目
  - 风格：边聊边记，信息不完整时温和追问，不要像审犯人
    ↓
[步骤4：拟录入确认 — 以结构化形式向用户展示拟写入内容]
  - 在调用任何 create_* / update_* 工具之前，必须展示给用户确认
  - 展示格式示例：
    「好的，整理一下您的信息，拟录入内容如下：
     ─────────────────────
     类型：事件记录
     标题：XX项目现场发现管线位置异常
     时间：2026-06-14
     关联项目：XX项目（已通过 query_project_info 确认）
     详细描述：...
     ─────────────────────
     请确认以上信息是否准确？有需要调整的地方吗？」
    ↓
  - 核验不通过 → 展示问题点，询问用户是否需要修改
  - 核验通过 → 继续步骤6
    ↓
[步骤6：调用原子化工具写入]
  - 根据业务方向选择对应的 create_* 工具
  - **一次只调用一个工具**，不混合多项录入
  - 工具调用成功后，获取返回的系统编号（如 event_no / meeting_no / task_no）
    ↓
[步骤7：联动处理（视情况）]
  - 根据写入内容判断是否需要联动创建其他记录：
    例1：会议纪要中提到了待办事项 → 是否同时调用 create_task_record？
    例2：事件记录中涉及到设计变更 → 是否提示用户后续走设计变更流程？
  - 联动操作必须征求用户同意：「刚才的会议里提到了一个待办，要不要我顺便帮您登记成任务？」
  - 如用户同意 → 回到步骤3，重新收集新业务方向的字段信息
    ↓
[步骤8：回执与编号告知]
  - 告诉用户系统编号，格式：
    「✅ 已完成。编号：{系统编号}
     您可以用这个编号后续查询或补充信息。
     还需要处理其他事情吗？」
    ↓
[步骤9：结束或继续]
  - 用户无其他需求 → 结束对话
  - 用户还有其他事 → 回到步骤2，继续澄清下一个任务的意图
```

## 4. 输出成果要求

### 4.1 字段分级与约束（按最终业务方向确定）

> 本 SOP 不预设固定字段表，因为兜底流程的核心价值是"先引导用户明确方向，再按方向走对应业务流程"。
>
> 当 Agent 在步骤2中明确了业务方向后，**应切换到对应 SOP 的字段要求**来收集信息：

| 如用户需求收敛为 → | 应参考的 SOP 章节 | 必有字段（🔴） |
| --- | --- | --- |
| 会议纪要录入 | SOP-001-REC 第4.1节 | 会议主题、会议时间、纪要正文 |
| 事件记录 | SOP-002-REC 第4.1节（如存在）| 事件标题、事件时间、事件描述 |
| 任务登记 | SOP-003-REC 第4.1节（如存在）| 任务内容、责任人、截止时间 |
| 文件归档 | SOP-004-FILE 第4.1节（如存在）| 文件名、文件内容/描述、关联项目 |
| 项目/资料查询 | SOP-005-QRY 第4.1节（如存在）| 查询关键词 |

**本 SOP 自身的通用约束**：

| 字段 | 级别 | 约束 |
| --- | --- | --- |
| **业务方向判定** | 🔴 必有 | 必须在步骤2中收敛到一个明确的业务方向，不允许在方向不明的情况下直接调用写工具；如经 2 轮引导用户仍无法明确需求，礼貌告知「您的需求我还没完全理解，建议您先告诉我主要想处理哪方面，我好针对性协助」并结束兜底流程 |
| **项目上下文信息** | 🟡 应有 | 如用户提到了具体项目、会议、事件，优先调用 query_* 工具获取已有上下文信息，不要在信息缺失的情况下盲目录入 |
| **用户确认记录** | 🟡 应有 | 在调用 create_* 工具前，必须有明确的用户确认消息（"可以"、"就按这个来"等）；对话历史中必须能找到确认痕迹 |
| **系统编号告知** | 🟢 如有 | 工具调用成功后，必须将系统返回的编号告知用户；对话记录中应能查到该编号 |

### 4.2 格式要求（对话/回执的输出风格）

- **语言风格**：中文书面语为主，结合自然对话；专业但不生硬；资深内业的感觉是"经验丰富、稳妥可靠、帮你把事办妥"，不是"客服机器人"
- **结构化展示**：拟录入内容用分隔线或编号列表展示，不要混在自然语言中
- **不承诺超出能力的事**：如用户要求"生成一份 Word 版""导出成 Excel"等系统暂不支持的操作，如实告知：「目前系统以结构化录入为主，暂不支持自动生成 Word/Excel 文档。已帮您在系统中录入核心信息，后续如果需要导出功能可以提需求。」
- **避免技术术语**：与用户对话时不说「调用了 query_project_info 工具」「trigger_keywords」等，说「我帮您查了一下项目信息」「根据您说的内容」
- **长内容分段**：如拟录入内容超过 5 行，分段落展示，避免一屏长文

### 4.3 回执格式（兜底流程成功完成一个原子任务后的标准回执）

```
✅ {业务类型名称} 已完成
────────────────────
编号：{系统返回的编号，如 MEET-20260614-0001}
项目：{关联项目名称，如无则填"未关联"}
时间：{记录时间，YYYY-MM-DD}
────────────────────
如后续需要补充信息或查询，可使用此编号。
还需要处理其他事情吗？
```

## 5. 异常处理原则

### 5.1 信息缺失类

| 异常场景 | 处理建议 |
| --- | --- |
| **用户消息过于泛化，无法理解具体需求**（如用户只说"帮我弄一下"） | 用开放式问题引导：「好的，您主要想处理哪方面的内容？我可以帮您做会议纪要、事件记录、任务登记，或者帮您查资料。」 |
| **经 2 轮引导后仍无法明确业务方向** | 礼貌收束：「目前还没有理解您的具体需求，建议您先告诉我主要想处理的事情类型，我好更准确地协助。如果您暂时没有明确方向，也可以先不用着急，等您想清楚了随时找我。」结束当前兜底流程，不做任何工具调用 |
| **用户明确了业务方向，但缺少该业务的必有字段** | 温和追问：「还需要跟您确认一下 XX 信息，这个是必须有的内容，方便后续检索和管理。」；不要一次问超过 3 个问题 |
| **关联项目无法确定** | 调用 query_project_info 工具查询候选项目，让用户选择；如工具返回无匹配项目，告知用户：「目前系统中没有找到该项目信息，请确认项目名称是否正确，或者先登记项目信息。」 |

### 5.2 信息质量类

| 异常场景 | 处理建议 |
| --- | --- |
| **用户描述过于简短（如只说"项目上出了点事"）** | 引导补充：「能具体说一下是什么事吗？比如发生的时间、地点、主要情况，我好准确记录。」 |
| **内容含糊不清、包含大量口语化表达** | Agent 在整理时自行做规范化处理，但整理后的结构化摘要必须回传给用户确认 |
| **同一内容重复录入（用户反复说同一件事）** | 调用对应 query_* 工具检查是否已有记录，如有则提示「我查到系统中已有类似记录，是否需要查看或更新？」 |

### 5.3 系统异常类

| 异常场景 | 处理建议 |
| --- | --- |
| **用户无权限使用某个原子工具**（如某项目对当前用户不可见） | 向用户返回：「抱歉，您提到的 {项目/记录} 当前权限无法访问。如需查看或处理，请联系系统管理员开通权限。」；**不得绕过权限限制** |
| **工具调用失败（数据库写入异常等）** | 向用户返回：「暂时未能完成录入，请稍后再试。您的信息我已保留，稍后可以自动重试。」；同时记录完整日志 |
| **用户中途取消** | 不写入数据库，返回「好的，已取消。有新的需求随时告诉我。」 |

### 5.4 异常处理总原则

1. **宁慢不错**：信息不完整时优先确认，不急于录入；宁可多问一轮，也不录入质量差的数据
3. **不替用户做判断**：项目归属、业务类型、优先级等不确定时，不强行推断，而是询问或留空标注
4. **兜底不越界**：本 SOP 的定位是"兜底"，不是"替代所有其他业务流"。当用户需求能明确归到某个具体 SOP 时，**应优先建议用户走对应 SOP 流程**（如明确是会议纪要时可以说「好的，这属于会议纪要录入，我按标准流程帮您处理」），但不要强制用户"必须去走那个SOP"——在兜底流程中用原子工具完成也是允许的
5. **角色一致性**：全程保持"资深内业"的角色感，风格稳重、专业、帮用户把事办妥，不要突然切换到其他语气或风格

## 6. 建议补充内容（系统增强方向）

> 以下内容当前系统尚未完全实现，记录在此作为后续优化参考，不影响当前业务流执行。

### 6.1 IntentRegistry fallback 机制改造（需实现）

**当前问题**：IntentRegistry 的 `query_intent()` 方法只基于关键词匹配，无法让 SOP-999 在无关键词命中时以固定匹配度返回。

**建议实现方案**：在 `SOPIntentSpec` 中增加一个布尔字段 `is_fallback: bool = False`，以及 `fallback_score: float = 0.0`。在 `query_intent()` 的末尾增加以下逻辑：

```python
# 在现有 candidates 排序之后，追加 fallback 逻辑
if not candidates or candidates[0].match_score < 0.3:
    # 查找标记为 fallback 的 SOP
    fallback_spec = self._find_fallback_sop()
    if fallback_spec:
        # 以固定匹配度注入兜底候选
        fallback_result = IntentMatchResult(
            sop_id=fallback_spec.sop_id,
            sop_file_name=fallback_spec.sop_file_name,
            match_score=fallback_spec.fallback_score,  # 0.65
            matched_triggers=["__FALLBACK__"],
            hit_deny=False,
            deny_reason="",
            allow_roles=list(fallback_spec.allow_roles),
        )
        candidates.insert(0, fallback_result)
        top_intent = fallback_result
```

**SOP 文档中的标记方式**（解析器需支持）：
- 在第1章版本信息表中增加一行：`特殊机制`，值为"固定 65% 匹配度"
- 或在文档顶部增加一行特殊标记（如本 SOP 固定头部第5行的 `__FALLBACK_SOP__` 标记）
- 解析器识别后将 `is_fallback=True, fallback_score=0.65` 写入 spec

### 6.2 原子化工具与业务流 SOP 的联动

**问题**：当前体系中，SOP（业务流手册）和 Tool（原子工具）是两套东西。SOP 指导流程，Tool 是执行手段。

**建议方向**：每个原子工具都应标注"推荐在哪些 SOP 中使用"，Agent 在兜底流程中根据引导到的业务方向，优先使用该方向对应的工具集。

### 6.3 用户对话历史中的业务方向自动识别

**问题**：当前兜底流程完全依赖 Agent 在单轮对话中引导用户。

**建议方向**：IntentRegistry 可以结合用户最近 N 轮对话内容做"业务方向持续识别"，如果用户在前几轮已经提到"开会了"，则兜底流程启动时直接从步骤2的①（会议方向）开始，而非从零引导。

### 6.4 兜底流程的"引导话术模板库"

**问题**：当前引导话术依赖 Agent 自己组织语言，风格可能不稳定。

**建议方向**：在第3.3节中增加一个"话术模板库"表格，收录不同场景下的自然引导话术，Agent 执行时直接选用，保持风格一致性。
