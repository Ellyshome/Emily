## 第2章 意图识别

### 2.1 触发此业务流的语义特征

**必须条件**：
- 审核任务、确认完成、确认通过
- 退回修改、驳回重做、不符合要求
- 验收成果、检查任务
- 审批任务、复核任务

**否定条件**：
- 创建新任务（应触发 SOP-009-REC）
- 查询任务状态（应触发 SOP-009-REC 内的 query_plan_tasks）
- 异常任务复核（P2 阶段功能，当前通过手动执行）

### 2.2 示例对话

**应触发此业务流**：
> 「确认张三的铺装材料验收任务已经完成」
> 「退回李四的周报任务，内容不够详细」
> 「审核通过 PTI-20260625-0001 这个任务」
> 「验收通过，这个任务没问题」

**不应触发此业务流**：
> 「给王五布置一个新任务」→ SOP-009-REC
> 「查看我提交的任务状态」→ SOP-009-REC
> 「记录今天验收发现的问题」→ SOP-002-REC

## 第3章 业务流描述

### 3.1 目标数据库表

- `plan_task_instances` — 任务实例
- `plan_task_logs` — 状态变更日志

### 3.2 使用的系统工具/API

| 工具名 | 用途 |
|--------|------|
| `review_plan_task` | 审核计划任务成果（确认或退回） |
| `query_plan_tasks` | 查询计划任务列表（找到待审核的任务） |

### 3.3 处理流程

```
用户请求
    │
    ├─ 查询待审核任务？
    │     └─ query_plan_tasks (role=initiator, status=SUBMITTED)
    │
    ├─ 确认通过？
    │     └─ review_plan_task (action=confirm)
    │         SUBMITTED → CONFIRMED
    │         → 调度机后续自动归档
    │         → 如有关联工作流则自动启动
    │
    ├─ 退回修改？
    │     └─ review_plan_task (action=return)
    │         SUBMITTED → RETURNED
    │         → 通知执行者修改后重新提交
    │
    └─ 不匹配 → 兜底处理
```

## 第4章 输出要求

### 必填字段
- ✅ 任务实例编号（instance_no）
- ✅ 审核动作（action: confirm / return）

### 应有字段
- 🟡 审核意见/原因（reason）

---

## 第5章 异常处理

### 缺失处理
- 缺少 instance_no：提示用户先查询任务列表找到目标编号

### 质量处理
- 实例不存在：提示用户检查编号
- 实例状态不是 SUBMITTED：提示用户当前状态不支持审核
- 非发起人审核：警告但允许（由权限系统控制）

### 系统处理
- 数据库写入失败：重试一次，仍失败则告知用户
- 状态流转冲突：检查当前状态，返回具体错误信息
