# 节点实例填充 — 业务流服务手册

> **适用对象**：AI Agent（Emily Agent，负责任务执行与语义理解）
> **允许用户角色**：`admin` / `project_owner`
> **业务目的**：针对单个节点，套用 V4 模板生成完整的节点实例 Markdown 文档。对缺失的关键字段主动向用户收集，通过多轮对话逐步补齐

## 2. 意图识别标准

### 2.1 触发此业务流的语义特征

**必须条件（满足其一即可）**：

- 用户要求针对某个具体节点"生成实例文档"、"填充节点详情"、"套用模板生成节点文档"
- 用户为已有节点补充或更新字段，如"帮我把 SG-JG 的监理单位补上"、"SG-015 的完成标准改为：..."
- 用户提供节点编号 + 已知字段值，要求生成该节点的完整实例 .md
- SOP-012 批量调用：导入 Excel 后，对每个解析出的节点自动串联调用本 SOP
- 用户说"帮我给 XX 节点出一份完整的节点说明书"

**否定条件（即使有上述关键词，也不应判定为此业务流）**：

- 用户上传 Excel 文件要求"解析这份项目计划" → 宏观导入，走 SOP-012-FLOW
- 用户询问"XX 节点是什么状态" → 查询，走 SOP-005-QRY
- 用户要求"修改节点状态为已阻塞" → 状态机管理，走 SOP-011-SYS
- 用户要求"起草一份新的 SOP" → 走 SOP-000-SYS

### 2.2 示例对话

**应触发此业务流**：

> 「景观工程节点 SG-JG 的监理单位是中建监理，帮我更新到节点实例文档里」

> 「SG-015 节点缺少完成标准，我现在补充：主体结构封顶且通过质监站验收」

> 「帮我给 QQ-001 土拓节点生成一份完整的节点实例文档」

> 「SOP-012 已完成节点树解析，现在对 SJ-JG 节点调用 SOP-013 生成实例」（系统级串联调用）

**不应触发此业务流**：

> 「这是我们项目的全生命周期 Excel，帮我导入」→ 宏观导入，走 SOP-012-FLOW
> 「景观工程节点现在是什么状态？」→ 查询，走 SOP-005-QRY
> 「帮我把所有工程节点的完成标准批量更新」→ 批量操作，建议先走 SOP-005-QRY 列出节点，再逐个走本 SOP

## 3. 业务流描述

### 3.1 产出物（不写入数据库表，产出为 Markdown 文件）

> **说明**：本 SOP 的产出物是单个节点的实例 Markdown 文档，存放于 `{阶段码}/` 目录下。不直接写入数据库。节点实例文档套用 V4 模板（参考 `emily-data/baseknowledge/全景节点参考文档.md` 及 `需求文件/全景节点图-梳理版V4/` 下的模板文件）。

| 产出物 | 格式 | 说明 |
| --- | --- | --- |
| 节点实例文档 | `{阶段码}/{节点编号}-{节点名称}.md` | 套用 V4 模板：继承关系表 → 继承字段清单 → 新增字段 → 业务表定义 → 节点状态流转 → 关联规则 → 变更与作废机制 |

### 3.2 使用的系统工具 / API

| 工具 | 功能 | 调用场景 |
| --- | --- | --- |
| `build_node_instance.py`（辅助脚本） | 确定性操作：接收结构化节点数据 + 指定模板，生成格式化的节点实例 .md 文件 | Agent 完成字段收集和确认后，调用脚本执行文档生成 |
| `文件写入`（系统基础能力） | 将生成的 Markdown 文档写入指定目录 | 节点实例文档生成后写入对应阶段目录 |
| `文件读取`（Agent 系统能力） | 读取 V4 模板文件（L0/L1 模板）以确定字段清单 | 步骤 1：匹配 L1 模板，加载模板内容 |
| `inspect_existing_tables`（数据库表结构检查） | 读取当前 `models.py` 的表全景 | 如模板引用了 DB 表（如 sm_nodes），校验字段一致性 |
| SOP-012-FLOW（上游 SOP） | 全景节点图构造：提供节点基础数据（编号、名称、完成标准等） | 导入场景下，SOP-012 批量调用本 SOP 前传入节点数据 |

### 3.3 处理流程

```
输入：节点编号 + 已知字段值（来自上游 SOP-012 或用户手工输入）
    ↓
[模板匹配] → 按节点编号的阶段码匹配 L1 模板：
  ① SJ → 设计阶段状态机模板（承包单位 / 甘特图 / 条件清单 / 设计文档索引）
  ② CB → 成本招采状态机模板（测算咨询单位 / 成本测算成果）
  ③ SG → 工程阶段状态机模板（承包+监理+分包 / 甘特图 / 文档库+表单索引）
  ④ QQ / YX / JF / GH / 其他 → 通用模板（仅 L0 基类字段）
  ⑤ 所有模板共用 L0 基类：3+1 时态模型 / 固有数据段 / 通用字段 / 表单审批流-基类 / 异常处理三阶段
    ↓
[字段状态判定] → 将模板字段分为三级，逐字段检查是否已填充：
  🔴 必有字段：
    · 节点编号（node_id）—— 来自输入
    · 节点名称（node_name）—— 来自输入
    · 完成标准（criteria）—— 来自输入
    ├── 已填充 → 写入实例
    └── 缺失 → **主动向用户询问**（每轮 ≤ 3 个问题）
  🟡 应有字段：
    · 责任部门（owner）/ 计划级别（plan_level）/ 是否关键节点 / 计划时间 / 上游节点 / 完工确认岗位
    ├── 已填充 → 写入实例
    └── 缺失 → 尽量从上下文推断填充；确实无法填充的标注「【待补充】」
  🟢 如有字段：
    · 监理单位 / 承包单位 / 节点成果列表 / 前置条件列表 / 变更与作废机制 / 节点日志
    ├── 有则填充
    └── 无则省略（不标注，不询问）
    ↓
[缺失收集] → 如有 🔴 必有字段缺失：
  ① 向用户列出缺失的 🔴 字段（每轮 ≤ 3 个），逐条询问
  ② 用户提供 → 填入，继续下一轮
  ③ 用户表示"暂无"或跳过 → 该字段标注「【缺失】」，在回执中提醒
  ④ 重复直到所有 🔴 字段已填充或用户明确跳过
    ↓
[阶段模板专属字段收集] → 根据匹配的 L1 模板：
  ① 列出该阶段模板要求但当前数据缺失的字段
  ② 设计阶段（SJ）：承包单位、条件清单表、设计文档索引
  ③ 工程阶段（SG）：承包单位、监理单位、分包单位、文档库索引
  ④ 成本阶段（CB）：测算咨询单位
  ⑤ 字段缺失 → 向用户确认（每轮 ≤ 3 个问题）
    ↓
[拟录入确认] → 以结构化形式向用户展示实例文档概要：
  ① 节点编号 + 名称 + 阶段
  ② 匹配的 L1 模板名称
  ③ 字段填充统计：🔴 {n1}/{t1} 已填、🟡 {n2}/{t2} 已填、🟢 {n3} 已填
  ④ V4 模板章节预览（继承关系→继承字段→新增字段→状态流转→关联规则→变更记录）
  ⑤ 等待用户确认或修改
    ↓
[调用 build_node_instance.py] → 传入结构化数据：
  ① 节点基础数据（JSON 或 CLI 参数）
  ② L1 模板标识（design / cost / engineering / generic）
  ③ 所有已收集的字段值
  ④ 脚本生成格式化的 .md 文件
    ↓
[文件写入] → 输出路径：
  {输出目录}/{项目名}/{阶段码}/{节点编号}-{节点名称}.md
  示例：解析结果/生态城26#地/SG/SG-JG-景观工程.md
    ↓
[返回确认信息] → 节点编号 + 文件路径 + 缺失字段提醒（如有）
```

## 4. 输出成果要求

### 4.1 字段分级与约束

| 字段 | 级别 | 约束 |
| --- | --- | --- |
| **节点编号**（node_id） | 🔴 必有 | 格式：`阶段码-序号`，如 `SJ-JG`、`SG-015`。由调用方（SOP-012 或用户）提供 |
| **节点名称**（node_name） | 🔴 必有 | 节点中文名称，如"景观设计"、"总包工程" |
| **完成标准**（criteria） | 🔴 必有 | 自由文本，承载该节点的完成判定标准。可为时间要求或成果要求 |
| **责任部门**（owner） | 🟡 应有 | 建设单位部门，如"设计部"、"工程部" |
| **计划级别**（plan_level） | 🟡 应有 | 枚举：一级/二级。一级为集团管控里程碑 |
| **是否关键节点**（is_milestone） | 🟡 应有 | 布尔。一级节点默认 true |
| **计划开启时间**（planned_start_date） | 🟡 应有 | 格式 YYYY-MM-DD |
| **计划结束时间**（planned_end_date） | 🟡 应有 | 格式 YYYY-MM-DD |
| **上游节点**（parent_name） | 🟡 应有 | 节点编号列表，如 `["GH"]` |
| **完工确认岗位** | 🟡 应有 | 默认值按阶段：SJ→设计部经理 / SG→工程部经理 / CB→成本招采部经理 / 其他→项目负责人 |
| **承包单位** | 🟢 如有 | 设计/工程阶段有，前期/营销阶段通常无 |
| **监理单位** | 🟢 如有 | 工程阶段（SG）有，其他阶段通常无 |
| **分包单位** | 🟢 如有 | 工程阶段（SG）可能有 |
| **节点成果列表**（deliverables） | 🟢 如有 | 如施工图、验收报告等 |
| **前置条件列表**（preconditions） | 🟢 如有 | 从上游依赖自动填充 |
| **变更与作废机制** | 🟢 如有 | V4 模板定义，初次填充可省略，后续实操补充 |
| **节点日志** | 🟢 如有 | 运维阶段动态追加，初次填充省略 |
| **目标表结构与复用决策**（table_decision） | 🔴 必有 | 如模板引用 DB 表，必须写明引用了哪些表 |

### 4.2 格式要求

- **文档结构**：严格按 V4 模板的章节顺序组织：继承关系 → 继承字段 → 新增字段 → 业务表定义 → 节点状态流转 → 关联规则 → 变更与作废
- **文件名**：`{节点编号}-{节点名称}.md`，如 `SJ-JG-景观设计.md`，中文允许，不包含特殊字符 `<>:"/\|?*`
- **表格格式**：继承关系表（层级/模板/说明三列）、继承字段表（字段/来源/本节点取值三列）与 V4 模板保持一致
- **状态流转**：使用文本流程图格式，`──→` 连接状态，下附流转条件表
- **变更记录**：每个节点实例文档末尾包含空的变更记录表（v1.0 / 日期 / 创建人 / "初版生成"）
- **缺失标记**：模板要求但数据缺失的字段标注 `【待补充】`，不允许留空

### 4.3 回执格式

```
📋 节点实例生成完成
──────────────
节点编号：{node_id}
节点名称：{node_name}
所属阶段：{stage_name}
匹配模板：{L1 模板名称}（{design/cost/engineering/generic}）
──────────────
字段填充：
  🔴 必有：{filled}/{total}（缺失：{missing_list}）
  🟡 应有：{filled}/{total}（待补充：{pending_list}）
  🟢 如有：{filled} 个字段已填充
──────────────
产出物：{路径}/{阶段码}/{节点编号}-{节点名称}.md
──────────────
[提醒]
  · {如有 🔴 缺失字段：以下字段缺失，请后续补充：{字段列表}}
  · {如有 🟡 待补充字段：以下字段标注为"【待补充】"，建议完善：{字段列表}}
  · 如需更新字段，可随时说"帮我把 {节点编号} 的 {字段名} 改为 ..."
```

## 5. 异常处理原则

### 5.1 信息缺失类

| 异常场景 | 处理建议 |
| --- | --- |
| **节点编号未提供**（`missing_node_id`） | 向调用方（SOP-012 或用户）确认：「请提供节点编号，格式如 SG-JG 或 SG-015」 |
| **完成标准缺失且用户跳过**（`missing_criteria_skipped`） | 在实例中标注「【缺失】」，在回执中提醒用户后续补充。不阻断生成 |
| **阶段码无法匹配 L1 模板**（`unknown_stage_code`） | 回退到通用模板（仅 L0 基类字段）。在实例文档头部注明"未匹配到阶段专属模板，使用通用模板" |
| **用户对询问无回应**（`no_user_response`） | 🔴 字段标注「【缺失】」、🟡 字段标注「【待补充】」，不阻塞生成。在回执中列出待确认事项 |

### 5.2 信息质量类

| 异常场景 | 处理建议 |
| --- | --- |
| **用户提供的字段值与已有数据冲突**（字段值不一致） | 提示用户冲突内容，询问以哪个为准。不自动覆盖 |
| **时间字段格式异常**（`invalid_date_format`） | 尝试解析多种格式，失败则保留原值并标注「⚠ 需确认格式」 |
| **上游节点编号不存在**（`parent_not_found`） | 保留引用，标注「⚠ 上游节点待确认」。建议用户先确认全景节点树 |
| **用户提供的字段值过短或无意义**（如完成标准仅写了"完成"） | 提示用户该字段过于笼统，建议细化。用户坚持则保留原值 |

### 5.3 系统异常类

| 异常场景 | 处理建议 |
| --- | --- |
| **V4 模板文件无法读取**（`template_read_failed`） | 使用内置的 L0 最小模板（节点编号 + 名称 + 完成标准 + 状态流转）生成简化版实例。在文档头部注明"模板加载失败，使用简化模板" |
| **build_node_instance.py 执行失败**（`script_exec_failed`） | 保留已收集的结构化数据，向用户返回错误信息。用户可稍后重试或手动执行脚本 |
| **文件写入失败**（`file_write_failed`） | 检查目录权限，返回错误信息。保留生成内容 |
| **文件名冲突**（`filename_conflict`） | 检查目标路径是否已有同名文件。如有，询问用户是否覆盖：① 覆盖 ② 保留旧文件并追加版本后缀（如 `SJ-JG-景观设计-v2.md`） |
| **上游 SOP-012 传入数据不完整** | 不阻断。缺失字段按本 SOP 的字段级别规则处理（🔴 询问、🟡 标注、🟢 省略） |

### 5.4 异常处理总原则

1. **宁慢不错**：🔴 必有字段缺失时优先向用户确认，每轮不超过 3 个问题
2. **有据可查**：所有「【待补充】」「【缺失】」「⚠」标注保留在实例文档中，后续可追溯
3. **不替用户做判断**：字段值不确定时不强行推断（如不能根据节点名称猜测监理单位），而是询问用户或留空
4. **不阻断流程**：单个字段的缺失不阻断整个实例文档生成。优先产出可用的半成品，由用户后续补充

## 6. 建议补充内容（系统增强方向）

> 以下内容当前系统尚未完全实现，记录在此作为后续优化参考，不影响当前业务流执行。

### 6.1 L1 模板注册表

**问题描述**：当前 L1 模板（设计/成本/工程/通用）通过阶段码前缀硬编码匹配，新增阶段类型需改代码。

**改进方向**：

1. 建立模板注册表 JSON 文件：`{阶段码前缀: {模板路径, 额外字段列表, 默认值}}`
2. Agent 读取注册表做模板匹配，新增阶段类型只需编辑 JSON 配置

### 6.2 字段填充历史学习

**问题描述**：同一项目的多个节点往往共享部分字段值（如监理单位、责任部门），当前每次都要重新收集。

**改进方向**：

1. 在批量导入场景下（SOP-012 串联调用），Agent 记忆用户在第一个节点提供的字段值
2. 后续节点的同类字段优先使用已确认值，仅需用户确认"沿用"还是"修改"

### 6.3 节点实例质量自检

**问题描述**：生成的节点实例文档缺少自动质量检查。

**改进方向**：

1. 开发检查脚本：校验必填字段是否全部填充、时间字段格式是否一致、上游节点引用是否存在
2. 在 `build_node_instance.py` 生成文档后自动运行检查，输出质量报告
