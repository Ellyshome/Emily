## 2. 意图识别标准

### 2.1 触发此业务流的语义特征

当用户消息同时满足以下条件时，应判定为「任务管理」请求：

**必须条件（满足其一即可）**：
- 明确提及任务分派、工作安排、待办事项、任务创建
- 包含"安排XX做YY"、"让XX负责YY"、"指派XX去YY"等分派语句
- 用户说"帮我记个待办"、"把这个加到任务列表"、"添加一个待办事项"
- 用户说"提醒我..."、"设置提醒..."、"以后..."、"定期..."等涉及时效的长期要求（此时也可触发 SOP-007 长期记忆）
- 提及具体责任人 + 工作内容 + 时间要求的组合
- 包含"待办"、"任务"、"提醒"、"截止日期"、"deadline"、"安排"、"跟进"、"负责"等关键词

**否定条件（即使有上述关键词，也不应判定为此业务流）**：
- 用户在会议纪要中顺带提到待办事项 → 优先会议纪要
- 只是询问任务状态或进度 → 属于查询
- 没有明确责任人或截止时间的笼统想法 → 普通对话，可引导但不强制录入

### 2.2 示例对话

**应触发此业务流**：
> 「安排张三下周五之前完成科技城外墙检查报告，优先级高。」

> 「帮我记个待办：明天提醒李工提交月报。」

**不应触发此业务流**：
> 「张三那个任务做完了吗？」→ 查询  
> 「我们可能需要做一次全面检查」→ 笼统想法，无明确责任人/时间

## 3. 业务流描述

### 3.1 目标数据库表

| 表名 | 作用 | 关键字段 |
| --- | --- | --- |
| `tasks` | 任务主表 | `task_no`（任务编号）、`title`（标题）、`description`（描述）、`owner_id`（责任人）、`status`（状态）、`due_date`（截止日期）、`project_id`（关联项目） |

### 3.2 使用的系统工具 / API

| 工具名 | 功能 | 调用场景 |
| --- | --- | --- |
| `record_task` | 任务创建 | 核心工具 |
| `query_data` | 查询现有任务/项目 | 检查重复、推断项目 |
| `query_my_nodes` | 查询本人负责 / 参与的全景节点 | 确定任务归属节点时使用 |

### 3.3 处理流程

```
用户发起任务描述
    ↓
[意图判定] → 确认为任务管理
    ↓
[信息整理] 提取要素：
  ① 任务标题（title）[必有]
  ② 责任人（owner）[应有]
  ③ 截止日期（due_date）[如有]
  ④ 描述（description）[如有]
  ⑤ 优先级（priority）[可选]
  ⑥ 关联项目（project_id）[应有]
    ↓
[节点归属确认] → 按 §3.5 规则确定归属节点（node_id）
    ↓
[拟录入确认] → 展示拟录入单（含归属节点）
    ↓
[调用 record_task] → 写入 tasks 表（携带 node_id）
    ↓
[返回确认信息] → 任务编号 + 归属节点 + 简要回执
```

### 3.4 Agent 调用指引（L3 agent loop）

1. **项目 UUID 解析**：若用户提供项目名称但不知 UUID，**必须先调 `resolve_project`** 解析 project_id，禁止将项目名称直接填入 project_id 字段
2. **工具失败自纠**：调用 `record_task` 返回错误时，分析 tool_result 中的 error 信息，调整参数后重试
3. **信息不足**：缺少必须字段（如 title）时，调用 `ask_user` 工具向用户提问
4. **节点归属**：调用 `record_task` 前必须按 §3.5 确定 `node_id`，把归属节点一并填入调用参数；不得跳过该步骤直接落临时节点
5. **完成回复**：录入成功后给出最终文本回复，包含任务编号与归属节点名称

### 3.5 节点归属规则

任务必须尽量落到具体全景节点，**临时节点（UNASSIGNED）只是最后兜底，不是默认归属**。

判定优先级（自上而下，命中即止）：

| 顺序 | 候选来源 | 采用方式 |
| --- | --- | --- |
| 1 | **该任务所属的任务包节点**：`query_my_nodes` 返回的任务节点中，成果/工序与任务内容匹配的那个 | 直接采用，并在拟录入单中展示给用户确认 |
| 2 | 本人负责的节点（`role=responsible`，含未启动节点） | 能匹配上就采用为默认归属，展示给用户确认 |
| 3 | 本企业参与的全景节点（`role=participant` / 会话上下文授权节点） | 列出候选让用户选定后采用 |
| 4 | 以上均无匹配，或用户明确表示不知道该归哪个节点 | 留空 `node_id`，落临时节点待归类，并在回执中说明 |

对话口径要求：

- 不要问用户"节点编号是多少"，用户说不出来节点编号是正常的；应直接给出**节点名称**候选
- 归属节点必须与任务所属项目一致，跨项目节点不得采用
- 用户明确说不知道时不要反复追问，按第 3 档落临时节点，后续可由管理员改挂到具体节点

## 4. 输出成果要求

### 4.1 字段分级与约束

| 字段 | 级别 | 约束 |
| --- | --- | --- |
| **title** 任务标题 | 🔴 必有 | ≤ 100 字 |
| **owner** 责任人 | 🟡 应有 | 从语义提取姓名 |
| **due_date** 截止日期 | 🟢 如有 | YYYY-MM-DD |
| **description** 描述 | 🟢 如有 | 详细说明 |
| **project_id** 关联项目 | 🟡 应有 | 自动匹配 |
| **node_id** 归属节点 | 🟡 应有 | 按 §3.5 规则确定；确无归属时留空（落临时节点） |

---

## 5. 异常处理原则

| 异常场景 | 处理建议 |
| --- | --- |
| **无标题** | 询问任务简述 |
| **无责任人** | 询问或留空 |
| **重复任务检测** | 提示已有类似任务 |
| **节点归属不确定** | 按 §3.5 逐档匹配（先看任务包节点），用户仍不确定则落临时节点，不得自行编造 node_id |
