## 2. 意图识别标准

### 2.1 触发此业务流的语义特征

当用户消息同时满足以下条件时，应判定为「会议纪要录入」请求：

**必须条件（满足其一即可）**：
- 明确提及会议纪要、会议记录、开会记录、会议归档
- 提及具体会议信息（时间 + 主题 + 参会人）的组合描述
- 提到某场会议的「结论/决议/纪要/议定事项/待办」

**否定条件（即使有上述关键词，也不应判定为此业务流）**：
- 用户只是在询问「某会议有没有开过」「会议纪要放哪儿了」 → 属于查询，不是录入
- 用户在讨论会议内容，但没有发起记录意图 → 属于普通对话
- 用户发送的是文件附件（如 PDF/Word）并标注「这是一份会议纪要」→ 优先走文件归档流程（file_storage），再提取信息做会议录入

### 2.2 示例对话

**应触发此业务流**：
> 「下午3点的周例会，张总、李工、王经理参加了，主题是 A 项目进度协调，结论是下周三前完成基础验收，小李负责跟进。帮我录进去。」

> 「昨天 B 标段现场协调会的纪要，麻烦记录一下：参会的是甲方工程部、施工单位、监理，结论是 CFG 桩检测报告周五前提交。」

**不应触发此业务流**：
> 「上次那个会议纪要你有吗？」→ 查询，不是录入  
> 「明天几点开会？」→ 日程询问

## 3. 业务流描述

### 3.1 目标数据库表

| 表名 | 作用 | 关键字段 |
| --- | --- | --- |
| `meetings` | 会议纪要主表 | `meeting_no`（会议编号，唯一）、`title`（会议主题）、`summary`（会议纪要正文）、`attendees`（参会人 JSON 数组）、`meeting_type`（会议类型）、`meeting_date`（会议时间）、`location`（会议地点）、`host_id`（主持人ID）、`conclusion`（会议结论与决议）、`action_items`（待办事项 JSON 数组）、`project_id`（关联项目）、`status`（状态 0=草稿 1=已确认 2=已归档） |
| `projects` | 关联项目 | 通过 `project_id` 关联，用于定位会议归属的项目 |
| `users` | 关联人员 | `host_id` / `created_by` 关联用户表，用于标记主持人与创建人 |
| `files` | 关联附件 | `related_file_ids` 关联文件表，用于存储会议的原始纪要文件（如 Word/PDF） |

### 3.2 使用的系统工具 / API

| 工具名 | 功能 | 调用场景 |
| --- | --- | --- |
| `record_meeting` | 会议纪要录入 | 核心工具，将整理好的会议信息写入 `meetings` 表 |
| `record_event` | 关键事件记录（可选） | 如会议中产生了重大结论（如签证、设计变更、付款节点），应同步录入一条事件 |
| `record_task` | 待办任务拆分（可选） | 如会议结论包含明确的责任人 + 截止时间的待办，应拆分为任务 |

### 3.3 处理流程

```
用户发起会议描述
    ↓
[权限检查] → 读取本SOP第1章的"权限控制"字段，校验当前用户角色是否在允许列表中：
  · 允许角色为 `all`：所有已绑定用户可使用
  · 权限不足：终止流程，回复「此业务（SOP-001-REC）仅 {允许角色} 可使用，您当前无权限。如需申请，请联系系统管理员」
    ↓
[意图判定] → 确认为会议纪要录入
    ↓
[信息整理] 提取以下要素：
  ① 会议主题（title）[必有]
  ② 会议时间（meeting_date）[应有，若未提及则使用当前日期]
  ③ 会议类型（meeting_type）[应有，自动推断]
  ④ 参会人员（attendees）[应有，列表化]
  ⑤ 会议地点（location）[如有]
  ⑥ 主持人（host）[如有]
  ⑦ 纪要正文（summary）[必有]
  ⑧ 会议结论（conclusion）[如有，与 summary 分开]
  ⑨ 待办事项（action_items）[如有，逐条拆分]
  ⑩ 关联项目（project_id / project_name）[应有，自动匹配]
    ↓
[缺失确认] → 如有必有字段缺失，向用户确认补全
    ↓
[拟录入确认] → 以结构化形式向用户展示拟录入内容，等待确认
    ↓
    ↓
[调用 record_meeting] → 写入 meetings 表
    ↓
[联动处理（可选）] → 视情况：
  · 重大结论 → record_event
  · 明确待办 → record_task
  · 关联文件 → files 表
    ↓
[返回确认信息] → 会议编号 + 简要信息回执
```

## 4. 输出成果要求

### 4.1 字段分级与约束

| 字段 | 级别 | 约束 |
| --- | --- | --- |
| **title** 会议主题 | 🔴 必有 | 不得为空，应简洁明了（建议 ≤ 50 字），建议格式：「项目名 + 会议类型 + 主题」，如「A 项目 · 周例会 · 第 12 期」 |
| **meeting_date** 会议时间 | 🟡 应有 | ISO8601 格式（如 `2026-06-14T15:00:00+08:00`）。如用户未明确说明时间，使用当前日期，但需在回执中标注「时间未指定，以录入日期为准」 |
| **meeting_type** 会议类型 | 🟡 应有 | 枚举值：0=周例会 1=专题会 2=协调会 3=技术交底 4=验收会 5=其他。根据主题自动推断，不确定时设为 5（其他）并在 summary 中备注 |
| **summary** 会议纪要正文 | 🔴 必有 | 结构化描述，建议分段：① 会议背景 / 议题 → ② 讨论过程 → ③ 决议内容。纯文本，可换行，不使用 Markdown 语法 |
| **attendees** 参会人员 | 🟡 应有 | JSON 字符串数组，如 `["张总（甲方）", "李工（监理）", "王经理（施工）"]`。应包含角色标注（括号内），便于后续检索 |
| **location** 会议地点 | 🟢 如有 | 详细地址或会议室名称，如「项目部二楼会议室」「A 标段现场办公室」 |
| **host_id** 主持人 | 🟢 如有 | 对应 `users` 表的 id。如已知姓名但无系统 ID，填入 `attendee_names` 并在 summary 中注明「主持人：XXX」 |
| **conclusion** 会议结论与决议 | 🟡 应有 | 与 summary 分离的「结论段」，逐条列出决议事项，每条格式：「序号 + 决议内容 + 责任人（如有）」 |
| **action_items** 待办事项 | 🟢 如有 | JSON 数组，每条建议包含：`{title, owner, due_date, priority}`。如用户明确指定了责任人 + 截止时间，应同时调用 `record_task` 创建任务 |
| **project_id / project_name** 关联项目 | 🟡 应有 | 优先匹配已有项目；如新项目且系统中不存在，先创建项目或暂不关联（不填 `project_id`），并在 summary 中注明「项目待关联」 |
| **related_file_ids** 关联文件 | 🟢 如有 | 用户上传了原始纪要文件时，先归档文件并取得 file_id，填入此字段 |

### 4.2 格式要求

- **标题（title）**：禁止使用全大写、特殊符号（除中文标点和「·」）
- **纪要正文（summary）**：使用中文书面语，避免口语化和网络用语；避免出现 emoji
- **参会人员（attendees）**：每条不超过 20 字，角色标注清晰
- **会议结论（conclusion）**：使用「1. XXXX」「2. XXXX」编号格式
- **待办事项（action_items）**：JSON 格式，确保可被系统解析

### 4.3 回执格式

录入成功后，返回给用户的信息应包含：

```
📋 会议纪要已归档
──────────────
编号：MEET-YYYYMMDD-NNNN
项目：{项目名}
主题：{会议主题}
时间：{会议时间}
参会人：{姓名1、姓名2、姓名3...}
──────────────
[如有关联动，在此追加：]
  · 已同步录入事件：EVT-XXXXXXXX-NNNN
  · 已拆分为任务：TSK-XXXXXXXX-NNNN
```

## 5. 异常处理原则

### 5.1 信息缺失类

| 异常场景 | 处理建议 |
| --- | --- |
| **无会议主题**（title 为空） | 直接向用户询问：「请问这次会议的主题是什么？（例：A 项目周例会）」 |
| **无会议纪要正文**（summary 为空） | 提示：「请描述一下会议讨论的主要内容和结论，我会整理成纪要」 |
| **无参会人员**（attendees 为空） | 提示：「方便的话请告诉我参会人员，这对后续追溯很有帮助。如果确实记不清，可以回复『暂不填』」 |
| **无关联项目**（project_id 为空） | 自动尝试从会议主题或上下文推断项目名称；推断失败时询问用户，或不关联项目但在 summary 中标注「项目待指定」 |

### 5.2 信息质量类

| 异常场景 | 处理建议 |
| --- | --- |
| **主题过于笼统**（如 title = "开会"） | 引导用户补充：「会议主题太简略了，能否告诉我是哪个项目、讨论什么议题的会议？」 |
| **参会人只有姓没有名**（如 "张总" "李工"） | 可以接受，但建议在 summary 中补充一句「参会人：含甲方张总、监理李工等，全名待确认」 |
| **同一时段重复录入**（相同 project_id + 相近 meeting_date + 相同 title） | 提示：「系统检测到已有类似会议记录，是否需要更新？还是这是另一场会议？」 |

### 5.3 系统异常类

| 异常场景 | 处理建议 |
| --- | --- |
| **用户无权限使用此SOP流**（`permission_denied`） | 权限检查发生在流程最开头，读取本SOP第1章的"权限控制"字段后判定。若用户角色不在允许列表中，回复：「此业务（SOP-001-REC）仅 {允许角色} 可使用，您当前无权限。如需申请，请联系系统管理员」；**不进入后续任何流程步骤**，记录日志 |
| **写入数据库失败**（`meeting_create_failed`） | 向用户返回：「会议纪要暂时未能录入，请稍后再试。您的信息我已保留，稍后可以自动重试」；同时记录日志，通知管理员 |
| **用户取消录入** | 不写入数据库，返回「已取消」 |

### 5.4 异常处理总原则

1. **宁慢不错**：信息不完整时优先确认，不急于录入
3. **不替用户做判断**：会议类型、项目归属等不确定时，不强行推断，而是询问或留空标注
4. **权限前置检查**：权限检查必须是流程的**第一个步骤**，不允许先处理业务再检查权限；权限不足时直接终止，不暴露后续流程信息

## 6. 建议补充内容（系统增强方向）

> 以下内容当前系统尚未完全实现，记录在此作为后续优化参考，不影响当前业务流执行。

### 6.1 会议编号规则

当前由系统自动生成 `MEET-YYYYMMDD-NNNN`。建议：
- 同一项目的会议编号可增加项目代码前缀，如 `A-PROJ-MEET-20260614-001`
- 周例会可特殊编号：`A-PROJ-WEEKLY-12`，便于按周检索

### 6.2 会议类型自动推断规则

建议根据关键词自动匹配：

| 关键词 | 匹配类型 |
| --- | --- |
| 周例会 / 周会 / 周报 / 周检 | 0 周例会 |
| 专题会 / 研讨会 / 评审会 | 1 专题会 |
| 协调会 / 协调 / 现场会议 | 2 协调会 |
| 技术交底 / 交底 / 图纸会审 | 3 技术交底 |
| 验收 / 验收会 / 验收检查 | 4 验收会 |
| 其他 / 不匹配任何关键词 | 5 其他 |

### 6.3 联动事件/任务的自动判定

建议在会议录入后，自动扫描 `conclusion` 字段：
- 包含「签证」「设计变更」「索赔意向」「停工」「复工」等关键词 → 自动提示是否同步录入事件
- 包含「负责」「截止」「完成」「跟进」+ 时间/人员 → 自动提示是否拆分为任务

### 6.4 检索与归档建议

- 会议纪要录入后 30 天内，应鼓励用户补充原始纪要文件（Word/PDF）并关联
- 同一主题系列会议（如持续 3 次周例会讨论同一问题），建议添加 `related_meeting_ids` 关联字段（当前表结构尚未包含，可后续扩展）
