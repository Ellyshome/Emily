## 第0章 前置合规理念

### 0.1 成果上报合规链

本业务流遵循一条不可断开的合规性校验链：

```
成果上报 ──必须来自──▶ 已分配的任务 ──必须挂载于──▶ 执行中的全景节点
```

**核心原则：**

1. **成果必有其主**：员工产出的任何工作成果，必须对应一个已分配的计划任务（`plan_task_instances`）。无任务归属的成果上报视为不合规。

2. **任务必有其源**：任何已分配的计划任务，必须挂载于一个正在执行中的全景节点（`panorama_nodes`，状态为 `IN_PROGRESS`）。无节点归属的任务布置视为不合规。

3. **节点必已启用**：全景节点必须已通过审批、处于启用/执行中状态。未启用的节点上不得挂载任务。

### 0.2 不合规场景与引导策略

| 缺失环节 | 场景描述 | 系统行为 |
|----------|----------|----------|
| **无任务归属** | 用户直接上传成果，但未找到对应的已分配任务 | 引导用户联系有权限的主管/项目负责人，先通过 `record_plan_task` 布置任务，再提交成果 |
| **无节点归属** | 任务已分配，但未关联任何全景节点，或关联节点状态非 `IN_PROGRESS` | 引导用户联系建设单位负责人，先通过 `create_node` 创建并启动对应全景节点，再挂载任务 |
| **节点未启用** | 任务关联的节点处于 `未启用` 或 `CONDITIONS_NOT_MET` 状态 | 引导用户联系部门负责人审批启用该节点，节点进入 `IN_PROGRESS` 后方可挂载任务 |
| **节点申报中** | 任务关联的实体节点尚在定制申报阶段，暂无可用节点 | 自动归入虚拟节点 `VIRTUAL-NODE`，标记为异常数据，通知管理员待实体节点建立后二次分配 |

### 0.3 合规链校验时机

- **成果提交时**（`submit_plan_task`）：校验任务实例是否存在 → 校验任务是否关联有效节点 → 校验节点是否处于执行中状态
- **任务创建时**（`record_plan_task`）：校验是否指定了关联的全景节点 → 校验节点是否已启用

任一环节缺失，系统均应**阻断操作**并输出引导信息，而非静默放行。

### 0.4 完工确认报告的三场景处理策略

对于「完工确认报告」等特殊类型成果的上传，在合规链基础上采用三级路由：

```
上传完工确认报告
    │
    ├─ 场景A：有挂载节点 + 有任务归属
    │     → 正常入库，成果标记 is_acceptance_check=true
    │     → 节点管理员负责验收任务
    │
    ├─ 场景B：有任务归属但无对应节点
    │     → 引导用户提醒所属建设单位对应的部门负责人建立全景节点
    │     → 节点建立并启用后，任务方可挂载、成果方可提交
    │
    └─ 场景C：节点尚在定制申报中（无实体节点）
          → 统一归入「虚拟节点」（virtual_node），等待节点建立后二次分配
          → 虚拟节点中的数据视为异常数据，需管理员定期处理
```

**虚拟节点定义**：
- 虚拟节点是系统预留的特殊全景节点（固定编号 `VIRTUAL-NODE`），状态恒为 `IN_PROGRESS`
- 用于承接暂时无实体节点归属的任务与成果，作为临时容器
- 管理员需定期巡检虚拟节点中的数据，在实体节点建立后执行二次分配

## 第2章 意图识别

### 2.1 触发此业务流的语义特征

**必须条件**：
- 下达任务、布置工作、创建任务
- 周期性任务、日报、周报、月报、定期上报
- 指派任务、分派工作
- 提交任务成果、提交报告、完成任务
- 上交、报送、上传成果
- 查看我的任务、待办任务、查询任务状态

**否定条件**：
- 查询已录入事件（应触发 SOP-005-QRY）
- 录入会议纪要（应触发 SOP-001-REC）
- 临时事件上报（应触发 SOP-002-REC）

### 2.2 示例对话

**应触发此业务流**：
> 「请给张三布置一个任务：本周五前完成S4地块铺装材料进场验收」
> 「创建周报任务，每周五17:00前提交，由李四负责」
> 「我提交S4地块铺装任务的成果，已完成验收」
> 「查看我待提交的任务」
> 「设定一个循环任务：每月20日前提交工程月报」

**不应触发此业务流**：
> 「查一下上周的事件记录」→ SOP-005-QRY
> 「记录一下今天的会议纪要」→ SOP-001-REC

## 第3章 业务流描述

### 3.1 目标数据库表

- `plan_task_templates` — 任务模板
- `plan_task_instances` — 任务实例
- `plan_task_logs` — 状态变更日志
- `plan_task_deliverables` — 任务成果

### 3.2 使用的系统工具/API

| 工具名 | 用途 |
|--------|------|
| `record_plan_task` | 创建计划任务（一次性或循环模板） |
| `submit_plan_task` | 提交计划任务成果 |
| `query_plan_tasks` | 查询计划任务列表 |

### 3.3 处理流程

```
用户请求
    │
    ├─ 创建任务？
    │     ├─ 一次性任务 → record_plan_task (is_recurring=false) → 创建实例 → WAITING
    │     └─ 循环任务 → record_plan_task (is_recurring=true) → 创建模板 → 激活
    │
    ├─ 提交成果？
    │     └─ submit_plan_task → WAITING → SUBMITTED
    │
    ├─ 查询任务？
    │     └─ query_plan_tasks → 返回任务列表
    │
    └─ 不匹配 → 兜底处理
```

## 第5章 异常处理

### 缺失处理
- 缺少截止时间：询问用户补充截止日期或循环规则

### 质量处理
- 截止时间已过期：提醒用户确认，记录过期任务
- 反向下达（执行者向主管下达任务）：标记 ANOMALY_PENDING_REVIEW，通知上级复核

### 系统处理
- 数据库写入失败：重试一次，仍失败则告知用户
