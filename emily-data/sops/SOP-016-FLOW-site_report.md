# 一线完工上报 — 业务流服务手册

> **适用对象**：AI Agent（会话主循环 / SOP 能力）
> **允许用户角色**：参建执行（L2）及以上；L1 访客只能咨询，不进入上报
> **业务目的**：接收一线员工的完工上报（部位、工程量、照片），记录事件并按全景节点归属归档
> **所属框架**：资料审核 / 现场记录 → 一线完工上报（当前子项）
> **文档风格**：地产企业内业文件管理规范，简洁明确，可执行

对一线员工的完工上报做结构化登记：先问清部位、工程量、照片，再按全景节点归属记录事件；命中已有任务记入任务，未命中则暂存到“待归类事件”收容节点。

## 2. 意图识别标准

### 2.1 触发此业务流的语义特征

**必须条件（满足其一即可）**：
- 用户说“登记一下/报一下/上报：今天干了 X 平米/米/株”
- 用户说“完工了/做完了/铺装完成了”，并带部位或工程量
- 用户发送现场照片并说“报进度/报完工”

**否定条件（即使有上述关键词，也不应判定为此业务流）**：
- 只是询问进度、节点状态 → 走节点查询（`query_nodes` / `query_my_nodes`）
- 只是普通聊天或发图片不说明事项 → 普通对话
- 材料进场、日常巡检、质量整改 → 当前未开放（后续子项）
- 设计变更、签证、验收审批 → 走对应流程（后续子项）

> **与 SOP-002 的边界（强制）**：只要消息里同时出现“施工部位/工序 + 完成工程量”（例如“铺装今天干了10平米”“2#楼道路铺装完成10㎡”），无论用户说的是“登记”“记录”还是“报一下”，都走本 SOP-016，**不得走 SOP-002 的 `record_event`**。完工上报必须经过部位确认、照片校验、节点归属和成果进度；直接用 `record_event` 记一条事件会丢失这些环节。

### 2.2 示例对话

**应触发**：
> 「登记一下，铺装今天干了10平米。」

> 「2#、4#楼间道路花岗岩铺装完成了，报一下。」

**不应触发**：
> 「鸿瑞府景观条线哪些节点超时了？」→ 节点查询
> 「今天天气怎么样？」→ 普通对话

## 3. 业务流描述

### 3.1 目标数据源

| 数据源 | 作用 |
| --- | --- |
| 用户当前消息 | 上报原文、部位、工程量 |
| 当前消息附件 | 现场照片（已由附件链路落盘，manifest 提供 file_no/本地路径） |
| 全景节点/成果 | 归属判定与归档目标 |

本 SOP 只处理当前会话的上报与照片，不主动查询图纸、预算或资料库。

### 3.2 使用的系统工具 / API

| 工具名 | 功能 | 调用场景 |
| --- | --- | --- |
| `site_report` | 解析上报、判定节点归属、记录事件；`dry_run=true` 只出建议 | **核心工具**，确认前后分别调用 |
| `resolve_file_path` | 把照片 file_no 解析为本地路径 | 需要核对/发送照片时 |
| `query_my_nodes` | 查询当前用户负责/参与的节点 | 用户说不清部位时，用节点名辅助确认 |

> 上报内容必须走 `site_report`，由它完成“事件 + 节点归属”；不要直接用 `record_event` 绕过归属判定。

### 3.3 处理流程

```
用户上报完工信息（文字/照片）
    ↓
[权限] L2 及以上 → 否则说明权限不足
    ↓
[槽位解析] 部位/工序、工程量+单位、照片
    ↓
[追问] 缺部位或照片 → 一次只问一项，最多追问 2 次
    ↓
[归属建议] site_report(dry_run=true) → 命中任务/里程碑/待归类
    ↓
[确认] 向用户复述：部位、工程量、照片数、将记入哪个节点
    ↓
[记录] 用户确认后 site_report(dry_run=false) → 记录事件并确认
    ↓
[回报] 已登记 + 归档节点 + 验收提醒
```

### 3.4 上报字段约束（简单版）

**必填**：
- 施工部位/工序（如“2#、4#楼间道路花岗岩铺装”）；
- 完成工程量 + 单位（如 10㎡）；
- 照片至少 2 张：整体远景 + 局部近景。

**选填**：班组、材料、质量情况、备注。

**照片口径**：从“当前消息附件”清单取照片的 `file_no`，填入 `site_report.photo_file_nos`；不要猜文件名或路径。照片至少 2 张，分别对应整体远景/局部近景；数量不足时不进入记录。

> **附件是唯一可信来源**：当前消息附件清单里出现“图片：file_no=FIL-…；本地路径=…”就说明照片已落盘。
> **不要**再调用 `query_files` / `query_data` 去“确认文件是否存在”——图片走的是附件库，不是项目文件台账，查台账只会得到“暂无文件记录”。
> `site_report` 返回 `success=true` 且带 `photo_count` 时，表示照片已随本次上报归档；直接复述结果，不要再用文件台账否定附件清单。

**追问规则**：
- 用户说“铺装今天干了10平米” → 只问“哪一段？”；
- 用户答“2#、4#楼间道路” → 再要“两张照片：整体远景 + 局部近景”；
- 最多追问 2 次；仍缺部位/照片时，如实说明“信息不足，暂不能归档”。

### 3.5 节点归属规则

`site_report` 按三档处理：

- **档 A**：命中已有任务/成果 → 记入该节点，并给出成果名；
- **档 B**：命中里程碑 → 记入该里程碑下；
- **档 C**：未命中 → 记入“待归类事件（收容节点）”，等待认领/迁正。

**必须遵守**：

1. 不承诺“已归档到某个正式节点”，除非 `site_report` 返回了目标节点；
2. 档 C 明确告诉用户“暂存到待归类事件，后续由负责人认领”；
3. 照片数量不足时，不进入记录，先请用户补照片；
4. 不代替人工确认质量；照片只校验数量与“整体/局部”，质量写“需人工确认”；
5. 记录完成后提醒验收责任人/验收节点。

## 4. 输出成果要求

### 4.1 字段分级与约束

| 字段 | 级别 | 约束 |
| --- | --- | --- |
| 登记结果 | 🔴 必有 | 部位、工程量、照片数、归档节点 |
| 归属说明 | 🔴 必有 | 档 A/B/C 与目标节点名称 |
| 验收提醒 | 🔴 必有 | 提醒联系相关负责人验收 |
| 质量说明 | 🟡 应有 | 照片仅数量校验，质量需人工确认 |
| 缺失项说明 | 🟢 如有 | 缺部位/照片/项目时说明 |

### 4.2 回复格式

```
已登记：2#、4#楼间道路花岗岩铺装，10㎡，照片2张；
已归档到「大区景观工程」下的「花岗岩铺装」任务（档A）。
照片质量需人工确认；请及时联系吴根林验收。
```

档 C：

```
已登记：苗木补种20株，照片2张；
未命中已有任务，已暂存到「待归类事件（收容节点）」。
后续由负责人认领/归位；请补充对应节点或联系项目负责人。
```

## 5. 异常处理原则

| 异常场景 | 处理建议 |
| --- | --- |
| 权限不足（低于 L2） | 说明需参建执行（L2）及以上；L1 只做咨询 |
| 项目不明确 | 请用户说明项目名称；仍不明确则暂停，不猜项目 |
| 部位不明确 | 只追问一次“哪一段/哪个部位”；仍不明确则暂停 |
| 照片不足/未收到 | 请用户补“整体远景 + 局部近景”两张；不进入记录 |
| 未命中任务/里程碑 | 走档 C 收容节点，明确告知“待归类”，不冒充正式节点 |
| `site_report` 不可用 | 说明上报服务未就绪，请联系管理员；不绕过归属判定直接 record_event |
| 用户要求修改已登记内容 | 说明当前只做新增；修改请走对应节点/事件维护流程 |
