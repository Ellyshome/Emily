# SOP 文档起草规范 — 业务流服务手册

> **适用对象**：AI Agent（MasterAgent）及 SOP 文档起草人  
> **允许用户角色**：`admin`（仅管理员可发起"起草SOP"请求）  
> **业务目的**：指导 Agent 或起草人按统一规范编写业务流 SOP 文档，确保结构一致、语言统一、标准明确  
> **文档风格**：地产企业内业文件管理规范，简洁明确，可执行

## 2. 意图识别标准

### 2.1 触发此业务流的语义特征

**必须条件（满足其一即可）**：
- 用户要求"起草一份SOP"、"写一份业务流程文档"、"新增一个业务流规范"
- 用户要求"修改现有SOP的格式"、"按新规范调整SOP"
- Agent 收到系统层面的指令：为某一新增业务编写服务手册
- 讨论主题涉及"某某业务的标准流程是什么"，且当前无对应 SOP 文档

**否定条件（即使有上述关键词，也不应判定为此业务流）**：
- 「这份会议纪要帮我录一下」→ 属于记录类业务，走 REC 流，不是起草 SOP
- 「查询一下某某SOP」→ 属于查询检索，走 QRY 流
- 「帮我把这份SOP改成Word」→ 属于文件格式转换，走 FILE 流

### 2.2 示例对话

**应触发此业务流**：
> 「团队新增了设计变更审批流程，帮我写一份SOP」

> 「事件记录这个业务，按会议纪要的格式给我出一份服务手册」

**不应触发此业务流**：
> 「那份会议纪要你有吗」→ 查询已有文档，走QRY流  
> 「下午3点的周例会，帮我录进去」→ 执行会议纪要录入，走REC流

## 3. 业务流描述

### 3.1 目标数据库表（规范文件本身不写入数据库，以下为其**产出物**（即新起草的各业务SOP）可能涉及的表）

> **表存在性优先检查原则（🔴必须遵守）**：
> 起草新 SOP 时，必须按以下顺序确定目标数据库表：
> 1. **优先复用现有表**：先查阅 `teambrain_core/infrastructure/database/models.py` 中已定义的所有表，逐张评估是否能承载本业务的数据需求
>    - 如某张现有表的字段结构 **70% 以上覆盖** 本业务数据需求 → 建议复用该表，不足字段通过 `extra_info` 或扩展字段承载
>    - 如某张现有表的 **业务含义完全匹配**（如都是"事件记录"）但字段略有不同 → 优先考虑扩展现有表，而非新建表
> 2. **字段不匹配时考虑扩展**：现有表字段不足，可通过以下方式之一解决（按优先级）：
>    - 在现有表中新增可空字段（需同步修改 `models.py`）
>    - 使用通用扩展字段（如 `extra_info JSON` 字段承载非结构化数据）
>    - 使用关联表承载扩展信息
> 3. **确实无法复用才引导建表**：如现有表均不能承载本业务，且扩展成本过高（需改动的字段超过表字段总数的 50%），才在 SOP 的第3.1节中明确写出"需要新建表 {表名}，字段结构如下：..."

| 表名 | 作用 | 关键字段 |
| --- | --- | --- |
| 不直接写表 | 本SOP的产出物是Markdown文档，存于`SOPrepository/`目录 | 文件名、业务流编号、版本号 |
| `meetings`（示例） | 产出的REC类SOP可能引用此表 | **meeting_no**、title、summary、attendees、meeting_date |
| `events`（示例） | 产出的REC类SOP可能引用此表 | **event_no**、title、content、event_date |
| `tasks`（示例） | 产出的REC类SOP可能引用此表 | **task_no**、title、description、assignee、due_date |

### 3.2 使用的系统工具 / API

| 工具名 | 功能 | 调用场景 |
| --- | --- | --- |
| `文件写入`（系统基础能力） | 将起草完成的Markdown文档保存到`SOPrepository/`目录 | SOP起草完成并经自检通过后 |
| `IntentRegistry 加载`（系统启动组件） | 扫描SOPrepository目录，解析意图判定章节并注入路由Agent | 新SOP文档写入后系统重启或动态加载时 |
| `内容自检`（本SOP第4.1节 + 第5章质量自检清单） | 按章节模板和质量清单逐条核对起草质量 | 起草流程的"自检确认"步骤 |
| `inspect_existing_tables`（数据库表结构检查工具） | 读取 `teambrain_core/infrastructure/database/models.py`，列出所有已定义的表名、字段名、字段类型、主键/外键信息，辅助评估"哪些表可复用" | 起草流程的"目标数据库表确定"步骤，在"第3.1节 → 优先复用现有表"之前调用，获取当前数据库表全景 |
| `generate_table_schema`（表结构建议生成工具） | 当确认需要新建表时，根据业务需求描述生成建议的表结构：表名、字段名（建议使用蛇形命名）、字段类型、主键/外键设计、索引建议 | 在"确实无法复用才引导建表"场景下调用，输出结构化的建表建议供 SOP 第3.1节引用 |

### 3.3 处理流程

```
用户发起"起草某业务SOP"的请求 / 系统识别到某业务缺少SOP
    ↓
[权限检查] → 读取本SOP第1章的"权限控制"字段，校验当前用户角色是否在允许列表中：
  · 允许角色为 `admin`：仅管理员可使用
  · 允许角色为 `all`：所有已绑定用户可使用
  · 允许角色为 `project_owner`：仅项目负责人可使用
  · 允许角色为 `自定义角色`：按文档中明确的角色名匹配
  · 权限不足：终止流程，回复权限提示话术（见第5章异常处理）
    ↓
[业务范围确认] → ①确认业务名称 ②确认业务类型(REC/FILE/FLOW/QRY/SYS) ③确认业务核心目的
    ↓
[分配编号] → 在SOPrepository目录中查找当前最大序号，分配新的三位数序号（永不重复使用旧号）
    ↓
[确定文件名] → 参考业务类型缩写表：
    REC(记录/录入)、FILE(文件管理)、FLOW(流程审批)、QRY(查询检索)、SYS(系统维护)
    → 按格式命名：SOP-[新序号]-[业务类型缩写]-[业务名称蛇形].md
    ↓
[起草：固定头部] → 复制粘贴以下内容，替换变量：
  ① # {业务名称} — 业务流服务手册
  ② 适用对象 / 业务目的 / 文档风格
  ③ 分隔线
    ↓
[起草：第1章 · 业务流版本信息] → 填写业务流编号、版本v1.0、参与编辑人、最后编辑人、最后编辑时间、关联系统模块
    ↓
[起草：第2章 · 意图识别标准] → 定义：
  ① 触发关键词（3-5条）
  ② 否定条件（2-3条，必须给出替代去向）
  ③ 示例对话（正例2条+、反例2条+）
    ↓
[起草：第3章 · 业务流描述] → 描述：
  ① 目标数据库表（🔴必须经过以下"表存在性检查流程"后确定）：
      ├─ 步骤1：调用 `inspect_existing_tables` 工具，获取当前 `models.py` 中所有已定义表的全景信息
      ├─ 步骤2：逐张评估现有表是否能承载本业务的数据需求（按本SOP第3.1节的"优先复用原则"）
      ├─ 步骤3：如找到 70% 以上字段覆盖的表 → 标记为"建议复用表"，列出可用字段和需补充的字段
      ├─ 步骤4：如业务含义匹配但字段不足 → 标记为"建议扩展表"，列出需要新增的字段名和类型
      ├─ 步骤5：如以上均不可行 → 调用 `generate_table_schema` 工具生成建议的新表结构
      └─ 最终在第3.1节中写明：「复用表 {表名}」或「建议扩展表 {表名}，新增字段：{字段列表}」或「需新建表 {表名}，字段结构：{字段列表}」
  ② 使用的系统工具/API（查tools/目录确认Tool定义）
  ③ 处理流程（先判定→再整理→再确认→最后写入）
    ↓
[起草：第4章 · 输出成果要求] → 定义：
  ① 字段分级与约束（必有🔴 / 应有🟡 / 如有🟢，每级至少1个字段，必有字段不超3个）
  ② 格式要求（中文书面语、分段原则等）
  ③ 回执格式（提供可复制模板）
    ↓
[起草：第5章 · 异常处理原则] → 覆盖：
  ① 信息缺失类（每个🔴字段对应一条）
  ② 信息质量类（主题笼统/时间不合理/内容残缺等）
  ③ 系统异常类（复制系统通用话术模板，替换业务名称和工具名）
  ④ 异常处理总原则（宁慢不错 / 有据可查 / 不替用户做判断）
    ↓
[起草：第6章 · 建议补充内容（可选）] → 如有系统增强建议则编写；无则整章省略
    ↓
[起草：第7章 · 业务流变更记录] → 初版记录：v1.0 / 日期 / 编辑人 / "初版发布，覆盖XX核心流程"
    ↓
[自检（关键步骤，不可跳过）] → 对照以下清单逐条核对：
  ① 结构完整性：是否包含全部必需章节（至少6章，第6章可省略）
  ② 意图判定明确：能否用一句话回答"什么样的消息走这个业务流"
  ③ 字段分级合理：必有/应有/如有三级是否清晰，每级至少1个字段
  ④ 数据库表映射正确（🔴核心检查）：
     ├─ 是否调用过 `inspect_existing_tables` 工具获取了表全景？
     ├─ 是否评估过现有表的复用可能性（70%字段覆盖标准）？
     ├─ 如果选择复用/扩展现有表：表名和字段名是否与 `models.py` 一致？
     └─ 如果选择新建表：是否明确列出了完整的字段结构、主键/外键设计？
  ⑤ 工具映射正确：工具名是否与tools/目录下定义一致
  ⑥ 异常覆盖全面：关键异常场景是否都有处理建议（至少4+）
  ⑦ 语言简洁明确：是否有冗余描述、口语化表达
  ⑧ 版本记录完整：第1章版本信息 + 第7章变更记录是否完整
    ↓
[确认与写入] → 自检通过后，将文档保存至 SOPrepository/ 目录；若自检不通过，返回修改对应章节
    ↓
[通知系统加载] → 提示：新SOP已起草完成，系统重启或IntentRegistry动态加载后，路由Agent将获得此业务的意图判定能力
    ↓
[返回确认信息] → SOP编号 + 文件路径 + 一句话说明此SOP覆盖的业务范围
```

## 4. 输出成果要求

### 4.1 字段分级与约束

| 字段 | 级别 | 约束 |
| --- | --- | --- |
| **业务流编号**（对应SOP-XXX-TYPE） | 🔴 必有 | 格式：`SOP-[三位数序号]-[业务类型缩写]`，序号全局递增永不重复，业务类型必须是 REC/FILE/FLOW/QRY/SYS 之一 |
| **权限控制**（allow_roles） | 🔴 必有 | 标记允许使用该 SOP 流的用户角色，必须从枚举中取值：`all`（所有人，默认）/ `admin`（仅管理员）/ `project_owner`（仅项目负责人）/ `自定义角色`（写清具体角色名，逗号分隔多角色）；缺失时 IntentRegistry 默认按 `all` 处理，但 Agent 应在起草时强制填写 |
| **第2章 · 意图识别标准** | 🔴 必有 | 必须包含"触发条件"+"否定条件"+"示例对话"三个子小节，每部分都有具体内容；否定条件必须给出替代去向 |
| **第4章 · 字段分级与约束** | 🔴 必有 | 必须有"必有🔴/应有🟡/如有🟢"三级字段定义，每级至少1个字段，必有字段不超过3个；字段名和表名必须与models.py核对一致 |
| **文件名** | 🔴 必有 | 格式严格遵循`SOP-[三位数序号]-[业务类型缩写]-[名称蛇形].md`，存放于`SOPrepository/`目录 |
| **第3章 · 业务流描述** | 🟡 应有 | 必须列出目标数据库表（含关键字段标注）和使用的系统工具（含调用场景），处理流程必须遵循"先判定→再整理→再确认→最后写入"原则；第3.1节表确定过程必须经过 inspect_existing_tables 工具检查，不可凭空设计表结构 |
| **目标表结构与复用决策**（table_decision） | 🔴 必有 | SOP 第3.1节必须明确写出表决策结论：格式为「复用表 {表名} / 建议扩展表 {表名}，新增字段：{字段列表} / 需新建表 {表名}，字段结构：{完整字段列表}」；同时必须简要说明"为什么不选择其他现有表"（1-2句话），便于后续维护理解决策依据 |
| **第5章 · 异常处理原则** | 🟡 应有 | 必须覆盖信息缺失类、信息质量类、系统异常类三类场景 |
| **第7章 · 业务流变更记录** | 🟡 应有 | 初版至少1条记录（v1.0），后续每次修改文档必须新增一条记录并更新第1章的版本号和最后编辑信息 |
| **文档语言与格式** | 🟡 应有 | 中文书面语；emoji仅限级别符号使用（🔴🟡🟢）；长文本分段每段不超过150字；列表编号风格统一 |
| **第6章 · 建议补充内容** | 🟢 如有 | 有系统增强建议则记录，无则整章省略；章节开头必须添加声明"以下内容当前系统尚未完全实现…" |
| **关联系统模块信息** | 🟢 如有 | 第1章末尾可补充当前关联的插件/类名/Tool名，便于后续维护定位 |

### 4.2 格式要求

- **章节结构**：严格按"7 + 2 固定模板"组织章节顺序与编号，不得缺省必需章节（第6章除外）
- **表格格式**：版本信息表、字段分级表、异常处理表等所有表格的列数和列名与本规范模板一致
- **流程表达**：第3.3节处理流程使用"文本流程图"格式，方括号`[步骤名]`标记步骤，4个空格+`↓`连接步骤
- **字段级别符号**：统一使用 🔴 🟡 🟢 三个 emoji 标注字段级别，不允许使用其他符号或文字级别
- **否定条件格式**：第2.1节否定条件后必须用 `→` 标注替代去向，不允许只写"不是这个"
- **示例对话格式**：第2.2节正面示例使用引用格式 `> 「...」`，反例后必须用 `→` 标注原因

## 5. 异常处理原则

### 5.1 信息缺失类

| 异常场景 | 处理建议 |
| --- | --- |
| **业务名称不明确**（`business_name`） | 向用户确认：「请问这份SOP对应的具体业务名称是什么？例如"会议纪要录入"、"事件记录"」 |
| **业务类型不明确**（`business_type`） | 对照本规范第1.2节业务类型缩写表，向用户确认该业务属于 REC/FILE/FLOW/QRY/SYS 中的哪一类 |
| **缺少意图触发关键词**（第2.1节必须条件为空） | 向起草人/业务负责人询问："用户说什么样的话时，应该走这个业务流？请提供3-5个关键词或表达方式" |
| **字段分级表为空**（第4.1节无字段定义） | 暂停起草，向业务负责人确认：该业务的产出物需要记录哪些关键信息？哪些信息是不可缺省的？ |

### 5.2 信息质量类

| 异常场景 | 处理建议 |
| --- | --- |
| **业务流编号与文件名不一致**（第1章业务流编号 ≠ 文件名前缀） | 自动校验并修正，确保第1章的业务流编号 = `SOP-` + 文件名中的三位数序号 + `-` + 业务类型缩写 |
| **否定条件未给出替代去向**（第2.1节否定条件只有"不是"，没有说明应走什么流程） | 补充说明：每一条否定条件后必须用 `→` 标注替代流程（如"属于查询，走QRY流"、"属于文件管理，走FILE流"） |
| **字段级别自相矛盾**（同一字段在不同上下文被标注为不同级别） | 重新梳理字段重要性，统一为一个级别；原则上必有字段不超过3个 |
| **数据库表/字段与models.py不一致**（第3.1节引用了不存在的表或字段） | 查阅 `teambrain_core/infrastructure/database/models.py`，交叉核对表名和字段名后修正；如业务涉及的表不存在，应先确认是否需扩展数据模型再继续起草 |
| **未经过表存在性检查直接写表**（第3.1节直接列出表名，但未说明是否调用过 inspect_existing_tables） | 调用 `inspect_existing_tables` 工具获取当前表全景，重新评估复用/扩展/新建三选一，在第3.1节中补充决策过程和结论；不可"直接认为需要建新表"，必须先排除复用可能性 |
| **表复用评估标准不明确**（第3.1节写"复用表X"但未说明字段覆盖率、为什么选择这张表而非其他表） | 在第3.1节补充说明：① 评估了哪些表？② 每张表的字段覆盖率约为多少%？③ 为什么最终选择表X（如"业务含义最匹配""字段覆盖度最高"）？补充说明 1-2 句话即可，不需要长篇分析 |
| **处理流程跳过"确认前置"**（流程中没有"拟录入确认"或类似确认步骤） | 在写入操作前插入"拟写入内容结构化展示 + 等待用户确认"的中间步骤；除非业务极其简单明确，否则不可省略确认 |

### 5.3 系统异常类

| 异常场景 | 处理建议 |
| --- | --- |
| **用户无权限使用此SOP流**（`permission_denied`） | 权限检查发生在流程最开头，读取本SOP第1章的"权限控制"字段后判定。若用户角色不在允许列表中，回复：「此业务（{业务流编号}）仅 {允许角色} 可使用，您当前无权限。如需申请，请联系系统管理员」；**不进入后续任何流程步骤**，记录日志 |
| **文件写入失败**（`sop_write_failed`） | 向用户/管理员返回：「SOP文档暂时未能写入`SOPrepository/`目录，请检查目录权限或磁盘空间。您起草的内容我已保留，稍后可以自动重试」；同时记录日志 |
| **文件重名冲突**（`sop_filename_conflict`） | 重新分配序号：扫描目录找出当前最大序号，取最大序号+1；**绝不覆盖已有文件**，绝不重复使用已分配过的序号 |
| **IntentRegistry 解析失败**（系统重启后无法解析某SOP的第2章） | 检查第2章意图识别标准的结构是否符合本规范模板：是否有"2.1 触发此业务流的语义特征"、是否有"必须条件"和"否定条件"的小节标题、是否有"2.2 示例对话"；如缺失则按模板补齐 |
| **需新建表但 models.py 尚未更新**（SOP 第3.1节写"需新建表X"，但 `models.py` 中不存在该表定义） | 向起草人提示：「当前 SOP 需要的数据表 {表名} 在 `models.py` 中尚未定义。请先完成以下步骤后再继续：① 在 `teambrain_core/infrastructure/database/models.py` 中新增表类定义（含完整字段和主键外键）；② 执行数据库迁移（如 alembic）使表实际落地；③ 在 SOP 第3.1节中补充「已创建表」的确认标记（如在表名后加注「✓已创建」）」。**在表落地前，不可将该 SOP 标记为"可执行"**，应在第3.1节头部加注「⚠ 待建表」标记 |
| **建议扩展表但未提交扩展方案**（SOP 第3.1节写"建议扩展表X，新增字段Y"，但 `models.py` 中尚未新增这些字段） | 同上处理：在 `models.py` 中新增字段并完成迁移后，在 SOP 第3.1节表名后加注「✓已扩展」；表扩展完成前保持「⚠ 待扩展」标记 |
| **用户取消起草** | 不写入文件，返回「已取消」 |

### 5.4 异常处理总原则

1. **宁慢不错**：信息不完整或有歧义时优先向业务负责人确认，不急于起草发布
2. **有据可查**：所有"坚持按当前版本发布"的情况，必须在第7章变更记录中注明"版本X.Y为临时版，存在XX待确认事项"，留下可追溯记录
3. **不替业务做判断**：业务类型归属、字段级别定义、否定条件范围等不确定时，不强行推断，而是向业务负责人询问或留空标注"待确认"
4. **权限前置检查**：权限检查必须是流程的**第一个步骤**，不允许先处理业务再检查权限；权限不足时直接终止，不暴露后续流程信息

## 6. 建议补充内容（系统增强方向）

> 以下内容当前系统尚未完全实现，记录在此作为后续优化参考，不影响当前业务流执行。

### 6.1 SOP 结构化解析与自动注入（高优先级）

**问题描述**：当前SOP文件为纯Markdown，意图识别标准（第2章）需要人工阅读后手动告知Agent，或由IntentRegistry通过文本解析提取。解析的鲁棒性依赖SOP是否严格遵循本规范的章节标题格式。

**改进方向**：
1. 在第2章定义一套更结构化的标记格式（如使用HTML注释或特定标记块），便于机器解析；
2. IntentRegistry 增加 SOP 内容解析器，在系统启动/动态加载时自动提取每个 SOP 的：
   - **业务标识**（业务流编号）
   - **权限控制**（allow_roles，从第1章的"权限控制"行解析）
   - **触发关键词**（从第2.1节提取）
   - **否定关键词**（从第2.1节提取）
   - **示例对话**（从第2.2节提取）
3. 解析结果注入 MasterAgent 的 system prompt，使 Agent 在处理用户消息时能基于所有 SOP 的意图规则 + 权限规则做路由判定；
4. **关键设计**：IntentRegistry 在匹配到意图后，**先返回两条信息**给 Agent：(a) 应进入哪个 SOP 流；(b) 当前用户角色是否有权限进入该 SOP 流**，确保 Agent 在执行前做权限校验。

### 6.2 SOP 起草辅助工具（中优先级）

**问题描述**：当前起草SOP依赖人工从本规范的"快速模板"（原第13章）复制粘贴，缺少自动化辅助。

**改进方向**：
1. 开发一个CLI工具或Agent Tool：`create_sop_template --name "事件记录" --type REC`，自动生成符合本规范的SOP骨架文件；
2. 工具自动分配序号（扫描目录取最大值+1）、自动填充版本信息、自动生成文件名；
3. 工具在生成骨架后，通过多轮对话向起草人询问业务细节，逐步填充第2-5章内容。

### 6.3 SOP 质量自检自动化（中优先级）

**问题描述**：第3.3节流程中的"自检"步骤依赖人工逐项核对，容易遗漏。

**改进方向**：
1. 开发SOP质量检查脚本：检查章节是否完整、必填表格是否有内容、业务流编号与文件名是否一致、第2章是否同时有正例和反例等；
2. 脚本输出一份自检报告，标注"通过/不通过"项，方便起草人快速定位需要修正的章节。

## 附3：Agent 执行所有SOP时的通用操作约束

### 工具调用原则

1. **一次只做一件事**：每次调用工具只执行一个明确动作，不要在一个工具调用中混合多项录入
2. **先确认后写入**：写入类工具（record_\*）在调用前，应向用户展示拟写入内容的结构化摘要，并等待用户明确确认
3. **不重复调用**：相同参数不要在短时间内反复调用同一工具，避免数据库重复写入

### 对话风格

1. **简洁直接**：提问不超过3个问题一次，问题过多时分批询问
2. **结构化展示**：展示拟录入内容时使用表格或编号列表，不使用大段自然语言
3. **不承诺系统能力之外的事**：如用户要求"生成一份Word版纪要"而系统暂无此能力，应如实告知
4. **避免技术术语**：与用户对话时使用业务语言（"会议编号""项目名称"），不说"meeting_no""project_id"等技术字段名

### 信息安全

1. **不记录敏感信息**：用户提供的身份证号、手机号、合同金额等敏感信息，除非业务必需（如人员登记），否则不录入数据库
2. **不推断隐私信息**：不根据参会人姓名、公司等信息推断其职务、联系方式等未明确提供的信息
3. **不向无关人员透露**：不在对话中泄露其他用户或其他项目的信息
