## 2. 系统组织框架：全生命周期节点图

项目运作以**全生命周期节点图**为锚点进行组织：

- 项目按阶段拆分为一系列**节点**（如：方案设计、施工图、施工准备、主体施工、竣工验收等）
- 每个节点有独立的：参与者清单、协作文件库、时限计划、条件需求、成果要求
- 节点之间通过条件需求与产出成果形成依赖链，推动项目流转

### 组织架构模型：公司-人员-节点 三级绑定

```
公司实体
  └─ 人员（每个用户绑定所属公司）
       └─ 参与节点（按公司为分组加入节点任务小组）
```

- **人绑定公司**：每个系统用户必须归属一个公司实体（建设单位、设计单位、总包、分包、监理、供应商等）
- **节点分小组**：每个节点由多家公司的人员共同参与，形成该节点的**任务小组**
- **节点设管理者**：每个节点指定一名或多名管理者（通常是建设单位项目经理或总监理工程师），负责该节点的权限审批与进度把控

### 节点权限模型

**权限以节点为边界进行管控**：

1. **节点可见性**：属于某节点任务小组的成员，才能查看该节点的内容
2. **节点公共文件**：被标记为「节点相关」的文件，该节点所有成员都可见
3. **公司级共享**：同一公司在同一节点的成员，默认共享该公司上传的文件
4. **管理者权限**：节点管理者拥有该节点的全操作权限，可增减成员、审批文件发布

## 3. 会话处理机制：Session + WorkItem 主线

与上述节点图（项目级组织框架）不同，即时消息处理采用独立的 Session 主线架构：

```
用户消息
  ↓
SessionAgent（每会话大脑）
  ├─ 快速通道：问候/感谢/告别 → 直接回复（无 LLM）
  ├─ LLM 意图识别 → SOP 匹配
  └─ 单 SOP / 复合 SOP / 未命中回退 → 创建 WorkItem
  ↓
PipelineBUS（4 节点执行总线）
  ├─ node1: 知识注入（SOP/工具/RAG）
  ├─ node2: 计划生成
  ├─ node3: 工具执行
  └─ node4: 成果总结
  ↓
回复用户
```

- **SessionAgent**：维护每个会话的上下文、用户记忆、权限快照。决定"这条消息要做什么"
- **WorkItem**：单次任务的完整记录，在 4 节点 PipelineBUS 中流转（CREATED → PLANNING → EXECUTING → DONE）
- **PipelineBUS**：声明式 Hook 机制（ALLOW/WARN/BLOCK 三态），支持鉴权、风险、日志等横切关注点

节点图是**组织框架**（管"项目结构是什么"），Session+WorkItem 是**执行机制**（管"每次对话怎么处理"），两者在不同层次协作。
