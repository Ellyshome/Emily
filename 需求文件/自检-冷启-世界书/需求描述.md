# 自检模块需求

## 一、模块定位
- 项目需要对自己的整体状态有感知，如冷启动、管理员要求
- 它是个**独立且固定的脚本**，无入参，输出结构化 JSON
- 固定在**冷启动时被调用一次**，也可由管理员手动触发
- **开发阶段原则**：精简、快速、满足基础需求即可

---

## 二、交付文件清单

本模块共交付 **3 个文件**：

| 序号 | 文件路径 | 文件类型 | 说明 |
|------|----------|----------|------|
| 1 | `scripts/self_check.py` | Python 脚本 | 自检模块：采集核心数据，输出结构化 JSON |
| 2 | `scripts/cold_start.py` | Python 脚本 | 冷启动模块：调用自检、发邮件、生成带数据的 prompt 上下文 |
| 3 | `emily-data/prompts/world_book.md` | Markdown 文档 | 世界书：系统核心概念与架构说明，作为 Prompt 模板 |

## 三、核心功能：自检数据采集

### 3.1 用户统计
| 字段 | 说明 |
|------|------|
| `user_count` | 总用户数（未删除） |
| `admin_count` | 管理员数 |

### 3.2 项目统计
| 字段 | 说明 |
|------|------|
| `project_count` | 项目总数（未删除） |

### 3.3 业务量统计
| 字段 | 说明 |
|------|------|
| `event_count` | 事件总数 |
| `task_count` | 任务总数 |
| `meeting_count` | 会议总数 |
| `file_count` | 文件总数 |

### 3.4 RAG 知识库存量

**数据源**：本地 SQLite 数据库 `data/knowledge_base/kb.db`（与 MaxKB 容器的 PostgreSQL 无关，是 Emily 项目自维护的知识库索引）。

数据库包含两张核心表：

| 表名 | 用途 | 关键字段 |
|------|------|----------|
| `knowledge_bases` | 知识库元信息 | `kb_name`, `doc_count`, `chunk_count`, `embedding_provider_id` |
| `kb_documents` | 文档明细 | `doc_name`, `file_type`, `file_size`, `chunk_count`, `media_count` |

**采集逻辑**：
- `kb_total_docs` = `SELECT SUM(doc_count) FROM knowledge_bases`
- `kb_total_chunks` = `SELECT SUM(chunk_count) FROM knowledge_bases`
- `kb_index_status` = 判定逻辑：① `kb.db` 文件存在 → 正常；② 文件存在但最后修改时间超过配置阈值（如 7 天）且 `doc_count = 0` → 需重建；③ 文件不存在 → 需重建

| 字段 | 说明 |
|------|------|
| `kb_total_docs` | 知识库文档总数 |
| `kb_total_chunks` | 知识库分块总数 |
| `kb_index_status` | 索引状态（normal / needs_rebuild / unavailable） |

## 四、输出格式

```json
{
  "check_time": "2026-07-02T10:30:00+08:00",
  "check_duration_ms": 500,
  "status": "ok",  // ok / warning / error
  "users": {
    "total": 15,
    "admins": 3
  },
  "projects": {
    "total": 2
  },
  "business": {
    "events": 45,
    "tasks": 120,
    "meetings": 18,
    "files": 89
  },
  "knowledge_base": {
    "total_docs": 156,
    "total_chunks": 892,
    "index_status": "normal"
  },
  "warnings": [],
  "error_message": null  // 仅 status=error 时有值
}
```

### 状态判定
- **error**：脚本自身执行异常（如数据库连接失败）导致全部或大部分数据无法采集。`error_message` 记录异常原因
- **warning**：数据采集完成，但 `warnings.length > 0` 或 `index_status != "normal"`（部分数据异常但不影响整体可用性）
- **ok**：一切正常

## 五、冷启动模块

`cold_start.py` 封装冷启动流程：串联自检 → 发送邮件 → 生成带数据的 prompt 上下文。

> **注**：本次任务仅负责生成该脚本文件本身。脚本如何被触发执行（容器 entrypoint / FastAPI lifespan / 管理员 API 调用等）不在本次任务考虑范围内。

### 5.1 工作流程
```
cold_start.py 被调用
  ├─ 导入并调用 self_check.py → 获取自检 JSON 数据
  ├─ 调用邮件模块发送报告给管理员
  └─ 读取 world_book.md → 注入自检数据 → 返回完整的 prompt 上下文文本
```

## 六、世界书

作为 Prompt 模板文件 `emily-data/prompts/world_book.md`

### 6.1 系统核心定位
Emily 是一个**团队协作公共 AI 大脑**，专为地产开发类工程协作搭建。系统以**全生命周期节点图**为核心框架，围绕节点组织人员、权限、文件与协作。

### 6.2 核心组织框架：全生命周期节点图

项目运作以**全生命周期节点图**为锚点进行组织：
- 项目按阶段拆分为一系列**节点**（如：方案设计、施工图、施工准备、主体施工、竣工验收等）
- 每个节点有独立的：参与者清单、协作文件库、时限计划、条件需求、成果要求
- 节点之间通过条件需求与产出成果形成依赖链，推动项目流转

### 6.3 组织架构模型：公司-人员-节点 三级绑定

```
公司实体
  └─ 人员（每个用户绑定所属公司）
       └─ 参与节点（按公司为分组加入节点任务小组）
```

- **人绑定公司**：每个系统用户必须归属一个公司实体（建设单位、设计单位、总包、分包、监理、供应商等）
- **节点分小组**：每个节点由多家公司的人员共同参与，形成该节点的**任务小组**
- **节点设管理者**：每个节点指定一名或多名管理者（通常是建设单位项目经理或总监理工程师），负责该节点的权限审批与进度把控

### 6.4 节点权限模型

**权限以节点为边界进行管控**：

1. **节点可见性**：属于某节点任务小组的成员，才能查看该节点的内容
2. **节点公共文件**：被标记为「节点相关」的文件，该节点所有成员都可见
3. **公司级共享**：同一公司在同一节点的成员，默认共享该公司上传的文件
4. **管理者权限**：节点管理者拥有该节点的全操作权限，可增减成员、审批文件发布

**文件权限示例**：
```
文件标记为「节点A-公共」→ 节点A的所有成员（甲乙丙丁各方）都可见
文件标记为「节点A-仅甲方」→ 仅建设单位在节点A的成员可见
文件标记为「全项目公开」→ 所有节点所有成员可见
```

### 6.5 核心能力模块

| 能力模块 | 功能说明 |
|---------|----------|
| **节点管理** | 全生命周期节点创建、状态流转、依赖维护 |
| **任务小组** | 按节点+公司分组管理参与人员 |
| **权限控制** | 以节点为锚点的三级权限体系（节点级/公司级/个人级） |
| **文件协作** | 节点公共文件库、分级可见性控制 |
| **事件记录** | 节点内质量/安全/进度/决策事件记录 |
| **任务管理** | 节点内任务分配、跟进、闭环 |
| **会议归档** | 节点会议纪要、行动项跟踪 |
| **知识库** | 项目资料的语义化检索与知识沉淀 |

### 6.6 会话处理机制：Session + WorkItem 主线

与上述节点图（项目级组织框架）不同，Emily 的**即时消息处理**采用独立的 Session 主线架构：

```
用户消息
  ↓
SessionAgent（每会话大脑）
  ├─ 快速通道：问候/感谢/告别 → 直接回复（无 LLM）
  ├─ LLM 意图识别 → SOP 匹配
  └─ 单 SOP / 复合 SOP / 未命中回退 → 创建 WorkItem
  ↓
PipelineBUS（4 节点执行总线）
  ├─ node1: 知识注入（SOP/工具/RAG）
  ├─ node2: 计划生成
  ├─ node3: 工具执行
  └─ node4: 成果总结
  ↓
回复用户
```

- **SessionAgent**：维护每个会话的上下文、用户记忆、权限快照。决定"这条消息要做什么"
- **WorkItem**：单次任务的完整记录，在 4 节点 PipelineBUS 中流转（CREATED → PLANNING → EXECUTING → DONE）
- **PipelineBUS**：声明式 Hook 机制（ALLOW/WARN/BLOCK 三态），支持鉴权、风险、日志等横切关注点

节点图是**组织框架**（管"项目结构是什么"），Session+WorkItem 是**执行机制**（管"每次对话怎么处理"），两者在不同层次协作。

### 6.7 动态注入自检数据

冷启动时，将自检数据的关键指标注入世界书，形成**带数据的自我认知**：

```
【系统状态】{日期}
- 服务用户：{users.total}人
- 在管项目：{projects.total}个
- 知识库文档：{knowledge_base.total_docs}份
- 整体状态：{status}

AI 助手须知：你是 Emily 团队协作大脑的一部分，以上是当前系统的真实运行数据。
Emily 有两层架构：① 组织层——以全生命周期节点为框架，按公司分组组织人员参与各节点，
文件权限与节点成员身份绑定；② 执行层——通过 Session+WorkItem 消息处理主线
处理每次对话（意图识别 → SOP 匹配 → 4 节点 PipelineBUS 执行 → 回复）。
你的回复应基于此架构理解，不得虚构或夸大系统能力范围。
```

## 七、技术实现要求

### 7.1 `scripts/self_check.py` 接口要求
- 提供入口函数：`SelfCheck.run()` → 返回 JSON 字典
- 任何查询失败 → 对应字段设为 `null`，加入 `warnings` 数组
- 脚本自身级异常（如 DB 连接失败）→ `status = "error"`，填写 `error_message`
- 脚本**永不崩溃**，捕获所有异常
- 目标执行时间：≤ 3 秒（含跨数据库查询）

### 7.2 `scripts/cold_start.py` 接口要求
- 提供入口函数：`ColdStart.run()` → 返回字符串（完整的系统 prompt 上下文文本）
- 内部调用 `self_check.py` 获取自检数据
- 调用邮件模块发送自检报告给管理员
- 读取 `world_book.md` 模板，用自检数据替换占位符变量
- 邮件凭证优先级：环境变量 `EMILY_EMAIL_*` → `core_config.json` → 跳过邮件步骤（不阻塞）

### 7.3 `emily-data/prompts/world_book.md` 要求
- Markdown 格式，可包含占位符 `{变量名}`
- 变量占位符与自检 JSON 结构一致
- 可被 `cold_start.py` 读取并替换变量

## 八、非功能需求

### 8.1 Fail-Open 策略
- `self_check.py` 任何子查询失败不阻塞整体流程：对应字段 `null`，记录 `warnings`
- `cold_start.py` 邮件发送失败不阻塞后续步骤：记录日志，继续生成 prompt 上下文
- `world_book.md` 模板文件缺失时的降级：`cold_start.py` 使用内置默认 prompt（硬编码的基础定位描述）

### 8.2 数据保鲜
- 每次调用 `SelfCheck.run()` 都重新查询数据库，不缓存上一次结果
- 知识库 `kb.db` 直接读取 SQLite 文件（只读模式），不通过 MaxKB HTTP API

### 8.3 依赖声明
| 交付物 | 依赖 |
|--------|------|
| `self_check.py` | PostgreSQL（emily 库）+ SQLite `data/knowledge_base/kb.db` |
| `cold_start.py` | `self_check.py` + `EmailService`（已有模块）+ `world_book.md` |
| `world_book.md` | 无运行时依赖 |

## 九、测试考量

### 9.1 `self_check.py` 测试
- **单元测试**：Mock DB session + Mock SQLite kb.db → 验证各统计字段正确性
- **异常场景**：DB 连接超时 → `status = "error"`；kb.db 不存在 → `index_status = "unavailable"`
- **边界场景**：空数据库（0 用户/0 项目）→ 各统计字段返回 0，`status = "ok"`
- 建议测试文件：`scripts/tests/test_self_check.py`

### 9.2 `cold_start.py` 测试
- **集成测试**：Docker 内 `docker exec emily-core uv run python scripts/cold_start.py` → 验证返回的 prompt 文本包含注入的数据
- **异常场景**：自检脚本报错 → 跳过邮件 + 返回基础 prompt；邮件凭证缺失 → 跳过邮件 + 日志 warning

### 9.3 `world_book.md` 测试
- **内容验证**：确保无占位符以外的虚构功能描述
- **变量完整性**：模板中的 `{变量名}` 与 `self_check.py` 输出的 JSON key 路径一致
- **Prompt 行为评估**：LLM 收到世界书后不应引导用户使用不存在的功能
