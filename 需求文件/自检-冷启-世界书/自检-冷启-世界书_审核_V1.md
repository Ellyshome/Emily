## 一、总体评价

这份需求文档整体**结构清晰、范围可控**，三个交付物（自检脚本、冷启动脚本、世界书）的职责边界划分合理。自检数据采集的 JSON schema 设计干净，"永不崩溃 + 哨兵值降级"的错误处理策略也非常务实，符合 Emily 项目已有的脚本模式（参考 `scripts/collect_session_data.py`）。

文档有两个亮点值得肯定：一是正确识别了已有 `EmailService` 模块可以复用，没有重复造轮子；二是世界书采用"模板 + 变量注入"的设计，使静态 Prompt 描述与动态运行数据分离，维护性好。

**但存在一个根本性的战略问题**：世界书（§6.2–6.4）描述的系统定位——"以全生命周期节点图为锚点、公司-人员-节点三级绑定、节点级权限模型"——与 Emily 当前的真实架构（Session 主线 + WorkItem + 4 节点 PipelineBUS）**严重不吻合**。这会导致 LLM 在收到世界书灌注后，对系统能力产生系统性误判，进而给出用户无法实际执行的操作指引。这是本审核报告最核心的关注点。

## 二、分维度审核

### 2.1 I. 战略合理性 — 技术总监

**审核结论**：❌ 存在严重问题

#### 问题 I-1：世界书描述的"全生命周期节点图"与当前系统架构不符

当前 Emily 的真实架构（来自 CLAUDE.md）是：

> 双容器系统 → Session 主线 → WorkItem + 4 节点 PipelineBUS

这是一个**消息驱动的 AI Agent 对话系统**，而非以节点图为锚点的项目管理系统。

而世界书 §6.2–6.4 描述了一个不存在于当前系统的概念模型：

| 世界书声称 | 当前系统真实情况 |
|-----------|----------------|
| "以全生命周期节点图为锚点进行组织" | Session/WorkItem 消息处理为主，节点图是边缘模块 |
| "公司-人员-节点三级绑定" | 用户绑定仅到公司（`UserBindingService`），无节点级绑定 |
| "节点权限模型"（可见性/公共文件/公司级共享/管理者权限） | 权限是 6 级树形继承（`PermissionSnapshot`），不以节点为边界 |
| "节点管理/任务小组/文件协作"等 8 大能力模块 | 实际能力是事件/任务/会议/文件 CRUD + SOP 引导 + RAG |

**为什么这是严重问题**：世界书将被注入到 LLM 的 system prompt 中。如果它声称系统具有"节点图锚点"能力，LLM 会自信地引导用户执行节点相关操作——而这些操作要么根本不存在，要么实现方式与描述完全不同。用户会得到"镜像中的功能"，进而对系统产生不信任。

**建议**：世界书必须**以当前真实架构为基础**重写 §6.2–6.5。应描述：
- Emily 是一个消息驱动的 AI 团队协作助手
- 通过 SessionAgent 维护对话上下文，通过 WorkItem 执行结构化的业务流程
- 支持事件记录、任务管理、会议归档、文件协作等核心业务能力
- 知识库 RAG 提供项目资料语义检索
- 通过与用户对话引导完成业务操作（而非用户自主导航节点图）

#### 问题 I-2：方案命名与实际能力不匹配

"世界书"（World Book）是互动小说/游戏中的概念，指定义虚构世界规则和背景的参考文档。对于一个企业 AI Agent 项目，这个命名既不直观，也容易误导理解。该文件的本质是 **System Prompt 模板**——一份描述系统定位、能力边界和行为准则的 Prompt 片段，冷启动时注入实时统计数据进行实例化。

**建议**：建议重命名为更直接的名字，如 `system_prompt_base.md` 或 `agent_core_prompt.md`，放在 `emily-data/prompts/` 下与现有 `master_agent.txt` 并列。如果坚持保留"世界书"概念，至少应在需求文档中明确定义其与 master_agent prompt 的关系（追加？替代？组合？）。

#### 问题 I-3：解决的是真实问题

✅ 自检数据采集（用户数、业务量、RAG 存量）解决的是**真实运维需求**——系统管理员需要快速了解系统运行概况，LLM Agent 也需要知道"自己在服务多少人、管多少数据"。

✅ 冷启动邮件通知也是**真实需求**——运维人员需要确认系统启动后状态正常。

⚠️ 世界书解决的真实问题是"给 LLM 提供系统自我认知"——这个是真实需求，但当前版本通过描述不存在的架构来实现，反而引入了问题。

#### 问题 I-4：受众假设基本正确

✅ 自检数据 → 管理员（邮件）和 LLM Agent（Prompt 注入），受众清晰。
✅ 冷启动脚本 → 运维触发，受众明确。
⚠️ 世界书 → LLM Agent（SessionContext 注入），受众正确，但内容需修正。

### 2.2 B. 架构合理性 — 资深架构师

**审核结论**：⚠️ 有改进空间

#### 问题 B-1：冷启动脚本的嵌入点不明确

需求 §5 说冷启动在"系统启动完成后自动执行一次"。但 Emily 的 `EmilyCore._ensure_initialized()` 是**懒加载**——在首次消息到达时才初始化，而非容器启动时。如果 `cold_start.py` 想访问 `EmilyCore` 的服务（如 `EmailService`），它必须等到 Core 初始化完成之后。

当前可用的嵌入点有两个：
- **FastAPI lifespan**（`api/server.py:34`）：`bootstrap.init()` 之后、yield 之前。适合发启动邮件，但此时还没有消息流量，Session 池为空，"注入 Session 全局上下文"无意义。
- **`EmilyCore._ensure_initialized()` 末尾**（`__init__.py:162`）：初始化完成标记后。此时所有服务就绪，但同样还没有 Session 实例。

**建议**：将冷启动功能拆分为两个独立的 Hook：
1. **Startup hook**（FastAPI lifespan 内）：调用自检 → 发邮件给管理员 → 记录启动日志
2. **Session-create hook**（`SessionFactory._build_context()` 内）：读取世界书模板 → 注入当前自检数据 → 写入 `SessionContext.extra["world_book"]`

这样解决了"启动时还没有 Session"的时序问题，也复用了 Session 的生命周期。

#### 问题 B-2：脚本模块化设计良好但应统一入口

需求将 `SelfCheck.run()` 和 `ColdStart.run()` 定义为独立入口函数，设计简洁。但需明确：
- `self_check.py` 是否需要数据库连接？如果需要，应该像 `collect_session_data.py` 一样内置 `_init_db_if_needed()`
- `cold_start.py` 是否应该作为 `EmilyCore` 的方法（如 `cold_start()`）被 lifespan 调用？还是保持独立脚本？
- 独立脚本在 Docker 容器内如何被触发？（`docker exec`？entrypoint 脚本？还是 HTTP API？）

**建议**：`self_check.py` 保持独立脚本（可被多种调用方使用），`cold_start.py` 改为 `EmilyCore` 的方法，在 lifespan 和 admin API 中调用。

### 2.3 H. 与现有系统一致性 — 资深架构师

**审核结论**：⚠️ 有改进空间

#### 问题 H-1：API 端点未遵循已有路由模式

需求 §7.4 定义了：
```
GET  /api/v1/admin/self-check
POST /api/v1/admin/self-check/email
```

当前 `api/server.py` 中没有任何 `/admin/` 前缀的路由。现有路由使用扁平结构（`/api/v1/message/send`、`/api/v1/session/terminate`）或模块前缀（`/api/v1/permission/`、`/api/v1/project-nodes/`）。

**建议**：两种对齐方案可选：
- **方案 A**：遵循现有扁平风格，不引入 `/admin/` 前缀：`GET /api/v1/self-check`、`POST /api/v1/self-check/email`
- **方案 B**：如果 `/admin/` 是一个有意为之的管理路由分组，应创建 `api/routes/admin.py`，并在 `server.py` 统一 `include_router`，同时更新 `docs/接口协议与调用约定.md`

#### 问题 H-2：与已有模块的复用关系明确

✅ 邮件模块已确认可复用：`EmailService.send()` + `EmailCredentials`
✅ SessionContext.extra 字段是合适的世界书注入点  
✅ `collect_session_data.py` 的哨兵值 + 子脚本 + CLI 入口模式可作为 `self_check.py` 的编写模板

### 2.4 C. 实现可行性 — 经验丰富的程序员

**审核结论**：✅ 基本可行，有少数需明确之处

#### 问题 C-1：知识库统计的数据源不明确

需求 §3.4 要求采集 `kb_total_docs`、`kb_total_chunks`、`kb_index_status`。但 MaxKB 的 `hit_test` API 是**纯检索接口**，不直接提供统计元数据。需要确认：

- MaxKB 是否有管理 API 可用于获取知识库文档数/分块数？
- 如果没有，是否需要直接查询 MaxKB 的 PostgreSQL？
- `kb_index_status` 如何判定？"正常/需重建"的判断标准是什么？

**建议**：在需求文档中补充数据源说明。如果 MaxKB 不提供统计 API，可考虑两种降级方案：
- 从 Emily 自己的 `knowledge_base` 相关表统计（如果有记录存入日志）
- 直接查询 MaxKB PostgreSQL 的 `dataset`/`document`/`paragraph` 表

#### 问题 C-2：冷启动邮件发送的凭证来源未指定

`EmailService.send()` 需要 `EmailCredentials`（SMTP host/port/username/password）。需求 §5.2 说"调用邮件模块发送给管理员"但没有说明：

- 发件人凭证从哪里获取？（环境变量 `EMILY_EMAIL_*`？core_config.json？）
- "管理员"的邮箱地址存在哪里？（DB users 表？core_config.json 的 admin_emails 字段？）

**建议**：在需求文档中明确：
- 凭证来源：复用 `EmailService` 已有的环境变量配置
- 管理员邮箱：建议在 `core_config.json` 中新增 `admin_email_list` 字段

#### 问题 C-3：自检脚本的目标执行时间过于乐观

需求 §7.1 要求"目标执行时间 ≤ 1 秒"。考虑到需要查询 4 个维度的数据（users/projects/business/knowledge_base），其中知识库统计可能需要跨容器查询 MaxKB PostgreSQL，1 秒可能不够。

**建议**：调整为 ≤ 3 秒，或分级标注各子查询的预期耗时。

### 2.5 E. 接口契约 — 经验丰富的程序员

**审核结论**：✅ 基本清晰

#### 问题 E-1：输出 JSON schema 中 `status` 字段值域不全

需求 §4 定义了 `status: "ok" / "warning"`，但没有 `"error"` 状态。如果自检脚本自身执行失败（如数据库连接超时），返回什么？

**建议**：增加 `"error"` 状态：
```json
{
  "status": "error",  // ok / warning / error
  "error_message": "数据库连接失败: Connection refused"
}
```

同步更新状态判定规则：`error` = 脚本自身异常；`warning` = 数据采集成功但有警告；`ok` = 一切正常。

#### 问题 E-2：API 端点缺少请求/响应 DTO 定义

需求 §7.4 只给了 URL 和 HTTP method，但没有：
- `GET /api/v1/admin/self-check` 的响应格式（是直接返回自检 JSON 还是包装在 `{code, data, message}` 标准信封中？）
- `POST /api/v1/admin/self-check/email` 的请求体（是否需要指定收件人？是否支持覆盖默认收件人？）

**建议**：参考 `docs/接口协议与调用约定.md` 的标准响应格式，补充完整的 Request/Response DTO。

## 四、替代方案

### 方案 A：最小化（✅ 推荐）

延续需求文档的 3 个交付物框架，但做以下关键调整：

- **思路**：
  1. 保留 `self_check.py` 和 `cold_start.py` 的基本设计
  2. **重写世界书**：去掉不存在的"节点图锚点"概念，改为描述 Emily 作为"消息驱动的 AI 团队协作助手"的真实定位
  3. 冷启动拆分为两个 Hook（Startup + Session-create），解决时序问题
  4. 复用 `EmailService` 和 `SessionContext.extra`

- **优势**：改动最小，核心数据采集逻辑不变，仅修正世界书内容
- **劣势**：世界书仍是独立文件，与 `master_agent.txt` 的关系需要额外管理
- **适用场景**：当前阶段——需求文档描述的"精简、快速、满足基础需求即可"原则

### 方案 B：统一 Prompt 模板体系

不引入新的"世界书"文件，而是扩展现有 Prompt 体系。

- **思路**：
  1. 在 `master_agent.txt` 中增加 `【系统状态】` 占位块
  2. `cold_start.py` 读取 `master_agent.txt`，替换占位块，生成最终 prompt
  3. 将世界书的内容（系统定位、能力边界、行为准则）合并到 `master_agent.txt`
  4. 自检数据采集逻辑不变

- **优势**：消除了"世界书"这一独立的命名概念；Prompt 管理统一；减少文件数量
- **劣势**：`master_agent.txt` 会变得更长；如果未来需要为不同场景生成不同的 prompt，灵活性受限
- **适用场景**：只需要一份 system prompt 的场景

### 方案 C：世界书作为"未来蓝图"保留

保留世界书原始内容，但标记为"愿景描述"而非"当前能力声明"。

- **思路**：
  1. 在世界书开头增加明确声明：`> ⚠ 以下描述的"全生命周期节点图"模型为 Emily 未来的目标架构，当前版本尚未完全实现。AI 助手不应基于此模型引导用户操作。`
  2. 追加一段"当前真实能力"描述，覆盖 Session+WorkItem 的实际功能
  3. 自检和冷启动逻辑不变

- **优势**：保留了节点图架构作为长期目标，为后续开发提供方向参照
- **劣势**：增加了 Prompt 复杂度；LLM 可能仍然被"未来蓝图"误导；本质上把"需求文档应该写的东西"放进了"运行时应读取的东西"
- **适用场景**：如果"全生命周期节点图"确实是近期要实施的架构迁移目标
