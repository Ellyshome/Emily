## 一、总体评价

### 2.2 B. 架构合理性 — 资深架构师

**审核结论**：⚠️

**亮点**：
- 三表分解（instructions / tools / datasets）是合理的关注点分离，比当前"7 章自由文本一股脑塞给 LLM"要好
- 将 SOP 视为"Skill"而非"文档"的定位升级，符合从"LLM 驱动"到"引擎驱动 + LLM 辅助"的演进方向

**问题 1：三表分解未触及执行确定性**

当前问题的本质不是"SOP 信息没结构化"——信息其实都在 §3.2（工具表）、§3.1（数据表）、§4（字段约束）中。问题是**即使信息在，执行仍 100% 靠 LLM 读文本再规划**。三表分解只解决了"信息结构化"，但如果不改执行模型，LLM 仍然只是"读结构化表 → 自由规划"，确定性不会根本提升。

**改进建议**：三表分解必须配合**步骤序列定义**——即 Skill 不仅描述"有哪些工具和数据"，还要定义"按什么顺序、什么条件调用哪些工具"。LLM 只负责需要推理的部分（如从用户输入中提取字段值、处理歧义）。这本质上是把 SOP 从"给人看的文档"变成"给引擎看的程序"。

**问题 2：与现有架构的集成点未定义**

当前 4 节点 BUS 是：node1(意图验证+注入) → node2(计划+标准) → node3(执行+验收) → node4(成果总结)。Skill 架构如何与之集成？至少有三种可能：
- **(a) Skill 定义替代 node2 planner**：步骤序列预定义，跳过 LLM 规划，node2 变为"加载 Skill 定义"
- **(b) Skill 定义作为 node2 planner 的约束模板**：LLM 仍规划，但必须遵循 Skill 定义的步骤框架
- **(c) Skill 定义替代整个 4 节点流程**：Skill 自带完整的执行管线

需明确选择哪种方案并说明理由。

**问题 3：与 BusinessFlowToolRegistry 的关系不清**

当前 BusinessFlowToolRegistry 管理工具定义（name / description / parameters / handler），Skill 的 tools 表与它有大量重叠。是 Skill 的 tools 表引用 BusinessFlowToolRegistry 中的工具？还是 Skill 的 tools 表是独立的定义？如果是引用，Skill 只需存工具名 + 参数映射；如果是独立定义，会导致工具 schema 双重维护。

**改进建议**：Skill 的 tools 表应**引用** BusinessFlowToolRegistry 中的工具名，只额外定义参数映射（从用户输入/前步结果/固定值 → 工具参数），不重复定义工具的 schema。

### 2.3 C. 实现可行性 — 经验丰富的程序员

**审核结论**：⚠️

**可行项**：
- 扩展现有 `sop_parser.py`（mistune AST）解析 §3-§7 在技术上完全可行，已有 §1+§2 的成熟模式
- BusinessFlowToolRegistry 的 `get_tools_schema()` 方法已支持按名称获取工具 schema，Skill 引用机制无技术障碍
- 离线 LLM 辅助解析器可行：将 SOP .md 喂给 LLM，输出结构化 JSON/YAML，人工审校后存为 skill 定义文件

**风险项**：
- **参数映射是最大技术挑战**：当前 SOP §4 的字段约束是自然语言（如"事件标题，必有，≤50字"），转为结构化的参数来源映射（如 `title: {source: "user_input", extraction: "事件标题", required: true, max_length: 50}`）需要精心设计映射语法
- **条件分支**：当前 SOP §3.3 的流程图是 ASCII art，其中包含条件判断（如"[无事件标题] → 向用户询问"）。转为结构化定义需要条件表达式语法
- **现有 SOP 质量参差不齐**：12 份 SOP 的 §3.3/§4 格式不完全一致，离线解析器需要处理变异

**改进建议**：
- 参数映射采用"来源枚举 + JSON Path + 约束"三层结构：`{source: "user_input"|"prev_step"|"fixed"|"context", path: "title", constraints: {required: true, max_length: 50}}`
- 条件分支初期不支持——Phase 1 只支持线性步骤序列，条件分支作为 Phase 2 扩展
- 离线解析器输出后必须人工审校，不能全自动

## 四、替代方案

### 方案 A：SOP 内嵌结构化步骤定义（✅ 推荐作为过渡方案）

- **思路**：在现有 SOP .md 文件的 §3.3 中增加 YAML/JSON 格式的步骤定义块，node2 planner 直接解析为 ExecutionPlan，LLM 仅负责参数提取
- **优势**：不引入新概念、不改 SOP 文件命名和组织方式、对现有架构改动最小、可逐步推广到 12 份 SOP
- **劣势**：SOP 文件混合了人可读文档和机器可执行定义，长期维护有隐患
- **适用场景**：快速验证"结构化步骤定义"的效果，为后续完整 Skill 体系提供数据支撑

### 方案 B：完整 Skill 体系（原始需求的方向）

- **思路**：新建独立的 Skill 定义文件（YAML/JSON），包含 instructions / tools / datasets / steps 四段结构，替代 SOP 的运行时解析
- **优势**：关注点分离彻底（SOP 文档给人看、Skill 定义给引擎看），长期可维护性最好
- **劣势**：工程量大，需改动多个核心模块；SOP 编写门槛提高；12 份 SOP 需全部迁移
- **适用场景**：方案 A 验证效果后，作为正式架构升级

### 方案 C：仅强化 Planner Prompt（最小改动）

- **思路**：不改 SOP 格式，仅在 node2 planner 的 system prompt 中注入更强的约束指令（如"必须严格按 SOP §3.3 的步骤执行"）
- **优势**：零代码架构改动，只需调 prompt
- **劣势**：本质还是"靠 LLM 自觉"，不提供确定性保障
- **适用场景**：如果 LLM 遵循度问题不严重，可作为临时补丁
