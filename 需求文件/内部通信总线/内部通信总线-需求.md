# 内部通信总线（InternalEventBus）— 需求文档 v0.1

> **状态**：需求草案 | **创建日期**：2026-06-28 | **依赖**：无外部依赖

***

## 一、背景与问题

### 1.1 现状

Emily 当前有以下通信机制：

| 机制                      | 类型                    | 覆盖范围                  | 局限                            |
| ----------------------- | --------------------- | --------------------- | ----------------------------- |
| `OutboundEventBus`      | asyncio.Queue pub/sub | Core → SSE → 薄插件 → IM | **仅出站**（推消息给人），不用于模块间通信       |
| `PipelineBUS`           | 顺序 4 节点执行总线           | WorkItem 执行上下文        | **仅是执行管道**，Hook 只挂载在 4 个固定节点上 |
| `EmilyCore.__init__` 注入 | 构造函数依赖注入              | Core → 各子系统           | 星型拓扑，每新增消费者需改 Core            |

**现状问题**：各子系统之间没有解耦的内部事件通道。当一个模块发生某事，需要通知其他模块时，只能通过以下方式——

1. **直接调用**：`StateMachineService` 被 `WorkItemAgent` 直接调用 `try_match_and_complete()`，调用方需知道被调用方接口
2. **共享 OutboundEventBus**：`PlanTaskScheduler` / `StaleDetector` / `OpsScheduler` 通过 `outbound_bus.publish("reply", ...)` 推送提醒——但这是借出站通道做内部通知，语义混乱
3. **Thread-local / 全局状态**：`PermissionCache` 失效需各写入方手动调用 `cache.invalidate()`

### 1.2 为什么需要内部事件总线

随着权限管理系统（4 阶段 16-21 天）、待办公告模块、主动通知投递等新模块的落地，**模块间通信需求会爆炸**：

- 权限变更 → 需要通知 SessionContext 刷新、缓存失效、审计日志写入、待办公告推送
- 状态机节点完成 → 需要通知 ProjectAgent 刷新健康度、触发下游节点激活
- 计划任务到期 → 需要通知待办公告模块创建待办、通知主动会话模块发起会话
- 运维探针发现异常 → 需要通知多个消费者（告警、日志、待办）

如果继续用直接注入模式，`EmilyCore.__init__` 最终会变成一张复杂的依赖图，每个模块都要持有所有潜在消费者的引用。

### 1.3 目标

设计一个 **轻量级进程内事件总线**（InternalEventBus），在现有架构约束下，以最小成本实现子系统间解耦通信。

***

## 二、设计原则

| # | 原则       | 说明                                  |
| - | -------- | ----------------------------------- |
| 1 | **轻量**   | 基于 asyncio 原生机制，零外部依赖，核心代码 < 200 行  |
| 2 | **解耦**   | 发布者不感知订阅者；订阅者可动态增减                  |
| 3 | **进程内**  | 同进程同事件循环，不做跨进程/跨容器（那是 MQ 的职责）       |
| 4 | **非阻塞**  | `publish()` 不等待订阅者完成；单个慢订阅者不影响其他订阅者 |
| 5 | **模式复用** | 遵循 `OutboundEventBus` 的接口风格，降低学习成本  |
| 6 | **渐进式**  | 不强制所有模块迁移；新事件先走总线，旧调用保持兼容           |

***

## 三、核心设计

### 3.1 架构定位

```
┌─────────────────────────────────────────────────────┐
│                    EmilyCore 进程                      │
│                                                       │
│  ┌──────────┐  ┌──────────┐  ┌──────────────┐        │
│  │ Permission│  │ StateMach │  │ PlanTask     │        │
│  │ Service   │  │ Service   │  │ Scheduler    │  ...   │
│  └────┬──────┘  └────┬──────┘  └──────┬───────┘        │
│       │publish       │publish         │publish           │
│       ▼              ▼                ▼                  │
│  ┌─────────────────────────────────────────────────┐   │
│  │              InternalEventBus                    │   │
│  │         (in-process pub/sub hub)                 │   │
│  └───────┬──────────┬──────────┬───────────────────┘   │
│          │subscribe │subscribe │subscribe               │
│          ▼          ▼          ▼                         │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐                │
│  │Cache     │ │Audit     │ │Session   │  ...           │
│  │Invalidate│ │Logger    │ │Refresher │                │
│  └──────────┘ └──────────┘ └──────────┘                │
│                                                       │
│  ┌─────────────────────────────────────────┐         │
│  │ OutboundEventBus (出站，推送到 IM)       │         │
│  │  ← 部分 InternalEvent 也会触发出站通知    │         │
│  └─────────────────────────────────────────┘         │
└─────────────────────────────────────────────────────┘
```

**关键区分**：

| <br />   | InternalEventBus                     | OutboundEventBus |
| -------- | ------------------------------------ | ---------------- |
| **通信方向** | 模块 ↔ 模块（东-西）                         | Core → IM（北-南）   |
| **消费者**  | 系统内部模块                               | 薄插件（SSE）→ 人类用户   |
| **事件语义** | 技术/领域事件                              | 用户可读消息           |
| **持久化**  | 不持久化（纯内存）                            | 不持久化（纯内存）        |
| **桥接**   | 某些事件可桥接到 OutboundEventBus（如权限变更通知用户） | <br />           |

### 3.2 核心 API

```python
class InternalEventBus:
    """进程内发布-订阅事件总线。

    设计参考 OutboundEventBus 的简洁风格，但提供基于事件类型的
    条件订阅（而非广播到所有订阅者）。
    """

    def subscribe(self, event_type: str, handler) -> None:
        """订阅指定事件类型。

        Args:
            event_type: 事件类型字符串（如 "permission.changed"）。
                        支持通配符 "*" 订阅所有事件。
            handler: async callable(event_type: str, data: dict) -> None
        """
        ...

    def unsubscribe(self, event_type: str, handler) -> None:
        """取消订阅。"""
        ...

    async def publish(self, event_type: str, data: dict) -> None:
        """发布事件到所有匹配的订阅者。

        - 广播到该 event_type 的所有订阅者（并发执行）
        - 单个 handler 异常不影响其他 handler
        - 无订阅者时静默丢弃（不记录日志）
        """
        ...
```

### 3.3 事件命名规范

采用 **倒置域名** 风格，用 `.` 分隔层级：

```
{领域}.{动作/状态}[.{子分类}]

示例：
  permission.changed          # 权限变更
  permission.granted.temp     # 临时授权
  permission.revoked.permanent # 永久授权被撤销
  sm.node.status_changed      # 全景节点状态变更
  sm.stage.completed          # 阶段完成
  plantask.reminder           # 计划任务提醒
  plantask.escalated          # 计划任务升级
  user.bound                  # 用户绑定 IM 账号
  session.closed              # 会话关闭
  ops.finding.stale           # 运维发现：卡滞
  ops.finding.mailbox         # 运维发现：邮件
  cache.invalidate            # 缓存失效
```

### 3.4 事件负载规范

每个事件 `data` 为 `dict`，**必须**包含以下元字段：

| 字段          | 类型    | 说明                               |
| ----------- | ----- | -------------------------------- |
| `timestamp` | `str` | ISO 8601 时间戳                     |
| `source`    | `str` | 发布者模块名（如 `"permission_service"`） |

其余字段按事件类型定义。示例：

```python
# 权限变更事件
{
    "timestamp": "2026-06-28T15:30:00+08:00",
    "source": "permission_service",
    "user_id": "uuid-xxx",
    "change_type": "level_upgrade",      # level_upgrade | unit_bind | grant | revoke
    "old_level": 2,
    "new_level": 3,
    "triggered_by": "uuid-yyy",          # 操作人
}

# 状态机节点变更事件
{
    "timestamp": "2026-06-28T15:31:00+08:00",
    "source": "state_machine_service",
    "node_id": "NODE001",
    "node_name": "样板段放线",
    "old_status": "进行中",
    "new_status": "已完成",
    "stage_id": "STAGE-1",
    "cascade_effects": ["NODE002→进行中"],  # 级联影响
}
```

## 四、事件类型清单（首批）

基于现有模块的通信需求，定义以下事件类型：

### 4.1 权限事件（`permission.*`）

| 事件类型                 | 发布者                      | 消费者                                                                | 触发时机                |
| -------------------- | ------------------------ | ------------------------------------------------------------------ | ------------------- |
| `permission.changed` | `PermissionService`      | `SessionPool`（刷新快照）、`PermissionCache`（失效）、`PermissionAuditLog`（记录） | 权限级别变更、单位绑定变更、授权/撤销 |
| `permission.granted` | `PermissionGrantService` | `PermissionAuditLog`、`NotificationDispatcher`（通知用户）                | 临时/永久授权             |
| `permission.revoked` | `PermissionGrantService` | `PermissionAuditLog`、`NotificationDispatcher`                      | 授权撤销                |

### 4.2 状态机事件（`sm.*`）

| 事件类型                     | 发布者                   | 消费者                                      | 触发时机     |
| ------------------------ | --------------------- | ---------------------------------------- | -------- |
| `sm.node.status_changed` | `StateMachineService` | `ProjectAgent`（刷新健康度）、`SMJournal`（写项目日志） | 节点状态变更   |
| `sm.stage.completed`     | `StateMachineService` | `ProjectAgent`、`NotificationDispatcher`  | 阶段全部节点完成 |
| `sm.cascade.completed`   | `StateMachineService` | `ProjectAgent`                           | 级联更新完成   |

### 4.3 计划任务事件（`plantask.*`）

| 事件类型                 | 发布者                 | 消费者                                                  | 触发时机    |
| -------------------- | ------------------- | ---------------------------------------------------- | ------- |
| `plantask.reminder`  | `PlanTaskScheduler` | `OutboundEventBus`（桥接，推 IM）、`AgentIssueClient`（创建待办） | 任务即将到期  |
| `plantask.overdue`   | `PlanTaskScheduler` | `OutboundEventBus`、`AgentIssueClient`                | 任务已超时   |
| `plantask.escalated` | `PlanTaskScheduler` | `OutboundEventBus`、`AgentIssueClient`                | 任务升级给上级 |

### 4.4 用户事件（`user.*`）

| 事件类型                | 发布者                  | 消费者                                         | 触发时机          |
| ------------------- | -------------------- | ------------------------------------------- | ------------- |
| `user.bound`        | `UserBindingService` | `PermissionService`（自动授予访客权限）、`SessionPool` | IM 用户首次绑定系统用户 |
| `user.unit_changed` | `PermissionService`  | `PermissionCache`（失效）、`SessionPool`（刷新）     | 用户单位归属变更      |

### 4.5 会话事件（`session.*`）

| 事件类型             | 发布者                         | 消费者                            | 触发时机 |
| ---------------- | --------------------------- | ------------------------------ | ---- |
| `session.closed` | `SessionPool` / `EmilyCore` | `OutboundEventBus`（已有路径，可改为桥接） | 会话终止 |

### 4.6 运维事件（`ops.*`）

| 事件类型               | 发布者                 | 消费者                                        | 触发时机   |
| ------------------ | ------------------- | ------------------------------------------ | ------ |
| `ops.finding`      | `OpsScheduler`（各探针） | `OutboundEventBus`（桥接，告警）、`SMJournal`（写日志） | 探针发现异常 |
| `ops.probe_failed` | `OpsScheduler`      | `OutboundEventBus`（通知管理员）                  | 探针自身异常 |

### 4.7 缓存事件（`cache.*`）

| 事件类型               | 发布者    | 消费者                                       | 触发时机      |
| ------------------ | ------ | ----------------------------------------- | --------- |
| `cache.invalidate` | 各数据写入方 | `PermissionCache`、`SOPIntentRegistry`（可选） | 数据变更需刷新缓存 |

## 五、集成方案

### 5.1 EmilyCore 初始化

```python
# emily_core/__init__.py

class EmilyCore:
    def __init__(self, config: Config, ...):
        ...
        self.outbound_bus = OutboundEventBus()       # 现有：出站
        self.internal_bus = InternalEventBus()        # 新增：内部

    def _ensure_initialized(self):
        ...
        # 在初始化各子系统后，注册内部事件订阅
        self._wire_internal_events()

    def _wire_internal_events(self):
        """将各子系统连接到内部事件总线（桥接 + 订阅）。"""
        ib = self.internal_bus

        # ── 桥接：内部事件 → 出站通知 ──
        ib.subscribe("permission.changed", self._on_permission_changed_for_im)
        ib.subscribe("plantask.*", self._on_plantask_event_for_im)
        ib.subscribe("ops.finding", self._on_ops_finding_for_im)

        # ── 缓存失效 ──
        if self._permission_cache:
            ib.subscribe("permission.*", lambda t, d: self._permission_cache.invalidate(d.get("user_id")))
            ib.subscribe("user.unit_changed", lambda t, d: self._permission_cache.invalidate(d.get("user_id")))

        # ── 状态机 → ProjectAgent ──
        if self._project_agent:
            ib.subscribe("sm.node.status_changed", self._project_agent.on_node_changed)
            ib.subscribe("sm.stage.completed", self._project_agent.on_stage_completed)
```

### 5.2 与 OutboundEventBus 的桥接

桥接逻辑放在 `EmilyCore` 中，不放在 `InternalEventBus` 内部（保持各自独立）：

```python
# 权限变更 → 通知用户
async def _on_permission_changed_for_im(self, event_type: str, data: dict):
    user_id = data.get("user_id")
    if data.get("change_type") == "level_upgrade":
        self.outbound_bus.publish("reply", {
            "target_user_id": user_id,
            "content": f"您的权限已升级为 {data.get('new_level_name')}",
        })
    # permission_changed 事件也推送给 SSE（用于 Session 刷新）
    self.outbound_bus.publish("permission_changed", data)
```

### 5.3 现有模块改造（渐进式）

| 模块                          | 当前做法                                           | 改为                                                        | 优先级 |
| --------------------------- | ---------------------------------------------- | --------------------------------------------------------- | --- |
| `PlanTaskScheduler` → IM 提醒 | `outbound_bus.publish("reply", ...)`           | `internal_bus.publish("plantask.reminder", ...)` → 桥接自动转发 | P1  |
| `StaleDetector` → IM 告警     | `outbound_bus.publish("reply", ...)`           | `internal_bus.publish("ops.finding.stale", ...)`          | P2  |
| `OpsScheduler` → 启动报告       | `outbound_bus.publish("reply", ...)`           | `internal_bus.publish("ops.startup_report", ...)`         | P2  |
| `StateMachineService` 被直接调用 | `WorkItemAgent` 直接调 `try_match_and_complete()` | 保留直接调用（这是编排逻辑，不是事件通知），但状态变更后 `publish` 事件                 | —   |
| `PermissionService` 缓存失效    | 无（尚未落地）                                        | `internal_bus.publish("permission.changed", ...)`         | P1  |

### 5.4 新模块接入

权限管理系统（设计阶段）和待办公告模块（需求阶段）应**原生接入 InternalEventBus**，不直接持有消费者引用。

## 六、非功能需求

### 6.1 性能

| 指标             | 目标                          | 策略                                      |
| -------------- | --------------------------- | --------------------------------------- |
| `publish()` 延迟 | < 1ms（无订阅者）/ < 10ms（10 订阅者） | 纯内存 dict 查找 + asyncio.create\_task 并发   |
| 单订阅者处理延迟       | 不阻塞 publish                 | 每个 handler 用 `asyncio.create_task` 异步执行 |
| 事件队列堆积         | 无队列设计，直接 push               | 不设中间队列；慢订阅者自己实现缓冲                       |
| 吞吐量            | > 1000 events/s             | 纯内存操作，无 I/O 瓶颈                          |

### 6.2 可靠性

| 指标           | 目标                | 策略                           |
| ------------ | ----------------- | ---------------------------- |
| Handler 异常隔离 | 单 handler 失败不影响其他 | try/except 包裹每个 handler      |
| 事件丢失         | 允许（非持久化，非关键路径）    | 若需可靠投递，由消费者自己实现 outbox/retry |
| 初始化顺序        | 发布者可先于订阅者启动       | 无订阅者时静默丢弃，不报错                |

### 6.3 可观测性

```python
# 通过 EmilyCore.health() 暴露
"internal_bus": {
    "subscription_count": 15,
    "event_types": 12,
    "events_published": 1234,     # 累计（可选，轻量计数器）
    "handler_errors": 2,          # 累计（可选）
}
```

### 6.4 约束

- **纯内存，不持久化**：进程重启丢失所有事件和订阅关系。订阅关系在 `EmilyCore._ensure_initialized()` 中重建。
- **不做事件溯源**：这是通信机制，不是审计机制。审计日志由各自模块写入 DB（如 `permission_audit_log`）。
- **不做跨容器通信**：emily-core 与 astrbot/napcat/maxkb 的跨容器通信继续走 HTTP/SSE。
- **不替代 OutboundEventBus**：出站消息推送给人类用户，仍走 OutboundEventBus；InternalEventBus 只管模块间。

## 七、与现有架构的关系

### 7.1 不破坏现有分层

```
API → EmilyCore → SessionAgent → WorkItemAgent → PipelineBUS → Application → Service → Repository → DB
                     │
                     ├── InternalEventBus（新增：横向模块通信）
                     └── OutboundEventBus（已有：纵向出站通信）
```

`InternalEventBus` 作为 `EmilyCore` 的成员，与 `OutboundEventBus` 平级。各 Service 通过 `EmilyCore` 获取 bus 引用（与现有 `outbound_bus` 模式一致）。

### 7.2 不引入新依赖

全部基于 Python 标准库 `asyncio` + `logging`，与 `OutboundEventBus` 的技术栈完全一致。

### 7.3 不影响 Mock 模式

Mock 模式下内部事件同样发布（只是消费者可能不做实质性处理），不需要特殊处理。

## 九、验收标准

1. ✅ `InternalEventBus` subscribe / unsubscribe / publish 基本功能
2. ✅ `publish()` 并发通知所有匹配订阅者（不阻塞）
3. ✅ 单个 handler 异常不影响其他 handler
4. ✅ 无订阅者时 publish 静默丢弃
5. ✅ 通配符订阅（如 `"plantask.*"` 匹配 `"plantask.reminder"`）
6. ✅ `EmilyCore.health()` 返回 bus 统计信息
7. ✅ 至少完成 2 个现有模块的改造：`PlanTaskScheduler` 改为发布内部事件 + 桥接到 OutboundEventBus
8. ✅ 权限管理系统阶段一（快照灌注）的 `permission.changed` 事件链路跑通

## 十、不做什么（Scope 边界）

1. ❌ **不做**持久化 / 事件重放 / 事件溯源
2. ❌ **不做**跨容器通信（那是 MQ/HTTP 的职责）
3. ❌ **不做**事件版本管理 / schema 校验
4. ❌ **不做**消息队列 / 背压控制（进程内不必要）
5. ❌ **不要**求所有现有模块立即迁移——新模块原生接入，旧模块渐进改造

***

## 十一、决策待确认

> 以下问题需要在进入实施计划前确认。

1. **通配符匹配方式**：简单前缀匹配（`"plantask.*"`）还是完整 glob（`"permission.*.temp"`）？建议前缀匹配，简单够用。
2. **同步 handler 支持**：当前设计只支持 async handler。是否需要兼容 sync handler？建议只支持 async（项目全链路 async）。
3. **事件类型注册**：是自由字符串（动态）还是枚举常量（类型安全）？建议常量定义 + 字符串兼容（枚举便于 IDE 补全，字符串允许扩展）。
