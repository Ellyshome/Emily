## 一、总体评价

这份需求文档准确地诊断了 Emily 当前子系统间通信的痛点——直接注入导致的星型耦合，并提出了一个简洁的解耦方案。文档亮点包括：**明确的 Scope 边界**（专设"不做什么"章节，避免范围蔓延）、**渐进式迁移策略**（不强制所有模块立刻改造）、以及**与 OutboundEventBus 的清晰职责划分**（内部 vs 出站，各司其职）。

整体方向正确。两总线架构（InternalEventBus + OutboundEventBus）在现有约束下是最优方案——既不破坏现有 OutboundEventBus 的工作流，又为模块间通信开辟了专有通道。事件命名规范（领域.动作）清晰，首批 7 类事件覆盖了已识别的高频通信需求。

但在 **实现细节** 上有几个关键问题需要修复后才能进入实施计划。核心问题是：① lambda 订阅导致的 unsubscribe 不可用、② Service 获取 bus 引用的方式未明确、③ 缺少递归发布和优雅关闭的保护机制。

## 二、分维度审核

### 2.1 架构合理性 — 资深架构师

**审核结论**：⚠️ 有改进空间

**通过项**：
- ✅ 两总线职责分离明确：InternalEventBus（模块 ↔ 模块）vs OutboundEventBus（Core → IM），互不污染
- ✅ 桥接放在 `EmilyCore._wire_internal_events()` 而非总线内部，保持各自独立——这是正确的解耦方式
- ✅ 事件命名采用层级命名空间（`permission.changed`），支持前缀订阅，比扁平命名更可维护
- ✅ Scope 边界清晰：不做持久化、不做跨容器、不做事件溯源——专注进程内通信，避免 over-engineering

**问题**：

1. ⚠️ **Service 获取 bus 引用的方式未明确**

   需求文档 §5.1 展示了 `EmilyCore._wire_internal_events()` 订阅端，§4.1-4.7 列出了各 Service 作为发布者。但发布者如何拿到 `internal_bus`？

   当前 Service 的模式是**构造函数注入**（如 `PlanTaskScheduler(outbound_bus=...)`）。如果照搬这个模式，每个需要发布事件的 Service 都要在构造函数中接收 `internal_bus`。但随着发布者增多，构造函数参数会膨胀。

   **建议**：明确两种注入方式二选一，在实施计划中指定：
   - **方案 A**：构造函数注入（与现有模式一致，推荐短期）
   - **方案 B**：`EmilyCore` 提供 `get_internal_bus()` 静态/模块级访问（简化调用，但引入全局状态）

2. ⚠️ **缺少递归/重入发布保护**

   需求文档未讨论一种危险场景：Handler A（订阅 `X`）处理过程中又 `publish("X")`，或 Handler A `publish("Y")` 触发 Handler B，Handler B 又 `publish("X")`。没有递归保护 = 潜在的无限循环或栈溢出。

   **建议**：在 §六 非功能需求中增加一条：**重入保护**——`publish()` 检测当前事件循环中是否已存在同事件类型的处理链，若检测到环则 `WARNING` 日志 + 丢弃事件（不发布）。实现可以用 `contextvars` 存储当前处理的事件链。

3. ⚠️ **缺少优雅关闭机制**

   需求文档未提及 Core 关闭时正在执行的 handler tasks 如何处理。`asyncio.create_task` 创建的 task 在进程退出时会被取消，但 handler 中如果有 await 阻塞点，可能处于不一致状态。

   **建议**：在 §六 非功能需求中增加：`EmilyCore.shutdown()` 调用 `internal_bus.shutdown(timeout_seconds=5)`，等待所有进行中的 handler 完成或超时取消。

### 2.2 实现可行性 — 经验丰富的程序员

**审核结论**：❌ 有严重问题

**通过项**：
- ✅ 核心 API（subscribe / unsubscribe / publish）简洁正确
- ✅ `< 200 行` 目标可行——`OutboundEventBus` 仅 62 行，加通配符匹配 + 并发执行可在 150 行内完成
- ✅ 无外部依赖，纯 asyncio + logging

**问题**：

1. ❌ **（阻塞）lambda 订阅导致 unsubscribe 不可用**

   [需求文档 §5.1 第 276-277 行](内部通信总线-需求.md#L276-L277)：
   ```python
   ib.subscribe("permission.*", lambda t, d: self._permission_cache.invalidate(d.get("user_id")))
   ```
   每次调用 `_wire_internal_events()` 创建新的 lambda 对象。`unsubscribe` 按 handler 引用匹配，但 lambda 是匿名函数，**无法在别处获取其引用来取消订阅**。

   实际后果：`PermissionCache` 重建时无法退订旧 handler，导致内存泄漏 + 重复执行。

   **修复建议**：规定 handler 必须是**可引用对象**——绑定方法（`self._on_xxx`）或具名函数。禁止在 `subscribe` 中直接使用 lambda。代码修改为：
   ```python
   # 正确写法
   ib.subscribe("permission.*", self._on_permission_invalidate_cache)
   
   # 或在 subscribe 返回退订 token
   token = ib.subscribe("permission.*", handler)
   ib.unsubscribe(token)  # 通过 token 退订
   ```

2. ❌ **（阻塞）`create_task` 的 task 泄露问题**

   需求文档 §6.1 提到 `asyncio.create_task` 并发执行 handlers。但没有讨论：
   - 谁来 `await` 这些 task？（没人 await → task 异常可能被静默吞掉）
   - handler 抛异常 → task 结束但异常未消费 → asyncio 输出 "Task exception was never retrieved" 噪音日志

   **修复建议**：收集 `create_task` 返回的 task 对象，在 `publish` 结束时 `gather(return_exceptions=True)` 等待全部完成再返回。或者至少用一个 done callback 捕获异常：
   ```python
   async def publish(self, event_type, data):
       tasks = []
       for h in self._handlers:
           task = asyncio.create_task(self._safe_invoke(h, event_type, data))
           tasks.append(task)
       # await asyncio.gather(*tasks, return_exceptions=True)  # 简单版
       # 或者 fire-and-forget with done callback（需求文档的原意）
   ```
   如果坚持 fire-and-forget，必须在需求中注明：handler 异常由 `_safe_invoke` 内部的 try/except + logging 处理，不依赖外层。

3. ⚠️ **通配符匹配的语义歧义**

   需求文档 §3.2 说 `"*"` 订阅所有事件，§5.1 使用 `"plantask.*"` 匹配子类型。但 `"plantask.*"` 有两层含义：
   - **前缀匹配**：匹配 `plantask.reminder`、`plantask.overdue` 等（简单，够用）
   - **通配符匹配**：`*` 仅在一个层级内扩展，`plantask.*` 不匹配 `plantask.reminder.daily`

   需求文档 §十一.1 提出"建议前缀匹配"，但与 `"*"` 订阅所有事件的语义冲突（前缀匹配下 `"*"` 匹配空字符串前缀 = 所有）。必须明确：
   - `"permission.*"` 是否匹配 `"permission.granted.temp"`（三级）？
   - 建议：`"permission.*"` 匹配 `permission.` 开头的**所有**事件（简单前缀匹配），`"*"` 匹配所有。这样实现最简单。

### 2.3 安全性 — 安全工程师

**审核结论**：⚠️ 有改进空间

**通过项**：
- ✅ 进程内总线天然免于网络攻击（非网络暴露）
- ✅ 事件不持久化，降低敏感数据泄露面

**问题**：

1. ⚠️ **事件负载无校验**

   需求文档 §3.4 规定 `data` 为自由 `dict`，只强制 `timestamp` 和 `source`。未校验的负载传到消费者，可能引发：
   - Handler 期望 `user_id` 为 str，但收到 int → 崩溃
   - 权限事件负载包含敏感字段（如 `old_level`、`new_level`）以明文在内存中流转

   **建议**：
   - 不强制 schema 校验（避免 over-engineering），但在 §3.4 增加**防御性编程约定**：消费者用 `data.get("key")` 而非 `data["key"]`，设置默认值
   - 敏感字段（如 password/token）明确禁止进入事件负载（在 §3.4 列黑名单）
   - 如果后续事件类型超过 20 种，再考虑引入 `TypedDict` 或 dataclass 做类型安全

2. ⚠️ **无事件源验证**

   任何模块可以 `publish("permission.changed", ...)` 伪造权限变更。虽然进程内攻击面小，但 bug 驱动的误发布同样危险。

   **建议**：在 §3.4 的 `source` 字段约定中增加：消费者可通过 `source` 做来源校验（如 `PermissionCache` 只接受 `source == "permission_service"` 的 `permission.changed`）。这是约定而非强制机制，成本为零。

## 四、替代方案

### 方案 A：两总线方案（当前方案，✅ 推荐）

- **思路**：新增 `InternalEventBus`，与现有 `OutboundEventBus` 并存，桥接逻辑在 `EmilyCore` 中。
- **优势**：职责分离清晰；不破坏现有代码；渐进式迁移；遵循现有模式
- **劣势**：多一个概念需要团队理解；桥接代码需维护
- **适用场景**：权限管理系统、待办公告等新模块原生接入；现有模块逐步改造

### 方案 B：扩展现有 OutboundEventBus

- **思路**：给 `OutboundEventBus` 增加 `subscribe(event_type, handler)` 方法，使其同时服务内部和出站通信。
- **优势**：单一总线，概念更少；代码改动更小（只改 OutboundEventBus）
- **劣势**：**职责混淆**——一条总线既推送 IM 消息又做模块间通信；内部事件和出站事件混合在同一个命名空间中；OutboundEventBus 的 `asyncio.Queue` 模式（每个订阅者独立队列）不适合内部事件（内部事件需要条件订阅）；将来出站通道的变更可能意外影响内部通信
- **适用场景**：不推荐。短期简单但长期混乱。

### 方案 C：零总线，全回调注入

- **思路**：不引入总线。每个模块仍通过构造函数注入回调（如 `on_permission_changed: Callable`）。
- **优势**：完全不引入新概念；类型安全（回调有签名）
- **劣势**：随着消费者增加，构造函数爆炸（权限变更需要 N 个回调，每个发布者都要有 N 个 Callable 参数）；难以动态增减消费者；与"解耦"目标背道而驰
- **适用场景**：只有 1-2 个事件、1-2 个消费者时可行。本项目已超过这个规模。
