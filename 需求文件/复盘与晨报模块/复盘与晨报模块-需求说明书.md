# 复盘与晨报模块 — 需求说明书

> 版本：V1.0 | 日期：2026-07-09
> 本文档定义 Emily 每日复盘总结与晨报推送模块的完整需求，包括 LLM 复盘的输入数据源、查询逻辑、输出成果、以及定制 Prompt。

---

## 一、模块定位

Emily 当前已拥有 5+ 张进化日志表持续采集运行数据，但**零机制**将观察转化为自我改进。本模块要解决的核心问题：

1. **保存什么？** — 从原始日志中提炼三层进化知识体（日洞察 → 进化规则 → 进化补丁）
2. **如何进化？** — 通过修改 Emily 的 5 个可突变面（Prompt/SOP/Skill/Hook/用户记忆），形成完整的进化闭环

---

## 二、系统架构总览

### 2.1 进化闭环

```
     ┌──────────────┐
     │  日志采集层    │  ← 已有：5+ 张进化日志表持续写入
     │  (Observe)    │
     └──────┬───────┘
            │ 每日 22:00 调度触发
            ▼
     ┌──────────────┐
     │  日洞察引擎    │  ← 新增：DailyInsightHandler
     │  (Reflect)    │     聚合日志 → 硬规则异常检测 → LLM 总结 → 写 Daily Insight
     └──────┬───────┘
            │ 每周日 22:30 调度触发
            ▼
     ┌──────────────┐
     │  规则归纳器    │  ← 新增：RuleInductionHandler
     │  (Generalize) │     读近7天 Insight → LLM 归纳 → 写 Evolution Rule (DRAFT)
     └──────┬───────┘
            │ 规则累积 ≥ 阈值 或 发现强信号
            ▼
     ┌──────────────┐
     │  补丁生成器    │  ← 新增：PatchGenerator
     │  (Mutate)     │     读 CONFIRMED Rules → LLM 生成变更 → 写 Evolution Patch (DRAFT)
     └──────┬───────┘
            │ 管理员审批（全部人工）
            ▼
     ┌──────────────┐
     │  补丁应用器    │  ← 新增：PatchApplier
     │  (Apply)      │     修改配置文件 → 热重载 → 状态→APPLIED
     └──────┬───────┘
            │ 7 天后对比指标
            ▼
     ┌──────────────┐
     │  效果验证器    │  ← 新增：PatchValidator
     │  (Validate)   │     对比前后指标 → CONFIRMED / ROLLED_BACK
     └──────────────┘
```

### 2.2 Emily 的 5 个可突变面

| 可突变面 | 位置 | Patch 能改什么 |
|---------|------|--------------|
| Prompt 模板 | `emily-data/prompts/session.md` | 路由规则、同义词映射、措辞微调 |
| SOP 定义 | `emily-data/sops/*.md` | 步骤调整、确认策略 |
| Skill 路由 | `emily-data/skills/*.skill.yaml` | 匹配关键词、instructions |
| Hook 配置 | `emily-data/config/hook_config.json` | 审计规则、风险阈值 |
| 用户记忆 | `emily-data/user_memory/*.md` | 长期偏好观察 |

### 2.3 关键设计决策

- **Patch 安全边界**：只改 `emily-data/` 下的配置文件，不触碰 `emily-core/` 下的 Python 代码
- **全部人工审批**：所有补丁需管理员审批后才能应用
- **管理员专属可见**：进化洞察/规则/补丁仅管理员可查询（permission_level ≥ 5）
- **小步快跑**：一条规则 = 一个 Patch，避免大范围行为突变
- **可追溯**：每个 Patch 记录 来源 Rule → 来源 Insight → 来源日志记录

## 三、日洞察引擎（Daily Insight）— 详细设计

### 3.1 触发方式

- 调度器每日 22:00 自动触发（`generate_daily_insight` 作业）
- 手动触发：`POST /api/v1/evolution/insights/generate?date=2026-07-09`

### 3.2 LLM 输入数据源

以下为复盘时需要查询的数据库表及具体字段、查询逻辑：

#### 数据源 A：Pipeline 执行日志 — `pipeline_execution_logs`

| 查询字段 | 聚合方式 | 说明 |
|---------|---------|------|
| `created_at` | WHERE 条件：当日 0:00~24:00 | 时间过滤 |
| `matched_sop_id` | GROUP BY + COUNT | 各 SOP 命中分布 |
| `match_confidence` | GROUP BY + COUNT | high/medium/low/none 分布 |
| `is_fallback` | COUNT WHERE true | Fallback 次数 |
| `is_compound` | COUNT WHERE true | 复合请求次数 |
| `final_status` | GROUP BY + COUNT | DONE/FAILED/ABORTED 分布 |
| `was_blocked` | COUNT WHERE true | 被 Hook 阻断次数 |
| `elapsed_ms` | AVG / MAX / P95 | 耗时统计 |
| `node1_ms` ~ `node4_ms` | AVG | 各节点平均耗时 |
| `abort_reason` | WHERE final_status='ABORTED' | 阻断原因 Top N |
| `intent_reasoning` | 采样 low/none confidence | 低置信度推理原因 |

**SQL 示例**：
```sql
-- SOP 命中率
SELECT
  COUNT(*) AS total,
  SUM(CASE WHEN is_fallback = false THEN 1 ELSE 0 END) AS hit,
  SUM(CASE WHEN is_fallback = true THEN 1 ELSE 0 END) AS fallback,
  SUM(CASE WHEN is_fallback = false THEN 1 ELSE 0 END)::float / NULLIF(COUNT(*), 0) AS hit_rate
FROM pipeline_execution_logs
WHERE created_at >= '{date}T00:00:00' AND created_at < '{next_date}T00:00:00';

-- 各 SOP 分布
SELECT matched_sop_id, COUNT(*) AS cnt
FROM pipeline_execution_logs
WHERE created_at >= '{date}T00:00:00' AND created_at < '{next_date}T00:00:00'
  AND is_fallback = false
GROUP BY matched_sop_id ORDER BY cnt DESC LIMIT 10;

-- 失败/阻断详情
SELECT final_status, COUNT(*) AS cnt,
       STRING_AGG(DISTINCT abort_reason, '; ') AS reasons
FROM pipeline_execution_logs
WHERE created_at >= '{date}T00:00:00' AND created_at < '{next_date}T00:00:00'
  AND final_status IN ('FAILED', 'ABORTED')
GROUP BY final_status;
```

#### 数据源 B：SOP 路由日志 — `sop_routing_logs`

| 查询字段 | 聚合方式 | 说明 |
|---------|---------|------|
| `is_hit` | COUNT WHERE false | 未命中次数 |
| `matched_sop_id` | WHERE is_hit=false, GROUP BY | 未命中时的空值统计 |
| `match_confidence` | WHERE is_hit=false | 低置信度分布 |
| `message_content` | WHERE is_hit=false, 采样 Top 10 | 未命中消息原文 |
| `fallback_action` | GROUP BY + COUNT | 兜底动作分布 |
| `llm_reasoning` | WHERE is_hit=false, 采样 | LLM 推理原因 |

**SQL 示例**：
```sql
-- 未命中消息采样
SELECT message_content, llm_reasoning, match_confidence
FROM sop_routing_logs
WHERE log_date = '{date}' AND is_hit = false
ORDER BY created_at DESC LIMIT 10;
```

#### 数据源 C：用户反馈信号 — `user_feedback_signals`

| 查询字段 | 聚合方式 | 说明 |
|---------|---------|------|
| `signal_type` | GROUP BY + COUNT | 各信号类型分布 |
| `signal_strength` | AVG | 平均信号强度 |
| `trigger_message` | WHERE signal_type='explicit_correction', 采样 | 纠正消息原文 |
| `conversation_id` | GROUP BY + COUNT | 哪些会话反馈最多 |

**SQL 示例**：
```sql
-- 反馈信号汇总
SELECT signal_type, COUNT(*) AS cnt, AVG(signal_strength) AS avg_strength
FROM user_feedback_signals
WHERE created_at >= '{date}T00:00:00' AND created_at < '{next_date}T00:00:00'
GROUP BY signal_type;

-- 纠正信号详情
SELECT trigger_message, context_summary
FROM user_feedback_signals
WHERE created_at >= '{date}T00:00:00' AND created_at < '{next_date}T00:00:00'
  AND signal_type = 'explicit_correction'
ORDER BY signal_strength DESC LIMIT 5;
```

#### 数据源 D：RAG 检索日志 — `rag_retrieval_logs`

| 查询字段 | 聚合方式 | 说明 |
|---------|---------|------|
| `hit_count` | AVG / WHERE =0 | 平均命中数 + 零命中次数 |
| `top_score` | AVG | 平均最高分 |
| `avg_score` | AVG | 平均分 |
| `query_text` | WHERE hit_count=0, 采样 Top 10 | 未命中查询原文 |
| `provider` | GROUP BY + COUNT | 检索源分布 |
| `latency_ms` | AVG / MAX | 检索延迟 |
| `error_summary` | WHERE !='', 采样 | 检索错误 |

**SQL 示例**：
```sql
-- RAG 命中率
SELECT
  COUNT(*) AS total,
  SUM(CASE WHEN hit_count > 0 THEN 1 ELSE 0 END) AS hit,
  AVG(top_score) AS avg_top_score,
  AVG(latency_ms) AS avg_latency
FROM rag_retrieval_logs
WHERE created_at >= '{date}T00:00:00' AND created_at < '{next_date}T00:00:00';

-- 零命中查询采样
SELECT query_text, provider
FROM rag_retrieval_logs
WHERE created_at >= '{date}T00:00:00' AND created_at < '{next_date}T00:00:00'
  AND hit_count = 0
ORDER BY created_at DESC LIMIT 10;
```

#### 数据源 E：业务事件日志 — `business_event_logs`

| 查询字段 | 聚合方式 | 说明 |
|---------|---------|------|
| `event_category` | GROUP BY + COUNT | event/task/meeting/file/permission/system 分布 |
| `event_action` | GROUP BY + COUNT | created/confirmed/blocked/archived 分布 |
| `project_id` | GROUP BY + COUNT | 各项目活跃度 |
| `user_name` | GROUP BY + COUNT + ORDER BY DESC | 最活跃用户 Top 10 |

#### 数据源 F：Session 生命周期日志 — `session_lifecycle_logs`

| 查询字段 | 聚合方式 | 说明 |
|---------|---------|------|
| `event_type` | WHERE = 'created', COUNT | 新建会话数 |
| `message_count` | WHERE event_type='archived', SUM | 总消息数 |
| `duration_ms` | WHERE event_type='archived', AVG | 平均会话时长 |

#### 数据源 G：Agent 推理日志 — `agent_reasoning_logs`

| 查询字段 | 聚合方式 | 说明 |
|---------|---------|------|
| `matched_sop_id` | GROUP BY + COUNT | 各 SOP 命中分布 |
| `fallback` | COUNT WHERE true | Fallback 次数 |
| `execution_result` | GROUP BY + COUNT | success/failed/timeout |
| `iteration_count` | AVG / MAX | 平均迭代次数 |
| `max_iterations_reached` | COUNT WHERE true | 触达上限次数 |
| `error_message` | WHERE execution_result='failed', 采样 | 失败原因 |

#### 数据源 H：工具调用日志 — `tool_call_logs`

| 查询字段 | 聚合方式 | 说明 |
|---------|---------|------|
| `tool_name` | GROUP BY + COUNT | 工具使用频率 |
| `is_success` | COUNT WHERE false | 工具失败次数 |
| `error_message` | WHERE is_success=false, GROUP BY tool_name | 工具失败原因 |

#### 数据源 I：项目节点 — `project_nodes`

| 查询字段 | 聚合方式 | 说明 |
|---------|---------|------|
| `status` | GROUP BY + COUNT | 节点状态分布 |
| `progress` | WHERE status='IN_PROGRESS', AVG | 平均进度 |
| `node_type` | GROUP BY + COUNT | 节点类型分布 |
| `deadline` | WHERE < 当日+7天 AND status='IN_PROGRESS' | 即将到期节点 |
| `updated_at` | WHERE 当日有变更 | 进度变化节点 |

### 3.3 硬规则异常检测（不依赖 LLM）

在 LLM 总结之前，先用确定性逻辑检测异常信号：

| 异常标识 | 检测规则 | 严重度 |
|---------|---------|-------|
| `high_fallback` | fallback 率 > 30% | 🔴 高 |
| `sop_correction_spike` | 单 SOP 纠正信号 > 3 次/天 | 🔴 高 |
| `low_rag_hit` | RAG 零命中率 > 50% | 🟡 中 |
| `slow_pipeline` | Pipeline 平均耗时 > 10s | 🟡 中 |
| `volume_anomaly` | 消息量同比前日 ±50% | 🟡 中 |
| `tool_failure` | 单工具失败率 > 20% | 🔴 高 |
| `iteration_overflow` | max_iterations_reached > 3 次/天 | 🟡 中 |
| `node_overdue` | 存在 IN_PROGRESS 节点已过 deadline | 🔴 高 |

## 分析指引

1. **路由质量**：重点关注 Fallback 消息——它们代表 Emily 无法理解的用户意图。分析是否存在可归纳的同义词模式（如"帮我查"都未命中 SOP-005）
2. **执行质量**：关注 FAILED/ABORTED 的 Pipeline 执行——它们代表系统处理失败。分析失败是否有共性
3. **用户体验**：关注 explicit_correction 信号——用户说"不对"、"搞错了"代表 Emily 的回复出了问题。分析纠正集中在哪些 SOP
4. **知识库覆盖**：关注 RAG 零命中查询——它们代表用户问了知识库里没有的内容。分析是否需要补充知识
5. **节点推进**：关注节点进度变化——哪些在正常推进、哪些停滞、哪些有逾期风险
6. **模式发现**：寻找跨日可能复现的规律（如某 SOP 总在特定时段出错、某用户总用特定表述触发 fallback）
7. **健康评分**：综合 SOP 命中率、Fallback 率、纠正率、节点推进速度打分（0-100）
```

## 归纳指引

1. **只归纳跨日复现的模式**：单日出现的异常不算规律，至少在 2 个不同日期出现才纳入
2. **置信度计算**：出现天数 / 分析周期天数（如 5天出现 / 7天周期 = 0.71）
3. **每个规则必须有具体证据**：引用具体的日期、指标数值，不要笼统描述
4. **suggested_action 必须可操作**：不能写"优化路由"，要写"在 session.md 路由规则中增加：'帮我查'/'查一下'/'看看' → SOP-005 映射"
5. **区分业务规律和系统问题**：
   - 业务规律："周三查询请求比平时高40%" → 记录观察，指导资源分配

6. **不要过度归纳**：相关不等于因果，低置信度的规则也要如实标注
```

## 五、补丁生成器（Evolution Patch）— 详细设计

### 5.1 触发方式

- 规则归纳完成后，对 CONFIRMED 状态的 Rule 自动触发补丁生成
- 手动触发：`POST /api/v1/evolution/patches/generate?rule_no=R-003`

### 5.2 LLM 补丁生成 Prompt

保存位置：`emily-data/prompts/evolution_patch.md`

```markdown
<!-- evolution_patch.md — 进化补丁生成 Prompt -->
<!-- 输入变量: {rule_no}, {rule_title}, {rule_description}, {rule_category},
     {rule_suggested_action}, {current_target_content}, {target_path} -->

你是 Emily 系统的进化补丁生成器。你需要根据进化规则，生成一个具体的配置文件变更补丁。

## 来源规则
- 编号：{rule_no}
- 标题：{rule_title}
- 描述：{rule_description}
- 类别：{rule_category}
- 建议动作：{rule_suggested_action}

## 目标文件
- 路径：{target_path}
- 当前内容：
```
{current_target_content}
```

---

## 输出要求

请严格按照以下 JSON 格式输出：

```json
{
  "patch_type": "append|replace_section|insert_after",
  "target_path": "相对 emily-data/ 的文件路径",
  "search_anchor": "替换/插入时的定位锚点（如 ## 路由规则）",
  "patch_content": "要插入/替换的具体内容",
  "risk_level": "low|medium|high",
  "risk_reasoning": "风险等级判定理由",
  "expected_effect": "预期效果描述",
  "validation_criteria": "如何验证补丁是否生效（具体指标和阈值）"
}
```

## 生成指引

1. **append**：在指定段落末尾追加内容（如同义词映射追加到路由规则段末尾）
2. **replace_section**：替换某个 ## 标题下的完整段落（如修改确认策略描述）
3. **insert_after**：在指定锚点后插入新内容（如在 SOP 某步骤后插入新步骤）
4. **风险等级判定**：
   - low：只增加不修改（追加同义词、追加备注），不影响已有行为
   - medium：修改已有逻辑（修改确认策略、调整步骤顺序），可能影响部分用户
   - high：修改核心路由规则或权限相关逻辑，影响全体用户
5. **patch_content 必须是可直接写入文件的完整文本片段**，不要用省略号
6. **validation_criteria 必须具体**：如"7天内 SOP-002 纠正率从 15% 降至 10% 以下"
7. **不要修改代码文件**：只能修改 emily-data/ 下的配置/Prompt/SOP/Skill 文件
```

## 六、补丁审批与应用

### 6.1 审批流程（全部人工）

1. 补丁生成后状态为 **DRAFT**
2. 次日晨报推送待审批补丁列表给管理员
3. 管理员审批方式：
   - API：`POST /api/v1/evolution/patches/{id}/approve`
   - QQ 回复："审批通过 EP-001"
4. 审批后 PatchApplier 执行：
   a. 读取目标文件当前内容 → 保存为 `rollback_snapshot`
   b. 应用 patch_content（append/replace_section/insert_after）
   c. 触发热重载（SkillRegistry.reload() / HookConfig reload）
   d. 状态 → **APPLIED**
5. 管理员可拒绝：`POST /api/v1/evolution/patches/{id}/reject`，状态 → **REJECTED**

### 6.2 效果验证（7 天后自动）

- 每日 08:00，PatchValidator 检查已应用 ≥ 7 天的 Patch
- 对比应用前后关键指标（根据 validation_criteria 中定义的标准）
- 结果判定：
  - **CONFIRMED**：指标改善或无显著恶化
  - **ROLLED_BACK**：指标显著恶化 → 自动回滚（用 rollback_snapshot 恢复原始内容）

## 七、晨报模块 — 详细设计

### 7.1 触发方式

- 调度器每日 07:30 自动触发（`generate_morning_report` 作业）

### 7.2 输入数据源

| 数据源 | 表 | 查询内容 |
|-------|-----|---------|
| 用户负责节点 | `project_nodes` | WHERE responsible_user_id = 用户ID AND status = 'IN_PROGRESS' |
| 节点进度变化 | `project_nodes` | WHERE updated_at 在昨日范围内 AND responsible_user_id = 用户ID |
| 待办任务 | `tasks` | WHERE assignee_id = 用户ID AND status IN ('WAITING','SUBMITTED','RETURNED') |
| 昨日动态 | `business_event_logs` | WHERE user_id = 用户ID AND created_at 在昨日范围内 |
| 截止临近 | `project_nodes` | WHERE deadline < 当日+7天 AND status = 'IN_PROGRESS' AND responsible_user_id = 用户ID |
| 进化摘要 | `evolution_daily_insights` | 昨日洞察（仅管理员可见） |
| 待审批补丁 | `evolution_patches` | WHERE status = 'DRAFT'（仅管理员可见） |

### 7.3 晨报生成逻辑

1. 查询所有 active 用户
2. 对每个用户按其负责内容组装数据
3. 生成个性化晨报

### 7.4 晨报模板

```

{end}

📌 待办任务
{for each pending task}
{紧急度图标} {任务标题} — {截止提示}
{end}

📊 昨日动态
{for each recent event}
{事件描述}
{end}

⚠️ 注意
{for each overdue/upcoming node}
{风险提示}
{end}

{收尾语：根据紧急任务数动态生成}
```

进度图标规则：
- 🟢 进度 ≥ 70% 或 进度上升
- 🟡 进度 30%-70%
- ⚪ 进度 < 30% 或 待启动

紧急度图标规则：
- 🔴 截止 ≤ 1天
- 🟡 截止 ≤ 3天
- 🟢 截止 > 3天

管理员额外内容：

```

### 7.5 晨报导送方式

- 通过 QQ 群/私聊推送给对应用户
- 管理员额外收到系统进化摘要
