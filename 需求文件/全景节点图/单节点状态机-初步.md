# 地产项目全景节点 - 单节点状态机标准框架

## 一、设计原则

### 1.1 设计理念
- **行业适配**：针对地产开发全生命周期特征，覆盖报建、设计、施工、采购、营销、交付六大线条
- **责任清晰**：明确各角色在节点中的权责边界，符合地产行业矩阵式管理模式
- **风险可控**：内置风险预警机制，关键节点设置强制卡点
- **数据穿透**：支持从集团→项目→节点的逐级穿透查询

### 1.2 适用范围
本框架适用于地产项目全景节点管理系统中的所有节点类型：
- 规划设计类节点
- 工程施工类节点
- 采购招采类节点
- 开发报建类节点
- 营销策划类节点
- 交付入伙类节点

## 三、节点状态机设计

### 3.1 状态定义

| 状态编码 | 状态名称 | 状态描述 | 颜色标识 |
|---------|---------|---------|---------|
| DRAFT | 草稿态 | 节点信息录入中，未正式发布 | 灰色 #9e9e9e |
| PENDING | 待启动 | 节点已配置完成，等待前置条件满足 | 蓝色 #2196f3 |
| READY | 可启动 | 前置条件全部满足，可启动 | 浅蓝色 #03a9f4 |
| RUNNING | 进行中 | 节点正在执行中 | 黄色 #ffc107 |
| DELAYED | 已延误 | 超过计划完成时间但未完成 | 橙色 #ff9800 |
| REVIEWING | 审核中 | 成果提交，正在审核确认 | 紫色 #9c27b0 |
| COMPLETED | 已完成 | 节点成果通过审核，正式完成 | 绿色 #4caf50 |
| SUSPENDED | 已暂停 | 节点执行被暂停 | 深灰 #607d8b |
| CANCELLED | 已取消 | 节点被取消，不再执行 | 红色 #f44336 |

### 3.2 状态流转规则

```
状态流转图：

  草稿态 → 待启动 → 可启动 → 进行中 → 审核中 → 已完成
                       ↓        ↓
                     已暂停    已延误
                       ↓
                     已取消

流转规则说明：
1. DRAFT → PENDING：节点信息完整，提交审批后自动流转
2. PENDING → READY：前置条件满足度达到100%
3. READY → RUNNING：责任主体点击"启动节点"，需上传启动确认单
4. RUNNING → DELAYED：系统自动判断（当前时间>计划完成时间且状态=RUNNING）
5. RUNNING → REVIEWING：执行方提交成果，触发审核流程
6. REVIEWING → RUNNING：审核不通过，退回修改
7. REVIEWING → COMPLETED：审核通过，节点完成
8. 任意状态 → SUSPENDED：触发暂停条件（如项目暂停）
9. SUSPENDED → 原状态：暂停解除
10. 任意状态 → CANCELLED：节点废弃（需审批）
```

### 3.3 状态触发条件

#### 【待启动 → 可启动】前置条件校验
前置条件类型：
- **节点依赖**：某前置节点必须已完成（如"施工图完成"是"施工招标"的前置）
- **文档依赖**：必须上传某些指定文档（如"国土证"是"规划报建"的前置）
- **审批依赖**：某个审批流程必须通过（如"项目定位会通过"是"方案设计"的前置）
- **时间依赖**：必须到指定日期后才能启动

前置条件满足度计算：
```
满足度 = (已满足条件数 / 总条件数) * 100%
- 满足度 < 100%：不可启动，显示具体缺失项
- 满足度 = 100%：状态自动变为"可启动"
```

## 四、节点交付成果管理

### 4.1 成果标准清单（模板化配置）

| 成果编码 | 成果名称 | 成果类型 | 必填 | 审核要求 | 归档要求 |
|---------|---------|---------|------|---------|---------|
| DOC-001 | 设计说明 | Word/PDF | 是 | 需成本部审核 | 永久归档 |
| DOC-002 | 总平面图 | CAD/PDF | 是 | 需开发部审核 | 永久归档 |
| DOC-003 | 效果图 | JPG/PPT | 否 | 需营销部审核 | 长期归档 |
| DOC-004 | 政府批复 | PDF扫描件 | 是 | 需开发部确认 | 永久归档 |

### 4.2 成果审核流程
```
提交成果 → 发起方自检 → 责任部门初审 → 相关部门会签 → 分管领导终审
         ↓          ↓          ↓          ↓          ↓
       自动校验   完整性审核   符合性审核   跨专业审核   最终确认
```

### 4.3 成果版本管理
- 每次成果提交生成新版本号（V1.0, V1.1, V2.0...）
- 保留所有历史版本，支持版本对比
- 只有最终通过版标记为"正式版"

## 六、操作日志与审计

### 6.1 操作日志记录

| 操作类型 | 记录内容 | 记录时机 |
|---------|---------|---------|
| 状态变更 | 原状态→新状态、变更原因、操作人、时间 | 每次状态变化 |
| 信息修改 | 修改字段、原值、新值、修改人、时间 | 每次字段修改 |
| 成果上传 | 文件名、版本、上传人、时间 | 每次上传 |
| 审批操作 | 审批人、审批意见、审批结果、时间 | 每次审批 |
| 异常操作 | 异常类型、异常描述、触发条件 | 异常发生时 |

### 6.2 审计追踪要求
- 所有操作不可删除、不可修改
- 支持按操作人、时间段、操作类型筛选查询
- 关键操作需短信/邮件通知相关干系人

## 七、节点预警机制

### 7.1 预警规则配置

| 预警类型 | 触发条件 | 预警级别 | 通知对象 | 处理要求 |
|---------|---------|---------|---------|---------|
| 进度预警 | 当前完成率 < 计划完成率的80% | 黄色预警 | 节点负责人 | 3天内回复应对措施 |
| 进度预警 | 当前完成率 < 计划完成率的60% | 红色预警 | 部门负责人 | 每周汇报进展 |
| 节点延误 | 超过计划完成时间 | 红色预警 | 分管领导 | 启动专项跟进 |
| 成果预警 | 成果审核不通过超过2次 | 黄色预警 | 双方负责人 | 组织专题会议 |
| 风险预警 | 高风险项未在7天内处理 | 红色预警 | 风控部门 | 介入协调 |

### 7.2 预警通知方式
- 系统消息
- 企业微信/钉钉通知
- 短信（红色预警）
- 邮件（周度汇总）

## 八、绩效考核指标

| 指标名称 | 计算公式 | 考核对象 |
|---------|---------|---------|
| 节点按时完成率 | 按时完成节点数 / 应完成节点数 * 100% | 责任部门、责任人 |
| 节点工期偏差率 | （实际工期-计划工期）/计划工期 * 100% | 执行单位 |
| 成果一次通过率 | 一次审核通过成果数 / 总提交成果数 * 100% | 执行单位 |
| 前置条件满足率 | 按期满足的前置条件数 / 总前置条件数 * 100% | 相关责任部门 |

## 附：节点状态机配置示例

```yaml
# 示例：建筑方案设计节点配置
nodeCode: SJ-JZ
nodeName: 建筑方案设计

nodeLevel: 二级节点
nodeType: 关键节点

responsibleDept: 设计管理部
responsiblePerson: 张三

# 前置条件
preConditions:
  - type: node
    dependNode: GH-XMWJH
    dependNodeName: 项目定位会
    required: true
  - type: document
    docType: 国土证
    required: true

# 交付成果标准
deliverables:
  - code: DOC-001
    name: 方案设计说明
    type: PDF
    required: true
    reviewFlow: [成本部, 开发部]
  - code: DOC-002
    name: 总平面图
    type: CAD+PDF
    required: true
    reviewFlow: [开发部, 工程部]

# 预警规则
alertRules:
  - type: progress
    threshold: 80
    level: yellow
    notify: [节点负责人]
  - type: progress
    threshold: 60
    level: red
    notify: [部门负责人, 分管领导]
```
