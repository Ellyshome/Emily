# 地产项目全景节点 — 单节点状态机建议框架

> **文档定位**：本文档是单节点状态机的**设计级建议框架**，面向系统架构设计与数据库建模阶段。
> 以资深地产行业职业经理人视角，结合地产开发全生命周期真实管控逻辑撰写。
> 当前系统已实现 5 态 NodeStatus（NOT_STARTED / IN_PROGRESS / BLOCKED / DELAYED / COMPLETED），
> 本文档在此基础之上提出 **7 态扩展方案** 及配套的行业化增强设计。
>
> **前置阅读**：[全景节点规则.md](./全景节点规则.md)（节点编码与阶段划分）、[单节点结构-手写需求.md](./单节点结构-手写需求.md)（原始需求）
>
> **适用阶段**：设计 → 施工 → 交付（当前工程一期聚焦设计+施工两阶段，规划/交付各仅一个端点节点）

## 一、行业背景与管理诉求

### 1.1 地产开发为什么需要节点状态机

地产开发区别于普通项目管理的6个根本特征：

| # | 行业特征 | 对状态机的设计要求 |
|---|---------|------------------|
| 1 | **多利益主体博弈**：建设单位、承包单位、政府部门、监理、审计——至少5方视角 | 状态变更必须区分"谁发起"与"谁确认"，不能仅靠单一角色推进 |
| 2 | **报建驱动进度**：政府审批节点是硬瓶颈，且审批时间不可控 | 报建类节点需"等待外部回复"逻辑，不能全靠内部完成率衡量 |
| 3 | **三边工程常态**：边设计、边施工、边报建的并行推进 | 节点前置条件必须支持 SOFT（建议满足）与 HARD（必须满足）分级 |
| 4 | **样板引路制度**：施工前必须先做样板，样板通过后方可大面积展开 | 施工类节点必须有"样板确认"里程碑，不能直接从"进行中"跳到"已完成" |
| 5 | **停止点检查**：关键节点完成后，必须由监理/甲方联合检查方可进入下一节点 | "已完成"不是执行方说了算——需经"待审核"中间态 |
| 6 | **进度款与节点绑定**：工程付款通常按节点完成比例支付 | 节点完成状态直接触发财务付款条件，状态变更需高审计要求 |

### 1.2 节点管理的5大核心诉求

```
进度穿透 ── 从集团→区域→项目→单节点，逐级下钻，任何一级都能看到真实进展
责任锁定 ── 每个节点有且仅有一个 Accountable（最终负责方），不可推诿
成果可追溯 ── 每个节点产出什么、谁审核的、哪个版本是最终版，全链路留痕
风险可预警 ── 不是"已经延期了才报警"，而是"偏离基准计划的趋势阶段"就预警
决策有依据 ── 所有状态变更必须附带原因与附件，不可仅"口头确认"
```

### 1.3 框架适用范围

本框架覆盖地产全景节点图中的 **6 大类节点**：

| 节点大类 | 编码前缀 | 典型节点示例 | 状态机特殊要求 |
|---------|---------|-------------|--------------|
| 规划设计 | SJ-* | 建筑方案设计、施工图完成、景观方案评审 | 强依赖前置文档（条件图），多轮评审 |
| 工程施工 | SG-* | 主体结构封顶、外檐完工、精装湿作业完成 | 样板引路、停止点检查、巡检记录绑定 |
| 开发报建 | （预留） | 建设工程规划许可证、施工许可证 | 外部审批时间不可控，需"等待政府回复"子态 |
| 采购招采 | （预留） | 总包定标、精装单位定标 | 定标→合同签订两阶段，关联成本科目 |
| 营销策划 | （预留） | 开盘、交房 | 强时间窗口约束 |
| 交付入伙 | JF | 竣工验收交付 | 当前仅一个端点节点 |

> **当前工程一期聚焦**：SJ-*（设计）与 SG-*（施工）两大类的节点。

### 1.4 管控级别矩阵

不同节点在集团管控体系中的定位不同，直接影响预警升级路径和审批权限：

| 管控级别 | 定义 | 状态变更审批人 | 预警通知范围 | 节点类型示例 |
|---------|------|--------------|-------------|-------------|
| **集团控** | 影响项目整体里程碑的关键节点 | 集团分管副总裁 | 集团+区域+项目三级 | 施工许可证取得、主体结构封顶、竣工备案 |

| **项目控** | 项目内部管控节点 | 项目总 | 项目内部 | 单项深化设计完成、月度巡检 |

### 2.2 责任矩阵（RACI-V 增强模型）

地产行业区别于标准 RACI 的关键在于：**Verifier（验证方）**——监理/第三方检测机构独立验证，
这是行业特有的多方制衡机制。

| 角色 | 缩写 | 地产语境含义 | 配员规则 |
|------|------|-------------|---------|
| **执行方** | R | 具体完成工作的单位/人（承包单位项目经理） | 必须是外键→企业表，不能为空 |
| **最终负责方** | A | 建设单位节点负责人（甲方项目/设计/工程经理） | **有且仅有一人**，不可多人共担 |
| **咨询方** | C | 需要提供专业意见的部门/单位（成本部、开发部、设计顾问） | 可多个，需标注咨询事项 |
| **告知方** | I | 需要知晓结果的部门/单位（物业前介、营销、客服） | 可多个，成果抄送即可 |
| **验证方** | V | 独立验证工作成果的第三方（监理公司、检测机构、政府质监站） | 施工类节点必填，设计类节点可选 |

### 2.3 时间计划管理（双轨制）

地产项目计划频繁调整是常态。需要 **基准计划（Baseline）** 与 **滚动预测（Forecast）** 双轨并行：

> **基准计划**：经审批的正式计划版本，是绩效考核的依据，变更需走计划变更审批流。
> **滚动预测**：基于当前实际进展的最新估计，可频繁更新，不做为考核依据。

| 字段 | 类型 | 说明 | 当前系统映射 |
|------|------|------|-------------|
| base_start_date | Date | 基准计划启动日期（审批后锁定） | `planned_start_date` |
| base_end_date | Date | 基准计划完成日期（审批后锁定） | `planned_end_date` |
| base_duration_days | Int | 基准计划工期（工作日，自动计算） | **新增** |
| base_version | Int | 基准版本号（每次正式调整 +1） | **新增** |
| forecast_start_date | Date | 滚动预测启动日期（随时可更新） | **新增** |
| forecast_end_date | Date | 滚动预测完成日期 | **新增** |
| actual_start_date | DateTime | 状态变为 IN_PROGRESS 的精确时间 | `actual_start_date` |
| actual_end_date | DateTime | 状态变为 COMPLETED 的精确时间 | `actual_end_date` |
| duration_deviation_pct | Decimal | 工期偏差率 = (实际工期-基准工期)/基准工期×100% | **新增** |

**基准调整审批规则**：

| 调整幅度 | 审批层级 | 是否需要说明原因 |
|---------|---------|----------------|
| < 5天 | 项目总 | 备注原因即可 |
| 5-15天 | 区域总 | 需附说明报告 |
| > 15天 | 集团分管副总裁 | 需附专项分析报告 |

### 2.4 节点健康度综合评分

单一维度（进度）不足以反映节点真实状态。建议引入 **四维加权健康度**：

```
节点健康度 = P × 40% + C × 25% + Q × 25% + S × 10%

其中：
  P (Progress)：计划完成率 = 已消耗工期内的实际完成量 / 计划应完成量 × 100%
  C (Cost)：成本偏差率 = 1 - |(已发生成本 - 目标成本) / 目标成本|
  Q (Quality)：质量得分 = (一次验收通过次数 / 总验收次数) × 100%
  S (Safety)：安全得分 = 100 - 隐患未整改数 × 20（最低为 0）
```

| 健康度区间 | 颜色标识 | 含义 |
|-----------|---------|------|
| ≥ 90 | 绿色 | 健康，无需干预 |
| 75-89 | 黄色 | 关注，节点负责人自查 |
| 60-74 | 橙色 | 预警，项目总介入 |
| < 60 | 红色 | 危险，升级至区域/集团 |

## 三、状态机核心设计

### 3.1 状态定义（7 态）

在当前 5 态基础上，拆分为更精准的 7 态。核心设计决策：
- "未启动"拆分出"已就绪"——前置条件满足了就该看得见，不能藏在"未启动"里
- 增加"待审核"——已完成工作是执行方自评，要经过审核才进入真正的"已完成"
- "已阻塞"与"已冻结"区分——前者有解除路径，后者是终结态

| # | 状态编码 | 状态名称 | 描述 | 颜色 | 当前系统映射 |
|---|---------|---------|------|------|-------------|
| 1 | `NOT_STARTED` | 未启动 | 节点已创建，前置条件不满足，不可启动 | 灰 #9E9E9E | ✓ 现有 |
| 2 | `READY` | 已就绪 | 前置条件全部满足，等待责任主体启动 | 蓝 #2196F3 | **新增** |
| 3 | `IN_PROGRESS` | 进行中 | 节点执行中 | 黄 #FFC107 | ✓ 现有 |
| 4 | `REVIEWING` | 待审核 | 执行方提交成果，等待审核方确认 | 紫 #9C27B0 | **新增** |
| 5 | `COMPLETED` | 已完成 | 成果审核通过，节点正式闭环 | 绿 #4CAF50 | ✓ 现有 |
| 6 | `BLOCKED` | 已阻塞 | 因障碍物无法推进，有明确阻塞原因和解除路径 | 橙 #FF9800 | ✓ 现有 |
| 7 | `FROZEN` | 已冻结 | 节点被终止（取消/暂停），不再作为活跃节点 | 红 #F44336 | **新增**（合并 SUSPENDED+CANCELLED） |

### 3.2 状态转移矩阵（7×7）

下表中：**A** = 自动流转（系统判断条件触发），**M** = 手动操作（需审批），**—** = 禁止流转

| 从 \ 到 | NOT_STARTED | READY | IN_PROGRESS | REVIEWING | COMPLETED | BLOCKED | FROZEN |
|---------|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| **NOT_STARTED** | — | **A** 前置条件100%满足 | — | — | — | — | M 需审批 |
| **READY** | A 前置条件降级 | — | **M** 责任主体启动 | — | — | — | M 需审批 |
| **IN_PROGRESS** | — | — | — | **M** 执行方提交成果 | M 简化节点直完 | **M** 遇障碍暂停 | M 需审批 |
| **REVIEWING** | — | — | **M** 审核退回修改 | — | **M** 审核通过 | — | M 需审批 |
| **COMPLETED** | — | — | — | — | — | — | — |
| **BLOCKED** | — | — | **M** 阻塞解除恢复 | — | — | — | M 需审批 |
| **FROZEN** | — | M 解冻→回到原状态 | M 解冻→回到原状态 | — | — | — | — |

> COMPLETED 是**不可逆的终态**——一旦完成，不再接受任何状态变更。如需修改，走"成果变更"流程创建新节点版本，而非回退已完成节点的状态。

### 3.3 状态流转判定逻辑（伪代码）

```python
def evaluate_state_transition(node: SMNode) -> StateChange | None:
    """每个 tick 评估节点应发生的自动状态变更。"""

    # Rule 1: NOT_STARTED → READY（前置条件100%满足）
    if node.status == "NOT_STARTED":
        score = evaluate_preconditions(node.node_id)
        if score.hard_score == 100 and score.soft_score >= 80:
            return StateChange(to="READY", trigger="precondition_met", auto=True)

    # Rule 2: READY → NOT_STARTED（前置条件降级——如依赖节点被回退）
    if node.status == "READY":
        score = evaluate_preconditions(node.node_id)
        if score.hard_score < 100:
            return StateChange(to="NOT_STARTED", trigger="precondition_lost", auto=True)

    # Rule 3: IN_PROGRESS → BLOCKED（计划到期自动标记延期，不再直接转 DELAYED）
    if node.status == "IN_PROGRESS":
        if date.today() > node.base_end_date:
            return StateChange(to="BLOCKED", trigger="past_deadline", auto=True,
                               reason=f"超过计划完成日期 {node.base_end_date}")

    # Rule 4: BLOCKED → IN_PROGRESS（阻塞原因解除 + 再次启动）
    # 需手动操作，不由系统自动判断

    # No automatic transition otherwise
    return None
```

### 3.4 按节点类型的差异化流转

不同节点类型的"进行中→待审核"路径有细微差异，体现地产行业真实工作流：

#### 3.4.1 施工类节点（SG-*）

```
IN_PROGRESS → [样板确认] → [停止点检查] → REVIEWING → COMPLETED
                  ↓                ↓
              样板不通过          停止点不通过
              → 整改→重验        → 整改→重验
```

- **样板确认**：样板通过后方可大面积施工。样板不通过→记录问题→整改→复验，但不改变主状态
- **停止点检查**：甲方/监理联合检查，通过后方可进入下一节点。这在"IN_PROGRESS→REVIEWING"前触发

#### 3.4.2 设计类节点（SJ-*）

```
IN_PROGRESS → [方案阶段评审] → [图纸审查] → REVIEWING → COMPLETED
                   ↓                ↓
              方案不通过          图纸不通过
              → 退回修改         → 退回修改
```

- 设计类节点的"成果"通常是图纸或方案文本，审核链为：自检→专业审核→跨专业会签→（政府图审，部分节点）
- "方案评审"与"图纸审查"是行业惯用的两个里程碑，可在节点内以子状态记录，不改变主状态

#### 3.4.3 报建类节点（预留）

```
IN_PROGRESS → [资料递交] → [政府部门受理中] → [取得批复] → COMPLETED
                   ↓              ↓
               资料不全        超时未回复
               → 补正          → 升级催办
```

- "政府部门受理中"是外部依赖，时间不可控。系统需标记"等待中"天数，超过行业惯例阈值自动升级

### 3.5 前置条件模型

#### 3.5.1 5 类前置条件

| 条件类型 | 说明 | 地产行业示例 | 判定方式 |
|---------|------|-------------|---------|
| **节点依赖** | 某前置节点必须达到指定状态 | SG-JG（景观工程）依赖 SJ-JG（景观设计）为 COMPLETED | 系统自动查询依赖节点状态 |
| **文档就绪** | 必须收到/上传指定文档 | 施工招标依赖"施工图审查合格书"已上传 | 系统查询文档库 |
| **审批通过** | 某审批流程必须已完成 | 建筑方案设计依赖"项目定位会"会议纪要确认 | 对接审批流系统 |
| **资源到位** | 人机料法环5要素齐备 | 总包进场依赖"三通一平"完成 + 施工许可证取得 | 人：责任人已指派；机：设备已进场；料：甲供材已到货；法：施工方案已审批；环：现场条件具备 |
| **时间窗口** | 必须到指定时间/季节后才能启动 | 景观种植依赖春季合适季节；开盘依赖预售证取得日期 | 系统比较当前日期与目标日期 |

#### 3.5.2 条件组合逻辑

```yaml
preconditions:
  logic: AND  # AND | OR | CUSTOM
  items:
    - type: node_dependency
      target: SJ-JZ
      required_status: COMPLETED
      hard: true          # HARD: 必须100%满足
      weight: 1.0

    - type: document_ready
      target_doc: "施工图审查合格书"
      hard: true
      weight: 1.0

    - type: document_ready
      target_doc: "地质勘察报告"
      hard: true
      weight: 1.0

    - type: resource_ready
      resource_type: "material"
      description: "首批钢材到场"
      hard: false         # SOFT: 建议满足，不强制卡住
      weight: 0.3

    - type: approval_passed
      approval_name: "施工组织设计审批"
      hard: true
      weight: 1.0
```

#### 3.5.3 满足度计算

```
Hard 满足度 = (已满足的 HARD 条件数 / 总 HARD 条件数) × 100%
  → Hard 满足度 = 100% 时，节点才能进入 READY

Soft 满足度 = (已满足的 SOFT 条件加权得分 / 总 SOFT 条件加权得分) × 100%
  → Soft 满足度 ≥ 80% 时，视为"建议已基本满足"
  → Soft 满足度 < 80%：可在启动时显示警告但不阻断

综合满足度 = Hard 满足度 × 0.7 + Soft 满足度 × 0.3
  → 用于节点健康度评分，不用于阻断逻辑
```

## 五、四维联动管理

### 5.1 进度 — S 曲线与挣值分析

地产工程管理常用 **挣值法（EVM）** 评估节点真实进展：

| 指标 | 公式 | 含义 |
|------|------|------|
| PV（计划价值） | 按基准计划此时应完成的工作量 × 预算单价 | 计划值 |
| EV（挣值） | 实际完成的工作量 × 预算单价 | 挣值 |
| AC（实际成本） | 实际发生的成本 | 实际成本 |
| SV（进度偏差） | EV - PV | > 0 表示提前，< 0 表示滞后 |
| SPI（进度绩效指数） | EV / PV | > 1 表示提前，< 0.8 表示严重滞后需预警 |

> 将挣值分析下沉到单节点层面，可实现从"宏观里程碑管理"到"微观节点挣值"的穿透。

### 5.2 成本 — WBS 科目三栏对比

每个节点对应成本系统中的 WBS（工作分解结构）科目：

| 成本项 | 目标成本 | 已发生成本 | 预估结算 | 偏差率 | 预警阈值 |
|--------|---------|-----------|---------|--------|---------|
| 节点对应合同金额 | 合同签约价 | 累计产值 | 预计结算价 | > 103% 橙色, > 105% 红色 |
| 节点关联变更签证 | 0 | 累计变更额 | 预计变更额 | > 签约价 3% 预警 |
| 节点甲供材成本 | 预算量×单价 | 已领用量×单价 | 预计用量×单价 | > 5% 预警 |

### 5.3 质量 — 一次验收通过率

施工类节点的关键质量指标：

| 指标 | 计算方式 | 行业基准值 | 预警值 |
|------|---------|-----------|--------|
| 一次验收通过率 | 一次通过次数 / 总验收次数 × 100% | ≥ 85% | < 70% 橙色, < 50% 红色 |
| 整改闭环率 | 已闭环整改项 / 总整改项 × 100% | 100% | < 95% 红色 |
| 巡检得分 | 最近一次甲方/监理巡检评分 | ≥ 85 分 | < 70 分 红色 |

### 5.4 安全 — 综合评分

- 安全交底完成率（100% 为底线）
- 危险源识别覆盖率
- 隐患整改及时率
- 关联停工令数量与状态

## 七、预警与升级机制

### 7.1 三级预警体系

| 级别 | 名称 | 含义 | 自动触发条件（示例） | 通知对象 | 关闭条件 |
|------|------|------|--------------------|---------|---------|
| 🟡 | **黄色提醒** | 偏差刚出现，仍有时间纠正 | SPI < 0.9、距离计划完成日期还剩30%工期但完成率<50% | 节点负责人 | 回复处理措施即关闭 |
| 🟠 | **橙色预警** | 偏差持续，需要上级关注 | SPI < 0.8、超出计划完成日期、黄色预警7天未关闭 | 节点负责人 + 部门负责人 | 需上级确认处理方案 |
| 🔴 | **红色升级** | 偏差严重，将影响整体里程碑 | SPI < 0.6、超出计划完成日期>15天、橙色预警7天未关闭 | 节点负责人 + 部门负责人 + 分管领导 | 需分管领导确认 |

### 7.2 按管控级别的升级路径

```
                项目控节点              区域控节点            集团控节点
黄色提醒 → 节点负责人            → 节点负责人            → 节点负责人
   ↓ 7天未关闭
橙色预警 → 部门负责人            → 区域部门负责人         → 集团部门负责人
   ↓ 7天未关闭
红色升级 → 项目总                → 区域总经理             → 分管副总裁
   ↓ 7天未关闭
专项汇报 → PMO办公室             → 集团PMO               → 集团总裁办公会
```

### 7.3 预警自动计算示例

```python
def evaluate_alerts(node: SMNode) -> list[Alert]:
    alerts = []

    # 进度预警
    if node.status == "IN_PROGRESS":
        elapsed_pct = (today() - node.actual_start_date) / (node.base_end_date - node.base_start_date)
        completion_pct = node.actual_progress  # 需有进度上报机制
        spi = completion_pct / max(elapsed_pct, 0.01)

        if spi < 0.9:
            alerts.append(Alert(level="YELLOW", type="progress", detail=f"SPI={spi:.2f}"))
        if spi < 0.8:
            alerts.append(Alert(level="ORANGE", type="progress", detail=f"SPI={spi:.2f}"))
        if spi < 0.6:
            alerts.append(Alert(level="RED", type="progress", detail=f"SPI={spi:.2f}"))

    # 成本预警
    cost_deviation = (node.actual_cost - node.target_cost) / node.target_cost
    if cost_deviation > 0.03:
        alerts.append(Alert(level="ORANGE", type="cost", detail=f"成本偏差{cost_deviation:.1%}"))
    if cost_deviation > 0.05:
        alerts.append(Alert(level="RED", type="cost", detail=f"成本偏差{cost_deviation:.1%}"))

    # 质量预警
    if node.first_pass_rate < 0.7:
        alerts.append(Alert(level="ORANGE", type="quality", detail=f"一次通过率{node.first_pass_rate:.0%}"))
    if node.first_pass_rate < 0.5:
        alerts.append(Alert(level="RED", type="quality", detail=f"一次通过率{node.first_pass_rate:.0%}"))

    return alerts
```

## 八、操作日志与审计

### 8.1 地产行业特有的审计要求

| 操作类型 | 审计要求 | 当前系统映射 |
|---------|---------|-------------|
| 状态变更 | 记录 from→to、操作人、时间、原因、附件 | `sm_status_history` ✓ 已实现 |
| 信息修改 | 记录被修改字段、原值、新值、修改人、时间 | `sm_audit_logs` ✓ 已实现 |
| 成本变更 | **必须关联审批流编号**——成本>10万变更需双人确认 | 建议增强 |
| 设计变更 | **必须关联洽商/变更记录编号**——设计变更与洽商是一对一关系 | 建议新增 |
| 工期调整 | **基准计划变更需走审批流**——>7天延期需区域审批 | 建议增强 |
| 成果提交 | 记录文件名、版本、提交人、时间、审核人、审核意见 | `sm_node_deliverables` 可扩展 |

### 8.2 四眼原则（关键操作双人确认）

以下操作需要 **操作人 + 确认人** 双人方可生效：

| 操作 | 阈值 | 需要确认人 |
|------|------|-----------|
| 节点成本调增 | > 10万元 | 成本部负责人 |
| 基准计划延期 | > 7天 | 项目总 |
| 节点状态设冻结 | 任意 | 部门负责人 |
| 已完成节点回退 | 任意 | **禁止**（走成果变更流程） |

### 8.3 不可篡改设计

- 所有 `sm_status_history` 和 `sm_audit_logs` 记录 **仅追加（append-only）**，不支持 UPDATE/DELETE
- 对关键操作（成本变更、状态冻结）记录 hash 链：每条新记录包含上一条记录的 hash → 可检测是否被篡改
