## 一、架构概览

### 1.1 三级分层

```
脉络层 (Stage)     7 阶段宏观状态、进度百分比、里程碑标记
节点层 (Node)       ~115 节点、5 态状态机、依赖关系 DAG、成果物追踪
数据层 (Index)      数据库索引 + 文档索引 + 公共记忆库（阶段三实施）
```

### 1.2 与现有系统的关系

全局状态机是**独立新模块**，通过 EmilyCore 延迟初始化集成，不修改现有管道/会话/工作项逻辑。它是项目维度的状态管理，与现有消息级/会话级状态机分层共存：

| 层级 | 粒度 | 现有效能 |
|------|------|----------|
| 全局状态机 (新增) | 项目全生命周期 → 天/周/月 | **本次实施** |
| Session 状态机 | 对话生命周期 → 秒/分 | `session/session_state.py` — CREATED/ACTIVE/WAITING_CONFIRM/ARCHIVING/CLOSED |
| WorkItem 状态机 | 任务执行单元 → 毫秒/秒 | `workitem/workitem_state.py` — CREATED/PLANNING/EXECUTING/DONE/FAILED |
| PlanTask 状态机 | 计划任务实例 → 分钟/小时 | `services/plan_task_service.py` — 7 态（WAITING→SUBMITTED→CONFIRMED→ARCHIVED） |

### 1.3 代码模式遵循

完全遵循项目现有约定（参考源代码探索结果）：

| 模式 | 来源 | 说明 |

关键路径决定项目最短工期，是依赖图中最长的串行链路：

```
1.1 → 1.2 → 1.4 → 1.5 → 1.6 → 1.7
  → 3.1(跨阶段) → 1.8
    → 2.1.1 → 2.1.2 → 2.1.3 → 2.1.4
      → 2.2.5a(景观方案 — 专业中最高等的路线) → 2.2.5b

            → 5.1.1(等待 4.14 平行链)
              → 5.1.2 → 5.1.3 → 5.1.4 → 5.2.1 → 5.2.2 → 5.2.3 → 5.5.1 → 5.7.1
                → 5.12.8 → 5.12.9
                  → 6.7 → 6.8 → 6.16 → 6.17 → 6.19
                    → 7.5 → 7.6 → 7.7 → 7.9
```

### 2.4 跨阶段依赖

阶段存在"回边"——阶段三节点 3.1（勘测定界）依赖阶段一节点 1.7，完成后**回馈到阶段一**节点 1.8。这不是循环，而是合法的 DAG 汇聚。数据模型必须允许多阶段重叠。

### 2.5 特殊模式

**a/b 配对**（8 对 16 节点）
每个专业有 `方案(a)` 和 `施工图(b)` 两个子节点，严格顺序 a→b。全部 8 个 b 节点完成后，2.1.5（建筑施工图设计）方可启动。方案：存储 `pair_group_id` + `phase_order` 关联配对节点。

**循环节点**（5 个节点触发多次，非单次完成）
- 5.12.2 隐蔽工程验收 → 每结构子阶段触发 ~3-5 次
- 5.12.3 分部分项工程验收 → 每子阶段触发 ~10-14 次
- 5.12.4 材料设备进场检验 → 每材料批次触发 ~50-200 次
- 5.12.6 工程进度款审核支付 → 月度 ~12-36 次
- 5.12.7 施工现场安全文明检查 → 持续性 ~50-100+ 次

方案：添加 `recurrence_type` 字段（SINGLE / PER_SUB_PHASE / PERIODIC / PER_EVENT）和 `recurrence_completed_count`。

**外部触发节点**（2 个完全由外部发起）
1.1（地块意向达成——商业决策）、5.12.5（变更令——开发商工程部单独签发）。方案：暴露 `forceActivateNode(nodeId, reason)` API，带审计日志绕过依赖检查。

**里程碑节点**（10 个阶段边界标记）
1.8, 2.1.6, 3.4, 3.5, 3.8, 4.14, 5.12.8, 6.19, 7.6, 7.8。方案：`is_milestone` 布尔标志 + 完成时触发阶段进度推送。

#### 3.3 状态机引擎

**NodeStatus** — 5 种标准状态（来自需求 §3.2）：

```python
class NodeStatus(Enum):
    NOT_STARTED = "NOT_STARTED"       # 未启动：前置条件不满足
    IN_PROGRESS = "IN_PROGRESS"       # 进行中：前置满足，正在执行
    BLOCKED = "BLOCKED"               # 已阻塞：遇到阻碍无法推进
    DELAYED = "DELAYED"               # 已延期：超过计划完成时间
    COMPLETED = "COMPLETED"           # 已完成：终态

TRANSITIONS = {
    NOT_STARTED:  [IN_PROGRESS],
    IN_PROGRESS:  [COMPLETED, BLOCKED, DELAYED],
    BLOCKED:      [IN_PROGRESS, DELAYED],
    DELAYED:      [IN_PROGRESS, COMPLETED],
    COMPLETED:    [],                  # 终态，禁止一切转移
}
TERMINAL_STATES = frozenset({COMPLETED})
```

### 阶段二：关联与联动 — 目标 2-4 天

#### 3.6 前置条件满足度公式

来自需求 §4.3：

```
满足度 = Σ(前置节点状态系数 × 依赖权重)

状态系数：
  COMPLETED           = 1.0
  IN_PROGRESS(>80%)   = 0.8（弱依赖可提前启动）
  IN_PROGRESS(≤80%)   = 0.5
  BLOCKED / DELAYED   = 0
  NOT_STARTED         = 0

强依赖约束：
  任何强依赖(required=True)非 COMPLETED → 满足度上限 99%（禁止启动）
```

**实现**：`StateMachineService.calculate_precondition_score(node_id)` —— 遍历 `sm_node_dependencies` 中 `from_node_id=node_id` 的行 → 查每个 `to_node_id` 的状态 → 按公式求和。使用内存缓存 + 状态变更时失效（同 PermissionSnapshot 模式）。

#### 3.7 BFS 级联更新

需求 §5.3 规定。当节点 A 变更为 COMPLETED 时：

```
节点A COMPLETED
  → 查询所有 from_node_id=A 的下游节点（即 to_node_id 字段 = A 的 from_node_id）
  → 对每个下游重新计算 precondition_score
  → satisfied==100 且当前 NOT_STARTED → 自动变更为 IN_PROGRESS
  → 继续传播到下一层
  → 直到：无新节点变更 或 传播深度>5
```

**约束**：整个级联在**同一事务**中完成（失败全回滚）；传播深度上限 5（防无限循环）。

#### 3.8 钩子函数

遵循现有 `Hook` 基类模式（`workitem/pipeline/hook.py`）。每个状态变更触发：

| 钩子 | 触发时机 | 标准动作 |
|------|----------|----------|
| `on_enter_in_progress` | 进入 IN_PROGRESS | 通知责任人、记录实际开始时间、创建任务清单 |
| `on_enter_completed` | 进入 COMPLETED | 生成验收报告、级联更新下游满足度、更新阶段进度、检查里程碑 |
| `on_enter_blocked` | 进入 BLOCKED | 通知项目经理、暂停下游依赖、标记风险升级 |

#### 3.17 关键路径识别

DAG 最长路径算法（拓扑排序 + DP）：

```python
def compute_critical_path(dag, node_weights):
    # 1. 拓扑排序
    # 2. earliest_start = max(前驱 earliest_end + 前驱权重)
    # 3. latest_start 反推
    # 4. slack = latest_start - earliest_start
    # 5. slack == 0 → 关键路径
```

关键路径随状态变更动态变化。完成关键路径上的节点后触发实时重新计算。

#### 3.18 风险自动预警

每日巡检（并入 `PlanTaskScheduler._tick` 或新建 `SMHealthChecker`）：

- 所有 `IN_PROGRESS` + `planned_end_date < now` → 标记 DELAYED
- 所有 `BLOCKED` + 阻塞 > 7 天 → 风险升级
- 所有 `NOT_STARTED` + `planned_start_date < now` → 标为延期风险
- 关键路径上的 DELAYED/BLOCKED 节点 → 综合风险等级计算
