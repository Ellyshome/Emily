# 需求：系统进化日志统一收束

> 版本：V1 | 日期：2026-07-09 | 状态：草案
> 关联：[Pipeline执行日志收束需求_V1.md](Pipeline执行日志收束需求_V1.md)（本文档为其上位需求）

---

## 1. 全局判断：是的，应该统一收束

Pipeline 执行日志是"脊椎"，但光有脊椎不够。Emily 中还有 5 类对进化至关重要的信息流正在流失，它们互相关联，应该共享统一的设计规范和写入机制，而非各自为政。

**统一收束 ≠ 一张大表**，而是：

```
┌──────────────────────────────────────────────────────────────┐
│              统一日志规范（共享约定）                          │
│  · pipeline_run_id 关联                                      │
│  · user_id + conversation_id                                 │
│  · created_at UTC ISO8601                                    │
│  · 非阻断写入（失败只 warning）                                │
│  · 文本字段截断上限                                           │
│  · 共享写入工具函数                                           │
├──────────┬──────────┬──────────┬──────────┬──────────┬───────┤
│ pipeline_ │ llm_     │ rag_     │ session_ │ scheduler│业务事件│
│ execution │ interact │ retrieval│ lifecycle│ _job_logs│_logs  │
│ _logs    │ _logs    │ _logs    │ _logs    │          │       │
│(已有需求) │(本文档)  │(本文档)  │(本文档)  │(本文档)  │(已有)  │
└──────────┴──────────┴──────────┴──────────┴──────────┴───────┘
         全部通过 pipeline_run_id 关联
```

## 2. 五类流失信息详析

### 2.1 LLM 交互日志（`llm_interaction_logs`）

**现状**：LLMClient 已有 `_trace_callback` 机制，但**无人接入**。每次 LLM 调用的 prompt/response/token/latency 全部流失。

**流失的信息**：

| 调用场景 | 调用方 | 流失了什么 | 进化价值 |
|---------|--------|-----------|---------|
| 意图识别 | SessionAgent._recognize_intent | prompt + 识别结果 + token | 评估意图识别质量 |
| 执行计划 | WorkItemAgent.node2_plan | prompt + plan + token | 评估计划合理性 |
| 工具执行 | SkillExecutor | prompt + tool_call + token | 评估工具调用准确率 |
| 守护审核 | RealGuardian | prompt + verdict + token | 评估守护有效性 |
| 对话压缩 | SessionContext.compress_overflow | prompt + 摘要 + token | 评估压缩质量 |
| 摘要整合 | SessionContext._consolidate | prompt + 新摘要 + token | 评估摘要质量 |
| 参数提取 | SkillParamExtractor | prompt + 参数 + token | 评估参数提取准确率 |

**需要收集**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | String (PK) | UUID |
| `pipeline_run_id` | String (INDEX) | 关联 Pipeline 执行（可空——压缩/整合不在 Pipeline 内） |
| `conversation_id` | String (INDEX) | 会话 ID |
| `user_id` | String | 用户 ID |
| `call_category` | String | intent / planning / execution / guardian / compression / consolidation / param_extract |
| `call_sequence` | Integer | 同一 pipeline 内的调用序号 |
| `model` | String | 使用的模型名 |
| `message_count` | Integer | 发送的 messages 数量 |
| `tool_count` | Integer | 提供的工具数量 |
| `json_mode` | Boolean | 是否 JSON 模式 |
| `response_type` | String | text / json / tool_call |
| `response_summary` | String | 响应摘要（截断 500 字） |
| `finish_reason` | String | stop / length / tool_calls / content_filter |
| `prompt_tokens` | Integer | 输入 token 数 |
| `completion_tokens` | Integer | 输出 token 数 |
| `total_tokens` | Integer | 总 token 数 |
| `latency_ms` | Integer | 耗时毫秒 |
| `is_error` | Boolean | 是否调用失败 |
| `error_summary` | String | 错误摘要（截断 200 字） |
| `created_at` | String | UTC ISO8601 |

**实现路径**：接入 LLMClient 已有的 `_trace_callback`，在回调中写入 DB。**这是最低成本的实现——LLMClient 已经在收集这些数据，只是没人接。**

### 2.2 RAG 检索日志（`rag_retrieval_logs`）

**现状**：MaxKB 和本地 fallback 检索后，query/results/scores 全部流失。StepResult 中的 `rag_results` 在内存中消失。

**流失的信息**：
- 用户问了什么知识问题？
- MaxKB 命中了什么？得分多少？
- 命中结果是否被采纳（喂给了 LLM）？
- MaxKB 不可用时是否回退到本地？
- 检索耗时多少？

**需要收集**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | String (PK) | UUID |
| `pipeline_run_id` | String (INDEX) | 关联 Pipeline 执行 |
| `conversation_id` | String | 会话 ID |
| `user_id` | String | 用户 ID |
| `query_text` | String | 检索查询文本 |
| `provider` | String | maxkb / local_fallback / unavailable |
| `hit_count` | Integer | 命中结果数 |
| `top_score` | Float | 最高相似度分 |
| `avg_score` | Float | 平均相似度分 |
| `results_summary` | Text | 命中结果摘要 JSON（截断 2000 字） |
| `was_used_by_llm` | Boolean | 结果是否被喂给 LLM |
| `latency_ms` | Integer | 耗时毫秒 |
| `error_summary` | String | 错误摘要 |
| `created_at` | String | UTC ISO8601 |

**进化价值**：
- 知识库命中率低 → 需要补充知识文档
- 某类查询总是低分 → embedding 模型或分块策略需优化
- 本地 fallback 频繁触发 → MaxKB 配置/连通性需排查

### 2.3 Session 生命周期日志（`session_lifecycle_logs`）

**现状**：Session 创建、刷新、压缩、归档的完整过程只在 Python logger 中，无结构化记录。

**流失的信息**：
- 何时创建、何时归档、存活多久？
- 上下文刷新了几次？刷新了哪些字段？
- 压缩了几次？压缩了多少消息？压缩后摘要质量如何？
- 归档时的对话轮次、上下文快照

**需要收集**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | String (PK) | UUID |
| `conversation_id` | String (INDEX) | 会话 ID |
| `user_id` | String (INDEX) | 用户 ID |
| `event_type` | String | created / refreshed / compressed / archived / terminated |
| `detail_json` | Text | 事件详情 JSON |
| `message_count` | Integer | 事件时的消息数 |
| `duration_ms` | Integer | 事件耗时（压缩/归档耗时） |
| `created_at` | String | UTC ISO8601 |

**进化价值**：
- 压缩频率高 → prompt 可能太长，需优化
- 归档存活时间短 → 用户交互模式分析
- 刷新字段分布 → 权限变更频率

### 2.5 用户反馈信号日志（`user_feedback_signals`）

**现状**：**完全缺失**。Emily 不知道用户是否满意，无法从交互模式中提取反馈信号。

**应提取的隐式信号**：

| 信号 | 检测方式 | 进化含义 |
|------|---------|---------|
| 重复请求 | 同一用户 3 分钟内发送相似消息 | 上次回复不满意 |
| 显式纠正 | 消息含"不对"/"错了"/"不是这个"/"重新" | 明确不满 |
| 截断追问 | 消息含"继续"/"然后呢"/"还有吗" | 回复不完整 |
| 确认满意 | 消息含"好的"/"谢谢"/"对" | 满意 |
| 会话放弃 | 用户消息后 30 分钟无回复 | 可能不满意 |

**需要收集**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | String (PK) | UUID |
| `pipeline_run_id` | String (INDEX) | 关联 Pipeline 执行 |
| `conversation_id` | String | 会话 ID |
| `user_id` | String | 用户 ID |
| `signal_type` | String | repeat_request / explicit_correction / truncation_followup / positive / abandonment |
| `signal_strength` | Float | 信号强度 0.0-1.0 |
| `trigger_message` | String | 触发信号的消息内容（截断 200 字） |
| `context_summary` | String | 关联的 Emily 回复摘要 |
| `created_at` | String | UTC ISO8601 |

**进化价值**：
- 高频纠正 → 意图识别或执行逻辑需优化
- 高频重复 → 回复质量需提升
- 截断追问 → 输出完整性需改善

## 3. 统一日志规范

### 3.1 共享约定

所有 6 类日志表（含 Pipeline 执行日志 + 业务事件日志）必须遵守：

| 约定 | 规则 |
|------|------|
| **关联 ID** | 所有在 Pipeline 内产生的日志必须含 `pipeline_run_id` |
| **用户上下文** | 必须含 `user_id`（可空，系统级操作无用户） |
| **时间格式** | 统一 `created_at` UTC ISO8601 |
| **写入模式** | 非阻断——写入失败只 `logger.warning`，不影响业务主流程 |
| **截断上限** | Text 字段 ≤ 5000 字，String 字段 ≤ 500 字 |
| **不存原始 prompt** | LLM 完整 prompt/response 不入库（太长 + 隐私），只存摘要和统计 |
| **索引策略** | `pipeline_run_id` + `user_id` + `created_at` 三列建索引 |

### 3.2 共享写入工具

```python
# emily_core/infrastructure/logging/log_writer.py

class EvolutionLogWriter:
    """统一日志写入工具——所有进化日志的写入入口。

    保证：
    1. 非阻断（异常只 warning）
    2. 截断（防止超大 payload）
    3. 异步（asyncio.to_thread 包裹同步 DB 写入）
    """

    @staticmethod
    async def write(model_class, **kwargs):
        """非阻断写入一条日志。"""
        try:
            # 截断
            kwargs = EvolutionLogWriter._truncate(kwargs)
            await asyncio.to_thread(EvolutionLogWriter._sync_write, model_class, kwargs)
        except Exception as e:
            logger.warning("EvolutionLogWriter.write failed for %s: %s",
                          model_class.__tablename__, e)

    @staticmethod
    def _sync_write(model_class, kwargs):
        with get_session() as session:
            entry = model_class(**kwargs)
            session.add(entry)
            session.commit()

    @staticmethod
    def _truncate(kwargs, text_limit=5000, string_limit=500):
        truncated = {}
        for k, v in kwargs.items():
            if isinstance(v, str):
                limit = text_limit if k.endswith('_json') or k.endswith('_summary') or k == 'detail_json' else string_limit
                truncated[k] = v[:limit]
            else:
                truncated[k] = v
        return truncated
```

### 3.4 关联查询示例

```sql
-- "用户张工今天的完整交互链路"
SELECT
  pel.matched_sop_id, pel.final_status, pel.elapsed_ms,
  lil.call_category, lil.total_tokens, lil.latency_ms as llm_latency,
  rrl.query_text, rrl.hit_count, rrl.top_score,
  ufs.signal_type
FROM pipeline_execution_logs pel
LEFT JOIN llm_interaction_logs lil ON lil.pipeline_run_id = pel.pipeline_run_id
LEFT JOIN rag_retrieval_logs rrl ON rrl.pipeline_run_id = pel.pipeline_run_id
LEFT JOIN user_feedback_signals ufs ON ufs.pipeline_run_id = pel.pipeline_run_id
WHERE pel.user_name = '张工'
  AND pel.created_at >= '2026-07-09T00:00:00Z'
ORDER BY pel.created_at;
```

## 4. 建设优先级

| 优先级 | 日志表 | 理由 |
|--------|--------|------|
| **P0（立即）** | `pipeline_execution_logs` + `hook_execution_logs` 增强 | 脊椎——没有它其他日志无法关联 |
| **P1（紧随）** | `llm_interaction_logs` | 成本中心——LLM 是最大开销，必须可追踪；且 `_trace_callback` 已存在，接入成本最低 |
| **P1（紧随）** | `business_event_logs` | 替代文件级 EventJournal，使业务事件可查询可分析 |
| **P2（第二批）** | `rag_retrieval_logs` | 知识质量评估——需要了解 RAG 命中情况 |
| **P2（第二批）** | `user_feedback_signals` | 最具进化价值但检测逻辑需要开发 |
| **P3（第三批）** | `session_lifecycle_logs` | 运维价值高但进化价值中等 |
| **P3（第三批）** | `scheduler_job_logs` | 运维价值高但进化价值低 |

---

## 5. 一句话总结

**6 类进化日志 + 2 类已有增强 = 8 张表，共享统一规范，通过 pipeline_run_id 串联成一条完整的"请求→思考→决策→执行→反馈"链路。先建脊椎（P0），再接四肢（P1-P3）。写入工具统一为一个 `EvolutionLogWriter`，确保非阻断、截断、异步三原则。**
