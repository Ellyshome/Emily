## 一、总体评价

V1 → V2 的改动是方向性的：砍掉固定阈值卡滞检测，将核心从"定时扫表报警"转向"凌晨 LLM 复盘 + 个人晨报"。这个转变解决了 V1 中最致命的问题——固定阈值无法处理节点间复杂的前置依赖关系（"7 天预警"对预售许可证这种节点毫无意义）。

文档的降级策略设计得具体且可操作（LLM 不可用 → 纯规则摘要；推送时用户不在线 → 邮件 fallback；凌晨 3 点系统挂了 → 启动时检查补漏），这些细节在实施时能省大量决策时间。

需要关注的核心风险是 LLM 成本——每天一次全项目复盘，按 30 个活跃节点、每个节点一次 chat_json 调用，每天约 30 次 LLM 调用。晨报生成（按 owner 分组）可复用节点评估的结果，不额外增加调用次数。这个成本量级是可控的（每日约 0.3-0.5 元人民币量级，取决于模型），但建议在配置中预留频率调整的灵活性——比如先从每周三次开始验证效果，再改回每日。

## 二、分维度审核

### 2.1 战略合理性（I）— 技术总监

**审核结论**：✅ 通过

1. **真实痛点**：每个节点负责人在早晨上班时拿到一份"你今天该关心什么"的简报，这个需求在工程管理场景中是真实的——项目经理和工程师的第一个动作往往是打开系统看今天有什么要处理。把"主动看"变成"推送过来"，减少了信息获取的摩擦。

2. **没有更简单的办法**：固定的卡滞检测已确认不适用（产证办理 vs 施工进度的前置依赖差异），LLM 动态推理是解决这个问题的合理路径。每天一次批量评估（凌晨 3 点）是省成本的优化——不是每个 Tick 都调 LLM。

3. **名实匹配**：文档明确声明"不是 Agent"、"LLM 推理后即释放"。命名 Monitor 是准确的。唯一的语义张力在于——凌晨复盘调用 LLM 做风险评估，这其实已经是轻度"Agent"行为了（判断风险等级、生成建议文案），但因为它只在固定时间执行、不做后续跟踪、不自主创建任务，Monitor 仍然比 Agent 更准确。

4. **受众匹配**：晨报推送给 `owner_dept_id`，这是正确的受众——关心"我的节点有没有风险"的人。冷启动报告给管理员——关心"系统有没有正常启动"的人。层次清晰。

### 2.2 架构合理性（B）— 资深架构师

**审核结论**：✅ 通过

1. **挂在 PlanTaskScheduler 的 Tick 中是正确的**：凌晨 3 点和早上 9 点的检查逻辑是简单的 `datetime.now().hour == X` 判断，不需要独立调度循环。

2. **一个实现细节**：Tick 间隔是 60s，理论上 3:00:00 到 3:00:59 之间只会命中一次。但如果有多个 Tick 在同一分钟窗口内执行（高负载下延迟），需要用一个 `_review_executed_today` 布尔标记避免重复触发。建议在实施计划中加上这个防重标记。

3. **`get_dependency_chain` 递归查询的复杂度**：如果一条依赖链深达 10 层，递归 SQL（或 Python 中多次查询）可能耗时。建议在 Repo 层用一次 JOIN 查询拉平依赖树，而非 N 次逐层查询。这属于实现细节，需求层面不需要修改。

4. **晨报推送的时间读取**：文档提到"从公司制度中读取上班时间"。经核查，当前系统没有 `company_config` 表或 `work_hour` 配置。建议在配置项中直接使用 `ops_monitor_brief_delivery_hour`（默认 9），将"从公司制度读取"作为后续扩展标注而非当前依赖。

### 2.3 实现可行性（C）— 资深程序员

**审核结论**：⚠️ 有改进空间（1 个阻塞点 + 2 个依赖确认）

1. **`NodeDependencyRepo.get_dependency_chain()` 可复用现有模型**：`node_dependencies` 表已经存在（`from_node_id` / `to_node_id`），可通过一次 SQL JOIN 查询获取完整的依赖链。递归方向：从目标节点出发，沿 `depends_on_node_id` 方向向上追溯。这不需要 new table，但 Repo 方法需要新增。

2. **`EventRepository` 缺少"最近 7 天事件数"的便捷查询**（阻塞）：Digest 需要 `event_count`，但 `EventRepository` 的 `query_events(time_range="this_week")` 返回的是列表而非计数。建议新增 `count_recent(project_id, days=7)` 方法。

3. **晨报生成是否额外调 LLM？** §4.1.4 说"按 owner_dept_id 分组合成个人晨报"，但没有明确这个合成是否需要 LLM。从上下文推断：每个节点的 `morning_brief_for_owner` 已在复盘阶段由 LLM 生成好了，分组只是按 owner 拼接 + 套模板。建议在文档中明确："晨报合成不额外调用 LLM——节点级文案在复盘阶段已生成，分组为纯模板拼接。"

### 2.4 AI/LLM 设计 — AI/ML 工程师

**审核结论**：⚠️ 有改进空间

1. **LLM 调用模式合理**：每天一次批量评估，每节点一次 LLM 调用。预估 30 个活跃节点 × 单次 chat_json ~2s = 60s 串行总耗时，在凌晨 3 点完全可接受。如果后续节点数增长，可改为并行调用（asyncio.gather）。

2. **LLM prompt 需要更多约束**。需求文档给出了输入/输出结构，但 prompt 中缺少约束条件——LLM 可能会高估或低估风险。建议在实施时给 prompt 增加：
   - 历史同类节点的完成耗时参考（如有）
   - 明确的风险判定规则："只有在计算后确认 deadline 前无法完成，才标记为 high"
   - 自校准提示："如果数据不足以做出可信判断，标记为 unknown 而非 hard guess"

3. **风险评估的准确性需要冷启动期**：系统刚上线时没有历史数据，LLM 只能根据节点名称和 deadline 做粗略判断。建议在文档的降级策略中增加一条："历史数据不足时，LLM 评审结果应标注 `confidence: low`，晨报中提示'此为系统初步评估，准确性随项目数据积累而提升'"。

## 四、替代方案

当前方案在凌晨批量 LLM 复盘 + 固定时间推送的框架下已是最佳选择。

一个可考虑的变体是：不按 owner 分组推送，而是直接写入 Digest 让用户在 IM 中主动询问 SessionAgent。这样省掉了晨报存储和推送的复杂度，但失去了"主动推送"的价值——用户还是需要主动问。当前方案选择推送，对一个运维助手来说是正确的偏主动方向。

**核心建议**：优先解决 B1（EventRepository.count_recent）和 B2（company_config 不存在），它们是 Digest 和晨报推送的直接阻塞点。
