# 需求审查：项目级状态机 & 项目记忆模块

> 审查对象：`project state and memory.md` 中的两份需求
> 审查视角：资深架构师 / 程序员，结合 Emily 项目实际代码与已有设计
> 产出形式：审查（问题/风险/建议）+ 关键决策点方案对比
> 状态机处理：与 `Emily_权限系统设计.md` §12 合并为统一设计

---

## 一、Context（背景与审查目标）

`project state and memory.md` 提出两个新模块：**项目级状态机**（反映项目文档目录/DB结构/模块树推进状态，分层、可审计、受权限控制）和**项目记忆模块**（公共+私有记忆，含对话摘要、零散信息仓库、RAG 集成、定时整理）。

审查发现：**两份需求都没有引用项目中已存在的大量相关设计与代码**，存在显著的重复设计与对接缺口。本审查的核心价值就是把需求落到现有代码上，指出哪些可复用、哪些是真正的新工作、哪些决策点需要先拍板。用户已确认状态机需求与 `Emily_权限系统设计.md` §12 合并为统一设计。

## 三、需求一：项目级状态机 — 审查

### 3.1 优点
- **分层（总表-分表树）原则正确**：地产项目多企业、多专业协作，树状划分合理，且与领域模型（阶段→分部→任务）天然对应。
- **"仪表盘"被动状态理念正确**：状态不持业务逻辑、由调度机/执行模块驱动流转——与 `定时任务模块需求.md` §2.2 已确立的理念一致，全系统状态机风格统一。
- **专设审计表（谁/何时/改了什么）**：与 `plan_task_logs`（JSON 快照）模式一致，可复用。
- **主动声明与权限系统并行开发、需先商定接口**：依赖识别准确。

### 3.2 与 §12 合并分析（用户已确认合并）
需求文档与 `Emily_权限系统设计.md` §12 描述的是**同一个状态机**，但互不引用。合并要点：

| 需求文档表述 | §12 已有设计 | 合并结论 |
|---|---|---|
| 模块树，前后关系，三态（前置未满足未启动/运转中/办结） | `ProjectPhase`（外）+ `ProjectStage`（内）+ `stage_dependencies` DAG；5 态 `NOT_STARTED/RUNNING/PAUSED/COMPLETED/CANCELLED` + `PRE_STARTING` | 采用 §12 的表结构；状态集合见决策点 1 |
| 文档目录/DB 结构与仓库联动 | §12 未覆盖此"元数据映射" | **需求文档的补充价值**：§12 只管业务阶段状态，不管"文档目录汇总/DB 表结构映射"。这部分应作为状态机的**只读元数据视图**独立设计（见 3.3-2） |
| 业务内容由 session-agent 分散协程更新 | §12 的 `ProjectStateService.validate()` + 乐观锁 `version` | 合并：复用 §12 服务 + 乐观锁，补充并发控制（见决策点 3） |
| 专设审计表 | `project_state_audit_logs` | 直接复用 §12 表 |
| 权限分组 CURD | `project_state_permissions` + 字段级 public/internal | 直接复用 §12 表与权限接口 |
| 分层总表-分表 | `ProjectPhase`→`ProjectStage` 树 | 直接复用 |

**合并后统一设计基准**：以 §12 的表结构（`ProjectPhase`/`ProjectStage`/`stage_dependencies`/`project_state_permissions`/`project_state_audit_logs`）为骨架；需求文档贡献"文档目录 + DB 结构元数据映射"与"分层划分原则"两点补充。

### 3.3 问题与风险

1. **【高风险】"数据自动关联文件仓库与数据库"机制未定义**。需求说"数据部分通过自动关联文件仓库与数据库实现自动关联实现"，但没说*怎么*关联。文件上传/DB 写入如何触发状态变更？现有代码已有天然挂载点却未被提及：
   - `record_file` 工具（`tools/`）写文件后 → 可触发关联 Stage 状态刷新
   - Pipeline `after:` hooks（`workitem/pipeline/bus.py`）→ 可监听业务成果落库事件
   - `EventJournal`（`services/event_journal.py`）已记录系统事件
   不定义触发机制，"自动关联"就是空话。

2. **【高风险】"session-agent 分散协程更新"无并发控制**。多个 session 并发更新同一 Stage 状态会丢更新。`plan_task` 已用 PG advisory lock + 乐观锁 `version` 解决同类问题（`plan_task_scheduler.py:133`、`plan_task_repo.py` 终态守卫），状态机必须照搬同类机制。需求未提。

3. **【中风险】状态集合粗细不一致**。需求三态（未启动/运转中/办结）实际隐含第 4 态"前置条件未满足"（= §12 `PRE_STARTING`）。§12 还有 `PAUSED`/`CANCELLED`。地产项目确有暂停/取消场景（如政策停工、阶段废止）。见决策点 1。

4. **【中风险】阶段目录来源未指定**。两份领域文档冲突（6 阶段 vs 7 阶段）。状态机的阶段目录应**配置化**，不硬编码任何一份。见决策点 4。

5. **【中风险】依赖权限系统（Phase III），而权限系统本身仅脚手架**。`authorize()` 恒 ALLOW、`PermissionSnapshot` 未灌注。状态机被 §12 标为 Phase IV，序列上是 auth→state machine。若并行开发，接口必须先冻结（需求已意识到，但未列出接口清单）。

6. **【低风险】"文档目录汇总/DB 表结构映射"是配置还是运行时数据？** 应是**持久化配置**（项目初始化时录入，随仓库/DB 变更由管理员或自动扫描更新），不是每次 session 重建。`SessionContext.schema_summary` 已有骨架字段可承接只读摘要。

### 3.4 关键决策点（方案对比）

#### 决策点 1：状态集合
- **A. 三态**（未启动/运转中/办结）：最简，但无法表达"前置未满足"与"暂停/取消"。
- **B. §12 五态 + PRE_STARTING**（`PRE_STARTING/NOT_STARTED/RUNNING/PAUSED/COMPLETED/CANCELLED`）：表达力够，与权限设计一致。
- **C. 四态**（PRE_STARTING/RUNNING/COMPLETED + CANCELLED，无 PAUSED）：折中，去掉暂停。
- **推荐 B**：与 §12 一致免重复设计；地产项目确有停工/废止场景，PAUSED/CANCELLED 必要。

#### 决策点 2：数据自动关联触发机制
- **A. 事件驱动（Pipeline hooks + 工具回调）**：`record_file`/`record_event` 等工具落库后，`after:` hook 推送事件给 `ProjectStateService` 刷新关联 Stage。实时、解耦。
- **B. 调度器轮询扫描**：`PlanTaskScheduler` 增加一个 tick 周期扫描文件仓库/DB 变更。简单但有延迟、耗资源。
- **C. 仅显式工具调用**：只能由 session-agent 显式调"更新状态"工具。最可控但非"自动"。
- **推荐 A**：现有 Pipeline hooks 架构就是为此设计的；B 作兜底（catch-up 扫描）。

#### 决策点 3：并发控制
- **A. 乐观锁（`version` 字段 + CAS）**：§12 已设计 `version`；更新失败重试。适合低冲突场景。
- **B. PG advisory lock（类 `plan_task_scheduler`）**：强一致，但跨 session 持锁成本高。
- **C. 行级锁（`SELECT ... FOR UPDATE`）**：DB 原生，简单。
- **推荐 A + C 混合**：常态用乐观锁 `version`（§12 已有），状态流转服务内对关键行用 `FOR UPDATE`。与 `plan_task` 风格一致。

#### 决策点 4：阶段目录来源
- **A. 以 `生命周期.md` 7 阶段 ~75 节点为种子**：最结构化、有节点 ID（LS-X-XX）、含前置条件 DAG。
- **B. 以 `阶段划分）.md` 6 阶段为种子**：更细的子任务分解。
- **C. 配置化（DB 表 + 管理界面），两份文档仅作导入素材**：不硬编码，项目可定制。
- **推荐 C**：阶段目录落 `ProjectPhase`/`ProjectStage` 表，提供导入脚本吃两份文档；运行期以表为准。避免硬编码任一文档。
