## 一、背景与目标

### 1.1 背景

Emily 项目在运行过程中产生大量项目文档（施工图、证照、成本测算单、施工日志、公司制度、时间计划等），存放于项目公共文档库。不同参建单位、不同角色的用户对同一文档库中的文件应有不同的访问权限，需要一套以全景节点为锚点的细粒度文档可见性管控机制。

### 1.2 目标

实现对项目参与者合理的文档可见性控制，以**最小化权限和访问范围**为原则，在安全与便捷之间取得平衡。

### 1.3 范围

| 包含 | 不包含 |
|------|--------|
| 项目文档库内存放的项目文档（施工图、证照、成本测算单、施工日志、公司制度、集团要求、时间计划等） | SOP 文档（走独立权限管控） |
| 各类文件的上传、查看、下载、编辑、删除、授权操作 | 数据库（不提供直接访问，走查询工具 + Hook 管控） |

## 二、核心概念定义

| 术语 | 定义 | 统一用词 |
|------|------|----------|
| **项目文档库** | 项目业务过程中产生的文档的存放目录。含业务文档、公司制度、集团要求、时间计划等。 | 文档库 |
| **文档** | 存放于项目文档库内的文件。如各专业施工图、施工许可/用地许可等证照、各专业成本测算单、各专业施工日志等。 | 文档 / 文件 |
| **SOP 文档** | 标准作业流程手册（Standard Operating Procedure），独立于项目文档库，走 SOP 权限管控链路。 | SOP |
| **全景节点** | Emily 的全景节点图体系中的节点（对应 `sm_nodes` / `project_nodes` 表）。项目工作分解为节点，每个节点有明确的责任范围。 | 节点 |
| **节点负责人** | 全景节点的管理责任人。由建设单位部门负责人（如设计部经理、工程部经理、成本部经理）批准创建节点后，创建者即为节点负责人。 | 节点负责人 |

| **节点默认可见** | 在本节点运行过程中由系统或用户上传产生的文件，自动对该节点所有参与单位可见，无需节点负责人手动设置。 | 节点默认可见 |

## 三、权限模型

### 3.1 核心模型

```
节点负责人 ──→ 选择文档（设为"节点可见"）
           ──→ 选择参与单位（已入库的企业）
           ──→ 权限生效：参与单位的所有用户获得该文件的访问权
```

以全景节点为锚点，节点负责人将文档库内的文件设为"节点可见"，并选择已入库的企业为参与单位。归属该参与单位的用户即自动获得这些文件的访问权。

### 3.2 默认规则

**本节点产生的所有文件，默认本节点参与者可见**（系统自动创建授权记录，`visibility_type=NODE_DEFAULT`），无需节点负责人手动设置。

### 3.3 操作类型矩阵

不同角色对节点可见文件的允许操作：

| 角色 | 查看 | 下载 | 编辑 | 删除 | 管理可见性 |
|------|:---:|:---:|:---:|:---:|:---:|
| 非建设单位用户 | ✅ | ✅ | ❌ | ❌ | ❌ |
| 建设单位用户（非节点负责人） | ✅ | ✅ | ✅ | ⚠️ 仅本部门 | ❌ |
| 节点负责人 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 管理员（L5）+ | ✅ | ✅ | ✅ | ✅ | ✅ |

> ⚠ 非建设单位用户对文件**只可读**（查看 + 下载），无写入/修改/删除权限。

## 四、权限层级与优先级

### 4.1 权限继承

权限所有者的**上级自动继承下级的权限**。即：上级的可见文档集合 ⊇ 下级的可见文档集合。

### 4.2 与 6 级 RBAC 体系的集成

文档节点可见权限作为独立授权维度，嵌入现有 RBAC+ABAC 混合模型的优先级链：

```
DENY（显式拒绝）
  > 单独文件授权（permission_grants grant_type=FILE_SPECIFIC）
    > 节点文档可见（NODE_VISIBLE / NODE_DEFAULT）
      > 临时授权（TEMP）
        > 永久授权（PERMANENT）
          > 单位归属自动授权（AUTO）
```

**优先级解读**：
- 管理员（L5+）的显式 DENY 可覆盖一切
- 单独对某文件的授权优先于节点群体授权
- 节点文档可见是**群体授权**（节点+企业维度的批量授权），优先于个人的临时/永久授权
- 节点文档可见不可覆盖显式 DENY 和单独文件授权

### 4.3 权限决策公式

```
用户最终可见 = 节点可见(是) AND 密级可见(是) AND 6级RBAC通过(是)
```

三个条件必须**同时满足**（AND 逻辑），任一条不通过则不可见：
- **节点可见**：文件已设为该节点可见，且用户归属的参与单位已被选为可见范围
- **密级可见**：文件的密级（`confidentiality`）≤ 用户权限级别对应的最大可见密级
- **6 级 RBAC**：用户的 6 级权限分组（L1-L6）对该资源类型的访问资格

### 4.4 与行级安全的叠加

`row_security.py` 已对 `files` 表注入 `company_id` 过滤。文档节点权限在此基础上**叠加 node_id 维度的附加过滤**，两层为 **AND** 关系：

```
最终可见文件 = company_id ∈ 用户归属企业（行级安全）
            AND node_id ∈ 用户参与的节点
            AND (node_id, file_id) ∈ NodeAccessibleFile（节点文档可见）
```

## 五、安全设计

### 5.1 密级降级防护

**节点可见性不能绕过文档密级限制**。

文档密级（`File.confidentiality`）与用户可见密级的映射：

| 文档密级 | 编码值 | L1 访客 | L2 参建执行 | L3 参建管理 | L4 建设主管 | L5 管理员 | L6 系统管理员 |
|----------|:------:|:-------:|:----------:|:----------:|:----------:|:--------:|:----------:|
| 公开 | 0 | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| 内部 | 1 | ❌ | ✅ | ✅ | ✅ | ✅ | ✅ |
| 机密 | 2 | ❌ | ❌ | ❌ | ❌ | ✅ | ✅ |
| 绝密 | 3 | ❌ | ❌ | ❌ | ❌ | ❌ | ✅ |

> 即使节点负责人将一份"机密"文档设为"节点可见"，L2 参建执行用户也**不能**看到——因为 L2 的最大可见密级是"内部"。

### 5.2 参与单位选择约束

节点负责人选参与单位时，可选项限定为：
- **本项目关联的履约中企业**（`CompanyInfo.status=active` 且在本项目有节点分配）
- 已退场、未关联本项目的企业不出现在可选列表中，防止跨项目信息泄露

### 5.3 建设单位用户权限边界

- 只有**节点负责人**可以管理文件可见性（设为节点可见 / 取消节点可见 / 调整参与单位范围）
- 其他建设单位用户（非节点负责人）仅有查看、编辑文件的权限，**不能**修改文件的可见性设置

### 5.4 Agent 安全约束（IM 接口）

通过 IM 自然语言接口进行文档可见性操作时，Agent 必须遵守以下安全约束：

1. **逐项确认**：Agent 根据自然语言描述匹配出的文件清单，必须逐项列出（含文件名、密级、上传时间），由发起用户逐项确认，**禁止批量一键确认**
2. **仅推荐不授权**：Agent 的角色是文件推荐 + 范围建议，**不得直接操作权限表**。最终授权动作始终由后端执行
3. **审计日志**：每次节点可见性设置 / 撤销操作写入 `permission_audit_log`（`operation_type=NODE_VISIBILITY_CHANGE`）
4. **发起人校验**：只有建设单位用户（L4+）可以发起文档可见性管理请求。非建设单位用户的请求应拒绝并引导其向节点负责人申请

### 5.5 审计要求

所有节点可见性管理操作记录到 `permission_audit_log` 表（已存在，`models.py:1066`）：

| 操作类型 | operation_type | 记录内容 |
|----------|---------------|----------|
| 设为节点可见 | NODE_VISIBILITY_GRANT | 操作人、文件ID、节点ID、可见企业ID |
| 取消节点可见 | NODE_VISIBILITY_REVOKE | 操作人、文件ID、节点ID、撤销原因 |
| 节点删除级联取消 | NODE_VISIBILITY_CASCADE | 系统触发、节点ID、影响文件数 |

### 6.2 需扩展的字段

`NodeAccessibleFile` 表需扩展以下字段以支持完整的文档权限模型：

| 新增字段 | 类型 | 用途 | 优先级 |
|----------|------|------|:-----:|
| `company_id` | String FK→`company_info.id` | 限定可见的企业（目前仅限定节点，允许跨节点统一授权场景如所有企业可见时为空） | **高** |
| `visibility_type` | String(20) | `NODE_DEFAULT`（系统自动：本节点产生的文件）/ `NODE_VISIBLE`（节点负责人主动设置） | 中 |
| `is_active` | Boolean | 默认 True，撤销后设为 False 以保留审计记录，替代物理删除 | 中 |

### 6.3 查询模式

查询用户可见的文档（SQL 概要）：

```sql
-- 用户在 node_id=N 下可见的文件
SELECT f.* FROM files f
INNER JOIN node_accessible_files naf
  ON f.id = naf.file_id AND naf.node_id = :user_node_id AND naf.is_active = TRUE
WHERE (naf.company_id = :user_company_id OR naf.company_id IS NULL)
  AND f.confidentiality <= :user_max_confidentiality   -- 密级过滤
  AND f.is_deleted = FALSE
```

行级安全拦截器（`row_security.py`）先注入 `company_id` 过滤，再通过 `NodeAccessibleFile` JOIN 叠加节点维度过滤。

## 七、节点负责人判定规则

### 7.1 主判定路径

节点负责人 = **创建节点的建设单位部门负责人**（记录创建时的 `user_id`）。

节点只能由建设单位部门负责人批准创建（如设计部经理、工程部经理、成本部经理）。创建者自动成为节点负责人。

### 7.2 备选判定路径

当节点负责人调离或不可用（如账号停用），系统通过 `CompanyInfo.function_scope` 推导备选负责人：

```
备选负责人 = CompanyInfo.function_scope 中 node_id 匹配的部门负责人
```

其中 `function_scope` 是一个 JSON 字段，格式为：
```json
{
  "node_001": { "department": "设计部", "manager_id": "user_zhang" },
  "node_002": { "department": "工程部", "manager_id": "user_li" }
}
```

### 7.3 支持多负责人

一个节点可以有多个负责人（通过 `NodeAccessibleFile` 的 `added_by` 字段自然支持，不限制同一 `node_id` 的授权人）。系统不限制节点负责人数量，但建议每个节点至少 1 名、不超过 5 名负责人。

## 八、边界条件与异常处理

### 8.1 节点删除

- 节点删除时，关联的 `NodeAccessibleFile` 记录中 `is_active` 设为 `False`（逻辑删除）
- 系统自动写入 `NODE_VISIBILITY_CASCADE` 审计事件
- 之前通过该节点获得文件访问权的用户，在节点删除后**丧失**对应权限

### 8.2 用户调离单位

- 用户被移出参与单位时，自动丧失该单位对应的文档访问权
- 无需手动回收权限，行级安全 + 节点过滤会自然排除该用户

### 8.3 权限撤销

- 节点负责人可以撤销自己设置的文件"节点可见"（`is_active=False`，逻辑删除）
- 撤销操作需填写原因（必填，记录到审计日志）
- 撤销后已获得权限的用户实时丧失访问权（下次查询时不可见）
- 节点负责人变更时，前负责人的权限设置**保留有效**，新负责人可以选择撤销

### 8.4 跨节点文件

- 同一文件可以被多个节点的负责人设为"节点可见"（`NodeAccessibleFile` 的 `UniqueConstraint(node_id, file_id)` 约束的是同一节点的重复设置，跨节点允许）
- 文件的最终可见范围 = 所有关联节点的参与单位用户的**并集**（叠加各自密级和 RBAC 检查）

### 8.5 建设单位用户可见范围

- 建设单位用户（L4+）默认可见本项目所有文件（不受节点可见性限制）
- 但密级检查仍然有效——L4 建设主管不能看"机密"文件

## 九、接口方案

### 9.1 IM 自然语言交互（主入口）

用户通过 IM 提交自然语言描述，由 Agent 辅助完成文档可见性管理：

```
用户: "把 B3 区 2 层结构施工图设为节点可见，给 XX 施工单位看"
Agent: → 解析意图
      → 通过 GET /api/v1/files/by-node/{node_id} 查询节点关联文件
      → 结构化匹配文件清单
      → 逐项展示给用户确认（含文件名、密级、上传时间）
用户: 逐项确认
后端: → 写入 NodeAccessibleFile 记录
      → 写入 permission_audit_log
      → 返回操作结果
```

### 9.2 补充 API（Agent 内部查询依赖）

新增 `GET /api/v1/files/by-node/{node_id}` 端点，供 Agent 内部使用：

```
GET /api/v1/files/by-node/{node_id}
  ?keyword=结构施工图         # 可选，文件名模糊搜索
  &file_type=drawing          # 可选，文件类型过滤
  &company_id=xxx             # 可选，已可见企业过滤

Response:
{
  "node_id": "...",
  "files": [
    {
      "id": "...",
      "filename": "B3区2层结构施工图_V3.pdf",
      "file_type": "drawing",
      "confidentiality": 1,
      "confidentiality_name": "内部",
      "uploaded_at": "2026-06-15T10:30:00",
      "related_company_ids": ["..."]
    }
  ]
}
```

> 此 API 为 Agent 内部查询依赖，不要求用户直接使用。Agent 拿到结构化数据后做精确匹配和展示，避免纯文本匹配的歧义。

### 9.3 操作确认流程

```
1. 用户自然语言描述 → Agent 解析意图
2. Agent 查询候选文件清单 → 逐项展示（含关键属性）
3. 用户逐项确认（"第 1 项确认" / "全部确认"需要二次确认提示）→ Agent 展示操作预览
4. 用户最终确认 → 后端执行授权 → 返回结果 + 审计记录编号
```

## 十、性能与展望

### 10.1 当前策略

性能保证**暂不考虑**，当前阶段优先完成功能闭环。未来遇到性能问题时有以下优化路径：
- `NodeAccessibleFile` 表的 `idx_naf_node` / `idx_naf_file` 索引已覆盖基础查询
- 可引入 L2 用户白名单缓存（复用现有 `PermissionCache` 的两级缓存架构）
- 大文件库场景可考虑物化视图预计算用户可见文件集

### 10.2 后续扩展（不在本次范围）

- **目录级权限继承**：设置某目录为"节点可见"时，子文件自动继承。当前先不做，等实际需要时扩展
- **文档预览水印**：低权限用户预览机密文档时叠加水印（用户名+时间），防止截屏泄密
- **SSE 权限变更实时推送**：文档可见性变更后通过现有 SSE 机制推送 `permission_changed` 事件

## 十二、验收标准

1. 节点负责人可通过 IM 自然语言将文档设为对指定参与单位"节点可见"
2. 非建设单位用户仅能查看/下载被授权的文档，无法编辑/删除
3. 密级高于用户可见等级的文档，即使设为"节点可见"也不对用户展示
4. 节点删除后，关联的节点可见权限自动取消（逻辑删除）
5. 用户调离参与单位后，自动丧失该单位的文档访问权
6. 所有节点可见性管理操作记录到 `permission_audit_log`，可审计追溯
7. Agent 操作流程有逐项确认步骤，禁止静默批量授权
8. 节点负责人可查看、撤销自己设置的节点可见授权
9. 建设单位用户（非节点负责人）不可管理文档可见性
10. 参与单位选择列表仅包含本项目关联的履约中企业
