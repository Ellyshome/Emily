### 2.2 架构合理性 — 资深架构师

**审核结论**：⚠️ 方向正确，需明确集成路径

**亮点**：
- 以全景节点为权限锚点与现有 Emily 架构高度契合。`sm_nodes` 表已存在，`company_info.function_scope` 字段（职能-节点映射 JSON）在设计文档中已定义，二者构成天然的数据基础
- "节点产生文件默认参与者可见"的默认策略符合最小惊讶原则，降低了权限配置成本

**需澄清的架构问题**：

1. **权限优先级位置**：现有系统定义了 `DENY > 单独文件授权 > TEMP > PERMANENT > AUTO`。新需求中的"节点负责人设置文档可见"应插入优先级链的哪个位置？建议在 `单独文件授权` 和 `TEMP` 之间，即：
   ```
   DENY > 单独文件授权 > 节点文档可见(DOC_NODE_VISIBLE) > TEMP > PERMANENT > AUTO
   ```

2. **与行级安全的交互**：现有 `row_security.py` 通过 SQLAlchemy 拦截器对 `files` 表注入 `company_id` 过滤。文档节点权限需要在 `company_id` 过滤之外叠加 `node_id` 维度过滤，两层过滤的关系是 AND 还是 OR？建议 **AND**（最严格）：用户既要属于参与单位（company 过滤），又要节点有文档可见权限（node 过滤）。

3. **权限编码扩展**：需要新增文档节点权限的编码格式。建议：
   ```
   DOC-{security_level}-{project_id}-{node_id}-{file_id}
   示例: DOC-INTERNAL-PRJ001-NODE005-FILE042
   ```
   节点负责人的"设为节点可见"操作实质上是创建一个 `grant_type=NODE_VISIBLE` 的授权记录。

4. **缓存失效**：文档可见性变更需触发 `PermissionCache.invalidate_user()` 使相关节点参与者的 L2 白名单失效，否则权限变更不实时。

### 2.4 数据设计 — 资深架构师

**审核结论**：⚠️ 需求未涉及，需从零设计

当前 `files` 表（`models.py`）的结构需要确认。假设需要新增以下数据模型：

**方案建议**：新增 `file_node_visibility` 关联表

```sql
file_node_visibility:
  id            String PK       -- UUID
  file_id       String FK       -- → files.id
  node_id       String           -- 全景节点 ID（关联 sm_nodes）
  company_id    String FK        -- → company_info.id（可见单位）
  set_by        String FK        -- → users.id（设置人，节点负责人）
  visibility_type String(20)     -- NODE_VISIBLE / NODE_DEFAULT
  created_at / updated_at / is_deleted
```

**设计考量**：
- `visibility_type=NODE_DEFAULT` 表示"本节点产生的文件"——由系统自动创建
- `visibility_type=NODE_VISIBLE` 表示"节点负责人主动设为可见"——由人工操作创建
- 查询用户可见文档时：`file_id IN (SELECT file_id FROM file_node_visibility WHERE node_id IN user.authorized_node_ids AND company_id IN (user.company_id, user.partner_ids))`
- 这与现有权限编码系统兼容——可以表示为 `DOC-INTERNAL-*-NODE005-FILE042`

### 2.5 安全性 — 安全工程师

**审核结论**：⚠️ 方向正确但缺少安全细节

**认可的方面**：
- "以节点为锚点"的权限边界设计遵循最小权限原则
- "本节点产生的文件默认本节点参与者可见"是合理的默认安全策略

**缺失的安全考量**：

1. **越权风险**：节点负责人能否将文件设为"对非参与单位可见"？如果能，这就是一个**权限放大漏洞**——节点负责人不应有超出节点范围的授权能力。建议严格限制"可见单位"的下拉选择范围为已关联该节点的单位。

2. **密级降级风险**：如果一份标记为 CONFIDENTIAL（机密）的文档，节点负责人将其设为"节点可见"，是否意味着 L2 参建执行用户也能看到？如果是，这构成了**密级降级**。建议规则：文档密级必须 ≥ 用户可见密级，节点可见性不能绕过密级检查。即：
   ```
   最终可见 = 节点可见(是) AND 密级可见(是) AND 6级RBAC通过(是)
   ```

3. **文档所有权与审计**：谁可以撤销"节点可见"设置？仅设置人还是所有节点负责人？撤销操作是否需要审计日志？建议全部节点负责人可管理，且所有设置/撤销操作写入 `permission_audit_log`（`operation_type=DOC_VISIBILITY_CHANGE`）。

4. **文档流转安全**：当文档关联的节点被删除/归档后，文档的权限如何处理？建议保留当时的可见性快照（不自动公开），由管理员手动处理。

5. **批量操作风险**："选择公共库内的文档设为节点可见"——如果是批量选择数百份文档，需要有确认机制防止误操作导致大规模信息泄露。

## 四、替代方案

### 方案 A：扩展现有权限编码体系（✅ 推荐）

- **思路**：将文档节点可见性建模为 `DOC-NODE_VISIBLE-{project_id}-{node_id}-{file_id}` 权限编码，通过 `permission_grants` 表（新增 `grant_type=NODE_VISIBLE`）存储。节点负责人"设为可见"时，系统自动为该节点所有参与单位的用户创建 AUTO 授权记录。鉴权时走现有的 `check_access(resource_type="DOC", ...)` 路径。
- **优势**：最小侵入现有架构；复用权限编码/缓存/审计基础设施；权限优先级自然嵌入现有链路
- **劣势**：节点参与单位多时会产生大量 AUTO 授权记录（如 100 单位 × 50 文件 = 5000 条）；授权记录与参与单位列表不同步（单位新增/退出时需级联更新）
- **适用场景**：参与单位数量可控（< 50）的项目

### 方案 B：新增独立 `file_node_visibility` 关联表 + 查询时动态 JOIN

- **思路**：建独立关联表，不在 `permission_grants` 中存储。鉴权时通过查询关联表动态计算可见性，而非依赖预计算的权限快照。
- **优势**：无授权记录膨胀问题；参与单位变更自动生效；更灵活（支持目录级继承、过期自动清理）
- **劣势**：鉴权需额外 DB 查询（性能挑战）；需在行级安全拦截器中增加 JOIN 逻辑（复杂度上升）；不走缓存体系（需独立缓存设计）
- **适用场景**：大规模项目（参与单位 > 50，文档量 > 1000）

### 方案对比

| 维度 | 方案 A（扩展权限编码） | 方案 B（独立关联表） |
|------|------------------------|---------------------|
| 实现复杂度 | 低（复用现有 infra） | 中（新表 + 新逻辑） |
| 与现有架构契合度 | 高（自然融入 RBAC+ABAC） | 中（平行的新维度） |
| 扩展性（大量文档/单位） | 中（授权记录膨胀） | 高（动态查询） |
| 缓存命中率 | 高（走 L1/L2 缓存） | 低（需独立缓存） |
| 审计完整性 | 高（permission_audit_log 统一） | 中（需额外审计） |
| 推荐偏向 | ✅ 阶段一首选 | 阶段二优化（性能驱动迁移） |
