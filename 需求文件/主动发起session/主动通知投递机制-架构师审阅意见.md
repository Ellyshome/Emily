## 🔴 致命问题：主动推送通道根本不通

### 现状

需求文档 §3.1 架构图和 §6.4 声称：

> "复用现有出站通道：OutboundEventBus → SSE → 插件 SSEListener → IM 推送"
> "插件 SSEListener 已按 conversation_id 派发，无需改动"（D06）

**这是错误的。** 当前 SSEListener 的 `_handle_reply()` 实现（`data/plugins/emily_agent/adapters/sse_listener.py:104-118`）：

```python
async def _handle_reply(self, data: dict) -> None:
    conv_id = data.get("conversation_id", "")
    event = self._event_registry.get(conv_id)   # ← 必须有对应的 AstrMessageEvent
    if event is None:
        return                                   # ← 静默丢弃
    reply = ReplyMessage(...)
    await self.outbound.send(reply, event)       # ← send() 依赖 event 对象
```

而 `AstrBotOutboundSender.send(reply, event)` 通过 `event.set_result()` / `event.stop_event()` 发送——**完全依赖入站消息产生的 `AstrMessageEvent` 对象**。

### 问题链

1. **`_event_registry` 只在用户发消息时注册**：`main.py:84-85` — `self._event_registry[msg.conversation_id] = event`，仅用户主动发消息时才存在 entry
2. **主动通知时无入站 event**：系统主动推送，用户没有发消息 → registry 中无 event → `_handle_reply` 直接 return → 消息静默丢弃
3. **现有 PlanTaskScheduler 通知已经是坏的**：`plan_task_scheduler.py:200-208` 发的是 `{"user_id": ...}` 而非 `{"conversation_id": ...}`，SSEListener 找不到 event → 通知全部丢失。这不是新问题，但需求文档没有识别到

### 影响

- 需求中整个"OutboundEventBus 直推"的核心投递路径 **实际上不可达**
- `UserConversationResolver` 解决了 `user_id → conversation_id` 的映射问题，但 **解决了映射也推不过去**——即使有 conversation_id，registry 里也没有对应的 event 对象

### 建议：新增 `"proactive_push"` SSE 事件类型 + 插件新发送机制

放弃 D06（复用 reply 事件类型），改为：

1. **Core 侧**：`NotificationDispatcher` publish 新事件类型 `"proactive_push"`，payload 携带 `conversation_id` + `content`（而非依赖 reply 的 registry 查找机制）
2. **插件侧**：SSEListener 新增 `_handle_proactive_push()` handler，走 AstrBot Context API 直接向指定 conversation 发消息，**不依赖 `_event_registry`**
3. **AstrBot Context API**：需要调研 `star.Context` 是否提供 `send_message(conversation_id, text)` 类 API。如果 AstrBot 框架不支持主动发送，则需要通过 NapCat 的 HTTP API 直接发消息（`/send_private_msg` / `send_group_msg`），跳过 AstrBot 的 event 机制

**这一改动是整个需求能否落地的关键前提。** 不解决插件侧的发送通道，后端再完善也推不到用户。

## 🟡 需修正的设计决策

### 1. D06"复用 reply 事件类型"应推翻

原因已如上述。补充一点：`reply` 事件的语义是"对入站消息的回复"，`proactive_push` 是"系统主动推送"，两者的生命周期、路由逻辑、依赖上下文完全不同。强行复用 `reply` 会让 handler 里充满 `if/else` 分支判断是回复还是推送，违反单一职责。

### 2. D03"调度并入 PlanTaskScheduler tick"需审慎

**合理性**：避免新建调度器，共享 advisory lock — 思路正确。

**风险**：
- 当前 `_tick()` 已有 7 个步骤，加上通知扫描变成 8 个。如果通知投递某条卡住（如 OutboundEventBus publish 超时），会延迟后续所有 tick 逻辑（超时提醒、循环生成等）
- 通知投递和计划任务在业务优先级上不同——通知可以容忍秒级延迟，但超时提醒是刚性的

**建议**：仍并入 `_tick()`，但 **通知扫描放在 tick 末尾**，且 `NotificationDispatcher.tick()` 内部严格超时控制（如单次总耗时 ≤ 5s，单条投递 ≤ 500ms）。当前需求 §10 的"单次 tick 50 条上限"已有此意图，建议明确写入代码约束。

### 3. 离线降级机制与 agent_issues 的合并时机

需求 §7 提到"与 agent_issue 的上线触发共用同一拦截点"，但 **agent_issues 模块尚未实现**（无表、无服务、无 API）。`_check_pending_issues()` 只是设计规范中的提议。

**建议**：Phase 1 的离线降级只做通知自身的上线补推，**不与尚未存在的 agent_issues 合并**。在 SessionAgent 入口新增 `_check_failed_notifications(user_id)` 方法，独立实现。待 agent_issues 落地后（Phase 2），再将两者合并为统一的 `_check_pending_items(user_id)`。避免两个未实现模块互相耦合。

## 🔵 补充建议

### 1. 优先修复现有 PlanTaskScheduler 通知

当前 PlanTaskScheduler 的超时/截止提醒已经是坏的（user_id 键无法路由），这是生产 bug。建议 Phase 1 优先将 PlanTaskScheduler 的现有通知迁移到 NotificationService，而非等全模块接入。这同时验证了新机制的端到端通路。

### 2. conversation_id 的双重含义需显式区分

当前系统中 `conversation_id` 有两层含义：
- **IM 平台 conversation_id**：QQ 的会话标识（如 `private_123456`），`conversations.conversation_id` 存的就是这个
- **Core 内部 conversation_id**：`SessionPoolManager._sessions` 字典的 key，也是 `StandardMessage.conversation_id`

`UserConversationResolver` 解析出的应该是 **IM 平台 conversation_id**（插件用这个定位 IM 会话），而非 Core 内部的 UUID。需求文档没有明确这一点，建议在 `target_conversation_id` 字段注释中标明是 IM 平台 ID。

### 3. 考虑通知去重

计划任务超时提醒可能被重复触发（每次 tick 扫描到同一超时任务）。当前 PlanTaskScheduler 用 `reminded_at` 标记防重，但 NotificationService 的 `enqueue()` 没有去重机制。建议：
- `enqueue()` 增加 `dedup_key` 可选参数（如 `f"plan_task:overdue:{instance_id}"`）
- 入库前查 `WHERE source_module=... AND source_id=... AND status='PENDING'` 防止重复入队

### 4. REST 端点的必要性存疑

`POST /api/v1/notifications`（管理员手动创建）和 `GET /api/v1/notifications/stats` 在 Phase 1 的价值不大。建议 Phase 1 只做 `GET /api/v1/notifications`（列表查询 + 失败排查），其余端点推迟到 Phase 2。减少首批交付范围。

### 5. metadata_json 中的 delivered_on_login 标记有并发风险

§7 离线降级中，`metadata_json.delivered_on_login = true` 的更新是非原子的（读 JSON → 改字段 → 写回）。如果同一用户同时触发两条通知的上线补推，可能互相覆盖。建议用 `notification_delivery_logs` 新增一条 `result="DELIVERED_ON_LOGIN"` 的投递记录代替修改 metadata_json。

## 修正后的核心架构建议

```
业务模块 → NotificationService.enqueue() → notification_queue (PENDING)
    ↓ NotificationDispatcher.tick()（并入 PlanTaskScheduler tick 末尾）
    ├─ UserConversationResolver.resolve(user_id) → im_conversation_id
    ├─ outbound_bus.publish("proactive_push", {       ← 新事件类型，不复用 reply
    │      "conversation_id": im_conversation_id,
    │      "content": "...",
    │   })
    └─ 写 delivery_log + 更新 status

SSEListener._handle_proactive_push(data):              ← 插件新增 handler
    → 走 AstrBot Context API / NapCat HTTP API          ← 不依赖 _event_registry
    → 直接向 IM conversation 发送文本
```
