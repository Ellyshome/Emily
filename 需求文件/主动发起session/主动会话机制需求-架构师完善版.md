# 主动通知投递机制 — 需求规格说明书 v2.0

> 原始需求：[主动会话机制需求.md](主动会话机制需求.md) | 本文档为架构师完善版 | 最后更新：2026-06-26
>
> **v1.0 → v2.0 关键变更**：废弃"复用全局状态机 sm_nodes 表"方案（语义滥用，污染全景图）；废弃"预创建 Session 执行 initial_prompt"方案（与 SessionAgent 契约不匹配）；改为**独立轻量通知队列 + OutboundEventBus 直推**。

---

## 1. 背景与目标

### 1.1 痛点

当前系统主动触达用户的能力分散且不持久：
- 计划任务超时提醒通过 `OutboundEventBus` 直发，**用户不在线则消息丢失**
- 协同待办（agent_issues）、权限审批等模块各自实现通知，**逻辑不统一**
- 无持久化记录，无法追溯"通知是否送达、何时送达"

### 1.2 目标

建立统一的**主动通知投递机制**（Proactive Notification Delivery），实现：
- **持久化**：通知落库，用户离线不丢失
- **统一入口**：各业务模块通过单一 `NotificationService` 接入
- **零 LLM 消耗**：纯文本通知直推，不走 4 节点管道
- **复用现有出站通道**：`OutboundEventBus` + 插件 `SSEListener` 已支持无入站推送
- **可追溯**：每条通知有状态机（PENDING→SENT/FAILED/EXPIRED）+ 审计

### 1.3 与协同待办模块的关系

| 模块 | 角色 | 类比 |
|------|------|------|
| Agent 协同待办 (`agent_issues`) | **数据源**——"有什么事要人处理" | What |
| 主动通知投递 (`notification_queue`) | **投递通道**——"把事推送给对应的人" | How |

创建一个 agent_issue 时，顺带 enqueue 一条 notification 给 assignee。两者**不做成两个平行体系**，而是"事项 → 通知"的上下游。

## 2. 核心概念

### 2.1 主动通知

系统主动向用户推送的消息，区别于用户发起对话后的被动回复。

### 2.2 触发源

| 来源模块 | 典型场景 | 优先级 |
|----------|----------|--------|
| 计划任务 (`plan_task`) | 超时提醒、升级通知、周期实例生成 | HIGH/NORMAL |
| 协同待办 (`agent_issue`) | 待办提醒、审批通知、拒绝回执 | NORMAL |
| 权限系统 (`permission`) | 权限申请审批、异常数据审批 | HIGH |
| 全局状态机 (`state_machine`) | 阶段闭环提醒、关键路径延期预警 | NORMAL |
| 其他业务模块 | — | NORMAL |

### 2.3 投递模型（fire-and-forget 为主）

绝大多数主动通知是**一次性推送**（"任务X已超时"），不需要多轮交互。极少数需要用户交互的场景（如审批），由**用户回复时的入站消息**自然创建 Session 处理——Session 始终被动创建，不预创建。

## 3. 架构设计

### 3.1 整体架构

```
┌─────────────────────────────────────────────────────────────┐
│  业务模块层                                                  │
│  plan_task / agent_issue / permission / state_machine        │
└──────────────────────┬──────────────────────────────────────┘
                       ↓ NotificationService.enqueue(...)
┌─────────────────────────────────────────────────────────────┐
│  NotificationService（统一入口）                             │
│  · 校验 + 落库 notification_queue (status=PENDING)          │
│  · 关联 source_module / source_id                           │
└──────────────────────┬──────────────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────────────┐
│  NotificationDispatcher（调度投递）                          │
│  并入 PlanTaskScheduler 的 tick 循环（共享 advisory lock）   │
│  · 扫描 PENDING 且 scheduled_at <= now                      │
│  · UserConversationResolver 解析 user_id → conversation_id  │
│  · publish 到 OutboundEventBus("reply", {...})              │
│  · 标记 SENT / FAILED / EXPIRED                             │
└──────────────────────┬──────────────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────────────┐
│  出站层（复用现有）                                          │
│  OutboundEventBus → SSE /events/outbound → 插件 SSEListener  │
│  → AstrBot → IM 推送                                        │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 设计原则

1. **不预创建 Session**：通知直接 publish 到 OutboundEventBus，插件按 conversation_id 派发到 IM
2. **不经过 4 节点管道**：纯文本通知，零 LLM 消耗、零 WorkItem
3. **独立轻量表**：不复用 sm_nodes（避免污染全景节点图）
4. **调度器复用**：并入 `PlanTaskScheduler` tick，不新建平级调度器
5. **离线降级**：用户无可用 conversation 时降级为"上线触发提示"（复用 agent_issue 的上线机制）

## 5. 状态机

### 5.1 状态枚举

```
PENDING → SENT     （终态，投递成功）
PENDING → FAILED   （终态，重试耗尽）
PENDING → EXPIRED  （终态，超时未投递）
```

| 状态 | 含义 | 谁触发 |
|------|------|--------|
| `PENDING` | 已入队，等待投递 | NotificationService.enqueue |
| `SENT` | 已 publish 到 OutboundEventBus（终态） | NotificationDispatcher |
| `FAILED` | 重试耗尽仍失败（终态） | NotificationDispatcher |
| `EXPIRED` | 超过 expires_at 仍未投递（终态） | 过期扫描 |

### 5.2 转移矩阵

```python
TRANSITIONS = {
    PENDING: [SENT, FAILED, EXPIRED],
    SENT:    [],   # 终态
    FAILED:  [],   # 终态
    EXPIRED: [],   # 终态
}
TERMINAL_STATES = {SENT, FAILED, EXPIRED}
```

### 5.3 重试策略

| 失败类型 | 重试次数 | 退避 |
|----------|----------|------|
| 会话解析失败（用户无可用 conversation） | 0 | 不重试，降级上线提示 |
| OutboundEventBus publish 异常 | 3 | 指数退避 30s / 2min / 10min |
| 其他未知异常 | 2 | 1min / 5min |

重试耗尽 → `FAILED`，记录 `fail_reason`。

## 6. 核心组件

### 6.1 NotificationService（统一入口）

```python
class NotificationService:
    """主动通知统一入口——业务模块通过此服务投递通知。"""

    def __init__(self, repo: NotificationRepository, config: Config):
        self._repo = repo
        self._config = config

    async def enqueue(
        self,
        target_user_id: str,
        content: str,
        *,
        priority: str = "NORMAL",
        source_module: str = "",
        source_id: str = "",
        scheduled_at: str | None = None,   # None=立即
        expires_at: str | None = None,     # None=默认7天
        metadata: dict | None = None,
    ) -> str:
        """
        入队一条主动通知。

        Returns:
            notify_no: 通知编号 NTF-YYYYMMDD-NNNN
        """
```

### 6.2 UserConversationResolver（会话解析）

解决 v1.0 遗留的 `user_id → conversation_id` 错位问题。

```python
class UserConversationResolver:
    """解析用户 ID 到可投递的 IM 会话 ID。"""

    async def resolve(self, user_id: str) -> str | None:
        """
        解析优先级：
          1. 该用户的私聊 conversation（conversations.conversation_type='private'）
          2. 该用户最近活跃的群聊（按 messages.created_at desc）
          3. 都没有 → 返回 None（降级上线提示）

        Returns:
            conversation_id 或 None
        """
```

查询基础：`user_im_bindings`（IM 账号）+ `conversations`（会话）+ `messages`（最近活跃）。

### 6.3 NotificationDispatcher（投递调度）

**并入 `PlanTaskScheduler` 的 tick 循环**，不新建独立调度器。在 `PlanTaskScheduler._tick()` 中追加一步通知扫描，或共享 advisory-lock 模式新建轻量 tick。

```python
class NotificationDispatcher:
    """通知投递调度器——扫描 PENDING 通知并投递。"""

    def __init__(
        self,
        repo: NotificationRepository,
        resolver: UserConversationResolver,
        outbound_bus: OutboundEventBus,
        config: Config,
    ): ...

    async def tick(self) -> int:
        """
        单次调度：
          1. 过期扫描：PENDING + expires_at < now → EXPIRED
          2. 投递扫描：PENDING + scheduled_at <= now，按 priority 排序，限 50 条
          3. 对每条：
             a. resolve(user_id) → conversation_id（None 则降级 + 标记 FAILED）
             b. outbound_bus.publish("reply", {conversation_id, content})
             c. 成功 → SENT；失败 → retry_count++ 或 FAILED
          4. 写 delivery_log

        Returns:
            本轮投递成功数
        """
```

### 6.4 OutboundEventBus 事件复用

通知投递**复用现有的 `reply` 事件类型**，不新增事件类型：

```python
self._outbound_bus.publish("reply", {
    "conversation_id": conversation_id,
    "content": notification.content,
    "reply_to_message_id": None,   # 主动消息不引用
})
```

插件 `SSEListener` 已按 conversation_id 派发，无需改动。

## 7. 离线降级：上线触发提示

当 `UserConversationResolver.resolve()` 返回 None（用户从未与 Emily 对话，无可用会话），通知标记 `FAILED` + `fail_reason="no_resolvable_conversation"`，同时：

1. 在 `metadata_json` 中保留通知内容
2. 用户首次向 Emily 发消息时，`SessionAgent.handle()` 前置检查该用户的 `FAILED` 通知：
   ```
   ⚠ 您之前有 2 条未送达通知：
   1. [超时提醒] 任务「周报」已超时（06-20）
   2. [待办] AIS-20260620-0001 需您审批
   ```
3. 提示后标记 `metadata_json.delivered_on_login = true`，避免重复提示

此机制与 Agent 协同待办的"上线触发"（`_check_pending_issues`）**共用同一拦截点**，统一在 SessionAgent 入口处理。

```python
    from .services.notification_service import NotificationService
    from .services.notification_dispatcher import NotificationDispatcher

    self._notification_repo = NotificationRepository()

    self._user_conversation_resolver = UserConversationResolver()
    self._notification_dispatcher = NotificationDispatcher(
        repo=self._notification_repo,
        resolver=self._user_conversation_resolver,

        config=self.config,
    )
    # 投递调度并入 PlanTaskScheduler tick（见 9.2）
```

### 9.2 调度器并入

`PlanTaskScheduler._tick()` 追加通知投递步骤：

```python
async def _tick(self) -> None:
    # ... 原有：advisory lock / 超时提醒 / 周期生成 / 升级 ...

    # 新增：主动通知投递
    if self._notification_dispatcher is not None:
        try:
            sent = await self._notification_dispatcher.tick()
            if sent:
                logger.info("NotificationDispatcher tick: sent %d", sent)
        except Exception as e:
            logger.warning("NotificationDispatcher tick failed: %s", e)
```

### 9.3 业务模块注入

`NotificationService` 实例注入到需要发通知的模块：
- `PlanTaskService` / `PlanTaskScheduler`
- `AgentIssueService`
- `PermissionService`
- `StateMachineService`（阶段闭环提醒）

## 10. 非功能要求

| 项 | 要求 |
|----|------|
| 调度间隔 | 复用 PlanTaskScheduler tick（默认 60s），可独立配置 `notification_tick_seconds` |
| 单次 tick 处理量 | 最多 50 条 PENDING（防止阻塞） |
| 幂等性 | SENT 终态不可重复投递；PENDING 投递时用 `WHERE status='PENDING'` 原子更新防并发 |
| 异常容错 | 单条通知失败不影响其他通知；失败写 delivery_log |
| 并发控制 | 复用 PlanTaskScheduler 的 PG advisory lock，避免多实例重复投递 |
| 持久化 | 通知 + 投递日志均落 PostgreSQL，容器重启不丢失 |
| 可观测 | 每次投递写 delivery_log；失败通知可在 REST 端点查询 |

## 12. 与现有模块关系

```
业务模块（plan_task / agent_issue / permission / sm）
    ↓ NotificationService.enqueue()
notification_queue 表（PENDING）
    ↓ NotificationDispatcher.tick()（并入 PlanTaskScheduler）
    ├─ UserConversationResolver.resolve(user_id)
    │   ├─ 私聊 conversation 优先
    │   ├─ 最近活跃群回退
    │   └─ 无 → 标记 FAILED + 降级上线提示
    ├─ OutboundEventBus.publish("reply", {conversation_id, content})
    │   ↓ SSE /events/outbound
    │   ↓ 插件 SSEListener
    │   ↓ AstrBot → IM 推送
    └─ 写 delivery_log + 更新 status
```

**关键边界**：
- **不碰 sm_nodes**：全局状态机只管工程节点进度，通知走独立表
- **不预创建 Session**：Session 始终由用户入站消息被动创建
- **不经过 4 节点管道**：通知是纯文本出站，零 LLM
- **不新建调度器**：复用 PlanTaskScheduler tick

## 13. 设计决策记录

| 编号 | 决策 | 理由 |
|------|------|------|
| D01 | 独立 `notification_queue` 表，不复用 sm_nodes | sm_nodes 是工程节点图谱（stage_id/precondition_score/owner），通知是任务队列，语义完全不同，混用会污染全景图查询和进度计算 |
| D02 | 通知直接 publish OutboundEventBus，不预创建 Session | SessionAgent.handle() 契约是处理入站消息（快回+意图+WorkItem），通知是 fire-and-forget 出站，无需 4 节点管道；预创建 Session 还需伪造 StandardMessage，杀鸡用牛刀 |
| D03 | 调度并入 PlanTaskScheduler tick，不新建独立调度器 | 两者都是"扫表 + advisory lock + 投递/触发"模式，新建平级调度器违反 DRY，且多一个 asyncio 循环增加运维负担 |
| D04 | user_id → conversation_id 由 UserConversationResolver 解析 | 现有架构以 conversation_id 为路由键，但业务模块只知 user_id；需解析层弥合，并处理"用户无可用会话"的离线降级 |
| D05 | 离线降级复用 agent_issue 的上线拦截点 | 两个模块的"用户上线时补推"逻辑同构，合并为 SessionAgent 入口统一处理，避免两套拦截逻辑 |
| D06 | 复用 `reply` 事件类型，不新增 SSE 事件 | 通知本质就是一条出站回复，插件 SSEListener 已按 conversation_id 派发，新增事件类型无收益反而增加插件改动 |
| D07 | 4 态状态机（PENDING/SENT/FAILED/EXPIRED），无 ACCEPTED | 通知是单向推送，无需"受理人接受"语义；交互由用户回复入站消息触发，那是 SessionAgent 的职责 |
| D08 | 通知与 agent_issue 是上下游而非平行 | agent_issue 回答"什么事"，notification 回答"怎么送达"；创建 issue 时顺带 enqueue 通知，不做成两个独立触达体系 |
