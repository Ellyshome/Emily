## 二、分维度审核

### 2.1 架构合理性 — 资深架构师

**审核结论**：✅ 通过（有改进建议）

**亮点**：
- "文件级依赖"打破传统的节点串行模式，允许多专业并行作业，消除等待浪费。§9.3 的对比示例非常有力：景观工程因只需 3 个文件就绪即可启动，比传统计划提早半个月
- 父子节点 + 权重驱动的进度聚合，支持从粗到细的计划粒度，且约束了最多 3 层深度防止过度嵌套
- 事件总线观察者模式（NodeEventBus → OutboundEventBus → 多渠道推送）与 Emily 现有 SSE 出站总线契合，可以复用现有的 `OutboundEventBus` 基础设施
- 依赖约束设计合理（子节点不依赖其他父节点、禁止自己依赖祖先），防止了常见的依赖混乱
- 软删除 + 只增不改的事件日志模式与 Emily 现有设计习惯一致

**建议**：
1. **旧 `sm_*` 模块清理需要完整梳理（⚠️）**：目前代码中仍存在对 `sm_*` 的引用，需要在 V2 实施前/同步完成清理。待清理范围至少包括：
   - 数据库：10 张 `sm_*` 表（`sm_nodes`, `sm_node_dependencies`, `sm_node_deliverables`, `sm_stages`, `sm_status_history`, `sm_audit_logs`, `sm_simulation_results`，以及运维相关的 `ops_*` 如有引用）
   - ORM 模型：`models.py` 中对应 class 定义
   - 代码引用：如 `permission_service.py` 中的 `_derive_authorized_nodes`、`bus.py` 中的 `add_nodes` 等
   - 初始化/导入脚本：`import_nodes.py` 等
   - 路由端点：如有暴露的 `sm_*` 相关 REST API
2. **缺少 `project_id` 外键（❌）**：`project_nodes` 表没有项目归属字段。Emily 是多项目系统（`projects` 表已存在），节点必须归属到项目。建议增加 `project_id VARCHAR FK→projects.id`。
3. **3 态模型是否足够？（⚠️）**：V2 只有 条件不足→进行中→已完成 三态。实际工程中"阻塞"（BLOCKED，因外部因素无法推进）是高频场景。旧模块有 5 态正是因为实际需求。建议在文档中说明 V2 三态模型如何处理阻塞场景——是通过状态标记字段（如 `is_blocked`）？还是将阻塞归入"进行中"的某种子状态？或认为阻塞就是"条件不足"（因新增阻塞条件导致前置不满足）？
4. **阶段管理被简化为 `stage_id INT`**：旧 `sm_stages` 有完整的阶段元数据（进度/关键路径/边界条件）。V2 将阶段退化为一个标记字段，需明确：阶段级别的进度汇总、阶段间流转、阶段闭环条件由哪个模块负责？是前端计算？还是后端另有阶段服务？

### 2.2 数据设计 — DBA

**审核结论**：⚠️ 有改进空间

**亮点**：
- `node_dependencies` 的 UNIQUE(node_id, depends_on_deliverable_id) 约束防止重复依赖 ✅
- 时间戳使用字符串（与 Emily 现有 ISO8601 约定一致）✅
- JSON 数组用于列表字段（与现有模式如 `files.related_company_ids` 一致）✅
- 索引设计覆盖了主要查询路径（按状态、阶段、部门、父节点）✅
- 文件关联的 `source_module_id` + `source_module_type` 二元组提供灵活的溯源机制 ✅

**问题**：
1. **`depends_on_node_id` 冗余字段的数据一致性风险（⚠️）**：文档标注为"冗余字段，便于查询"。当 deliverable 的 node_id 变更时需同步更新此冗余字段。建议要么去掉（接受一次 JOIN，带索引的 JOIN 性能可接受），要么在文档中明确"由应用层事务包裹保证一致性"。
2. **`accessible_file_ids` TEXT JSON 数组的扩展性问题（⚠️）**：一个节点可能有几十甚至上百个文件。TEXT 存储 JSON 数组会变得臃肿，且 JSON 内查询无法使用索引。建议改为 M:N 中间表 `node_accessible_files(node_id VARCHAR, file_id VARCHAR, added_by VARCHAR, added_at VARCHAR)`，加索引 `idx_naf_file(file_id)`。
3. **`progress DECIMAL(5,2)` 语义需明确**：是百分比（0.00-100.00）还是比率（0.00-1.00）？现有系统 `plan_items.progress INTEGER 0-100`，建议统一为 `DECIMAL(5,2) 0.00-100.00` 并在文档中注明范围。
4. **缺少外键约束声明**：以下应明确声明 FK 关系：
   - `depends_on_deliverable_id` → `node_deliverables.deliverable_id`
   - `parent_node_id` → `project_nodes.node_id`
   - `startup_doc_id` → `files.id`
   - `owner_dept_id` → `company_info.id`（或对应部门表）
   - `related_company_id` → `company_info.id`
5. **VARCHAR(50) PK 边界**：`node_id VARCHAR(50)` 当前示例（SG-JG-01）只有 9 字符，但复杂项目编号可能超限。建议放宽至 VARCHAR(100) 或明确编码规范约束所有编号 ≤ 50 字符。
6. **`child_weight DECIMAL(3,2)` 精度限制**：范围仅 0.00-9.99。如果父节点有超过 10 个子节点，精度不够。建议改为 DECIMAL(5,4) 或约束每个父节点最多 10 个子节点。
7. **时间字段类型不一致**：`deadline`、`created_at`、`approved_at`、`completed_at` 均用 VARCHAR(50)，建议统一标注格式规范（如 ISO8601），确保与 Emily 现有 `_utc_now()` / `_beijing_now()` 的约定一致。

### 2.3 实现可行性 — 经验丰富的程序员

**审核结论**：⚠️ 有改进空间

**亮点**：
- 循环依赖检测（BFS 遍历）实现路径清晰，有明确的阻止条件
- 父子进度加权汇总公式明确可编码（`Σ(子节点进度 × 权重) / Σ(权重)`）
- 状态自动流转规则有明确的数学定义（前置满足度、成果完成度的计算公式）
- 权限矩阵（§4.2）角色-操作映射表可直接编码为鉴权逻辑

**建议**：
1. **"SOP标准化处理模块"难度需正视（⚠️）**：需求要求支持 xlsx/pdf/docx/md/txt 多格式解析 → 提取节点数据 → 自动映射到标准模板 → 智能推理补全缺失字段 → 生成标准化文档 → 版本管理。这本质上是 **文档理解 + 结构化提取 + 模板引擎 + 版本控制系统**，复杂度远高于普通的 CRUD 模块。建议分阶段：Phase 1 仅支持 xlsx + md，Phase 2 再覆盖 pdf/docx+口述引导。
2. **文件级依赖的连锁状态更新需要性能设计**：当节点数量达到 ~90+ 且有子节点时，每次文件上传都可能触发从子节点 → 父节点 → 依赖该节点的下游节点的递归重算。建议在需求中明确：① 最大递归深度上限 ② 批量更新机制（同一批文件上传只触发一次全量重算）③ 缓存策略。
3. **与现有 Emily 权限系统（v2.0 6级树形继承）的对接需明确**：现有系统有 `permission_groups` + `sop_permission_bindings` + 6级树形继承 + `auth_engine` 鉴权。V2 的权限控制（§4.2）定义了节点级别的角色权限，但未说明是否要对接现有鉴权基础设施。建议明确：节点操作是否走 `auth_engine.authorize()`？节点角色权限是复用 `permission_groups` 还是全新实现？
4. **事件总线与现有 SSE 出站总线的对接**：V2 的 NodeEventBus → OutboundEventBus 架构与 Emily 现有的 `OutboundEventBus`（`asyncio.Queue` pub/sub）概念契合。建议在需求中明确复用的接口约定，避免重复造轮子。

### 2.4 需求完整性 — 产品分析师视角

**缺失章节**：

   - `POST /api/v1/project-nodes/{node_id}/dependencies` 添加依赖
   - `DELETE /api/v1/node-dependencies/{id}` 移除依赖
   - `POST /api/v1/project-nodes/{node_id}/children` 挂载子节点
   - SSE 端点 `GET /api/v1/events/nodes` 的事件消息 JSON schema
2. **测试策略**：完全没有涉及测试。关键路径（状态流转、循环依赖检测、父子进度聚合、并发更新）的测试策略应该作为需求的一部分。
3. **验收标准**：每个功能模块应有明确的验收条件（如"给定节点A依赖文件F1和F2，当F1上传完成而F2未上传时，节点A应保持条件不足状态"）。
4. **错误处理**：未定义异常场景的处理方式——如循环依赖被阻止时的错误返回格式、文件上传失败对节点状态的影响、依赖的成果被删除时的级联处理。
