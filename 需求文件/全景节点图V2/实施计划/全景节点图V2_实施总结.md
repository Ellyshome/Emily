### 4.2 三态流转机制

```
                   ┌──────────────────────┐
                   │  CONDITIONS_NOT_MET  │  ← 前置依赖未满足
                   │     （条件不足）       │     或成果进度 < 100%
                   └──────────┬───────────┘
                              │
                  依赖全部满足 │ + 至少定义了一个成果
                              │
                              ▼
                   ┌──────────────────────┐
          ┌───────│     IN_PROGRESS      │
          │        │     （进行中）         │
          │        └──────────┬───────────┘
          │                   │
          │   阻塞条件出现      │ 所有必需成果 100% 完成
          │   (权重999依赖)     │
          │                   ▼
          │        ┌──────────────────────┐
          └───────►│     COMPLETED        │  ← 终态
                   │     （已完成）         │
                   └──────────────────────┘
```

**阻塞机制**：通过添加一条 `weight=999` 的依赖实现。状态机会因"前置满足度 < 1.0"自动从 IN_PROGRESS 回退到 CONDITIONS_NOT_MET。不新增额外的 BLOCKED 状态。

### 4.3 父子层级与进度汇总

- **嵌套深度上限 3 层**，每层子节点上限 100 个
- 子节点进度更新后，**自动向上递归重算祖先进度**（最多 3 层）
- 父节点进度 = Σ(子节点进度 × 子节点权重) / Σ 子节点权重
- 所有子节点 CONDITIONS_NOT_MET → 父节点 CONDITIONS_NOT_MET
- 所有子节点 COMPLETED → 父节点 COMPLETED
- 其他情况 → 父节点 IN_PROGRESS

### 4.4 权限访问控制

- 通过 `PermissionAuthEngine.check_access(resource_type="NODE", ...)` 统一鉴权
- 映射到现有 6 级权限体系（Level0 管理员→Level4 经办人）
- fail-open：鉴权异常时放行，不阻塞业务
- 权限检查在 Application 层统一执行，REST API 和 WorkItem 工具调用均受管控
