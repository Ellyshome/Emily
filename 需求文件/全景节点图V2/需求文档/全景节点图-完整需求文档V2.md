## 一、核心概念

### 1.0 核心理念（项目实施计划编制指导原则）

> **依赖不锁定节点，锁定具体成果文件**

这是本状态机系统最核心的设计原则，用于颠覆传统项目计划编制模式：

| 传统项目计划 | 本系统模式 |
|:-----------|:----------|
| ❌ 节点串行，必须等上游节点100%完成才能启动 | ✅ 只要需要的成果文件就绪，立即启动 |
| ❌ 编制粗粒度节点，不关心中间产出 | ✅ 每个节点明确定义所有产出成果，按需依赖 |
| ❌ 关键路径僵化，容易出现等待浪费 | ✅ 各专业并行作业，消除等待浪费 |
| ❌ 进度判断靠"感觉" | ✅ 进度判断靠"文件是否上传" |

---

### 1.1 全景节点图定义
- 是由各独立节点联合组成的有向无环图（DAG）
- 节点无法单独存在，必须与现有节点有联系
- 节点关联通过**前置条件**或**产出成果**作为连接纽带
  - 即：节点A产出的**具体成果文件** → 成为 → 节点B的前置条件
- 依赖不锁定节点，锁定具体成果文件
- 节点与联系可增删改
- 多节点可组成阶段
- **多项目隔离**：所有节点归属到具体项目

### 1.2 节点树状结构（父子节点）
- 节点支持父子层级关系（父节点ID外键）
- 一个父节点可挂载 N 子任务节点
- 子节点进度自动加权汇总到父节点

#### 子节点本质：同一个任务的粒度拆分
> 子节点不是"另一个独立任务"，而是**把一个大节点拆解成更细的并行执行单元**

```
示例：
【父节点】SG-002 主体结构施工
    ├── 【子节点1】SG-002-01 钢筋绑扎
    ├── 【子节点2】SG-002-02 模板支设
    └── 【子节点3】SG-002-03 混凝土浇筑
```

三个子节点**共同构成**"主体结构施工"这个大任务，而非三个独立的前后置任务。

---

### 1.3 关键区别：父子关系 VS 依赖关系

| 维度 | 父子关系（parent_node_id） | 依赖关系（node_dependencies） |
|:-----|:-------------------------|:----------------------------|
| **语义** | 整体 vs 部分（分解关系） | 前序产出成果 → 触发后序启动 |
| **依赖粒度** | 节点级 | 文件级（依赖具体成果文件，不锁定节点） |
| **执行方式** | 并行执行 | 按需并行，只要所需文件就绪即可启动 |
| **示例** | 钢筋/模板/混凝土 都是"主体结构"的一部分 | 景观施工图上传完成 → 景观工程立即启动（无需等设计节点100%完成） |
| **进度计算** | 加权平均汇总到父节点 | 按依赖的每个文件上传完成度 × 权重计算 |
| **状态流转** | 子节点集体完成 → 父节点才算完成 | 所需文件全部就绪 → B从"条件不足"→"进行中" |

### 1.5 子节点设计边界与约束

#### 约束1：嵌套深度限制（最多3层）
```
✅ 推荐：阶段 → 父节点 → 子节点
❌ 禁止：阶段 → 节点 → 子节点 → 孙子节点 → 曾孙节点...
```
> 原因：避免进度计算性能问题 + 用户认知负担 + 循环依赖检测复杂度

#### 约束2：前置条件范围限制
- ✅ **允许**：子节点的前置条件是自己的**兄弟节点**
- ❌ **禁止**：子节点的前置条件是**其他父节点**
  - 正确做法：由父节点去依赖其他父节点，子节点继承父节点的前置状态

#### 约束3：每个子节点有独立的成果与负责人
- 每个子节点有自己独立的 `node_deliverables`（产出成果）
- 子节点完成 = 自己的成果 100% 达成
- 子节点可以有独立于父节点的 `owner_dept`（主责条线/负责人）

#### 约束4：无子节点的退化模式
- 如果一个节点没有任何子节点 → 退化为**普通节点模式**
- 状态由自身的**前置条件**和**产出成果**直接决定（兼容基础逻辑）

#### 约束5：子节点数量上限
- 每个父节点最多 100 个子节点

## 二、节点状态机

### 2.1 三态流转模型（含阻塞场景处理）

节点是个简单状态机，具备核心三态：

| 状态 | 说明 | 流转条件 |
|:-----|:-----|:---------|
| **条件不足** | 前置条件未满足 / 被阻塞，无法开始 | 默认初始状态 / 新增阻塞条件导致 |
| **进行中** | 前置条件已满足，工作执行中 | 前置条件为空 OR 前置条件具备 → 自动流转 |
| **已完成** | 所有必需产出成果100%达成 | 产出成果达成度 ≥ 100% → 自动流转 |

```
条件不足 ──(前置满足)──→ 进行中 ──(成果100%)──→ 已完成
     ↑                        ↑
     └────(新增阻塞条件)──────┘
```

#### 阻塞场景处理方案
> 实际工程中的"阻塞"（BLOCKED）场景通过以下机制处理：
> 1. 向 `node_dependencies` 表**新增一个人工依赖项**（如"甲方设计变更确认单"）
> 2. 该依赖项权重设为 999（确保满足度达不到 1.0）
> 3. 节点自动从「进行中」回退到「条件不足」状态
> 4. 阻塞解除后，删除该人工依赖项，节点自动恢复流转

> **设计考量**：保持三态模型简洁，不新增状态枚举。阻塞本质上就是"新增了一个不满足的前置条件"，通过依赖机制统一处理，避免状态爆炸。

### 2.2 状态机特性
- 状态流转**自动触发**，无需人工操作状态
- 事件、状态**可被订阅**，有更新则主动推送
- 支持循环依赖检测（防止死锁）

### 3.3 表2：`node_dependencies` 前置依赖表

> **核心机制**：依赖不锁定节点，锁定具体的成果文件。下游节点无需等待上游节点全部完成，只要需要的成果文件就绪即可启动。

| 字段名 | 类型 | 可空 | 默认值 | 说明 |
|:-------|:-----|:-----|:-------|:-----|
| id | VARCHAR(100) | ❌ | - | 主键 |
| node_id | VARCHAR(100) | ❌ | - | 本节点（下游节点，外键→project_nodes.node_id） |
| depends_on_deliverable_id | VARCHAR(100) | ❌ | - | 依赖的成果文件ID（**外键→node_deliverables.deliverable_id**） |
| depends_on_node_id | VARCHAR(100) | ❌ | - | 成果所属的上游节点ID（外键→project_nodes.node_id） |
| dependency_type | VARCHAR(20) | ❌ | 'DELIVERABLE' | 依赖类型：DELIVERABLE（成果依赖） / TIME（时间依赖） |
| weight | DECIMAL(5,4) | ❌ | 1.0000 | 权重（0.0000-1.0000） |
| created_at | VARCHAR(50) | ❌ | - | 创建时间（ISO8601） |

**约束**
- UNIQUE(node_id, depends_on_deliverable_id) - 防止对同一成果的重复依赖

#### 设计说明

1. **文件级粒度依赖**：
   - 一个上游节点可产出多个成果文件
   - 下游节点按需依赖其中的一个或多个文件
   - 只要依赖的文件就绪，节点即可启动，无需等上游节点整体完成

2. **冗余字段一致性保证**：
   - `depends_on_node_id` 虽为冗余（可通过 deliverable JOIN 查到），但为简化查询保留
   - **一致性机制**：所有依赖增删改操作必须通过应用层事务包裹
   - 当 deliverable 的 node_id 变更时（罕见场景），必须同步更新此冗余字段
   - 备选方案：如性能可接受，可去掉此字段，查询时 JOIN `node_deliverables`

3. **典型场景示例**：
   ```
   景观工程节点(SG-001) 启动条件 = 以下3个文件全部就绪
     ├─ 景观施工图.pdf（来自景观设计节点 SJ-003，权重 0.4）
     ├─ 景观工程合同.pdf（来自成本合约节点 CB-002，权重 0.3）
     └─ 场地移交景观报告.pdf（来自工程总包节点 SG-000，权重 0.3）
   ```

## 四、核心业务规则

### 4.1 状态自动流转计算

#### 规则A：普通节点（无子节点）
直接由自身的前置条件和产出成果决定。

> **核心机制**：不依赖上游节点整体完成，只依赖具体成果文件是否就绪。

```
前置条件满足度 = Σ(依赖的成果文件是否已上传完成 × 权重)
```
- 满足度 ≥ 1.0 → 状态自动流转至「进行中」

```
单个成果完成度 = min(当前量 / max(目标量, 0.001), 1.0)
整体成果完成度 = Σ(必需成果的完成度) / max(必需成果总数, 1)
```
- 整体成果完成度 ≥ 1.0 → 状态自动流转至「已完成」

#### 规则B：有子节点的父节点
状态由所有子节点**集体决定**：

| 父节点状态 | 判定条件 |
|:----------|:---------|
| **条件不足** | 所有子节点都处于「条件不足」状态 |
| **进行中** | 至少有一个子节点处于「进行中」状态 |
| **已完成** | 所有**必需子节点**都处于「已完成」状态 |

> 注：子节点是否为"必需"，可由 `is_child_required` 字段标记（预留扩展），默认所有子节点都是必需的。

#### 父子节点进度联动
```
父节点进度 = Σ(子节点进度 × 子节点权重) / max(Σ(子节点权重), 0.0001)
```

#### 性能约束
- **最大递归深度**：子节点进度更新触发的祖先重算，最多递归 3 层（配合嵌套深度约束）
- **批量更新机制**：同一批文件上传只触发一次全量状态重算
- **缓存策略**：节点状态和进度计算结果缓存 TTL 5 分钟（或事件触发失效）

---

### 4.2 权限控制（与现有系统集成）

> **对接方案**：节点级权限操作复用现有鉴权基础设施
> - 权限定义复用 `permission_groups` 分组机制
> - 鉴权逻辑调用 `auth_engine.authorize()` 统一入口
> - 节点角色（负责人/上级/管理员）映射到现有权限级别

| 操作 | 允许角色（映射到现有权限级别） | 说明 |
|:-----|:------------------------|:-----|
| **子任务节点挂载** | 父节点主责条线负责人（Level3） + 负责人的上级领导（Level2） + 系统管理员（Level0） | 不能给别人的节点随便加子任务 |
| **编辑子节点字段** | 子节点自己的负责人（Level3） + 父节点负责人（Level3） + 系统管理员（Level0） | 子节点可以有独立的负责人 |
| **删除子节点** | 父节点负责人（Level3） + 系统管理员（Level0） | 删除前检查：已完成的子节点不可删除 |
| **调整父子关系（转移子节点）** | 原父节点负责人（Level3） + 新父节点负责人（Level3） + 系统管理员（Level0） | 不能随便"抢"别人的子节点 |
| 节点字段编辑 | 主责条线负责人（Level3） + 系统管理员（Level0） | - |
| 成果进度更新 | 主责条线负责人（Level3） + 指定经办人（Level4） | - |
| 节点废弃 | 项目总监（Level2） + 系统管理员（Level0） | - |
| 依赖关系调整 | 主责条线负责人（Level3） + 系统管理员（Level0） | - |

---

### 4.3 循环依赖检测
- 添加依赖时执行 BFS 遍历检测
- 父节点不能依赖自己的子节点（任何层级）
- 子节点不能依赖自己的祖先节点
- 发现循环依赖立即阻止并提示用户

---

### 4.4 阶段级进度管理

> 阶段退化为 `stage_id INT` 标记字段，阶段级汇总由应用层计算：

1. **阶段进度**：该阶段所有根节点（parent_node_id 为空）进度的加权平均
2. **阶段流转**：阶段内所有节点完成 → 自动标记为阶段完成
3. **阶段闭环条件**：阶段内所有必需成果 100% 上传完成

> **设计决策**：不单独建 `project_stages` 表，阶段定义与现有 `projects.lifecycle_stage` 枚举对齐。

---

### 4.5 错误处理与边界条件

| 异常场景 | 处理方式 |
|:---------|:---------|
| **循环依赖检测命中** | 阻止操作，返回清晰错误码 + 可视化依赖链路 |
| **文件上传失败** | 节点状态不变，记录失败事件，不触发重算 |
| **依赖的成果被软删除** | 自动将该依赖权重置为 0，不影响节点流转，记录警告事件 |
| **并发更新同一节点** | 乐观锁（基于 updated_at），冲突时重试 3 次后提示用户 |
| **子节点数量超限** | 阻止新增，提示超过 100 个子节点上限 |

## 五、数据录入形态（分阶段实施）

### 5.1 SOP标准化处理模块（分阶段实施计划）

> **复杂度评估**：多格式文档解析 → 结构化提取 → 智能补全 → 模板生成 → 版本管理，本质上是文档理解 + 结构化提取 + 模板引擎 + 版本控制系统。需分阶段实施，避免一次性复杂度过高。

| 阶段 | 范围 | 预期交付 |
|:-----|:-----|:--------|
| **Phase 1**（首发） | xlsx 格式解析 + Markdown 格式解析 | 支持 Excel 批量导入 + Markdown 节点定义 |
| **Phase 2**（后续迭代） | PDF/DOCX 解析 + 口述引导录入 | 支持文档智能提取 + 对话式录入 |

---

### 5.2 SOP标准化约束
无论采用何种录入方式，所有节点数据在进入状态机前必须经过标准化处理：

#### 5.2.1 标准节点文档生成
- **输入源支持（Phase 1）**：xlsx、md 文件提取
- **输入源支持（Phase 2）**：pdf、docx、txt、用户口述
- **标准化处理**：所有输入源均需参考标准模板（类似 `.env.example` 的模板机制）整理成统一格式的标准节点文档
- **文档留存**：标准化后的文档作为节点的「启动文档记录」，永久留存于状态机数据库
- **版本管理**：节点字段的任何变更都应生成新的文档版本，并保留完整历史记录

### 5.3 xlsx 文件导入（Phase 1 实现）
- 解析文件获取节点数据
- 根据标准模板自动填入标准化字段
- 缺失数据智能推理，生成补全建议供用户确认
- 支持批量导入后，自动生成依赖关系建议
- 支持父子节点层级的批量导入（通过编号识别层级关系）
- 导入完成后自动生成「启动文档记录」并存档

### 5.4 口述引导录入（Phase 2 实现）
- 对话式引导用户根据标准模板逐项填入
- 智能追问缺失信息
- 自动生成节点编号与依赖关系
- 支持"先创建父节点，再逐步加子节点"的渐进式录入
- 录入完成后自动生成「启动文档记录」并存档

## 六、结构化文件存储模块

### 6.1 文件关联与溯源机制

所有与节点绑定的文件必须记录其来源与关联关系，确保完整可追溯。

#### 6.1.1 文件关联字段
文件存储模块需为每条文件记录增加以下字段：

| 字段名 | 类型 | 可空 | 说明 |
|:-------|:-----|:-----|:-----|
| `source_module_id` | VARCHAR(100) | ✅ | 来源模块ID（节点ID/其他业务对象ID） |
| `source_module_type` | VARCHAR(50) | ❌ | 来源模块类型标识 |

#### 6.1.2 模块类型枚举
| 类型标识 | 说明 | 示例 |
|:---------|:-----|:-----|
| `NODE_STARTUP_DOC` | 节点启动文档记录 | 节点录入时生成的标准化文档 |
| `NODE_WORKLOAD_DOC` | 节点工作量申报文档 | 进度更新时上传的工作量证明材料 |
| `NODE_DELIVERABLE_DOC` | 节点成果物文档 | 节点产出的交付文件 |
| `NODE_ATTACHMENT` | 节点通用附件 | 节点相关的其他文件 |

### 6.2 文件访问权限控制

#### 6.2.1 权限控制机制

> **核心原则**：文件只对与之关联的节点的企业用户可见

| 权限维度 | 规则 |
|:---------|:-----|
| **默认可见范围** | 节点 `related_company_id`（关联单位）的所有员工用户，默认有权访问 `node_accessible_files` 表中关联的所有文件 |
| **跨企业隔离** | 文件与节点强绑定，其他节点关联单位的用户不可见 |
| **示例** | 「景观施工图」文件只对景观工程节点关联的景观单位员工可见，门窗单位员工不可见 |

#### 6.2.2 权限设置与修改

| 操作 | 允许角色 |
|:-----|:---------|
| **初始化文件列表** | 节点创建时自动关联相关文件 |
| **新增/移除可见文件** | 节点主责条线负责人 + 负责人的上级领导 |
| **批量调整权限** | 项目总监 + 系统管理员 |

#### 6.2.3 操作记录与追溯

所有权限变更操作都必须记录到 `node_events` 事件表：

| 事件类型 | 记录内容 |
|:---------|:---------|
| `FILE_ACCESS_ADDED` | 新增可见文件：文件ID、操作人、操作时间 |
| `FILE_ACCESS_REMOVED` | 移除可见文件：文件ID、操作人、操作时间 |
| `FILE_ACCESS_BATCH_UPDATED` | 批量更新文件列表：变更前后快照 |

---

### 6.3 文件存储规范

| 规范项 | 要求 |
|:-------|:-----|
| **文件格式支持** | xlsx、pdf、docx、md、txt、jpg、png 等常用格式 |
| **版本控制** | 同一节点同一类型文件多次上传需保留完整版本历史 |
| **存储路径** | 按节点ID分目录存储，便于检索 |
| **权限控制** | 文件访问权限继承节点的权限（负责人可上传/下载）+ `node_accessible_files` 白名单机制 |
| **删除机制** | 软删除机制，保留删除记录，不物理删除文件 |
| **修改机制** | 所有文件修改均采用"新增版本+标记旧版失效"方式，不覆盖原有文件 |
| **历史追溯** | 文件的所有版本、所有删除/修改操作都有时间戳和操作人记录，完整可查 |

---

### 6.4 与节点状态机的集成

1. **节点创建时**：自动生成「启动文档记录」并绑定 `startup_doc_id`
2. **节点更新时**：字段变更生成新的文档版本，记录变更历史
3. **成果上传时**：自动绑定 `NODE_DELIVERABLE_DOC` 类型
4. **进度申报时**：支持上传 `NODE_WORKLOAD_DOC` 工作量证明材料

## 九、项目实施计划编制指南

### 9.1 计划编制原则

| 原则 | 说明 |
|:-----|:-----|
| **成果导向原则** | 每个节点必须明确定义所有产出成果，不能只写"完成XX工作" |
| **最小依赖原则** | 只列出启动节点**真正需要**的前置文件，不要为了"保险"多加依赖 |
| **专业并行原则** | 跨专业节点尽可能并行，依赖具体文件而非整个节点完工 |
| **可验证原则** | 每个进度节点都必须对应可验证的文件上传，不能靠口头汇报 |

### 9.2 计划编制步骤

1. **步骤1：拆解节点**
   - 按专业/区域/工序拆分成合适粒度的节点
   - 设计父子节点层级（不超过3层，单父节点不超过100子节点）

2. **步骤2：定义成果**
   - 为每个节点列出所有产出成果文件
   - 为每个成果定义：名称、目标量、单位

3. **步骤3：建立依赖（最关键）**
   - 为每个节点找出：**少而准**的前置文件
   - 直接关联到具体成果的ID，不是关联到节点
   - 给每个依赖分配合理权重（总和建议为1.0，支持人工阻塞用大权重）

4. **步骤4：设定时间**
   - 为每个节点设定截止时间（ISO8601）
   - 关键路径节点可额外设置预警时间

### 9.3 编制示例（对比）

**❌ 传统计划（错误示范）**
```
节点：景观设计（8.1-8.30）
节点：景观工程（9.1-11.15）
  └─ 前置依赖：景观设计节点100%完成
```

**✅ 本系统计划（正确示范）**
```
节点：景观设计（8.1-8.30）
  └─ 产出成果：
      ├─ 景观施工图.pdf（预计8.15完成）
      ├─ 苗木清单.xlsx（预计8.20完成）
      └─ 景观概算.pdf（预计8.30完成）

节点：景观工程（8.16-11.15）
  └─ 前置依赖（共3个文件）：
      ├─ 景观施工图.pdf（来自景观设计，权重 0.4）
      ├─ 景观工程合同.pdf（来自成本合约，权重 0.3）
      └─ 场地移交报告.pdf（来自工程总包，权重 0.3）
```

> **效果**：景观工程在8.16就可以启动，比传统计划提早了半个月！

### 9.4 计划动态调整

本系统支持项目执行过程中的动态调整：
- 可随时新增/移除节点的依赖文件
- 可调整各依赖文件的权重
- 可随时新增子节点细化工作
- 所有调整自动记录在 `node_events` 事件表中，全程可追溯

## 十、测试策略与验收标准

### 10.1 关键路径测试用例

| 测试场景 | 输入 | 预期输出 |
|:---------|:-----|:---------|
| 前置文件逐个上传 | A依赖F1+F2，先传F1再传F2 | F1上传后A仍为条件不足；F2上传后A自动变为进行中 |
| 父子进度联动 | 子节点进度从50更新到100 | 父节点进度自动按权重重算 |
| 循环依赖检测 | A依赖B，B依赖C，C依赖A | 阻止操作，返回依赖链路错误 |
| 阻塞场景处理 | A在进行中，新增一个权重999的依赖 | A自动回退到条件不足 |
| 并发更新冲突 | 两个请求同时更新同一节点 | 乐观锁生效，只有一个成功，另一个提示重试 |

### 10.2 验收标准（按模块）

| 模块 | 验收条件 |
