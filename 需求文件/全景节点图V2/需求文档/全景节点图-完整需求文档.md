## 一、核心概念

### 1.0 核心理念（项目实施计划编制指导原则）

> **依赖不锁定节点，锁定具体成果文件**

这是本状态机系统最核心的设计原则，用于颠覆传统项目计划编制模式：

| 传统项目计划 | 本系统模式 |
|:-----------|:----------|
| ❌ 节点串行，必须等上游节点100%完成才能启动 | ✅ 只要需要的成果文件就绪，立即启动 |
| ❌ 编制粗粒度节点，不关心中间产出 | ✅ 每个节点明确定义所有产出成果，按需依赖 |
| ❌ 关键路径僵化，容易出现等待浪费 | ✅ 各专业并行作业，消除等待浪费 |
| ❌ 进度判断靠"感觉" | ✅ 进度判断靠"文件是否上传" |

---

### 1.1 全景节点图定义
- 是由各独立节点联合组成的有向无环图（DAG）
- 节点无法单独存在，必须与现有节点有联系
- 节点关联通过**前置条件**或**产出成果**作为连接纽带
  - 即：节点A产出的**具体成果文件** → 成为 → 节点B的前置条件
- 依赖不锁定节点，锁定具体成果文件（见上文核心理念）
- 节点与联系可增删改
- 多节点可组成阶段

### 1.2 节点树状结构（父子节点）
- 节点支持父子层级关系（父节点ID外键）
- 一个父节点可挂载 N 子任务节点
- 子节点进度自动加权汇总到父节点

#### 子节点本质：同一个任务的粒度拆分
> 子节点不是"另一个独立任务"，而是**把一个大节点拆解成更细的并行执行单元**

```
示例：
【父节点】SG-002 主体结构施工
    ├── 【子节点1】SG-002-01 钢筋绑扎
    ├── 【子节点2】SG-002-02 模板支设
    └── 【子节点3】SG-002-03 混凝土浇筑
```

三个子节点**共同构成**"主体结构施工"这个大任务，而非三个独立的前后置任务。

---

### 1.3 关键区别：父子关系 VS 依赖关系

| 维度 | 父子关系（parent_node_id） | 依赖关系（node_dependencies） |
|:-----|:-------------------------|:----------------------------|
| **语义** | 整体 vs 部分（分解关系） | 前序产出成果 → 触发后序启动 |
| **依赖粒度** | 节点级 | 文件级（依赖具体成果文件，不锁定节点） |
| **执行方式** | 并行执行 | 按需并行，只要所需文件就绪即可启动 |
| **示例** | 钢筋/模板/混凝土 都是"主体结构"的一部分 | 景观施工图上传完成 → 景观工程立即启动（无需等设计节点100%完成） |
| **进度计算** | 加权平均汇总到父节点 | 按依赖的每个文件上传完成度 × 权重计算 |
| **状态流转** | 子节点集体完成 → 父节点才算完成 | 所需文件全部就绪 → B从"条件不足"→"进行中" |

### 1.5 子节点设计边界与约束

#### 约束1：嵌套深度限制（最多3层）
```
✅ 推荐：阶段 → 父节点 → 子节点
❌ 禁止：阶段 → 节点 → 子节点 → 孙子节点 → 曾孙节点...
```
> 原因：避免进度计算性能问题 + 用户认知负担 + 循环依赖检测复杂度

#### 约束2：前置条件范围限制
- ✅ **允许**：子节点的前置条件是自己的**兄弟节点**
- ❌ **禁止**：子节点的前置条件是**其他父节点**
  - 正确做法：由父节点去依赖其他父节点，子节点继承父节点的前置状态

#### 约束3：每个子节点有独立的成果与负责人
- 每个子节点有自己独立的 `node_deliverables`（产出成果）
- 子节点完成 = 自己的成果 100% 达成
- 子节点可以有独立于父节点的 `owner_dept`（主责条线/负责人）

#### 约束4：无子节点的退化模式
- 如果一个节点没有任何子节点 → 退化为**普通节点模式**
- 状态由自身的**前置条件**和**产出成果**直接决定（兼容基础逻辑）

## 二、节点状态机

### 2.1 三态流转模型
节点是个简单状态机，具备三态：

| 状态 | 说明 | 流转条件 |
|:-----|:-----|:---------|
| **条件不足** | 前置条件未满足，无法开始 | 默认初始状态 |
| **进行中** | 前置条件已满足，工作执行中 | 前置条件为空 OR 前置条件具备 → 自动流转 |
| **已完成** | 所有必需产出成果100%达成 | 产出成果达成度 ≥ 100% → 自动流转 |

```
条件不足 ──(前置满足)──→ 进行中 ──(成果100%)──→ 已完成
```

### 2.2 状态机特性
- 状态流转**自动触发**，无需人工操作状态
- 事件、状态**可被订阅**，有更新则主动推送
- 支持循环依赖检测（防止死锁）

### 3.3 表2：`node_dependencies` 前置依赖表

> **核心机制变更**：依赖不锁定节点，锁定具体的成果文件。下游节点无需等待上游节点全部完成，只要需要的成果文件就绪即可启动。

| 字段名 | 类型 | 可空 | 默认值 | 说明 |
|:-------|:-----|:-----|:-------|:-----|
| id | VARCHAR(100) | ❌ | - | 主键 |
| node_id | VARCHAR(50) | ❌ | - | 本节点（下游节点） |
| depends_on_deliverable_id | VARCHAR(100) | ❌ | - | 依赖的成果文件ID（关联 node_deliverables 表） |
| depends_on_node_id | VARCHAR(50) | ❌ | - | 冗余字段，成果所属的上游节点ID（便于查询） |
| dependency_type | VARCHAR(20) | ❌ | 'DELIVERABLE' | 依赖类型：DELIVERABLE（成果依赖） / TIME（时间依赖） |
| weight | DECIMAL(3,2) | ❌ | 1.00 | 权重（0.00-1.00） |
| created_at | VARCHAR(50) | ❌ | - | 创建时间 |

**约束**
- UNIQUE(node_id, depends_on_deliverable_id) - 防止对同一成果的重复依赖

#### 设计说明

1. **文件级粒度依赖**：
   - 一个上游节点可产出多个成果文件

2. **典型场景示例**：
   ```
   景观工程节点(SG-001) 启动条件 = 以下3个文件全部就绪
     ├─ 景观施工图.pdf（来自景观设计节点 SJ-003）
   ```

#### 事件生命周期

```
1. 触发：用户操作 / 系统自动流转 → 产生事件
2. 发布：事件写入 NodeEventBus 内存总线
3. 推送：所有订阅者收到实时通知（前端/IM/第三方系统）
4. 持久化：事件立即写入 node_events 数据库表（最终归宿）
5. 查询：后续可按节点ID/时间/操作人/事件类型检索审计
```

> **关键特性**：所有事件只增不改，软删除也会记录为一条 DELETE 事件，原始记录永久保留。

## 四、核心业务规则

### 4.1 状态自动流转计算

#### 规则A：普通节点（无子节点）
直接由自身的前置条件和产出成果决定。

> **核心机制**：不依赖上游节点整体完成，只依赖具体成果文件是否就绪。

```
前置条件满足度 = Σ(依赖的成果文件是否已上传完成 × 权重)
```
- 满足度 ≥ 1.0 → 状态自动流转至「进行中」

```
单个成果完成度 = min(当前量 / 目标量, 1.0)
整体成果完成度 = Σ(必需成果的完成度) / 必需成果总数
```
- 整体成果完成度 ≥ 1.0 → 状态自动流转至「已完成」

#### 规则B：有子节点的父节点
状态由所有子节点**集体决定**：

| 父节点状态 | 判定条件 |
|:----------|:---------|
| **条件不足** | 所有子节点都处于「条件不足」状态 |
| **进行中** | 至少有一个子节点处于「进行中」状态 |
| **已完成** | 所有**必需子节点**都处于「已完成」状态 |

> 注：子节点是否为"必需"，可由 `is_child_required` 字段标记（预留扩展），默认所有子节点都是必需的。

#### 父子节点进度联动
```
父节点进度 = Σ(子节点进度 × 子节点权重) / Σ(子节点权重)
```
- 任何子节点进度更新 → 自动触发所有祖先节点进度重算
- 递归向上更新，直到根节点

---

### 4.2 权限控制（含子节点细化）

| 操作 | 允许角色 | 说明 |
|:-----|:---------|:-----|
| **子任务节点挂载** | 父节点主责条线负责人 + 负责人的上级领导 + 系统管理员 | 不能给别人的节点随便加子任务 |
| **编辑子节点字段** | 子节点自己的负责人 + 父节点负责人 | 子节点可以有独立的负责人 |
| **删除子节点** | 父节点负责人 + 系统管理员 | 删除前检查：已完成的子节点不可删除 |
| **调整父子关系（转移子节点）** | 原父节点负责人 + 新父节点负责人 + 系统管理员 | 不能随便"抢"别人的子节点 |
| 节点字段编辑 | 主责条线负责人 + 系统管理员 | - |
| 成果进度更新 | 主责条线负责人 + 指定经办人 | - |
| 节点废弃 | 项目总监 + 系统管理员 | - |
| 依赖关系调整 | 主责条线负责人 + 系统管理员 | - |

---

### 4.3 循环依赖检测
- 添加依赖时执行 BFS 遍历检测
- 父节点不能依赖自己的子节点（任何层级）
- 子节点不能依赖自己的祖先节点
- 发现循环依赖立即阻止并提示用户

## 五、数据录入形态

### 5.1 SOP标准化约束
无论采用何种录入方式，所有节点数据在进入状态机前必须经过标准化处理：

#### 5.1.1 标准节点文档生成
- **输入源支持**：xlsx、pdf、docx、md、txt 文件提取，或用户口述
- **标准化处理**：所有输入源均需参考标准模板（类似 `.env.example` 的模板机制，后期提供）整理成统一格式的标准节点文档
- **文档留存**：标准化后的文档作为节点的「启动文档记录」，永久留存于状态机数据库
- **版本管理**：节点字段的任何变更都应生成新的文档版本，并保留完整历史记录

### 5.2 xlsx 文件导入
- 解析文件获取节点数据
- 根据标准模板自动填入标准化字段
- 缺失数据智能推理，生成补全建议供用户确认
- 支持批量导入后，自动生成依赖关系建议
- 支持父子节点层级的批量导入（通过编号识别层级关系）
- 导入完成后自动生成「启动文档记录」并存档

### 5.3 口述引导录入
- 对话式引导用户根据标准模板逐项填入
- 智能追问缺失信息
- 自动生成节点编号与依赖关系
- 支持"先创建父节点，再逐步加子节点"的渐进式录入
- 录入完成后自动生成「启动文档记录」并存档

文件存储模块需为每条文件记录增加以下字段：

| 字段名 | 类型 | 可空 | 说明 |
|:-------|:-----|:-----|:-----|
| `source_module_id` | VARCHAR(100) | ✅ | 来源模块ID（节点ID/其他业务对象ID） |
| `source_module_type` | VARCHAR(50) | ❌ | 来源模块类型标识 |

#### 6.1.2 模块类型枚举
| 类型标识 | 说明 | 示例 |
|:---------|:-----|:-----|
| `NODE_STARTUP_DOC` | 节点启动文档记录 | 节点录入时生成的标准化文档 |
| `NODE_WORKLOAD_DOC` | 节点工作量申报文档 | 进度更新时上传的工作量证明材料 |
| `NODE_DELIVERABLE_DOC` | 节点成果物文档 | 节点产出的交付文件 |
| `NODE_ATTACHMENT` | 节点通用附件 | 节点相关的其他文件 |

### 6.2 文件访问权限控制

#### 6.2.1 权限控制机制

> **核心原则**：文件只对与之关联的节点的企业用户可见

| 权限维度 | 规则 |
|:---------|:-----|
| **默认可见范围** | 节点 `related_company_id`（关联单位）的所有员工用户，默认有权访问 `accessible_file_ids` 列表中的所有文件 |
| **跨企业隔离** | 文件与节点强绑定，其他节点关联单位的用户不可见 |
| **示例** | 「景观施工图」文件只对景观工程节点关联的景观单位员工可见，门窗单位员工不可见 |

#### 6.2.2 权限设置与修改

| 操作 | 允许角色 |
|:-----|:---------|
| **初始化文件列表** | 节点创建时自动关联相关文件 |
| **新增/移除可见文件** | 节点主责条线负责人 + 负责人的上级领导 |
| **批量调整权限** | 项目总监 + 系统管理员 |

#### 6.2.3 操作记录与追溯

所有权限变更操作都必须记录到 `node_events` 事件表：

| 事件类型 | 记录内容 |
|:---------|:---------|
| `FILE_ACCESS_ADDED` | 新增可见文件：文件ID、操作人、操作时间 |
| `FILE_ACCESS_REMOVED` | 移除可见文件：文件ID、操作人、操作时间 |
| `FILE_ACCESS_BATCH_UPDATED` | 批量更新文件列表：变更前后快照 |

---

### 6.3 文件存储规范

| 规范项 | 要求 |
|:-------|:-----|
| **文件格式支持** | xlsx、pdf、docx、md、txt、jpg、png 等常用格式 |
| **版本控制** | 同一节点同一类型文件多次上传需保留完整版本历史 |
| **存储路径** | 按节点ID分目录存储，便于检索 |
| **权限控制** | 文件访问权限继承节点的权限（负责人可上传/下载）+ `accessible_file_ids` 白名单机制 |
| **删除机制** | 软删除机制，保留删除记录，不物理删除文件 |
| **修改机制** | 所有文件修改均采用"新增版本+标记旧版失效"方式，不覆盖原有文件 |
| **历史追溯** | 文件的所有版本、所有删除/修改操作都有时间戳和操作人记录，完整可查 |

---

### 6.4 与节点状态机的集成

1. **节点创建时**：自动生成「启动文档记录」并绑定 `startup_doc_id`
2. **节点更新时**：字段变更生成新的文档版本，记录变更历史
3. **成果上传时**：自动绑定 `NODE_DELIVERABLE_DOC` 类型
4. **进度申报时**：支持上传 `NODE_WORKLOAD_DOC` 工作量证明材料

```
OutboundEventBus（全局出站总线）

SSE前端 / IM群 / Webhook第三方
```

支持按以下维度过滤订阅：

| 过滤维度 | 示例 |
|:---------|:-----|

| 事件类型 | 只订阅状态变更事件 |
| 主责条线 | 只订阅工程部节点 |
| 所属阶段 | 只订阅施工阶段 |

### 7.3 推送渠道

## 九、项目实施计划编制指南（核心原则落地）

本状态机系统的设计理念直接指导项目实施计划的编制方式，彻底改变传统的粗粒度节点计划。

### 9.1 计划编制原则

| 原则 | 说明 |
|:-----|:-----|
| **成果导向原则** | 每个节点必须明确定义所有产出成果，不能只写"完成XX工作" |
| **最小依赖原则** | 只列出启动节点**真正需要**的前置文件，不要为了"保险"多加依赖 |
| **专业并行原则** | 跨专业节点尽可能并行，依赖具体文件而非整个节点完工 |
| **可验证原则** | 每个进度节点都必须对应可验证的文件上传，不能靠口头汇报 |

### 9.2 计划编制步骤

1. **步骤1：拆解节点**
   - 按专业/区域/工序拆分成合适粒度的节点
   - 设计父子节点层级（不超过3层）

2. **步骤2：定义成果**
   - 为每个节点列出所有产出成果文件
   - 为每个成果定义：名称、目标量、单位

3. **步骤3：建立依赖（最关键）**
   - 为每个节点找出：**少而准**的前置文件
   - 直接关联到具体成果的ID，不是关联到节点
   - 给每个依赖分配合理权重

4. **步骤4：设定时间**
   - 为每个节点设定截止时间
   - 关键路径节点可额外设置预警时间

### 9.3 编制示例（对比）

**❌ 传统计划（错误示范）**
```
节点：景观设计（8.1-8.30）
节点：景观工程（9.1-11.15）
  └─ 前置依赖：景观设计节点100%完成
```

**✅ 本系统计划（正确示范）**
```
节点：景观设计（8.1-8.30）
  └─ 产出成果：
      ├─ 景观施工图.pdf（预计8.15完成）
      ├─ 苗木清单.xlsx（预计8.20完成）
      └─ 景观概算.pdf（预计8.30完成）

节点：景观工程（8.16-11.15）
  └─ 前置依赖（共3个文件）：
      ├─ 景观施工图.pdf（来自景观设计，权重0.4）
      ├─ 景观工程合同.pdf（来自成本合约，权重0.3）
      └─ 场地移交报告.pdf（来自工程总包，权重0.3）
```

> **效果**：景观工程在8.16就可以启动，比传统计划提早了半个月！

### 9.4 计划动态调整

本系统支持项目执行过程中的动态调整：
- 可随时新增/移除节点的依赖文件
- 可调整各依赖文件的权重
- 可随时新增子节点细化工作
- 所有调整自动记录在 `node_events` 事件表中，全程可追溯
