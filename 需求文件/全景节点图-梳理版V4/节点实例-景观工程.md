## 业务表定义

### 工程分解表（继承表单审批流-基类）

> 定义工序的分解结构和量化标准。每道工序一条记录。支持版本管理，变更时创建新版本而非覆盖旧数据。

#### 继承自审批流-基类
- 表单号（KEY）
- 表单提交时间 / 提交人 / 生效时间 / 批准人 / 审批意见 / 审批回复
- 作废时间 / 作废批准人 / 作废原因 / 替代表编号

#### 业务字段
- 分解工序名称
- 分解工序编号（唯一）
    - 规则：`节点编号-工序序号-V版本号`，如 `SG-JG-001-V1`
    - 变更时保留原工序序号，仅递增版本号
- 工序关联的父工序编号（默认无，用于层级工序）
- 父版本分解表编号（为空表示初始版本；变更时指向原版本）
- 变更原因（仅当父版本编号非空时必填）
- 工序描述
- 量化数量
- 量化单位
    - 需关联标准计量单位字典（米、平方米、立方米、棵、套等）
- 管理责任岗（FK → 建设单位对应岗位人员）
- 承包单位（FK → 承包单位表）

---

### 工程计划表（继承表单审批流-基类）

> 为每个已生效的分解工序编制计划排期。审批通过后「生效时间」即为计划截止时间。

#### 继承自审批流-基类
- 表单号（KEY）
- 表单提交时间 / 提交人 / 生效时间 / 批准人 / 审批意见 / 审批回复
- 作废时间 / 作废批准人 / 作废原因 / 替代表编号

> **注**：此处的「生效时间」指审批通过后计划生效的**截止时间点**（即计划必须在此时间前完成），
> 而非生效的起始时刻。时间约束均以此为基准。

#### 业务字段
- 工程计划表单号（KEY）
- 分解工序编号（FK → 工程分解表，且该分解表必须已生效）
- 开始时间
- 结束时间

---

### 工程实现表（纯记录表，不继承审批流）

> 记录每道工序的实际执行时间段。此表为事后录入的客观记录数据，不需要单独走审批流程。
> 实现时间的合理性由关联约束保证（不得突破计划表的时间边界，超出则触发延期审批流程）。

- 工程实现表单号（KEY）
- 分解工序编号（FK → 工程分解表，且该分解表必须已生效）
- 开始时间
- 结束时间

---

### 工作量确认表（继承表单审批流-基类）

> 工序完成后由承包单位提交、经监理确认、管理责任岗最终批准的完工量化签认单。

#### 继承自审批流-基类
- 表单号（KEY）
- 表单提交时间 / 提交人 / 生效时间 / 批准人 / 审批意见 / 审批回复
- 作废时间 / 作废批准人 / 作废原因 / 替代表编号

#### 业务字段
- 分解工序编号（FK → 工程分解表，且该分解表必须已生效）
- 提交人（必须来自承包单位人员表）
- 提交时间
- 量化数量
- 监理确认人（必须来自监理单位人员表）
- 监理确认时间

> **流程**：提交人提交 → 监理确认人确认 → 管理责任岗最终批准。监理不同意的，不进入最终批准环节。

## 节点状态流转

> 遵循父类「所有状态变更须负责人手动确认」原则。「自动」仅指系统发出提醒。

```
未启动 ──→ 运作中 ──→ 完工归档
```

| 流转 | 触发条件 | 说明 |
|------|---------|------|
| **未启动 → 运作中** | 第一张工程分解表审批生效后，系统**提醒**节点负责人，负责人手动启动 | 分解表生效 = 工程具备启动条件，但不是自动切状态 |
| **运作中 → 完工归档** | 所有工序完成（详见下方判定规则）后，节点负责人手动发起完工确认 | 完工确认人必须是「完工确认岗位」（工程部经理） |

### 工序完成判定

单道工序的完成条件：**∑该工序所有已生效工作量确认单的「量化数量」= 工程分解表中该工序的「量化数量」**

- 当 ∑ < 分解表数量：工序仍在进行中，可继续提报
- 当 ∑ = 分解表数量：该工序判定为完成
- 当 ∑ > 分解表数量：**数据异常**，触发基类的异常处理机制（阶段 1→2→3 升级）

## 关联规则

### 数据关系 — 工程量确认
- 工作量单数量：`工作量确认表` 中对应工序的 `量化数量`
- 工程分解表数量：`工程分解表` 中的 `量化数量`
- 所有「工作量单数量」之和等于「工程分解表数量」时，本工序判定为完成
- 不应存在「工作量单数量」之和大于「工程分解表数量」的状态（数据异常，触发异常处理机制）

### 人员约束
| 约束 | 说明 |
|------|------|
| 提交人 | 工作量单 `提交人` 必须是承包单位人员表中的在册人员 |
| 计划单批准人 | 必须是项目职务表中 `工程经理` |
| 完工确认批准人 | 必须是 `管理责任岗` |
| 监理确认人 | 必须是监理单位人员表中的在册人员 |
| 确认顺序 | 工作量确认单需先经监理单位确认，再由管理责任岗最终批准 |

### 时间约束
| # | 约束 | 说明 |
|---|------|------|
| 1 | 提报时间 ≤ 计划生效时间 | 工程量提报不应晚于计划表的审批生效时间。此处的「生效时间」指计划截止节点，非起始时刻 |
| 2 | 提报时间 ≥ 实现结束时间 | 提报必须在工序实际完工之后 |
| 3 | 实现开始 ≥ 计划开始 | 同一工序下，实际开工不早于计划开工 |
| 4 | 实现结束 ≤ 计划结束 | 同一工序下，实际完工不晚于计划结束。超出则触发延期审批流程 |
| 5 | 批准人+批准时间同时录入 | 批准时两字段不可缺一 |

### 录入约束
- 节点处于「完工归档」后，仅 `备注` 字段可逐条追加后备说明信息，其他字段不可更改
- 批准时间与批准人两字段必须同时录入，缺一不可生效

### 跨表一致性约束
- 工程计划表的 `分解工序编号` 必须对应一个**已生效**的工程分解表
- 工程实现表的 `分解工序编号` 必须对应一个**已生效**的工程分解表
- 工作量确认单的 `分解工序编号` 必须对应一个**已生效**的工程分解表

## 变更与作废机制

### 作废与变更的区别

| | 适用场景 | 处理方式 | 级联影响 |
|:--|------|------|------|
| **表单作废** | 错误提交、完全废弃 | 填写作废原因和替代表编号，标记作废 | 关联的计划表/实现表/确认单同步作废 |
| **提交新版本** | 业务调整、工程变更 | 基于当前生效的分解表创建新版本，旧版本保留 | 关联表需同步评估是否调整 |

### 工程变更流程

1. 需变更时，基于当前生效的分解表创建新版本
2. 新版本分解表填写「父版本分解表编号」和「变更原因」
3. 新版本重新走审批流程（提交→审批→生效）
4. 关联的计划表、实现表、确认单需同步评估是否需要调整
5. 旧版本数据保留，不物理删除（版本链可追溯）
