## 业务表定义

### 地块分区表（字典表）

> 景观设计可能存在多个独立分区并行推进。各地块分区独立排期、独立评审。

- 地块分区编号（KEY）
- 地块分区名称
- 分区类型（枚举：大区 / 展示区 / 样板院 / 标段 N / …）
- 分区描述

---

### 任务阶段分解表（继承表单审批流-基类）

> 定义景观设计的标准阶段序列。每个地块分区 × 每个设计阶段 = 一条任务记录（N:N 关系）。

#### 继承自审批流-基类
- 表单号（KEY）
- 表单提交时间 / 提交人 / 生效时间 / 批准人 / 审批意见 / 审批回复
- 作废时间 / 作废批准人 / 作废原因 / 替代表编号

#### 业务字段
- 地块分区（FK → 地块分区表）
- 设计阶段（枚举：概念阶段 / 方案阶段 / 扩初阶段 / 施工图阶段）
- 阶段描述
- 承包单位（FK → 承包单位表）
- 管理责任岗（FK → 建设单位对应岗位人员）

---

### 设计计划表（继承表单审批流-基类）

> 为每个地块分区的每个设计阶段编制排期计划。

#### 继承自审批流-基类
- 表单号（KEY）
- 表单提交时间 / 提交人 / 生效时间 / 批准人 / 审批意见 / 审批回复
- 作废时间 / 作废批准人 / 作废原因 / 替代表编号

> **注**：此处的「生效时间」指审批通过后计划生效的**截止时间点**（即该阶段设计必须在此时间前完成），
> 而非生效的起始时刻。时间约束均以此为基准。

#### 业务字段
- 设计计划表单号（KEY）
- 地块分区（FK → 地块分区表）
- 设计阶段（FK → 任务阶段分解表·设计阶段）
- 开始时间
- 结束时间

---

### 设计实现表（纯记录表，不继承审批流）

> 记录每个地块分区、每个设计阶段的实际执行时间段。此表为客观记录数据，不需要单独走审批流程。
> 实现时间的合理性由关联约束保证。

- 设计实现表单号（KEY）
- 地块分区（FK → 地块分区表）
- 设计阶段（FK → 任务阶段分解表·设计阶段）
- 开始时间
- 结束时间

## 节点状态流转

> 遵循父类「所有状态变更须负责人手动确认」原则。「自动」仅指系统发出提醒。

```
未启动 ──→ 运作中 ──→ 完工归档
```

| 流转 | 触发条件 | 说明 |
|------|---------|------|
| **未启动 → 运作中** | 第一张设计计划表审批生效后，系统**提醒**节点负责人，负责人手动启动 | 计划表生效 = 设计具备启动条件，但不是自动切状态 |
| **运作中 → 完工归档** | 所有地块分区 × 所有设计阶段均通过评审会审批（详见下方判定规则）后，节点负责人手动发起完工确认 | 完工确认人必须是「完工确认岗位」（设计部经理） |

### 阶段完成判定

**各地块分区的每个设计阶段独立判定完成**，判定条件：

- 该阶段对应的评审会明确表示**通过**，才算该阶段完成
- 所有地块分区的全部设计阶段均完成后，节点具备完工确认条件

## 关联规则

### 地块分区 × 设计阶段 N:N 关系

- 各地块拥有独立的阶段分解表实例，为 N:N 关系
- 同一地块的不同设计阶段可并行推进（如展示区已进入施工图阶段，大区仍在方案阶段）
- 不同地块之间无强制先后顺序（由项目计划自行安排）

### 人员约束

| 约束 | 说明 |
|------|------|
| 计划单批准人 | 必须是项目职务表中 `设计部经理` |
| 完工确认批准人 | 必须是 `管理责任岗` |
| 阶段评审通过批准 | 各设计阶段的评审会通过，由**集团设计部**审批 |

### 时间约束

| # | 约束 | 说明 |
|---|------|------|
| 1 | 设计阶段实际结束 ≤ 设计计划表截止时间 | 各阶段完工不应晚于计划表的审批生效截止时间 |
| 2 | 设计完工时间 ≥ 设计实现结束时间 | 完工确认必须在对应阶段实际结束之后 |
| 3 | 实现开始 ≥ 计划开始 | 同一地块+阶段下，实际开工不早于计划开工 |
| 4 | 实现结束 ≤ 计划结束 | 同一地块+阶段下，实际完工不晚于计划结束。超出则触发延期审批流程 |
| 5 | 批准人+批准时间同时录入 | 批准时两字段不可缺一 |

### 录入约束

- 节点处于「完工归档」后，仅 `备注` 字段可逐条追加后备说明信息，其他字段不可更改
- 批准时间与批准人两字段必须同时录入，缺一不可生效

### 跨表一致性约束

- 设计计划表的 `地块分区` 和 `设计阶段` 必须对应一个已生效的任务阶段分解记录
- 设计实现表的 `地块分区` 和 `设计阶段` 必须对应一个已生效的任务阶段分解记录

## 变更与作废机制

### 作废与变更的区别

| | 适用场景 | 处理方式 | 级联影响 |
|:--|------|------|------|
| **表单作废** | 错误提交、完全废弃 | 填写作废原因和替代表编号，标记作废 | 关联的计划表/实现表同步作废 |
| **变更申请** | 设计范围调整、方案变更 | 基于当前生效的分解表创建新版本，旧版本保留 | 关联表需同步评估是否调整 |

### 设计变更流程

1. 需变更时，在原分解表基础上创建新版本
2. 新版本重新走审批流程（提交→审批→生效）
3. 关联的设计计划表、设计实现表需同步评估是否需要调整
4. 旧版本数据保留，不物理删除（版本链可追溯）
