# 全景节点两层制 — 需求基线 V1

> **定位**：重构全景节点的类型体系——把现有三层（里程碑 / 工作包 / 任务）收敛为两层（里程碑 / 任务），消除"一项工作该归到哪一层"的模糊。
> **状态**：需求基线（待评审 → 出 PRD / 计划）
> **来源**：2026-09-16 设计讨论结论固化
> **不含**：上报匹配链路重构、LLM 进度判断（均见 §四 非目标）

---

## 一、目标

1. 节点类型从 3 类收敛为 2 类，归类不再依赖人的习惯判断。
2. 任务成为**唯一的进度事实来源**；里程碑成为**纯聚合视图**，不再承载进度计算。
3. 状态机保持三态（未启动 / 运行中 / 已完结），但语义明确、判据可机检。

---

## 二、核心决策

### D1 类型收敛
节点类型只剩两类：`MILESTONE`（里程碑）、`TASK`（任务）。`WORK_PACKAGE` 退场。

### D2 归类判据（单向提升，可机检）
> **有子节点 → 必为里程碑（自动提升）；无子节点 → 任务，或"尚未分解的里程碑"（创建时显式声明，不下沉）。**

实施期澄清（2026-09-16）：最初拟定的"无子节点一律为任务"过严，与 D5 冲突——用户场景明确「大区景观施工里程碑，当前没有任何任务 → 未启动」，若强制下沉为任务，里程碑就永远无法处于"未启动"。故改为**单向提升**：结构只保证"有子节点必为里程碑"，叶子节点的类型由创建意图决定（默认任务）。

已退场类型 `WORK_PACKAGE` 由迁移脚本按结构收敛：有子节点 → 里程碑，无子节点 → 任务。

不附加"里程碑不得挂成果"之类的约束——有子节点时节点自身成果本就不参与状态判定，无副作用（见 §四-3）。

### D3 允许里程碑嵌套
里程碑可挂在里程碑之下，用以承接原"中间分组层"的语义。深度上限不再写死 3 层，改为约束"**任务必须是叶子节点**"。

### D4 状态为纯派生
三态一律由系统派生，**不可人工填写**。"已完结"的判定采用**方案 A**：成果量到位（`current_amount ≥ target_amount`）或签认通过。

### D5 未启动判据（原"选项 ii"）
**任务**（叶子）：
- 前置依赖未满足 → 未启动
- 无成果定义 → 未启动
- 完成量为 0 → **未启动**
- 0 < 完成量 < 目标 → 运行中
- 完成量达标 → 已完结

**里程碑**：由直接子节点的三态聚合，**不另写独立规则**。
- 全部子节点未启动 → 未启动
- 全部子节点已完结 → 已完结
- 其余 → 运行中

> 等价性说明：用户表述的"有任务且有上报才算启用"与"任务判量 + 逐层聚合"三种情形逐一核对一致（无任务→未启动；有任务无量→未启动；有上报→运行中），故只实现一条逻辑，避免两套规则打架。

### D6 删除系统侧进度计算
移除节点进度百分比的硬编码计算与写库，含：
- `_recalc_node_status` 中的 progress 计算分支
- 父子权重聚合（`child_weight` 一并搁置，不启用）

`project_nodes.progress` 列**保留**（不改表、兼容存量），但不再由系统写入。
`determine_node_status` 中 `completion >= 1.0 → COMPLETED` 的判定**必须保留**——它是任务完结的唯一自动路径。

> 注意：`calc_deliverable_completion` 被两处调用，一处算进度（删除）、一处定状态（保留），不可整函数删除。

## 四、非目标（本基线明确不做）

1. **不做父子进度加权聚合**——`child_weight` 保持不启用。
2. **不用 LLM 判断进度或状态**——状态是硬门禁（上报入口、我的节点、上报匹配范围、超期预警、漂移检测均依赖它），不可复现的判定不得进门禁。LLM 仅可用于只读、不落库的建议类场景（如"该更新了"提示、汇报口吻润色）。
3. **不清理挂在里程碑/原工作包上的既有成果**——有子节点时自身成果不参与状态判定，保留无副作用。
4. **不含上报匹配逻辑重构**——沿用现有 `node_deliverable_matcher`。
5. **不新增状态**——"里程碑未启动"含"尚未分解"与"无人报量"两种情况，如需提示放在展示层，不扩状态枚举。
