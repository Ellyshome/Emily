## 硬约束（违反即失败）

> 项目铁律直接引用 [宪法 §2](../.claude/skills/_shared/constitution.md)，不自行发明。

1. **禁止修改已有接口签名**：除非本设计明确标注"修改接口签名"，否则只在已有类中新增方法，不修改现有方法（`UserRepository.update_user` 等既有方法保持不变，新增窄写方法并存）。
2. **遵循宪法铁律 C0~C13**，逐条自检并列出本设计涉及项：

   | 铁律 | 本设计如何遵守 |
   |------|--------------|
   | C0 根治而非迁就 | 不在路由/前端解析记忆文本、不复刻提示词装配；一律在 service 层补齐能力 |
   | C2 分层不可跳 | 端点 → `PersonnelService`(Service) → `UserRepository`/`CompanyRepository`(Repository) → DB；记忆走 `UserMemoryService` |
   | C6 Sync repo + to_thread | Repository 全 sync；端点/工具用 `asyncio.to_thread` 包 sync Service |
   | C10 工具必须带参数 schema | 三个写工具完成"源文件 `_XXX_SCHEMA` → `_reg_biz(params=)` → `TOOL_SCHEMA_MAP`/`TOOL_META_MAP`/`TOOL_WRITE_MODE_MAP`/`REGISTERED_TOOLS` 同步" |
   | C11 功能注册接入 | 写能力经 `tools/registry.py` 注册；只读能力落 service 层并被 console 端点消费（无孤儿） |
   | C12 Session 主循环冻结 | `session/loop.py` 零改动；提示词能力层装配为"两份实现"并登记遗留收敛项 |
   | C13 Web 控制台 = 观察窗口 | 能力层先行；console 端点零业务逻辑、零裸 SQL、零直调 repo/provider；复用 service |

3. **每模块验收**：每个模块的验收检测必须通过，否则停止并报告。
4. **遵循接口契约**：跨模块调用只经约定接口，不绕过接口直接操作对方内部数据。
5. **不私自扩需**：发现规格缺陷回退 req-review，不在本设计新增/改写需求。
6. **接线闭合（宪法 §3 Q6）**：任何产出物必须有消费者（见"接线矩阵"）。

## 数据流设计

### 核心流程

| 流程 | 触发条件 | 参与者 | 数据流向 | 异常路径 |
|------|---------|--------|---------|---------|
| 人员列表 | GET `/console/personnel/list` | M6→M3→M1 | 查询 users ⋈ company_info，返回五列 DTO | 空库返回空列表；DB 异常返回 `_err` |
| 记忆条目 | GET `/console/personnel/memory?user_id=` | M6→M2 | 读 `{username}-长期记忆.md` 解析 `##` 条目 | 无文件/无条目/功能关闭各有明确返回 |
| 等级调整 | POST `/console/personnel/level` | M6→M3 | 授权判定→校验→`set_level`→`record_action(旧→新)` | 越权/非法值→拒+留痕 |
| 归属调整 | POST `/console/personnel/company` | M6→M3 | 授权判定→校验企业→`set_company`→留痕 | 越权/企业无效→拒+留痕 |
| 企业增删 | POST `/console/personnel/company-create/delete` | M6→M3 | 授权判定(L4+)→查重/计数→增/软删→留痕 | 越权/重名/有归属→拒+留痕 |
| 提示词生成 | POST `/console/personnel/prompt` | M6→M4 | `SessionContext.create` + 能力目录 + 模板渲染 | 人员不存在/模板缺失→明确文案 |

## M1: 数据访问层扩展

**依赖**：无

**实现的需求**：US-01（人员五列读取）、US-04（等级窄写）、US-05（归属窄写）、US-06（企业清单/增删/计数）

**层级**：Repository

**职责**：提供人员五列连接查询、企业清单/查重/新增/软删/在职人数统计、等级与归属的窄写（无校验无授权，纯数据访问）。

### 接口契约

#### 对外接口（`emily_core/repositories/user_repo.py` 新增，保持 `@staticmethod` + `get_session` 风格）

| 接口/类 | 类型 | 签名 | 说明 |
|---------|------|------|------|
| `UserRepository.list_personnel` | 方法 | `(limit: int = 2000) -> list[PersonnelRow]` | 五列连接查询，返回 DTO 列表（dict 或 dataclass） |
| `UserRepository.set_level` | 方法 | `(user_id: str, level: int) -> User \| None` | 只写 `users.level`；目标不存在返回 None |
| `UserRepository.set_company` | 方法 | `(user_id: str, company_id: str \| None) -> User \| None` | 只写 `users.company`（None 表清空归属） |

#### 对外接口（`emily_core/repositories/company_repo.py` 新建）

| 接口/类 | 类型 | 签名 | 说明 |
|---------|------|------|------|
| `CompanyRepository.list_companies` | 方法 | `(include_deleted: bool = False) -> list[CompanyRow]` | 企业清单 + 在职人数 |
| `CompanyRepository.get_by_name` | 方法 | `(name: str) -> CompanyInfo \| None` | 按名称查有效企业（查重用） |
| `CompanyRepository.create` | 方法 | `(name: str, unified_code: str, project_leader_id: str, creator_id: str) -> CompanyInfo` | 新增企业 |
| `CompanyRepository.soft_delete` | 方法 | `(company_id: str) -> bool` | 逻辑删除（`is_deleted=True`） |
| `CompanyRepository.count_active_members` | 方法 | `(company_id: str) -> int` | 统计 `users.company == company_id 且 is_deleted==False 且 status=='active'` 的人数 |

#### 依赖接口（本模块需要调用哪些已有接口）

| 现有接口 | 来源模块 | 调用目的 |
|----------|---------|---------|
| `get_session` | `infrastructure/database/session.py` | 会话管理 |
| `User` / `CompanyInfo` | `infrastructure/database/models.py` | ORM 模型 |

### 数据模型

**无新增表/列**（约束 8）。复用现有表：

| 表名 | 关键列（本设计读取/写入） |
|------|--------------------------|
| `users` | `id`, `username`, `creator_id`, `company`(FK,可空), `level`, `status`, `is_deleted`, `created_at`(String ISO) |
| `company_info` | `id`, `company_name`, `unified_code`, `project_leader_id`, `creator_id`, `status`, `is_deleted`, `created_at` |

**人员列表五列 DTO（`PersonnelRow`）字段**：

| 字段 | 来源 | 说明 |
|------|------|------|
| `user_id` | `users.id` | 人员标识 |
| `username` | `users.username` | 姓名 |

| `PersonnelService.adjust_user_company` | 方法 | `(operator_id: str, target_user_id: str, company_id: str, reason: str = "") -> dict` | 归属调整，`company_id=""` 表清空 |

**统一返回结构**：`{"success": bool, "reason_code": str, "message": str, "data": dict|None}`。
`reason_code` 取值（供留痕三态与前端文案）：

| reason_code | 含义 | 留痕 result |
|-------------|------|-------------|
| `""` | 成功 | succeeded |
| `permission_denied` | 越权/取不到操作人等级（fail-closed） | rejected |
| `invalid_level` | 等级值非法（非 1-6） | rejected |
| `user_not_found` | 目标人员不存在 | rejected |
| `company_not_found` | 目标企业不存在/已删 | rejected |
| `company_has_members` | 企业仍有在职归属人员 | rejected |
| `duplicate_company_name` | 同名有效企业已存在 | rejected |

> 上述 `reason_code` 是否加入 `audit.REJECT_CODES`：本设计**直接调用 `record_action` 显式传 `result`**（而非依赖 `@audited` 的 `classify_result`），因此不强制加入；但为与其他动作点一致，M3 在留痕时显式传 `result=RESULT_REJECTED`。可选将新 `reason_code` 补入 `REJECT_CODES`（属审计口径表可扩），由编码阶段判定。

### 核心算法/策略

#### 授权判定矩阵（D6/D8，PRD R1/R2/R3）

> `op` = 操作人 `users.level`；取不到操作人 → 一律拒绝（fail-closed）。

| 动作 | 规则 |
|------|------|
| 调整等级 | `op >= 6`：`new_level ∈ [1,6]`；`op ∈ [3,5]`：`new_level ∈ [1, op)`；`op ∈ [1,2]`：拒绝 |
| 调整企业归属 | `op >= 4`：任意；`op == 3`：仅可操作 `target.company == op.company` 的人员（本企业人员进出）；`op ∈ [1,2]`：拒绝 |
| 企业增删 | `op >= 4`：允许；`op ∈ [1,3]`：拒绝 |

> 说明：调整等级"op ∈ [3,5] → new_level < op"是按 D6 原文的逐级下压（L5→≤L4，L4→≤L3，L3→≤L2）；L6 特例可调至同级。不限制"目标当前等级"（D6 只约束可调到的目标值，未约束目标对象当前等级）。

#### 企业新增最小字段取值（PRD 附录 B 问题 7 的答案）

| `company_info` 必填无默认列 | 取值口径 |
|------------------------------|---------|
| `company_name` | 用户输入，必填，非空 |
| `unified_code` | 空串 `""`（本期不采集，满足 NOT NULL） |
| `project_leader_id` | `operator_id`（新增人即初始负责人） |
| `creator_id` | `operator_id` |

其余列用 ORM 默认值（`status='active'`、`is_deleted=False`、`type/scope/partners/department/function_scope` 等）。

#### 留痕策略（PRD R7/R8，US-10）

写动作在服务层显式调用 `audit.record_action`（挂载点唯一），不依赖 `@audited` 装饰器，以便把**变更前后值**写入 `detail_json`：

| 参数 | 取值 |
|------|------|
| `category` | `"personnel"` |
| `action` | `user_level_updated` / `user_company_updated` / `company_created` / `company_deleted` |
| `target_type` | `"user"` / `"company"` |
| `actor_id` | `operator_id` |
| `detail_json` | `{"old_level": x, "new_level": y, "reason": r}` 或 `{"old_company": a, "new_company": b, "reason": r}`（企业增删传 `{"company_name": n}`） |
| `result` | `RESULT_SUCCEEDED` / `RESULT_REJECTED`（被拒也留痕） |

> 留痕失败非阻断（`record_action` 内部已 try/except 告警）。

### 数据模型

无数据模型变更；写入复用 M1 窄写方法。
