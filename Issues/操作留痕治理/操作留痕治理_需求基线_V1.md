# 操作留痕治理 — 需求基线 V1（讨论稿）

> **性质**：讨论稿，供决策确认；确认后转 PRD 与计划
> **日期**：2026-09-16
> **依据**：emy-console 全端点走查 + 日志写入链路取证（`console_resources.py` / `business_event_logger.py` / `log_writer.py` / `console_log_repo.py` / `models.py`）
> **关系**：独立需求线，不并入「检索通道治理」「LangGraph 编排内核化」

## 一、背景与问题

1. **现象（留痕不齐）**：emy-console 各操作留痕口径不一致——
   - 已留痕：文件删除（`file/console_file_delete`）、RAG 移除（`rag/console_rag_delete`）、系统自检（`system/console_self_check`）、节点参与人/共享文件增删（`node_events`）、模拟对话（全链路）。
   - 无留痕：**文件上传**（仅 `files` 一行 + 物理文件）、**RAG 入库**（仅 `knowledge_chunks.metadata` 的 `stage/role`）、**RAG 查库**（`rag_retrieval_logs` 仅由 LLM 工具路径写）、**密级调整**（仅 `logger.info` 运行时日志）。
2. **现象（渠道断链）**：渠道身份在会话层完整、在业务事件层丢失。
   - 有：`session_archives`（`platform` / `im_user_id` / `is_guest`）、`messages.sender_im_id` + `conversations.im_platform`、`user_im_bindings`。
   - 无：`business_event_logs` 仅有 `user_id` + `user_name`，无法回答"该业务操作从哪个渠道发起"。同一用户的 QQ 与企微事件在库中不可区分。
3. **现象（只记成功）**：现有记录口径为"成功才记"。权限被拒路径直接返回，不留痕（典型：`file_service.update_confidentiality` 的"仅上传人本人或 L5/L6 管理员可调整"），越权尝试无记录。
4. **现象（暗记脆弱）**：console 模拟对话的标识是 `messages.event_id` 字符串前缀 `console_chat_`：不可索引、只覆盖单一入口、命名变更即导致历史数据不可查。
5. **定性**：非单点遗漏，而是缺少**统一的留痕归因模型**——每张日志表各记各的维度，导致"记了什么"依赖具体代码路径，"来源是谁"无法回答。
6. **影响**：
   - 运维动作无痕（RAG 入库、上传）→ 无法回答"这批知识是谁什么时候灌的"。
   - 渠道不可溯 → 无法按渠道统计、无法与 `user_im_bindings` 交叉校验身份真实性。
   - 越权无痕 → 留痕不具备审计价值。
   - 测试流量与真实流量同构 → 行为分析、进化闭环、SOP 命中率统计被污染，且只能靠前缀 grep 隔离。
7. **结论**：需独立立项，建立统一留痕归因模型并补齐 console 缺口。

## 二、目标

1. **G1 留痕完整**：所有**状态变更**类操作（含成功、失败、被拒绝三态）均留痕，覆盖全部 entrypoint。
2. **G2 来源可溯**：每条留痕都能回答"谁 + 从哪来 + 做了什么 + 成没成"，其中"从哪来"含来源类型与渠道账号。
3. **G3 流量可分离**：console（后台测试）与 IM（真实用户）流量在同一存储中可被结构化过滤，不依赖字符串约定。
4. **G4 底座统一**：新增留痕通过统一写入器与统一上下文注入落地，不要求逐个调用点改传参。

## 三、范围

- **纳入**：`business_event_logs` / `messages` / `node_events` / `scheduler_job_logs` 等留痕表的维度对齐；`BusinessEventLogger` 上下文机制扩展；console 四个写操作端点补录；`ConsoleLogRepo` 增加来源过滤维度。
- **不纳入**：`EvolutionLogWriter` 的"非阻断 + 截断 + 异步"三原则（保持不变）；Session 归档正文机制；`EventJournal` md 双写的存废（另案评估）；历史日志的物理清理。

## 四、术语

1. **状态变更操作**：产生数据写入或状态迁移的操作（增删改、入库、密级调整、确认/驳回）。
2. **三态**：成功 / 失败（异常）/ 被拒（权限或校验不通过）。
3. **来源四分类**：`im`（IM 渠道）/ `console`（后台控制台）/ `scheduler`（计划任务）/ `system`（系统内部：守护、进化、自动归档、重启收口）。
4. **暗记**：标识一条消息或操作由 console 触发的结构化字段（取代现字符串前缀）。
5. **归因四元组**：`actor` + `source/channel/channel_account` + `action/target` + `result`。

## 五、功能需求

1. **FR-1 统一留痕归因模型**：所有留痕表向归因四元组对齐，字段命名与取值域统一；不得各表自造维度。
2. **FR-2 三态记录**：状态变更操作的成功、失败、被拒绝均须留痕；被拒记录须含拒绝原因。**读取类默认不记**（防自激），仅"高风险读"（全量导出、文件下载、跨项目查询）按需记录。
3. **FR-3 防自激约束**：console 日志面板刷新、`/llm-trace` 增量轮询、SSE keep-alive 帧等观测行为**必须不产生留痕**。
4. **FR-4 来源与渠道落地**：`business_event_logs` 增加 `source` / `channel` / `channel_account` / `result` / `error_reason`；`channel` 仅在 `source=im` 时必填。**不强制"所有留痕必须有通讯工具"**（scheduler / system 无渠道可填）。
5. **FR-5 上下文自动注入**：扩展 `BusinessEventLogger` 既有 `_current_context` 机制，承载 `source` / `channel` / `channel_account`；在入口注入一次，下游业务事件自动携带，避免逐点改传参。
6. **FR-6 IM 入口一次注入**：在 `core.handle_message` 入口从 `StandardMessage` 提取渠道身份写入上下文；覆盖 QQ / 企微 / 小程序 / 邮箱四渠道，不改任何 SOP 或工具。
7. **FR-7 console 入口统一注入**：在 console 路由层以统一入口（依赖或中间件）注入 `source=console` + 全局操作人，避免各端点手工传参。
8. **FR-8 console 写操作补录**：`/console/upload`、`/console/rag-index`、`/console/rag-search`、`/console/file-confidentiality` 各补一次业务事件留痕；补录后按 FR-5 自动出现在"日志聚合"的业务事件模块，**不将 `files` / `knowledge_chunks` 纳入模块白名单**。
9. **FR-9 暗记结构化**：`messages` 增加 `source` 字段，四渠道入口与 console 统一写入；`console_chat_` 前缀降级为兼容手段，不再作为判定依据。
10. **FR-10 系统与调度来源补全**：`scheduler_job_logs` 补 `source` 与 `actor`（取值可为"系统"/作业标识），使其与业务事件处于同一归因模型；`system` 类操作统一登记。
11. **FR-11 消费端来源过滤**：`ConsoleLogRepo` 的模块白名单机制保留，增加 `source` 过滤参数；日志面板提供"排除 console 测试流量"开关，行为分析与进化闭环默认排除。
12. **FR-12 写入失败可观测**：为"留痕写失败"增加计数或记录，纳入既有 `scripts/self_check.py` 体检项，解决"未记"与"记失败"外部不可区分的问题。
13. **FR-13 历史回填与文档同步**：存量 `business_event_logs` 按 `event_action` 前缀回填 `source`（`console_*`→console；其余→im；无法判定→system）；`messages.event_id` 前缀迁移至 `source`；同步更新 `docs/数据库设计.md`、`docs/接口协议与调用约定.md`。

## 六、非功能需求

1. **NFR-1 非阻断不变**：沿用 `EvolutionLogWriter`「失败只告警、截断（Text 5000 / String 500）、`asyncio.to_thread` 异步」三原则。
2. **NFR-2 主链路零额外开销**：留痕不得引入额外 LLM 调用；不得让运维动作走通意图路由与 ReAct 循环。
3. **NFR-3 可过滤**：`source` 建索引，过滤查询不因新增字段劣化。
4. **NFR-4 可回退**：新增字段与注入逻辑可整体关闭，回落到当前行为。
5. **NFR-5 不改写业务语义**：`project_events`（面向项目成员的业务台账）不得混入运维动作。

## 七、约束

1. **入口不合并**：console 操作不得包装为 IM 消息投递——会造成 LLM 成本放大、`project_events` 台账污染、用户权限模型与无鉴权后管视角冲突、真实行为数据失真。统一的是**日志模型**，不是**调用入口**。
2. **权限模型不改**：IM 走 L1–L6 用户权限与项目可见范围；console 走后台视角，两者不互相让渡。
3. **改动方式**：优先扩展现有结构与 `_PENDING_COLUMNS` 补列机制，不新建重复表。

## 八、非目标

1. 不重构 `EvolutionLogWriter` 与非阻断原则。
2. 不替换 `EventJournal` md 双写（存废另案）。
3. 不做日志聚合面板的 UI 重设计（仅加过滤开关）。
4. 不做日志的归档压缩与生命周期治理。
5. 不改造 `session_archives` 的归档正文机制。

## 九、验收方向

1. **补录覆盖**：console 上传 / RAG 入库 / 查库 / 密级调整四操作，各自产生一条含归因四元组的留痕。
2. **渠道溯源**：QQ 与企微两渠道对同一用户各发一条录入类指令，`business_event_logs` 中两条记录的 `channel` / `channel_account` 可区分且与 `user_im_bindings` 一致。
3. **三态覆盖**：非上传人、非 L5/L6 用户尝试改密级，须产生一条"被拒"留痕（含原因）。
4. **流量分离**：`WHERE source != 'console'` 可一键排除 console 测试流量；面板开关排除后行为分析与真实流量统计不受影响。
5. **防自激**：连续刷新日志面板 / 轮询 `/llm-trace` 五分钟，"日志聚合"条数不因观测行为增长。
6. **不回归**：主链路（消息处理、SOP 执行）无新增告警；非阻断原则下留痕失败不影响业务返回。
7. **回填正确**：存量数据按前缀规则回填后，抽样核对 `source` 取值正确。

## 十、决策记录（2026-09-16 确认）

| 编号 | 议题 | 决策 |
|------|------|------|
| Q1 | "所有操作都要记录"的口径 | **收窄为"所有状态变更必须留痕且记三态"**；读取类默认不记，仅高风险读按需记 |
| Q2 | 留痕是否强制携带通讯工具 | **否**。统一为 `actor + source + channel + channel_account`，`channel` 仅 `source=im` 时必填 |
| Q3 | console 是否走"用户+通讯工具"模式 | **仅模拟对话维持现状**；其余 console 操作保持独立 API，统一的是日志模型而非入口 |
| Q4 | console 暗记形式 | **结构化字段 `source`**，取代 `console_chat_` 字符串前缀 |
| Q5 | console 缺口补齐方式 | **补业务事件留痕，不将 `files` / `knowledge_chunks` 纳入 `LOG_MODULES` 白名单** |
| Q6 | 上下文注入 vs 逐点传参 | **上下文自动注入**（扩展 `BusinessEventLogger._current_context`），避免逐调用点改动 |
