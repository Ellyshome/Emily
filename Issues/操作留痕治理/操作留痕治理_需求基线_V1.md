## 一、背景与问题

1. **现象（挂载点错位：留痕挂在入口层，不在统一执行层）** —— 本需求的首要问题。
   - 全仓 `BusinessEventLogger` 仅 4 处调用点：`application/event_app.py`、`task_app.py`、`meeting_app.py`（**仅 IM 入口**）+ `api/routes/console_resources.py`（**仅 console 入口**）；`emily_core/services/` 下 **0 处**。
   - 统一执行层本已存在：按约束 10，`scripts/`（开发者 CLI）、`tools/`（LLM 工具）、`api/routes/`（console）、IM 四者**共享 `emily_core/services/`**，各入口均为薄壳。留痕却没有挂在这一层。
   - 后果：同一个动作从不同入口走，**有无留痕取决于该入口有没有人写过**，而非取决于动作本身。
   - 铁证（文件删除）：IM 与 console 调用的是**同一个** `file_manager.soft_delete`，但留痕只写在 console 侧私有函数 `_delete_file` 内 → 从 IM 删除文件**无痕**。
   - 脚本侧：`manage_nodes.py` → `services/node_batch.py` / `node_batch_update.py` → 无痕。**跑脚本批量建节点，`business_event_logs` 零记录**。
   - 结论：这不是"漏了几个点"，而是"挂错了层"。按入口补录的解法，入口增加一个就再漏一次。
2. **现象（留痕不齐）**：各入口留痕口径不一致——
   - 已留痕：文件删除（`file/console_file_delete`）、RAG 移除（`rag/console_rag_delete`）、系统自检（`system/console_self_check`）、节点参与人/共享文件增删（`node_events`）、模拟对话（全链路）。
   - 无留痕：**文件上传**（仅 `files` 一行 + 物理文件）、**RAG 入库**（仅 `knowledge_chunks.metadata` 的 `stage/role`）、**RAG 查库**（`rag_retrieval_logs` 仅由 LLM 工具路径写）、**密级调整**（仅 `logger.info` 运行时日志）。
3. **现象（console 绕过统一执行层）**：console 四个缺口端点中三个**未经过 service 层**，直接触达下层——
   - `/console/upload` → 直接 `FileRepository.create` + 手写落盘，绕过 `FileStorageService`；
   - `/console/rag-index` → 直接调 **tool** `handle_embed_and_index`；
   - `/console/rag-search` → 直接 `new PgVectorRagProvider`；
   - 仅 `/console/file-confidentiality` 走了 `FileService.update_confidentiality`（但 service 内亦无痕）。
   - 即 console 在路由层**复刻/绕过**既有能力，违反约束 14（console 只接线既有能力，不得自行实现）。这是问题 1 的必然结果：挂载点不在统一层，console 就只能自己造一份。
4. **现象（测试流量与真实流量不可结构性分离，且事后不可推）**：
   - console 模拟对话**走的就是真实 IM 入口**（真实 `core.handle_message`、真实 `user_id`、真实渠道标识），其产物与真实 QQ 消息**在数据上完全同构**；现仅靠 `messages.event_id` 前缀 `console_chat_` 区分。
   - 该手段有三重局限：
     (a) **只覆盖"有消息"的链路**——上传 / RAG 入库 / 密级调整 / 脚本批量改节点等操作**没有 message**，记号无处可加；
     (b) **留痕表无关联键**——`business_event_logs` 仅有 `pipeline_run_id`、**无 `message_id`**（且 `log()` 收了 `conversation_id` 参数却未入库），`files` / `knowledge_chunks` / `node_events` 无任何消息标识，故即使存在"分辨方法"也**找不到键**去判断；
     (c) **前端加记号可被绕过**——`emy-test` 与 curl 均直接打 HTTP，不经 console 页面。
   - 结论："这条记录是真实发生还是测试产生"这一信息，**只在请求进入的那一刻存在**，事后无法反推，必须在该刻捕获并落到字段。
5. **现象（渠道断链，但不构成主维度）**：渠道身份在会话层完整（`session_archives.platform` / `im_user_id`、`messages.sender_im_id` + `conversations.im_platform`、`user_im_bindings`），而在业务事件层丢失——`business_event_logs` 仅 `user_id` + `user_name`。
   - 但渠道本质是**传输方式**，不是留痕的主语（主语是"人 + 动作 + 对象 + 结果"），故**定位为附属字段**，仅在真实用户行为时有意义，不承担分类职责（见 §四.6）。
6. **现象（只记成功）**：现有记录口径为"成功才记"。权限被拒路径直接返回，不留痕（典型：`file_service.update_confidentiality` 的"仅上传人本人或 L5/L6 管理员可调整"），越权尝试无记录。
7. **现象（暗记脆弱）**：console 模拟对话的标识是字符串前缀：不可索引、只覆盖单一入口、命名变更即导致历史数据不可查；且现由**后端** `chat_send` 写入，与"前端加记号"的设想相比更可靠，但仍不结构性。
8. **现象（上下文载体不可靠）**：`BusinessEventLogger._current_context` 为**类级可变字典**，多会话 / 多作业并发时互相覆盖，归因信息即使写入也不可信。
9. **定性**：非单点遗漏，而是**缺少统一的留痕挂载点与归因模型**——每张日志表各记各的维度、每个入口各写各的记录，导致"记了什么"依赖具体代码路径，"来源是谁"无法回答。
10. **影响**：
    - 运维动作无痕（RAG 入库、上传、脚本建节点）→ 无法回答"这批知识/这批节点是谁什么时候灌的"。
    - **测试流量混入消费端** → 行为分析、进化闭环、SOP 命中率统计被污染。Emily 会把自己造的测试数据当成用户真实行为来学 —— 这是本需求最刚性的动机。
    - 渠道不可溯 → 无法按渠道统计、无法与 `user_im_bindings` 交叉校验身份真实性。
    - 越权无痕 → 留痕不具备审计价值。
    - **入口越多、补录越漏** → 留痕工作量随入口线性增长，且永远追不上新入口。
11. **结论**：需独立立项，**把留痕下沉到统一执行层（service 动作层）建立单一挂载点**，并在此之上补齐归因维度与流量性质标识。

## 二、目标

1. **G1 留痕完整**：所有**状态变更**类操作（含成功、失败、被拒绝三态）均留痕，覆盖全部 entrypoint——**且覆盖方式是"动作本身留痕"，而非"每个入口各自补录"**。
2. **G2 归因可答**：每条留痕都能回答"**谁 + 做了什么 + 对象是什么 + 成没成 + 这条属于哪类行为**（真实用户 / 运维 / 系统 / 测试）"。
3. **G3 流量可分离**：测试流量与真实流量在同一存储中可被**结构化**过滤（读字段），不依赖字符串约定；提供统一"分辨方法"供消费端调用。
4. **G4 挂载点唯一**：留痕**只挂在统一执行层（`emily_core/services/` 的动作方法）**，入口层只负责注入上下文。新增一个入口不需要新增任何留痕代码。
5. **G5 链路不变**：统一的是**日志模型与执行层**，**不是调用入口** —— 不做入口分流、不做硬性拦截、不改变任何请求路径。

## 三、范围

- **纳入**：
  - **统一执行层（`emily_core/services/`）的留痕挂载点**：动作层留痕写入器 / 装饰器 + 动作边界定义；
  - **service 返回约定统一**（三态判定的前置条件）；
  - **上下文注入机制**（contextvars 化）与各入口注入：IM（`core.handle_message`）、console（路由层统一依赖）、调度（作业入口）、脚本（CLI 入口）；
  - **console 绕过 service 的端点回接**：`/console/upload`、`/console/rag-index`、`/console/rag-search` 先在 service 层补齐能力，再同源接线；
  - `business_event_logs` 增加**流量性质与渠道**维度；`messages` / `node_events` / `scheduler_job_logs` 等留痕表的维度对齐；
  - `ConsoleLogRepo` 增加**流量性质过滤**维度与统一分辨方法。
- **不纳入**：
  - `EvolutionLogWriter` 的"非阻断 + 截断 + 异步"三原则（保持不变）；
  - Session 归档正文机制；
  - `EventJournal` md 双写的存废（另案评估）；
  - 历史日志的物理清理；
  - **`scripts/` 下 44 个 CLI 脚本的逐个改造**（脚本仅作为入口注入一次上下文，不逐个脚本改代码）；
  - **不做入口分流 / 硬隔离**（不改请求路径、不拦测试流量，仅打标；见 G5）。

## 四、术语

1. **统一执行层**：`emily_core/services/`。各入口（IM / console / scripts / tools / scheduler）共享的动作实现层（依据约束 10：scripts 与 tools 共享 service 层，互不调用）。
2. **动作边界**：**service 的公开方法即"一个动作"**。service 内部互调（如 `node_batch` 调 `node_state_machine`）不构成独立动作，不重复留痕。
3. **挂载点**：留痕的**唯一记录位置**（service 动作层）。入口层不得写留痕。
4. **状态变更操作**：产生数据写入或状态迁移的操作（增删改、入库、密级调整、确认/驳回）。
5. **三态**：成功 / 失败（异常）/ 被拒（规则或权限不通过）。**口径**：
   - **动作已开始**后的规则/权限拒绝（判定在 service 内，如 `file_service.update_confidentiality` 的"仅上传人本人或 L5/L6"）→ **属于"被拒"，须留痕**；
   - **请求尚未进入动作**的参数校验拒绝（判定在入口，如 `file_id` 为空、密级值域非法）→ **不计入三态、不留痕**（未产生任何状态变更）；
   - 即：**校验位置 ≠ 留痕位置**。入口可继续做参数校验（属防护，应保留），只是不产生留痕。
6. **流量性质（`source`）四分类** —— `source` 的语义是"**这条留痕属于哪一类行为**"，**不是"从哪个入口进来"**：

   | 取值 | 含义 | 消费端用途 |
   |------|------|-----------|
   | `user` | 真实用户行为（经 IM 渠道） | 行为分析、SOP 命中率、进化闭环的**样本** |
   | `ops` | 人发起的运维操作（console 直接操作、脚本 CLI） | 审计与运维追溯；**排除出**用户行为画像 |
   | `auto` | 无人触发的系统行为（调度、守护、进化、归档） | 同上排除；另用于系统自身健康度统计 |
   | `test` | 测试流量（console 模拟对话） | **必须排除**，最刚性的一类 |

   说明：`ops` / `auto` 与"有没有 actor"相关但不等价（`ops` 有操作人，`auto` 无），故显式记录，不依赖"`actor` 是否为空"的隐含约定。
7. **渠道（`channel`）与来源标识（`channel_account`）**：
   - `channel`：传输方式（QQ / 企微 / 小程序 / 邮箱）。**附属信息，非留痕主维度**；仅 `source=user` 时必填（`ops` / `auto` / `test` 可空）。
   - `channel_account`：该来源的**具体标识**。`user` → 渠道账号（QQ 号 / 企微 userid）；`ops` → 操作载体（`cli` / `console`）；`auto` → 作业标识。非必填。
   - 即 `channel_account` 的统一语义是"来源标识"，故 `ops` 内部（console 直接操作 vs 脚本 CLI）**无需另设维度即可区分**（见 Q18）。
8. **暗记**：标识一条消息或操作由 console 触发的结构化字段（取代现字符串前缀）。
9. **分辨方法**：消费端统一的读取入口，用于判断"这条留痕属于哪类行为"（读 `source` 字段，**不得 grep 字符串前缀**）。
10. **归因四元组**：`actor` + `source/channel/channel_account` + `action/target` + `result`。

## 五、功能需求

### 前置条件（先行，缺则后续 FR 无法落地）

1. **FR-14 service 返回约定统一**：统一执行层的动作方法须提供**可判定的结果**（建议统一为 `{success, reason_code, reason}` 形态或等价的结构化结果），使挂载点能机械区分「成功 / 失败（异常）/ 被拒（规则或权限不通过）」三态。现状返回形态混杂（`{"success": ...}` 字典 / ORM 对象 / `raise` / `None`），**必须先收敛，否则 FR-2 无法落地**。现有部分 service 已具备该结构（如 `file_service.update_confidentiality` 返回 `{"success": False, "error": "permission_denied", ...}`），可据此归纳错误码到三态的映射。
2. **FR-15 动作边界与单点挂载**：定义"一个动作 = service 的一个公开方法"，留痕**只在该层写入一次**。需给出判定规则，防止一次用户动作因 service 内部互调产生多条留痕（与 FR-3 防自激同源）。挂载方式建议为统一装饰器 / 统一写入器，保证不依赖逐个方法手写。

### 归因与来源

3. **FR-1 统一留痕归因模型**：所有留痕表向归因四元组对齐，字段命名与取值域统一；不得各表自造维度；**记录点唯一落在 service 动作层**。
4. **FR-4 流量性质与渠道落地**：`business_event_logs` 增加 `source`（取值见 §四.6）/ `channel` / `channel_account` / `result` / `error_reason`：
   - `source` 记**流量性质**（`user` / `ops` / `auto` / `test`），**不记入口类型**；新增 `source` 索引；
   - `channel` 为**附属字段**，仅 `source=user` 时必填；**不强制"所有留痕都必须有通讯工具"**（`ops` / `auto` / `test` 无渠道可填）；
   - `actor`（`user_id`）**不得因缺失而静默不留痕**：`ops` 类动作若未取得操作人，须记 `actor=unknown` 并保留记录（现 `console_resources.py` `_delete_file` 为 `if operator_id:` 才写 → 缺失即无痕）。
5. **FR-5 上下文自动注入**：扩展 `BusinessEventLogger` 既有 `_current_context` 机制，承载 `source` / `channel` / `channel_account`。要点：
   - **载体必须更换为 `contextvars`**（现为类级可变字典，见 §一.8，按约束 0 根治而非迁就），并发会话 / 并发作业之间互不串扰；
   - **注入发生在各入口的后端代码**（非前端、非消息字段）——因为"是不是测试"只在请求进入那一刻可知（§一.4）；
   - 入口注入一次，下游动作自动携带，避免逐点改传参。
6. **FR-6 IM 入口一次注入**：在 `core.handle_message` 入口从 `StandardMessage` 提取渠道身份写入上下文，并置 `source=user`；覆盖 QQ / 企微 / 小程序 / 邮箱四渠道，不改任何 SOP 或工具。
7. **FR-7 入口职责收窄为"注入上下文"**：四类入口各自**只做一次上下文注入**，**不在入口层记录留痕**。各自默认取值：

   | 入口 | 注入点 | 默认 `source` |
   |------|--------|--------------|
   | IM | `core.handle_message` | `user` |
   | console | 路由层统一依赖 / 中间件；模拟对话 → `test`，直接操作 → `ops` | `test` / `ops` |
   | 调度 | 作业执行入口 | `auto` |
   | 脚本 | CLI 入口 | `ops` |

   入口层对 `BusinessEventLogger` 的直接调用**一律移除**（现存的 `application/*_app.py` 与 `console_resources.py` 中的记录点随本 FR 迁移至 service 动作层）。

### 覆盖补齐

8. **FR-8 console 端点回接统一执行层**：`/console/upload`、`/console/rag-index`、`/console/rag-search` 三个绕过 service 的端点，**先在 service 层补齐对应能力**（文件上传归档 / 知识入库 / 知识检索），再由 console 与 IM 各入口**同源调用**该能力——与业务工具、脚本共用同一实现。要求：
   - 不在路由层直接调 repo / tool / provider（消除约束 14 违规，见 §一.3）；
   - **不做"端点补录"**：留痕由 FR-15 的挂载点在 service 动作层自动产生；
   - 同样**不将 `files` / `knowledge_chunks` 纳入日志聚合白名单**。
9. **FR-9 暗记结构化**：`messages` 增加 `source` 字段（取值语义同上，消息链路通常为 `user` / `test`），各入口统一写入；`console_chat_` 前缀降级为兼容手段，不再作为判定依据。
10. **FR-10 系统与调度来源补全**：`scheduler_job_logs` 补 `source` 与 `actor`，标为 `auto`（`actor` 取值可为"系统"/作业标识），使其与业务事件处于同一归因模型；`auto` 类操作统一登记。
11. **FR-11 消费端分辨与过滤**：`ConsoleLogRepo` 的模块白名单机制保留，增加 `source` 过滤参数，并提供**统一分辨方法**（供日志面板、行为分析、进化闭环共用；**读字段，不 grep 前缀**）。日志面板提供"排除测试流量"开关；行为分析与进化闭环**默认排除 `test`**（并默认排除 `ops` / `auto`，仅取 `user` 作样本）。

### 质量与存量

12. **FR-2 三态记录**：状态变更操作的成功、失败、被拒绝均须留痕；被拒记录须含拒绝原因；三态口径见 §四.5。判定依据为 FR-14 的统一返回约定。**读取类默认不记**（防自激），仅"高风险读"（全量导出、文件下载、跨项目查询）按需记录。
13. **FR-3 防自激约束**：console 日志面板刷新、`/llm-trace` 增量轮询、SSE keep-alive 帧等观测行为**必须不产生留痕**；service 内部互调不得重复留痕（FR-15）。
14. **FR-12 写入失败可观测**：为"留痕写失败"增加计数或记录，纳入既有 `scripts/self_check.py` 体检项，解决"未记"与"记失败"外部不可区分的问题。
15. **FR-13 历史回填与文档同步**：存量 `business_event_logs` 按 `event_action` 前缀回填 `source`（`console_*` → `ops`；其余按是否经 IM 渠道判定为 `user`，无法判定 → `auto`）；`messages.event_id` 前缀迁移至 `source`（`console_chat_` → `test`，其余 `user`）；同步更新 `docs/数据库设计.md`、`docs/接口协议与调用约定.md`。

## 六、非功能需求

1. **NFR-1 非阻断不变**：沿用 `EvolutionLogWriter`「失败只告警、截断（Text 5000 / String 500）、`asyncio.to_thread` 异步」三原则。
2. **NFR-2 主链路零额外开销**：留痕不得引入额外 LLM 调用；不得让运维动作走通意图路由与 ReAct 循环。
3. **NFR-3 可过滤**：`source` 建索引，过滤查询不因新增字段劣化。
4. **NFR-4 可回退**：新增字段与注入逻辑可整体关闭，回落到当前行为。
5. **NFR-5 不改写业务语义**：`project_events`（面向项目成员的业务台账）不得混入运维动作。
6. **NFR-6 入口零留痕代码**：新增一个入口（渠道）时，留痕侧**不需要写任何代码**——只要该入口经过统一执行层并注入一次上下文。此为 G4 的可验证形式。
7. **NFR-7 不改链路**：新增机制不得改变任何请求路径、不得新增拦截或分流逻辑（G5）。

## 七、约束

1. **挂载点唯一（新增）**：留痕记录点**唯一在 service 动作层**。入口层（`api/routes/`、`application/`、`scripts/`）**禁止直接调用 `BusinessEventLogger` / 留痕写入器**；发现即为回归（约束 13 同类纪律：能力增长落在能力层，不在入口层复制）。
2. **console 不得绕过统一执行层（新增）**：重申约束 14——console 的动作类能力必须复用 service 层既有能力，不得在路由层复刻或直接触达 repo / tool / provider。既有三处绕过点随 FR-8 回接。
3. **不新建重复层（新增）**：留痕挂载点复用 `emily_core/services/`，**不新建独立的"留痕服务层"或"操作层"**，避免与既有分层（约束 2：API → EmilyCore → Session → WorkItem → Application → Service → Repository）冲突。
4. **入口不合并、不隔离**：console 操作不得包装为 IM 消息投递（会造成 LLM 成本放大、`project_events` 台账污染、权限模型冲突、行为数据失真）；也不得在入口做测试流量拦截/分流。统一的是**日志模型与执行层**，入口仅**注入标记**。
5. **标识必须结构化**：流量性质须落库为字段（FR-4），**禁止以字符串前缀 / 消息体记号作为判定依据**（可被绕过且不可索引，见 §一.4）。
6. **权限模型不改**：IM 走 L1–L6 用户权限与项目可见范围；console 走后台视角，两者不互相让渡。
7. **改动方式**：优先扩展现有结构与 `_PENDING_COLUMNS` 补列机制，不新建重复表。

## 八、非目标

1. 不重构 `EvolutionLogWriter` 与非阻断原则。
2. 不替换 `EventJournal` md 双写（存废另案）。
3. 不做日志聚合面板的 UI 重设计（仅加过滤开关）。
4. 不做日志的归档压缩与生命周期治理。
5. 不改造 `session_archives` 的归档正文机制。
6. 不逐个改造 `scripts/` 下的 CLI 脚本（脚本只作为入口注入上下文）。
7. 不做入口分流、测试流量拦截或链路隔离。

## 九、验收方向

1. **挂载点唯一**：`api/routes/`、`application/`、`scripts/` 下对留痕写入器的调用数**为 0**；业务事件均由 service 动作层产生。新增一个入口（渠道）无需改动留痕代码（NFR-6）。
2. **同源同痕**：文件删除分别从 IM 与 console 触发，**两条均产生留痕**且 `source` 可区分（现状：IM 侧无痕）。
3. **脚本留痕**：运行 `scripts/manage_nodes.py` 建节点/改节点，产出带归因四元组的留痕，`source=ops`（现状：零记录）。
4. **补录覆盖**：console 上传 / RAG 入库 / 查库 / 密级调整四操作，各自产生一条含归因四元组的留痕，且其执行路径**经过 service 层**（无路由层直调 repo / tool / provider）。
5. **无消息操作也可分辨**：上传 / RAG 入库 / 密级调整 / 脚本节点变更**没有 message**，但仍能通过 `source` 分辨真实与测试——这是本方案相对"消息加记号"的核心增量。
6. **真实/测试可分离**：`emy-test` 直发 HTTP 产生的留痕与 console 页面产生的留痕**均可被识别为 `test` / 非 `user`**（不依赖调用方自觉加记号）；`WHERE source='user'` 即真实用户行为样本。
7. **渠道溯源**：QQ 与企微两渠道对同一用户各发一条录入类指令，两条记录的 `channel` / `channel_account` 可区分且与 `user_im_bindings` 一致。
8. **三态覆盖**：非上传人、非 L5/L6 用户尝试改密级（判定在 service 内），须产生一条"被拒"留痕（含原因）；而请求参数校验类拒绝（`file_id` 为空）**不产生**留痕。
9. **流量分离**：`WHERE source='user'` 可一键排除测试与运维流量；面板开关排除后行为分析与真实流量统计不受影响。
10. **防自激**：连续刷新日志面板 / 轮询 `/llm-trace` 五分钟，"日志聚合"条数不因观测行为增长；一次用户动作在 `business_event_logs` 中**只产生一条**记录（无 service 内部互调重复）。
11. **并发不串扰**：两个会话（或一个会话 + 一个调度作业）并发执行状态变更动作，各自留痕的 `source` / `channel` / `actor` 不串（验证 FR-5 的 contextvars 载体）。
12. **不回归**：主链路（消息处理、SOP 执行）无新增告警；请求路径与拦截行为无变化（NFR-7）；非阻断原则下留痕失败不影响业务返回。
13. **回填正确**：存量数据按前缀规则回填后，抽样核对 `source` 取值正确。

## 十、决策记录（2026-09-16 确认）

| 编号 | 议题 | 决策 |
|------|------|------|
| Q1 | "所有操作都要记录"的口径 | **收窄为"所有状态变更必须留痕且记三态"**；读取类默认不记，仅高风险读按需记 |
| Q2 | 留痕是否强制携带通讯工具 | **否**。`channel` 为附属字段，仅 `source=user` 时必填 |
| Q3 | console 是否走"用户+通讯工具"模式 | **仅模拟对话维持现状**；其余 console 操作保持独立 API，统一的是日志模型而非入口 |
| Q4 | console 暗记形式 | **结构化字段**，取代 `console_chat_` 字符串前缀 |
| Q5 | console 缺口补齐方式 | **补业务事件留痕，不将 `files` / `knowledge_chunks` 纳入 `LOG_MODULES` 白名单** |
| Q6 | 上下文注入 vs 逐点传参 | **上下文自动注入**，避免逐调用点改动 |
| Q7 | **留痕挂载点** | **统一执行层 = `emily_core/services/` 的动作方法**（非 `scripts/`，非入口层）。挂载点唯一，入口层只注入上下文 |
| Q8 | **console 缺口补齐路径** | **先补 service 能力再同源接线**，随挂载点自动获得留痕；**不做端点级补录**（原 FR-8 方案废弃） |
| Q9 | **前置条件** | FR-14（service 返回约定统一）与 FR-15（动作边界定义）**先行**，否则三态与防重复无法落地 |
| Q10 | **上下文载体** | 必须为 `contextvars`，**不得沿用类级可变字典**（现 `_current_context` 并发不安全） |
| Q11 | **`source` 语义** | **流量性质**（`user` / `ops` / `auto` / `test`），**不是入口类型**。理由：console 模拟对话走的即真实 IM 入口，其产物与真实消息数据同构；按入口分类会把它误标为"另一渠道"，而它本质是"真实渠道上的测试流量" |
| Q12 | **脚本动作归类** | 归 `ops`（有 actor 的人发起运维动作），**不单设 `script` 取值**；与调度（`auto`，无人触发）严格区分 |
| Q13 | **`source` 的不可替代职责** | 只有一条：**标识测试流量**（`test` vs 其余）。该区分数据同构、事后不可推。`ops` / `auto` 与 `actor` 相关但显式记录更好（避免依赖"`actor` 为空"的隐含约定） |
| Q14 | **三态口径（被拒）** | **动作已开始**后的规则/权限拒绝须记（判定在 service 内）；**请求尚未进入动作**的参数校验拒绝不计入三态、不留痕。**校验位置 ≠ 留痕位置** |
| Q15 | **标识落点与消费方式** | 落 `business_event_logs.source` 字段，由留痕写入器透传；消费端经**统一分辨方法读字段**。**不采用"消息上加记号 + 前缀 grep"**（无消息的操作无处可加；留痕表无关联键；前端记号可被 `emy-test` / curl 绕过） |
| Q16 | **链路不变** | 统一的是日志模型与执行层，**不做入口分流 / 硬隔离**；入口仅注入标记，请求路径与拦截行为一律不变 |
| Q17 | **console 是否加认证（原 D1）** | **本期不纳入**。认证属独立安全议题，涉及前端静态页携带凭证与 `_PUBLIC_PREFIXES` 调整（同批还放行 `/api/v1/scripts`、`/api/v1/config`），改动面超出本需求边界；且本需求刚需（动作留痕 / 三态 / 真实与测试分离）**不依赖认证**。**但须显式声明限制**：`ops` / `test` 的 `operator_id` 由请求体自述，**不具备对外审计效力**，仅作内部参考；本期只做两项低成本补强——`actor` 缺失必留痕（见 FR-4）、记录来源 IP。console 认证立为独立后续项 |
| Q18 | **`ops` 内部是否再细分（原 D2）** | **不新增列**。`channel_account` 语义定为"来源标识"：`ops` 填操作载体（`cli` / `console`）、`auto` 填作业标识，即可区分"后台点的"与"脚本跑的"；若未来成为刚性需求再补 `ops_source` 列（`_PENDING_COLUMNS` 机制成本低） |
