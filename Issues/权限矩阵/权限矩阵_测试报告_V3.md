## 〇、执行摘要（先看这里）

本次在真实 Docker 环境执行了 **M1 可见性探针 / M2 工具直调探针 / M3 IM 端到端 / M4 console 端点 / M5 DB 断言 / M6 审计断言** 六类方法，覆盖 R2~R18 主体能力。

**三项最重要结论**：

1. **能力正确性总体良好**：R2/R3/R4/R5/R8/R10/R11/R13/R14/R15/R18 的档位边界、失败文案、审计留痕，与计划 §3 反馈字典**逐字吻合**。特别是 R11 证伪了 GAP-4（L6 能移除共享文件，`>=5` 未被写成 `==5`）。
2. **三个高危"直调越权"（新发现，计划未预见）**：L1 访客**能直接调用** `record_file`（上传文件）、`record_event`（记录事件）；L1 能通过 `query_node` 读到**非参与项目的节点**。这三者均为 **handler 层无自身鉴权、仅靠可见性过滤（tool set）兜底** —— IM 路径因工具不可见而被挡，但**任何绕过可见性过滤的调用路径（直调/工具编排/未来新入口）都能长驱直入**，属宪法 Q6 意义上的"封边失效"。
3. **GAP-2 成立（计划已预见，本次证实）**：L3 通过 `record_task` + `node_id` **成功把任务挂到节点下**，绕过 `create_task_node` 的 L5+ 门禁。

**另有两项与 V3 计划的偏差需回写**：V3 计划中的表名/字段名与实际不一致（`nodes`→`project_nodes`、`is_deleted`→`is_discarded`、`users.name`→`users.username`/`level`、`permission_audit_logs`→`business_event_logs`），已在本报告全部修正。

## 十、结论与建议

### 10.1 测试结论

**❌ 未通过**。核心能力（人员/企业/节点/文件/RAG 出库）的**档位边界与失败文案绝大多数正确**（42/48 通过），审计留痕满足 D8，console 与工具通道同源。但存在：

- **3 个高危直调越权（B1/B2/B3）** —— 均为"仅靠可见性过滤兜底、handler 无自身鉴权"，构成封边失效；
- **1 个高危旁路越权（B4=GAP-2）** —— `record_task` 可绕过节点挂载门禁；
- **1 个口径不符（B5）** + **2 个注册/前置缺陷（B6/B7）**。

按 §7 判定标准，"存在 🔴 高危 + 违反 Q6 封边" → **未通过**。

### 10.2 待改进项（按优先级）

1. **修复直调越权（B1/B2/B3）**：为 `record_file`/`record_event`/`query_node` 在 handler 或 service 层补**自身等级/可见性门禁**，不依赖 tool set 过滤——这是最根本的一条（"根治而非迁就"，约束0）。
2. **修复 GAP-2（B4）**：`record_task` 携 `node_id` 时增加挂载等级判定。
3. **修复工具注册（B6）**：注册 `embed_and_index` 或清理 SOP 3.2 声明，清理 `tool_registry` 唯一键冲突。
4. **对齐 Q8（B5）与注13（B7）**：明确 R15 起点与 SOP-012 归属。
5. **补测清单（§3.2）**：R6、R17、GAP-3、GAP-6、R4-空企业删除、R2-L4/L1、R16 机密泄露专项。

### 10.3 遗留风险

- 未做 R16 的 **`node_conf_cap` 机密泄露对抗测试** —— 若实现有误可能泄露机密文件。
- REST/CLI 通道（GAP-3）与纠错类入口（GAP-6）**完全未验**。
