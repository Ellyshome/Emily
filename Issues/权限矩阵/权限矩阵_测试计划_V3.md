## 〇、本计划的验证闭环

```
目标格（权限表 R1~R18 × L6~L1）
   ↓ 用 M1 核验"可见性"（能否看见）
   ↓ 用 M2 核验"可执行性"（看见后能否执行 / 执行结果）
   ↓ 用 M3/M4 核验"两条通道"（IM 对话 / console 后台）
   ↓ 用 M5/M6 核验"落地效果"（DB 真实变化 / 审计留痕）
   ↓ 与【预期反馈字典】逐字比对 → 判定 ✅达成 / ❌未达成
   ↓ 未达成 → 登记 GAP + 实现动作
```

> **核心原则**：**"可见"与"可执行"必须分开验**——`sop_only` 工具"看得见但跑不通"是本模块最典型的空窗（GAP-1 即此类）。任何格子只验可见性 = 未完成。

### M1 可见性探针（验"能否看见"）

- **判定基线**：`level` 必须等于该用户的真实等级（**若为 1 说明快照降级**，须先查用户是否存在/状态是否为 active）。

- **注意**：L1 会额外剔除 `mcp:*` 工具（`fetch_available_tools` 内建）。

### M2 工具直调探针（验"可执行性"）

> **关键坑**：`scripts/toolmgr.py call` 只传 `params`，而 handler 的操作人是**独立形参** `user_id` → 直调时恒为空 → **一律 fail-closed**。因此：
> - **能用的**：`toolmgr.py` 只适合测「无操作人 → 必须拒绝」的 fail-closed 用例。
> - **要测"某等级用户调用"必须走下方探针**（从注册表取已装配 handler，再补 `user_id` 关键字）。

**临时探针脚本**（执行时落地，**用后删除**）：`scripts/_perm_probe.py`

```python
"""权限探测探针（临时）。用法：
    uv run python scripts/_perm_probe.py <tool> <user_id|-> '<params_json>'
    user_id 传 - 表示不注入操作人（验 fail-closed）
"""
import asyncio, json, sys
sys.path.insert(0, "emily-core")
from emily_core.bootstrap import init

core = init(); core._ensure_initialized()
tool, uid, raw = sys.argv[1], sys.argv[2], (sys.argv[3] if len(sys.argv) > 3 else "{}")
params = json.loads(raw)
h = core._business_flow_tools.get(tool).handler      # partial 已注入依赖
kw = {} if uid == "-" else {"user_id": uid}
try:
    out = asyncio.run(h(params, **kw))
except TypeError:                                     # 不支持 user_id 形参的工具（如人员类回落 operator_id）
    if uid != "-":
        params["operator_id"] = uid
    out = asyncio.run(h(params))
print(json.dumps(out, ensure_ascii=False, indent=2))
```

**示例**：

```powershell
# 无操作人 → 预期 fail-closed 拒绝
uv run python scripts/_perm_probe.py delete_file - '{"file_no":"FIL-20260920-0001"}'
# L3 操作人（非上传人）→ 预期 permission_denied
uv run python scripts/_perm_probe.py delete_file <L3_UUID> '{"file_no":"FIL-20260920-0001"}'
# L5 操作人 → 预期 success
uv run python scripts/_perm_probe.py delete_file <L5_UUID> '{"file_no":"FIL-20260920-0001"}'
```

**在容器内执行**（若 DB 只在容器网络内可达）：
```powershell
docker cp scripts/_perm_probe.py emily-core:/app/_perm_probe.py
docker exec emily-core python /app/_perm_probe.py delete_file <L3_UUID> '{"file_no":"..."}'
```

## 四、用例卡（逐能力行，含方法 + 预期反馈）

> 每卡三段：**① 方法与命令**　**② 档位预期反馈表（逐字）**　**③ DB/审计断言与判定**。

### R1 人员可见范围（注1）

**① 方法**：M1 取六档用户快照的 `project_ids` / `authorized_node_ids`；M5 反查节点归属。

```powershell
# 逐档执行 M1，记录 project_ids 与 authorized_node_ids
docker exec emily-postgres psql -U emily -d emily -c "
SELECT c.company_name, c.is_admin FROM company_info c WHERE c.id='<用户company_id>';"
```

**② 预期反馈**：

| 档 | 预期 |
|---|---|
| 管理单位（`is_admin=true`） | 可见 = 本项目**全部节点**；`project_ids` = 其项目 |
| 其他单位 | 可见 = `node_participant_companies` 推导集；**不随等级变化**（六档同单位结果应一致） |
| 无企业 / 无参与 | 可见集 = **空**；业务查询被拒（见 R9/§3.1 `暂无可查询的项目数据…`） |

**③ 判定**：`authorized_node_ids` 与 SQL 推导集**逐元素相等**；六档同单位用户的集合**完全相同** → ✅。

### R2 人员等级调整（注2）

**① 方法**：M2（人员类支持 `user_id` 形参**或** `params.operator_id` 回落，故 `toolmgr` 亦可）

```powershell
uv run python scripts/_perm_probe.py update_user_level <操作人UUID> '{"target_user_id":"<目标UUID>","new_level":4,"reason":"权限验证测试"}'
```

**② 档位预期反馈表**：

| 操作人 | new_level | 预期 `success` | 预期 `reason_code` / `message` |
|---|---|---|---|
| L6 | 6 | true | `""` / `ok`；`data.new_level=6` |
| L5 | 4 | true | `""` / `ok` |
| L5 | 5 | **false** | `permission_denied` / `权限不足：不可将该人员调整至目标等级` |
| L4 | 3 | true | `""` / `ok` |
| L4 | 4 | **false** | 同上 |
| L3 | 2 | true | `""` / `ok` |
| L3 | 3（等于自身） | **false** | 同上 |
| L2 / L1 | 任意 | **false** | `permission_denied`；且 M1 显示工具**不可见** |
| 任意 | 7 | **false** | `invalid_level` / `目标等级须在 1-6 之间` |
| `-`（无操作人） | 4 | **false** | `permission_denied` / `操作人不存在` |

**③ 断言**：
```sql
-- 成功侧：等级确实变更
SELECT id, permission_level FROM users WHERE id='<目标UUID>';
-- 拒绝侧：零变更 + 有 rejected 审计
SELECT result, error_reason FROM permission_audit_logs
WHERE action='user_level_updated' ORDER BY created_at DESC LIMIT 5;
```
**判定**：拒绝时 `success=false` **且** `permission_level` 未变 **且** 存在 `result=rejected` 审计行 → ✅（三条件缺一不可，D8 要求"被拒也留痕"）。

**④ 失败诊断线索**：若 L5 调 L5 却成功 → 检查 `_can_adjust_level` 是否被绕过（服务层判定点唯一性）；若拒绝但无审计 → D8 留痕要求未满足。

## 七、判定与产出

### 7.1 逐格判定口径

| 情形 | 判定 |
|---|---|
| 目标 ✓ 且 可见 ✓ 且 可执行 ✓ 且 DB/审计 ✓ | ✅ 达成 |
| 目标 ✓ 但**不可见**或**可见不可执行** | ❌ 未达成（能力空窗） |
| 目标 ✗ 但实际可执行 | ❌ 未达成（越权） |
| 属已知取舍（R4/L3、R15/Q8）且与权限表字面一致 | ✅ 达成（备注"已知取舍"） |
| 环境阻塞（TEI/LLM 未就绪） | ⏭️ SKIP（须注明，不计入达成率分母） |

### 7.2 达成率

```
格子达成率 = 已达成格数 / (96 - SKIP 格数)
注释达成率 = 已成立注数 / 14
通道一致性 = IM 与 console 结论一致的格子数 / 有 console 对应入口的格子数
```

### 7.3 产出

`权限矩阵_测试报告_V3.md`：11 章 + **逐格达成矩阵（96 格，每格：结论 / 证据 / 命令）** + **差距登记表（含实现动作与回归验证）** + `wiring_scan` 原始输出。
