## 一、设计口径裁定（5 项，计划 V2 §设计口径裁定 A~E）

> 性质：**为实现而必须作出的解释性裁定**，不是新增需求。计划已按"建议"落地；改判即触发对应模块的接口调整。

| # | 裁定（计划已落地） | 若维持的影响 | 若改判的影响与代价 | 需动层级 | 建议 | 结论 |
|---|-----------------|------------|-----------------|---------|------|------|
| **A** | **在追踪群列表不按身份收敛，群消息列表 / 检索按身份收敛**。依据：AC-US-06.1「列出**在追踪群**」、G4「能列出**全部**在追踪群」；US-08 的场景限定为"一份**群消息检索**请求" | 群名与人工备注对全体使用者可见（**不含**群内消息内容）；对话侧"有哪些群"的发现价值成立 | 若列表也收敛：用户无从得知"可以就哪些群提问"，G4 与 AC-US-06 的能力发现价值丧失。改动面 ≈ M5（列表加作用域）+ M6（回复语义）+ M7（上栏），3 个接口 | 计划为主；若认为属 AC-US-06.1 的口径变更 → 两者 | 维持 | |
| **B** | **控制台写动作分工**：① 备注维护走**既有脚本通道**（控制台零新增写路由）；② 名册刷新由控制台路由调用 M4 的**同一 Service**（与脚本同源） | AC-US-13.5 的"写能力唯一"按"**人工录入**写能力唯一"解释；名册刷新（数据保鲜、无人工录入）不计入新增写能力 | 若要求名册刷新也走脚本通道：打开视图 / 查看名册都变成一次 subprocess 调用，AC-US-04.2 的"数秒内完成"风险上升；若改为"仅按钮手动刷新"，则 AC-US-04.2 的"打开即先刷新"落不了地 → 须改该 AC | 规格解释（涉及 AC-US-13.5 与 AC-US-04.2 的关系） | 维持 | |
| **C** | **名册新鲜度承载位挂在群台账**（`conversations.roster_synced_at`），过期结论单一判定点。对应 PRD 附录 B-3 | 名册**为空**（从未成功拉取）的群也能被判定"从未同步"，因而能被巡检列出 | 若改挂名册表自身：零行的群无处表达"从未同步" → **过期巡检恰好漏掉最需要巡检的那批群**；若两处都挂：两个时间源必然漂移 | 纯计划（附录 B-3 明确留给 plan） | 维持 | |
| **D** | **附件打开走"控制台侧同源只读路由"**：路由只做定位与交付，复用既有文件能力（锚定文件台账 → 复用 `FileManager`；仅有本地路径 → 存储根下解析 + 目录穿越防护；两者皆无 → 仅元信息） | AC-US-11.6 的"显示元信息**并可打开**"可完整交付 | 若判定"复用既有附件查看通道"不成立：US-11.6 回归"超出本版范围"，M7 退化为**仅显示元信息** → 须改 AC-US-11.6 措辞 | 两者（可能触发 AC 变更） | 维持；**本项是 5 项中最可能被判不成立的，建议优先回** | |
| **E** | **名册未就绪时统一回报"没有匹配记录"**，不明示名册状态；名册的缺失/过期只在**控制台与日志**可见。依据：AC-US-08.3「返回空且回复中**不泄露**该群消息内容」+ PRD §九.1 场景 19「过期巡检只做在控制台与日志，不给 LLM 暴露运维巡检能力」 | 对话侧维持现有失败语义，不新增失败类型；与 AC-US-07.7 的空结果口径一致 | 若要求向使用者明示"名册未就绪"：M5 需增加可区分的结果类型 + M6 回复文案 + M7 呈现，3 个接口；且与"不泄露"方向存在张力。**同时应从 PRD 风险 4 中关闭该待决项** | 两者 | 维持 | |

## 二、PRD 待决项（3 项，PRD V2 §六 风险 1 / 3 / 9）

> 性质：PRD 自留的开放项，计划已按**建议值**实现但未替 PRD 拍板。复核后请回填 PRD 对应行。

| # | 待决项（PRD 位置） | 计划采用的实现值 | 影响 | 建议 | 结论 |
|---|-----------------|---------------|------|------|------|
| **1** | 名册新鲜度门槛的**取值**（风险 1） | 默认 **7 天**，落为**可配项** `EMILY_GROUP_ROSTER_TTL_DAYS`（代码默认 7），无需改代码即可调 | 取值**大** → 已退群者的检索放行窗口长（安全方向）；取值**小** → 逐群调平台接口的频次高（可能触平台频率限制）。窗口上限恒等于该值（惰性刷新的方向性缺口） | 7 天；上线后按实际平台调用频次调整 | |
| **2** | 是否引入**按群检索的专门数据结构**（风险 3 / 附录 B-1） | **不引入**，只加复合索引 `messages(group_id, created_at)`，随初始化自动补齐 | 当前规模下顺序扫描可接受，索引足以支撑"按群 + 时间收敛 + 排序"；引入专门结构会带来写放大与一致性负担 | 本期只加索引；把"是否需要专门结构"留给实测（以 `EXPLAIN` 出现非索引扫描为触发条件另立项） | |
| **3** | **存量消息来源标记缺失**的处置（风险 9） | **不回填**；默认排除规则只对带标记的记录生效；检索结果**不额外标注**缺失来源 | 存量群消息可能仍混入测试数据（检索可信度）；回填需判定依据且存在误判风险 | 按实现值；若业务方要求回填，另立脚本条目（`backfill_*` 家族） | |
