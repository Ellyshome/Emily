# 群信息保存与复用 — 概要设计（SD）

> **基于规格（PRD）**：[群信息保存与复用_PRD_V2.md](./群信息保存与复用_PRD_V2.md)（`群信息保存与复用_PRD_V2.md`，2026-09-23，含 §4.1 铁律 / §4.4 约束型技术决策 / 22 条 US）。**本设计基于 PRD V2**；据 PRD 附录 A，V2 修订了 AC-US-09.3 的下线测试范围、收窄 AC-US-22.2 并新增 AC-US-22.4（`history` 动作必然失败修复）
> **上游需求**：[群信息保存与复用_需求基线_V1.md](./群信息保存与复用_需求基线_V1.md)（2026-09-23）
> **宪法版本**：v1.2（[`_shared/constitution.md`](../../.claude/skills/_shared/constitution.md)）
> **设计版本**：v2.0（修订 V1.0：随 PRD V2 同步两处验收口径，并把 `history` 修复纳入 M8；见 §变更记录）
> **级别**：System Design（概要设计）
> **目标**：把"群台账 + 群成员名册 + 群消息"补齐为可查记录，并以**一份只读取数出口**同时服务对话侧能力与 emy-console 群追踪视图；数据承载项随初始化自动补齐，不碰内核、不引入定时机制。

## 硬约束（违反即失败）

> 项目铁律直接引用 [宪法 §2](../../.claude/skills/_shared/constitution.md)，**不自行发明**。

1. **禁止修改已有接口签名**：只能在已有类中新增方法，或修改已有方法的**实现语义**（须在本设计中显式标注"修改实现语义"）。确需改签名时逐处标注"修改接口签名"并给出调用方同步清单。本设计**未使用**任何"修改接口签名"许可。
2. **遵循宪法铁律 C0~C13**：本设计涉及的铁律及遵守方式：

   | 铁律 | 本设计如何遵守 |
   |------|--------------|
   | C0 根治而非迁就 | 平台拉取能力经 **SSE 请求-响应**（M2）落实到既有发布-订阅总线的事件类型扩展点，而非启用 NapCat HTTP 服务器绕开薄插件这个平台边界 |
   | C2 分层不可跳 | `api/routes → Service → Repository → DB` 严格单向；控制台路由与工具 handler 均只调 Service，不碰 Repo/DB（M5/M7 验收项） |
   | C3 SOP 即路由 | 群信息查询能力在 SOP-005 增补一节 + `### 3.2 使用的系统工具` 表声明 `query_groups`（M6） |
   | C6 Sync repo + to_thread | 新增 Repo 方法全 sync；Service 的 async 入口用 `asyncio.to_thread` 包裹读库（M4/M5） |
   | C9 ToolManager / ScriptManager 边界 | 面向对话的是进程内只读工具 `query_groups`（M6）；可重复维护动作走 `scripts_registry.yaml` 脚本（M3/M4）；两者共享 Service 层但不互相调用 |
   | C10 工具必须带参数 schema | `_QUERY_GROUPS_SCHEMA` → `registry.py` 传 `params=` → `tools_consistency.py::TOOL_SCHEMA_MAP`，三步齐备（M6） |
   | C11 功能注册接入（元原则） | 工具 → `tools/registry.py`；脚本 → `scripts_registry.yaml`；控制台模块项 → `MODULE_ITEMS` + `MODULE_PANEL_SELECTORS`；平台动作 → 插件 `SSEListener._handlers` + 内核出站事件类型；兜底可见性 → `fallback_policy.py` 白名单登记。无裸文件、无硬编码接线（M2~M7 逐条登记） |
   | C12 Session 主循环冻结（元原则） | 本模块**改动清单不含** `session/loop.py`、`session/session_agent.py`、`session/graph_wiring.py`、LangGraph 引擎文件；群台账不经会话上下文下发（M6 完全由只读能力达成） |
   | C13 控制台 = 观察窗口 | 群追踪视图三种读取与控制台侧作用域收敛均复用 M5 同一出口；路由层只做参数校验 → 调 Service → 包装统一响应；写能力走既有脚本通道（M7） |
   | Q5 无越界 | 不引入新依赖；除 `messages(group_id, created_at)` 索引外不新增数据结构 |
   | Q6 接线闭合 | 产出物逐项登记消费者（见"接线矩阵"）；新增配置项 / DB 列 / 公开方法配静态可达性验收命令 |

3. **每模块验收**：每个模块的验收检测必须通过，否则停止并报告。
4. **遵循接口契约**：所有跨模块调用必须通过约定的接口，不允许绕过接口直接操作对方内部数据。
5. **不私自扩需**：发现规格缺陷**回退 req-review**，不在本设计里新增/改写需求（回退与裁定记录见"§ 规格裁定记录"与"§ 设计口径裁定"）。
6. **接线闭合（宪法 §3 Q6）**：任何产出物必须有消费者（见"接线矩阵"）；无消费者不得进入编码。

## 数据流设计

### 核心流程

| 流程 | 触发条件 | 参与者 | 数据流向 | 异常路径 |
|------|---------|--------|---------|---------|
| 手动同步群清单 | 控制台脚本面板 / CLI 执行 `sync_groups.py` | 脚本 → M3 → M2 → SSE → 插件 → NapCat | `get_group_list` 结果 → `upsert_groups` 写 `conversations`（`title`、`member_count`）；**`note` 不参与写入** | 插件未连接 / 超时 / 平台不支持 → `ok=False` + 明确原因；台账不变；不阻断任何链路 |
| 惰性刷新名册 | 控制台打开群追踪 / 查看名册 / 执行刷新脚本 | M7（或脚本）→ M4 → M2 → SSE → 插件 | `is_stale` → 需刷新 → `get_group_member_list` → `group_members` upsert + `roster_synced_at` 更新 | 刷新失败 → 保留现有数据、如实提示、**不写 `roster_synced_at`**（不把失败当新鲜） |
| 群消息检索（对话侧） | LLM 调 `query_groups(action="messages")` | M6 → M5 → M1 | `resolve_visible_group_ids(tier="actor")` → `query_group_messages` → 命中列表（群/发言人/时间/片段/定位标识） | 群标识解析不出 → `not_found`；歧义 → 候选列表；空 → 如实回报；异常 → `success=False` + `reply`，对话主链路不受影响 |
| 群追踪视图取数 | 控制台打开 / 翻页 / 检索 / 看名册 | M7 → M5 / M4 | 同一出口，`tier="observer"`；名册区可能触发 M4 的惰性刷新 | 单区域失败 → 该区域提示，视图其余可用（AC-US-14.2） |
| 备注维护 | 控制台备注表单（经既有脚本通道）/ CLI | 前端 → `POST /api/v1/scripts/run/set_group_note` → 脚本 → M3 | `conversations.note` 覆盖写 + `business_event_logs` 留痕（旧值→新值） | 未二次确认 → 由 `writes_db` + `check_arg` 机制**降级为 `--dry-run` 预览**（AC-US-15.4） |
| 过期群巡检 | 控制台巡检区 / CLI `list_stale_rosters.py` | M7 / M4 | 读 `conversations.roster_synced_at` 与 TTL 比较 → 过期群清单 + 留痕 | 无过期群 → 空列表，不报错、不臆造 |

### 关键数据流（对话侧检索）

```
用户问"XX材料什么时候进场"
  → Session 主循环（不改动）经能力目录选中 query_groups
  → handler(params, user_id)                     [M6]
  → GroupQueryService.resolve_group_ref(group)   [M5] 备注名/群名/群号 → 唯一群
  → GroupQueryService.resolve_visible_group_ids(actor_user_id, tier="actor")  [M5]
       名册内 且 level>=2 → 允许集合；缺失/空/低等级 → 空集（fail-closed）
  → MessageRepository.query_group_messages(keyword, group_ids=允许集合, exclude_sources=("test","ops"))  [M1]
  → 命中 → {哪个群(备注名) / 谁说的 / 什么时候 / 原文片段 / 定位标识}  → reply
  → 未命中 → "该群/该时间范围内没有匹配记录"
```

## M2: 平台拉取通道（内核 ↔ 薄插件 request/response）

**依赖**：无（复用既有 `OutboundEventBus`；本模块不改该类）

**实现的需求**：US-02（手动拉取群清单）、US-03（拉取成员名册）、US-04（按需刷新）、US-18（入口形态）

**层级**：Service（`services/platform_action_service.py`）+ `api/routes`（`routes/platform.py`）+ 薄插件（`data/plugins/emily_agent/`）

**职责**：把"按需调用平台 OneBot 动作"的能力实现为一次可等待的请求-响应：内核把请求经既有 SSE 出站总线推给薄插件，插件执行 `bot.call_action` 并回调结果。**这是本模块唯一的平台访问路径**，不新增监听端口、不改部署拓扑、不引入新依赖。

### 接口契约

#### 对外接口（内核侧）

| `PlatformActionService.request` | 方法 | `async def request(self, action: str, params: dict, *, platform: str = "", timeout: float = 8.0) -> dict` | 发起一次平台动作并等待结果；返回 `{"ok","data","error","request_id"}` |

### 核心算法/策略

| 算法/策略 | 用途 | 选型理由 | 备选方案 |
|----------|------|---------|---------|
| **SSE 请求-响应**（`request_id` + `asyncio.Future` + `wait_for(timeout)`） | 让内核按需触发平台动作并同步取得结果 | ① 复用了既有发布-订阅总线，事件类型是其开放扩展点，内核侧 `outbound_bus.py` **零改动**；② 薄插件是平台边界的唯一持有者（AstrBot 持有 bot 连接），符合双容器解耦；③ 不新增监听端口、不改 `docker-compose` / NapCat 配置、不引入新依赖；④ 天然满足"无定时、无常驻"——请求是事件驱动的一次性动作 | ① **启用 NapCat OneBot HTTP 服务器供内核直调**：需改 `emily-data/napcat_config/onebot11_*.json` 的网络配置（新增 `httpServers`）并新增内核→napcat 的容器间调用面与 token 管理，等于绕开薄插件这个既定平台边界，破坏"内核不碰平台"的解耦（`emily-core` 当前对 NapCat 仅有 Docker API 读状态这一条只读旁路）；② **内核轮询插件**：插件无 HTTP 服务端，需新建；③ **周期性拉取**：违反约束 12 注（系统无定时机制）与 PRD §1.3-4 |
| **动作白名单放在插件侧** | 防止内核下发任意 OneBot 动作 | 平台边界自行守卫，fail-closed（未知动作直接拒绝）；内核只可能发出两个已知动作，白名单是纵深防御 | 仅在内核侧校验：平台边界无自守能力，任一内核侧缺陷即扩散为任意动作 |
| **无订阅者短路** | 插件离线时快速失败 | `subscriber_count() == 0` 时 `publish` 会静默丢事件，等待只会白等 `timeout` 秒；短路后立即返回 `{"ok": False, "error": "插件未连接"}`，符合"快速且如实回报" | 一律等满超时：控制台惰性刷新会白卡 8 秒，体验与 AC-US-04.2 的"数秒内完成"相悖 |
| **请求-合流（同一 action+params 在途时复用同一 future）** | 避免并发触发同一平台拉取（如控制台连点、巡检与刷新并发） | 拉名册是逐群调平台接口，QQ 侧有频率限制；合流避免重复调用，同时不改变幂等语义（US-20 是 DB 行数口径） | 不做合流：并发重复调用平台，可能触发频率限制 |

### DTO 定义

| DTO | 字段 | 用途 | 流向 |
|-----|------|------|------|
| `PlatformActionResult` | `ok: bool`, `data: Any`, `error: str`, `request_id: str` | 平台动作统一返回 | M2 → M3/M4 |
| `PlatformActionEvent` | `request_id: str`, `action: str`, `params: dict`, `platform: str` | SSE 事件负载 | M2（内核）→ 插件 |
| `PlatformResultCallback` | `request_id: str`, `ok: bool`, `data: Any`, `error: str` | 插件回调负载 | 插件 → M2（内核） |

### 数据模型

**无数据模型变更**（不新增表、不新增列、不新增索引；`platform_action` 是内存态事件类型，无持久化）。在途请求仅存在于 `PlatformActionService._pending` 的内存字典中，进程内有效。

### 核心算法/策略

| 算法/策略 | 用途 | 选型理由 | 备选方案 |
|----------|------|---------|---------|
| 全量覆盖式 upsert（按 `(im_platform, group_id, im_user_id)` 唯一键） | 幂等且能识别退群 | 唯一约束是幂等的物理保证；"本批未出现即标记退群"是唯一无需额外状态就能识别离群的方式 | 增量 append：无法识别退群，且重复拉取会重复插行（违反 AC-US-03.1 / US-20.2） |
| `is_active` 软标记（不删行） | 退群者保留 + 成员数只计在册 | 删行会让"名册"与"群消息里他说过的话"两处口径打架（AC-US-03.4）；软标记同时满足两处 | 直接删行（基线备选 A）：历史检索的主体消失 |
| 名册新鲜度挂 **`conversations.roster_synced_at`** | 过期判定的单一承载位 | ① 判定发生在"取某群是否要刷新"这一步，主语是**群**；② 名册为空的群也必须能被判定为过期（挂在名册表上时零行就无处可挂）；③ 与群列表/巡检同一次查询即可得出过期标识，避免两处时间源漂移 | 挂在名册表自身（如 `group_members.synced_at`）：空名册群无法表达"从未同步"；两者都挂：两个时间源必然漂移 |
| 作用域判定**不看 `is_active`** | 方向性缺口按 TTL 压窗而非提前收紧 | AC-US-08.5 明确要求"已退群者在名册新鲜度窗口内仍可检索"；按 `is_active` 过滤会让退群者立即不可查，与 AC 直接冲突 | 按 `is_active` 过滤：与 AC-US-08.5 冲突 |
| **`ensure_fresh` 只被人在场路径调用** | 保证机器人检索路径全链路只读 | AC-US-04.4 / 约束 §4.4-10；`query_groups` handler 不引用任何刷新入口 | 检索路径"顺手刷新"（基线 S5）：当场违反"调用前后行数不变" |

### 核心算法/策略

| 算法/策略 | 用途 | 选型理由 | 备选方案 |
|----------|------|---------|---------|
| **一个查询函数覆盖"列表 + 检索"**（`keyword` 为空即列表） | 满足"三种读取只有一处实现"且"两入口口径一致" | 列表与检索的唯一差别是 `keyword` 是否参与 `ilike`；合并后**结构上不可能出现两端口径不一致**（AC-US-12.4 / 17.3） | 两个函数：需要两处维护同款来源排除与分页，正是本次要避免的漂移形态 |
| 作用域用**档位参数**（`tier`）区分，而非两套过滤 | 单一实现 + 两端共用（§4.4-9 / AC-US-13.2） | `observer` 返回 `all_groups=True`，`actor` 返回收敛集合；实现只有一处，控制台无法"另立一套" | 控制台另写过滤：必然漏改一处 |
| `actor` 档 = 名册内 **且** `level >= 2`，且**不看 `is_active`** | 安全边界（D1 建议 B′） | 名册只说明"此人在群里"，不说明"有资格看全群历史"；L1 是未登记用户自动获得的档位；不看 `is_active` 以对齐 AC-US-08.5 的方向性缺口 | 纯名册内（含 L1）：把访客放进全群历史可见范围 |
| **fail-closed 三条件**：`actor_user_id` 为空 / 该群无名册行 / 名册为空 → 空集 | 绝不出现"缺数据即放宽"（§4.4-8 / AC-US-08.2） | 前置判空（而非"过滤后为零"）保证语义是"未授权"而非"碰巧无命中" | 名册缺失回退旧口径（基线备选）：等于缺数据即放宽 |
| 群标识解析优先级：群号（唯一键）> 备注精确 > 群名精确 > 备注包含 > 群名包含 | 让调用方不需提供内部标识（AC-US-07.4） | 群号是唯一键（`(im_platform, conversation_id)` 唯一约束）→ 命中即无歧义；文本匹配可能多个 → 返回候选请其再问 | 只做精确匹配：用户口语化表达命中率低 |
| 默认排除 `test`/`ops` 的来源过滤**下沉到 Repo 查询** | 两端同口径且不各补一份 | 若在 Service 内存过滤，"先取 limit 再过滤"会导致返回条数远小于 limit（既有 `_filter_by_scope` 的问题）；下沉到 SQL 让 `total` 与分页都准确 | 内存过滤：分页与总数都不准 |
| 游标语义**严格化**：`before_id` 锚点无效 → 明确回报（不静默退化为"取最新 N 条"） | 如实回报（R16） | 既有 `list_recent_by_group` 锚点查不到时静默退化，会让"加载更多"看起来成功却重复返回首页数据；新函数采用严格语义 | 沿用静默退化：用户侧表现为"翻页无进展"的静默错误 |

## M6: 对话侧能力 `query_groups`

**依赖**：M5

**实现的需求**：US-06（列出在追踪群 + 自我说明）、US-07（原文检索）、US-09（注册通道 + SOP 声明 + 可下线）、US-10（只读/幂等/失败不阻断/如实回报）

**层级**：`tools/`（业务工具）+ 注册通道（`tools/registry.py`）+ 一致性登记（`infrastructure/tools_consistency.py`）+ 兜底可见性登记（`workitem/langgraph_engine/agent/fallback_policy.py`，仅登记）+ SOP 声明（`emily-data/sops/`）

**职责**：把 M5 的取数出口暴露为面向对话的**只读**能力；不新增任何写路径、不触碰会话上下文装配。

### 接口契约

#### 对外接口

| 接口/类 | 类型 | 签名 | 说明 |
|---------|------|------|------|
| `_QUERY_GROUPS_SCHEMA` | 常量 | `dict`（JSON Schema） | 定义在 `tools/group_tool.py`（注册三步第一步） |
| `_QUERY_GROUPS_DESCRIPTION` | 常量 | `str` | 自我说明四要素（AC-US-06.2） |
| `handle_query_groups` | 方法 | `async def handle_query_groups(params: dict, user_id: str = "", **kw) -> dict` | 返回 `{"success","reply","data"}`；失败/拒绝加 `error_code` |

#### Schema（逐字段）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `action` | string | `enum: ["list","messages"]`，必填 | `list` = 列出在追踪群；`messages` = 检索群消息原文 |
| `keyword` | string | `action=messages` 时必填 | 检索关键词（子串匹配，不做语义扩召回） |
| `group` | string | 可空 | 群以"备注名 / 平台群名 / 群号"任一表达；留空 = 跨全部在追踪群 |
| `time_range` | string | `enum: ["today","week","month","all"]`，默认 `all` | 时间范围 |
| `limit` | integer | 默认 20，上限 50 | 返回条数上限 |
| `include_sources` | boolean | 默认 `false` | 是否包含测试 / 运维来源（默认排除） |

#### 工具描述（自我说明四要素，AC-US-06.2）

必须让调用方在不读任何外部上下文的前提下知道：
1. 系统正在**留存群消息**（含未 @ 机器人的群内消息）；
2. 本能力可**列出系统在追踪哪些群**（含人工功能备注、成员数、已留存消息数、最近活跃）；
3. 本能力可按关键词**检索群内消息原文**（可限定群与时间范围，默认排除测试与运维来源）；
4. 典型用途：**"某材料的进场时间""验收时间""谁到场"这类信息常由某人在群里报备，可到群里找原文**。
并在描述中声明**权限口径**：仅返回发起者所在的、且在群成员名册内的群的消息（等级 ≥ 参建执行）。

#### 注册三步 + 放行登记 + SOP 声明

| 步骤 | 落地位置 | 内容 |
|------|---------|------|
| ① 源文件常量 | `tools/group_tool.py` | `_QUERY_GROUPS_SCHEMA` / `_QUERY_GROUPS_DESCRIPTION` |
| ② 注册传参 | `tools/registry.py`（`_register_*` 内） | `_reg_biz(reg, "query_groups", _QUERY_GROUPS_DESCRIPTION, _h("group_tool","handle_query_groups"), params=_QUERY_GROUPS_SCHEMA, category="base", permission_flag="all", write_mode="read")` |
| ③ 一致性登记 | `infrastructure/tools_consistency.py` | `REGISTERED_TOOLS` + `TOOL_META_MAP`：`"query_groups": ("群信息查询","base","all","meta")` + `TOOL_SCHEMA_MAP`：`("emily_core.tools.group_tool","_QUERY_GROUPS_SCHEMA")`（只读，不入 `TOOL_WRITE_MODE_MAP`） |
| ④ **兜底可见性登记** | `workitem/langgraph_engine/agent/fallback_policy.py` | `_BASIC_TOOLS` ∪= `{"query_groups"}`、`_ADVANCED_READ_TOOLS` ∪= `{"query_groups"}` |
| ⑤ SOP 声明 | `emily-data/sops/SOP-005-QRY-data_query.md` | 增补一节（能力位置 / 发现方式 / 适用场景 / 权限口径）+ `### 3.2 使用的系统工具` 表追加 `query_groups` 行 |

> **第 ④ 步是本能力"对话侧实际可达"的真正开关**（实测结论）：`exposure_mode` 在全仓**没有任何运行时消费者**（只有写入、种子、回读，无任何 `==`/`!=` 比较）；运行时决定一个工具能否被调用的是 `session/loop.py` 的 `_execute_business_tool` 门禁与 `tool_adapter.build_tool_specs` 的档位裁剪，两者都只读 `FallbackPolicy.resolve(tier, with_write=True)`——即 `fallback_policy.py` 的 `_BASIC_TOOLS`（basic 档）/ `_ADVANCED_READ_TOOLS`（advanced 档）两个 frozenset。
>
> 该文件自述其定位为**唯一事实源**："高级兜底只读集：……（单一事实源）"、"运行期动态登记的只读工具……仍以此模块为唯一事实源，**不在其他文件另立名单**"。因此新增只读能力的可见性**只能在此登记**（本步骤即按其既定契约登记，不修改任何机制、不改判定逻辑）。
>
> `_BASIC_TOOLS` 与 `_ADVANCED_READ_TOOLS` **两处都要登记**：`FallbackPolicy.gate()` 按 `level >= 4 或 is_management_unit` 划档，`basic` 档对应 `level < 4` 与 actor 缺失场景，`advanced` 对应 `level >= 4`；只登记一处会导致某一档用户调用被拒（回复"该操作在当前档位不可用"）。L1 访客（basic 档）也须能调用本工具——但**能调用不等于能看到内容**：`action=messages` 对 L1 一律返回空（AC-US-08.4），安全由作用域收敛承担，可见性由白名单承担，两者职责分离。

#### 注册项清单（本能力的"全部注册项"——即下线测试的移除范围）

> PRD V2 的 **AC-US-09.3** 要求"移除该 SOP 声明**与**该能力的**全部注册项**后 → 能力不可用且无残留触发器"。上表 ①~⑤ 即该清单，逐项列明便于验收与静态复核：

| # | 注册项 | 位置 | 移除后的效果 |
|---|--------|------|-------------|
| 1 | 源文件 schema / 描述常量 | `tools/group_tool.py` | 常量消失，注册与校验无据可依 |
| 2 | 工具注册调用 | `tools/registry.py` | 工具不再进入 `BusinessFlowToolRegistry` → 能力目录不再出现 |
| 3 | `REGISTERED_TOOLS` 条目 | `infrastructure/tools_consistency.py` | 一致性校验不再要求该工具（缺此条会报"僵尸条目"反向错误） |
| 4 | `TOOL_META_MAP` 条目 | 同上 | `_ensure_tool_registry_seed()` 不再向 `tool_registry` 表 upsert → `get_available` 查不到 → `session_api_ids` 无它（fail-closed） |
| 5 | `TOOL_SCHEMA_MAP` 条目 | 同上 | V14 反向校验不再要求该映射 |
| 6 | 兜底白名单登记（2 处） | `workitem/langgraph_engine/agent/fallback_policy.py` 的 `_BASIC_TOOLS` / `_ADVANCED_READ_TOOLS` | 即便工具残留，调用也会被档位门禁拒绝 |

### 核心算法/策略

| 算法/策略 | 用途 | 选型理由 | 备选方案 |
|----------|------|---------|---------|
| 单一工具、两个动作（`list` / `messages`） | 收敛工具体面，降低 LLM 选择成本 | 与 PRD FR-QRY-1 一致；两个动作共用同一出口，参数重叠（`group`/`limit`） | 两个工具：能力目录冗余，且作用域口径要维护两处 |
| 群标识由服务端解析，**LLM 不给内部 ID** | 调用方不需知道 UUID（AC-US-07.4） | LLM 无从得知 `conversations.id`（UUID）与业务群号的区别；服务端用群号/备注/群名解析是唯一可靠路径 | 要求 LLM 传 `conversation_id`：实际不可用 |
| 失败一律带 `reply` | 框架 `result_digest` 只读 `reply` | 框架消费点（`session/loop.py`、`workitem/.../loop.py`）取 `payload["reply"]` 作摘要；不带 `reply` 的失败对用户是空回复 | 用 `error` 键（`chat_archive` 风格）：框架不读，用户看不到原因 |
| `success=False` + `reply` 而非抛异常 | 不阻断对话主链路（AC-US-10.2） | handler 抛异常虽被框架兜住，但会记 failed 并可能打断本轮其他动作；主动返回失败态语义更准确 | 抛异常：把所有失败都记成"工具执行异常"，丢失原因粒度 |

## M7: 控制台「群追踪」视图

**依赖**：M3（备注脚本通道）、M4（名册与惰性刷新）、M5（三种读取与作用域）、既有脚本执行通道（`scripts_runner.py`）

**实现的需求**：US-11（模块项 + 上下两栏 + 筛选排序）、US-12（跨群检索 + 两入口同源 + 跳群）、US-13（接入式复用 + 写能力唯一）、US-14（分页回溯 + 不白屏 + 拉取式）、US-15（名册查看 + 备注维护 + 过期识别与手动刷新）、US-16（敏感标注 + 不加鉴权）、US-04.2/04.5（端到端闭合）

### 附件打开的实现口径（复用既有通道，不新建附件服务）

| 情形 | 处理 |
|------|------|
| `message_attachments.file_id` 非空（已锚定文件台账） | 经既有 `FileManager.get_by_file_no()` / `resolve_local_path()` 定位并返回字节流 —— 复用既有文件能力，不新建服务 |

### 核心算法/策略

| 算法/策略 | 用途 | 选型理由 | 备选方案 |
|----------|------|---------|---------|
| 群追踪路由**独立成文件** `console_groups.py` | 让"路由层无业务查询"可被独立静态扫描 | `console_resources.py` 已 3104 行 / 61 路由；独立文件使 M7 的验收项（grep 无 ORM/SQL）能精确到本模块，且与 `node.py` 的领域路由先例一致 | 追加进 `console_resources.py`：静态检查要跨整个巨型文件，且本模块的接线面被淹没 |

**实现的需求**：US-22（参数漂移修正 + `history` 动作修复）、US-21.3（文档同步）

**层级**：`tools/` 注册与参数定义 + `docs/`

**职责**：① 消除 `chat_archive` 的两份参数定义（**只补参数可见性，不改既有可用路径的检索行为**）；② **修复 `history` 动作的必然失败**——该动作因缺必填实参而从来不可用，而 US-22 使其变为可见的"是否包含前导消息"参数只在该动作生效，不修则该参数的可见性没有可工作的消费方（PRD V2 AC-US-22.4）；③ 把本模块的数据承载项与脚本同步进文档。

### 接口契约

| 接口/类 | 类型 | 签名 | 说明 |
|---------|------|------|------|
| `chat_archive_tool._CHAT_ARCHIVE_SCHEMA` | 常量 | `dict` | **唯一一份定义**（= 原内联完整版：`action` / `keyword` / `conversation_id` / `user_name` / `user_id` / `time_range` / `limit` / `include_progress`，`required=["action"]`） |
| `chat_archive_tool._CHAT_ARCHIVE_DESCRIPTION` | 常量 | `str` | 唯一一份描述（= 原 `ToolDefinition.description` 原文） |

> **`search` / `user` 两个分支的调用语句不改**：AC-US-22.2 的"结果集合不变"由此得到结构性保证（`history` 分支的修复是 V2 显式纳入的例外，见 AC-US-22.4）。

### 核心算法/策略

| 算法/策略 | 用途 | 选型理由 | 备选方案 |
|----------|------|---------|---------|
| 以 `chat_archive_tool.py` 的**完整版**为准，抽成模块级常量 | 消除两份定义 | 完整版在 `ToolDefinition` 中已描述工具的**真实能力**（含 `time_range` / `include_progress` / `user_id`）；注册用的简版才是错的那一份（AC-US-22.1） | 以简版为准：等于放弃这三个参数，与"完整能力一致"相悖 |
| `project/__init__.py` **再导出**而非删除符号 | 保证既有导入路径不失败 | 该子包的职责本就是"聚合面 + 再导出"（其 docstring 与既有 11 个符号同款做法）；直接删除会让 `registry.py` 的导入报错 | 直接删除符号并要求 `registry.py` 改导入：多余改面 |
| **修 `history` 分支的缺失实参** | 让参数可见性有可工作的消费方 | US-22 让 `include_progress` 变为可见，而它的唯一消费方就是这条永远失败的分支；不修则交付的是"更完整但必然失败的参数面"（正是 US-22 想根治的"定义了却没用上"，宪法 Q6）。且 `actor_user_id` 在 handler 内已取得，属恢复既有意图而非重新设计行为 | 不修：AC-US-22.3 的"可见并使用"在该参数上无法成立；或删除该参数与动作：等于缩减既有能力面，且需改工具描述与 enum，改动面更大 |
| **不修 `user` 分支的取数写法** | 守住"不顺手重构无关代码"（Q5） | 该写法依赖空关键词通配语义，结果仍按 `sender_user_id` 正确收敛，不构成功能失效；修复收益仅涉及正文为空的记录 | 顺手改掉：属越界重构，且会引入 AC-US-22.2 之外的额外行为变化面 |
| 结构上防再次漂移 | 避免同类缺陷复发 | 唯一定义 + `TOOL_SCHEMA_MAP` 指向定义模块 + `check_tools_consistency` 的 V5/V14 覆盖 → 再出现"两份定义"会被一致性检查或代码检索直接暴露 | 只改内容不收敛结构：下次仍可能漂移 |

## 已归档：规格项 1 的原始分析（AC-US-09.3 与 R18 的口径差）

> 以下为计划 V1 阶段提交的回退材料原文（含实测证据），保留以支撑 PRD V2 的变更依据；结论已并入上表。

### 规格项 1：AC-US-09.3 的验收表述与 R18 的口径不一致

| 项 | 内容 |
|---|------|
| AC-US-09.3 原文（PRD V1） | "`counterpart`：移除该 SOP 声明后重启 → 群信息查询能力不可用且无残留触发器（证明经注册通道接入）" |
| PRD R18 原文 | "**可下线**：移除 SOP 声明**与能力注册**即回落为'照常留存但无查询入口'，无残留触发器" |
| 实测事实（证据） | ① `exposure_mode` 在全仓**无任何运行时消费者**（只有写入 / 种子 / 回读，无 `==`/`!=` 比较）；② 工具可达性的实际判定在 `session/loop.py::_execute_business_tool`（业务工具）与 `tool_adapter.build_tool_specs`（档位裁剪），两者只读 `FallbackPolicy.resolve(tier, with_write=True)` 的硬编码 frozenset；③ `permission_flag="all"` 的工具由 `ToolRegistryRepo.get_available` **无条件放行**（`category=="base"` 分支）；④ SOP 的 `### 3.2` 工具声明是**并集**（`fetch_available_tools._merge_sop_declared_tools`），其判定键是 **`sop_allow`（准入清单）**，与本轮是否**匹配到**该 SOP 无关，也不会缩小集合 |
| 结论 | 在当前机制下，`permission_flag="all"` 的工具**无法**做到"仅移除 SOP 声明即不可用"：即使不登记进兜底白名单，只要消息路由到了**任意**一个已准入的 SOP（SOP 能力经 `_run_capability` 分支执行、不走业务工具的白名单门禁），该工具仍在 `session_api_ids` 中且无门禁拦截。因此 AC-US-09.3 的字面验收**不改变可达机制即不可达**；而 R18 的"移除 SOP 声明**与能力注册**"是可达且可验证的 |
| 建议 | ① 以 **R18 为准**修正 AC-US-09.3 的表述为"移除 SOP 声明**与工具注册（含一致性登记与兜底白名单登记）**后重启 → 能力不可用"；② 不采用"只声明、不登记兜底白名单"的替代设计（见下方否决理由）；③ 另将"`exposure_mode` 无运行时消费者"登记为独立待办（该字段目前是写入即回读却不参与判定的字段，属 Q6 的潜在死字段，但修复它会影响全部 60+ 工具的放行口径，须独立立项） |
| 否决"仅靠 SOP 声明、不登记兜底白名单"的理由 | 该设计让本能力的可达性**依赖 LLM 的 SOP 语义路由**：只有消息被路由到声明它的 SOP（或任意其他已准入 SOP）时才可调用。而 US-06/US-07 是本模块的 P0 主体（G4/G5"群可发现 / 群可检索"），把它押在一个概率性的意图匹配结果上，等于让 P0 能力在最需要它的口语化提问（"某某材料啥时候进场"）上随机失效；且该失效难以在验收中稳定复现。相比之下，"登记兜底白名单 + 以 R18 口径验收下线"是可确定验证的组合 |
| 本设计取值 | 按 ① 设计与验收（M6 验收 9/10），并把 `exposure_mode` 无运行时消费者的事实作为**既有观察**登记（不在本模块修复） |

### 规格项 2：`chat_archive` 的既有实现缺陷（**裁定：① 纳入 US-22；② 不修**）

> 以下两处均已按源码逐行复核（`tools/chat_archive_tool.py:26-124`），并据此修正了初稿中的一处不准确描述。

| 缺陷 | 位置与原文 | 现象 | 约束冲突 | 建议 |
|------|-----------|------|---------|------|
| **① `action="history"` 分支必然失败（硬缺陷）** | `tools/chat_archive_tool.py:70-74` 调用 `chat_archive_service.get_conversation_history(conversation_id=…, limit=…, include_progress=…)`，而该方法签名为 `get_conversation_history(self, actor_user_id: str, conversation_id: str, …)`——`actor_user_id` 无默认值且被省略 | 该分支必然抛 `TypeError: missing 1 required positional argument`，history 动作**从来不可用**（框架兜住后返回"工具执行异常"） | AC-US-22.2"修正**只补参数可见性，不改检索行为**：既有调用方式的结果集合不变"。修此缺陷会把结果从"必然失败"变为"返回历史"，字面上属行为变更 | **建议纳入 US-22 一并修**（见下方理由） |
| **② `action="user"` 只给 `user_id` 时传空关键词（瑕疵，非功能失效）** | `tools/chat_archive_tool.py:99-104` 传 `keyword=user_name if user_name else ""`，`search_messages` → `search_messages_fulltext` 先 `content.ilike('%%')`，**随后仍按 `sender_user_id == user_id` 过滤** | 结果语义仍为"该用户的消息"（**并非命中全表**）；实际影响仅两处轻微瑕疵：依赖 `LIKE '%%'` 的迂回写法，且 `LIKE` 不匹配 `NULL` → `content` 为 NULL 的记录（如纯附件类消息）会被漏掉 | 同上 | **建议不修**（见下方理由）；如需处理，登记为独立低优先项 |

**本设计处理（已按 PRD V2 落实）**：M8 做参数可见性收敛（AC-US-22.1/22.3）**并修复 ①**（AC-US-22.4）；② 不修，登记为低优先项（PRD §6 风险 13）。

**裁定依据**：

- **① 纳入 US-22 一并修复**，理由是 US-22 自身的闭合要求把它拉了进来：US-22 让 `include_progress` 变为**可见**（AC-US-22.3 还要求"补充后的参数被实际调用方**可见并使用**"），而 `include_progress` 的**唯一消费方就是 history 分支**——即这条永远失败的分支。若不同时修复，US-22 交付的是"一个更完整、更会诱导 LLM 选择、但必然失败的参数面"：参数可见性修好了，其消费者却是死的，这正是 US-22 想根治的"定义了却没用上"的另一种形态（宪法 Q6 接线闭合）。修复内容仅为**补传一个已被签名要求的实参**（`actor_user_id` 在 handler 内已就绪，:29 已取到），是恢复既有意图，不是重新设计行为。
- **② 不修**：它不构成功能失效（结果仍按 `sender_user_id` 正确收敛），修它属于"顺手重构无关代码"（宪法 Q5 红线），收益近乎为零（仅影响 `content` 为 NULL 的记录）。已登记为低优先项。
- 比对范围相应写明：AC-US-22.2 只比对 `action="search"` 与 `user` 动作的命中集合；`history` 动作作为**修复项**单独验收（修复前必失败 → 修复后返回历史），见 M8 验收 4 / 5。

## 设计口径裁定

> 以下 4 项是**为实现而必须作出的解释性裁定**（非新增需求）。每项给出 PRD 依据，供 req-review 复核；若复核不通过，属"偏差 2-4 个接口或模块职责调整"，按阶段反思规则追加新版修订记录（不回溯修改既有版本）。

### 裁定 A：群列表不按身份收敛，群消息按身份收敛

| 项 | 内容 |
|---|------|
| 裁定 | `list_tracked_groups`（在追踪群列表）对**全体使用者可见全部在追踪群**；`list_group_messages` / `search_group_messages` 收敛到发起者的允许群集合 |
| 依据 | AC-US-06.1"提供**一个**只读能力，可列出**在追踪群**；每条含备注名…"；G4"群可发现｜**能列出全部在追踪群**"；而 US-08 的场景是"一份**群消息检索请求**由不同身份的人发起"，AC-US-08.1 限定"**检索结果**先收敛到发起者的允许群集合" |
| 理由 | 若列表也收敛，用户就无从得知"可以就哪些群提问"，G4 与 AC-US-06 的能力发现价值丧失；而 US-08 的安全边界明确针对消息检索 |
| 影响 | 群名与备注对全员可见（不含群内消息）。这是 PRD R11 / §六 风险 11 已登记的"可见范围放宽"的一部分 |

### 裁定 B：控制台的写动作分工

| 项 | 内容 |
|---|------|
| 裁定 | ① **备注维护**（人工录入的台账主数据）：经**既有脚本通道**（`POST /api/v1/scripts/run/set_group_note`），控制台侧零新增路由；② **名册刷新**（数据保鲜，非人工录入）：控制台路由调用 M4 的**同一 Service 方法**（与 `refresh_group_roster.py` 同源），不新增写能力 |
| 依据 | AC-US-13.5"控制台的群相关**写能力唯一**：群备注维护，且经既有脚本通道接入（不在路由层直接写库）"；AC-US-04.2"在**人在场**的路径（**控制台打开群追踪、查看某群名册**、执行维护脚本）遇到过期群时，**先刷新该群再呈现**"；AC-US-15.5"名册过期的群在视图中**可被实际识别**，并可由运维**手动触发刷新**" |
| 理由 | 备注是人工录入动作（低频、需二次确认）→ 走注册脚本通道最合规；名册刷新由"人在场"自动触发、无人工录入，把每次打开视图都变成一次 subprocess 调用不现实；两者共用同一 Service（与三种读取共用同一出口同构），单一实现纪律未被破坏 |
| 张力说明 | AC-US-13.5 的字面"写能力唯一"与 AC-US-04.2/15.5 的控制台触发刷新存在措辞张力；本设计按"人工录入写能力唯一 = 备注维护；数据保鲜写动作 = 复用 M4 既有能力"落地 |

### 裁定 C：名册新鲜度的承载位挂在群台账

| 项 | 内容 |
|---|------|
| 裁定 | `conversations.roster_synced_at`（群台账）为唯一承载位；过期结论由 `GroupRosterService.is_stale` 单一计算 |
| 依据 | AC-US-04.1"每个**群**记录'名册最后同步时间'"；附录 B-3 将此列为 plan 阶段须定的方案型问题 |
| 理由 | ① 判定主语是"群"；② 名册为空的群（从未拉取成功）也必须能被判定过期——挂在名册表上时零行就无处可挂；③ 群列表与过期巡检只需一次查询即可得出过期标识，避免两个时间源漂移 |
| 备选 | 挂在 `group_members`（或两处都挂）——前者无法表达"从未同步"，后者必然漂移 |

### 裁定 D：附件打开走"控制台侧同源只读路由"

| 项 | 内容 |
|---|------|
| 裁定 | 群追踪面板内附件按 M7 的三种情形处理（锚定文件台账 → 复用 `FileManager`；仅有 local_path → 存储根下解析并做目录穿越防护；两者皆无 → 仅元信息） |
| 依据 | AC-US-11.6"消息附件显示元信息并可打开（**复用既有附件查看通道，不新建附件服务**）"；PRD §4.3 假设 5"既有附件查看通道可被控制台复用"（若不成立，US-11.6 需另建路径，超出本版范围） |
| 理由 | 既有 `GET /api/v1/files/{file_no}/download` 受 `X-Emily-Token` 约束（其 docstring 明确"勿挪入 `/console` 白名单前缀"），浏览器不可直达；控制台侧只能经一条**只做定位与交付、不做业务判断**的路由复用既有文件能力 |

### 裁定 E：名册未就绪时对使用者的回报形态

| 项 | 内容 |
|---|------|

| 理由 | ① AC-US-08.3 要求"不在名册内的高等级身份检索该群消息 → 返回空，且**回复中不泄露该群消息内容**"；明示"名册未就绪"会让使用者据此推断该群在系统内的留存状态，方向上与"不泄露"同源，属不必要的信息暴露。② 对话侧能力（US-09）的定位于"照常留存但无查询入口"，**运维巡检不是对话侧职责**——PRD §九.1 场景 19 已明确"过期巡检只做在控制台与日志，不给 LLM 暴露运维巡检能力（保持工具体面收敛）"。③ AC-US-07.7 已规定空结果如实回报的形态，与统一口径一致 |
| 影响 | 使用者（含运维）在对话侧无法区分"该群真没消息"与"名册未就绪"；定位手段是控制台的过期标识与 `list_stale_rosters.py`（M7 / M4） |
| 待确认 | 若 req-review 判定需向使用者明示名册状态，则 M5 的失败态需增加一种可区分的结果类型，M6 的 reply 文案与 M7 的呈现同步调整（属"偏差 2-4 个接口调整"，按阶段反思规则出新版修订记录）；**该待决项同时应从 PRD §6 风险 4 中关闭** |
