# 群信息保存与复用（模块）— 需求基线 V1

**一句话**：把 QQ 侧的群信息保存补齐成闭环——群台账带人工功能备注、群成员名册入库、群内消息（含未 @ 的）持续落库，让"哪些群在保存什么"第一次成为可查的记录。
**一句话**：把已保存的群信息以只读查询工具交给 LLM——它自己就能列出"有哪些群在保存信息"（带备注），并按关键词检索群消息原文，回答"某材料什么时候进场"这类散落在群里的问题。
**一句话**：在 emy-console 单开一项「群追踪」视图——右侧上半栏列当前正在追踪的群，下半栏看选定群的通讯内容，并提供跨群文字检索；该视图的全部取数逻辑落在 Emily 的能力层，控制台接线复用、不复刻。

> **性质**：需求基线（讨论稿），确认后转 PRD 与计划
> **日期**：2026-09-23
> **状态**：待评审（已定口径见 §十一；待定项见 §十二）
> **代码校对**：2026-09-23（§八、§十三 锚点均经实测核对）
> **通道范围**：**仅 QQ（NapCat）**。企业微信侧群消息不纳入本基线（见 §二 边界）

## 一、背景与问题

1. **群消息其实一直在存，只是存了没人能用**：NapCat 群消息经 OneBot11 反向 WebSocket 进入 Core，默认 `monitor` 模式下群内未 @ 机器人的消息也会落库（先落库、后判是否回复），`messages.group_id` 逐条冗余群号。但群上下文回溯与群级记忆注入被一个恒为 False 的开关挡住，每轮计算结果被直接丢弃——**存下来是事实，读到不是**。
2. **群只是"一个会话"，没有台账语义**：`conversations` 表里的群行只有平台下发的群名（`title`），没有任何字段承载"这个群是干什么的"。而 `title` 每次群清单同步都会被平台群名覆盖，所以人工写的备注放进去必然丢失。
3. **群成员完全没有建模**：全库无群成员表；插件只调 `get_group_list`，从不调 `get_group_member_list`；`member_count` 在插件侧采集并上送，服务端 upsert 时直接丢弃。今天"某人参与了哪个群"的唯一判据是"该人是否在群里发过言"——只潜水的人识别不出来。
4. **查询侧只有一个通路，且口径很窄**：`chat_archive` 是唯一能查消息正文的工具，走 `content ILIKE %关键词%` 子串匹配；作用域只放行"本人发过言的会话"，群聊还额外以"本人首条消息时间"为下界裁掉更早历史。没在群里说过话的人查什么都空。
5. **LLM 不知道有哪些群**：没有任何工具或上下文告知"系统正在保存哪些群的信息"，模型既不知道群的存在，也不知道可以去群里找答案。唯一一处群清单展示是启动邮件里给管理员看的一行统计。
6. **结论**：本期把"群台账 + 群成员名册 + 群消息"三样信息补齐成可查记录，并把"有哪些群、群里说过什么"以只读工具交给 LLM。**不做群报备的事件抽取、不做 session 级注入、不做向量检索**——这三件是各自独立的后续命题。

## 二、定位与边界

两条能力线：

```
写侧：群清单同步 ──────┐
      群备注（人工）    ├→ conversations / group_members / messages（保存记录）
      群成员名册（QQ）  │
      群消息落库（既有）┘
                                    ↓
读侧：query_groups（只读工具，带参数 schema） → LLM 对话
```

- **本期只做"信息记录"，不做语义加工**：不把群消息抽成事件/任务/成果，不做摘要沉淀，不做向量入库。
- **"让 LLM 知道有哪些群"由工具达成，不碰会话上下文**：群台账通过工具的 `list` 动作与工具描述暴露；**不新增 session prompt 注入、不改会话上下文装配**。理由是会话主循环与其上下文装配属内核冻结范围（CLAUDE.md 约束 13），业务功能增长一律落能力层；且系统当前不存在周期性自动触发机制（约束 12 注）。
- **不新造可见性规则**：查询作用域收敛到单一出口，具体口径见 §十一 D1 与 §十二-1（推荐 B′，待确认）。
- **不做企业微信**：企微当前通道（自建应用 Webhook / 微信客服）在平台侧就不推群消息；企微群消息需"智能机器人"或"会话内容存档"另立项。
- **不做群消息的语义检索**：不进 `knowledge_chunks`——该链路的 `doc_id` 必须锚定 `files.id`，且可见性只认 `files` 表上的关系计算，属安全敏感改造。
- **控制台是观察窗口，不是第二套系统**：群追踪视图定位为"观察 Emily 正在保存什么"的窗口，**取数逻辑一律落在 Emily 能力层**（service 层，与 `query_groups` 工具同源），控制台路由只做接线与呈现；**禁止在控制台路由层复刻检索/列表逻辑，禁止裸 SQL 直查表**（CLAUDE.md 约束 14）。控制台侧只读，唯一写能力是群备注维护（复用 FR-GRP-2 的维护脚本）。

### 2.1 与既有 `chat_archive` 工具的分工

| 工具 | 面向 | 数据范围 | 本期处置 |
|------|------|---------|---------|
| `chat_archive`（既有） | 会话历史、私聊记录 | 全部会话，作用域=本人发过言 | **保留**，不删不合并 |
| `query_groups`（本期新增） | 群台账 + 群消息 | 群台账（含备注）、群成员、群消息 | 新增 |

> 两者都读 `messages`，但入口语义不同：前者是"翻我和谁的对话"，后者是"看某个群在说什么"。**本期不重构 `chat_archive` 的作用域**，仅修其注册 schema 漂移（见 FR-COM-5）。

## 三、目标

1. **G1 群可命名**：每个已知群可承载一条人工功能备注（如"景观施工工程群"），与平台群名分离、不被同步覆盖。
2. **G2 群可成册**：QQ 侧 bot 加入的全部群与其成员名册可入库，含成员 IM 身份、显示名（可选角色/入群时间）、与系统用户的绑定关系。
3. **G3 消息可留存**：群内消息（含未 @）持续落库、可按群回溯，且能区分真实用户消息与测试／运维消息。
4. **G4 群可发现**：LLM 通过一个只读工具能列出"系统正在保存信息的群"（备注名 / 平台群名 / 平台 / 成员数 / 已存消息数 / 最近活跃）。
5. **G5 群可检索**：LLM 能按关键词（可限定群、时间范围）检索群消息原文，结果带"哪个群 / 谁说的 / 什么时候"。
6. **G6 不阻断**：群清单同步、名册刷新、消息落库任一失败都不影响消息主链路与对话。
7. **G7 群可观察**：emy-console 单开一项「群追踪」，上半栏列出正在追踪的群（含备注、成员数、消息数、最近活跃），下半栏查看选定群的通讯内容，并支持跨群文字检索；**全部取数复用 Emily 能力层**，控制台不自造逻辑。

## 四、范围

**纳入**
- `conversations` 增人工备注列；群成员名册（新表）；成员数落地；群清单同步的幂等与手动再同步入口；
- QQ `get_group_member_list` 采集链路、与 `user_im_bindings` 的绑定解析；
- 群消息落库闭环的核对与来源标记（沿用既有 `source` 机制）；
- 新增只读工具 `query_groups`（`list` / `messages` 两个动作）+ 参数 schema + 注册三步 + SOP 声明；
- 群备注维护脚本（带 `params` schema，供控制台调用）；
- **emy-console 新增「群追踪」模块项**：群列表 + 选定群通讯内容 + 跨群文字检索（只读取数复用能力层）；
- 既有 `chat_archive` 注册 schema 漂移修正（低风险附带项）。

**不纳入**
- 群报备/群消息的事件、任务、成果抽取与沉淀；
- session 创建期把"用户参与的群"注入提示词（内核冻结，后续独立立项）；
- 群级记忆（`group_memories`）与群上下文回溯（`group_context_service`）的注入开关启用；
- 群消息入向量库、进 `knowledge_chunks`、进世界书；
- 企业微信 / 微信群 / 微信小程序的群消息；
- 群消息自动摘要、群画像、活跃度分析；
- 全局权限矩阵改造（若 §十一 D1 选 B，则只做"群消息检索作用域"这一处收敛，不动全局权限体系）；
- **控制台的群消息编辑 / 删除 / 导出**，以及群消息的实时推送（WebSocket / SSE 实时流）——本期为拉取式只读视图；
- **控制台新增群相关写能力**（除群备注维护外），亦不在控制台路由层新写取数逻辑。

## 五、术语

1. **群台账**：`conversations` 中 `conversation_type='group'` 的行，一个群一行；`conversation_id` = 群号（QQ 群号）。
2. **群备注**：人工填写的"这个群是干什么的"功能说明，独立于平台群名。
3. **群名册**：某群的成员清单，以 IM 身份（QQ 号）为主键落地。
4. **群消息**：`messages` 表中 `group_id` 非空的行，含未 @ 机器人的静默收集消息。
5. **静默收集**：`monitor` 模式下群内未 @ 机器人的消息被落库但不触发回复的既有机制。
6. **检索作用域**：一次群消息检索中，发起者被允许看到的群集合。
7. **注册三步**：新工具接入的固定流程——源文件定义 `_XXX_SCHEMA` → `registry.py` 注册时传 `params=` → `tools_consistency.py` 的 `TOOL_SCHEMA_MAP` 与 `TOOL_META_MAP` 登记（CLAUDE.md 约束 11）。
8. **群追踪视图**：emy-console 中新增的一个模块项，由"上半栏群列表 + 下半栏通讯内容 + 跨群检索"三块组成，只读。
9. **接入式复用**：控制台的读写能力必须调用 Emily 能力层（service / 工具 / 脚本），不在控制台路由层另写一份业务逻辑（CLAUDE.md 约束 14）。
10. **取数出口**：本文中"群台账列表 / 群消息列表 / 跨群检索"三种读取的唯一实现处（一个 service），工具与控制台路由**共同调用它**。

## 六、功能需求

> 编号 `FR-{域}-{序}`。域：`GRP` 群台账与保存 / `QRY` 群信息查询 / `CON` 控制台群追踪视图 / `COM` 共通。

### FR-GRP 群台账与保存

- **FR-GRP-1 群清单同步**：QQ 侧拉取 bot 加入的全部群并 upsert 到 `conversations`。沿用**启动时同步一次**，并新增**手动再同步入口**（脚本 + 复用既有 `POST /api/v1/groups/sync`）。⚠️ 不得实现为周期性定时任务——系统当前不存在周期性自动触发机制（约束 12 注），需周期执行时由外部调度调用脚本或 API。
- **FR-GRP-2 群备注（人工，核心）**：
  1. `conversations` 新增 `note` 列，承载人工功能备注。
  2. **与 `title` 严格分离**：`title` 继续存平台群名且允许被同步覆盖；`note` 只由人工设置，**任何同步链路不得写 `note`**。
  3. 展示口径：有 `note` 时以 `note` 为主标识、`title` 为附注；无 `note` 时回退显示 `title`。
  4. 设置入口：维护脚本（带 `params` schema，含"群"动态候选源）+ 控制台接线（复用能力层，约束 14）；**不在控制台路由层新写业务逻辑**。
  5. 备注变更留痕（谁 / 何时 / 旧值 → 新值）。
- **FR-GRP-3 群成员名册**：
  1. 新增 `group_members` 表，唯一键 `(im_platform, group_id, im_user_id)`；字段至少含 `display_name`、`role`（owner/admin/member，可空）、`joined_at`（可空）、`first_seen_at`、`last_seen_at`、`user_id`（FK→`users.id`，可空）。
  2. 采集来源：QQ `get_group_member_list`（OneBot action）。平台无该 action（如企微）时跳过并记 warning，**不阻断**。
  3. **绑定解析**：名册以 IM 身份落地；`user_id` 经 `user_im_bindings`（唯一约束 `(im_platform, im_user_id)`）解析，未绑定者**保留 IM 身份不丢弃**，允许后续补绑。
  4. 刷新为**全量覆盖式 upsert**：同群同人只保留一行；退群者处置见 §十一 D4。
  5. **保鲜机制 = 惰性刷新（口径见 §十一 D7）**：
     - 每个群记录"名册最后同步时间"（用于 TTL 判定）；TTL 建议 7 天。
     - **触发点只在"人在场"路径**：打开控制台群追踪、查看某群名册、执行维护脚本时，若该群已过期则先同步刷新再呈现。
     - **LLM 检索路径不触发刷新**——只读现有名册，保证工具全链路只读（FR-QRY-6 / NFR-3 / §九.2-5）。
     - **不实现为系统内置定时任务**（约束 12 注）。维护脚本保持可手动执行，供外部调度在需要时挂上。
  6. **可选增强：事件驱动**（机制二）——对含敏感内容的群，接入 QQ 成员变动通知以让"退群"即时生效；若采用，须与惰性刷新**共用同一写入函数**（幂等 upsert），避免两条路径各写一份导致口径不一致。
  7. **过期可见**：控制台与日志须能列出"名册已过期的群"，供运维点击刷新，不以静默掩盖。
- **FR-GRP-4 成员数落地**：`member_count` 不再丢弃；来源口径见 §十一 D3。
- **FR-GRP-5 群消息落库闭环**：核对既有链路（先落库、后判是否回复；`monitor` 模式未 @ 也落库），确保群消息必落 `messages`、`group_id` 冗余正确、`sender_user_id` 回填正确、附件走既有链路。**不新增写入路径**。
- **FR-GRP-6 来源标记**：沿用既有 `messages.source` 机制（`_current_source()`，取值 `user / test / ops / auto`），**不新建字段**；`query_groups` 的群消息检索**默认排除 `test` 与 `ops`**，避免测试数据污染检索结果可信度。
- **FR-GRP-7 群可关联项目（本期只确认可用性）**：`conversations.project_id` 列已存在但当前无消费者；本基线只确认其可用，**是否启用见 §十一 D5**。

### FR-QRY 群信息查询

- **FR-QRY-1 工具形态**：新增**只读**业务工具 `query_groups`（进程内 async handler，登记进 `tool_registry`，带参数 schema）。**不得**用 subprocess CLI 脚本作为 LLM 通道。两个动作：
  - `action="list"`：列出系统正在保存信息的群。每条带群标识、**备注名（无则平台群名）**、平台、成员数、已存消息数、最近活跃时间。
  - `action="messages"`：按关键词检索群消息原文。可限定群、时间范围、条数；每条带所属群（备注名）、发言人、时间、原文片段、消息定位标识。
- **FR-QRY-2 自我说明**：工具描述须让 LLM 在不读任何外部上下文的前提下知道：① 系统正在保存群消息；② 本工具能列出有哪些群；③ 能按关键词检索群内原文；④ 典型用途（"某材料的进场时间可能是群里某人报备的"）。
- **FR-QRY-3 参数约束（约束 11）**：
  1. 按注册三步落地：源文件 `_QUERY_GROUPS_SCHEMA` → `registry.py` 传 `params=` → `tools_consistency.py` 的 `TOOL_SCHEMA_MAP` + `TOOL_META_MAP` 登记。
  2. **LLM 不给内部 ID**：群以"备注名 / 群名 / 群号"表达，由服务端解析；不唯一时返回候选请 LLM 再问，解析不出则明确回报"未找到"。
  3. `keyword` 在 `action="messages"` 时为必填；`limit` 设上限。
- **FR-QRY-4 检索作用域（安全边界）**：命中集合必须先收敛到发起者的允许群集合，且该收敛**只有一处实现**（对齐 `docs/Spec/项目归属与可见范围_Spec.md` 的单一出口纪律，禁止各处各自过滤）。口径见 §十一 D1。
- **FR-QRY-5 可解释**：每条结果可回答"为什么是这条"——所属群（备注名）、发言人、时间、原文出处；不得只给结论。
- **FR-QRY-6 只读与稳健**：只读、幂等、不写库；空结果如实回"该群 / 该时间范围内没有匹配记录"，**不臆造**；查询异常不阻断对话主链路。
- **FR-QRY-7 检索口径**：本期**不做向量检索、不做语义扩召回**，命中即子串匹配（与既有 `chat_archive` 同口径，避免两套检索语义并存）。
- **FR-QRY-8 SOP 声明**：在合适 SOP 增补一节"群信息查询"——工具位置、发现方式、适用场景与权限口径；仅增补，不改既有触发条件与工具清单。
- **FR-QRY-9 控制台呈现**：群台账、名册与群消息在控制台的呈现见 **FR-CON**（本节不重复规定）。

### FR-CON 控制台群追踪视图

> **定位**：观察窗口。取数逻辑全部来自 Emily 能力层，控制台只接线与呈现（CLAUDE.md 约束 14）。

- **FR-CON-1 模块项与布局**：
  1. emy-console 左侧「模块能力」新增一项「**群追踪**」，点击进入群追踪视图（沿用既有模块项的注册与切换方式）。
  2. 右侧视图为**上下两栏**，中间为可拖拽的横向分隔条（复用既有 resizer 范式）。
  3. **上半栏 = 当前正在追踪的群列表**：每行显示备注名（无备注则平台群名）、平台、成员数、已存消息数、最近活跃时间。支持按备注名/群名筛选、按最近活跃排序。
  4. **下半栏 = 选定群的通讯内容**：时间正序展示发言人、时间、正文；附件显示元信息并复用既有附件查看通道；支持向上回溯与"加载更多"。
  5. 在上半栏选定某群 → 下半栏切换到该群消息。
- **FR-CON-2 跨群文字检索**：
  1. 视图内提供关键词检索框，**检索范围跨全部正在追踪的群**。
  2. 结果列表展示"哪个群 / 谁说的 / 什么时候 / 原文片段"；点击结果可切到该群的消息视图。
  3. 支持两种入口：跨群全局检索、在当前选定群内检索；两者**共用同一取数出口**。
  4. 结果默认排除 `test` / `ops` 来源（与 FR-GRP-6 一致）。
- **FR-CON-3 分页与回溯**：群列表可分页；群消息必须分页（复用既有 `before_id` 锚点回溯思路），**不得一次拉全量**。
- **FR-CON-4 取数接入式复用（核心）**：
  1. **三种读取——群台账列表 / 群消息列表 / 跨群检索——只有一处实现**，位于 Emily service 层（新增服务或扩展既有聊天检索服务）；`query_groups` 工具的 handler 与 emy-console 路由**共同调用它**。
  2. 控制台路由只做：参数校验 → 调 service → 按既有约定包装统一响应。**不得在路由层拼业务查询**。
  3. **禁止**：路由层直写 SQL 直查表、路由层复刻检索条件、为控制台单独再写一份列表逻辑（CLAUDE.md 约束 14）。
  4. 交付顺序上，**先补齐服务层取数出口，再接线到控制台**；能力层缺失时不得控制台先行。
- **FR-CON-5 只读性**：视图全部只读；**唯一写能力是群备注维护**，经 FR-GRP-2 的维护脚本（既有脚本注册通道）接入，不在路由层直接写库。视图打开与检索不改变任何表行数。
- **FR-CON-6 取数出口的入参补齐**（现状缺口，须在服务层一并解决）：
  - 既有全文检索**没有按群过滤的入参**、**不能排除来源**、**无分页**；按群取最近消息的方法同样不能排除来源。
  - 取数出口需补齐：按群过滤、按来源排除、分页游标（群消息回溯）。
  - 该扩展落在 repo / service 层，**工具与控制台同时受益**，不各补一份。
- **FR-CON-7 群成员名册查看**：上半栏选定群后可查看该群成员名册（IM 身份、显示名、绑定状态、角色），数据来自 FR-GRP-3。
- **FR-CON-8 失败可见**：某群消息读取失败不得导致整视图白屏；错误在面板内提示，其余功能仍可用。

### FR-COM 共通

- **FR-COM-1 注册通道**：工具 → `tools/registry.py`；脚本 → `scripts_registry.yaml`（带 `params` schema，约束 10b）；控制台模块项 → 既有 emy-console 模块清单注册方式 + 路由复用能力层（约束 14）。无裸文件、无硬编码接线。
- **FR-COM-2 内核冻结**：本模块**不得触及**会话主循环（`session/loop.py`）、LangGraph 执行引擎与会话上下文装配（约束 13）。**本期明确不做 session prompt 注入**；"LLM 知道有哪些群"由工具达成。
- **FR-COM-3 无周期性自动触发**：群清单与名册刷新一律做成**可手动 / 可外部调度的脚本或 API**，不引入任何常驻或定时机制（约束 12 注）。
- **FR-COM-4 数据层变更登记**：新增列须登记进 `init_db` 的 `_PENDING_COLUMNS`（`create_all()` 不会为已有表补列）；新表由 `create_all()` 创建。同步更新 `docs/Manual/数据库设计.md`（维护约定 3）。
- **FR-COM-5 消除 schema 漂移（附带修正）**：`chat_archive` 当前注册用的是 `tools/project/__init__.py` 的简版 schema，而完整版（含 `time_range` / `include_progress`）定义在同一工具的 `ToolDefinition` 中未被使用——同一工具两份 schema。本期把注册改为以完整版为准，**只补参数可见性，不改检索行为**。
- **FR-COM-6 权限**：`query_groups` 为只读，`permission_flag="all"`，exposure 沿用 base 只读口径；群备注与名册维护沿用管理级口径，不新造权限规则。
- **FR-COM-7 幂等**：重复同步群清单、重复拉取名册、同一消息重复投递均不产生重复行。
- **FR-COM-8 可下线**：移除工具注册与 SOP 声明后，系统回落为"群消息照常落库但无查询入口"，无残留触发器。

## 七、非功能需求

1. **NFR-1 不阻断主链路**：群清单同步、名册刷新、备注维护任一失败均不影响消息落库与对话；失败可见（日志 + 返回值），不静默。
2. **NFR-2 无新增常驻成本**：无常驻进程、无定时任务；查询工具按需调用，不额外增加对话轮次。
3. **NFR-3 只读安全**：`query_groups` 全链路只读；备注与名册的写入只在明确的维护入口。
4. **NFR-4 可解释**：任何命中都能回答"哪个群 / 谁说的 / 什么时候 / 原文是什么"。
5. **NFR-5 单一出口**：检索作用域收敛只有一处实现，便于审计与后续调整。
6. **NFR-6 注册通道接入**：工具须经 `tool_registry` 注册并带参数 schema；脚本须在 `scripts_registry.yaml` 声明 `params`。
7. **NFR-7 主循环冻结**：本模块改动不得触及会话主循环与内核文件（约束 12/13）；落地后须以静态扫描自证。
8. **NFR-8 控制台同源**：控制台不新增业务逻辑，写能力复用能力层（约束 14）。
9. **NFR-9 数据质量可见**：名册采集失败、成员数与名册不一致、群消息来源混杂等情况应可巡检，不以静默降级掩盖。
10. **NFR-10 检索收敛**：群消息检索须能按"群 + 时间范围"有效收敛；`messages` 现有索引为 `idx_msg_source_created(source, created_at)`，若数据量下不足以支撑按群检索，允许本模块为 `messages(group_id, created_at)` 增索引（须一并登记进 `_PENDING_INDEXES`）。
11. **NFR-11 取数单一出口**：群台账列表 / 群消息列表 / 跨群检索三种读取只有一处实现（service 层），工具与控制台共同调用；控制台路由层无业务查询语句。
12. **NFR-12 控制台同源可核验**：控制台的读写能力必须可被指认到 Emily 既有能力（service / 工具 / 脚本）；交付时须能回答"这一屏的数据来自哪个 service 的哪个方法"。
13. **NFR-13 视图可用性**：群列表与群消息均分页；单群消息读取失败不白屏；视图打开不引入长事务或全表扫描。

## 九、验收方向（用户视角，修改前 → 修改后）

### 9.1 用户可见差异

| # | 场景（用户动作） | 修改前（现状） | 修改后 |
|---|-----------------|--------------|--------|
| 1 | 在某个群里正常聊天（没有 @ Emily） | 消息照常落库；Emily 不回复 | 不变（安静记录） |
| 2 | 问"系统在保存哪些群的信息" | 答不出来；模型不知道群的存在 | 能列出群清单，每个群带功能备注（无备注则显示平台群名）、平台、成员数、已存消息数、最近活跃 |
| 3 | 问"XX 材料的进场时间" | 只能在"本人发过言"的会话里做子串匹配；若该群本人没说过话，返回空 | 能给出群里相关消息原文：哪个群、谁说的、什么时候，由用户自行判断 |
| 4 | 想限定在某个群查 | 只能给 `conversation_id`，且需事先知道 UUID | 用备注名或群名即可，如"查一下景观施工工程群" |
| 5 | 想给一个群做标注（"这个群是景观施工的"） | 无处可放；群只有平台下发的群名 | 可设置人工备注；后续所有展示与检索都以备注为主标识 |
| 6 | 群在平台侧被改了名 | 群名随同步更新 | 备注保持不变；平台群名作为附注更新 |
| 7 | 想看某群有哪些人 | 无此能力；只能靠"谁发过言"推测 | 可查到成员名册（IM 身份、显示名、已绑定系统账号）；未绑定者保留 IM 身份 |
| 8 | 群里某人从未发言，但确实是群成员 | 系统识别不到他参与该群 | 名册中有他（未绑定则保留 IM 身份） |
| 9 | 名册采集失败（bot 权限不足 / 平台不支持） | 不适用 | 明确回报失败原因，不静默；群消息记录与对话不受影响 |
| 10 | 检索一个从没有消息的群 | 不适用 | 如实回"该群暂无匹配记录"，不臆造 |
| 11 | 打开 emy-console 想看都有哪些群在被记录 | 控制台左侧没有群相关条目，无任何群视图 | 左侧「模块能力」多出「群追踪」一项；打开后上半栏列出正在追踪的群（备注名、平台、成员数、消息数、最近活跃） |
| 12 | 在上半栏点选某个群 | 不适用 | 下半栏显示该群的通讯内容（发言人、时间、正文，时间正序），可向上回溯、加载更多 |
| 13 | 在群追踪里搜"钢筋进场" | 不适用 | 跨全部追踪群给出命中列表：哪个群、谁说的、什么时候、原文片段；点结果切到该群消息 |
| 14 | 只看某个群里的检索结果 | 不适用 | 在当前选定群范围内检索，与跨群检索走同一取数出口、结果口径一致 |
| 15 | 想给群里某条记录看附件 | 不适用 | 附件显示元信息并可打开（复用既有附件查看通道） |
| 16 | 某个群的消息读取出错 | 不适用 | 该区域提示错误，视图其余部分仍可用，不整屏白屏 |
| 17 | 在控制台改某个群的备注 | 不适用 | 经群备注维护脚本（既有脚本通道）写入，与对话侧看到的备注一致 |
| 18 | 打开某群的名册查看，但该群名册已很久没更新（超过 TTL） | 不适用 | 先自动刷新该群名册再显示（约 1~2 秒等待）；刷新失败时如实提示并显示现有数据，不白屏 |
| 19 | 在对话里问"哪些群的名册过期了" | 不适用 | 不适用——**过期巡检只做在控制台与日志**，不给 LLM 暴露运维巡检能力（保持工具体面收敛） |
| 20 | 在对话里检索某群消息，而该群名册已过期 | 不适用 | 检索照常返回结果，**不在此路径上刷新名册**（工具保持只读）；名册的过期窗口由 TTL 兜住 |

3. **备注是否也承载"项目归属"语义（对应 §十一 D5）**：备注是自由文本还是结构化（项目 + 用途两字段）？

4. **名册怎么保持不过期（对应 D7）**：指**群成员名册**（每个群有谁），不是群清单。有人加群、有人退群，名册会过期。三种机制：
   - **机制一｜周期全量**：定时拉全部群成员覆盖写入。无未知项，但延迟 = 周期，且要挂外部调度。
   - **机制二｜事件驱动 + 低频兜底**：QQ 成员变动通知即时更新，另加全量对账兜底。延迟最低，但依赖"通知可达"这个尚未实测的前提。
   - **机制三｜惰性刷新（按需，推荐）**：**不设调度**，在真正用到某群名册时才检查它是否过期，过期就当场拉一次。即"需要的时候临时更新"。
   - **建议：选机制三**。理由：① 不依赖任何外部调度，正好绕开"系统已无定时任务机制"；② 名册只在被用到时才有价值，为没被看过的群每天拉一遍是浪费（拉名册是逐个群调 QQ API，有频率限制）；③ 成本随使用量走，而非随群数量走。
   - **机制三必须配两条护栏**（否则会留一个洞）：
     - **护栏一｜TTL 门槛**：给每个群记"名册最后同步时间"，超过 TTL（建议 **7 天**）即视为过期。**这一条是必需的**，原因见下。
     - **护栏二｜权限路径不写库**：刷新的触发点**只放在"人在场"的路径**（打开控制台群追踪、查看某群名册、维护脚本）——这些场景等 1~2 秒可接受。**LLM 检索路径不触发刷新**，只读现有名册。否则会与本文档既有条款冲突：FR-QRY-6 与 NFR-3 要求工具全链路只读，§九.2 第 5 项更直接要求"`query_groups` 调用前后相关表行数不变"——在检索路径里顺手写名册会当场违反自己的验收条款。
   - **必须知道的一个方向性缺口**：惰性刷新对**新入群的人**是安全的——他没进名册就查不到，属 fail-closed（拒绝），刷新后即可查到；但对**已退群的人**是**危险的**——他仍在名册里，就仍能检索该群消息，属 fail-open（放行）。**机制三本身补不上这个方向，只能靠 TTL 把窗口压住**（最长 = TTL）。所以：
     - 若选纯机制三 → TTL 取小（**3~7 天**），并在控制台/日志暴露"名册已过期的群"供运维点击刷新；
     - 若该群含敏感内容（报价、合同、甲方沟通）→ **叠加机制二的事件驱动**，让"退群"即时生效，惰性只做兜底。即"**惰性为主、事件为增强**"。
   - **触发方**：机制三无需调度；维护脚本仍保持可手动执行（也便于外部调度需要时挂上）。系统内**不引入任何常驻/定时机制**（约束 12 注）。
   - **备选**：机制一（每日 1 次全量）——若希望延迟有界且不愿依赖"通知可达"与"TTL 巡检"；机制二单独使用——若实测确认通知可达且群数量少。
   - 回答：
