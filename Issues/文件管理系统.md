# 文件管理系统设计

> **文档定位**:文件管理的权威设计依据。涵盖分类学(taxonomy)、关联模型、分辨策略、整理策略。
> **基线梳理**:见 [待执行计划/文件管理系统_FileManager工具_计划_V1.md](../待执行计划/文件管理系统_FileManager工具_计划_V1.md) 的 Context 段
> **状态**:设计已定稿,待补 M5 实施计划

---

## 〇、需求来源(原始问题)

> 当前文件管理系统是如何约定的,用户上传的文件、群内上传的文件、位图,是否自动下载?是否自动归类。是否对一般用户可见(检索可见性)?权限如何约束的?是否可以要求 emily 发其拥有的文件、图片给自己?
>
> 各渠道上传的文件应如何组织管理。上传的文件、图片有各种属性、目的,有的是完工确认,比如取得的证照,施工许可之类的。有的是验收记录附图(可能是一套文件相互关联)、有的是图纸、过程讨论图纸。有的是做法参考、优秀工艺参考样图。也有纯闲聊发的 gif 和梗图。你觉得应该如何分辨、整理?

---

## 一、现状与痛点

当前 Emily 文件管理有四个割裂痛点:

1. **分类学混淆**:`file_category` 7 类(PROJECT_LICENSE/CONTRACT/WORK_RECORD/PHASE_DELIVERABLE/PROCESS_DOC/MANAGEMENT_SPEC/OTHER)混合了"业务意图"和"文档类别"两个正交维度。"优秀工艺参考样图"和"梗图"都只能落 OTHER,业务价值天差地别却挤同一格。
2. **能力不闭环**:能录能查能改分类,但不能发、不能删、不能成组、不能版本化。用户拿到 `file_no` 后无路可走。
3. **权限双标**:`query_files` 走 `project_ids`(无密级),`search_files` 走 `session_accessible_files`(含密级)。
4. **附件链路断裂**:入站附件不自动下载,依赖 `record_file` 触发,IM URL 过期即丢失。

M1-M4(见实施计划)解决痛点 2/3/4。**本文档解决痛点 1**,并修订 M4 的成组方案。

---

## 二、设计原则:三层正交分类

文件有三个正交维度,不应塞进一个字段:

| 层 | 维度 | 字段 | 决定什么 |
|----|------|------|----------|
| 第一层 | 业务意图 | `purpose`(新增) | 保留策略 / 检索可见性 / 默认处理流程 |
| 第二层 | 关联结构 | `parent_file_id` + `attachment_of`(新增) + `source_module_id` | 文件间关系 |
| 第三层 | RAG 索引 | `rag_indexed`(新增) + `rag_collection`(新增) | 是否进知识库 |

`file_category`(现有 7 类)**降级为次分类**(文档类别),描述"文档是什么",不再承担业务意图职责。

---

## 三、第一层:业务意图 `purpose`(主分类)

### 5 类枚举

| purpose | 含义 | 典型 | 保留策略 | 检索可见性 | 默认处理 |
|---------|------|------|----------|-----------|----------|
| **EVIDENCE** | 凭证证据 | 证照、施工许可、合同、批复、验收合格单 | 永久 | 项目全员 | 强制核验 + 关联节点交付 |
| **RECORD** | 工作记录 | 验收附图、施工记录、会议附件 | 项目周期 | 项目全员 | 成组关联 + 可选入 RAG |
| **DESIGN** | 设计图纸 | 施工图、过程讨论图 | 长期 | 项目全员 | 版本链管理 |
| **REFERENCE** | 参考样例 | 优秀工艺、做法参考、规范条文图 | 长期 | **跨项目**通用库 | 入通用 RAG 知识库 |
| **CHAT** | 闲聊素材 | gif、梗图、表情包 | **不入 files 表** | 仅发送者(IM 内) | 只留 messages.attachments URL |

### purpose 与 file_category 的关系(正交)

`purpose` 是主分类(决定行为),`file_category` 是次分类(描述文档类别)。两者正交:

| 文件 | purpose | file_category |
|------|---------|---------------|
| 施工许可证 | EVIDENCE | PROJECT_LICENSE |
| 总承包合同 | EVIDENCE | CONTRACT |
| 验收附图(一套) | RECORD | PHASE_DELIVERABLE |
| 施工日志附件 | RECORD | WORK_RECORD |
| 施工图 v3 | DESIGN | PROCESS_DOC |
| 优秀工艺样图 | REFERENCE | OTHER(或新增 KNOWLEDGE) |
| 梗图 | CHAT | 不入 files 表 |

### 字段定义

```python
class FilePurpose:
    EVIDENCE = "EVIDENCE"      # 凭证证据
    RECORD = "RECORD"          # 工作记录
    DESIGN = "DESIGN"          # 设计图纸
    REFERENCE = "REFERENCE"    # 参考样例
    CHAT = "CHAT"              # 闲聊素材(不入 files 表,仅作枚举完整性)

    ALL = [EVIDENCE, RECORD, DESIGN, REFERENCE]  # CHAT 不入库
```

**新增字段**:
- `purpose`: String(50), default="RECORD", not null —— 业务意图
- `purpose_confirmed`: Boolean, default=False —— LLM/用户是否已确认(入站规则给的候选默认 False)

## 四、第二层:关联结构(三种正交关系)

### 4.1 版本链(已有,DESIGN 类典型)

**字段**:`parent_file_id` + `is_latest` + `version`(均已就位)

**语义**:同一文件的迭代版本。施工图 v1 → v2 → v3,旧版本 `is_latest=False`,新版本 `parent_file_id` 指向上一版。

### 4.2 附件链(新增,主从结构)

**字段**:`attachment_of`(String, FK → files.id, nullable, 新增)

**语义**:一套文件 = 1 个主文件 + N 个附件。主文件是"攒总"(如验收合格单),附件挂靠其下(如各专业施工图)。

| 取值 | 语义 |
|------|------|
| NULL | 主文件 或 独立文件(NULL 统一表示,不区分) |
| 非空 → files.id | 附件,挂靠到主文件 |

**规则**(已确认):
- **禁止嵌套**:附件的 `attachment_of` 只能指向主文件(主文件 `attachment_of IS NULL`),不能指向另一个附件。应用层校验。
- **主文件软删除**:附件保持原状(`attachment_of` 仍指向已删除主文件)。检索时主文件不返回(`is_deleted=True` 过滤),附件独立可见。
- **NULL 统一表示主/独立**:不区分主文件与独立文件,查询时 `attachment_of IS NULL` 即"主或独立"。

**查询一套文件**:
```sql
SELECT * FROM files
WHERE id = :master_id OR attachment_of = :master_id
ORDER BY (attachment_of IS NULL) DESC, created_at;
-- 主文件排首位,附件按时间
```

### 4.3 业务关联(已有,全部 purpose 通用)

**字段**:`source_module_id` + `source_module_type`(均已就位)

**语义**:文件 → 业务对象(节点/事件/会议)。与附件链不同:这是文件到业务对象的关联,不是文件到文件。

`source_module_type` 取值:`NODE_STARTUP_DOC` / `NODE_WORKLOAD_DOC` / `NODE_DELIVERABLE_DOC` / `NODE_ATTACHMENT` / `EVENT_DOC` / `MEETING_DOC`。

### 4.4 三种关系正交

一个文件可同时处于三条链:

```
建筑施工图 v2
├── 版本链:parent_file_id → 建筑施工图 v1
├── 附件链:attachment_of → 图纸评审验收合格单
└── 业务关联:source_module_id → 节点 SG-001(主体结构施工)
```

### 用户的典型场景映射

> "某专业施工图成果,都属于图纸评审验收合格单的附件"

```
图纸评审验收合格单(EVIDENCE, 主文件, attachment_of=NULL)
├── 建筑施工图成果(DESIGN, 附件, attachment_of=合格单.id)
├── 结构施工图成果(DESIGN, 附件, attachment_of=合格单.id)
├── 机电施工图成果(DESIGN, 附件, attachment_of=合格单.id)
└── 评审会议纪要(RECORD, 附件, attachment_of=合格单.id)
```

**关键**:主从结构不要求 purpose 一致——主文件是 EVIDENCE(攒总凭证),附件可以是 DESIGN/RECORD。purpose 是文件自身属性,attachment_of 是文件间关系。

## 五、第三层:RAG 索引标志

**新增字段**:
- `rag_indexed`: Boolean, default=False —— 是否已入 RAG 知识库
- `rag_collection`: String(100), default="" —— 所属集合(项目库 / 通用参考库)

**默认入 RAG 规则**:

| purpose | 默认 rag_indexed | rag_collection |
|---------|------------------|----------------|
| EVIDENCE | False | — |
| RECORD | False(可选入) | 项目库 |
| DESIGN | False | — |
| REFERENCE | **True** | **通用参考库** |
| CHAT | — | 不入 files 表 |

REFERENCE 类入通用 RAG 库,**跨项目可检索**(见 §七)。

## 六、CHAT 处理策略(不入 files 表)

**决策**:闲聊素材(gif、梗图、表情包)不入 `files` 表,只留 `messages.attachments` 的 IM 平台 URL。

**理由**:
- 无业务价值,不入库节省存储
- 检索不可见,不污染文件查询结果
- IM URL 过期即丢失,可接受
- 不需要 purpose=CHAT 的 files 记录(CHAT 仅作枚举完整性,实际不入库)

**分辨规则**(入站时,M3 自动下载阶段判断):
- 群聊图片 + 文件名匹配梗图模式(`*.gif`、含"表情/meme/梗") + 无业务关键词 → 不下载,不入库
- LLM 也可在 record_file 时判断"无业务价值"拒绝归档

**边界情况**:用户后来发现"梗图"其实是现场照片 → 用户显式说"归档这张图" → record_file 正常录入,purpose 由 LLM 判断(通常 RECORD)。

---

## 七、REFERENCE 跨项目通用库

**决策**:REFERENCE 类文件入通用 RAG 库,所有项目用户可检索。

**实现**:
- `rag_collection = "general_reference"`(通用库,区别于项目库 `project_<id>`)
- 入 MaxKB 通用知识库集合,`knowledge_search` 工具检索时跨项目可见
- `files` 表中 `project_id` 可为 NULL(REFERENCE 不绑定项目)
- 权限:`session_accessible_files` 同步时,REFERENCE 类文件对所有用户可见(或按 `info_level` 过滤)

**与文件检索解耦**:REFERENCE 类主要通过 `knowledge_search`(RAG 语义检索)访问,而非 `query_files`(结构化查询)。`query_files` 默认只查项目内文件,REFERENCE 走 RAG 通道。

## 八、分辨策略:规则 + LLM 协同(三时机)

不让 LLM 凭空判断,分三个时机各司其职:

### 时机 1:入站时(M3 自动下载后)—— 规则为主,给候选 purpose

规则匹配(在 AttachmentDownloader 或独立 RuleEngine 中):

| 信号 | 候选 purpose |
|------|-------------|
| `*.gif` / 文件名含"表情/meme/梗" / 群聊 + 无业务关键词 | CHAT(不入库) |
| 文件名含"证/许可/执照/合同/批复/合格单" | EVIDENCE |
| 文件名含"图/.dwg/施工图/设计/图纸" | DESIGN |
| 文件名含"参考/样例/规范/工艺/做法" + 私聊或跨项目语境 | REFERENCE |
| 其余 | RECORD(默认) |

候选 purpose 写入 `purpose` 字段,`purpose_confirmed=False`。

### 时机 2:录入时(record_file)—— LLM 确认/修正

LLM 拿到候选 purpose + 上下文 + 用户意图,确认或修正,填 `file_category`。用户显式说"这是验收附图"则直接定 RECORD。

LLM prompt 需注入 purpose 5 类定义 + 典型示例(见 §十一 prompt 调整)。

### 时机 3:事后校正

- `update_file_purpose` 工具:改 purpose(如 CHAT → RECORD,用户后来发现梗图其实是现场照片)
- `link_to_master` 工具:把文件挂到主文件下(设 `attachment_of`)
- `unlink_attachment` 工具:把附件提升为独立文件(`attachment_of = NULL`)
- 管理员批量校正

## 九、整理策略:按 purpose 分治

| purpose | 整理动作 | 自动化程度 |
|---------|----------|-----------|
| EVIDENCE | 强制关联节点交付物 + Guardian 核验 + 入项目证照库 | 半自动(需核验) |
| RECORD | 成组关联到事件/验收(attachment_of 主文件) + 可选入项目 RAG | 半自动(成组建议) |
| DESIGN | 建版本链(parent_file_id) + 旧版本归档不删 + 同名文件提示升版 | 半自动(版本检测) |
| REFERENCE | 入通用 RAG + 跨项目标签 | 自动入 RAG |
| CHAT | 不入 files 表,IM URL 过期自动失效 | 全自动 |
