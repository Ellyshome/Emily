## 1. 讨论结论摘要

把"全景节点维护者"从"一个常驻 agent"降维成"一个能力"，走 SOP 声明路径，纯签认可信度，先跑起来验证，再按反馈演进。

核心洞察：**"这说到底是人之间的问题"** —— 节点怎么拆是组织口径之争，AI 不该"强制"收敛，而应"显性化分歧 + 提案 + 签认"。

---

## 2. 最终方案形态

> 写一份 SOP 声明文件 → 经能力层（`SopCapabilityRunner`）注册 → agent loop 里 LLM 多步完成「解析文件 → 读规则书/世界书 → 推导 → 调 `create_node` 批量落库」

**关键**：这是"声明 + agent loop 运行时推导"，不是旧式单工具 SOP（约束 3/5 的 `chat_json` 直调），**推导逻辑不写成代码**。

三个落点（最小集）：

1. 一份 SOP 文件 `SOP-013-SYS-node_propose.md`（放 `emily-data/sops/`，零 Python 业务代码）
2. 可信度零改动：复用现有签认（`SignoffService` + `ACK node=4`），节点入库即"未签认"，检索标"（未签认，暂不可信）"
3. 共识来源零改动：规则书（应然）+ 世界书 structure 层（实然），已注入 session prompt

## 3. 关键设计决策

| # | 决策 | 结论 |
|---|------|------|
| 1 | 定位 | 能力，不做常驻 agent、不碰 A2A |
| 2 | 实现路径 | SOP 声明 + agent loop 运行时推导（不写死推导代码） |
| 3 | 可信度 | **纯签认（A 方案）**：入库即生效，签认不阻断，检索标注不可信；不引入草稿态、不做对话预览确认 |

## 4. 待明确规则项（次日填写）

### 4.1 已有约定（确认沿用即可，不重填）

以下口径已由 [全景节点填报格式约定_V1.md](./资料驱动节点更新/全景节点填报格式约定_V1.md) 定义，维护者的推导依据直接引用：

- [ ] 节点本体：里程碑 vs 任务的判定（有子节点=里程碑，叶子=任务，任务须带可计量成果）
- [ ] 节点命名：对象+动作/状态，≤20 字，不带项目名/日期
- [ ] 节点阶段：立项 / 规划设计 / 工程施工 / 交付结算
- [ ] 产物与"文件识别特征"：抬头字样、编号特征、关键字段、文件形态（§3.2）
- [ ] 完成判定：一句话 + 引用产物编号
- [ ] 文件→节点映射口径（附录 B：文件识别特征/典型文件名 = LLM 判定依据）

### 4.2 真正待补的口径（需业务方明确）

以下在现有文档里**没有明确**，需要明天填：

1. **节点生命周期/流转触发**：三态流转（未激活→激活→完成）的触发条件是什么？**何时废弃节点**？（填报格式约定只定义了"完成判定"，未定义废弃/流转触发）
2. **新建 vs 挂载的判定规则**：来一份新文件，什么时候建新节点、什么时候挂到现有节点？（diff 判定口径）
3. **节点编号生成策略**：无编号节点怎么生成？（沿用 `generate_node_id` 还是按资料名派生？）
4. **权重/精细依赖**：填报格式约定明确"本期权重不填"，那维护者推导时依赖/权重给不给？默认值/规则是什么？
5. **相对锚点换算**：计划时点用"取得施工许可证后 30 天"这类相对锚点，实例化到具体项目时如何换算为日期？

### 4.3 必须拍板的矛盾与边界（最关键）

1. **【矛盾】纯签认 vs 人工确认闸口**：
   - 今天讨论定：**纯签认**，节点入库即生效，未签认仅检索标注"不可信"；
   - 但 [资料驱动节点更新_意向需求基线_V1.md](./资料驱动节点更新/资料驱动节点更新_意向需求基线_V1.md) F6 定：变更草案"**暂不落库，确认后才执行写入**"。
   - **两者冲突，必须二选一或明确分层**：AI 推导的节点是"直接入库+签认标注"，还是"先草案+人工确认才落库"？

2. **【边界】三个机制的关系**：
   - 成果反推（单产物→节点完成）／ 资料驱动（计划资料→整树装配）／ 全景节点维护者（文件→节点）
   - 是同一个能力的不同触发，还是三个独立能力？各自入口、触发时机如何区分？

3. **【载体】通用参考节点库（模板库）落地**：填报格式约定 V1 的产出是"各专业通用参考节点库"，这个模板库作为系统数据怎么落地？维护者如何用它当"参考系"判断一个项目大概率会经过哪些节点？

4. **【未决】意向基线 F1-F9 的 4 个开放问题**（见该文档第五节）：草案确认载体（IM 内确认 / Web 列表）、资料类型识别方式（规则/LLM/两级）、无编号节点编号策略、触发时机（全量识别 / 按分类过滤）。

## 5. 暂缓项与演进触发条件

本轮明确搁置：

- A2A / 常驻 agent（等"需要主动、跨 session 找人对齐"被真实需求逼出）
- 跨项目高权限读取（行级隔离已按 Q9 关闭、不在本期范围，须另立需求）
- `rule_inductor` 的 `node_structure` 自总结类别（等实践反馈积累后）
- B 方案"对话预览确认"（用户已否，选纯签认）

**演进触发**：跑几个项目，收集"LLM 自由推导质量"反馈——若推导可控则纯 SOP 足够；若推导不可控（乱拆、漏读规则书），则升级为"专用工具强约束推导"（写 `propose_nodes` 专用工具 + 专用 prompt）。
