# 节点事件订阅推送 — 现状分析报告

> 分析日期：2026-07-23  
> 涉及模块：NodeEventBus / NodeService / OutboundEventBus / SSE  
> 核心问题：设计经理是否能订阅自己感兴趣的节点，在状态变化或上传完工确认单时收到推送通知？

### 1.1 节点事件总线 — NodeEventBus

**文件**：`emily-core/emily_core/node_event_bus.py`

基于 `asyncio.Queue` 的发布-订阅总线。核心数据结构：

- **NodeEvent**：事件体，含 `event_id / node_id / event_type / project_id / stage_id / old_value / new_value / operator_id / created_at`
- **SubscriptionFilter**：订阅过滤器，支持按 `node_id` / `event_types` / `project_id` / `stage_id` / `owner_dept_id` 过滤
- **NodeEventBus**：`subscribe(sub_id, filter_)` / `unsubscribe(sub_id)` / `publish(event)` 三方法模型

关键设计点：
- `publish()` 时自动转发到 OutboundEventBus（第135行）
- `subscribe()` 时可根据 filter 做细粒度匹配
- 支持两种模式：无过滤（全量）和带过滤（按需）

### 1.2 SSE 实时推送端点

**文件**：`emily-core/api/sse/node_events.py`

- **端点**：`GET /api/v1/events/nodes?project_id={project_id}`
- **协议**：Server-Sent Events (text/event-stream)
- **行为**：建立连接 → 订阅 NodeEventBus → 持续推送匹配的 node_event → 15s 心跳
- **当前过滤维度**：仅 `project_id`（可通过 `SubscriptionFilter` 扩展）

### 1.3 出站事件总线 — OutboundEventBus

**文件**：`emily-core/emily_core/outbound_bus.py`

全局出站总线，目前仅处理 4 种事件类型：

| 事件类型 | 用途 | 推送目标 |
|----------|------|----------|
| `reply` | Agent 最终回复 | IM (QQ) |
| `progress` | 前导进度消息 | IM (QQ) |
| `file_send` | 文件发送请求 | IM (QQ) |
| `session_closed` | 会话关闭通知 | IM (QQ) |

**注意**：当前 OutboundEventBus 没有 `node_event` 或 `node_notify` 的处理逻辑。NodeEventBus 虽然在 `publish()` 中调了 `self._outbound_bus.publish("node_event", ...)`，但 OutboundEventBus 的 SSE 监听端不识别此类型，会被静默丢弃。

## 2. 已记录的事件类型

`node_service.py` 中 `_record_event()` 方法已在以下场景写入 `node_events` 表：

### 2.1 状态机流转事件

| event_type | 触发场景 |
|------------|----------|
| `node_created_auto_activated` | 管理员创建节点（自动激活） |
| `node_created_pending_approval` | 普通用户创建节点（待审批） |
| `node_activated` | 审批通过，节点激活 |
| `node_activation_rejected` | 审批拒绝，节点废弃 |
| `node_discarded` | 主动废弃节点 |
| `node_updated` | 更新节点信息 |
| `status_changed` | **状态机自动流转**（CONDITIONS_NOT_MET → IN_PROGRESS → COMPLETED） |

### 2.2 成果/完工确认事件

| event_type | 触发场景 |
|------------|----------|
| `deliverable_updated` | 新增成果 / 更新成果进度 |
| `deliverable_submitted` | **提交完工成果**（PENDING → SUBMITTED） |
| `deliverable_confirmed` | **完工确认单确认**（SUBMITTED → CONFIRMED） |
| `deliverable_returned` | **驳回成果**（SUBMITTED → RETURNED） |
| `deliverable_resubmitted` | **重新提交**（RETURNED → SUBMITTED） |

### 2.3 依赖关系事件

| event_type | 触发场景 |
|------------|----------|
| `dependency_added` | 新增依赖关系 |
| `dependency_removed` | 移除依赖关系 |
| `BLOCKING_CONDITION_ADDED` | 人工阻塞条件（weight=999） |

### 2.4 node_events 表结构

```sql
CREATE TABLE IF NOT EXISTS node_events (
    id          VARCHAR(100) PRIMARY KEY,
    event_id    VARCHAR(100) NOT NULL,
    node_id     VARCHAR(100) NOT NULL,
    event_type  VARCHAR(50) NOT NULL,
    old_value   TEXT DEFAULT '',
    new_value   TEXT DEFAULT '',
    operator_id VARCHAR(100) DEFAULT '',
    remark      TEXT DEFAULT '',
    created_at  VARCHAR(50) NOT NULL
);
```

## 3. 缺失能力分析

### 缺口 A：事件未推送到总线

当前 `node_service._record_event()` 只写 DB：

```python
def _record_event(self, node_id, event_type, ...):
    self._event_repo.create(...)  # ← 仅 DB 写入
    # ❌ 缺少：self._node_event_bus.publish(NodeEvent(...))
```

**影响**：NodeEventBus 基础设施虽然在，但没有生产者发布事件，SSE 端点和 OutboundEventBus 转发链路是空的。

### 缺口 B：无用户级订阅模型

- 没有 `user_node_subscriptions` 表来持久化"用户 X 关注节点 Y"
- 没有 REST API 让用户订阅/取消订阅节点
- NodeEventBus 的 `SubscriptionFilter.owner_dept_id` 字段虽然定义了，但从未被填充
- 前端没有"我关注的节点"视图

### 缺口 C：无 IM 个人推送通道

- OutboundEventBus 只处理群聊回复（reply/progress），没有"定向推送到人"的路由逻辑
- 即使 node_event 到达 OutboundEventBus，也没有机制根据订阅表查找关注者并发起 IM 推送
- SubscriptionFilter 中虽有 `owner_dept_id` 字段，但实现中未使用（`_matches_filter` 方法未校验该字段）

```python
# node_event_bus.py L138 — owner_dept_id 被定义了但未参与匹配
@staticmethod
def _matches_filter(event, filter_):
    if filter_.node_id is not None and event.node_id != filter_.node_id:
        return False
    if filter_.event_types is not None and event.event_type not in filter_.event_types:
        return False
    if filter_.project_id is not None and event.project_id != filter_.project_id:
        return False
    if filter_.stage_id is not None and event.stage_id != filter_.stage_id:
        return False
    # ⚠ owner_dept_id 虽然定义了，但 _matches_filter 中未校验
    return True
```

## 4. 现状总结

| 能力 | 状态 | 说明 |
|------|------|------|
| 事件记录（DB） | ✅ 完整 | 14 种事件类型全量写入 node_events 表 |
| 事件总线基础设施 | ✅ 已搭建 | NodeEventBus + SubscriptionFilter + SSE 端点 |
| 总线生产端接入 | ❌ 未接入 | `_record_event()` 未调用 `NodeEventBus.publish()` |
| 用户订阅模型 | ❌ 不存在 | 无 user_node_subscriptions 表 / API |
| IM 个人推送 | ❌ 不存在 | OutboundEventBus 无 node_event 路由 / 无定向推送 |

**结论**：当前系统对"设计经理订阅感兴趣节点 → 状态变化/完工单上传时收到推送"这个需求的覆盖率为 0%。基础设施已有 30%（事件总线框架 + 事件记录），但生产接入、订阅模型、推送通道三块均缺失。

---

## 5. 实现路径建议

按优先级排序：

### 阶段 1：接通事件生产链路（低成本）
在 `node_service._record_event()` 中注入 `NodeEventBus` 并调用 `publish()`，使事件流入总线 → OutboundEventBus → SSE 前端可用。

### 阶段 2：用户订阅模型（中等成本）
- 新建 `user_node_subscriptions` 表（user_id, node_id, event_types, subscribed_at）
- 新增 REST API：`POST/DELETE /api/v1/subscriptions/nodes`
- 前端增加"关注节点"按钮

### 阶段 3：IM 推送通道（中等成本）
- OutboundEventBus 新增 `node_notify` 事件类型
- 实现定向推送服务：node_event 到达 → 查订阅表 → 找到关注者 → 通过 IM 插件推送到人
- 支持订阅粒度配置（只收 status_changed / 只收 deliverable_confirmed 等）
