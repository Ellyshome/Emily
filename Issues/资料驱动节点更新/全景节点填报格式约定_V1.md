# 全景节点填报格式约定 V1

> **用途**：各业务口按本约定提交本专业「全景节点」，汇总后作为 Emily 的通用参考节点库（模板库）使用。
> **面向对象**：各专业/部门业务同事（不需要了解系统，按格式填表即可）。
> **本版定位**：最小可用。只收关键节点与产物，不要求图全；字段不足处可不填，后续版本再扩展。
> **提交方式**：一个专业提交一份文件（Markdown 表格或 Excel 均可，字段一致）；文件名 `全景节点_XX专业_v1`；由 <项目负责人指定汇总人> 统一回收。

---

## 一、先对齐三件事（决定你填多少）

1. **只报关键节点**：每个专业首报 **3～8 个**「项目基本都会经过」的节点，优先报里程碑。日常细碎工作不用报。
2. **一个节点 = 一个能被判定"完成/未完成"的时点**，不是任务清单。填不出"什么算完成"的，就不是节点。
3. **只写本专业视角**：跨专业关系写在「前置节点」里引用，不要替别的专业定义节点。

> 参考方向：全景节点要能让系统回答两件事——
> ① 这个项目走到哪了；② **别人上传一份文件，能不能认出它属于哪个节点、该节点是否已完成**。
> 所以「产物 + 文件识别特征」是本次填报的重点，比计划时间还重要。

---

## 二、要填两张表

- **表 1 节点表**：一行一个节点。
- **表 2 产物表**：一行一个产物，用「节点编号」关联表 1。一个节点可以有多个产物。

### 表 1：节点表

| 列 | 必填 | 填写说明 |
|---|---|---|
| 节点编号 | 必填 | 格式 `专业码-两位序号`，如 `景观-01`。专业码见附录 A（全公司统一，避免撞码）；编号在本专业内唯一 |
| 节点名称 | 必填 | **不带项目名、不带年份日期**，≤20 字。命名规则：对象 + 动作/状态，如「景观施工图完成」「主体结构封顶」「施工许可证取得」 |
| 节点类型 | 必填 | 二选一：`里程碑` / `任务`。里程碑=对外可见重大节点（批文、封顶、验收等）；任务=承载可计量成果的节点（成果名 + 目标量 + 量纲）。**类型由填报声明决定，系统不按结构改写**；层级上里程碑不得挂在任务之下，任务之下只能挂任务 |
| 所属阶段 | 必填 | 四选一：`立项` / `规划设计` / `工程施工` / `交付结算` |
| 上级节点 | 选填 | 填本表内的父节点编号；没有上级就留空 |
| 责任部门 | 必填 | 本节点由谁负责，如「工程部」「成本部」「景观部」 |
| 计划时点 | 必填 | 二选一写法：<br>① 绝对日期：`2026-03-31`<br>② **相对锚点**（推荐，模板可复用于所有项目）：`取得施工许可证后 30 天`、`开工前 15 天` |
| 完成判定 | 必填 | 一句话说清"什么条件算完成"，尽量引用产物编号，如「表 2 的 景观-02-P1、景观-02-P2 均齐备」 |
| 前置节点 | 选填 | 本节点开始/完成的前提节点，填编号或名称，多个用顿号分隔；跨专业也写在这里 |
| 备注 | 选填 | ≤100 字。只写必要补充，如「分标段实施，可按标段分别判定」 |

### 表 2：产物表

| 列 | 必填 | 填写说明 |
|---|---|---|
| 节点编号 | 必填 | 关联表 1 的节点编号 |
| 产物编号 | 必填 | `节点编号-P序号`，如 `景观-02-P1` |
| 产物名称 | 必填 | 名词性、明确范围，如「景观施工图设计文件（全套）」；不要写「图纸」「资料」这种笼统词 |
| 必需性 | 必填 | `必需` / `可选`。**每个节点至少 1 条「必需」产物** |
| 数量/单位 | 必填 | 如 `1 套`、`1 份`、`3 张` |
| **文件识别特征** | **必填**（本表重点） | 写"打开文件能看到什么"，3～5 条即可。见第三节规范 |
| 典型文件名 | 选填 | 实际见过的文件名关键词或命名规律，越真实越好，如「含"景观施工图""园建""绿化"」 |
| 版本口径 | 选填 | 区分过程稿与定稿，如 `送审版` / `批复版` / `盖章扫描件`。仅当"必须拿到某版本才算完成"时填 |

## 三、填写规范（重点看「文件识别特征」）

### 3.1 节点名称

| | 示例 |
|---|---|
| 好 | 景观施工图完成；主体结构封顶；建设工程规划许可证取得 |
| 差 | 景观图纸的事（笼统）；2026 年 3 月出图（带日期，模板无法复用）；设计+报建+施工（一个节点混了好几件事） |

### 3.2 文件识别特征怎么写

写"能一眼看到的客观特征"，不要写要求、不要写评价。建议覆盖这四类，能写几条写几条：

1. **抬头/标题字样**：文件里出现的正式名称，如「景观施工图设计文件」「施工图设计文件审查合格证」
2. **编号特征**：有没有编号、编号长什么样，如「建字第 4403002025B0001 号」「图号前缀 建施-XX、结施-XX」
3. **关键字段**：落款单位、盖章类型、日期、结论性文字，如「审查结论：合格」「设计单位出图章」
4. **文件形态**：格式与量级，如「PDF，成套多张」「彩色扫描件 1-5MB」「常打包为 ZIP」

> 判断标准：**换一个没做过这个项目的人来看，能不能照着这几条把那类文件认出来**。能，就合格。

| | 示例 |
|---|---|
| 好 | 标题含"景观施工图"或"园建施工图"；图号按"园建-XX / 绿化-XX / 水景-XX"分册；图框内有设计单位出图章与项目名称；PDF 或 DWG，常打包 ZIP |
| 差 | 应该是设计院出的（是猜测，不是特征）；要专业的人才能看懂（等于没写）；很重要，必须齐（是要求，不是特征） |

### 3.3 其他常见错误

| 问题 | 修正 |
|---|---|
| 一个节点塞了多件事 | 拆成多个节点，用「前置节点」串联 |
| 产物写「相关资料」 | 写清具体是哪份文件，实在不确定就不报 |
| 计划时间写死具体日期 | 改写成相对锚点（`开工后 60 天`），便于跨项目复用 |
| 全填「里程碑」 | 里程碑只报**对外可见的重大节点**，其余填「任务」 |
| 只写"该节点已完成" | 写清完成条件，并对应到产物 |

## 五、提交前自查（6 项）

1. 每个节点都能回答「什么算完成」。
2. 每个节点至少 1 条「必需」产物，且写了「文件识别特征」。
3. 节点名称里没有项目名、没有具体日期。
4. 计划时点用的是相对锚点或明确日期，不是"视情况"。
5. 前置节点提到的节点，能在本表或已有专业表里找到。
6. 本专业首批节点数在 3～8 个之间。

---

## 六、本期不要求填（避免过度投入）

- 任务级分解（把节点再往下拆到人、到周）
- 工期天数、工时、人力投入
- 成本/合同金额、付款条件
- 风险、质量、安全检查项
- 审批流与签认人名单（签认机制另行推进）
- 节点之间的权重、精细依赖（本期用「前置节点」文字表达即可）

以上字段后续版本按需扩展，届时单独发补充说明。

## 附录 B：与系统字段的对应关系（供汇总与系统对接参考，填报人无需关心）

| 本约定字段 | 系统字段 | 说明 |
|---|---|---|
| 节点编号 | `node_id` | 业务编号，直接入库 |
| 节点名称 | `node_name` | 直接入库 |
| 节点类型 | `node_type` | 里程碑→`MILESTONE`；任务→`TASK`。**填报值即最终类型**（系统不按结构改写） |
| 所属阶段 | `stage_id` | 立项=0；规划设计=1；工程施工=2；交付结算=3 |
| 上级节点 | `parent_node_id` | 由编号解析 |
| 责任部门 | `owner_dept_id` | 直接入库 |
| 计划时点 | `deadline` | 相对锚点需在实例化到具体项目时换算为日期 |
| 完成判定 / 备注 | `remark` | 取摘要 |
| 产物名称 / 必需性 / 数量单位 | `node_deliverables` | 逐条入库 |
| 文件识别特征 / 典型文件名 | 模板专用（不入库） | LLM 判断「上传文件是否属于该节点产物」的核心依据 |
| 前置节点 | `node_dependencies` | 自然语言描述，按名称匹配上游节点/产物 |
