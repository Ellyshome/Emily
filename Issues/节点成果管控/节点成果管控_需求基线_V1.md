## 一、背景与问题

### 1.1 业务诉求

原始意向（[节点成果管控.md](../节点成果管控.md)）原文：

> 所有事件，作为保底都可以上传，但有规划的任务节点，可以预定上传成果的审核标准。比如：一个'景观工程'节点下的'地面铺装施工'下的子任务'面层铺装'，要求上传的完工信息，不能只有谁、铺了多少，还要求对所上传工作量进行拍照。

即：**任务级可定制"完工必须带什么证据"（如完工位置照片）；缺证据时不拒绝录入，但必须让用户显式确认"缺证上传"。**

### 1.4 定性

这不是"加一个必填校验"，而是补上**成果管控的三层缺件**：

1. **定义层缺件**：成果上无法表达"完工要什么证据"；
2. **校验层缺件**：两条完工录入链路（成果提交 / 聊天事件）都不看证据；
3. **留痕层缺件**：缺证据放行这件事，系统里没有任何记录。

## 二、目标

| # | 目标 | 判定 |
|---|------|------|
| G1 | **可定制**：任一任务的成果可独立配置证据要求（如"需完工位置照片 ≥1 张"），未配置则行为与今天完全一致 | 配置后生效、不配置零影响 |
| G2 | **软校验**：完工录入时按要求检查，**不满足不拒绝** | 返回"需确认"而非报错 |
| G3 | **显式确认**：用户确认"缺证上传"后放行，且**该确认动作被记录** | 可回答"谁、何时、确认了哪条缺证上传" |
| G4 | **两条链路同一口径**：成果完工提交与聊天事件录入，用同一套证据要求与同一套确认语义 | 两条链路对同一成果判定一致 |
| G5 | **可被下游消费**：缺证状态对查询、节点进度与 Atlas 归属判定/签认可读 | 查询结果中可区分"证据齐备"与"缺证放行" |

## 三、范围

### 纳入

- 成果级"证据要求"的数据定义与配置入口（创建时随带 + 事后单独配置）；
- 成果完工提交链路（`submit_deliverable`）的软校验与缺证确认放行；
- 聊天事件录入链路（`record_event`）的软校验与缺证确认放行（含附件字段补齐）；
- 缺证放行的留痕（`node_events`）与状态标记；
- 缺证状态在成果/事件查询结果中的可读呈现；
- 消费既有死参数 `is_acceptance_check`，把"完工确认"语义真正接上。

### 不纳入（本期明确不做）

1. **不做硬门禁**：不允许出现"配了必须照片就绝对无法录入"的配置——按业务口径，保底始终可上传（用户已确认）；
2. **不做照片内容智能核验**：不判断"这张照片是不是真的完工位置、是不是拍的铺装"；
3. **不做照片数量/工作量自动对齐**：不校验"铺了 200 ㎡ 是否够 200 ㎡ 的照片"；
4. **不做缺证后的补交提醒与闭环催办**（可另立需求）；
5. **不做模板库 → 证据要求的自动映射**（本期只留字段，模板改造另立）；
6. **不改动节点三态状态机**：缺证放行**不影响**节点进度的计算口径（是否影响留待 PRD 定，见 §九 Q2）。

## 四、关键设计决策

> D1 / D2 已由用户拍板；D3 起为待评审建议。

| # | 决策项 | 结论 | 状态 |
|---|--------|------|------|
| **D1** | **证据要求的载体** | **落在成果表**：给 `node_deliverables` 增加证据要求列（JSON），节点/成果创建时可配置。不做独立"要求表"，不引入新聚合 | ✅ 已拍板 |
| **D2** | **校验触发点** | **两条链路都做**：① 成果完工提交（`submit_deliverable`）；② 聊天事件录入（`record_event`）。口径一致，不允许一条严一条松 | ✅ 已拍板 |
| **D3** | **校验强度** | **软校验 + 显式确认**：不满足时**不拒绝**，返回"需确认"；用户确认后以"缺证"标记放行。默认值恒为"允许缺证放行"，不提供"绝对阻断"选项 | 建议（与用户口径一致） |
| **D4** | **缺证语义的对外用词** | 建议主口径 **"缺证上传"**，备选"凭证暂缺 / 无图完工上报 / 缺件上报"。**用词未定，见 §九 Q1** | 待定 |
| **D5** | **配置权限** | 沿用既有节点写入口径：L5+ / 建设单位人员 / 节点责任人或创建人可配置；提交人无配置权 | 建议 |
| **D6** | **证据类型** | 本期只做 **"照片"** 一种（`require_photo`），"任意附件"与"指定文件类型"作为字段预留，不做校验 | 建议 |
| **D7** | **留痕位置** | 走既有 `node_events`（不可变事件流），新增事件类型 `deliverable_submitted_incomplete`；聊天链路同时在事件备注打缺证标记（复用现有 `[守护标记]` 风格） | 建议 |
| **D8** | **与"完工确认"的关系** | 消费既有死参数 `is_acceptance_check`：仅当该次提交被识别为"完工确认"时，才按证据要求校验（避免与"过程进度上报"混淆） | 建议（待 PRD 确认判定规则） |

## 五、功能需求（FR）

### FR-1 证据要求的数据定义
- 成果可携带证据要求，字段至少覆盖：是否需要照片、最少张数、给用户的提示语（如"完工位置照片"）。
- **默认为空**：未配置 = 无要求 = 现有行为不变（向后兼容硬要求）。
- 需给出 JSON 结构与缺省值（草案见 §六）。

### FR-2 配置入口一：创建任务时随带
- `create_task_node` 增加可选参数（如 `require_photo` / `evidence_hint`），创建 TASK 节点并自动落成果时一并写入。
- 不传则与今天一致。

### FR-3 配置入口二：对已有成果单独配置
- 提供配置/修改证据要求的能力（API 端点 + 工具口径），受 D5 权限约束。
- 已进入 CONFIRMED 的成果是否允许改配置，见 §九 Q3。

### FR-4 成果完工提交链路的软校验
- `submit_deliverable` 在既有校验之后追加证据校验：证据要求为空 → 直接通过；有要求且附件缺 → **不拒绝**，返回"需确认 + 缺什么"的结构化信号。
- **必须同时删除/激活死参数**：`is_acceptance_check` 要么被真正消费，要么明确下线，**不得继续以"传了但没人读"的状态存在**（宪法 §3 Q6 断线口径）。

### FR-5 缺证确认放行
- 用户在收到"需确认"提示后表达确认 → 带上确认标记再次提交 → **提交成功**，并：
  - 成果上标记证据状态（齐备 / 缺证放行）；
  - 写入 `node_events` 缺证事件（含确认人、时间、缺少项）；
  - 复用既有 pending / confirm 交互，不新造第二套确认存储。

### FR-6 聊天事件录入链路的软校验
- **前置补齐**：`record_event` 的入参需能携带照片/附件（今天完全没有该字段）。
- 归属到某节点/成果后，按其证据要求做同样的软校验与确认放行；事件备注打缺证标记。
- 若无法确定归属（落临时节点），是否校验见 §九 Q4。

### FR-7 缺证状态的可读呈现
- 成果列表 / 我的任务 / 节点详情中可区分"证据齐备"与"缺证放行"。
- 供 Atlas（归属判定、签认可信度）与后续查询消费。

### FR-8 留痕与追溯
- 可回答：**谁、在什么时候、为哪条成果/事件、确认了缺哪一项证据**。
- 留痕只增不改，与既有节点事件审计口径一致。

## 六、数据模型草案

### 6.1 已有表改动

| 表 | 改动 | 字段 | 说明 |
|---|------|------|------|
| `node_deliverables` | 新增列 | `evidence_requirements`（TEXT，default `''`） | JSON 字符串，空 = 无要求 |
| `node_deliverables` | 新增列 | `evidence_status`（VARCHAR(20)，default `''`） | `FULL`（齐备）/ `INCOMPLETE_CONFIRMED`（缺证放行）/ `''`（无要求） |

迁移按既有约定新增 `NNN_add_deliverable_evidence.sql`（[scripts 目录](../../emily-core/emily_core/infrastructure/database/scripts)）。

### 6.2 `evidence_requirements` 草案

```json
{
  "require_photo": true,
  "min_photo_count": 1,
  "hint": "完工位置照片",
  "allow_incomplete": true
}
```

| 字段 | 含义 | 缺省 |
|------|------|------|
| `require_photo` | 是否要求照片 | `false` |
| `min_photo_count` | 最少张数 | `1` |
| `hint` | 追问用户时的提示语 | `"完工照片"` |
| `allow_incomplete` | 是否允许缺证放行（**本期恒为 true**，字段预留） | `true` |

> 设计意图：`allow_incomplete` 存在但不提供 `false` 分支，是为了让"保底始终可上传"成为**显式声明**而非隐含假设；未来若要开硬门禁，只需改配置语义而不动表结构。

## 七、验收口径（基线级）

| # | 验收项 | 方式 | 预期 |
|---|--------|------|------|
| 1 | 向后兼容 | 未配置证据要求的成果走完提交→确认全流程 | 行为与今天完全一致 |
| 2 | 软校验不伤链路 | 配了"需照片"但提交不带附件 | **不报错**，返回"需确认 + 缺照片" |
| 3 | 确认后可放行 | 用户确认缺证后再提交 | 提交成功，`evidence_status=INCOMPLETE_CONFIRMED` |
| 4 | 有证据直接过 | 配了"需照片"且带附件提交 | 直接通过，`evidence_status=FULL` |
| 5 | 留痕可追溯 | 查 `node_events` | 有缺证事件，含确认人与缺少项 |
| 6 | 双链路同口径 | 同一成果分别从两条链路录入 | 判定与提示一致 |
| 7 | 死参数闭合 | 静态检索 `is_acceptance_check` | 定义处与消费处均存在（或已下线），**不允许仅 1 处** |
