# Agent 未回答问题 + 节点查询 0 结果根因分析

> 日期：2026-07-22
> 触发场景：`uv run python .claude/skills/emy-test/cli.py --managed --llm --message "我当前在什么全景节点里？" --sender "孙建国"`
> 测试用户：孙建国（level 2 参建执行，中天建设集团，岗位 `["施工员","班组长"]`，user_id=91bcc1d9-c084-4088-8b14-c4ada7d51393）

---

## 一、问题现象

用户问"我当前在什么全景节点里？"，收到回复：

> 您当前在翠湖庭院住宅小区项目的全景节点中，但系统未找到具体的节点名称。如需进一步确认，建议您通过项目全景视图查看当前所在位置。
>
> ⚠️ [reply] 回复声称用户在'翠湖庭院住宅小区项目'中，但执行步骤显示找到0个节点，存在幻觉

Guardian 自动标记了幻觉问题：回复声称用户"在"某项目中，但执行步骤实际找到 0 个节点。

---

## 二、直接原因：node4 LLM 回复合成失败 → 退回硬编码兜底（已修复）

### 2.1 链路

[workitem_agent.py:559](emily-core/emily_core/workitem/workitem_agent.py#L559) `_llm_synthesize_reply()` 回退链：LLM `chat_messages(json_mode=True)` → 取 `data.get("reply","")` → 若 `reply and len(reply) > 20` 则返回，否则退到硬编码兜底（line 647-651）。

硬编码兜底只报告统计数字，**完全丢弃了 `step_results` 里工具实际返回的节点信息**。

### 2.2 合成失败的三个 Bug（均已修复）

| Bug | 位置 | 现象 |
|-----|------|------|
| **A. `_build_tools_text` 调不存在的方法** | [workitem_agent.py:661](emily-core/emily_core/workitem/workitem_agent.py#L661) | `@staticmethod` 调 `BusinessFlowToolRegistry.get_instance()`，但该类无此方法（非单例，实例经 `self._business_flow_tools` 注入）。日志确认 `AttributeError`，prompt 的 `{available_tools}` 永远是"（无可用工具）" |
| **B. workitem.md 缺 JSON schema** | [workitem.md](emily-data/prompts/workitem.md) | 代码用 `json_mode=True` 取 `data.get("reply","")`，但 prompt 从没说要输出 `{"reply":"..."}`，LLM 可能用别的键 → reply 为空 |
| **C. 短回复静默退回无日志** | [workitem_agent.py:625](emily-core/emily_core/workitem/workitem_agent.py#L625) | `if reply and len(reply) > 20` 不满足时直接退兜底，不留日志 |

### 2.3 已实施修复

1. **Fix 1**：`_build_tools_text` 改实例方法，用 `self._business_flow_tools`（[workitem_agent.py:669](emily-core/emily_core/workitem/workitem_agent.py#L669)）
2. **Fix 2**：硬编码兜底优先返回最后一个成功 step 的 `output`（工具实际返回内容），而非统计数字（[workitem_agent.py:653](emily-core/emily_core/workitem/workitem_agent.py#L653)）
3. **Fix 3**：workitem.md 补 JSON 输出 schema `{"reply":"..."}`
4. **Fix 4**：LLM 合成短回复/缺键时补 warning 日志（[workitem_agent.py:628](emily-core/emily_core/workitem/workitem_agent.py#L628)）

### 2.4 验证结果

复测同一条消息，回复已变为实际内容（不再是"操作已完成！共执行 1 个步骤..."）。日志确认 `get_instance` 报错消失、LLM 合成成功。

## 三、独立问题：节点查询 0 结果 / 幻觉根因（待决策）

修复 node4 后，Guardian 仍标记了一个幻觉问题。深入排查发现这是**三层问题叠加**，不是 bug 而是架构层面的语义缺口。

### 3.1 第 1 层（核心）：系统没有"当前节点"概念 — 语义错配

用户问"我当前在什么全景节点里？"，隐含"我正处于某个节点中"的前提。但系统里**根本没有"当前/活跃节点"这个概念**。能间接回答的只有两个维度，且都不是"当前在哪个节点"：

| 维度 | 来源 | 孙建国的实际情况 | 能否回答"当前在哪个节点" |
|------|------|------------------|--------------------------|
| `authorized_node_ids` | [permission_service.py:420](emily-core/emily_core/services/permission_service.py#L420) `_derive_authorized_nodes(company)`，从 `company.function_scope` 解析，空则回退 `company.scope` | function_scope 空 → 回退 scope = `["主体施工","机电安装","装饰装修"]` | ❌ 这是**权限概念**（公司业务范围关键词），不是具体节点实例 |
| `responsible_user_id` | [node_task_tool.py:130](emily-core/emily_core/tools/node_task_tool.py#L130) `query_my_nodes` → `ProjectNodeRepo.find_by_responsible_user(user_id, status='IN_PROGRESS')` | 孙建国负责 **0 个**节点 | ❌ 查的是"我负责的节点"，不是"我当前所在的节点" |

### 3.2 第 2 层（数据）：孙建国未被指派为任何节点的责任人

数据库实测：

- 项目 `翠湖庭院住宅小区`（b460c78e-7721-4357-847d-2e0b43f07426）共 24 个节点
- **全部 24 个节点的 `responsible_user_id` = 王建国**（2d2b4eb1-653f-45c5-9590-362d6eb71ad7，level 6 系统管理员）
- 孙建国负责 0 个

所以 `query_my_nodes` 返回"找到 0 个节点"是**查询结果正确**——数据里确实没有指派给他的节点。这要么是节点指派数据未完善，要么是他的角色不映射到具体节点责任。

### 3.3 第 3 层（LLM 合成）：0 结果时用 session 上下文拼凑，产生误导

node4 合成回复时，LLM 手上有两个信息源：

- `step_results`："找到 0 个节点"
- session 上下文 `{project_name}` = "翠湖庭院住宅小区"（这个**不是幻觉**，DB 确认 b460c78e 就是这个名字）

LLM 把两者拼成了"您当前在翠湖庭院住宅小区项目的全景节点中，但系统未找到具体的节点名称"——前半句"当前在...全景节点中"与后半句"未找到节点"自相矛盾。Guardian 正确抓住了这个矛盾。

**注意**：项目名本身不是幻觉，幻觉在于"您当前在...全景节点中"这个基于 0 结果的推断。

### 3.4 根因总结

这不是一个 bug，而是**架构层面的语义缺口**：

1. **系统缺"当前节点"语义**：没有 `current_node_id` / `active_node` / `focus_node` 字段追踪用户正在哪个节点上工作。`authorized_node_ids` 是权限维度，`responsible_user_id` 是责任维度，都不是"当前所在"。

2. **`query_my_nodes` 语义不匹配用户意图**：用户问"我在哪"，工具查的是"我负责哪些"——0 结果时无法区分"你没负责任何节点" vs "你当前没在某个节点上"。

3. **数据未指派**：孙建国作为施工员/班组长，在 24 个节点上都不是责任人（全归王建国）。

4. **LLM 合成未约束 0 结果话术**：工具返回 0 时，LLM 从 session 上下文拿了项目名拼凑，产生矛盾表述。

## 四、可能的修复方向（待决策）

| 方向 | 内容 | 评估 |
|------|------|------|
| **A（治本）** | 引入"当前节点"概念——在 `users` 表或 session 中加 `current_node_id`，用户切换/进入节点时更新。新增 `get_current_node` 工具直接返回 | 改动大，涉及 DB schema + 业务流程，但从根本上解决语义缺口 |
| **B（治标，最小改动）** | 在 node4 合成 prompt 或 `query_my_nodes` 的 reply 里约束 0 结果话术——当返回 0 时明确说"您目前没有负责的在施节点"，禁止 LLM 用项目名拼凑"当前在...中" | 改动小，但只解决幻觉，没解决"无法回答当前节点" |
| **C（数据修复）** | 把孙建国指派为相关节点的责任人（如他岗位对应的"主体施工"类节点） | 治标，不解决语义缺口，其他用户仍会遇到 |
| **D（利用已有信息）** | 当 `query_my_nodes` 返回 0 时，回退用 `authorized_node_ids`/`scope` 回答"您的业务范围是 X、Y、Z，但当前没有指派给您负责的具体节点" | 中等改动，利用现有数据给出有意义的回答 |
