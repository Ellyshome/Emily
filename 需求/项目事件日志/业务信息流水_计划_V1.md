## 硬约束（违反即失败）

1. **分层不可跳**：`API → EmilyCore → Application → Service → Repository → DB`。新模块严格按此分层，工具层调 Service，Service 调 Repository，Repository 调 ORM
2. **业务内核独立**：`emily_core` 不 import 任何 `astrbot.*` 包（CLAUDE.md 约束 1）
3. **Sync repo + `asyncio.to_thread`**：Repository 全 sync，async Service/工具用 `asyncio.to_thread()` 包裹（CLAUDE.md 约束 6）
4. **工具必须带参数 schema**：新工具三步走——① tool 源文件定义 `_XXX_SCHEMA` 常量 → ② `registry.py` 注册时传 `params=_XXX_S` → ③ `tools_consistency.py` 的 `TOOL_SCHEMA_MAP` 添加映射（CLAUDE.md 约束 11）
5. **不修改已有方法签名**：`EventRepository.update_status`、`EventService.confirm_event`、`EventApplication.handle_confirmation` 均需扩展签名——本设计明确标注"修改接口签名"，通过新增带默认值的参数实现向后兼容
6. **`create_all()` 不 ALTER 已有表**：`events.confirmed_by` 新列必须在 `_PENDING_COLUMNS` 映射注册，由 `_ensure_columns()` 自动补齐（CLAUDE.md 踩坑速查）
7. **不新增 LangGraph 节点**：`query_project_journal` 作为 LLM 工具挂 ToolManager，由 executing 阶段 agent loop 自主调用，不改图结构（PRD D4）
8. **md 永远可由 DB 重生成**：不实时双写，不做增量强一致性保证（PRD D1/D5）
9. **每模块验收**：每个模块的验收检测必须通过，否则停止并报告

## 数据流设计

### 核心流程

| 流程 | 触发条件 | 参与者 | 数据流向 | 异常路径 |
|------|---------|--------|---------|---------|
| 事件认证（修复后） | 用户回复"确认" | SessionAgent→EventApp→EventService→EventRepo→DB | actor_user_id 透传 → 写 events.confirmed_by + business_event_logs.user_id=认证人 | 透传失败时回退为 event.user_id（兼容旧路径）+ warning |
| LLM 查询台账 | 用户问"昨天谁报的" | executing agent loop → query_project_journal 工具 → ProjectJournalService → Repository → DB | 工具返回结构化 entries → LLM 合成回复 | 工具异常返回 error dict，LLM 据 error 回复"查询失败" |
| 录入上下文增强 | 用户发"录入7#楼铺装完工" | executing agent loop →（LLM 自主决定）query_project_journal → record_event | 查历史作为上下文 → 再调录入工具 | LLM 不调用查询工具 → 直接录入（非阻断，仅缺历史提示） |
| md 导出 | 用户发"导出今天台账" | executing agent loop → export_project_journal 工具 → ProjectJournalService.export_to_file → 文件系统 | 返回 {path, entries, mode} → LLM 回复路径 | 文件写入失败 → 工具返回 error，LLM 提示重试 |

## M1: DB 字段补齐 + BUG 修复

**依赖**：无（首建模块）

**层级**：跨层（ORM / Repository / Service / Application / Session）

**职责**：补齐 `events.confirmed_by` 字段，修复认证人被记为录入人的 BUG，使认证操作人可溯。

### 接口契约

#### 对外接口（签名扩展——均通过新增带默认值参数实现向后兼容）

| 接口/方法 | 类型 | 签名 | 说明 |
|-----------|------|------|------|
| `EventRepository.update_status` | 修改 | `update_status(event_id: str, status: str, confirmed_by: str = "") -> None` | confirmed 分支额外写 `event.confirmed_by = confirmed_by` |
| `EventService.confirm_event` | 修改 | `confirm_event(event_id: str, actor_user_id: str = "") -> Optional[Event]` | 透传 `actor_user_id` 给 `repo.update_status` |
| `EventApplication.handle_confirmation` | 修改 | `handle_confirmation(event_id: str, action: str, actor_user_id: str = "") -> HandlerResult` | confirm 分支：`event_service.confirm_event(event_id, actor_user_id)` + `_log_business_event(user_id=actor_user_id or event.user_id)` |
| `SessionAgent._handle_confirm` | 修改 | 内部调用 `handle_confirmation(event_id, action, actor_user_id=self._current_actor["user_id"])` | 从已有 `self._current_actor` 取认证操作人 |

#### 依赖接口（本模块需要调用哪些已有接口）

| 现有接口 | 来源模块 | 调用目的 |
|----------|---------|---------|
| `self._current_actor["user_id"]` | SessionAgent（已有，BUG-005 群聊修复遗留） | 获取当前认证操作人 UUID |

### 数据模型

#### 已有表改动

| 表名 | 改动 | 新增字段/索引 |
|------|------|-------------|
| `events` | 新增字段 | `confirmed_by VARCHAR DEFAULT ''` —— FK 软关联 → users.id，记录认证操作人 |

#### `_PENDING_COLUMNS` 映射注册

在 [session.py](emily-core/emily_core/infrastructure/database/session.py#L61) 的 `_PENDING_COLUMNS` 字典追加：

```
"events": [
    ("confirmed_by", "VARCHAR", "''"),
]
```

> **设计约束**：参照现有 `"files"` / `"hook_execution_logs"` 条目格式。`_ensure_columns()` 启动时检查 information_schema，缺失则 `ALTER TABLE events ADD COLUMN confirmed_by VARCHAR DEFAULT ''`。

## M2: ProjectJournalRepository

**依赖**：M1

**层级**：Repository

**职责**：跨表合并时间线查询——从 `events` + `node_deliverables` 读认证类动作，批量解析用户/公司信息，返回统一格式的台账条目。

### 接口契约

#### 对外接口

| 接口/类 | 类型 | 签名 | 说明 |
|---------|------|------|------|
| `ProjectJournalRepository` | 类 | — | 纯读 Repository，@staticmethod 风格（参照 `ProjectNodeRepo`） |
| `query_event_entries` | 方法 | `query_event_entries(*, project_id: str = "", project_ids: list[str] | None = None, date_from: str = "", date_to: str = "", auth_status: str = "", user_id: str = "", limit: int = 200) -> list[dict]` | 查 events 表的 created + confirmed 动作，返回原始 dict 列表 |
| `query_deliverable_entries` | 方法 | `query_deliverable_entries(*, project_id: str = "", project_ids: list[str] | None = None, date_from: str = "", date_to: str = "", auth_status: str = "", user_id: str = "", limit: int = 200) -> list[dict]` | 查 node_deliverables 表的 submitted + confirmed 动作（JOIN project_nodes 取 project_id） |
| `resolve_users_batch` | 方法 | `resolve_users_batch(user_ids: list[str]) -> dict[str, dict]` | 批量解析 user_id → {name, company_name, company_type, position}，避免 N+1 |

#### 返回的 dict 结构（统一）

`query_event_entries` 单条 dict：

| 字段 | 类型 | 说明 |
|------|------|------|
| `timestamp` | str | ISO8601（created 用 `created_at`，confirmed 用 `confirmed_at`） |
| `entry_type` | str | `event_created` / `event_confirmed` |
| `target_no` | str | `event_no` |
| `target_id` | str | `event.id` |
| `summary` | str | `event.title` |
| `recorder_user_id` | str | `event.user_id`（录入人） |
| `auth_user_id` | str | `event.confirmed_by`（认证人，可能为空） |
| `auth_status` | str | `event.status`（pending/confirmed/cancelled） |
| `project_id` | str | `event.project_id` |
| `remark` | str | `event.remarks` 或从 payload 提取 |

`query_deliverable_entries` 单条 dict：

| 字段 | 类型 | 说明 |
|------|------|------|
| `timestamp` | str | submitted 用 `submitted_at`，confirmed 用 `confirmed_at` |
| `entry_type` | str | `deliverable_submitted` / `deliverable_confirmed` |
| `target_no` | str | `deliverable_id` |
| `target_id` | str | `NodeDeliverable.id` |
| `node_id` | str | 所属节点 `node_id`（JOIN project_nodes） |
| `summary` | str | `deliverable_name` + `current_amount`/`target_amount` + `unit` |
| `recorder_user_id` | str | `submitted_by` |
| `auth_user_id` | str | `confirmed_by` |
| `auth_status` | str | `submission_status`（PENDING/SUBMITTED/CONFIRMED/RETURNED） |
| `project_id` | str | `project_nodes.project_id`（JOIN 得到） |
| `remark` | str | `return_reason`（如有） |

#### 依赖接口

| 现有接口 | 来源模块 | 调用目的 |
|----------|---------|---------|
| `Event` ORM | models.py | events 表查询 |
| `NodeDeliverable` / `ProjectNode` ORM | models.py | node_deliverables + project_nodes JOIN |
| `User` / `UserImBinding` / `CompanyInfo` ORM | models.py | 批量解析用户/公司 |
| `get_session()` | session.py | DB 会话上下文 |

### 核心算法/策略

| 算法/策略 | 用途 | 选型理由 | 备选方案 |
|----------|------|---------|---------|
| 两表分别查 + Service 层合并排序 | 时间线合并 | events 与 node_deliverables 字段差异大，DB UNION 需对齐列类型复杂；Python 层 `sorted(key=timestamp)` 简单且 limit 内可控 | DB UNION ALL——字段对齐成本高，放弃 |
| 批量预取用户字典 + 内存 JOIN | resolve_users_batch 避免 N+1 | 单次查询可能返回 200+ 条目，逐条查用户会产生 N+1；先收集所有 user_id，一次 `WHERE id IN (...)` 查出，再内存匹配 | ORM `joinedload`——跨表关系复杂，events.user_id 是软关联无 FK，不适用 |
| 日期按北京时间解释 | date_from/date_to 语义统一 | 现有 `EventRepository.query_events` 用 UTC，但台账面向用户读，需北京时间；查询时 `date_from + 08:00` 转 UTC 做过滤 | 全 UTC + 前端转换——增加复杂度 |

## M3: ProjectJournalService

**依赖**：M2

**层级**：Service

**职责**：调用 M2 查询台账条目，合并时间线，渲染 md，导出文件。对外提供 `query` / `render_md` / `export_to_file` 三个方法。

### 接口契约

#### 对外接口

| 接口/类 | 类型 | 签名 | 说明 |
|---------|------|------|------|
| `ProjectJournalService` | 类 | — | 台账服务，参照 `EventService` 实例化风格 |
| `query` | 方法 | `async def query(*, project_id: str = "", project_ids: list[str] = None, date_from: str = "", date_to: str = "", entry_types: list[str] = None, auth_status: str = "", user_id: str = "", keyword: str = "", limit: int = 100) -> list[JournalEntry]` | 合并 M2 两表查询 + keyword 模糊匹配 + 用户/公司解析 + 时间排序 |
| `render_md` | 方法 | `def render_md(entries: list[JournalEntry], *, project_name: str, date_str: str) -> str` | 纯函数，渲染 md 字符串（参照 PRD §4.5 格式） |
| `export_to_file` | 方法 | `async def export_to_file(*, project_id: str, project_name: str, date_str: str = "", date_range: tuple[str,str] = (), mode: str = "full") -> dict` | 写 md 文件，返回 {path, entries, mode} |

#### DTO 定义

| DTO | 字段 | 用途 | 流向 |
|-----|------|------|------|
| `JournalEntry` | `timestamp: str` / `entry_type: str` / `summary: str` / `recorder: dict` / `auth: dict` / `target: dict` / `remark: str` | 统一台账条目（PRD §6.1） | M2 dict → M3 entry → M4 返回 / md 渲染 |

`recorder` / `auth.auth_user` 结构：`{"user_id": str, "name": str, "company": str, "role": str}`（由 `resolve_users_batch` 填充）。

#### 依赖接口

| 现有接口 | 来源模块 | 调用目的 |
|----------|---------|---------|
| `ProjectJournalRepository` | M2 | 查询 events + deliverables + 解析用户 |
| `ProjectRepository.find_by_id` | 现有 | 导出时取项目名（若调用方未传） |
| `config.project_journal_export_dir` | Config | md 文件目录 |
| `config.project_journal_max_entries` | Config | 单次导出上限 |

### 核心算法/策略

| 算法/策略 | 用途 | 选型理由 | 备选方案 |
|----------|------|---------|---------|
| append 模式去重键 = `target.no + entry_type` | 增量导出去重 | event_no / deliverable_id 全局唯一，+entry_type 区分 created/confirmed 两条 | 用 target_id——但 UUID 不如业务编号可读 |
| md 渲染按 timestamp 升序 | 时间线可读性 | 用户翻阅台账是按时间顺序 | 按类型分组——破坏时间线，放弃 |
| 文件路径 `{export_dir}/{project_id}/{YYYY-MM}/{YYYY-MM-DD}.md` | 分项目+日期切片（PRD D2） | 单项目单日文件大小可控；分年月避免单目录文件过多 | 全项目混一份——检索不便，放弃 |
| query 为 async + `asyncio.to_thread` 包裹 M2 sync 调用 | 分层约束 #6 | Repository 全 sync，Service 用 to_thread 包裹 | 全 async Repository——违反约束 #6 |

## M4: LLM 工具层

**依赖**：M3

**层级**：Tool 层（BusinessFlowTool handler）

**职责**：定义 `query_project_journal` / `export_project_journal` 两个工具 handler + schema，注册到 ToolManager。

### 接口契约

#### 对外接口（工具 handler）

| 接口/类 | 类型 | 签名 | 说明 |
|---------|------|------|------|
| `handle_query_project_journal` | async 函数 | `async def handle_query_project_journal(params: dict, **kw) -> dict` | 调 `ProjectJournalService.query()`，返回 {success, entries, count} |
| `handle_export_project_journal` | async 函数 | `async def handle_export_project_journal(params: dict, **kw) -> dict` | 调 `export_to_file()`，返回 {success, path, entries, mode} |
| `_QUERY_JOURNAL_SCHEMA` | 常量 | dict（JSON Schema） | 工具参数 schema，见下方 |
| `_EXPORT_JOURNAL_SCHEMA` | 常量 | dict（JSON Schema） | 工具参数 schema，见下方 |

#### `_QUERY_JOURNAL_SCHEMA` 结构

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `project_id` | string | 否 | 项目 UUID（不知则先调 resolve_project） |
| `date_from` | string | 是 | 起始日期 YYYY-MM-DD（北京时间） |
| `date_to` | string | 否 | 结束日期，单日查询与 date_from 相同 |
| `entry_types` | array[string] | 否 | event_created/event_confirmed/deliverable_submitted/deliverable_confirmed |
| `auth_status` | string enum | 否 | pending/confirmed/all |
| `keyword` | string | 否 | 模糊匹配 summary |

#### `_EXPORT_JOURNAL_SCHEMA` 结构

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `project_id` | string | 是 | 项目 UUID |
| `date_str` | string | 否 | 单日 YYYY-MM-DD，空则今天 |
| `date_from` / `date_to` | string | 否 | 范围导出 |
| `mode` | string enum | 否 | full（默认）/ append |

#### 工具描述（注入 LLM prompt，关键）

`query_project_journal` 描述必须含两种调用场景（PRD §5.2）：
1. 用户主动查询历史
2. 录入类 SOP 执行前上下文增强

#### 依赖接口

| 现有接口 | 来源模块 | 调用目的 |
|----------|---------|---------|
| `ProjectJournalService` | M3 | 实际业务 |
| `_reg_biz` / `_tool` / `_h` | registry.py | 工具注册 |
| `session_ctx.project_ids` | SessionContext | 权限过滤（三层权限第二层，参照 `ProjectResolver`） |

### 核心算法/策略

| 算法/策略 | 用途 | 选型理由 | 备选方案 |
|----------|------|---------|---------|
| 权限过滤：handler 内用 `session_ctx.project_ids` 约束 | 三层权限第二层 | 参照 `ProjectResolver.handle` 模式——若 `project_id` 不在 session 可见集合内，返回 found=false 不泄漏；`project_id` 为空时只查可见项目 | 全表查——违反权限模型 |
| handler 不直接 new Service，由 registry 注入 | 与现有工具一致 | 参照 `record_event` 的 `partial(_h(...), event_app=core._event_app)` 模式，Service 实例由 `EmilyCore` 创建并注入 | handler 内 new——破坏 DI 一致性 |

### 工具注册（registry.py 追加）

在 `_register_business` 末尾追加（参照专家库工具注册段）：

```
from .project_journal_tool import (
    handle_query_project_journal, handle_export_project_journal,
    _QUERY_JOURNAL_SCHEMA, _EXPORT_JOURNAL_SCHEMA,
)
pjs = getattr(core, "_project_journal_service", None)
if pjs is not None:
    _buc += _reg_biz(reg, "query_project_journal", "查询项目业务台账（历史事件与认证记录）",
                     partial(handle_query_project_journal, journal_service=pjs),
                     params=_QUERY_JOURNAL_SCHEMA, category="base", permission_flag="all")
    _buc += _reg_biz(reg, "export_project_journal", "导出项目业务台账为md文件",
                     partial(handle_export_project_journal, journal_service=pjs),
                     params=_EXPORT_JOURNAL_SCHEMA, category="business", permission_flag="write")
```

> **设计约束**：`category="base"` 让 `query_project_journal` 对所有 SOP 开放（PRD §5.5 上下文增强需要）；`export_project_journal` 用 `category="business"` + `permission_flag="write"`（L3+ 工程师以上）。

`EmilyCore.__init__` 需新增 `self._project_journal_service = ProjectJournalService()`（参照 `self._event_app` 初始化位置）。

## 阶段反思指令

每完成一个模块的设计，在进入下一个模块之前，执行以下反思：

1. **检查设计完整性**：本模块的接口契约、数据模型、验收检测是否完整
2. **检查设计偏差**：是否有与 PRD 不符的设计？记录差异
3. **判断是否继续**：
   - 如果偏差 ≤ 1 个接口调整 → 直接修改设计文档对应模块，继续
   - 如果偏差 2-4 个接口或模块职责调整 → 在设计文档末尾追加 "v1.1 修订记录"，继续
   - 如果偏差 > 4 个接口或架构方向变化 → **停止**，报告给用户，等用户决定是否重新生成设计
