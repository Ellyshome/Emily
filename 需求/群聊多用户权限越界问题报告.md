# 群聊多用户权限越界问题报告

> **发现日期**：2026-07-26
> **严重级别**：高 — 权限逃逸 + 操作归属错误
> **影响范围**：所有群聊场景，多用户轮流 @机器人 时触发
> **关联功能**：SessionPool 路由、SessionContext 权限快照、AuthHook 鉴权

---

## 问题概述

Emily 群聊中，**第一个 @机器人 的用户的权限会被"锁定"为整个群 Session 的权限基准**。后续其他用户 @机器人 时，继承第一个用户的权限级别，而非使用自身的实际权限。

---

## 复现路径

```
1. 管理员 A (L6) 在群内 @Emily 创建了一个事件
   → SessionContext 以 A 的身份创建：level=6, sop_allow=["all"]

2. 施工员 B (L2) 紧接着 @Emily 尝试删除该事件
   → 预期：AuthHook 拒绝 (B 无删除权限)
   → 实际：AuthHook 通过 (因为 SessionContext.level=6，是 A 的权限)
```

---

## 根因分析

### 根因一：群聊 conversation_id = group_id，所有人共享一个 Session

在 [inbound_adapter.py](file:///d:/app/Emily/data/plugins/emily_agent/adapters/astrbot/inbound_adapter.py) 中：

```python
conversation_id = group_id or sender_id  # 群聊时 = group_id
```

这意味着群内所有成员共享同一个 `conversation_id`，SessionPool 以此作为唯一 key。

### 根因二：SessionPool.route() 对已有 Session 忽略 user_id

在 [session_pool.py](file:///d:/app/Emily/emily-core/emily_core/adapters/session/session_pool.py#L112-L127) 中：

```python
async def route(self, message, user_id="", db_message_id=""):
    conv_id = message.conversation_id
    entry = self._sessions.get(conv_id)
    if entry is None:
        # 新 Session：user_id 被传入 SessionFactory
        agent = self._factory.create(message, user_id=user_id)
    else:
        # 已有 Session：user_id 被忽略 ← 问题所在
        pass
    return await entry.agent.handle(message, db_message_id=db_message_id)
```

### 根因三：SessionContext 创建后不可变

在 [session_context.py](file:///d:/app/Emily/emily-core/emily_core/session/session_context.py) 中，`SessionContext.create(user_id)` 初始化时一次性加载该用户的全部权限快照（level、sop_allow、authorized_node_ids 等），此后不再随消息更新。

### 根因四：WorkItem 归属写死为 SessionContext 的 user_id

在 [session_agent.py](file:///d:/app/Emily/emily-core/emily_core/session/session_agent.py) 的 `_split_into_workitems()` 中，所有新创建的 WorkItem 均使用 `user_id=self.context.user_id`，即第一个用户的 ID。后续无论谁 @bot，WorkItem 都记录为第一个用户的操作。

---

## 影响分析

| 影响维度 | 严重程度 | 说明 |
|----------|---------|------|
| **权限控制** | 严重 | 低权限用户可越权执行高权限操作（删除、系统配置修改等） |
| **审计追溯** | 严重 | 操作记录归属到错误用户，无法追责 |
| **数据安全** | 中等 | SOP 白名单被绕过，用户可执行本无权访问的流程 |
| **功能正确性** | 中等 | Context 刷新时刷新的是第一个用户的权限，非当前操作者 |

## 当前 Session 生命周期的完整问题链路

```
群聊 group_001:
  ┌─────────────────────────────────────────────────────────────┐
  │                                                            │
  │  T1: 用户A(L6) @bot                                        │
  │   → handle_message: sender_id→user_id=A ✓                  │
  │   → SessionPool: 新session, factory.create(user_id=A)      │
  │   → SessionContext: level=6, sop_allow=["all"]              │
  │   → AuthHook: level=6 通过 ✓                                │
  │   → WorkItem: user_id=A ✓                                  │
  │                                                            │
  │  T2: 用户B(L2) @bot                                        │
  │   → handle_message: sender_id→user_id=B ✓                  │
  │   → SessionPool: 命中已有session, user_id=B 被忽略 ✗        │
  │   → SessionContext: 仍是 level=6, sop_allow=["all"] ✗       │
  │   → AuthHook: level=6 通过 ✗ (应为L2拒绝)                   │
  │   → WorkItem: user_id=A ✗ (应记录B)                        │
  │                                                            │
  └─────────────────────────────────────────────────────────────┘
```

## 候选方案

### 方案 A：复合 Session Key（`conversation_id + user_id`）

将 SessionPool 的 key 从 `conversation_id` 改为 `(conversation_id, user_id)` 二元组。

| 优点 | 缺点 |
|------|------|
| 权限完全隔离，每个用户独立 Session | 群聊上下文断裂——A 和 B 无法在同一对话中协作 |
| 改动集中在 SessionPool 层 | 内存消耗增加（N 个用户 = N 个 Session） |

### 方案 B：每条消息动态替换 SessionContext

保持 Session 的 `conversation_id` key 不变，但在 `SessionAgent.handle()` 入口处根据当前 `sender_id` 动态刷新 SessionContext 中的权限快照。

| 优点 | 缺点 |
|------|------|
| 保留群聊上下文连续性 | 需要每次重新查询权限数据 |
| Session 数量不膨胀 | 改动面大（SessionAgent + WorkItem 的 user_id 写入处都需要改） |
| | Context 刷新后之前用户的权限记忆消失，prompt 需要重新渲染 |

### 方案 C：混合方案 — Session 共享上下文 + WorkItem 独立鉴权

Session 保持群共享（维护对话上下文），但在 WorkItem 创建和 AuthHook 执行时使用当前消息的真实 `user_id` 鉴权，而非 SessionContext 中的 user_id。

| 优点 | 缺点 |
|------|------|
| 兼顾上下文连贯性和权限正确性 | 需要改造 PipelineBUS 和 AuthHook 的 user_id 来源 |
| Session 数量不膨胀 | WorkItem 调度器需接受独立 user_id |

### 方案 D：当前不修复，记录为已知限制

在文档中标注：群聊多用户权限隔离为已知限制，当前版本群聊假定为单用户或同权限组成员使用。

| 优点 | 缺点 |
|------|------|
| 零改动成本 | 存在安全风险，不适合面向权限分级的真实团队群聊 |

## 讨论建议

1. Emily 的实际群聊使用模式是什么？群内用户权限是否同质（均为同级别项目成员）？
2. 如果权限差异确实存在，方案 C（Session 共享上下文 + WorkItem 独立鉴权）看起来代价最小且兼顾两面，建议优先评估
3. 方案 A 简单但会破坏群聊的对话连续性——如果群聊本就是"每人各自办事"而非"协作讨论"，这反而是优势
