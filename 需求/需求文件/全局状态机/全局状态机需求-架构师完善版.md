## 一、概述
### 1.1 项目背景
本系统定位为**地产单项目的AI团队大脑**，作为项目业务管理的核心基础设施。全局状态机是AI感知项目状态、进行智能决策、触发自动化行动的**核心神经系统**。

### 1.2 设计目标
- ✅ **可感知**：AI能准确知道项目当前"在什么状态"
- ✅ **可预测**：AI能推演"如果X发生，会导致什么结果"
- ✅ **可控制**：人类能清晰地干预、审批、回溯
- ✅ **可扩展**：支持不同项目的节点定制化
- ✅ **可审计**：所有变更全程可追溯

## 二、整体架构设计
### 2.1 分层架构原则
采用**"脉络层-节点层-数据层"**三级树状架构：

```
┌─────────────────────────────────────────────────────────────┐
│                        脉络层（宏观）                         │
│  阶段级状态机：6个阶段整体状态、阶段间流转关系、里程碑进度     │
├─────────────────────────────────────────────────────────────┤
│                        节点层（中观）                         │
│  88个标准节点状态机：节点状态、依赖关系、责任人、成果物        │
├─────────────────────────────────────────────────────────────┤
│                        数据层（微观）                         │
│  数据库索引 + 文档库索引 + 公共记忆库 + 审计日志              │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 四大核心子模块

| 子模块 | 定位 | 是否使用状态机 | 核心职责 |
|--------|------|---------------|----------|
| **全景进程模块** | 核心状态引擎 | ✅ 完整状态机 | 管理88个节点的全生命周期 |
| **数据库索引** | 元数据目录 | ❌ 纯静态 | 提供表结构、字段含义、关联关系查询 |
| **文档库索引** | 文档元数据 | 🤔 轻量状态机 | 管理文档元数据+审批流程 |
| **公共记忆库** | AI记忆管理 | ✅ 完整状态机 | 管理记忆的生命周期、有效性、影响范围 |

## 三、状态机核心设计规范
### 3.1 状态机7大核心要素
所有状态机必须完整定义以下7项：

| 要素 | 说明 | 约束要求 |
|------|------|----------|
| **1. 状态枚举** | 所有可能的状态 | 必须用Enum，禁止自由字符串 |
| **2. 转移矩阵** | 状态间合法转移路径 | 禁止循环依赖、禁止终态回退 |
| **3. 触发条件** | 每个转移的前置判断 | 必须可量化、可程序化判断 |
| **4. 依赖关系图** | 节点间的依赖网络 | 必须是有向无环图(DAG) |
| **5. 钩子函数** | 进入/离开/转移时的动作 | 必须幂等、可重试 |
| **6. 权限约束** | 谁能操作这个转移 | 最小权限原则 |
| **7. 异常处理** | 违反规则时怎么办 | 必须记录审计日志 |

### 3.2 标准状态枚举
所有节点统一使用以下5种状态：

```python
class NodeStatus(Enum):
    NOT_STARTED = "未启动"      # 初始状态，前置条件不满足
    IN_PROGRESS = "进行中"      # 前置条件满足，正在执行
    BLOCKED = "已阻塞"          # 遇到阻碍，无法继续推进
    DELAYED = "已延期"          # 超过计划完成时间
    COMPLETED = "已完成"        # 终态，所有成果已验收归档
```

### 3.3 标准状态转移矩阵

| 当前状态 | 允许转移到 | 触发条件 | 所需权限 |
|----------|-----------|----------|---------|
| 未启动 | 进行中 | 前置条件满足度≥100% | 节点责任人 |
| 进行中 | 已完成 | 所有成果归档 + 责任人确认 | 节点责任人 + 审批人 |
| 进行中 | 已阻塞 | 阻塞因子≥50% | 节点责任人 |
| 进行中 | 已延期 | 当前时间 > 计划完成时间 | 系统自动触发 |
| 已阻塞 | 进行中 | 阻塞因子＜30% | 节点责任人 |
| 已阻塞 | 已延期 | 当前时间 > 计划完成时间 | 系统自动触发 |
| 已延期 | 进行中 | 风险解除，重新启动 | 项目经理审批 |
| 已延期 | 已完成 | 所有成果归档 + 延期说明 | 项目经理审批 |
| 已完成 | - | 终态，禁止任何转移 | 禁止任何人操作 |

## 四、全景进程模块详细设计
### 4.1 节点数据结构

```typescript
interface ProjectNode {
    // ========== 基础信息 ==========
    nodeId: string;              // 节点编号，如 "2.6.1"
    nodeName: string;            // 节点名称
    stage: string;               // 所属阶段
    
    // ========== 状态机核心 ==========
    status: NodeStatus;          // 当前状态
    plannedStartDate: Date;      // 计划开始时间
    plannedEndDate: Date;        // 计划完成时间
    actualStartDate?: Date;      // 实际开始时间
    actualEndDate?: Date;        // 实际完成时间
    
    // ========== 人员与权限 ==========
    owner: string;               // 责任人ID
    approver?: string;           // 审批人ID（完成需要）
    viewer: string[];            // 可查看人员列表
    
    // ========== 依赖关系 ==========
    dependencies: {              // 前置依赖节点
        nodeId: string;
        weight: number;          // 依赖权重 0-1
        required: boolean;       // 是否强依赖
    }[];
    downstream: string[];        // 后续节点
    
    // ========== 成果物 ==========
    deliverables: {
        name: string;
        required: boolean;       // 是否必填
        uploaded: boolean;       // 是否已上传
        fileId?: string;
    }[];
    
    // ========== 运行时数据 ==========
    preconditionScore: number;   // 前置条件满足度 0-100%
    blockReason?: string;        // 阻塞原因
    delayReason?: string;        // 延期原因
    riskLevel: "正常" | "关注" | "高风险";
}
```

### 4.2 脉络层数据结构

```typescript
interface ProjectStage {
    stageId: string;             // 阶段编号 1-6
    stageName: string;
    status: "未启动" | "进行中" | "已完成";
    totalNodes: number;
    completedNodes: number;
    progress: number;            // 阶段完成率 0-100%
    milestone: boolean;          // 是否里程碑阶段
    criticalPath: string[];      // 本阶段关键路径节点
}
```

### 4.3 节点依赖计算规则

**前置条件满足度计算公式：**
```
满足度 = Σ(前置节点状态系数 × 依赖权重)

其中状态系数：
  已完成 = 1.0
  进行中且进度>80% = 0.8 （弱依赖可提前启动）
  进行中且进度≤80% = 0.5
  其他状态 = 0
```

**强依赖约束：** 任何强依赖节点非"已完成"时，满足度最高只能到99%，不允许启动。

## 五、钩子函数与级联更新机制
### 5.1 标准钩子定义

每个状态变更自动触发以下三类钩子：

| 钩子类型 | 触发时机 | 标准动作清单 |
|----------|---------|-------------|
| **on_enter** | 进入某状态时 | 通知相关人员、初始化数据、更新依赖节点 |
| **on_exit** | 离开某状态时 | 检查数据完整性、计算耗时、记录对比 |
| **on_transition** | 特定转移发生时 | 特殊审批、风险标记、审计记录 |

### 5.2 标准钩子实现

```python
# ==================== 进入状态钩子 ====================
def on_enter_IN_PROGRESS(node):
    """节点启动时"""
    发送消息通知责任人(node.owner, f"节点【{node.name}】已启动")
    记录实际开始时间(node)
    创建节点任务清单(node)

def on_enter_COMPLETED(node):
    """节点完成时"""
    生成节点验收报告(node)
    更新所有后续节点的前置满足度(node.downstream)
    计算阶段完成率(node.stage)
    检查是否触发里程碑(node)
    记录审计日志(node, "完成节点")

def on_enter_BLOCKED(node):
    """节点阻塞时"""
    发送阻塞预警给项目经理(node)
    暂停所有依赖此节点的后续任务
    标记项目风险等级提升

def on_enter_DELAYED(node):
    """节点延期时"""
    发送延期预警(node.owner, 项目经理)
    自动推演对关键路径的影响
    生成延期影响分析报告

# ==================== 离开状态钩子 ====================
def on_exit_IN_PROGRESS(node):
    """离开进行中时"""
    计算节点实际耗时与计划对比
    检查所有输出成果完整性
```

### 5.3 级联更新传播机制

当节点状态变更时，采用**BFS广度优先遍历**进行级联更新：

```
节点A完成
  ↓
更新所有直接下游节点（B、C、D）的满足度
  ↓
检查每个下游是否达到启动条件
  ↓
达到条件的自动变更为"进行中"
  ↓
继续传播到下一级（E、F、G）
  ↓
直到没有新节点被激活
```

**传播停止条件：**
- 没有新节点状态发生变化
- 或传播深度超过5级（防止无限循环）

## 八、公共记忆库模块设计
### 8.1 定位与边界
✅ **完整状态机，这是AI Agent的核心记忆系统**  
记忆不是写进去就永远正确的，它有生命周期，会过期、被推翻、产生影响。

### 8.2 记忆状态机

```
记忆状态流转：
  活跃有效 → 已更新 → 活跃有效
              ↓
            已过期（时间到期）
              ↓
            被推翻（新记忆否定旧记忆）
              ↓
            已归档（历史参考）
```

### 8.3 数据结构

```typescript
interface PublicMemory {
    memoryId: string;
    content: string;             // 记忆内容
    source: string;              // 来源：会议记录/决策文件/人工输入
    sourceDocId?: string;        // 来源文档
    author: string;              // 创建人
    createTime: Date;
    expiryTime?: Date;           // 过期时间（如果有时效性）
    status: "活跃有效" | "已更新" | "已过期" | "被推翻" | "已归档";
    references: string[];        // 哪些节点/Agent引用了这条记忆
    replacedBy?: string;         // 被哪条新记忆取代
    confidence: number;          // 可信度 0-100%
    tags: string[];              // 分类标签
}
```

### 8.4 级联影响机制
当记忆被推翻时，状态机自动：
1. 找到所有引用过这条记忆的AI会话
2. 标记受影响的节点决策需要重新评估
3. 通知相关责任人检查
4. 生成影响范围报告

## 九、权限与审计机制
### 9.1 权限矩阵

| 操作 | 节点责任人 | 项目经理 | 系统管理员 | AI Agent |
|------|-----------|---------|-----------|----------|
| 查看节点状态 | ✅ | ✅ | ✅ | ✅ |
| 启动节点（未启动→进行中） | ✅ | ✅ | ❌ | ✅（需人工确认） |
| 完成节点（进行中→已完成） | ✅（需审批） | ✅审批 | ❌ | ✅（需审批） |
| 标记阻塞/延期 | ✅ | ✅ | ❌ | ✅ |
| 强制跳过约束 | ❌ | ✅（需记录风险） | ✅ | ❌ |
| 修改节点依赖关系 | ❌ | ✅ | ✅ | ❌ |
| 回滚状态变更 | ❌ | ❌ | ✅ | ❌ |

### 9.2 审计日志规范
所有操作必须记录以下信息：

```typescript
interface AuditLog {
    logId: string;
    timestamp: Date;
    operator: string;            // 操作人/Agent
    targetType: "node" | "memory" | "document";
    targetId: string;
    action: string;              // 操作类型
    oldValue?: any;              // 变更前值
    newValue?: any;              // 变更后值
    reason?: string;             // 操作原因
    riskMarked?: boolean;        // 是否标记风险
    clientInfo: {                // 操作来源
        ip: string;
        userAgent: string;
    };
}
```

### 9.3 审批流程
**节点完成审批链：**
```
责任人提交完成申请
    ↓
状态机自动校验：成果齐全？前置完成？
    ↓ ↓ ↓
校验不通过 → 驳回，说明原因
校验通过 → 通知审批人
    ↓
审批人确认
    ↓
节点标记为"已完成" + 触发级联更新
```

## 十、沙盘推演能力设计
### 10.1 推演API

```typescript
interface SimulationRequest {
    scenarioName: string;
    assumptions: {
        nodeId: string;
        assumedStatus: NodeStatus;
        delayDays?: number;
    }[];
    depth: number;               // 推演深度
}

interface SimulationResult {
    affectedNodes: string[];     // 受影响节点清单
    totalDaysImpact: number;     // 对总工期的影响
    criticalPathChanged: boolean; // 关键路径是否变化
    riskLevelChange: "无变化" | "上升一级" | "上升二级";
    recommendations: string[];   // 建议措施
    newNodeStatuses: {
        [nodeId: string]: NodeStatus;
    };
}
```

### 10.2 推演能力边界
- 推演不影响真实数据，完全在内存沙箱中进行
- 推演结果只做参考，不触发任何真实动作
- 最大推演深度：10级（防止性能问题）

## 十四、非功能需求
### 14.1 性能要求
| 操作 | 响应时间要求 |
|------|-------------|
| 单个节点状态查询 | < 100ms |
| 单个节点状态变更（含级联） | < 1s |
| 全项目进度计算 | < 3s |
| 沙盘推演（深度5级） | < 5s |

### 14.2 可靠性要求
- 系统可用性：99.9%
- 数据零丢失：所有变更必须持久化
- 状态机引擎必须**幂等**：同一操作执行多次结果一致

### 14.3 可扩展性要求
- 支持节点自定义（增加、删除、修改依赖）
- 支持钩子函数扩展（业务方可以自定义动作）
- 支持状态扩展（未来可以加新状态）

## 十六、风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 级联更新性能问题 | 节点多了会卡 | 异步化、批量处理、限制传播深度 |
| 数据不一致 | 状态机和实际情况对不上 | 每日巡检任务 + 人工对账机制 |
| 权限太复杂 | 开发周期长 | 第一版先做简单角色，后续和鉴权模块同步 |
| 自定义需求太多 | 标准框架被改乱 | 提供"标准节点+扩展属性"，不允许改核心 |
| 状态回滚需求 | 出错了怎么办 | 提供管理员专用的状态回滚功能，全程审计 |
