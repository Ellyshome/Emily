# 资料驱动全景节点更新 — 意向需求基线 V1

> **定位**：新特性方向。让 Emily 在团队投喂资料（尤其是全景计划/进度计划类）时，自动分析资料、决定全景节点的「创建 / 更新」，替代目前"人工逐条建节点"。
> **状态**：意向基线（待评审、再细化 PRD）
> **本次范围**：仅"资料 → 节点创建/更新"；**不含"邀请签认"**（暂缓）。
> **相邻但不同的机制**：`需求/根据成果反推里程碑节点机制.md` 解决的是"上传单个产物 → 反推某节点是否已完成"；本基线解决的是"投喂一份计划类资料 → 装配/刷新整棵节点树"。两者共用节点写入能力，但触发逻辑不同，需分开设计。

---

## 一、目标

团队任一人上传/归档资料后，系统能识别资料是否属于"计划类"，抽取其节点信息，与项目当前全景节点对照，产出**待确认的变更草案**；经人确认后，自动完成节点的批量创建与更新。

---

## 二、特性清单（逐条）

### F1 资料投喂入口
- 支持两种触发：① 文件归档（SOP-004）后异步挂载分析；② 用户显式指定"按这份资料更新全景节点"。
- 输入面向"文本可解析"资料（pdf/docx/md/txt/表格）；扫描件走既有 OCR/解析链路。
- 上传主链路不被阻断，分析异步执行。

### F2 资料类型识别
- 判定资料是否为"计划类/全景类"（全景计划、进度计划、WBS、节点清单、里程碑表等）。
- 非计划类资料不触发节点装配，直接被忽略（可记录判定结果）。
- 输出带置信度；低置信度不自动进入装配，转人工判定或忽略。
- 判定结论与文件记录关联，可追溯。

### F3 计划结构化抽取
- 从计划类资料中抽取节点树：节点名称、编号（若有）、截止时间、交付成果、前置依赖、父子层级。
- 输出格式对齐现有批量建树 schema（`nodes` 列表：node_id / node_name / deadline / deliverables / dependencies / children），可直接喂给 `create_node_tree`。
- 资料未提供的字段（编号、时间等）按规则生成或留空，并标注"资料未给出"。

### F4 现有节点对照（diff）
- 将抽取结果与项目当前全景节点比对，产出三类决策：**新增 / 更新 / 无变化**。
- 比对键：优先节点编号；无编号时用"节点名称 + 项目"，名称近似仅提示、不自动改名。
- "更新"只作用于资料明确写入的字段，**不因资料未提及而删除**任何现有节点或字段。

### F5 节点写入执行
- 复用现有服务：新增走 `node_batch.create_node_tree`，更新走 `node_batch_update.batch_update_nodes`，依赖/成果沿既有工具链写入。
- 全程按项目隔离，写入携带操作人与来源文件身份。
- 不新增一套节点存储逻辑，只做编排。

### F6 人工确认闸口（提交前暂存）
- 抽取 + diff 结果先形成"变更草案"，**暂不落库**；确认后才执行写入。
- 草案呈现：新增/更新/无变化清单 + 每项依据的资料出处。
- 支持部分采纳（勾选要执行的条目），未采纳的丢弃。
- 这是替代"自动直接改库"的安全设计。

### F7 幂等与重复投喂
- 同一份资料重复投喂，不产生重复节点、不重复更新（依据来源文件指纹/内容摘要判重）。
- 同名新版本文件视为新输入，重新抽取并 diff。
- 单个节点/条目幂等：重复执行同一草案结果一致。

### F8 溯源与留痕
- 每个由资料产生/更新的节点，记录来源文件（file_id）、抽取时间、操作人、采纳条目。
- 变更写入现有 `node_events` 事件流，审计口径与手工操作一致。
- 可回答"这个节点是哪份资料、哪次投喂带来的"。

### F9 权限与失败处理
- 投喂、审定草案、执行写入沿用现有等级权限（节点写入需 L3+，废弃等高危操作另计）。
- LLM 抽取失败、资料不可解析、diff 异常：不阻断文件归档主链路，记录失败原因并支持重试（对齐现有"失败不阻塞"约束）。

---

## 三、非目标（本基线明确不做）

1. 邀请签认 / 待签认通知（用户明确暂缓）。
2. 依据资料自动废弃或删除节点。
3. 从非计划类资料（合同、证照、会议纪要）反推节点结构。
4. 多份资料联合装配（一次只处理一份资料）。
5. 自动推进节点进度/标记完成（属"成果反推"机制，不在本基线）。

---

## 四、依赖与约束

- 依赖全景节点 V2：5 张表 + 批量创建/更新服务 + 签认字段（已就绪）。
- 依赖文件解析链路 `content_summary`（已就绪）。
- 依赖 LLM 结构化抽取能力（现有 DeepSeek 通道）。
- 变更草案需一个承载载体（IM 对话确认 或 Web/API），**待定**。
