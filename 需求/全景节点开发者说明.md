# 全景节点（Project Node）开发者说明

## 一、整体架构

全景节点系统采用四层架构设计，每层职责分明：

| 层 | 文件路径 | 职责 |
|---|---|---|
| Application | `emily-core/emily_core/application/node_app.py` | 编排 Service 调用 + 生成统一响应 + 权限校验入口 |
| Service | `emily-core/emily_core/services/node_service.py` | 核心业务逻辑：CRUD、状态流转、依赖管理、事件记录 |
| State Machine | `emily-core/emily_core/services/node_state_machine.py` | 纯计算引擎：状态判定、循环检测、进度计算（不依赖数据库） |
| Repository | `emily-core/emily_core/repositories/node_repo.py` | 5 张表的数据访问层 |
| Commands | `emily-core/emily_core/services/node_commands.py` | Service 层公共方法入参数据结构（dataclass） |

外部入口方式有四种：

| 入口 | 路径 | 说明 |
|---|---|---|
| IM 自然语言 | `emily-data/sops/SOP-011-SYS-node_manage.md` | 通过 SOP 业务流触发，LLM Agent 直调工具 |
| REST API | `emily-core/api/routes/node.py` | 14 个端点，供外部系统集成 |
| CLI 脚本 | `scripts/manage_nodes.py` | 运维批量操作（创建/更新/激活/废弃/查询） |
| 计划任务 | `emily-core/emily_core/scheduler/jobs/periodic_node.py` 等 | 定时自动创建、截止提醒 |

## 二、节点四态状态机

### 2.1 状态定义

| 状态 | 含义 | 说明 |
|---|---|---|
| `NOT_ACTIVATED` | 未启用 | 初始状态，等待部门负责人审批 |
| `CONDITIONS_NOT_MET` | 条件不足 | 已激活，但前置依赖或成果未满足 |
| `IN_PROGRESS` | 进行中 | 条件满足，工作可执行 |
| `COMPLETED` | 已完成 | 终态，所有必需成果 100% 完成 |

### 2.2 流转规则

```
NOT_ACTIVATED ──审批通过──▶ CONDITIONS_NOT_MET ──条件满足──▶ IN_PROGRESS ──成果100%──▶ COMPLETED
                                       ▲                                          │
                                       └──────────── 阻塞回退 ─────────────────────┘
```

代码定义在 `node_state_machine.py` 第 36-41 行：

```python
VALID_TRANSITIONS: dict[str, frozenset[str]] = {
    NOT_ACTIVATED: frozenset({CONDITIONS_NOT_MET}),   # 审批通过后激活
    CONDITIONS_NOT_MET: frozenset({IN_PROGRESS}),
    IN_PROGRESS: frozenset({COMPLETED, CONDITIONS_NOT_MET}),  # 阻塞时回退
    COMPLETED: frozenset(),  # 终态
}
```

### 2.3 状态判定逻辑（`determine_node_status`）

- **无子节点的叶子节点**：由前置依赖满足度 + 成果完成度决定状态
  - 前置条件满足度 = Σ(依赖成果文件已上传 × 权重)，需 ≥ 1.0
  - 成果完成度 = Σ(必需成果 current/target) / 必需成果总数，需 ≥ 1.0
  - 无任何成果定义的节点 → 保持 CONDITIONS_NOT_MET
- **有子节点的父节点**：由所有子节点集体决定
  - 全部 CONDITIONS_NOT_MET → CONDITIONS_NOT_MET
  - 全部 COMPLETED → COMPLETED
  - 否则 → IN_PROGRESS

## 三、数据库设计

### 3.1 核心表

| 表名 | ORM 模型 | 说明 |
|---|---|---|
| `project_nodes` | `ProjectNode` | 节点主表 |
| `node_deliverables` | `NodeDeliverable` | 产出成果表 |
| `node_dependencies` | `NodeDependency` | 前置依赖表 |
| `node_events` | `NodeEvent` | 操作事件审计日志 |
| `node_participant_companies` | `NodeParticipantCompany` | 节点-参建单位多对多关联 |

### 3.2 ProjectNode 关键字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `node_id` | String(100) | 业务主键，如 `SG-JG-01-2026` |
| `node_name` | String(500) | 节点名称 |
| `node_type` | String(20) | MILESTONE / WORK_PACKAGE / TASK |
| `status` | String(20) | 四态之一 |
| `owner_dept_id` | String(100) | 主责条线 |
| `deadline` | String(50) | 截止时间（ISO8601） |
| `responsible_user_id` | String(100) | 责任人 FK→users.id |
| `visibility_mode` | String(30) | 文件可见模式：specific / all_project_files |
| `is_discarded` | Boolean | 软删除标记 |

### 3.3 NodeDeliverable 关键字段

| 字段 | 说明 |
|---|---|
| `deliverable_id` | 成果编号（业务主键，自动生成如 `{node_id}-DELV-{seq}`） |
| `target_amount` | 目标量（DECIMAL 字符串） |
| `current_amount` | 当前量 |
| `is_required` | 是否必需成果 |
| `submission_status` | PENDING / SUBMITTED / CONFIRMED / RETURNED |

### 3.4 关键设计特性

- **依赖锁定成果而非节点**：`node_dependencies.depends_on_deliverable_id` 指向具体成果，不绑定整个上游节点，上游某个成果就绪即可启动下游
- **权重支持人工阻塞**：`weight >= 999` 表示阻塞条件，无法通过正常成果满足来解除
- **软删除**：废弃通过 `is_discarded=True` 标记，不物理删除数据

## 四、节点树层级体系

### 4.1 层级结构

采用项目 → 阶段 → 楼栋 → 具体节点的树状分解：

- 父子关系通过 `parent_node_id` 字段维护
- 嵌套深度上限 **3 层**，子节点上限 **100 个**
- 父节点进度由子节点进度**加权汇总**自动计算
- 支持 BFS 循环检测，防止非法父子关系

### 4.2 节点类型

| 类型 | 说明 |
|---|---|
| `MILESTONE` | 里程碑节点，标记关键阶段节点 |
| `WORK_PACKAGE` | 工作包节点，默认类型，可分解为子节点 |
| `TASK` | 任务节点，叶子节点，挂载具体执行任务 |

## 五、成果提交确认工作流

成果在节点内部有自己的生命周期：

```
PENDING ──submit──▶ SUBMITTED ──confirm──▶ CONFIRMED (自动设 current=target)
                      │         ▲
                      └─return──┘ (可重新提交)
```

### 5.1 关键合规约束

> 成果上报必须来自已分配任务，任务必须挂载于执行中的全景节点（status=IN_PROGRESS）。
> 未启用（NOT_ACTIVATED / CONDITIONS_NOT_MET）的节点不得挂载任何任务。

### 5.2 提交权限

- 提交人必须是节点责任人或同部门（owner_dept_id）人员
- CONFIRMED 时自动将 `current_amount` 设为 `target_amount`，触发状态重算

## 七、三维权限模型

采用角色级别 × 数据范围 × 操作类型的三维矩阵式鉴权：

### 7.1 角色级别

| 级别 | 名称 | 典型权限 |
|---|---|---|
| L1 | 访客 | 只读 |
| L2 | 参建执行 | 成果进度更新 |
| L3 | 参建管理 | 编辑/成果更新/依赖调整 |
| L4 | 建设主管 | 节点废弃 |
| L5 | 管理员 | 自动激活节点、审批任何部门 |
| L6 | 系统管理员 | 全部操作 |

### 7.2 节点操作权限规则

- **创建节点**：仅建设单位人员可创建（`company_type == "建设单位"`）
- **审批节点**：部门负责人或 L5+ 管理员
- **变更责任人**：部门负责人或 L5+ 管理员
- **提交成果**：节点责任人或同部门人员

## 八、自动化与智能特性

### 8.1 文件→节点智能匹配

`NodeDeliverableMatcher`（`emily-core/emily_core/services/node_deliverable_matcher.py`）通过 4 级优先级匹配上传文件与全景节点：

| 优先级 | 策略 | 置信度权重 |
|---|---|---|
| 1 | 文件名关键词匹配 | 0.9 - 1.0 |
| 2 | 文件类型 + 阶段推断 | 0.7 - 0.85 |
| 3 | 摘要关键词匹配 | 0.6 - 0.75 |
| 4 | 时间窗口加分（±7天内） | +0.1 |

高置信度（≥ 0.85）时通知管理员介入确认。

### 8.2 节点模板系统

`emily-data/node_templates/` 目录下存放参考节点模板：

- 每个模板详细定义：节点说明、完成条件、产物清单、文件识别特征
- 模板索引 `index.yaml` 供 AI 工具快速了解模板库内容
- Session 拉起时模板索引可能被注入 prompt，告诉 AI 有模板库可用
- 维护脚本：`uv run python scripts/maintain_node_template_index.py`

### 8.3 截止时间提醒

`NodeDeadlineHandler`（`scheduler/jobs/node_deadlines.py`）定时扫描：

- 临近截止节点（在 `before_minutes` 分钟内到期）
- 已超期节点

通过 `OutboundEventBus` 推送提醒消息。

### 8.4 周期节点自动创建

`PeriodicNodeHandler`（`scheduler/jobs/periodic_node.py`）：

- 创建 TASK 类型叶子节点
- 基于 `node_name + project_id` 的 MD5 哈希生成 `node_id`，实现幂等（同名同项目不重复创建）

### 8.5 批量节点创建

`node_batch.py`（`emily-core/emily_core/services/node_batch.py`）：

- 4 阶段有序执行：创建节点 → 添加成果 → 挂载父子 → 添加依赖
- 依赖按名称模糊解析（无需硬编码 deliverable_id）
- 幂等：已存在的节点跳过而非报错
- 支持 dry-run 模式

## 九、事件审计系统

所有节点操作均通过 `_record_event` 写入 `node_events` 表，事件类型包括：

| 事件类型 | 触发场景 |
|---|---|
| `node_created_pending_approval` | 普通用户创建节点，待审批 |
| `node_created_auto_activated` | 管理员创建节点，自动激活 |
| `node_activated` | 审批通过 |
| `node_activation_rejected` | 审批拒绝 |
| `node_updated` | 字段更新 |
| `node_discarded` | 节点废弃 |
| `status_changed` | 状态自动流转 |
| `auto_triggered` | 节点已完成 |
| `dependency_added` / `dependency_removed` | 依赖变更 |
| `deliverable_submitted` / `deliverable_confirmed` / `deliverable_returned` | 成果提交确认 |
| `BLOCKING_CONDITION_ADDED` / `BLOCKING_CONDITION_REMOVED` | 阻塞条件变更 |
| `responsible_user_changed` | 责任人变更 |

同时通过 `OutboundEventBus` 发布实时事件（`node_pending_approval`、`node_auto_activated`），支持 SSE 推送和通知下游系统。

## 十一、CLI 运维脚本

`scripts/manage_nodes.py` 支持的操作：

```bash
# 从 YAML 批量创建节点树
uv run python scripts/manage_nodes.py create --file nodes.yaml [--dry-run]

# 从 YAML 批量更新节点字段
uv run python scripts/manage_nodes.py update --file updates.yaml [--dry-run]

# 批量激活/废弃
uv run python scripts/manage_nodes.py activate --file activate.yaml
uv run python scripts/manage_nodes.py discard --file discard.yaml

# 批量更新成果进度
uv run python scripts/manage_nodes.py progress --file progress.yaml

# 批量管理节点文件关联
uv run python scripts/manage_nodes.py link-files --file links.yaml

# 查询项目节点概览
uv run python scripts/manage_nodes.py query --project-id <uuid>
```
