# Session × WorkItem 工作流系统化质量保障层

## Context

用户在审视归档 `2026-07-23_黄志强_12345601.md` 后，发现三类现象：LLM 调用缺思考内容、工具参数显示 `{}`、Guardian 标了幻觉却照发编造回复。修复 A/B/C（archive 字段名、client end 阶段补传 model/json_mode、node2 注入工具 schema）已执行。

诊断进一步暴露：Guardian 已审但结果没被消费、node4 LLM 合成失败即落固定串、意图识别失败即降级、工具参数无 schema 校验。这些是"审核/重试/校验"机制的断点。用户决定走**系统性改造**路线，要求作为资深架构师给出完整方案。

**架构师立场**：系统化不等于堆机制。当前问题 80% 是"已有机制最后一公里没接通"（Guardian 审了不用、降级链末端偷懒）。本方案的目标是把断点接通成闭环，并引入轻量的打分与重试策略，但用四条硬约束防止过度工程。方案成败取决于克制——做完若某层收益不高，应敢砍。

---

## 设计原则（四条硬约束，把风险转成约束）

1. **可观测优先于控制流**：每次重试 / 校验 / 打分 / 纠正都必须结构化留痕（归档 + 进化日志），状态写入 WorkItem，让人能复盘。不做黑盒重试。
2. **重试必须换策略**：原样重试无意义。每次重试降级一档（json→text、低温→高温、复杂→简化），不设"原样重试 N 次"。
3. **打分三层融合，禁纯 LLM 自评**：规则分（硬，可自动验）+ LLM 审核分（软，Guardian issues）+ 反馈分（滞后，用户采纳/修改）。LLM 自评分有自我偏好，"分高但错"比"没分"更危险。
4. **纠正有边界**：最多 1 次软纠正，不递归、不死循环。纠正失败仍走诚实兜底。软质量（Guardian/打分）只触发纠正不阻断；硬规则（schema/权限）才 BLOCK。

---

## 现状接入点分析（bus.py / hook.py 能力边界）

PipelineBUS.run() 每节点顺序：`before hooks(可BLOCK) → handler → after hooks(fire-and-forget)`。Hook 声明式注册到 `HOOK_TYPE_MAP` + `hook_config.json`。

| 机制 | 能否做 Hook | 原因 | 接入方式 |
|------|-----------|------|---------|
| 硬校验（schema/enum/权限） | 可（before 下游节点） | before 可 BLOCK | 但为就近可读，放 handler 内部 |
| 软打分 / 留痕 | 可（after node4） | after fire-and-forget 适合记录 | QualityScorerHook |
| 重试 | ✗ | after 无法回退重做 | handler 内部 LLM 调用点 |
| 纠正闭环 | ✗ | 需重合成，after 改不了 handler 结果 | node4 handler 内部 |

结论：**重试与纠正必须在 handler 内部**（贴着调用点）；**打分与留痕可做 Hook**（横切）；**硬校验放 handler 内部**（就近，不引入 Hook 注册负担）。

## 分层架构（5 层）

### 层 1 — 输入校验（ValidationGate，handler 内部调用）

新增 `workitem/pipeline/validation_gate.py`，纯函数模块，被 node2/node3 handler 调用：

- `validate_plan(plan, tool_registry)`：node2 `_llm_plan` 后校验——每个 step.tool_name 在 registry、tool_params 键名在 tool.parameters.schema 内、required 参数不缺
- `validate_tool_params(tool_name, params, schema)`：node3 `_real_execute` 执行前校验——query_type 落在 enum、必填项非空、类型匹配
- 校验失败：硬违规（不在 enum / 缺必填）→ 返回 `StepResult(success=False, output="参数校验失败: ...")`，不把垃圾值喂给工具；软违规（多余字段）→ 剥离后继续

接入：[workitem_agent.py:326](emily-core/emily_core/workitem/workitem_agent.py#L326) `_map_to_execution_plan` 后调 validate_plan；[workitem_agent.py:482](emily-core/emily_core/workitem/workitem_agent.py#L482) 工具调用前调 validate_tool_params。Skill 路径同样在 [executor.py:125](emily-core/emily_core/skill/executor.py#L125) handler 调用前接入。

### 层 2 — 执行重试（RetryPolicy，handler 内部 LLM 调用点）

新增 `workitem/pipeline/retry_policy.py`，提供 `with_retry(strategy_chain)` 装饰器 / 上下文。每个调用点声明自己的降级链：

| 调用点 | 降级链 |
|--------|--------|
| 意图识别 [session_agent.py:325](emily-core/emily_core/session/session_agent.py#L325) | (json, temp=0.1) → (json, temp=0.3) → fallback |
| node2 规划 [workitem_agent.py:313](emily-core/emily_core/workitem/workitem_agent.py#L313) | (json, temp=0.1) → (text, temp=0.3) → fallback_steps |
| node4 合成 [workitem_agent.py:769](emily-core/emily_core/workitem/workitem_agent.py#L769) | (json, temp=0.3) → (text, temp=0.5) → honest_fallback |
| 参数提取 [param_extractor.py:154](emily-core/emily_core/skill/param_extractor.py#L154) | (json, temp=0.1) → (json, temp=0.3) → default/fail |

每次重试换策略并记日志（attempt 序号、策略、耗时、失败原因），写入 LLM 日志的 response_summary 或独立 retry_log 字段。**不设原样重试。**

### 层 3 — 输出校审 + 质量打分（QualityScorer，三层融合）

新增 `workitem/pipeline/quality_scorer.py`：

```
QualityScore = {
  rule_score:   float,     # 硬规则：schema/enum/必填/权限违规 → 0；否则 1
  llm_score:    float,     # Guardian issues 按严重度加权（幻觉=重，啰嗦=轻）
  feedback_score: float,   # 历史反馈（离线，本轮默认 1.0）
  final:        float,     # rule 一票否决，否则加权
  issues:       list[Issue],
  action:       "pass" | "correct" | "fallback",
}
```

- rule_score：ValidationGate 结果（层 1 复用）
- llm_score：复用 RealGuardian.review_reply 的 issues（已有），按 issue 严重度映射扣分
- feedback_score：本轮默认 1.0，离线由 FeedbackSignalDetector 历史数据回填（用户曾对类似回复否定 → 降权）
- action 阈值：final ≥ 0.8 → pass；0.5–0.8 → correct；< 0.5 → fallback

Guardian 改造：[real_guardian.py:103](emily-core/emily_core/workitem/pipeline/real_guardian.py#L103) `review_reply` 返回结构化 `QualityScore`（兼容现有 GuardianNote，扩展 issues 严重度字段）。

### 层 4 — 纠正闭环（CorrectionLoop，node4 handler 内部状态机）

node4_summary 改造为状态机（[workitem_agent.py:610](emily-core/emily_core/workitem/workitem_agent.py#L610)）：

```
draft_v1 = synthesize(wi)                    # 含层2重试
review_v1 = QualityScorer.score(draft_v1)
if review_v1.action == "correct":
    draft_v2 = synthesize(wi, inject=review_v1.issues)   # 把问题喂回 prompt
    review_v2 = QualityScorer.score(draft_v2)
    final = draft_v2 if review_v2.action != "fallback" else draft_v2
elif review_v1.action == "fallback":
    final = honest_fallback(wi)              # 诚实兜底（见层5）
else:
    final = draft_v1
```

- 最多 1 次纠正，不递归
- 纠正 prompt 注入："你上次的回复存在以下问题：{issues}，请基于真实 step_results 重新回复，不要编造"
- 状态写入 `wi.correction_trace`（v1 review → v2 review），归档可见
- 纠正后仍不达标 → 走诚实兜底，不强行发出问题回复

### 层 5 — 诚实兜底 + 留痕（兜底重写 + ArchiveHook 增强）

**兜底重写**（[workitem_agent.py:813-841](emily-core/emily_core/workitem/workitem_agent.py#L813-L841)）：
- `honest_fallback(wi)`：有 LLM 且 step_results 非空 → LLM 基于 step_results 生成"我尝试了 X，但 Y，建议 Z"
- step_results 全空 → LLM 基于 user_input 回复"未能完成，原因 + 建议"
- LLM 完全不可用 → 保留固定串"Emily 已处理完毕"（唯一合理场景）
- session_agent.py:238 汇总兜底同理：replies 全空时走 LLM 而非固定串

**留痕增强**：
- ArchiveHook（[hook.py:302](emily-core/emily_core/workitem/pipeline/hook.py#L302)）已逐段追加，扩展 render_node_section 输出：重试链路（attempt 序号/策略）、校验结果、打分、纠正轨迹
- 新增 QualityScorerHook（after:wi_node4）写打分到进化日志，供离线分析重试率/幻觉率/打分趋势
- LLM 日志表（evolution_llm_interaction_logs）增字段或复用 metadata 记 retry_attempt / correction_round

## 关键决策记录

1. **打分用三层融合而非 LLM 自评**——规则分一票否决，LLM 分软加权，反馈分滞后修正。避免"分高但错"。
2. **重试用策略链而非计数器**——每个调用点声明降级链，不做统一重试框架（抽象必失真）。
3. **纠正闭环在 node4 handler 内，不做 Hook**——after hook 是 fire-and-forget 无法重做。最多 1 次，不递归。
4. **硬校验放 handler 内不放 Hook**——就近可读，避免 before hook 校验上一节点输出的时序绕弯。
5. **不引入多 agent 互审 / Plan-Act-Reflect 多层循环**——当前 4 节点已隐含 Plan-Act-Reflect，再叠层冗余且难调试。
6. **Guardian 保持软标记，不升级为拦截器**——LLM 不确定性不应变硬阻断。硬阻断留给 Hook(Auth) + ValidationGate。

## 实施分期

### Phase 1 — 断点接通（低风险，立刻见效）
- 层 1 ValidationGate（validate_plan + validate_tool_params）
- 层 5 兜底重写（honest_fallback + session 汇总兜底走 LLM）
- 层 2 node4 合成降级重试（json→text，最常用调用点先行）

### Phase 2 — 闭环（中风险，需评估延迟/成本）
- 层 3 QualityScorer（三层融合，Guardian 返回结构化 score）
- 层 4 CorrectionLoop（node4 状态机，1 次纠正）
- 层 2 意图识别 / 规划 / 参数提取降级重试补齐

### Phase 3 — 度量（离线，不影响主链路）
- QualityScorerHook 写进化日志
- ArchiveHook 输出重试/校验/打分/纠正轨迹
- FeedbackSignalDetector 回填 feedback_score

每期独立验收。Phase 1 完成后若已覆盖 80% 现象，Phase 2/3 可按需推进或暂缓。

## 验证方式

每个 Phase 用 emy-test 跑同一组场景，对比归档前后：

1. **幻觉纠正**（层 3+4）：发"我现在在什么节点里？"，验证 node4 检测到编造后触发 1 次重合成，最终回复不再含未支撑的具体节点，或诚实承认信息不足
2. **参数校验**（层 1）：构造 LLM 规划出 query_type="node" 的场景，验证 node3 校验拦截而非把垃圾值喂工具
3. **兜底诚实**（层 5）：构造 step-01 失败场景，验证兜底回复基于 step_results 而非"已处理完毕"
4. **重试降级**（层 2）：mock LLM 首次返回非法 JSON，验证第二次换 text 模式成功，归档记录两次 attempt
5. **打分留痕**（层 3）：归档 node4 段可见 final score / issues / action

## 架构师保留意见

1. **最大的风险是打分被当 KPI**——一旦有人开始优化"分数"而非"回复质量"，系统会刷分。打分只用于触发纠正和留痕，**不暴露给用户、不作为系统性能指标对外**。
2. **Phase 2 的延迟成本要实测**——node4 多一次 Guardian + 可能 1 次重合成，最坏情况延迟翻倍。若 P95 延迟超阈值，纠正闭环改异步（先发 v1，后台纠正后补发），但这会复杂化交互。建议 Phase 2 先同步实现，测延迟再决定。
3. **敢砍**——Phase 1 后若现象已解决 80%，Phase 2/3 的打分与离线度量可暂缓。不要为了"系统完整"而上没收益的层。
4. **与 CLAUDE.md 第 7 条一致**——Hook 三态 deny-wins 不变，Guardian 仍软标记，硬阻断仍由 Auth+ValidationGate 承担。本方案不改变现有 Hook 语义，只新增 after:wi_node4 的 QualityScorerHook。
