## P0-1（🔴 高）低权限用户被明确告知"无权查看的节点名称"

### 什么时候遇到的

验收 **TC02（摘要按可见节点裁剪）** 和 **TC12（三书全文按权限裁剪）** 时。用的是一个真实低权限账号：

- **周文斌**，权限等级 `level=1`（访客），系统判定他**没有任何可见的全景节点**（`authorized_node_ids = []`）。

### 实际看到什么

我用这个账号发了一句普通提问：

> 用户（周文斌）：**"翠湖庭院现在项目进展怎么样"**

Emily 的回答里直接点名了**三个他无权查看的节点**：

> "…逾期节点主要是**方案设计、可行性研究、规划许可证办理**。"
> "…7天内到期节点：**绿化种植（09-15）**、**硬质铺装与园路（09-15）**。"
> "…存在阻塞链条：**可行性研究→立项审批→规划报建**，**方案设计→规划许可证→施工总控/地基与基础工程**…"

### 期望是什么

按需求：项目态势信息（含节点名称、逾期、阻塞）**必须按"当前提问者的可见节点范围"裁剪**；一个没有任何节点权限的访客，**不应**从 Emily 口中得知这些节点叫什么。

### 为什么会这样（不用看代码也懂）

系统里有"三本书"，其中**项目态势书**在组装成给 Emily 看的资料时，会输出四行内容：

1. 项目名与阶段 —— 公共信息，正常；
2. 节点统计（多少完成/进行中/逾期）—— 正常；
3. **"我可见节点"** —— 这一行**做了**权限过滤（所以显示"我可见节点（0）：无"）；
4. **"🔴 逾期：…"** —— 这一行**漏了**权限过滤，直接把逾期节点名全部列了出来。

也就是说：**同一份资料里，第 3 行记得按权限裁剪，第 4 行忘了**。而第 4 行里恰恰就是节点名称。同理，在"按需查阅全文"时，**"近期事件""7天内到期""阻塞"这三段也都没有按权限裁剪**，里面的节点名照单全收。

一句话：**权限过滤只做了一半，做的是"统计与明细"，漏的是"逾期/事件/阻塞"这些同样带节点名的段落。**

- 证据（可复现）：把"可见节点集合"设为空，直接渲染摘要 → 返回内容仍包含 `方案设计 / 可行性研究 / 规划许可证办理`。
- 影响面：**所有低权限用户**；这些名字会进入 Emily 的"思考资料"并被复述给用户，等于把未授权节点名泄给了无权的人。
- 对应验收标准：AC-US-01.2、AC-US-04.2（零越权泄漏）→ 因此 TC02、TC12 判 **FAIL**。

### 怎么复现

1. 用 `level=1` 且无授权节点的账号（如周文斌）向 Emily 提问"项目进展"。
2. 观察回复中是否出现具体节点名（如"方案设计""可行性研究""规划许可证办理"）。
3. 辅助验证：以该用户渲染会话资料，检查"逾期"行是否仍列出节点名。

### 修复方向（通俗）

渲染项目态势资料时，**凡是输出"节点名称"的地方都要先过一遍权限**——不只是"节点明细"和"我可见节点"，还要包括"逾期节点""近期事件涉及的节点""7天内到期""阻塞链"。要么统一在出口处按可见集合过滤，要么在生成态势书时就给每条记录带上节点编号，便于统一求交。

> ⚠️ 注意：修复前请先看 **P0-2**——因为目前"可见节点集合"几乎是空的，若只做过滤，可能变成"所有节点信息对所有人都不显示"。

## P0-2（🔴 高）"用户能看哪些节点"与"系统里的节点编号"是两套对不上的编码

### 什么时候遇到的

在验证 TC02 时，需要拿到"某用户可见的节点清单"，结果发现**所有账号的"我可见节点"都是 0**，于是追查了数据来源。

### 实际看到什么

**A. 系统里"节点"长这样**（项目态势书中的节点编号）：

```
EMR-GH-01-01、EMR-LX-01-01、EMR-GH-01-02、EMR-GH-01、EMR-SG-01-04 …
（共 27 个节点）
```

**B. 系统里"用户能看哪些节点"长这样**（由公司信息推导）：

| 用户 | 所属公司 | 公司业务范围 | 系统给出的"可见节点" |
|------|---------|-------------|-------------------|
| 周文斌（L1） | 鑫达建材供应商 | ["钢材供应","混凝土供应"] | `[]`（空） |
| 赵明远（L3） | 上海建筑设计研究院 | ["方案设计","施工图设计"] | `['construction','design']` |
| 王建国（L6） | 翠湖地产建设集团 | ["立项审批","投资控制"] | `[]`（空） |

**C. 两者求交集的结果**：`[]`（永远为空）。

### 期望是什么

"按可见节点裁剪"要成立，前提是**两边的标识能对上**——用户身上记的应该是"能看哪些节点编号"，而不是"条线关键词"。

### 为什么会这样（不用看代码也懂）

- 系统判断"用户能看哪些节点"时，读的是**公司信息里的业务范围**，把它**推导成一串行业/条线关键词**（例如 `design`、`construction`）。
- 而项目态势书里的节点，用的是**节点自己的编号**（例如 `EMR-GH-01-01`）。
- 这两套东西**天生不可能相等**，所以：
  - "我可见节点"永远是 **0**；
  - 一旦按这个集合去做过滤，结果要么**什么都没过滤掉**（如果过滤逻辑写漏了，就是现在的 P0-1），要么**把所有人都挡在外面**（如果严格过滤）。

### 影响

- 这是 P0-1 的"另一半"：**即使把漏掉的过滤补上，只要编码对不上，裁剪也没有正确的数据基础**。
- 换句话说，"按可见节点裁剪"这个能力**目前实际上是失效状态**，只是被 P0-1 的"泄漏"掩盖了——用户看到的是不该看的，而不是看不到该看的。

### 需要谁来决定

这不是纯技术 bug，而是**口径问题**，需要产品/设计确认：

1. "用户可见节点"到底应该由什么决定？（公司业务范围？还是**用户与节点的参与关系**——系统里已有一张"节点参与人"表 `node_participants`，但目前所有用户都是 0 条记录）
2. 如果答案是"参与关系"，那需要先补齐 `node_participants` 数据，并把"可见集合"改成存**真实节点编号**。

### 怎么复现

对任意账号查询其"可见节点集合"，与项目态势书里的节点编号对照：前者是 `design/construction` 之类的词，后者是 `EMR-…` 编号，交集恒为空。

## P1-1（🟠 中高）"查询我负责的节点"这个工具每次调用都会崩溃

### 什么时候遇到的

验收 **TC04（先查后办的复合请求）** 时。王建国（L6）发了一句复合请求：

> "帮我查一下翠湖庭院的逾期节点，然后帮我记一条事件：逾期节点复盘会议已召开"

Emily 在处理过程中调用了"查询我负责的节点"这个工具，日志随即报错（14:59:34）：

```
[ERROR] emily.langgraph.loop: tool_node query_my_nodes failed:
        cannot access local variable 'nid' where it is not associated with a value
        UnboundLocalError: cannot access local variable 'nid' where it is not associated with a value
```

### 实际看到什么

- 工具**直接报错**（`UnboundLocalError`），没有返回任何结果。
- 会话没有中断——Emily 绕道用别的资料回答了（最终回复里仍正确列出了王建国名下的 2 个节点），所以**用户侧当时看不出来**，问题只在日志里。

### 期望是什么

"查询我负责的节点"应正常返回该用户负责/参与的节点列表。

### 为什么会这样（不用看代码也懂）

这个工具在合并两份节点列表时，用了一个变量（`nid`，表示"当前节点编号"）来做去重。但代码里**只有在"发现重复节点"时**才给这个变量赋值；**正常处理第一个节点时，它根本还没被赋值就被拿去用了**，于是程序当场崩溃。

结果就是：**只要这份列表里有"不重复的正常节点"（这是绝大多数情况），工具就会失败**——等于这个工具**对所有用户、所有调用都是坏的**。

### 影响

- 用户问"我负责哪些节点 / 我的任务"这类问题时，Emily 拿不到工具结果，只能靠其它资料"猜"或绕道回答，**答案的完整性没有保障**。
- 这是**历史遗留缺陷**（该工具文件本次未被改动），但它会直接影响依赖它的场景，建议单独修复。

### 怎么复现

任何触发"查询我负责的节点"的提问（例如"我在哪些节点上""我负责什么"），观察后台日志是否出现上述 `UnboundLocalError`。

### 修复方向

去重逻辑改为：**先用当前节点编号判断是否重复，再把它加入已处理集合**——即保证"当前节点编号"在使用前一定已经被赋值。

## P2-1（🟡 中）按计划清理容器缓存的步骤在本环境无法执行

### 什么时候遇到的

执行验收计划 §3.2 前置第 2 步「清除容器 pycache」时。

### 实际看到什么

```
rm: cannot remove '/app/emily_core/.../__pycache__/xxx.cpython-312.pyc': Read-only file system
```

代码目录在容器内是**只读挂载**，删不掉缓存。

### 影响与结论

**不影响测试有效性**。因为代码是从宿主机实时挂进来的，文件修改时间已更新，Python 在导入时会**自动识别并重新编译新代码**，不存在"沿用旧字节码"的风险。重启后 `_ensure_tool_registry_seed: synced 40 tools` 也证实新代码已生效。建议把计划里这一步标注为"本环境不适用"。

## P2-2（🟡 中）规则书若被"半成品数据"渲染，"没写适用等级的条文"会消失

### 什么时候遇到的

验收 **TC21（规则书按等级裁剪 + 缺标注兼容）** 时，测试脚本里手工拼了一份规则书章节（其中一章故意不写适用等级）直接交给渲染函数。

### 实际看到什么

- 经由**正常解析流程**（先解析规则书再渲染）时：未标注等级的章节**按全员可见**处理 ✅（符合预期）。
- 但若**跳过解析、直接把手拼的章节交给渲染**：未标注等级的章节**被静默丢弃** ❌。

### 影响与结论

当前**所有正式入口都会先解析再渲染**，所以线上不会出问题，属于**潜在风险**：
一旦将来有人新增调用、忘了走"解析"这一步，就会出现"某些条文对所有人消失"，而且**不报错、很难发现**。
建议在渲染层也补一个"缺等级就按全员可见"的兜底，彻底落实"缺标注不丢条文"。

## P3-1（🟢 低）模型偶发返回不合法 JSON，导致一次意图识别失败后回退重试

### 什么时候遇到的

验收期间（14:59:13）王建国的那次复合请求处理过程中。

### 实际看到什么

```
[ERROR] emily.llm: Failed to parse LLM response as JSON:
```

### 影响与结论

这是**模型侧偶发**（大模型偶尔输出不是合法 JSON 的内容），系统随后**自动回退到主模型重试并成功**，属于既有容错机制在正常工作，**非本次需求引入**，不影响结论。仅作运行时记录。

## 建议处理顺序

1. **先定 P0-2 的口径**（"用户可见节点"到底怎么来）——否则 P0-1 修不彻底，要么继续漏、要么全挡。
2. **再修 P0-1**（把所有输出节点名的地方统一按可见集合过滤）。
3. **修 P1-1**（"查询我负责的节点"必崩，影响面广且修复成本低）。
4. 视排期处理 P2-2；P2-1/P3-1 仅记录。
