# 检索通道治理 — 需求基线 V1（讨论稿）

> **性质**：讨论稿，供决策确认；确认后转 PRD 与计划
> **日期**：2026-09-12
> **依据**：RAG 功能实战测试（12 用例）与调用链取证；`knowledge_chunks` 实况；提示词与工具注册表实况
> **关系**：与本项目「LangGraph 编排内核化」为两条独立需求线，并行推进，不合并

## 一、背景与问题

1. **现象**：L6 用户问「节点A的投标报价是多少」，模型连调 `query_node`（失败）、`query_my_nodes`（成功）、`query_files`（空）三次，**知识库检索一次未触发**；`rag_retrieval_logs` 对该查询 0 行。
2. **定性**：卡点在**通道选择**，不在密级（L6 达标）、不在检索过滤（检索未发生）。
3. **根因**：六条检索通道平铺给模型，提示词明确"没有先分类再决定的前置环节"，选择完全依赖工具名与描述的语义匹配。
4. **影响**：可答的题答不出（漏答）；错误通道被选中（错答风险）；权限边界依赖"恰好选对通道"（安全面）。
5. **结论**：信息获取缺少治理层，需独立立项。

## 二、目标

1. **G1 可解释**：每次信息获取都能说明用了哪条通道、命中什么、为何不用其他通道。
2. **G2 可自愈**：主通道空结果时能确定性升级到备选通道，而非停在原地。
3. **G3 可治理**：新增通道必须登记元数据；路由规则外置可配，不散落在工具描述与图代码中。

## 三、范围

- **纳入**：六条可调用检索通道（知识库、文件台账、节点台账、结构化业务数据、自我认知、专家名册）与会话期注入类通道（预取、三书与规则书、长期记忆、群上下文）的元数据登记与引用。
- **不纳入**：写入类能力（`record_*`、`create_*`、`update_*` 等）；文档解析与 OCR（属加工而非检索）；专家名册的启封（仍按 D10 休眠）。

## 四、术语

1. **通道**：一次信息获取的入口（工具或注入）。
2. **命中**：通道返回可用内容。
3. **升级**：主通道空结果后，按规则改走备选通道。

## 五、功能需求

1. **FR-1 通道元数据注册**：每个通道登记七项——所属域、回答对象、参数、权限维度、是否含正文、空结果语义、升级目标。
2. **FR-2 描述与注册同源**：工具 description 由元数据生成，避免提示词与实现漂移。
3. **FR-3 通道分工表**：给出「问题类型 → 首选通道 → 备选通道」的显式表，写入提示词。
4. **FR-4 实体解析前置**：问题中出现实体（节点、项目、文件）时先解析存在性；存在走台账，不存在转文档检索。
5. **FR-5 空结果确定性升级**：主通道空结果即按升级目标改道；仍空则明确告知"未找到"并说明已查范围。
6. **FR-6 多路融合（受策略表约束，四档）**：常态单通道；空结果串行升级为默认；升级阶段允许并发 2~3 路并做去重与来源排序；常态并发仅对策略表白名单的问题类型开放，不全局开。
7. **FR-7 出处标注**：回答标注来源通道与对象（文档名、记录类别）。
8. **FR-8 全通道检索日志**：记录通道、跳数、命中数、是否被采用、耗时、权限过滤结果（现仅知识库有日志）。
9. **FR-9 路由规则可配置**：规则表外置为配置文件，改动不需改图代码、不需发版。
10. **FR-10 权限收窄贯穿**：所有通道统一复用既有可见性唯一权威来源，失败即拒（fail-closed）。

## 六、非功能需求

1. **NFR-1 常态成本不增**：默认单通道调用，仅在空结果时升级。
2. **NFR-2 可观测**：每次检索可回溯（日志 + 会话归档）。
3. **NFR-3 可回退**：策略表可整体关闭，回到当前"模型自选"行为。
4. **NFR-4 不改写内核**：路由规则不进入图代码，图只作执行者。

## 七、约束

1. 不得引入第二编排器（与内核图化的 D7 一致）。
2. 不得全量并发检索。
3. 通道可见性必须复用既有唯一权威来源，宁少答不泄露。
4. 规则不得硬编码进图或散落在工具实现中。

## 八、非目标

1. 不替换全文搜索引擎。
2. 不做排序与重排算法研究。
3. 不做跨库联邦查询。
4. 不启封休眠通道。

## 九、验收方向

1. 以现有 RAGENV 测试集扩展"通道选择"语料：每题标注**期望命中通道**与**期望不命中通道**。
2. 回归题采用本次两处现象：RAG-04（节点进度被台账抢占）、RAG-11（实体不存在即终止）。
3. 判定三件事：通道是否选对、空结果是否升级、来源是否标注。

### 10.1 Q3 释义：什么是"常态两路并发"

**定义**：每一次提问都同时对两条或多条通道发起检索，把多路结果合并后交给模型。

**与"按需升级"的对比**（以本次 RAG-11 为例，问「节点A的投标报价」）：

| 方式 | 执行过程 | 一跳延迟 | 检索次数 | 漏答风险 |
|------|---------|---------|---------|---------|
| 常态两路并发 | 同时调 `knowledge_search` 与 `query_node`，两路结果合并给模型 | 取最慢一路 | 每次 2 跳起 | 低（总有一路可能命中） |
| 按需升级（本基线默认方案） | 先 `query_node`；失败→`query_my_nodes`；仍空→按升级目标转 `knowledge_search` | 常态仅 1 跳 | 常态 1 跳，异常时才增加 | 取决于升级规则是否覆盖 |

**并发吸引人的地方**：提高召回，降低"选错通道"的概率，不必依赖策略表覆盖全部分支。

**代价（四条）**：

1. **成本**：每次提问都多一次检索（含一次 embedding 请求与一次库查询）；高频场景下检索量成倍上升。
2. **延迟**：并发取最慢一路，慢通道会拖住整体；串行只在需要时才付这条延迟。
3. **噪声与错答**：多路口径不同（台账字段与文档正文）混在一起，模型需处理更多互相干扰的内容。
4. **权限暴露面与可解释性**：一次性访问更多数据源，审计面扩大；回答混合多源后，事后难判断哪条通道真正贡献了答案（与 G1 冲突）。

**建议的档次划分**（供决策）：

| 档次 | 形态 | 适用 |
|------|------|------|
| A | 单通道（常态） | 大多数问题 |
| B | 空结果升级（串行，按策略表改道） | **本基线默认** |
| C | 升级阶段并发（仅在升级时并发 2~3 路做融合） | 升级时的默认动作 |
| D | 常态并发 | **仅对策略表中白名单的问题类型开启**，不全局开 |

**已决策（2026-09-12）**：采用上述四档——常态单通道、空结果串行升级为默认、升级阶段可并发、常态并发仅白名单。即全局不开常态并发，按问题类型逐条白名单开启，既避免"停在原地"，又不让成本常态化。

### 10.2 Q7 释义：文件密级简化

**背景**：治理排查中发现，密级推导 `_derive_info_level` 存在"管理单位抬级"缺陷——建设单位（is_admin）的 L3 用户被抬到 confidential，导致其经节点参与看到机密文件。梳理后确认文件密级共 4 级（0公开/1内部/2机密/3绝密），且与 SOP 安全等级命名存在冲突。

**已决策（2026-09-12）**，共四条：

1. **系统管理员即 L6**：`_derive_info_level` 仅 `level >= 6` 返回 confidential，删除"管理单位抬级"分支。
2. **上传人可定密级**：文件密级由上传者上传时确定（保留现有 `confidentiality` 字段语义）。
3. **机密为白名单制**：机密(2) 仅 ①上传者 / ⑥系统管理员(L6) / ④显式授权 可见；节点/项目参与不再自动放行机密文件。
4. **现有绝密降级为机密**：取消绝密(3)，存量绝密文件统一降级为机密(2)；联动同步 `env-test` 模拟环境种子数据（改 0 基三档 + CASE 标签 + 帮助文案）。

**结果**：文件密级收敛为 `0=公开 / 1=内部 / 2=机密（白名单制）`。
