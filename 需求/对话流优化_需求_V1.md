# 对话流优化 — 需求文档

> **版本**：V1.0
> **编制日期**：2026-07-24
> **背景来源**：2026-07-24 22:45 / 22:49 两次测试，用户单句提问触发 7 次 LLM 调用、900+ 行抓包且回复为"抱歉"的劣化现象分析
> **关联日志**：`emily-data/logs/llm_trace.md`（1066 行，7 次调用）、`emily-data/logs/emily_20260724.log:251-280`

## 1. 问题背景

### 1.1 现象

用户李景利连续两轮提问"今天项目有什么进展？"、"当前有哪些运转中的节点？"，系统表现：

- **回复质量差**：两轮均回复"抱歉，查询出现问题/遇到参数错误…"
- **抓包体量异常**：单轮对话产生 3 次同步 LLM 调用，md 抓包 900+ 行
- **Token 消耗高**：单轮 3 次调用合计 prompt ~7800 tokens，全用 `deepseek-reasoner`

### 1.2 7 次调用画像（实测）

| # | 阶段 | model | prompt+completion | 推理 token | 输出 |
|---|------|-------|-------------------|-----------|------|
| 0 | 路由 | reasoner | 5210+129 | 83 | `{"sop_id":"SOP-005-QRY"}` |
| 1 | 合成回复 | reasoner | 2193+95 | 53 | "抱歉，查询出现问题…" |
| 2 | 审核回复 | reasoner | 340+63 | 57 | `{"issues":[]}` |
| 3 | 路由 | reasoner | 5256+182 | 136 | `{"sop_id":"SOP-005-QRY"}` |
| 4 | 合成回复 | reasoner | 2240+115 | 71 | "抱歉，遇到参数错误…" |
| 5 | 审核回复 | reasoner | 345+90 | 84 | `{"issues":[]}` |
| 6 | 会话摘要 | reasoner | 602+759 | 598 | 摘要文本（异步） |

### 1.3 根因分层

| 层级 | 性质 | 描述 |
|------|------|------|
| **P0** | 代码 bug | [param_extractor.py:154](emily-core/emily_core/skill/param_extractor.py#L154) 调 `chat_json(prompt)` 少传 `user_message`，导致所有 `source:user_input` 必填参数提取抛 `TypeError`，查询类 SOP 全挂——**已于本次修复** |
| **P1** | 设计优化 | 模型选择、参数提取冗余往返、Guardian 审核对查询类无价值 |
| **P2** | 架构重构 | system prompt 膨胀、历史消息管理失控、节点串行化 |

## 2. 优化目标

| 指标 | 当前 | 目标 |
|------|------|------|
| 简单查询的同步 LLM 调用数 | 3 次（路由+合成+审核） | 1-2 次 |
| 单次 system prompt token | 5000+ | 路由 ≤1500，合成 ≤2000 |
| 查询类 SOP 回复成功率 | 0%（bug 修复前） | ≥95% |
| 单轮抓包行数 | 900+ | ≤400 |
| 简单查询端到端延迟 | ~4 秒（3 次 reasoner 串行） | ≤2 秒 |

## 3. P1 — 短期优化（低改动、高收益）

### P1-1｜按节点选择模型，reasoner 降级为 chat

**问题**：7 次调用全用 `deepseek-reasoner`。路由（输出 `sop_id`）、审核（输出 `issues`）是结构化轻量任务，不需要思维链。

**方案**：
- 路由节点（SessionAgent 意图识别）：改用 `deepseek-chat`
- 审核回复节点（Guardian review_reply）：改用 `deepseek-chat`
- 合成回复节点（node4）：保留 `deepseek-reasoner`（需基于 step 结果组织自然语言）
- 会话摘要：保留 `deepseek-reasoner`（需合并摘要，推理有价值）

**改动位置**：[session_agent.py](emily-core/emily_core/session/session_agent.py) 意图识别调用、[real_guardian.py:122](emily-core/emily_core/workitem/pipeline/real_guardian.py#L122) review_reply 调用、[client.py](emily-core/emily_core/infrastructure/llm/client.py) 增加按用途选模型的参数。

**验收**：路由/审核调用日志 model 字段为 `deepseek-chat`；合成/摘要仍为 `deepseek-reasoner`。

### P1-2｜路由阶段一并输出 query_type，省掉 step-01 参数提取往返

**问题**：路由已判定 SOP-005-QRY（查询类），但 `query_type` 枚举（event/task/meeting/file/message/summary）又拆到 step-01 由 LLM 单独提取——多一次往返，且这次恰是 P0 bug 打挂的环节。

**方案**：
- 扩展路由 JSON schema：`SOP-005-QRY` 命中时附带 `query_type` 字段
- 路由 prompt 增加枚举映射说明（"进展/动态→summary"、"事件→event"、"任务→task"…）
- SkillExecutor 对 SOP-005-QRY step-01：若路由已输出 query_type，直接注入，跳过 LLM 提取

**改动位置**：[session.md](emily-data/prompts/session.md) 路由输出格式、[workitem_agent.py](emily-core/emily_core/workitem/workitem_agent.py) node2 传参、[executor.py:101](emily-core/emily_core/skill/executor.py#L101) 参数预填逻辑。

**验收**：单轮查询的 LLM 调用从 3 次降为 2 次（路由+合成）；query_type 正确派生。

### P1-3｜查询类 SOP 跳过 Guardian 审核回复

**问题**：Guardian review_reply 对"抱歉"类回复几乎永远输出 `{"issues":[]}`（实测 2 次均空）。合成回复本身基于 step 结果诚实生成，LLM 不会主动产生幻觉/矛盾。对 L1 风险（查询类）审核是纯浪费。

**方案**：
- 按风险等级门控：L1（查询类）跳过 review_reply；L2/L3（录入/删除类）保留
- 风险等级由 SOP 元数据或 step 工具类型判定（query_data → L1，record_* → L2，discard/delete → L3）

**改动位置**：[workitem_agent.py](emily-core/emily_core/workitem/workitem_agent.py) node4 调用 review_reply 前加风险判断、[real_guardian.py:110](emily-core/emily_core/workitem/pipeline/real_guardian.py#L110) review_reply 入口。

**验收**：查询类 SOP 不再产生审核 LLM 调用（jsonl 中无 call[2]/[5] 等价记录）；录入类仍审核。

## 4. P2 — 中期重构（结构性改动）

### P2-1｜system prompt 分层裁剪

**问题**：路由和合成都塞了完整 system prompt（角色+世界书+规则书全文+系统自我描述+9 个 SOP 步骤+20 工具描述+路由规则），5000+ tokens。各节点实际只需要子集。

**方案**：按节点组装 prompt：
- **路由节点**：角色简介 + SOP 目录（仅编号+一句话说明）+ 路由规则 + 输出格式。去掉规则书全文、工具描述、系统自我描述。
- **合成节点**：执行 Agent 角色 + 可用工具清单 + 回复合成规则 + 格式约束。去掉 SOP 目录、路由规则、规则书全文。
- **审核节点**：维持现状（已精简，340 tokens）。
- 规则书/世界书/系统自我描述作为"按需检索"内容，仅当用户问题涉及元认知或规则判断时注入（见 SOP-999-SYS bypass 路径已有此机制）。

**改动位置**：[session_context.py](emily-core/emily_core/session/session_context.py) prompt 组装、[session.md](emily-data/prompts/session.md) / [workitem.md](emily-data/prompts/workitem.md) 模板拆分。

**验收**：路由 prompt ≤1500 tokens；合成 prompt ≤2000 tokens；回复质量不下降（emy-test 回归）。

### P2-2｜历史消息按发送者过滤 + 摘要频率提升

**问题**：
1. 历史消息混入其他用户消息（"张工，3#楼…"系列是别人发给张工的，非当前用户李景利），污染意图识别
2. 大量裸 user 消息无 assistant 配对
3. 摘要仅在会话过期归档时合并（实测 23:00:22 才 consolidate），会话存活期间历史无限增长

**方案**：
- 历史消息按 `sender_id` 过滤：只塞当前用户的消息 + Emily 的回复
- 历史窗口限制：最近 N 轮（建议 N=4）完整 user+assistant 配对，更早的走摘要
- 摘要频率：每 5 轮触发一次摘要 consolidation，不等归档

**改动位置**：[session_agent.py](emily-core/emily_core/session/session_agent.py) 历史组装、[session_context.py](emily-core/emily_core/session/session_context.py) 摘要触发逻辑。

**验收**：抓包中 messages 不含其他 sender 的 user 消息；会话超过 5 轮后历史条数稳定（不随轮数线性增长）。

### P2-3｜简单查询的快路径合并（路由+合成一体化）

**问题**：4 节点管道对简单查询过度串行。路由判定 SOP 后，仍要 node2 执行 → node4 合成，每次重发 system prompt。

**方案**（探索性，需评估）：
- 对 L1 查询类 SOP 且单工具调用（如纯 query_data）：路由阶段直接带工具结果回到合成，合并为 1 次调用
- 或：路由 + 参数提取 + 工具调用在一次 chat_with_tools 中完成（function calling），合成单独 1 次

**前置条件**：P1-2 完成（query_type 路由派生）后再评估，避免参数提取环节阻塞。

**验收**：简单查询端到端 ≤2 秒；同步 LLM 调用 ≤2 次。

## 5. 优先级与依赖

```
P0 (已修) ──┐
            ├──> P1-1 (模型选择)      独立可做
            ├──> P1-2 (路由派生 query_type)  独立可做
            └──> P1-3 (Guardian 风险门控)    独立可做
                       │
                       v
                P2-1 (prompt 分层)  ── 依赖 P1 验证回复质量不降
                P2-2 (历史过滤)
                P2-3 (快路径合并)   ── 依赖 P1-2
```

| 项 | 改动量 | 风险 | 建议时序 |
|----|--------|------|----------|
| P1-1 | 小（模型参数） | 低 | 立即 |
| P1-2 | 中（prompt + 传参） | 中（路由 JSON 准确性） | 立即 |
| P1-3 | 小（风险门控） | 低 | 立即 |
| P2-1 | 大（prompt 重构） | 中（回复质量回归） | P1 验收后 |
| P2-2 | 中（历史组装） | 中（上下文丢失） | P1 验收后 |
| P2-3 | 大（管道改造） | 高（架构变动） | P2-1/P2-2 后 |

## 6. 验收方式

每项优化完成后用 emy-test 回归（遵守 CLAUDE.md 规则，使用 users 表真实 sender）：

```powershell
# 查真实用户
docker exec emily-postgres psql -U emily -d emily -c "SELECT id, username, permission_level FROM users WHERE status = 'active' LIMIT 5;"

# 测试查询类 SOP
uv run python .claude/skills/emy-test/cli.py --managed --llm --message "今天项目有什么进展？" --sender "李景利"
uv run python .claude/skills/emy-test/cli.py --managed --llm --message "当前有哪些运转中的节点？" --sender "李景利"
```

**通过标准**：
- 回复包含实际查询结果（非"抱歉"）
- 抓包行数较优化前减少 ≥50%
- 同步 LLM 调用数符合各项目标
- 日志无 `param_extractor` / `executor Step` WARNING/ERROR
