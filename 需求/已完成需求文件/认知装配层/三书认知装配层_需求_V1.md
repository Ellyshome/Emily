## 1. 问题诊断

### 1.1 根因：三书与 Agent 认知路径断连

论文设计三书为"上下文组织层"，职责是**以摘要先行、按需深入的方式为 Agent 提供公共认知**（论文 §4.2.2）。实际实现经历了两个极端：

| 阶段 | 做法 | 问题 |
|------|------|------|
| 早期 | 三书全文灌入 session prompt | 上下文爆炸、M4 前缀缓存失效、违反"摘要先行" |
| P1-1 | 砍掉三书占位符 + 工具/Schema/文件/模板目录全量注入 | **矫枉过正**：连摘要/索引也一并删除，三书与 Agent 彻底断连 |

### 1.2 现状证据（已核实）

| 书 | 灌入 SessionContext | 进 prompt | 其他消费方 |
|---|---|---|---|
| 世界书 | ✅ 全文读入内存 | ❌ 占位符已删 | 归档头部仅记字符数；偏差检测/世界书服务（运维侧） |
| 规则书 | ✅ 全文读入内存 | ❌ 占位符已删 | 归档头部仅记字符数；`RuleBookLoader` 注释仍写"注入 {rule_book}"（过时） |
| 认知书 | ✅ 按权限裁剪后读入 | ❌ 占位符已删 | 归档头部仅记字符数；REST API `/api/v1/meta-cognition/*`（运维侧） |

**结论**：三书在会话链路里"装入内存 → 只被数字符数 → 丢弃"，对 LLM 不可见。论文设计的"上下文组织层"退化为"运维展示工件"。

### 1.3 跑偏根因

把"三书不该全文灌入"误读为"三书不该进 prompt"。正确做法是：**三书摘要进 prompt（常驻索引）、全文走工具检索（按需深入）**——这正是论文原意。

## 2. 设计目标

**一句话**：把三书从"运维工件"接回"Agent 认知输入"，按"摘要常驻 + 全文按需"的原设计落地，使无状态 LLM 在每次会话获得**最小充分的系统认知与态势感知**，并具备按需深入检索与受控操作的能力。

### 2.1 与论文设计对齐

| 论文概念 | 论文职责（§4.2.1-4.2.2） | 本需求落地 |
|---|---|---|
| 项目态势书（世界书） | 项目节点/事件骨架的信息地图 | 摘要常驻（节点骨架，按 authorized_node_ids 裁剪）+ 工具取全文 |
| 组织规则书（规则书） | 适用约束，语义检索+元数据筛选 | 摘要常驻（适用规则标题列表，按 level 裁剪）+ 工具取全文 |
| 系统能力书（认知书） | 可调用能力元数据，Agent 先匹配再加载 | 摘要常驻（可见表/工具/权限骨架，按 db_perms 裁剪）+ 工具取全文 |
| 摘要先行、按需深入 | 不全文灌入，摘要注入+按需检索 | 常驻摘要 + `meta_cognition_read` 工具 |

### 2.2 与现有架构对齐

| 现有机制 | 本需求如何利用 |
|---|---|
| M4 前缀缓存（base 字节稳定） | 摘要进阶段2 变量替换（Session 级稳定），不破坏 base |
| P1-1 的 `get_prompt_variables` | 恢复被删的映射，但值改为裁剪摘要而非全文 |
| `SessionDataFetcher` 全量采集 | 三书已采集，仅补摘要裁剪函数 |
| `refresh()` 热更新 | 摘要随版本号变化自动刷新 |
| 分级兜底 M2 `write_mode` 元数据 | `meta_cognition_read` 归 READ 类，对兜底档可见 |
| 分级兜底 M0 chat_archive 作用域 | 资源检索通道的组成部分 |

## 3. 装配层设计

> **核心理念**：三书是开发者的架构概念（数据来源/生成/维护/裁剪维度），不是 LLM 的 prompt 结构。LLM 看到的是按语义命名的段落（项目态势/信息处理原则/权限分级），不感知"书"的存在。三书摘要自然融入既有段落，不独立标注。

### 3.1 使命与边界（常驻 base，纯静态）

- **回答**：Emily 是谁、为什么存在、行为底线
- **形态**：session.md 顶部 3-5 行，无变量，字节固定
- **内容示例**：*"Emily 是企业工程项目管理团队的信息中枢，使命是让团队协作有据可查、流程规范受控、知识持续沉淀。Emily 不替代人做组织决策，不归属任何个人，是团队的公共大脑。本次调用中，你以 Emily 的路由视角理解用户诉求并输出路由结果。"*
- **改动点**：session.md 模板文字

### 3.2 三书摘要融入既有段落（常驻 base，按语义命名）

- **回答**：现在什么情况（世界书→项目态势）、受什么限制（规则书→信息处理原则/文件处理原则）、系统能力是什么（认知书→权限分级/文件分类）
- **设计原则**：不新增"世界书摘要""规则书摘要"等以书名命名的段落，而是把摘要内容融入 session.md 既有的语义段落
- **新增占位符**（值=裁剪摘要，融入既有段落）：

| 占位符 | 融入哪个段落 | 来源（开发者视角） | 摘要形态 | 裁剪维度 |
|---|---|---|---|---|
| `{project_brief}` | ### 项目态势（补在项目名称/类型/状态之后） | 世界书 `content_text` 前 N 行 / 节点骨架 | ≤200 字 | `authorized_node_ids`（仅可见节点） |
| `{rule_brief}` | ### 信息处理原则 + ### 文件处理原则 | 规则书前 N 行 / 适用规则标题列表 | ≤200 字 | `level`（权限线过滤） |
| `{system_brief}` | ### 权限分级体系 + ### 文件分类体系 | 认知书 D3 权限分级 + D2 文件分类 | ≤200 字 | `db_perms`（仅可见表） |

- **框架简介**：项目态势段补 2-3 行"全景节点"框架说明（三级节点/状态流转/协作模式）；文件分类体系段补 1-2 行文件管理框架（版本链/附件/业务关联）
- **不进路由 prompt 的内容**：工具清单 / 可访问数据表 / 全景节点模板 / 可见文件数——这些是执行层资源，执行层已自带完整 OpenAI function-calling spec（含参数 schema），路由层不需要
- **热重载**：摘要值在 `refresh()` 时随三书版本号变化自动刷新（已有热更新字段）
- **改动点**：session.md 加 3 占位符（融入既有段落）+ `get_prompt_variables` 加 3 映射 + 三书 fetcher 复用裁剪逻辑

### 3.3 全文按需检索（工具层）

- **回答**：需要更详细的项目态势/规则条文/系统能力全文时怎么取
- **新增工具** `meta_cognition_read`：

| 项 | 说明 |
|---|---|
| 工具名 | `meta_cognition_read` |
| 参数 | `book: "world" \| "rule" \| "system"`（必选）；`query: str`（可选，关键词过滤） |
| 行为 | 从 DB/文件取裁剪后全文（复用现有 fetcher 的裁剪逻辑），返回给 Agent |
| 注册 | base 组（READ 类），所有 SOP 可用，兜底档也可见 |
| 关系 | 与 `chat_archive`/`knowledge_search` 同属检索类 |

- **改动点**：`meta_cognition_read` 工具注册 + schema + `tools/registry.py` 登记 + `tools_consistency.py` 元数据

### 3.4 统一检索/操作入口（工具层，执行阶段）

- **回答**：怎么查（检索通道）、怎么动手（受控操作）
- **检索类**（READ，兜底档按白名单开放）：

| 工具 | 作用 | 现状 |
|---|---|---|
| `knowledge_search` | RAG 知识检索 | ✅ 已有 |
| `chat_archive` | 会话历史检索 | ✅ 已有（补群聊作用域，见分级兜底 M0） |
| `query_data` | DB 业务数据查询 | ✅ 已有 |
| `query_files` / `query_node` | 文件/节点查询 | ✅ 已有 |
| `meta_cognition_read` | 三书全文按需检索 | ❌ 新增（3.3） |

- **操作类**（APPEND / TRANSITION / OVERWRITE / DELETE，严格走 SOP + 确认 + 审计）：
  - 经 SOP 路由命中后暴露
  - 高级兜底档放开 APPEND/TRANSITION（见分级兜底计划 M2/M4）
  - OVERWRITE/DELETE 永不进兜底
- **设计原则**：路由层看到"有什么能力"的 SOP 类型树 → 执行层自带完整工具 spec（相当于 -h 自介绍） → 索引与操作分离

## 4. 装配后的 Session Prompt 结构

```

├── 〇、使命与边界（静态，无变量）                  ← 3.1 新增
├── 一、本次调用说明（路由器角色声明）                ← 已有
├── 二、角色与定位                                   ← 已有
├── 三、行为规范
│   ├── 判断视角                                     ← 已有
│   ├── 路由规则                                     ← 已有
│   ├── 信息处理原则  ← 规则书摘要融入（§三-四）     ← 3.2 新增
│   ├── 文件处理原则  ← 规则书摘要融入（§七）        ← 3.2 新增
│   └── 输出契约（output_spec / query_type / constraints / 续接）  ← 已有
├── 四、当前会话上下文
│   ├── 用户身份（姓名/职位/部门/企业/权限/节点）    ← 已有
│   ├── 项目态势      ← 世界书摘要融入 + 全景节点框架  ← 3.2 新增
│   ├── 长期记忆                                     ← 已有
│   └── 往期对话历史（按需检索）                      ← 已有
└── 五、能力与资源
    ├── SOP 类型树（业务流程目录）                     ← 已有
    ├── 权限分级体系  ← 认知书 D3 融入                ← 3.2 新增
    ├── 文件分类体系  ← 认知书 D2 融入 + 文件管理框架   ← 3.2 新增
    ├── 知识库                                        ← 已有
    └── 按需深入引导（meta_cognition_read）            ← 3.3 新增
```

**与 V1 设计的关键差异**：
- 三书摘要不独立标注"世界书摘要""规则书摘要"等标题，而是融入按语义命名的既有段落
- 工具清单/可访问数据表/全景节点模板/可见文件数**不进路由 prompt**——这些是执行层资源，执行层已自带完整 OpenAI function-calling spec

## 5. 缓存策略

| 内容 | 位置 | 稳定性 | 缓存影响 |
|------|------|--------|---------|
| 使命与边界 | base（静态） | 字节固定 | ✅ 不破坏 M4 |
| 路由规则 + 输出契约 | base（静态） | 字节固定 | ✅ |
| 权限变量 | 每条消息渲染 | 每轮可变 | 不进 base（M4 已分离） |
| 三书摘要（项目态势/信息处理原则/权限分级/文件分类） | 阶段2 变量替换 | Session 内稳定 | ✅ Session 级缓存 |
| 三书全文 | 工具结果（消息尾部） | 动态 | 不影响 base |

**代价估算**：常驻摘要 ≈ 3 × ~200 字 + 框架简介 ~200 字 ≈ 增加约 500-800 字（~350-550 tokens），换取 LLM 对项目态势/适用约束/系统能力的认知。相比原三书全文灌入（数万字），代价可接受。且不包含工具清单/表清单/节点模板（省 ~600 字），比 V1 设计更精简。

## 6. 三书生成与刷新策略

| 层 | 职责 | 时机 | 现状 |
|---|---|---|---|
| 权威层 | Builder 生成全量书 → DB/文件 | 事件驱动（偏差检测/人工/调度） | ✅ 已有（`SystemDescriptionService.check_and_update`、`ProjectWorldBookBuilder`、`RuleBookLoader`） |
| 会话视图层 | 从最新权威版做按人裁剪 → SessionContext | 每次 Session 创建 + refresh | ✅ 采集链路已有；裁剪逻辑认知书已有，世界书/规则书需补 |
| 按需检索层 | Agent 用工具取裁剪后全文 | Agent 主动调用 | ❌ 待新增 `meta_cognition_read` |

**关键原则**：
- 生成在权威层（事件驱动、幂等、带版本号），不在会话创建时重建——避免并发重复生成；
- 会话只装载"最新权威版的裁剪视图"——实时性 = 读的是最新版本；
- 热重载在 `refresh()` 中按版本号比对——落后则重取裁剪。

## 10. 待 req-review 审核的开放问题

### Phase 1 开放问题

1. **摘要字数上限**：建议 200 字/项，是否合适？过短可能丢关键骨架，过长影响 base 稳定性。
2. **规则书裁剪维度**：当前规则书是全文 md 文件无元数据标签，"按 level 裁剪"需补什么？是加 frontmatter 标注适用线/级，还是全文取前 N 行？
3. **世界书裁剪实现**：世界书 `content_text` 是 LLM 生成的自由文本，"按 authorized_node_ids 裁剪"具体怎么做？是生成时按节点分段、还是读取后按关键词过滤？
4. **`meta_cognition_read` 的 query 参数**：是否需要语义检索（走 RAG），还是关键词匹配即可？
5. **使命卡内容**：§3.1 的示例文案是否合适？是否需要从论文/白皮书提取更正式的表述？

### Phase 2 开放问题

6. **编排器规划方式**：规则编排（if-else/状态机）vs LLM 编排（调 LLM 做目标分解）vs 混合？简单请求应跳过编排器避免延迟。
7. **依赖 DAG 深度上限**：为防止无限编排，DAG 最大深度建议几层？（建议 3）
8. **动态 WI 生成时机**：WI-1 执行完后，是编排器主动检查"是否需要追加 WI-2"，还是 WI-1 的 structured_result 里带 `suggested_followup` 由编排器消费？
9. **跨域检索的权限边界**：编排器动态追加的 WI 如果跨 SOP，权限按原请求者还是按 WI 自身的 sop_id 校验？
10. **编排器失败回退**：编排器规划失败或 LLM 不可用时，是否回退为当前的"flat 拆分"（is_compound 并行无依赖）？

## 11. 会话编排层（Phase 2）

> **前置依赖**：Phase 1（认知装配）落地——编排器需要装配层注入的能力索引/态势摘要来规划。
> **实施时机**：Phase 1 验收通过后，单独走 req-plan。

### 11.1 问题诊断

当前 SessionAgent 的任务处理是**扁平并行**模型：

```
用户消息 → 路由 JSON → 拆分 WI（平行，无依赖）→ 各自执行 → 合成回复
```

| 能力 | 现状 | 缺口场景 |
|---|---|---|
| 多任务并行 | ✅ `is_compound + sub_tasks`（上限 5，无依赖） | — |
| 多 WI 结果合成 | ✅ `_synthesize_final_reply` LLM 合成 | — |
| WI 间依赖编排 | ❌ WI 列表执行前一次性确定 | "查逾期节点→给每个负责人发提醒"需要先查再发 |
| 动态 WI 生成 | ❌ 无"基于上一步结果追加下一步"机制 | "查项目概况→如果发现风险→创建待解决问题" |
| 跨域检索 | ❌ WI 被锁在单 SOP 工具白名单内 | 信息不足时不能跨 SOP/工具自主查 |
| Session 级规划 | ❌ 无目标分解/计划 | 复杂请求只能靠路由 LLM 一次性猜对 |

### 11.2 设计目标

在 SessionAgent 内注入**编排策略组件**（`SessionOrchestrator`），使会话具备：
- **目标分解**：复杂请求 → 带依赖的 WI DAG（A→B→C）
- **动态生成**：基于上一步 structured_result 决定是否追加下一步 WI
- **跨域检索**：WI 执行中信息不足时，编排器决定"去哪个 SOP/工具查"并动态追加 WI

### 11.3 架构形态：组件注入（不内联）

参照 SessionAgent 已有的 `FocusLock`/`ConfirmQueue`/`SessionScheduler` 模式：

```
SessionAgent
  ├─ context: SessionContext          （已有）
  ├─ focus: FocusLock                 （已有）
  ├─ confirm_queue: ConfirmQueue      （已有）
  ├─ scheduler: SessionScheduler      （已有）
  ├─ orchestrator: SessionOrchestrator （新增）
  │
  └─ _handle_impl 改造后:
       ② _recognize_intent（不变）
       ③ _split_into_workitems → 改为调 orchestrator.plan(intent, context, actor)
          ├─ 简单请求：plan 返回 [wi]（与现在一致，跳过编排器）
          ├─ compound：plan 返回 [wi1, wi2, ...]（并行，与现在一致）
          └─ 依赖请求：plan 返回 [{wi1}, {wi2, depends_on: wi1.id}]（新）
       ④ scheduler.run_all_with_message → 改为支持依赖序执行（run_dag）
       ⑤ 合成回复（不变）
```

**设计原则**：
- 编排器只做"规划"，不做执行/合成/归档；
- SessionAgent 只调 `orchestrator.plan()` 入口，不关心内部实现；
- 编排策略可替换（规则编排 vs LLM 编排 vs 混合），不改 SessionAgent；
- 简单请求（confidence=high, is_compound=false）跳过编排器，零延迟增加。

### 11.4 模块拆分

#### M7: SessionOrchestrator（编排策略组件）

**依赖**：Phase 1（能力索引/态势摘要注入后，编排器可基于装配内容规划）

**层级**：Session 层（与 `FocusLock`/`ConfirmQueue` 同级）

**职责**：接收路由 intent + 会话上下文，产出带依赖关系的 WI DAG

**接口契约**：

| 接口/类 | 类型 | 签名 | 说明 |
|---|---|---|---|
| `SessionOrchestrator` | 类 | — | 编排策略组件 |
| `plan(intent: dict, context: SessionContext, actor: dict) -> list[WorkItemPlan]` | 方法 | 输入路由结果+上下文+操作者；输出 WI 计划 | 主入口 |
| `on_wi_done(wi: WorkItem, done_list: list) -> list[WorkItemPlan]` | 方法 | WI 执行完后回调；返回追加的 WI（动态生成）或空 | 动态追加 |
| `WorkItemPlan` | dataclass | `{wi: WorkItem, depends_on: list[str], dynamic: bool}` | 单个 WI 计划项 |

**规划策略**（初始版本，混合模式）：

| 请求类型 | 策略 | 调 LLM | 说明 |
|---|---|---|---|
| 简单（单 SOP, high confidence） | 直接返回 [wi] | 否 | 零延迟，与现状一致 |
| 并行复合（is_compound） | 拆分 sub_tasks → 平行 WI | 否 | 与现状一致 |
| 依赖复合（需先 A 再 B） | 调 LLM 做目标分解 → 依赖 DAG | 是 | 新增能力 |
| 信息不足（confidence=low/medium） | 先追加"检索 WI"→ 基于结果再规划 | 可选 | 新增能力 |

#### M8: Scheduler 依赖序执行

**依赖**：M7

**层级**：WorkItem 调度层（`SessionScheduler`）

**职责**：支持 WI DAG 的按依赖序执行（现有 `run_all` 只支持并行）

**接口契约**：

| 接口/类 | 类型 | 签名 | 说明 |
|---|---|---|---|
| `SessionScheduler.run_dag(plans: list[WorkItemPlan], ...) -> list[WorkItem]` | 新增方法 | 输入带依赖的 WI 计划；按拓扑序执行 | 依赖序执行 |
| `SessionScheduler.run_all(...)` | 不变 | 保持兼容（简单场景仍用并行） | — |

**执行规则**：
- 拓扑序：无依赖的 WI 可并行；有依赖的等前置完成
- 前置失败：后继 WI 标记 `skipped`（不执行），不抛异常
- 动态追加：每轮 WI 完成后调 `orchestrator.on_wi_done()`，有追加则继续执行
- 深度上限：DAG 最大深度 3（防无限编排，开放问题 #7）

#### M9: 跨域检索编排

**依赖**：M7、M8

**层级**：编排策略（M7 的子能力）

**职责**：WI 执行中信息不足时，编排器动态追加"检索 WI"

**场景示例**：
```
用户："帮我看看翠湖庭院有没有需要注意的质量问题"
  ↓ M7: plan → [WI-1: SOP-005-QRY(query_type=event, filters=[quality])]
  ↓ M8: 执行 WI-1 → 结果：3 条质量事件
  ↓ M7: on_wi_done(WI-1) → 发现事件关联了规范条文
  ↓ M7: 动态追加 WI-2: fallback(knowledge_search, query="相关规范要求")
  ↓ M8: 执行 WI-2 → 结果：规范条文摘要
  ↓ 合成回复："发现 3 条质量事件…根据《XXX规范》…"
```

**边界**：
- 动态追加的 WI 仍受权限校验（actor_snapshot）
- 动态追加只追加 READ 类 WI（检索），不追加写操作（写仍需原 SOP 路由）
- 追加上限 2 个（总 DAG 深度 ≤ 3）

### 11.7 验收标准

| # | 验收项 | 验证方式 |
|---|---|---|
| 1 | 简单请求零延迟 | 单 SOP 请求不调 LLM 编排，响应时间不增 |
| 2 | 依赖请求正确编排 | "查逾期→发提醒"→ WI-1 先执行，WI-2 等 WI-1 结果 |
| 3 | 动态 WI 生成 | WI-1 结果含 `suggested_followup` → 编排器追加 WI-2 |
| 4 | DAG 深度上限 | 超过 3 层时停止追加并回复已有结果 |
| 5 | 前置失败不崩 | WI-1 失败 → WI-2 标记 skipped，不抛异常 |
| 6 | 跨域检索受权限 | 动态追加的检索 WI 不越过 actor 权限 |
| 7 | 编排器回退 | LLM 不可用时回退为 flat 拆分（与现状一致） |

### 11.8 阶段反思指令

Phase 2 实施时，每完成一个模块（M7→M8→M9），进入下一个之前执行：

1. **检查设计完整性**：接口契约、验收检测是否完整；
2. **检查偏差**：是否与 §11.2-§11.4 设计不符；
3. **判断是否继续**：
   - 偏差 ≤ 1 个接口调整 → 直接修正，继续；
   - 偏差 2-4 个接口 → 追加修订记录，继续；
   - 偏差 > 4 个接口或架构方向变化 → **停止**，报告用户决定。
