## 一、总体评价

本文档提出了一个面向项目运维的实时 Web 监控页面需求，动机清晰——Emily 部署在项目本地电脑上，运维人员需要直观了解系统运行状态，这是真实的运维痛点。需求对监控项的列举有合理之处（IM 账号状态、Session 池、全景节点、文件/人员列表），覆盖了运维最关心的几个维度。

然而，文档存在严重的完整性缺陷：仅 13 行描述，缺乏背景说明、目标定义、非功能需求、技术选型、部署方案、数据源获取路径等关键信息。多项监控需求在当前架构下存在明显的技术鸿沟——IM 在线状态无数据源、Session 池跨容器无 API、实时推送机制未定义。如果不补齐这些信息直接进入实施，大概率会走弯路或返工。

核心问题可以概括为：**需求描述的是"看什么"，但没有回答"怎么看"和"从哪看"**。

## 四、替代方案

### 方案 A：emily-core 内嵌监控路由（✅ 推荐）

- **思路**：在 emily-core FastAPI 中新增 `/api/v1/monitor/*` 路由组，同时托管前端静态文件。emily-core 既提供监控 API 又 serve 前端页面
- **优势**：
  - 复用现有 FastAPI 服务，零新增容器
  - Session 池状态可直接从内存获取，无需跨进程通信
  - 复用现有 SSE 机制推送实时数据
  - 部署最简——新增端口映射即可
- **劣势**：
  - emily-core 承担了额外职责（serve 静态文件），但量极小（只读页面），影响可控
  - 端口需从 `127.0.0.1` 改为 `0.0.0.0`，需配合路由级权限控制
- **适用场景**：当前项目规模（单机 5 容器，1-5 个管理员并发访问）

### 方案 B：独立监控容器

- **思路**：新建第 6 个容器（如 `emily-monitor`），内置 Web 服务（如 Node.js + Vue），通过 HTTP 调用 emily-core 监控 API 获取数据
- **优势**：
  - 完全解耦，不影响 emily-core 稳定性
  - 可独立部署/升级前端
  - 安全隔离更清晰（监控容器可暴露端口，core 不变）
- **劣势**：
  - 新增 1 个容器 + 1 套构建流程
  - Session 池状态仍需 emily-core 暴露 API，开发量不减反增
  - 前端技术栈独立，增加维护成本
- **适用场景**：监控需求复杂（告警、历史趋势图、多实例聚合），团队有前端专人维护

### 方案 C：极简静态页 + Docker API

- **思路**：不新增任何后端代码，用纯静态 HTML 页面通过 JavaScript 直接调 Docker Engine API（查容器状态）+ emily-core 现有 API（查节点/文件/人员），浏览器端组装数据
- **优势**：
  - 零后端开发，部署最简（Nginx 静态托管或直接 file:// 打开）
  - 不修改 emily-core 任何代码
- **劣势**：
  - Session 池状态无法获取（无现有 API）
  - IM 账号在线状态无法获取
  - 跨域问题需处理（Docker API、emily-core API 不在同源）
  - 扩展性差，后续需求增长需重构
- **适用场景**：快速出 MVP，仅关注容器运行状态和 DB 数据查询
