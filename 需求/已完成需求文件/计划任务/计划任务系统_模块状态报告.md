## 一、模块概述

计划任务系统实现建设工程项目管理中"生产者-消费者"模式的后端功能：管理者下达工作指标（计划任务），执行者在时效内上传成果，"收货销项"。包含任务模板与实例管理、七态状态机、循环任务自动生成、超时提醒、审计日志、计划外事件匹配、工作流集成。

**技术栈**：Python 3.12 + SQLAlchemy（同步）+ asyncio 后台调度循环。无 APScheduler/Celery，零外部调度依赖。

**当前状态**：✅ P0（6 项）+ P1（5 项）+ P2（5 项）全部修复完成，编译/导入/行为测试通过。模块已具备端到端运行能力，待真实环境有效性测试。

## 四、状态机（七态）

```
                ┌──────────────────────────┐
                │ ANOMALY_PENDING_REVIEW   │ ← 鉴权异常（发起人权限 < 执行人）
                └────────────┬─────────────┘
                  approve ↓     ↓ reject
 None → WAITING ←────────┘     CANCELLED(终态)
         │
         ↓ submit
       SUBMITTED ←──── resubmit ──── RETURNED
         │  │                          ↑
   confirm   return ──────────────────┘
         ↓
       CONFIRMED
         ↓ archive
       ARCHIVED(终态)
```

**合法流转**（`ALLOWED_TRANSITIONS`）：

| 当前状态 | 可流转到 |
|----------|----------|
| None（新建） | WAITING、ANOMALY_PENDING_REVIEW |
| WAITING | SUBMITTED、CANCELLED、ANOMALY_PENDING_REVIEW |
| ANOMALY_PENDING_REVIEW | WAITING（approve）、CANCELLED（reject） |
| SUBMITTED | CONFIRMED、RETURNED、CANCELLED |
| RETURNED | SUBMITTED、CANCELLED |
| CONFIRMED | ARCHIVED、CANCELLED |
| ARCHIVED | （终态，不可变） |
| CANCELLED | （终态） |

- 非法流转 → `InvalidStateTransitionError`
- 终态修改 → `ArchivedTaskError`
- 实例不存在 → `TaskNotFoundError`
（三者均为 `ValueError` 子类，向后兼容）

```

       ├─ 5. 自动归档
       ├─ 6. 自动升级（超期 N 天）
       └─ 7. 工作流重试
```

## 六、核心机制详解

### 6.1 调度引擎 `_tick`（7 步，分布式锁保护）

**分布式锁**：用一个独立裸 Session（`get_session_raw`）跨整个 `_tick` 持有 `pg_advisory_lock`，`finally` 显式 `pg_advisory_unlock`。advisory lock 绑定连接，session 关闭即释放——故必须跨整 tick 保持同一 session，否则锁失效。多进程部署时其他进程 `pg_try_advisory_lock` 返回 false 直接跳过。

**七步**：
1. **超时检测**（`scheduler_overdue_check_interval` 节流）：扫描 `deadline_at < now` 的 WAITING 任务，通知执行者，`set_reminded_at`。
2. **临近截止提醒**（`scheduler_reminder_before_minutes`）：扫描 `deadline_at - now < N分钟` 且未提醒的 WAITING 任务，通知执行者。
3. **循环任务生成**（三触发）：
   - 主动补齐：遍历所有 ACTIVE 循环模板，确保当前周期实例存在（新激活模板首次 tick 即生成）
   - 归档触发：上一轮归档 → LLM 推算下一周期 → 生成
   - 容错补齐：已过期未归档/未取消的循环任务 → 补齐当前周期
4. **LLM 失败通知**：扫描 `llm_calculation_failed=True && !llm_failure_notified` 的**模板**，通知发起人人工处理，标记已通知。
5. **自动归档**：CONFIRMED → ARCHIVED。
6. **自动升级**（`scheduler_escalate_after_overdue_days`）：超期 N 天未升级的 WAITING 任务 → `escalate_to_supervisor`（转派执行人上级，记录 `escalated_at`/`original_executor_id`，`escalated_at IS NULL` 防重复升级）。
7. **工作流重试**：`retry_pending_workflow_starts`（CONFIRMED 且无 workflow_instance_id 的实例重试启动工作流）。

### 6.2 LLM 推算与降级（§2.4）

`_calc_current_period` / `_calc_next_period` 调 LLM 解析 `deadline_rule`（如"每周五17:00"）推算 `period_key` + `deadline_at`。

**降级策略**（对齐计划）：LLM 不可用或调用失败 → 抛 `LLMCalculationError`（**不做自动兜底推算**）→ 调用方 `mark_template_llm_failed` 标记模板 → step 4 通知发起人人工处理。推算成功时 `clear_template_llm_failed` 自愈（下次失败可重新通知）。

### 6.3 鉴权与异常标记

`_authorize_task_creation`：发起人 `permission_level < 执行人 permission_level`（如业务执行者向主管下达）→ 状态设为 `ANOMALY_PENDING_REVIEW`，记录 `supervisor_id` 供上级复核。上级 `review_anomaly_task`（approve→WAITING / reject→CANCELLED）。

### 6.4 计划外事件匹配（§2.5）

`PlanTaskMatchHook`（`before:wi_node3`）：对 `record_event`/`record_task` 步骤，提取上传上下文（项目/阶段/内容），调 `match_or_create_unscheduled`：
- 精确匹配（同项目+同阶段+同执行人+时间窗口±7天）→ 关联已有计划任务
- 无匹配 → 创建计划外实例（`is_unscheduled=True`）并自动提交
- 仅对带项目上下文的步骤触发；结果存入 `context.baggage["plan_task_matches"]`；永远 ALLOW（不阻断 SOP 流程）。

### 6.5 工作流集成（§4.4）

`WorkflowIntegrator`：
- `confirm_task` 后 → `start_workflow_after_confirmation`（按模板 `workflow_definition_key` 启动工作流实例，回写 `workflow_instance_id`）
- scheduler step 7 → `retry_pending_workflow_starts`（补偿未启动的）
- `workflow_client` 当前为 None（代码库无现成工作流系统），**接线已就位，待 client 注入即生效**。

### 6.6 事务边界（§4.6）

所有状态流转方法用 `with get_session() as session:` 共享事务，"状态变更 + 审计日志（+成果）"原子提交，任一步失败整体回滚。repo 的 `create`/`update_status`/`log.create`/`deliverable.create` 支持可选 `session` 参数（向后兼容）。

### 6.7 时区归一化（§5.4）

`_to_utc_iso`：写入 `deadline_at` 时归一化为 UTC ISO8601（naive 视为北京时间）。`_parse_iso_utc`：解析为 UTC datetime。保证 `find_overdue`/`find_near_deadline` 字符串比较可靠。

## 十、有效性测试指南

> 以下用例供你进一步测试模块有效性。建议用 `/emy-test` skill 对 Docker 内 emily-core 容器发模拟消息验证；涉及调度的用例需等待 tick 或临时调小 `scheduler_tick_seconds`。

### 10.1 测试前置条件

1. **数据库**：PostgreSQL 已建表（首次启动 `create_all` 自动建；若表已存在需补索引 DDL，见 3.2）。
2. **LLM**：配置 `llm_api_key`（循环任务推算截止时间依赖 LLM；无 LLM 时循环模板会被标记失败并通知）。
3. **用户数据**：至少 2 个用户，`permission_level` 不同（测鉴权异常）；为执行人配置 `supervisor_id`（测升级）。
4. **项目数据**：至少 1 个项目（测计划外匹配 + project_name 解析）。
5. **调度**：`scheduler_enabled=true`；测试时建议 `scheduler_tick_seconds=5` 加速。

### 10.2 端到端用例

#### 用例 A：一次性任务全生命周期（核心路径）
**步骤**：
1. 发消息触发 `record_plan_task`（title="提交周报"、executor_name=执行人姓名、deadline_at=未来时间、project_name=项目名）
2. 发消息触发 `submit_plan_task`（instance_no=上一步返回编号、content="周报内容"）
3. 发消息触发 `review_plan_task`（instance_no、action=confirm）
4. 等待调度 tick（step 5 自动归档）

**预期**：
- 步骤 1：实例创建，状态 WAITING，`instance_no` 返回；`executor_id`/`project_id` 已解析填充
- 步骤 2：状态 WAITING→SUBMITTED，`plan_task_deliverables` 有记录，`plan_task_logs` 有日志
- 步骤 3：状态 SUBMITTED→CONFIRMED；若有 `workflow_definition_key` 触发工作流（client 注入后）
- 步骤 4：状态 CONFIRMED→ARCHIVED

**验证点**：`select status, submitted_at, confirmed_at, archived_at from plan_task_instances where instance_no='...'` 状态依次推进；`plan_task_logs` 每步有 from→to 记录。

#### 用例 B：循环任务自动生成
**步骤**：
1. 触发 `record_plan_task`（is_recurring=true、deadline_rule="每周五17:00"、executor_name、project_name）
2. 等待调度 tick（step 3 主动补齐）

**预期**：
- 步骤 1：模板创建（DRAFT→ACTIVE），返回 `template_no`；回复"调度机将自动生成每期任务实例"
- 步骤 2：tick 后 `plan_task_instances` 生成当前周期实例（period_key 如 `2026-W26`），状态 WAITING，`deadline_at` 由 LLM 推算

**验证点**：`select * from plan_task_templates where template_no='...'` status=ACTIVE；`select instance_no, period_key, deadline_at from plan_task_instances where template_id='...'`。
**幂等验证**：再等一个 tick，不应重复创建同 period_key 实例（`uq_pti_period` 约束 + 应用层检查）。

#### 用例 C：鉴权异常标记
**前提**：用户 A（permission_level=1）向用户 B（permission_level=2）下达任务。
**步骤**：触发 `record_plan_task`（executor_name=B）
**预期**：实例状态为 `ANOMALY_PENDING_REVIEW`（非 WAITING），`anomaly_reason` 记录原因，回复提示"等待上级复核"。
**验证点**：`select status, anomaly_reason from plan_task_instances ...`。
**后续**：上级 `review_anomaly_task`（approve→WAITING / reject→CANCELLED）。

#### 用例 D：计划外事件匹配
**步骤**：发消息触发 `record_event`（带 project_name、description=成果内容、phase_code）
**预期**：`PlanTaskMatchHook` 在 `before:wi_node3` 触发：
- 若有匹配的挂起计划任务 → 关联（`plan_task_deliverables` 记录到该实例）
- 若无匹配 → 创建计划外实例（`is_unscheduled=True`），自动 SUBMITTED
**验证点**：`select is_unscheduled, anomaly_reason from plan_task_instances where is_unscheduled=true`；`context.baggage["plan_task_matches"]` 有记录（日志可见）。
**无项目上下文**：`record_event` 不带 project_name → 不触发匹配（hook 跳过）。

#### 用例 E：超时提醒
**步骤**：创建一个 `deadline_at` 已过去的 WAITING 任务，等待 tick（注意 `scheduler_overdue_check_interval` 节流，首次会执行）。
**预期**：执行者收到超时通知（`_OVERDUE_TEMPLATE`），`reminded_at` 更新。
**验证点**：`select reminded_at from plan_task_instances ...`；出站消息含超时通知。

#### 用例 F：LLM 失败降级
**步骤**：不配置 LLM（或 LLM 不可用），创建循环模板，等待 tick。
**预期**：
- `_calc_current_period` 抛 `LLMCalculationError`（无兜底）
- 模板 `llm_calculation_failed=True`
- step 4 通知发起人"无法自动推算截止时间，请手动设定"
- 不创建错误截止时间的实例
**验证点**：`select llm_calculation_failed, llm_failure_notified from plan_task_templates ...`；发起人收到通知。
**自愈**：配置 LLM 后下一 tick 推算成功 → `llm_calculation_failed` 清零。

#### 用例 G：超期自动升级
**前提**：执行人配置 `supervisor_id`；创建 `deadline_at` 早于 `now - scheduler_escalate_after_overdue_days` 的 WAITING 任务。
**步骤**：等待 tick（step 6）。
**预期**：`escalate_to_supervisor` 转派，`executor_id`=上级、`original_executor_id`=原执行人、`escalated_at` 有值、`escalation_reason` 记录。
**验证点**：`select executor_id, original_executor_id, escalated_at from plan_task_instances ...`。
**防重复**：再等 tick，已升级任务（`escalated_at` 非空）不再升级。

#### 用例 H：归档不可变
**步骤**：对一个 ARCHIVED 实例调用 `submit_plan_task` 或 `review_plan_task`。
**预期**：抛 `ArchivedTaskError`（ValueError 子类），回复"已处于终态，不可修改"。
**验证点**：状态不变，无新日志。

#### 用例 I：状态机非法流转
**步骤**：对 WAITING 实例直接调 `review_plan_task`（confirm）—— 跳过 submit。
**预期**：抛 `InvalidStateTransitionError`（WAITING→CONFIRMED 非法）。
**验证点**：状态保持 WAITING。

#### 用例 J：实例不存在
**步骤**：`submit_plan_task`（instance_no="PTI-不存在"）。
**预期**：抛 `TaskNotFoundError`，回复"找不到任务实例"。

#### 用例 K：分布式锁（多进程）
**步骤**：起两个 emily-core 进程，同时触发 tick。
**预期**：`pg_try_advisory_lock` 使其中一个跳过，日志可见"其他进程已在处理"；不会重复处理同一任务。
**验证点**：`select * from pg_locks where locktype='advisory'`；任务不重复归档/通知。
