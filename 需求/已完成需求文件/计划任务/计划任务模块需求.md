## 一、概念定义

### 1.1 术语更名
- **原**：定时任务系统
- **新**：计划任务系统 (Scheduled Task System)
- **原因**：避免与技术层面的"定时调度器"混淆，更准确体现"预定、有计划"的业务含义

### 1.2 信息上传机制分类
信息上传机制本质上分为两类：

1. **主动录入模式**：用户主动上报计划外工作
   - 示例：建设单位内业上报某时间接待临时到访人员信息

2. **生产者-消费者模式**：管理者下工作指标给执行者，执行者在时效内上传工作成果
   - 示例：主管指派任务，下属完成后提交

### 1.3 与工作流的关系
- 计划任务是**前置**：提前预定未来要发生的工作，等待"收货销项"
- 收到预料中的成果上传后，继续执行一般工作流
- 一般工作流若无对应计划，则标记为**计划外事件**
  - 可能原因1：主管人员忘记录入任务
  - 可能原因2：上传信息与挂起任务匹配失败
  - 可能原因3：纯意外事件（如临时访客）

## 二、核心设计原则

### 2.1 计划外事件标记
- 所有上报信息若无对应挂起任务，单独标记为「计划外事件」
- 用途：未来项目复盘时作为数据分析参考

### 2.2 状态机设计理念
- **状态机本质**：仪表盘功能，不自主行动
- **设计模式**：所有状态设计为「等待XX」模式，由调度机/执行模块驱动流转
- 状态不包含业务逻辑，仅反映当前所处阶段

## 三、状态机设计

### 3.1 状态定义
| 状态 | 说明 | 触发者 |
|------|------|--------|
| **等待执行** | 任务已创建，等待开始时间/执行者处理 | 调度机 |
| **已提交等待确认** | 执行者已提交成果，等待发起人确认 | 执行者提交 |
| **已退回等待更新** | 成果不符合要求，退回执行者修改 | 发起人退回 |
| **已确认待归档** | 成果已确认，等待归档入库 | 发起人确认 |
| **已归档** | 任务完成，数据已归档 | 调度机/执行模块 |

### 3.2 状态机字段
状态机至少包含以下字段：
- 任务发起人
- 执行人
- 任务描述
- 截止时间
- 成果要求核验标准（JSON格式存储）
- 当前状态
- 任务节点归属（外键关联项目总状态机）
- 状态变更日志（记录全生命周期，每次更新存档）

### 3.3 状态流转规则
```
等待执行 → 已提交等待确认 → 已退回等待更新 → 已提交等待确认 → 已确认待归档 → 已归档
                                    ↓
                                (可循环)
```

## 四、核心功能模块

### 4.1 执行模块（调度机）
负责维护计划任务系统，职责包括：
- 任务新增
- 状态路由流转
- 对外交互（与工作流、提醒系统集成）
- 归档入库

### 4.2 任务生成机制
#### 一次性任务
- 直接创建单个任务实例

#### 循环任务
- **底层实现**：本质仍是一次性任务
- **循环逻辑**：一轮任务完成后，由调度机根据模板规则自动生成下一轮任务
- **循环时间**：在任务需求中与用户沟通明确，无特殊要求则持续循环
- **中断处理**：
  - 执行者离职、失能等意外情况
  - 请求其顺位上级处理（接手或重新指派）

### 4.3 鉴权机制
- 任务发起时对任务与发起人进行鉴权
- **异常场景**：业务执行者权限的用户，向主管下达任务
  - 处理方式：标记为异常
  - 复核流程：由其直接上级复核后决定（下发 or 终止退回）

### 4.4 归档机制
- 状态流转至「已确认待归档」时，由调度机触发归档
- 归档数据持久化至数据库
- 归档后任务不可变更

### 4.5 审计日志
- 状态机单独设日志字段
- 记录执行全生命周期
- 每次状态更新都存档快照
- 技术依赖：PostgreSQL

## 五、成果核验标准设计

### 5.1 存储方式
- 使用JSON格式灵活存储核验规则
- 由前端SOP模块负责具体校验逻辑
- 本模块只存储规则，不做校验

### 5.2 规则示例
```json
{
  "requiredFields": ["fileUrl", "description"],
  "fileTypes": [".pdf", ".docx"],
  "minFileSize": 1024,
  "customRules": []
}
```

## 六、与工作流集成

### 6.1 集成模式
- 采用「确认后启动工作流」模式
- 计划任务确认后，启动后续一般工作流
- 工作流实例ID与任务实例关联

### 6.2 数据流向
1. 计划任务：负责前置预定、成果收集确认
2. 工作流：负责后续标准化业务流程
3. 两者通过任务实例ID关联

## 七、意外处理

### 7.1 超时提醒
- **临近提醒**：截止时间前1小时，提醒执行者
- **超时通知**：
  - 告知任务负责人
  - 告知执行者已超时

### 7.2 幂等性处理
- 使用**唯一业务键**保证不重复创建
- 唯一键规则：`template_id + date_period`
  - 示例：周报模板 + 2024年第25周 = 唯一标识
- 重复创建时直接返回已有实例，无需人工确认

### 7.3 高并发
- 暂不考虑高并发场景
- 依据：普通地产项目任务频率不会超过系统压力上限

## 十、使用场景

### 场景1：周报、日报类循环任务
- **描述**：特定范围的几家公司指定对接人需定时上传报告（日报、周报）
- **机制**：发起人设定固定周期循环执行
- **提醒**：定期时间未收到则提醒，提前收到则不再提醒

### 场景2：一次性指派具体任务
- **示例**：建设单位景观工程主管下达任务给景观承包单位负责人
  - 任务内容：某编号施工界面在本月20日前完成地面石材铺装
- **机制**：上传完工申报时，自动关联挂起的计划任务
- **集成**：按公司规定的一般完工确认SOP业务流程，引导提交符合预期的成果
  - 口语格式化整合
  - 信息与附件完整度确认

## 十一、数据库设计概要

### 核心表结构

#### plan_task_template（任务模板）
- id, name, description
- initiator_id, executor_id
- deadline_rule（Cron表达式或固定日期）
- verification_standard（JSON）
- task_type（ONCE / WEEKLY / MONTHLY）
- workflow_definition_key
- status（DRAFT / ACTIVE / INACTIVE）
- created_at, updated_at

#### plan_task_instance（任务实例）
- id, template_id
- period_key（周期标识，如2024-W25、2024-M06）
- executor_id
- deadline_at
- status（等待执行 / 已提交等待确认 / 已退回等待更新 / 已确认待归档 / 已归档）
- submitted_at, confirmed_at
- workflow_instance_id
- created_at, updated_at

#### plan_task_log（状态变更日志）
- id, instance_id
- from_status, to_status
- operator_id, reason
- snapshot（JSON快照）
- created_at

#### plan_task_deliverable（任务成果）
- id, instance_id
- type（FILE / TEXT / JSON）
- content / file_url
- submitted_by, submitted_at

## 十二、实施优先级

| 优先级 | 功能模块 | 说明 |
|--------|----------|------|
| **P0** | 一次性任务基础功能 | 创建、提交、确认、状态流转 |
| **P0** | 简单循环任务 | 按周/按月生成下一轮任务 |
| **P1** | 基础提醒功能 | 临近截止、超时提醒 |
| **P1** | 工作流集成 | 确认后启动后续流程 |
| **P2** | 反向下达复核机制 | 执行者向主管下达任务的异常处理 |
| **P2** | 计划外事件分析 | 先标记，分析功能后续实现 |
