# 异常处理日志修复计划

> **目标**：全量修复 `emily-core/emily_core/` 中"静默吞异常"的 `except` 块，确保所有意外异常都有 log 记录，恢复系统可观测性。
>
> **执行者**：AI 开发工具（本文档自包含，无需额外上下文）
> **预估改动**：26 处 `except` 块，涉及 18 个文件
> **风险等级**：低（仅添加 log 语句，不改业务逻辑）
>
> ← 返回 [CLAUDE.md](../CLAUDE.md)

## 一、背景

Emily 项目在排查"世界书生成异常"时发现：部分 `except` 块用 `pass` 或 `return 默认值` 静默吞掉异常，**导致系统出错时 log 文件里毫无痕迹**，调试困难。最讽刺的是，有些静默吞异常的函数本身就是日志/遥测助手（如 `_log_business_event`）——日志功能自己坏了也不出声。

本计划对全量 `except` 块做分类审计，定位所有"静默吞意外异常"的位置，并给出逐项修复方案。

## 二、审计概况

## 三、修复原则

### 3.1 判定标准：哪些该修，哪些不修

| 异常类型 | 是否需 log | 说明 |
|---------|-----------|------|
| `except Exception` / `except Exception as e`（宽异常） | ✅ **必须 log** | 捕获所有意外，不 log = 丢线索 |
| 裸 `except:` | ✅ **必须 log**（本项目无） | 同上 |
| `except (ValueError, TypeError)` | ❌ 不需 | 预期的类型转换回退，是控制流 |
| `except json.JSONDecodeError` | ❌ 不需 | 预期的解析回退 |
| `except ImportError` | ❌ 不需 | 可选导入（非 API 场景回退） |
| `except asyncio.CancelledError` | ❌ 不需 | 任务取消，预期行为 |
| `except RuntimeError`（无事件循环） | ❌ 不需 | 预期条件 |

### 3.2 log 级别选择

| 场景 | 级别 | 理由 |
|------|------|------|
| 日志/遥测助手自身失败 | `debug` | 避免"日志坏了一直刷日志"的递归风暴 |
| 热路径意外异常（影响业务） | `warning` | 需要可见但不告警 |
| 关键操作失败（用户可感知） | `error` | 需要排查 |
| 非关键路径（清理/观测插件） | `debug` | 可选，便于诊断 |
| 解析回退（类型/JSON） | 不 log | 预期控制流 |

### 3.3 统一修复模式

所有修复遵循：

```python
# 修改前
except Exception:
    pass

# 修改后
except Exception as e:
    logger.{级别}("{简短描述} failed: %s", e, exc_info=True)
```

**关键点**：
- `as e` 捕获异常对象
- `exc_info=True` 记录完整堆栈（重要！单行 `%s` 只记异常消息，不含调用栈）
- 消息格式统一为 `"{功能描述} failed: %s"`
- 用文件已有的模块级 `logger`（所有目标文件均已定义，除 `pending_issue_tool.py` 需新增）

### 3.4 项目约定

- 项目根目录：`d:\app\Emily`
- 源码目录：`emily-core/emily_core/`
- 所有文件已有 `logger = logging.getLogger("emily.xxx")` 模块级定义（`pending_issue_tool.py` 除外，需新增）
- 日志输出到 `emily-data/logs/emily_YYYYMMDD.log`
- Python 环境用 `uv run python ...`

## 十、注意事项

1. **只加 log，不改逻辑**：本计划所有修复都是"在 except 块内加 logger 调用"，不改变返回值、不改变控制流、不改变异常处理范围。原 `return None` / `return ""` / `pass` 的后续行为保持不变。

2. **`exc_info=True` 必须带**：单 `%s` 只记异常消息字符串（如 "No module named 'openai'"），不含调用栈。`exc_info=True` 让 logging 模块附加完整 traceback，这才是排查所需的。**不要省略。**

3. **`pending_issue_tool.py` 需新增 logger**：修复 15 前必须先在文件顶部加 `import logging` 和 `logger = logging.getLogger("emily.tool.pending_issue")`。其他文件均已存在 logger，不要重复定义。

4. **不改窄异常**：第七节列出的 `except (ValueError, TypeError)` / `except json.JSONDecodeError` 等是预期控制流，加 log 会产生噪音，**不要动**。

5. **log 级别不要过高**：日志助手自身失败用 `debug`（避免日志风暴），不要用 `error`。热路径意外异常用 `warning`。只有用户可感知的失败（如修复 21/22）用 `error`。

6. **编码**：文件含中文注释，编辑时确保 UTF-8 编码。PowerShell 环境预设 `$env:PYTHONIOENCODING="utf-8"`。

7. **`__pycache__` 清除**：Docker bind-mount 不触发 Python 重编译，每次代码变更后必须清除（见 9.1 步骤 2），否则改动不生效。

8. **不改 `scripts/` 和 `.claude/`**：本计划只修 `emily-core/emily_core/` 业务内核。`scripts/` 是 CLI 工具，`emy-test` 是测试工具，不在范围内。
