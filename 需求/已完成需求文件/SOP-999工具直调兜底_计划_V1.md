# SOP-999 工具直调兜底改造 — 实施计划

> **计划版本**：v1.1（v1.0 + 安全限制策略：默认安全 + 写操作确认 + 路由触发约束）
> **基于讨论**：本会话四轮架构讨论（问题定性 → SOP-999 复用判断 → 更新机制设计 → 暴露面限制）
> **目标**：把 SOP-999-SYS 从"半残的对话引导 SOP"改造为"无专属 SOP 时的工具直调兜底"，建立 tools 白名单的**派生更新机制**，并以**默认安全 + 写操作确认**收敛 LLM 自主调工具的暴露面
> **不在范围**：路由 LLM 的 function-calling 化（违背约束 5，不做）、新增定时任务/webhook 触发机制、SOP-999 原对话引导语义的保留（明确放弃）

---

## Context

### 为什么做

当前 `--managed --llm` 模式下，路由 LLM 的能力边界被 [session.md:91](../emily-data/prompts/session.md#L91) 显式锁死在 SOP 类型树——"类型树未列出的能力，你不具备"。新工具若无对应 SOP，LLM 在路由阶段看不到它，永远不会自主调用。这是 SOP 即路由设计（约束 5）的必然代价，不是 bug。

现状存在两块"已就位但悬空"的基建：
1. **SkillExecutor 的元能力路径**（[executor.py:221](../emily-core/emily_core/skill/executor.py#L221) `_llm_resolve_params`）——Skill YAML 不定义 ParamMapping 时 LLM 动态推参，已实现但无 WorkItem 触达
2. **`.sop_index.json` 的 `fallback_tools` + `dump_as_text` 的 `FALLBACK_BY_TYPE`**——按类型分组的裸工具白名单，已注入路由 prompt，但路由协议没给 LLM 表达出口，LLM 看到提示却没法落地

同时 SOP-999-SYS 当前是**半残**的：
- `.skill.yaml` 的 step-03 `tool_name: null`，按 [executor.py:60](../emily-core/emily_core/skill/executor.py#L60) 不真正调工具
- `.md` 手册描述的触发机制（IntentRegistry + match_score=0.65）已随约束 8 废弃 SOPIntentRegistry 而失效
- tools 白名单只 4 个工具，且手动维护

### 范围

- **SOP-999-SYS.skill.yaml 重写**：语义从"资深内业对话引导"改为"LLM 选工具 + 推参 + 直调"
- **tools 白名单派生化**：`.skill.yaml` 的 tools 字段不再手写，由 SkillRegistry 运行时从 `tool_registry` 派生计算
- **`FALLBACK_BY_TYPE` 改派生**：[registry.py:149-156](../emily-core/emily_core/skill/registry.py#L149-L156) 硬编码改为按 `tool_registry.category` 分组派生
- **路由 prompt 给出口**：[session.md](../emily-data/prompts/session.md) 把 SOP-999 定位改为"工具直调兜底"，LLM 在无专属 SOP 时路由到它
- **SkillExecutor 扩展动态 tool_name**：支持 step.tool_name=`__DYNAMIC__`，从 prev_step 取 LLM 选定的工具名 + 参数直调
- **一致性检查扩展**：V14（派生白名单⊆REGISTERED_TOOLS）+ V15（暗工具检测），复用 self_check 启动触发
- **`tool_registry` 加 `exposure_mode` 列**：按 `permission_flag` 分级默认——`all`(只读)默认 `meta`（可被 SOP-999 直调），`write`/`admin` 默认 `sop_only`（必须走专属 SOP）；破坏性工具（delete/discard/return/unlink）显式标 `sop_only`

### 安全限制策略（默认安全 + 写操作确认）

SOP-999 把工具直调权交给 LLM，暴露面扩大。三层限制收敛误用风险（越权风险由现有权限层挡，不在此处）：

1. **白名单收紧**：`exposure_mode` 默认值按 `permission_flag` 分级——只读工具(`all`)默认进白名单，写/管理工具(`write`/`admin`)默认 `sop_only` 不进白名单。破坏性工具（`delete_file`/`discard_nodes`/`return_node_deliverable`/`unlink_attachment`）显式标 `sop_only`，永不进白名单
2. **写操作强制确认**：SOP-999 的 step-02 在调 `permission_flag != all` 的工具前，走 ConfirmQueue 拟执行确认——LLM 选好工具+推好参后，先发"将要调用 X，参数 Y，确认？"给用户，用户确认后才执行。恢复原 SOP-999 的"拟录入确认"语义
3. **路由触发约束**：session.md 路由规则明确——SOP-999 仅当用户请求**明确指向工具能力**时路由，模糊请求（"帮我处理一下"）走 fallback 对话引导。降低 prompt 注入成功面

### 预期收益

- 新工具注册（register_all + TOOL_META_MAP + seed）后，下次容器启动 / SkillRegistry.reload 自动进入 SOP-999 派生白名单（**仅限只读类**，写/管理类需显式标 `meta`），LLM 可自主调用
- `scriptmgr check` 报告"暗工具"——既无专属 SOP、也未标 sop_only、将自动进 SOP-999 的工具，开发者据此决定写专属 SOP 还是接受直调
- 消除 `.sop_index.json` 的 `fallback_tools`（SYS 类型已空着）和 `FALLBACK_BY_TYPE` 两处手动镜像，统一为派生产物
- 闲置的 `_llm_resolve_params` 元能力路径被激活
- **默认安全**：破坏性工具永不进白名单，写操作必须用户确认，模糊请求不路由——LLM 误用面被收敛到只读工具

## 探查发现的关键约束（影响实施）

1. **工具事实来源是 5 处镜像**（[tools_consistency.py:33-127](../emily-core/emily_core/infrastructure/tools_consistency.py#L33-L127)）：`register_all`（代码源头）→ `REGISTERED_TOOLS`/`TOOL_META_MAP`/`TOOL_SCHEMA_MAP`（检查器镜像）→ `tool_registry` 表（DB，`_ensure_tool_registry_seed` 自动种子）→ `seed_tool_registry.sql`（DB 种子）。SOP-999 白名单必须成为**派生产物**，不能是第 6 个手动镜像
2. **`SkillDefinition` / `SkillTool` 是 `@dataclass(frozen=True)`**（[definition.py:16,42,50](../emily-core/emily_core/skill/definition.py#L16)）：运行时改 tools 字段需要 `dataclasses.replace` 重建，不能直接赋值
3. **`_PENDING_COLUMNS` 自动补齐机制**（CLAUDE.md 踩坑：`create_all()` 不 ALTER 已有表）：`tool_registry` 加 `exposure_mode` 列必须注册到 `bootstrap.py::init_db` 的 `_PENDING_COLUMNS` 映射，否则启动不会自动 ALTER
4. **路由用 v4-flash，推参不可靠**（[session_agent.py:347-349](../emily-core/emily_core/session/session_agent.py#L347-L349) 注释"便宜快"）：工具选择 + 参数推导交给 SkillExecutor 的主模型 LLM（`ctx.llm_client`），不让路由 LLM 推参数。路由只决定 sop_id
5. **SkillExecutor 元能力路径触发条件**（[executor.py:102](../emily-core/emily_core/skill/executor.py#L102)）：`step.tool_name in allowed_tools` 走 Skill 推荐路径，否则走 `_llm_resolve_params`。SOP-999 的"动态选工具"超出这两条路径，需新增 `__DYNAMIC__` 分支
6. **`_ensure_tool_registry_seed` 启动触发**（[bootstrap.py:116](../emily-core/emily_core/bootstrap.py#L116)）：容器启动自动种子 tool_registry，是"启动时同步"的现成挂载点
7. **`check_quick` 启动集成**（[tools_consistency.py:329](../emily-core/emily_core/infrastructure/tools_consistency.py#L329)）：self_check 启动时跑，fail-open 不阻断。V14/V15 挂这里
8. **元认知路径不走 SOP-999**（[session.md:29](../emily-data/prompts/session.md#L29)）："你能做什么/权限怎么分级"→ fallback=true + RAG + [session_reply.md:48](../emily-data/prompts/session_reply.md#L48) 能力树回答。改造时不要让 LLM 把元认知询问路由到 SOP-999 调工具
9. **`__pycache__` 不自动刷新**（CLAUDE.md 踩坑）：每次代码变更后 `docker exec emily-core find /app/emily_core -name '__pycache__' -type d -exec rm -rf {} +`
10. **约束 5 张力**：本方案不破坏约束 5——路由 LLM 仍只选 sop_id，工具选择在 SkillExecutor 内部用主模型 LLM（不是路由 LLM 的 function-calling）。`_llm_resolve_params` 已是这套哲学的既成实现，SOP-999 只是激活它
11. **`permission_flag` 三级**（[seed_tool_registry.sql](../emily-core/emily_core/infrastructure/database/scripts/seed_tool_registry.sql)）：`all`（只读+通用）/ `write`（写入）/ `admin`（管理）。是 `exposure_mode` 默认值分级的安全锚点
12. **ConfirmQueue 已存在**（[session_agent.py:26](../emily-core/emily_core/session/session_agent.py#L26) import）：拟执行确认复用现有基建，不新建确认机制

1. **业务内核独立**（CLAUDE.md 约束 1）：`emily_core` 不 import `astrbot.*`
2. **分层不可跳**（CLAUDE.md 约束 2）：`API → EmilyCore → Session → WorkItem → Application → Service → Repository → DB`

10. **不改 SkillExecutor 外部接口**：`__DYNAMIC__` 分支是 step.tool_name 的新取值，不新增 executor 方法签名，不改 `SkillExecutionContext` 结构
11. **元认知路径不污染**：[session.md:29](../emily-data/prompts/session.md#L29) 的 meta_cognition 仍走 fallback=true + RAG，不路由到 SOP-999
12. **默认安全（exposure_mode 分级）**：`exposure_mode` 默认值按 `permission_flag` 分级——`all`→`meta`，`write`/`admin`→`sop_only`。破坏性工具（`delete_file`/`discard_nodes`/`return_node_deliverable`/`unlink_attachment`）在 `TOOL_META_MAP` 显式标 `sop_only`，即便未来调默认值也永不进 SOP-999 白名单

## M2 — SkillRegistry 派生计算：SOP-999 白名单 + FALLBACK_BY_TYPE 派生化

### 交付物

- [ ] `SkillRegistry._compute_meta_tools()` 方法：派生 SOP-999 的 tools 白名单
- [ ] `SkillRegistry.load/reload` 末尾调用 `_compute_meta_tools`，用 `dataclasses.replace` 注入 SOP-999 的 SkillDefinition
- [ ] `dump_as_text` 的 `FALLBACK_BY_TYPE` 从硬编码改为按 `tool_registry.category` 分组派生
- [ ] `.sop_index.json` 的 `fallback_tools` 不再手动维护（由 dump_as_text 派生输出，索引文件该字段可保留为只读缓存或移除）

### 步骤

1. **`emily-core/emily_core/skill/registry.py`** 新增方法：
   ```python
   def _compute_meta_tools(self) -> list[SkillTool]:
       """派生 SOP-999 工具直调白名单。
       
       公式：全部 REGISTERED_TOOLS
            − ∪(所有 Skill YAML 的 tools[].name)   # 被专属 SOP 引用的
            − {t for t in tool_registry if exposure_mode == 'sop_only'}
       
       fail-open：tool_registry 不可用时回退到 REGISTERED_TOOLS 减被引用工具。
       """
   ```
   实现要点：
   - 从 `tool_registry_repo.get_all_active()` 取全部工具的 `(api_id, display_name, category, exposure_mode)`
   - 遍历 `self._registry.values()`，收集所有非 SOP-999 Skill 的 `tools[].name` 成 `referenced` 集合
   - 白名单 = `{t.api_id for t in db_tools if t.exposure_mode != 'sop_only'}` − `referenced`
   - 返回 `[SkillTool(name=api_id, description=display_name) for api_id in sorted(白名单)]`
   - try/except 包裹，异常时 `logger.warning` + 返回空列表（fail-open）

2. **`SkillRegistry.load` / `reload`** 末尾（`self._registry` 替换完成后）调用 `_compute_meta_tools`，用 `dataclasses.replace` 重建 SOP-999 的 SkillDefinition：
   ```python
   sop999 = self._registry.get("SOP-999-SYS")
   if sop999 is not None:
       meta_tools = self._compute_meta_tools()
       self._registry["SOP-999-SYS"] = dataclasses.replace(sop999, tools=meta_tools)
       logger.info("SOP-999 meta tools derived: %d tools", len(meta_tools))

   async def _execute_dynamic_step(self, step, ctx: SkillExecutionContext) -> StepResult:
       """执行 __DYNAMIC__ 步骤：从 prev_step 取 tool_name + params，校验白名单后直调 handler。
       
       prev_step 的 output_key（如 tool_call）含 {tool_name, params}。

       # 1. 从 step_results 取 prev_step 输出（约定 output_key="tool_call"）
       tool_call = ctx.step_results.get("tool_call") or {}
       tool_name = tool_call.get("tool_name")
       params = tool_call.get("params") or {}
       
       if not tool_name:
           return StepResult(step_id=step.id, success=False,
                             output="动态工具选择失败：未提供 tool_name")
       
       # 2. 校验白名单（SOP-999 派生 tools）+ Session 可见 API
       allowed = {t.name for t in ctx.skill.tools}
       if tool_name not in allowed:
           return StepResult(step_id=step.id, success=False,
                             output=f"工具 '{tool_name}' 不在 SOP-999 派生白名单中")
       if tool_name not in {t["api_id"] for t in ctx.session_available_tools}:
           return StepResult(step_id=step.id, success=False,
                             output=f"工具 '{tool_name}' 不在 Session 可见 API 中")
       
       # 3. 取工具 handler
       tool = ctx.business_flow_tools.get(tool_name)
       if tool is None:

       tool_meta = next((t for t in ctx.session_available_tools if t["api_id"] == tool_name), {})
       perm_flag = tool_meta.get("permission_flag", "all")
       if perm_flag != "all":
           # 拟执行确认：把"将要调用 X，参数 Y"发给用户，等 ConfirmQueue 返回

           confirmed = await self._request_user_confirm(ctx, tool_name, params)
           if not confirmed:
               return StepResult(step_id=step.id, success=False, output="用户取消执行")
       
       # 5. 注入运行时上下文 + 调用
       params["_user_id"] = ctx.user_id
       params["_message_id"] = ctx.message_id
       params["_conversation_id"] = ctx.conversation_id
       params["_session_scope"] = self._build_session_scope(ctx.session_context)
       
       handler_result = await tool.handler(**handler_kwargs)
       handler_dict = handler_result if isinstance(handler_result, dict) else {}

       tool_call_record = ToolCallRecord(
           tool_name=tool_name,
           tool_input=params,
           tool_output=handler_dict,
           success=handler_dict.get("success", True),
           elapsed_ms=elapsed_ms,
       )
       setattr(tool_call_record, "trigger", "sop999")  # 审计标记：SOP-999 LLM 自主直调
       # ... 其余 StepResult 构建参照 executor.py:128-168
   ```
