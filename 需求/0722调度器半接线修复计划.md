# 调度器半接线修复计划

> 日期：2026-07-22
> 背景：修 `SchedulerEngine` 的 `TypeError: can't compare offset-naive and offset-aware datetimes`（已修，见 [docs/技术踩坑备忘录.md](../docs/技术踩坑备忘录.md) 踩坑 2.13）时，发现该崩溃发生在 `_is_due`（tick 早期），`_execute_job` 根本没机会跑——所以一直没人发现调度器有三处「半接线」问题。TypeError 修好后这三处才暴露。

## 三处半接线问题

1. **action_type 对不上**：3 个种子作业的 action_type / handler_module / action_params 全是旧架构残留，无对应 handler，每周期触发一次 "No handler"。
2. **execution 状态不流转**：`_execute_job` 从不调 `update_execution_status`，执行记录永远停留 PENDING。
3. **无 reschedule**：`next_execution_at` 创建后永不更新（停在 2026-07-21），作业靠幂等按 period_key 挡，到点行为不精确。

---

## 问题 1：action_type / handler_module / params 对齐

### 现状

种子数据 [010_seed_runtime_data.sql](env-test/010_seed_runtime_data.sql#L146) 里的三作业：

| 作业 | 种子 action_type | 种子 handler_module（已失效） | 种子 params | 已注册 handler |
|------|------|------|------|------|
| JOB-001 | `create_task_node` | `emily_core.scheduler.handlers.task_handler` | `{"task_title","task_priority"}` | `create_periodic_node`（[periodic_node.py](../emily-core/emily_core/scheduler/jobs/periodic_node.py)） |
| JOB-002 | `morning_report` | `emily_core.scheduler.handlers.report_handler` | `{"report_type","recipients"}` | `generate_morning_report`（[morning_report.py](../emily-core/emily_core/scheduler/jobs/morning_report.py)） |
| JOB-003 | `file_expiry_reminder` | `emily_core.scheduler.handlers.file_handler` | `{"threshold_days","check_categories"}` | **无** |

引擎按 `job.action_type` 查 handler（[engine.py](../emily-core/emily_core/scheduler/engine.py) `_execute_job` 里 `self._handlers.get(job.action_type)`），`handler_module` 字段运行时不用（仅信息）。所以三作业全部命中 `No handler`。

### 参数也不兼容（即便对齐 action_type 仍会空跑）

- `PeriodicNodeHandler.execute` 读 `project_id / node_name / responsible_user_id / deadline / parent_node_id / owner_dept_id / description / creator_id`，**不读** `task_title / task_priority` → JOB-001 需重写 params。
- `MorningReportHandler.execute` 读 `push_to_group`，**不读** `report_type / recipients` → JOB-002 需重写 params（否则用默认 "项目群"，不崩但不准）。

### 修复

**A1. 更新种子 SQL**（新环境，[010_seed_runtime_data.sql](env-test/010_seed_runtime_data.sql)）三作业改为：

| 作业 | action_type | handler_module | action_params |
|------|------|------|------|
| JOB-001 | `create_periodic_node` | `scheduler.jobs.periodic_node` | `{"project_id":"<真实项目UUID>","node_name":"本周进度汇报","owner_dept_id":"项目总","creator_id":"scheduler"}` |
| JOB-002 | `generate_morning_report` | `scheduler.jobs.morning_report` | `{"push_to_group":"项目群"}` |
| JOB-003 | `check_file_expiry`（见 A3） | `scheduler.jobs.file_expiry` | `{"threshold_days":30,"check_categories":["PROJECT_LICENSE"]}` |

**A2. 存量环境迁移**：已 seeded 的库写一个 `UPDATE scheduler_jobs SET ... WHERE job_no IN (...)` 脚本（放 [scripts/](../scripts/) 或 [emily-data/db_seeds/](../emily-data/db_seeds/)）。注意 JOB-001 的 `project_id` 要填真实项目 UUID（如 ECOCITY-26 对应的 id）。

**A3. JOB-003 二选一**：

- **(推荐) 新建 FileExpiryReminderHandler**：`scheduler/jobs/file_expiry.py`，`action_type="check_file_expiry"`，execute 查 files 表临期文件（`threshold_days`）经 `outbound_bus` 发提醒；在 [__init__.py](../emily-core/emily_core/__init__.py) 的 handler 注册区注册；种子 action_type 改 `check_file_expiry`。
- **(或) 暂停 JOB-003**：`UPDATE scheduler_jobs SET status='INACTIVE' WHERE job_no='JOB-003'`，待文件过期业务规则明确再补 handler。若 files 表的过期业务尚无定论，先选这条，避免造一个 TODO handler。

## 问题 2：execution 状态流转

### 现状

[engine.py](../emily-core/emily_core/scheduler/engine.py) `_execute_job`：`create_execution`（PENDING）→ before hooks → handler → after hooks → `SchedulerJobLogger`。**从不调 `update_execution_status`**（[scheduler_repo.py:159](../emily-core/emily_core/repositories/scheduler_repo.py) / [service.py:87](../emily-core/emily_core/scheduler/service.py) 的方法存在但无人调用）。结果：执行记录永远 PENDING；`has_period_execution` 原本只查 SUCCESS/RUNNING 因此失效（修 TypeError 时已临时改成「任意状态」应急）。

### 修复

**B1. `service.create_execution` 回传 execution_id**：当前只返回 `SchedulerOperationResult(success, execution_no)`，引擎拿不到 id 去调 `update_execution_status(execution_id, ...)`。改为同时回传 `execution_id`（在 [commands.py](../emily-core/emily_core/scheduler/commands.py) 的 `SchedulerOperationResult` 增字段，或 `create_execution` 直接返回 repo 对象）。

**B2. `_execute_job` 状态流转**（骨架）：

```python
exec_res = await self._service.create_execution(job.id, period_key)
exec_id = exec_res.execution_id
await self._service.update_execution_status(exec_id, "RUNNING")
try:
    handler = self._handlers.get(job.action_type)
    if handler is None:
        raise RuntimeError(f"No handler for action_type={job.action_type}")
    result = await handler.execute(ctx.action_params)
    await self._service.update_execution_status(
        exec_id,
        "SUCCESS" if result.success else "FAILED",
        result_summary=(result.summary or "")[:1000],
        error_message="" if result.success else (result.summary or "")[:1000],
    )
except Exception as e:
    await self._service.update_execution_status(exec_id, "FAILED", error_message=str(e)[:1000])
    raise
```

No-handler 从「静默 return」改为抛错落 FAILED，状态可追溯。

**B3. 幂等回调**：问题 3（reschedule）落地后，`next_execution_at` 会推进到下个周期，幂等不再是主闸门。此时把 `has_period_execution` 改回仅查 `SUCCESS`（允许同周期失败重试），PENDING/RUNNING 由 tick 串行 + advisory lock 兜底。

> ⚠ 顺序约束：reschedule 落地**前**不要改回 SUCCESS-only，否则 past-due 作业又每 tick 重跑。

## 问题 3：reschedule（next_execution_at 重算）

### 现状

`next_execution_at` 创建后永不更新。作业永远 past-due，靠幂等按 period_key 挡。到点不精确（tick 60s 粒度 + 幂等 period_key 粒度）。

### 修复

**C1. 新建 `scheduler/next_execution.py`**：

```python
from datetime import datetime, timedelta

def calc_next_execution(job, now: datetime) -> str:
    """返回下次执行时间 UTC-aware ISO；ONCE / 无法计算返回 ''。"""
    jt = getattr(job, "job_type", "ONCE")
    if jt == "INTERVAL":
        secs = getattr(job, "interval_seconds", 0) or 0
        return (now + timedelta(seconds=secs)).isoformat() if secs else ""
    if jt == "CRON":
        return _next_cron(getattr(job, "cron_expression", ""), now)
    return ""  # ONCE：一次性，不重排
```

**C2. cron 解析选型**：项目无 cron 解析器。推荐加依赖 `croniter`（成熟、5 字段 cron 全支持，处理 `0 9 * * 1` / `0 8 * * *` 这类无歧义）；备选手写极简解析器（仅支持 `分 时 * * 周/月` 当前用到的简单式，零依赖但扩展受限）。需在 [pyproject.toml](../pyproject.toml) 加 `croniter`。

**C3. `_execute_job` 末尾重算 + 写回**：

```python
now_iso = datetime.now(timezone.utc).isoformat()
next_at = calc_next_execution(job, datetime.now(timezone.utc))
await self._service.update_job_last_executed(job.id, now_iso, next_at)
if not next_at:  # ONCE：一次性作业跑完置 INACTIVE
    await self._service.update_job_status(job.id, "INACTIVE")
```

`update_job_last_executed` repo 已有（[scheduler_repo.py:133](../emily-core/emily_core/repositories/scheduler_repo.py)），service 层补一个 async wrapper（`asyncio.to_thread`）。

**C4. 时间格式统一为 UTC-aware ISO**：reschedule 写入的 `next_execution_at` 走 `datetime.now(timezone.utc).isoformat()`（带 `+00:00`），`_is_due` 走 aware-aware 比较。种子遗留的 naive 北京时间串由踩坑 2.13 的 Beijing-tz 兜底兼容，**不再产生新的 naive 串**。

## 实施顺序（建议）

1. **问题 3 + 问题 2 一起做**（都在 `_execute_job`，互相关联）：
   - 加 `next_execution.py` + `croniter` 依赖
   - 改 `_execute_job`：状态流转（B2）+ 末尾 reschedule（C3）+ ONCE 置 INACTIVE
   - `service.create_execution` 回传 execution_id（B1）+ 补 `update_job_last_executed` wrapper
   - **最后**把 `has_period_execution` 改回 SUCCESS-only（B3）
2. **问题 1（action_type 对齐）**：改种子 SQL + 存量迁移脚本 + JOB-003 handler（若做）。可与 1 并行。
3. 联调验证。

## 验证

- **状态流转**：跑一个作业，DB 查 `scheduler_executions` 对应记录 `status=SUCCESS/FAILED`、`started_at/finished_at` 非空（不再 PENDING）。
- **reschedule**：
  - CRON 作业执行后 `next_execution_at` 推进到下个 cron 触发点（aware ISO，带 `+00:00`）；
  - INTERVAL 作业推进 `now + interval_seconds`；
  - ONCE 作业执行后 `status=INACTIVE`。
- **action_type**：三作业不再 "No handler"；JOB-001 真创建节点、JOB-002 真推晨报、JOB-003（若做）真发提醒。
- **幂等不回归**：同周期重复 tick 不重复执行（SUCCESS-only 幂等 + reschedule 双保险）。
- **emy-test 联调**：发消息触发或等 tick，日志无 "No handler"、无 TypeError。
- **时间比较**：新写入的 aware `next_execution_at` 与 UTC `now` 比较，不再走 Beijing-tz 兜底分支（可加临时 log 验证）。

## 风险与取舍

- **croniter 依赖**：新增第三方库。若想零依赖，手写极简解析器仅支持当前 `0 9 * * 1` / `0 8 * * *` 形式，但后续 cron 复杂化会受限。推荐 croniter。
- **JOB-003 handler**：需真实 files 表查询逻辑（证照/许可临期）。若文件过期业务规则未定，建议先 INACTIVE，避免造 TODO handler。
- **存量迁移**：已 seeded 环境需跑 UPDATE 脚本；JOB-001 params 里 `project_id` 要填真实项目 UUID，不能空。
- **幂等回调时机**：reschedule 落地前不要把 `has_period_execution` 改回 SUCCESS-only（否则 past-due 作业又每 tick 重跑）；务必问题 3 先行。
- **handler_module 字段**：运行时不读，但种子里的旧路径有误导性，顺手改对。
