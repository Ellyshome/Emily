> **涉及脚本**：`emily-core/scripts/build_world_book.py` → `emily_core/services/world_book_builder.py`
> **问题数**：4 个（1 操作时序 + 2 数据一致性 + 1 依赖缺失）
>

## 一、背景

调用 `uv run python scripts/build_world_book.py` 生成项目世界书（存入 `project_world_books` 表，用于 prompt 注入），脚本报告"构建完成"但 DB 中查不到世界书；重跑后虽然写入，但内容稀疏（154 字，`initialization_tier=0`），且知识层报 `No module named 'openai'`。

经排查确认四个独立问题，本文档逐项记录。

## 二、问题总览

| # | 问题 | 类别 | 严重度 | 状态 |
|---|------|------|--------|------|
| 1 | 脚本写入后 DB 被重置，世界书被 TRUNCATE 清空 | 操作时序 | 🔴 主因 | 需流程修复 |
| 2 | `project_nodes.project_id` 存项目编码而非 UUID，世界书按 UUID 查到 0 节点 | 数据一致性 bug | 🔴 严重 | 需数据+源码修复 |
| 3 | `users.project_id` 全空，世界书按 UUID 查到 0 用户，tier=0 | 数据一致性 bug | 🔴 严重 | 需数据+源码修复 |
| 4 | 知识层 `_build_knowledge` 报 `No module named 'openai'` | 依赖缺失 | 🟡 中等 | 需装依赖 |

## 三、问题 1：DB 重置导致世界书丢失

### 3.1 错误现象

用户跑脚本，终端输出：
```
[INFO] 项目 ID: 30723154-ae1f-44bc-bb3a-43c3f76f1495
[INFO] 构建状态: built
[DONE] 世界书构建完成
```

但查 DB：
```sql
SELECT count(*) FROM project_world_books;  -- 返回 0
```

### 3.2 排查过程

```sql
-- 脚本报告的 project_id 在 DB 中不存在
SELECT id, code FROM projects WHERE id = '30723154-ae1f-44bc-bb3a-43c3f76f1495';
-- 0 行

-- 当前 EMERALD-01 的真实 ID 和创建时间
SELECT id, code, created_at, NOW() FROM projects WHERE code = 'EMERALD-01';
-- id = ceee178f-a318-42ce-858b-df172d54e437
-- created_at = 2026-07-21 07:30:14（脚本运行前刚重灌）
```

两个 UUID 不一致：脚本找到 `30723154-...`，DB 当前是 `ceee178f-...`。

### 3.3 根因

**操作时序问题，非代码 bug**：

1. 之前 DB 里 EMERALD-01 的 ID 是 `30723154-...`（旧种子）
2. 用户跑 `build_world_book.py` → 找到 `30723154` → **世界书写入成功**（脚本报告 "built" 属实）
3. 之后 DB 被 reset + 重新种子（`000_reset_all.sql` TRUNCATE 全表 + `007_seed_emerald_project.sql` 重灌）
4. 种子脚本 [007_seed_emerald_project.sql](../emily-core/emily_core/infrastructure/database/scripts/007_seed_emerald_project.sql) 用 `uuid_generate_v4()` 生成项目 ID → EMERALD-01 拿到新 UUID `ceee178f-...`
5. `000_reset_all.sql` TRUNCATE 了 `project_world_books` → 世界书被清空

**根因**：种子脚本用 `uuid_generate_v4()` 生成项目/用户/节点等所有主键，**每次重置重灌都换新 UUID**。世界书的 `project_id` 外键因此失效，即使没被 TRUNCATE 也查不到。

### 3.4 修复方案

**方案 A（推荐，流程修复）**：在测试环境搭建脚本末尾自动调用世界书重建，确保 reset 后自动补建。

在 [测试环境搭建-计划.md](测试环境搭建-计划.md) 描述的 `setup_test_env.ps1` 的 `Invoke-SeedData` 函数末尾追加：

```powershell
# [9] 世界书重建（reset 后 project_id 已变，旧世界书失效，必须重跑）
Write-Host "  [9] 重建项目世界书..." -ForegroundColor DarkGray
Push-Location "emily-core"
$env:PYTHONPATH = "emily-core"
uv run python scripts/build_world_book.py 2>&1 | Out-Null
Pop-Location
Write-Host "    [OK] 世界书已重建" -ForegroundColor Green
```

**方案 B（备选，固定 UUID）**：改种子脚本用固定 UUID 而非 `uuid_generate_v4()`。不推荐——多项目场景易冲突，且需改所有种子脚本。

**方案 C（文档约定）**：在 CLAUDE.md 踩坑速查追加："每次 DB 重置后必须重跑 `build_world_book.py`，否则世界书 project_id 对不上"。

### 3.5 验证

```powershell
# 重置 + 种子后，确认世界书自动重建
uv run pwsh scripts/setup_test_env.ps1
docker exec emily-postgres psql -U emily -d emily -c "SELECT project_id, version, length(content_text) FROM project_world_books;"
-- 应返回 1 行，project_id 与当前 projects.id 一致
```

## 四、问题 2：project_nodes.project_id 存编码非 UUID

### 4.1 错误现象

世界书 `content_text` 只有 154 字，七层中结构层/时间层/关系层全空（📊节点统计、🏁里程碑、⏰7天到期、🔴逾期、🔗阻塞都没出来）。

### 4.2 排查过程

```sql
-- project_nodes 表里 project_id 存的是什么
SELECT project_id, count(*) FROM project_nodes GROUP BY project_id;
-- project_id = 'EMERALD-01'（编码），24 行

-- 对比 projects 表
SELECT id, code FROM projects WHERE code = 'EMERALD-01';
-- id = ceee178f-...（UUID），code = EMERALD-01

-- 世界书按 UUID 查 vs 按编码查
SELECT '按UUID查' as way, count(*) FROM project_nodes WHERE project_id='ceee178f-a318-42ce-858b-df172d54e437'
UNION ALL
SELECT '按编码查', count(*) FROM project_nodes WHERE project_id='EMERALD-01';
-- 按UUID查: 0    按编码查: 24
```

世界书 builder 按 UUID 查（[world_book_builder.py:226-229](../emily-core/emily_core/services/world_book_builder.py#L226)）：
```python
nodes = session.query(ProjectNode).filter(
    ProjectNode.project_id == project_id,  # project_id = UUID ceee178f
    ProjectNode.is_discarded == False,
).all()
# → 返回 0 个节点
```

### 4.3 根因

**源码 bug**：[scripts/manage_nodes.py:324](../scripts/manage_nodes.py#L324) 直接用 YAML 里的 `project_id`（项目编码 `"EMERALD-01"`），未解析成 UUID：

```python
project_id = yaml_data.get("project_id", "")  # 读到 "EMERALD-01"（编码）
# ↓ 直接传给 create_node_tree，未解析成 UUID
```

而 `ProjectNode.project_id` 字段定义（[models.py:1027](../emily-core/emily_core/infrastructure/database/models.py#L1027)）注释明确："项目归属ID（FK→projects.id）"——**应该是 UUID**。

`world_book_builder.py`、`node_service.py` 等消费方都按 UUID 查，导致数据写法和读法不一致。

### 4.4 修复方案

#### 4.4.1 数据修补（立即生效）

```sql
-- 把 project_nodes.project_id 从编码转成 UUID
UPDATE project_nodes
SET project_id = sub.id
FROM projects sub
WHERE project_nodes.project_id = sub.code
  AND project_nodes.project_id NOT IN (SELECT id FROM projects);
```

执行后验证：
```sql
SELECT project_id, count(*) FROM project_nodes GROUP BY project_id;
-- 应显示 UUID ceee178f-...，24 行
```

#### 4.4.2 源码根治（避免未来再错）

**文件**：[scripts/manage_nodes.py](../scripts/manage_nodes.py)

在 `project_id = yaml_data.get("project_id", "")`（第 324 行）之后，增加编码→UUID 解析：

```python
# 修改前（第 324 行附近）
project_id = yaml_data.get("project_id", "")
creator_id = yaml_data.get("creator_id", "")
nodes = yaml_data.get("nodes", [])

if not project_id:
    print("错误：YAML 文件缺少 project_id")
    sys.exit(1)

# 修改后
project_id = yaml_data.get("project_id", "")
creator_id = yaml_data.get("creator_id", "")
nodes = yaml_data.get("nodes", [])

if not project_id:
    print("错误：YAML 文件缺少 project_id")
    sys.exit(1)

# 解析 project_id：若为项目编码则转成 UUID（project_nodes.project_id 应存 UUID）
project_id = _resolve_project_id(project_id)
if not project_id:
    print(f"错误：项目 '{yaml_data.get('project_id', '')}' 不存在，无法解析 UUID")
    sys.exit(1)
```

并新增解析函数（参照该文件已有的 `find_by_name()` 用户解析模式）：

```python
def _resolve_project_id(project_id_or_code: str) -> str:
    """将项目编码解析为 UUID。若传入的已是 UUID（projects.id 存在）则原样返回。"""
    from emily_core.infrastructure.database.session import get_session
    from emily_core.infrastructure.database.models import Project
    with get_session() as session:
        # 先按 id（UUID）查
        p = session.query(Project).filter(Project.id == project_id_or_code, Project.is_deleted == False).first()
        if p:
            return p.id
        # 再按 code（编码）查
        p = session.query(Project).filter(Project.code == project_id_or_code, Project.is_deleted == False).first()
        if p:
            return p.id
    return ""
```

> 注：需确认 `manage_nodes.py` 已有 DB 连接初始化（`init_db`）。该脚本已用 `find_by_name()` 查用户，说明 DB 已就绪，可直接复用 `get_session()`。

## 五、问题 3：users.project_id 全空

### 5.1 错误现象

世界书人员层（👥关键人员 / 🏗参建方）为空，且 `initialization_tier=0`，`initialization_status` 中 `T1_admin_user=false`、`T1_admin_email=false`。

### 5.2 排查过程

```sql
-- initialization_status
SELECT initialization_status FROM project_world_books WHERE project_id='ceee178f-...';
-- {"T1_project_name": true, "T1_project_code": true, "T1_project_address": true,
--  "T1_lifecycle_stage": true, "T1_admin_user": false, "T1_admin_email": false}

-- EMERALD-01 项目下有多少用户（按 project_id 匹配）
SELECT count(*) FROM users WHERE project_id = 'ceee178f-a318-42ce-858b-df172d54e437' AND is_deleted=false;
-- 0

-- 实际用户
SELECT username, level, project_id FROM users WHERE is_deleted=false LIMIT 5;
-- admin_wang / 6 / (空)
-- pm_li / 4 / (空)
-- ...所有用户 project_id 都是空
```

世界书 builder 按 UUID 查用户（[world_book_builder.py:145](../emily-core/emily_core/services/world_book_builder.py#L145) 和 [174-178](../emily-core/emily_core/services/world_book_builder.py#L174)）：
```python
users = session.query(User).filter(
    User.project_id == project_id,  # UUID ceee178f
    User.is_deleted == False,
    User.status == "active",
).all()
# → 返回 0 个用户
```

### 5.3 根因

**种子脚本 bug**：[002_seed_test_data.sql](../emily-core/emily_core/infrastructure/database/scripts/002_seed_test_data.sql) 创建用户时**不设 `project_id`**（全部 NULL）。

看脚本里 admin_wang 的 INSERT（第 48-58 行）：
```sql
INSERT INTO users (id, username, phone, email, status, is_admin, gender, id_card, qq, wechat, remark,
    creator_id, is_deleted, perm_list, org_category, level, supervisor_id, company, position, created_at, updated_at)
-- ↑ 列表里没有 project_id
```

7 个用户的 INSERT 都没带 `project_id`，导致全空。`002_seed_test_data_patch.sql` 补的 3 个用户同样未设。

### 5.4 修复方案

#### 5.4.1 数据修补（立即生效）

```sql
-- 给未分配项目的用户回填 EMERALD-01 的 UUID
-- （测试环境单项目，全部回填；多项目环境需按业务关系分别回填）
UPDATE users
SET project_id = (SELECT id FROM projects WHERE code = 'EMERALD-01' AND is_deleted = false)
WHERE (project_id IS NULL OR project_id = '')
  AND is_deleted = false;
```

执行后验证：
```sql
SELECT username, project_id FROM users WHERE is_deleted=false;
-- 所有用户 project_id 应为 ceee178f-...
```

> ⚠ 多项目环境注意：此 SQL 把所有未分配用户都归到 EMERALD-01。若有多个项目，需按 `company` 或业务关系分别回填。

#### 5.4.2 源码根治（改种子脚本）

**文件**：[emily-core/emily_core/infrastructure/database/scripts/002_seed_test_data.sql](../emily-core/emily_core/infrastructure/database/scripts/002_seed_test_data.sql)

**问题**：7 个用户的 INSERT 语句列名表里没有 `project_id`。

**修复**：在每个 INSERT 的列名表和 VALUES 里加 `project_id`。但此时项目尚未创建（002 在 007 之前跑），`projects` 表还没有 EMERALD-01。

**两种处理方式**：

**方式 A（推荐）**：在 `007_seed_emerald_project.sql` 项目创建后，追加用户回填：
```sql
-- 007 脚本末尾追加
UPDATE users
SET project_id = (SELECT id FROM projects WHERE code = 'EMERALD-01')
WHERE (project_id IS NULL OR project_id = '') AND is_deleted = false;
```

**方式 B**：调整种子顺序——先建项目（007）再建用户（002），在 002 里直接带 `project_id` 子查询：
```sql
INSERT INTO users (..., project_id, ...) VALUES (
    ...,
    (SELECT id FROM projects WHERE code = 'EMERALD-01'),
    ...
);
```

推荐方式 A（改动最小，不破坏现有脚本顺序）。

## 六、问题 4：知识层 `No module named 'openai'`

### 6.1 错误现象

脚本输出：
```
_build_knowledge failed: No module named 'openai'
```

知识层（层 6）构建失败，`sop_count=0`、`sop_ids=[]`，世界书里 SOP 覆盖信息为空。

### 6.2 排查过程

```bash
# openai 直接 import 只在 llm/client.py
grep -rn "^import openai\|^from openai" emily-core/emily_core/
# emily_core/infrastructure/llm/client.py:14: from openai import AsyncOpenAI

# skill/registry.py 本身不 import openai
grep -n "openai" emily-core/emily_core/skill/registry.py
# 无匹配

# 但 skill/__init__.py eagerly import 了所有子模块
cat emily-core/emily_core/skill/__init__.py
# from .executor import SkillExecutor  ← 这个会触发链式 import
```

**import 链**：
```
world_book_builder._build_knowledge
  → from ..skill.registry import SkillRegistry
    → Python 先运行 skill/__init__.py
      → from .executor import SkillExecutor          (skill/__init__.py:8)
        → from ..tools.business_flow_tools import BusinessFlowToolRegistry  (executor.py:19)
          → ... → from ..infrastructure.llm.client import ...
            → from openai import AsyncOpenAI         (llm/client.py:14)
              → ❌ No module named 'openai'
```

### 6.3 根因

**依赖缺失**：运行 `build_world_book.py` 的 Python 环境**未安装 openai**。

- openai **已声明**在 [emily-core/requirements.txt:10](../emily-core/requirements.txt#L10)：`openai>=1.0.0`
- Docker 容器内已装（emily-core 镜像构建时 `pip install -r requirements.txt`）
- 但**宿主机跑 `uv run python scripts/build_world_book.py` 时**，若 uv 环境或激活的 conda 环境（`(Emily)`）未装 openai，则 import 失败

**设计隐患**：`skill/__init__.py` eagerly import `executor`（执行器），而世界书 builder 只需要 `SkillRegistry.list_sop_ids()`（列出 SOP，不需要 LLM 执行）。但 Python 的包 import 机制导致访问 `skill.registry` 必先运行 `skill/__init__.py`，触发整个 executor→llm→openai 链。

### 6.4 修复方案

#### 6.4.1 方案 A（推荐，装依赖）

确保运行脚本的环境有 openai：

```powershell
# 方式 1：用 uv 安装（推荐）
cd d:\app\Emily\emily-core
uv pip install -r requirements.txt

# 方式 2：若在 conda env (Emily) 里跑，在该 env 里装
pip install "openai>=1.0.0"

# 验证
uv run python -c "import openai; print('openai', openai.__version__)"
# 应输出版本号
```

#### 6.4.2 方案 B（可选，源码优化——lazy import）

若希望世界书 builder 不依赖 openai（只列 SOP 不执行），改 [world_book_builder.py:396](../emily-core/emily_core/services/world_book_builder.py#L396) 的 import 方式，绕过 `skill/__init__.py` 的 eager import：

**当前无法直接绕过**——Python import 子模块必先运行包 `__init__.py`。要根治需改 `skill/__init__.py` 不 eager import executor，但这会影响其他消费方，**不在本计划范围**。

**建议**：先用方案 A 装依赖（openai 本就是系统必需依赖，LLM 客户端需要它）。方案 B 留作后续架构优化。

### 6.5 验证

```powershell

uv run python scripts/build_world_book.py
# 预期：不再出现 "_build_knowledge failed: No module named 'openai'"
# 知识层 sop_count > 0（若 emily-data/skills/ 目录有 .skill.yaml 文件）
```

## 九、注意事项

1. **数据修补 SQL 的多项目适配**：问题 3 的 `UPDATE users SET project_id=(SELECT id FROM projects WHERE code='EMERALD-01')` 在单项目测试环境安全。多项目环境需按 `users.company` → `company_info` → 业务关系分别回填，不能一刀切。

2. **manage_nodes.py 改动需同步检查**：`_resolve_project_id` 新增后，确认 008 YAML 里 `project_id: EMERALD-01` 仍能工作（编码会被解析成 UUID）。若 YAML 已用 UUID，`_resolve_project_id` 会先按 id 查到并原样返回，兼容。

3. **种子脚本顺序**：问题 3 的源码修复（方式 A）在 007 脚本末尾追加 UPDATE，依赖 002 已先跑完（用户已存在）。当前种子顺序 002→007 满足，不要调换。

4. **openai 依赖**：openai 是 emily-core 的硬依赖（LLM 客户端必需），不是可选依赖。所有跑 `emily_core` 代码的环境（宿主机脚本、容器、CI）都必须装。`requirements.txt` 已声明，确保 `uv pip install -r requirements.txt` 执行过。

5. **reset 后必重跑世界书**：问题 1 的根因是种子脚本用随机 UUID。即使不做问题 1 的流程修复，也需在 CLAUDE.md 或操作手册里写明"DB reset 后必须重跑 `build_world_book.py`"。

6. **世界书缓存**：`SessionContext` 在会话首次创建时读一次世界书并缓存（见 [session_context.py:195](../emily-core/emily_core/session/session_context.py#L195)）。重跑 `build_world_book.py` 后，**已存在的 Session 不会自动刷新**世界书——需重启 emily-core 或等 Session 过期重建。测试时若发现 prompt 里世界书没更新，重启 emily-core：
   ```powershell
   docker compose -f docker-compose-napcat.yml restart emily-core
   ```

7. **`__pycache__` 清除**：改完 `manage_nodes.py` 或 `world_book_builder.py` 后，若在容器内验证，必须清 pycache：
   ```powershell
   docker exec emily-core find /app/emily_core -name '__pycache__' -type d -exec rm -rf {} +
   ```
