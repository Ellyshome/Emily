# 存储与日志统一化修改计划

> 来源：针对「Session 保存 / 日志存放 / 是否需要统一存放方法」讨论中提出的第三部分三处改进项，细化为可执行修改计划。
> 编写日期：2026-07-22
> 涉及模块：`emily-core/emily_core/`（bootstrap / __init__ / session / services / infrastructure/logging）

---

## 背景与目标

经代码探查，当前 Emily 的存储与日志现状如下：

- **Session 内容**：主体已在 DB（`messages` 表为源头、`session_archives` 归档、`users.conversation_summary` 摘要），运行时活跃状态在内存。**这部分无需改动，设计合理。**
- **业务/进化日志**：已统一到 `EvolutionLogWriter.write()`（`infrastructure/logging/log_writer.py:34`），非阻断+截断+异步，**这层不需要再动。**
- **运行时调试日志**：Python 标准 `logging` 走 stdout，由 Docker 捕获；`_setup_logging()`（`bootstrap.py:19`）其实**已实现 FileHandler**，但受 `config.log_to_file` 开关控制——需确认默认状态并启用。
- **业务事件流水**：`EventJournal` 双写到 `.md` 文件，与 `BusinessEventLogger`（DB 表）形成「人读 + 机读」双轨，**有意为之，不合并。**

本计划聚焦三处**确有改进空间**的点，目标：消除重复、修复注入绕过、补齐运行时日志文件落盘。

---

## 修改①：抽取统一的数据路径解析工具

### 现状与问题

「容器路径探测 → 开发环境回退」的同一段逻辑在 **5+ 处**重复出现，每加一个文件级服务就复制一遍：

| # | 位置 | 服务 | 模式 |
|---|------|------|------|
| 1 | `__init__.py:662-679` | EventJournal | `config.journal_path` → `/app/journal/项目日志.md` → `emily-data/journal/项目日志.md` |
| 2 | `__init__.py:697-708` | UserMemoryService | `config.user_memory_dir` → `/app/user_memory` → `emily-data/user_memory` |
| 3 | `__init__.py:724-737` | PendingIssuesService | `config.pending_issues_path` → `/app/notebooks/待解决问题.md` → `emily-data/notebooks/待解决问题.md` |
| 4 | `__init__.py:386-395` | FileStorageService | `config.storage_root` → `/app/attachments` → `emily-data/attachments` |
| 5 | `__init__.py:243-249` | SkillRegistry | `/app/skills` → `config.skill_directory` → `emily-data/skills`（三级） |

此外服务类自身也带默认路径回退（如 `EventJournal.__init__` 的 `event_journal.py:32-40`、`PendingIssuesService.path` 的 `pending_issues.py:37-41`），与 Core 注入逻辑叠加后路径解析责任不清。

### 方案

新增一个共享路径解析工具，统一「config 值 → 容器路径 → 开发回退」三级探测：

**新增文件**：`emily-core/emily_core/infrastructure/paths.py`

```python
"""统一的数据路径解析工具。

三级探测：config 显式值 → 容器内路径(/app/...) → 开发环境回退(emily-data/...)。
"""
from pathlib import Path

# 项目根目录：infrastructure/ → emily_core/ → emily-core/ → Emily/
_PROJECT_ROOT = Path(__file__).resolve().parents[2]


def resolve_data_path(
    config_value: str,
    container_path: str,
    dev_relative: str,
) -> str:
    """解析数据存储路径。

    Args:
        config_value: Config 中显式配置的路径（优先级最高，非空即用）。
        container_path: 容器内默认绝对路径（如 /app/journal/项目日志.md）。
        dev_relative: 开发环境相对项目根的路径（如 emily-data/journal/项目日志.md）。

    Returns:
        最终生效的绝对路径字符串。
    """
    if config_value:
        return config_value
    cp = Path(container_path)
    if cp.parent.exists():  # 容器内目录存在 → 容器路径
        return str(cp)
    return str(_PROJECT_ROOT / dev_relative)
```

### 改动清单

1. **新增** `infrastructure/paths.py`（如上）。
2. **改 `__init__.py`** 5 处路径解析，替换为 `resolve_data_path()` 调用：
   - `_init_m8c_services`：EventJournal / UserMemoryService / PendingIssuesService 三段（`__init__.py:662-737`）
   - `_init_phase_c_deps`：FileStorageService（`__init__.py:386-395`）
   - `_init_skill_module`：skill_dir（`__init__.py:243-249`，注意此处是三级 fallback，调整为 `resolve_data_path` 的容器优先语义，或保留三级但抽公共片段）
3. **清理服务类自身回退**（可选，二期）：`EventJournal.__init__` 与 `PendingIssuesService.path` 内的默认路径推导改为「Core 必传 path，不传则 disabled」，避免双重回退语义冲突。**注意：此项需谨慎，因为 `session_agent.py:347` 当前正是依赖了 EventJournal 的默认回退——需先完成修改②再清理。**

### 验收要点

- 5 处路径解析行为**不变**（容器内仍走 `/app/...`，开发仍走 `emily-data/...`）。
- `docker logs emily-core` 启动日志中，5 个服务的 path/dir 输出与改动前一致。
- 新增单元测试覆盖 `resolve_data_path` 三分支（config 优先 / 容器路径存在 / 回退开发路径）。

## 修改②：SYS-confirm 复用 Core 注入的 EventJournal 实例

### 现状与问题

`session_agent.py:347` 在 `_handle_confirm` 里临时 new 了一个 EventJournal：

```python
event_app = EventApplication(EventService())
journal = EventJournal(path="", enabled=True)   # ← 临时实例，path="" 走默认回退
event_app.set_journal(journal)
```

问题：
1. **绕过 Core 的 journal 实例**：Core 在 `_init_m8c_services()` 创建的 `self._event_journal`（已注入 4 个 Application + query_service）没被复用，SYS-confirm 走的是另一个实例。
2. **绕过配置开关**：`enabled=True` 硬编码，忽略 `config.journal_enabled`；`path=""` 触发 `EventJournal` 自身默认路径回退，可能与其他服务写到不同位置（通常巧合一致，但不严谨）。
3. **重复创建 EventApplication**：`EventService` + `EventApplication` 在此临时 new，而 Core 已持有 `self._event_app`（已注入 journal）。

### 注入路径分析（已探查确认）

- `SessionFactory.__init__(self, bus, core=None)` 持有 `self._core`（`session_factory.py:25`）
- `SessionFactory.create()` 从 core 取 `_llm_client`、`_skill_registry` 传给 `SessionAgent`（`session_factory.py:50-60`）——**唯独没取 `_event_journal`**
- `SessionAgent.__init__` 也不接受 journal 参数（`session_agent.py:74-81`）

### 方案

沿现有 `llm_client` / `skill_registry` 的注入模式，把 Core 的 `_event_journal`（以及复用 `_event_app`）透传到 SessionAgent：

**改动 1 — `session_factory.py:50-60`**：增加 journal 透传
```python
journal = None
if self._core is not None:
    llm = getattr(self._core, "_llm_client", None)
    skill_registry = getattr(self._core, "_skill_registry", None)
    journal = getattr(self._core, "_event_journal", None)

agent = SessionAgent(
    conversation_id=conv_id,
    context=context,
    bus=self._bus,
    llm_client=llm,
    skill_registry=skill_registry,
    journal=journal,          # ← 新增
)
```

**改动 2 — `session_agent.py:74-93`**：构造函数增加 `journal=None` 参数并保存
```python
def __init__(self, conversation_id, context, bus, llm_client=None,
             skill_registry=None, journal=None):
    ...
    self._llm = llm_client
    self._skill_registry = skill_registry
    self._journal = journal      # ← 新增
```

**改动 3 — `session_agent.py:345-348`**：`_handle_confirm` 复用注入的 journal 与 Core 的 EventApplication
```python
# 优先复用注入的 journal；兜底仍临时构造（保持 fail-open）
journal = self._journal
if journal is None:
    journal = EventJournal(path="", enabled=True)
event_app = EventApplication(EventService())
event_app.set_journal(journal)
```

> 说明：保留 `journal is None` 的兜底分支，避免 Core 未初始化 journal 时 SYS-confirm 报错。但正常生产路径下走注入实例。

### 备选方案（更彻底，二期）

直接复用 Core 持有的 `self._event_app`（已注入 journal），而非在 SessionAgent 里 new `EventApplication(EventService())`。需把 `_event_app` 也透传进 SessionAgent。**一期不做**，因为 `handle_confirmation` 的调用契约需先确认 EventApplication 单例复用是否有状态污染风险。

### 验收要点

- 生产环境（Core 已初始化 journal）下，SYS-confirm 确认事件后，`项目日志.md` 由 Core 的 journal 实例写入，路径与 `config.journal_path` 一致。
- `config.journal_enabled=False` 时，SYS-confirm 不再写 journal（当前 bug：硬编码 enabled=True 会强制写）。
- 用 emy-test 走一遍「录入事件 → SYS-confirm 确认」流程，对比改动前后 `项目日志.md` 内容与 `business_event_logs` 表记录。
- `docker logs emily-core` 无新 warning。

## 修改③：运行时调试日志文件落盘（配置层，非加代码）

### 现状与问题（修正前述判断）

前文曾提「标准 logging 无文件落盘」——**不准确**。`bootstrap.py:19` 的 `_setup_logging()` 已实现：

```python
if config.log_to_file:
    os.makedirs(config.log_dir, exist_ok=True)
    date_str = datetime.now(BEIJING_TZ).strftime("%Y%m%d")
    log_file = os.path.join(config.log_dir, f"emily_{date_str}.log")
    file_handler = logging.FileHandler(log_file, encoding="utf-8")
    ...
    root_logger.addHandler(file_handler)
```

即 FileHandler 已就绪，日志格式 `%(asctime)s [%(levelname)s] %(name)s: %(message)s`，按日切分。**真正的问题是 `log_to_file` 开关是否默认开启、`log_dir` 在容器内是否有挂载——需确认。**

### 待确认项（实施第一步）

1. 查 `emily-core/emily_core/config.py` 中 `log_to_file` / `log_dir` / `log_level` 的默认值。
2. 查 `emily-data/config/core_config.json` 是否设置了 `log_to_file` / `log_dir`。
3. 查 `docker-compose-napcat.yml` 中 `emily-core` 是否有日志目录的 volume 挂载。

### 方案（依据确认结果二选一）

**方案 A — 默认已开启但未挂载**：
- 在 `docker-compose-napcat.yml` 为 `emily-core` 增加 volume：`./emily-data/logs:/app/logs`（路径以 `config.log_dir` 实际值为准）。
- 确认 `log_dir` 默认值指向 `/app/logs` 或类似容器内可写目录。

**方案 B — 默认关闭**：
- 在 `emily-data/config/core_config.json` 显式设置：
  ```json
  { "log_to_file": true, "log_dir": "/app/logs", "log_level": "INFO" }
  ```
- 或在 Config dataclass 将 `log_to_file` 默认值改为 `True`、`log_dir` 默认 `/app/logs`（容器优先）。
- 同步在 `docker-compose-napcat.yml` 增加日志目录 volume 挂载，否则容器重启日志丢失。

**方案 C — 增加日志轮转**（可选增强）：
- 当前 FileHandler 无大小/数量限制，长期运行会累积大文件。可改用 `logging.handlers.TimedRotatingFileHandler`（按日轮转 + 保留 N 天），在 `_setup_logging()` 内替换。**一期不做，标记为后续增强。**

### 改动清单

1. `config.py`：按确认结果调整 `log_to_file` / `log_dir` 默认值（若方案 B）。
2. `emily-data/config/core_config.json`：显式写入日志配置（推荐，优于改默认值）。
3. `docker-compose-napcat.yml`：`emily-core` 服务增加日志目录 volume。
4. `docs/技术踩坑备忘录.md`：补一条「运行时日志文件落盘配置」说明。

### 验收要点

- 重启 `emily-core` 后，容器内 `log_dir` 出现 `emily_YYYYMMDD.log`，内容与 `docker logs` 一致。
- `docker compose down && up` 后日志文件不丢失（volume 持久化）。
- `_setup_logging` 内 `try/except` 仍保证文件日志失败不阻断启动（现有逻辑，不破坏）。

## 实施顺序与依赖

```
修改②（journal 注入）  ← 独立，优先做，风险低、收益明确
    ↓
修改①（路径解析工具）  ← 抽公共工具，触及 5 处，需回归 5 个服务
    ↓
修改③（日志配置）      ← 配置层为主，需 docker volume 配合
```

- **修改②与修改①有耦合**：修改①的「清理服务类自身回退」子项需先完成修改②（否则 `session_agent.py:347` 的 `path=""` 兜底会失效）。因此修改②先做。
- **修改③完全独立**，可与任意一项并行。

## 整体验证

1. **容器重启验证**：`docker compose -f docker-compose-napcat.yml restart emily-core`，清 pycache 后观察启动日志无异常。
2. **emy-test 端到端**（按 CLAUDE.md 强制规则，先查 users 表取真实 UUID）：
   - 走「录入事件 → SYS-confirm 确认」流程 → 验证 `项目日志.md` 由注入实例写入（修改②）。
   - 走任意 SOP 流程 → 验证 5 个文件服务路径解析正常（修改①）。
   - 重启后查 `emily_YYYYMMDD.log` 存在且内容正确（修改③）。
3. **回归**：`docker logs emily-core` 对比改动前后启动日志，确认各服务 init path 输出一致（修改①行为不变）。

## 风险与回滚

- **修改①**：抽工具后若 `resolve_data_path` 的探测语义与某服务原有逻辑不一致（如 SkillRegistry 的三级 fallback vs 容器优先），可能改路径。**缓解**：逐个服务替换后单独 emy-test 验证；保留原逻辑作注释便于回滚。
- **修改②**：保留 `journal is None` 兜底分支，Core 未初始化时不阻断 SYS-confirm。风险极低。
- **修改③**：若 `log_dir` 指向不存在/无权限目录，`_setup_logging` 已有 `try/except` 兜底，只 warning 不阻断启动。
