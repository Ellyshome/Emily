关于全景节点，如果有新的文件上传，应该有机制观察判断，它是否是某个节点的产物，如果直接上传节点产物，但是节点还没创建过，应该提醒管理员，询问是否建立这个节点，并标记为已完成状态，尤其是一些里程碑的节点，比如有人上传了审核版本的景观施工图，则应该判断对应的’景观施工图节点’是否应该通知管理员标记为已完成。这应该是需要emily自备一套通用的参考节点，标记一般项目大概率会走过的节点，并写清楚各节点的产物，对应着来。

## AI 评审意见 v2（2026-07-25，基于补充说明更新）

### 一、需求核心——重新表述

经过补充说明，需求的内核更清晰了：**Emily 内置一套"行业参考节点知识库"，节点描述中定义产出成果及成果特征。当文件上传时，由 LLM 将文件信息（文件名、类型、可提取的内容线索）与参考节点描述做语义比对和推理，判断文件大概率属于哪个节点的产物。若当前项目实际节点库中尚不存在该节点，则主动向管理员发起询问。**

这个设计的两个关键场景：
1. **日常增量**：项目运行中有人上传了某个里程碑产物文件，但节点还没建 → 触发提醒
2. **项目中途批量接入**（你补充的重点）：Emily 在半途介入一个已运行一段时间的项目，前期有大量已完成的关键节点和资料需要一次性整合 → 批量扫描已有文件，反向还原项目进度

### 二、与上一版的思路修正

| 维度 | 上一版（规则为主） | 修正后（LLM 推理为主） |
|---|---|---|
| 匹配引擎 | 关键词+扩展名规则匹配为主，LLM 兜底 | **LLM 语义推理为主力**，规则仅做粗筛（减少 LLM 调用量） |
| 参考节点描述 | 简单 YAML 字段（keywords + extensions） | **丰富的自然语言描述**——产物是什么、包含什么内容、满足什么要求、典型命名习惯 |

### 三、参考节点知识库的设计

这是整个需求的**基石**——LLM 推理的质量直接取决于参考节点描述的质量。不能只是几个关键词，而应该是 LLM 可以"读懂"的语义描述。

建议的参考节点描述结构：

```yaml
# emily-data/node_templates/construction.yaml
# 每个参考节点是一份 LLM 可推理的"节点说明书"
project_type: "建筑工程"
nodes:
  - ref_id: "REF-CONST-MS-LANDSCAPE-DRAWING"
    node_name: "展示区/大区景观施工图出图"
    node_type: "MILESTONE"
    stage_id: 2  # 工程施工阶段
    stage_name: "工程施工"

    # ── 核心：LLM 推理依据 ──
    description: |
      景观施工图是景观工程从方案设计转入施工落地的关键里程碑节点。
      此节点标志着景观设计已完成施工图深度的绘制，图纸达到可指导现场施工的精度。
      通常在设计单位完成扩初设计、甲方和设计单位多轮评审修改后，
      最终输出审核版本的景观施工图（加盖出图章/审核章）。

    typical_artifacts:  # 典型产物描述——LLM 用来做语义匹配的核心字段
      - file_description: |
          景观施工图 CAD 文件或 PDF 图纸，通常以分册形式组织：
          总图分册（总平面图、索引图、竖向图、定位图、物料图）、
          详图分册（各节点详图、构筑物施工图）、
          水电分册（给排水施工图、电气施工图）、
          绿化分册（乔木/灌木/地被种植图）。
          审核版本通常在图纸封面或图框内标注"审核版""施工图""送审图"等字样，
          图纸编号体系遵循国家建筑标准（如建施-XX、景施-XX）。
        typical_filenames:  # 典型命名模式（供 LLM 参考，非硬匹配）
          - "景观施工图*审核*"
          - "*景施*"
          - "*景观*施工图*"
          - "*大区*景观*图纸*"
          - "Landscape Construction Drawing*"
        typical_extensions: [".dwg", ".pdf", ".rar", ".zip"]
        typical_quantity: "数十至上百个文件（分册打包）"
        typical_submitter: "设计单位项目负责人或设计总监"
        typical_stage_context: "通常在方案设计批复后、景观施工单位进场前"

    prerequisites:  # 前置依赖——帮助 LLM 理解这个节点在整个流程中的位置
      - "方案设计已获甲方批复"
      - "扩初设计评审通过"
      - "设计合同约定的施工图节点已到期或临近"

    # ── 创建时使用的节点字段 ──
    deliverables:
      - deliverable_name: "审核版景观施工图"
        target_amount: 1
        unit: "套"
        is_required: true
    owner_dept_hint: "设计部"
    related_company_hint: "设计单位"
```

**设计要点**：
- `description` 和 `typical_artifacts[].file_description` 用**完整的自然语言**写，而不是结构化关键词，因为 LLM 更擅长理解自然语言中的隐含特征
- `typical_filenames` 中的 glob 模式仅作**辅助参考**，不作为硬匹配规则——如果 LLM 推理结论与文件名模式矛盾，以 LLM 为准
- `typical_stage_context` 提供**流程位置锚点**，让 LLM 在推理时能判断"这个文件在整个项目流程中大概处于什么阶段"

### 四、LLM 推理匹配流程

这是需求的**核心引擎**。不论实时上传还是批量扫描，匹配流程一致：

```
文件上传/扫描
    ↓
[1] 提取文件特征
    - 文件名、扩展名、大小
    - 文件类别（file_category，已有字段）
    - 项目上下文（project_id → 项目类型、当前阶段、已有节点）
    - 如有解析能力：OCR 提取的标题栏文字、PDF 元数据
    ↓
[2] 粗筛（规则层，减少 LLM 调用）
    - 根据 file_category 缩小候选：PHASE_DELIVERABLE 类文件才进入匹配
    - 根据项目类型选参考模板集（construction / software / ...）
    - 排除已明确关联到节点的文件（file_id 已挂在某个 deliverable 上）
    ↓
[3] LLM 语义推理（核心步骤）
    输入给 LLM 的上下文：
    - 当前项目基本信息（项目名称、类型、当前阶段、已有的节点清单）
    - 文件特征（步骤1提取的全部信息）
    - 候选参考节点描述（步骤2筛选后的参考节点知识库条目）
    
    LLM 输出结构化判断：
    {
      "matched": true/false,
      "ref_node_id": "REF-CONST-MS-LANDSCAPE-DRAWING",
      "confidence": 0.85,           // 0.0 ~ 1.0
      "reasoning": "文件名包含'景观施工图审核版'，文件类型为DWG图纸包，
                    项目当前处于工程施工阶段，且已有节点中尚未出现景观施工图
                    相关里程碑。文件命名模式与该参考节点高度吻合。",
      "suggested_action": "create_and_complete",  // create_and_complete | attach_to_existing | ignore
      "suggested_node_name": "展示区景观施工图出图",  // LLM 可根据项目上下文调整
      "matched_deliverable": "审核版景观施工图"
    }
    ↓
[4] 冲突检查
    - 查询当前项目实际节点库：是否已有同名/相似节点？
    - 若已有但状态非 COMPLETED → 建议更新进度而非创建
    - 若已 COMPLETED → 仅关联文件
    ↓
[5] 决策分支
    ├── confidence >= 阈值（如 0.85）且无冲突 → 通知管理员确认
    ├── confidence < 阈值 → 静默记录，不打扰
    └── 管理员确认 → 创建节点 + 标记完成 + 关联文件
```

**关于 LLM 推理的成本**：
- 实时上传：每次最多 1 次 LLM 调用（单文件匹配），成本可控
- 批量扫描：可能需要多次 LLM 调用。可优化为**一次 LLM 调用批量匹配**（将项目已有文件清单 + 所有候选参考节点一次性输入，让 LLM 输出完整的匹配映射表），而不是逐文件调用

### 五、项目中途批量接入场景——独立的产品能力

这是你补充的重点场景，它与日常增量的处理逻辑有本质不同，应该作为一个**独立的产品功能**来设计：

**触发方式**：管理员主动发起，而非被动触发。例如：
- 管理员说："Emily，帮我扫描项目 ECOCITY-26 下已有的文件，看看哪些应该建立节点"
- 或者在 CLI 中执行：`uv run python scripts/manage_nodes.py scan-files --project-id ECOCITY-26`

**批量流程**：
```
管理员发起扫描
    ↓
Emily 拉取项目下所有未关联节点的文件（WHERE source_module_id = '' OR source_module_id IS NULL）
    ↓
将文件清单 + 参考节点知识库（按项目类型筛选后的子集）→ 一次性输入 LLM
    ↓
LLM 输出完整的匹配映射表：
[
  {file_id: "F-001", ref_node: "REF-CONST-MS-LANDSCAPE-DRAWING", confidence: 0.92, ...},
  {file_id: "F-002", ref_node: "REF-CONST-MS-LANDSCAPE-DRAWING", confidence: 0.88, ...},  // 同节点多个文件
  {file_id: "F-003", ref_node: null, confidence: 0, ...},  // 无法匹配
  ...
]
    ↓
Emily 汇总为一份"建议创建节点清单"，列出：
  - 建议创建的里程碑节点（去重合并后）
  - 每个节点匹配到哪些文件作为证据
  - 每个建议的置信度
    ↓
管理员审核清单 → 勾选确认 → 批量创建节点 + 标记完成 + 关联文件
```

**批量接入的独特需求**：
1. **去重合并**：同一个参考节点可能匹配到多个文件（如景观施工图的 CAD + PDF + 说明文档），这些文件应合并归属到同一个节点
2. **时效推断**：文件的 `created_at` 可以作为节点 `completed_at` 的参考
3. **缺失节点推导**：如果 LLM 识别出文件 A（方案设计）和文件 C（施工图），但缺少中间节点 B（扩初设计）的文件，应主动提示"根据参考标准流程，中间似乎缺少扩初设计节点"
4. **审批粒度**：批量场景下不应逐个节点确认（太累），而应一次性展示清单，管理员勾选后批量执行

### 七、与信息库（World Book）的关系

你提到的"信息库"是一个关键概念。当前 Emily 已有 `world_book_builder.py`（构建项目全景描述，供 LLM 上下文使用）。参考节点知识库可以融入这个体系：

- **World Book 作为推理上下文**：LLM 做文件→节点匹配时，World Book 提供当前项目的已有节点清单、项目阶段、参与单位等信息，作为匹配推理的"锚点"
- **参考节点知识库作为"外部知识"**：独立于具体项目，是所有项目共用的行业标准参照
- 两者组合 → LLM 既有"这个项目长什么样"的上下文，又有"这个行业的标准流程是什么"的参照

## 基础设施设计草案 —— 全景节点参考样板（Node Template）

> **定位**：这是 Emily 的"项目流程常识库"。存储于文件系统（`emily-data/node_templates/`），启动时加载到内存。供 LLM 推理匹配和节点批量创建两个场景消费。

---

### 一、总体架构

```
emily-data/node_templates/          ← 文件系统（Git 可追踪，人工可编辑）
  ├── construction.yaml             ← 建筑工程行业
  ├── construction_landscape.yaml   ← 可按专业拆分（可选）
  └── software.yaml                 ← 软件开发行业（未来）

        ↓ 启动时加载 / 运行时热重载

emily_core/infrastructure/node_template/
  ├── __init__.py                   ← 暴露 NodeTemplateRegistry 单例
  ├── definition.py                 ← NodeTemplateDefinition dataclass
  ├── parser.py                     ← YAML 解析 + 校验
  ├── registry.py                   ← 加载/查询/热重载/dump_as_text
  └── template_tool.py              ← 系统工具：模板查询（可选）

        ↓ 消费方

┌──────────────────────┬──────────────────────┬─────────────────────┐
│ artifact_matcher.py  │ manage_nodes.py CLI  │ world_book_builder  │
│ （未来：文件匹配）    │ template 子命令       │ （LLM 上下文注入）   │
└──────────────────────┴──────────────────────┴─────────────────────┘
```

**设计原则**：
- **文件系统为单一真相源**，不进数据库（避免同步问题，方便 Git 追踪和人工编辑）
- **对齐 SkillRegistry 模式**：scan → parse → atomic reload → dump_as_text。两者代码结构一致，降低维护心智负担
- **启动时加载，运行时热重载**：模板变更后无需重启容器（通过 CLI `reload` 命令或 API 触发）
- **dumb_as_text() 为 LLM 消费接口**：与 SkillRegistry.dump_as_text() 同模式，拼入 LLM prompt 的参考材料区

---

### 二、文件格式规范

#### 2.1 目录与命名

```
emily-data/node_templates/
  ├── construction.yaml       # 建筑工程行业（主文件，涵盖全阶段）
  ├── construction_*.yaml     # 可选：按专业拆分的子文件（如 landscape / structure / mep）
  └── {industry}.yaml         # 命名规则：{行业标识}.yaml，作为 industry 字段值
```

- 文件编码：UTF-8
- 文件扩展名：`.yaml`（与 Skill 的 `.skill.yaml` 区分，避免被 SkillRegistry 误扫描）
- 每个文件内可包含多个模板（一个 list）

#### 2.2 完整格式定义

```yaml
# ═══════════════════════════════════════════════════════════════════════
# 全景节点参考样板 —— 建筑工程行业
# 文件: emily-data/node_templates/construction.yaml
# ═══════════════════════════════════════════════════════════════════════

industry: "construction"              # 行业标识（必填，作为文件名前缀）
industry_name: "建筑工程"             # 行业中文名（必填）
version: "1.0.0"                     # 模板版本号（必填）
description: |                        # 行业概述（必填）
  建筑工程行业全景节点参考样板，覆盖从立项到交付结算的全生命周期。
  适用于住宅、商业综合体、产业园区等建筑工程项目。
stages:                               # 阶段定义（可选，供 LLM 理解阶段含义）
  - stage_id: 0
    stage_name: "立项阶段"
    description: "项目策划、可研、立项批复"
  - stage_id: 1
    stage_name: "规划设计阶段"
    description: "方案设计、扩初设计、施工图设计、报批报建"
  - stage_id: 2
    stage_name: "工程施工阶段"
    description: "招标采购、施工准备、主体施工、专项施工、竣工验收"
  - stage_id: 3
    stage_name: "交付结算阶段"
    description: "竣工备案、交付使用、结算审计、质保期管理"

templates:                            # 模板列表（必填）
  - ref_id: "REF-CONST-MS-001"        # 参考模板唯一标识（必填，建议格式 REF-{行业}-{类型}-{序号}）
```

### 三、Python 数据模型

对齐 `SkillDefinition` 的 dataclass 模式：

```python
# emily_core/infrastructure/node_template/definition.py

from dataclasses import dataclass, field


@dataclass(frozen=True)
class ArtifactDescription:
    """产物识别特征——LLM 匹配的核心依据。"""
    name: str                          # 产物名称
    file_description: str              # 自然语言描述（核心匹配字段）
    is_required: bool = True
    target_amount: float = 1.0
    unit: str = "份"
    typical_filenames: list[str] = field(default_factory=list)
    typical_extensions: list[str] = field(default_factory=list)
    typical_quantity: str = ""
    typical_submitter: str = ""


@dataclass(frozen=True)
class Prerequisite:
    """前置条件。"""
    description: str


@dataclass(frozen=True)
class NodeTemplateDefaults:
    """创建节点实例时的默认值。"""
    owner_dept_hint: str = ""
    related_company_hint: str = ""
    sort_order: int = 0
    remark: str = ""


@dataclass(frozen=True)
class StageDefinition:
    """项目阶段定义。"""
    stage_id: int
    stage_name: str
    description: str = ""


@dataclass(frozen=True)
class NodeTemplateDefinition:
    """单条参考节点模板。"""
    ref_id: str
    node_name: str
    node_type: str                    # MILESTONE / WORK_PACKAGE / TASK
    stage_id: int
    description: str                  # 节点描述（LLM 推理依据）
    typical_artifacts: list[ArtifactDescription]
    stage_name: str = ""
    prerequisites: list[Prerequisite] = field(default_factory=list)
    flow_position: str = ""
    defaults: NodeTemplateDefaults = field(default_factory=NodeTemplateDefaults)


@dataclass(frozen=True)
class NodeTemplateFile:
    """一个模板文件（.yaml）的完整内容。"""
    industry: str
    industry_name: str
    version: str
    description: str                  # 行业概述
    templates: list[NodeTemplateDefinition]
    stages: list[StageDefinition] = field(default_factory=list)
    source_file: str = ""             # 来源文件路径（加载时填充）
```

**设计决策**：
- 全部 `frozen=True`：模板加载后不可变，保证线程安全
- 不依赖 ORM：纯 dataclass，不映射数据库表
- `NodeTemplateFile` ≠ `NodeTemplateDefinition`：前者是文件级容器（industry + templates），后者是单条模板

### 四、Registry 接口约定

对齐 `SkillRegistry` 的接口模式：

```python
# emily_core/infrastructure/node_template/registry.py

class NodeTemplateRegistry:
    """全景节点参考样板注册表。
    
    生命周期：启动时 load() → 常驻内存 → 热重载 reload()。
    线程安全：所有读写操作持 RLock。
    """

    # ── 生命周期 ──
    def load(self) -> RegistryStatus: ...
    def reload(self) -> RegistryStatus: ...

    # ── 查询（按 ref_id 精确查）──
    def get(self, ref_id: str) -> NodeTemplateDefinition | None: ...

    # ── 查询（条件过滤）──
    def list_all(self) -> list[NodeTemplateDefinition]: ...
    def list_by_industry(self, industry: str) -> list[NodeTemplateDefinition]: ...
    def list_by_stage(self, stage_id: int) -> list[NodeTemplateDefinition]: ...
    def list_by_type(self, node_type: str) -> list[NodeTemplateDefinition]: ...
    def list_by_stage_and_type(self, stage_id: int, node_type: str) -> list[NodeTemplateDefinition]: ...

    # ── 模糊搜索（供管理员查找模板）──
    def search(self, query: str) -> list[NodeTemplateDefinition]: ...
    # 对 node_name + description 做子串匹配，返回得分排序

    # ── LLM 消费接口（核心）──
    def dump_as_text(
        self,
        *,
        industry: str | None = None,
        stage_id: int | None = None,
        ref_ids: list[str] | None = None,
    ) -> str: ...
    # 将符合条件的模板格式化为纯文本，供 LLM prompt 注入。
    # 输出结构：
    #   ## 参考节点模板（行业标准）
    #   ### REF-CONST-MS-001 项目立项批复 [MILESTONE | 立项阶段]
    #   节点描述：...
    #   典型产物：
    #     - 项目立项批复文件：...
    #       识别特征：...
    #       典型文件名：...
    #   前置条件：...
    #   流程位置：...

    def dump_for_matching(
        self,
        project_context: str,
        files_summary: list[dict],
        *,
        industry: str | None = None,
    ) -> str: ...
    # 专门为文件→节点匹配场景优化的输出。
    # 包含：项目上下文 + 文件清单 + 候选模板描述，
    # 末尾附带 LLM 结构化输出指令（JSON schema 约束）。

    # ── 元信息 ──
    def list_industries(self) -> list[str]: ...
    # 返回 ["construction", ...]

    def get_industry_info(self, industry: str) -> dict | None: ...
    # 返回 {"industry_name": "建筑工程", "version": "1.0.0", "template_count": 18, ...}

    def get_status(self) -> RegistryStatus: ...
    # 返回当前状态快照（同 SkillRegistryStatus 结构）
```

**关于 `dump_as_text()` 与 `dump_for_matching()` 的区别**：

| | `dump_as_text()` | `dump_for_matching()` |
|---|---|---|
| 用途 | 通用上下文注入（如 World Book） | 文件→节点匹配场景专用 |
| 包含内容 | 全部模板字段 | 匹配核心字段 + 项目上下文 + 结构化输出指令 |
| 末尾指令 | 无 | 附带 JSON schema 约束 + 匹配规则说明 |
| token 开销 | 较小（纯描述） | 较大（含指令） |

### 五、Parser 约定

```python
# emily_core/infrastructure/node_template/parser.py

def parse_template_file(file_path: str) -> NodeTemplateFile:
    """解析单个 .yaml 模板文件。
    
    Args:
        file_path: 模板文件绝对路径
    
    Returns:
        NodeTemplateFile: 解析结果
    
    Raises:
        TemplateParseError: 格式错误（含文件名和行号）
    """

class TemplateParseError(Exception):
    """模板解析错误，携带文件名和具体错误信息。"""
    def __init__(self, file_path: str, message: str): ...
```

**校验规则**（parse 时执行，fail-fast）：
1. `industry` 不能为空，必须与文件名前缀一致
2. `ref_id` 全局唯一（同一次 load 内）
3. `node_type` 必须是 `MILESTONE` / `WORK_PACKAGE` / `TASK` 之一
4. `stage_id` 必须是 0/1/2/3
5. `typical_artifacts` 至少 1 个
6. 每个 artifact 的 `name` 和 `file_description` 不能为空
7. 解析失败的文件记录到 RegistryStatus.failed_files，不阻断其他文件加载

### 十一、开放决策点

1. **一个行业一个文件 vs 一个模板一个文件？**
   - 建议：一个行业一个文件（YAML 内 list 组织）。理由：同类模板关联紧密，一起编辑更方便；文件数少，加载快。与 Skill 的 `*.skill.yaml` 一个 skill 一个文件不同（skill 间相互独立，模板间有前后序关系）。

2. **`ref_id` 的命名空间是全局还是行业内？**
   - 建议：全局唯一（`REF-CONST-MS-001`）。前缀包含行业，避免跨行业冲突。

3. **`dump_as_text()` 的输出要不要缓存？**
   - 建议：不缓存。内容依赖过滤参数（industry/stage_id 等），缓存命中率低；模板总数少（<100），实时拼接开销可忽略。

4. **`stage_id` 是否支持扩展（如 4/5）？**
   - 当前数据库 `stage_id` 对应 `projects.lifecycle_stage`（0-3）。如果未来行业需要更多阶段，模板的 `stage_id` 可以独立于项目阶段（模板的阶段是它自己的分类维度），但映射关系需要在匹配引擎中处理。当前先限制 0-3，保持与数据库一致。
