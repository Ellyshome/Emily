# Emily 系统技术栈定版 V1

> **定位**：系统级技术栈基线。为每个关注点指定唯一实现，并明确划定"不引入"的范围，作为后续所有需求与计划的选型依据。
> **日期**：2026-09-11
> **来源**：仓库实测调研（执行编排、调度宿主、领域服务三域全量走查）与内核迁移系列讨论
> **服务对象**：`需求/LangGraph编排内核化/` 下的需求基线与模块拆解清单
> **性质**：约束型技术决策。按宪法 §1.2，本文只定"选什么、不用什么、以什么为边界"，不写字段、签名与文件组织

---

## 一、定版原则

一个关注点只有一个实现。同一个问题出现两个组件，就是未来的排障成本。

核心依赖清单保持短。能不加就不加，每个新增都是一份凭据、一份备份、一条升级路径。

领域层不引框架。业务规则（权限判定、节点状态机、成果匹配、可见范围）用清晰的分层与普通代码表达，不交给框架代管。

选型只看两件事：能否减少自研代码量，是否带来新的运维面。只满足前者而后者代价过高的，不选。

所有新依赖锁定版本上界并登记。项目已被 `langgraph` 从 `>=0.2.0` 到实装 1.2.9 的 API 断裂伤过一次，教训要变成纪律。

---

## 二、LangGraph 的边界

这是本次定版最需要先划清的一条：LangGraph 承担编排与决策，不承担资源、数据、通道与业务规则。

**进 LangGraph 的**

| 内容 | 现状 |
|---|---|
| 会话主循环（LLM 与工具的条件边循环） | `session/loop.py` 手写，待改 |
| 任务级粗排与两级编排（层内并行、依赖跳过、深度上限） | `session/capability_plan.py` 手写游标，待改 |
| 能力调用边界（SOP 能力为子图，查询与写工具为节点） | `session/capability_runner.py` 部分具备 |
| 门禁与评审判定分支（权限、分级兜底、质量门、专家评审） | 评审已在图内，门禁待收敛 |
| 挂起与多轮续接 | 现为内存登记表，待改 |
| 失败三态回传与错误纠偏 | 已有 `CapabilityResult` 与 `error_analysis` |
| 检查点与断点恢复 | 已有 Postgres 检查点 |

**不进 LangGraph 的**

| 内容 | 归属 |
|---|---|
| 会话池、并发上限、分布式锁、TTL | 宿主外壳 |
| 事件推送与对外流式 | 宿主外壳（事件源可由图产出） |
| 定时作业与批处理 | 宿主外壳（调度引擎外移） |
| 领域业务规则与状态机 | 领域层，不引框架 |
| 数据读写与行级隔离 | Repository 与数据库 |
| 工具实现本体 | 能力层，无框架 |
| 检索与文档解析 | pgvector 与解析库 |
| 权限判定与可见范围推导 | 领域层，自研保留 |
| 审计、台账、归档 | 数据库表与文件 |

按此边界，LangGraph 覆盖的是"下一步做什么、走哪条路"，占系统的比重不大。这也是前面结论的由来：它可以大面积覆盖编排，但覆盖不了整个工作流系统。

## 三、技术栈全景

| 关注点 | 选定 | 状态 | 理由与边界 |
|---|---|---|---|
| 语言与运行时 | Python 3.12 + asyncio + uv | 已有 | 全系统统一，脚本与内核同一运行时 |
| 服务框架 | FastAPI + uvicorn | 已有 | 单端口：业务 18080（含 emy-console `/console/`）；原运维看板 18081 已于 2026-09-13 退役 |
| 进程与部署 | Docker Compose 单机多容器 | 已有 | 不引 Kubernetes，当前规模不需要编排平台 |
| 编排内核 | LangGraph（StateGraph + 检查点 + 中断） | 已有，扩展使用 | 唯一编排实现；见第二节边界 |
| LLM 客户端 | OpenAI 兼容 SDK | 已有 | 不引入 LangChain 主包 |
| 提示词与角色 | 文件化 prompt（`emily-data/prompts/`） | 已有 | 版本可追溯，优于代码内拼接 |
| 业务数据库 | PostgreSQL 16 + SQLAlchemy 2 + Alembic | 已有 | 业务台账、审计、归档同库 |
| 向量检索 | pgvector + 本地 TEI（BGE-m3） | 已有 | 不引独立向量数据库，避免第二份数据源 |
| 会话运行时 | 带过期的外部存储（键过期 + 分布式锁 + 订阅广播） | 新增 | 取代进程内会话池；多副本部署的前置条件 |
| 行级隔离 | 现有注入器，必要时下沉到数据库策略 | 候选 | 现状对复杂查询 fail-open，是需要收敛的点 |
| 权限判定 | 自研保留（三维短路 + 6 级树形继承 + 编码通配 + 缓存） | 已有，不换 | 现有表达力覆盖密级、企业类型、节点范围三维与通配编码，迁移会把已验证逻辑变成待验证 |
| 身份与认证 | 现有 API Token | 已有 | 出现 SSO 或多客户需求时再引入统一身份组件，暂缓 |
| 事件与推送 | 现有出站总线与 SSE 端点，事件源改为框架事件流 | 已有，改造 | 通道属于外壳，事件属于图 |
| 定时与批处理 | 现有数据库驱动调度器，外移出内核 | 已有，外移 | 它已具备幂等、跨副本互斥锁、执行日志、下次执行时间计算，换库收益为零 |
| 任务队列 | 暂不引入 | 暂缓 | 当前吞吐不需要；队列极易演变为第二编排器 |
| 文件存储 | 本地目录，规模上升时换对象存储 | 候选 | 多副本部署或大文件场景出现再切换 |
| 文档解析 | docling-slim + markitdown + camelot + pdf2image | 已有 | 表格与版式解析能力已验证 |
| 文本嵌入 | TEI cpu-1.6（版本已钉） | 已有 | 版本不可漂移，1.7 有段错误历史 |
| LLM 可观测 | 自托管 LLM 追踪平台 | 新增 | 取代人工阅读 jsonl 抓包 |
| 链路追踪 | OpenTelemetry | 新增 | 通用标准，与追踪平台互补 |
| 监控与告警 | 指标采集与看板组件 | 候选 | 替换自研看板的展示层，采集层可保留 |
| 错误聚合 | 异常聚合服务 | 候选 | 可选，上线后按需 |
| 脚本与运维面 | 现有 ScriptManager + 控制台 | 已有 | 参数 schema 与写库二次确认是既有正确设计 |
| 接入通道 | NapCat + AstrBot 薄插件（企业微信已有 compose） | 已有 | 薄插件只做去重、标准化、转发 |
| 前端 | 微信小程序 + 静态控制台 | 已有 | 不做框架迁移 |
| 测试与回归 | golden 语料 + 消息模拟 + 一致性校验脚本 | 已有，扩展 | 框架升级的回归语料要复用这套 |
| 配置 | 环境变量 + 配置文件 | 已有 | 已知问题：调度配置文件无代码读取，待修 |

## 四、明确不引入的清单

"技术栈"的实质是划定不做什么。以下逐条否掉，理由各一句。

| 不引入 | 理由 |
|---|---|
| LangChain 主包与 Agent 生态 | 现有内核刻意只用 LangGraph 与分块子包，全量引入会把依赖面与版本漂移风险放大数倍 |
| 耐久工作流引擎（Temporal 类） | 与 LangGraph 争夺执行权，等于自带第二个编排器 |
| 分布式任务队列（Celery 类） | 先把内核编排做完，队列在编排未定时只会增加一层调用栈 |
| 消息中间件（Kafka/RabbitMQ） | 单机多容器的规模用不上，Postgres 与订阅广播足够 |
| 独立向量数据库 | pgvector 已在用，第二份检索数据源会带来同步与权限过滤的双重麻烦 |
| 搜索引擎（OpenSearch 类） | 检索质量瓶颈在切分与可见范围过滤，不在检索引擎 |
| Kubernetes 与服务网格 | 部署复杂度与人力不匹配 |
| 策略引擎（Casbin/OPA 类） | 现有权限模型是多维加通配编码，策略引擎表达力不足，且现值是历史事故换来的资产 |
| 统一身份平台（Keycloak 类） | 单租户加 API Token 已满足现状，等 SSO 或多客户需求出现再引 |
| 低代码运营后台 | 控制台需求已由现有静态页与脚本注册表覆盖 |

## 五、新增依赖的引入门槛

任何新增组件在评审时必须逐条回答，缺一条不通过：

| 编号 | 问题 |
|---|---|
| 1 | 这个问题能否用配置或现有组件解决 |
| 2 | 它替代的是自研代码的哪一部分，删掉多少行 |
| 3 | 它带来哪些新运维面（凭据、备份、端口、升级） |
| 4 | 是否有官方镜像与可控的部署形态 |
| 5 | 版本上界锁在何处，由谁负责升级 |
| 6 | 升级回归语料落在哪里 |

第 5 与第 6 条是硬要求。已有的教训是版本假定与实装不符导致 API 断裂，修复成本远超当初写清一行版本号。

## 六、分期与迁移顺序

前置条件不变：2026-09-11 的会话重构需要先收敛（灰度开关默认关、测试有条件通过、尚有缺陷与测试数据待清）。

| 批次 | 内容 | 说明 |
|---|---|---|
| 批一 | 会话运行时存储、LLM 追踪、链路追踪、指标看板、对象存储（按需） | 都是装上即有收益且几乎不动业务代码，与内核迁移可并行 |
| 批二 | 行级隔离下沉、统一身份（按需） | 会触及表结构与登录链路，放在内核图化之后 |
| 不动 | 数据库、向量检索、权限判定、调度器、ScriptManager、通道、前端 | 保留现状，只做位置调整 |
| 不引 | 第四节全表 | 除非业务形态发生根本变化，否则不重新讨论 |

内核图化与外壳剥离建议分两次落地，避免一次变更同时改执行形态与运行环境。

## 七、与既有约束的关系

新增组件一律走注册通道接入，禁止裸文件与硬编码接线（宪法 C11、`CLAUDE.md` 约束 12）。

内核形态升级已获授权，`CLAUDE.md` 约束 13 已重述为"对业务功能增长冻结"，内核自身的形态升级属独立命题，需专项立项（见 `需求/LangGraph编排内核化/LangGraph编排内核化_需求基线_V1.md` 第七节）。

本文与模块拆解清单配套使用：拆解清单决定"每块归谁"，本文决定"归谁之后用什么实现"。两者冲突时以本文的组件边界为准，归属判断以拆解清单为准。

---

## 八、定版之后要守的纪律

定版的价值不在于写下来，而在于此后不再新增。一旦"遇到问题就引一个库"重新成为习惯，这份文件会退化为一份清单。

建议把三件事固定下来：新增依赖必须回答第五节六问；每个关注点的现有实现变更要回写本文；每季度核对一次"实际引用 vs 本文登记"，出现未登记依赖即视为违规处理。
