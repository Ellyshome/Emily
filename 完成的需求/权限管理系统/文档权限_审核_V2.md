### 2.2 架构契合度 — 资深架构师

**审核结论**：⚠️ 方向正确，需明确与现有系统的 3 个集成点

**亮点**：

- 以全景节点为锚点的设计与 Emily 架构高度契合。`File` 表已有 `source_module_id` / `source_module_type` 字段建立文件→节点关联，`NodeAccessibleFile` 表（`models.py:1264`）已实现 node_id↔file_id 的 M:N 映射，数据基础完备
- "本节点产生的文件默认参与者可见"的默认策略与现有 `row_security.py` 的 `company_id` 过滤互补，不冲突

**全新发现：`NodeAccessibleFile` 表已存在**。

```python
# models.py:1264-1283
class NodeAccessibleFile(Base):
    __tablename__ = "node_accessible_files"
    node_id     # ← 全景节点 ID
    file_id     # ← 文件 ID
    added_by    # ← 授权人 ID（正对应"节点负责人"）
    added_at    # ← 授权时间
    # UniqueConstraint(node_id, file_id)
```

这意味着 V1 审核中建议的"新建 `file_node_visibility` 表"**无需从零设计**——`NodeAccessibleFile` 已覆盖核心 M:N 关系。但该表目前缺少以下字段：

| 缺失字段 | 用途 | 优先级 |
|----------|------|--------|
| `company_id` | 限定可见的企业（目前仅限定节点，未限定企业） | **高** |
| `visibility_type` | 区分 NODE_DEFAULT（自动）/ NODE_VISIBLE（主动） | 中 |
| `is_active` | 支持撤销后保留审计记录而非物理删除 | 中 |

**需明确的 3 个集成点**：

1. **权限优先级位置**：需求未说明"节点文档可见"在现有优先级链中的位置。建议：
   ```
   DENY > 单独文件授权 > 节点文档可见(NODE_VISIBLE) > TEMP > PERMANENT > AUTO
   ```
   理由：节点负责人设置的是 **群体授权**（节点+企业维度的批量授权），其优先于个人的临时/永久授权，但低于显式 DENY 和单独文件授权。

2. **与行级安全的叠加**：`row_security.py` 已对 `files` 表注入 `company_id` 过滤。节点文档权限需叠加 `node_id` 维度的附加过滤。两层过滤关系建议为 **AND**（最严格）：
   ```
   最终可见文件 = company_id ∈ 用户归属企业
              AND node_id ∈ 用户参与的节点
              AND (node_id, file_id) ∈ NodeAccessibleFile
   ```
   如果期望的是 OR（用户只要满足任一条件即可见），请在需求中明确说明。

3. **权限编码系统对接**：`code_compiler.py` 已注册 `DOC` 资源类型和 4 级密级。节点文档可见可以通过 `PermissionGrant` 表（`grant_type=NODE_VISIBLE`）或查询 `NodeAccessibleFile` 表实现。建议在需求中明确选哪一种（推荐前者，与现有缓存体系兼容；后者需独立缓存设计）。

### 2.3 安全性 — 安全工程师

**审核结论**：⚠️ 方向正确，有 4 项安全需补

**认可的方面**：
- "非建设单位用户只可读"明确了最小权限边界
- "节点删除则权限自动取消"是良好的生命周期安全策略
- "用户调离单位自动丧失权限"确保人员变动时权限及时回收
- 以节点为锚点的授权边界天然防止跨节点越权

**安全考量缺口**：

1. **密级降级风险（V1 已提及，仍未解决）**：第 5 行未提及密级检查。如果有文件标记为"机密"（`confidentiality=2`），节点负责人将其设为"节点可见"，L2 参建执行用户是否也能看到？如果答案是"是"，则构成严重的密级降级漏洞。**强烈建议**：
   ```
   最终可见 = 节点可见(是) AND 密级可见(是) AND 6级RBAC通过(是)
   ```
   即节点可见性不能绕过密级检查。文档密级 ≥ 用户可见最大密级时方可展示。

2. **自然语言接口的安全边界**：第 12 行描述"通过 IM 自然语言提交文件描述，由 agent 选择文件"——这引入了 LLM 幻觉风险：
   - Agent 可能理解错误，将未授权的文件展示给用户（信息泄露）
   - Agent 可能误解"确认范围"的指令，批量授权了不应授权的文件
   - **建议**：① agent 选出的文件清单必须由发起的建设单位用户**逐项确认**（非批量确认）；② 每次设置操作写入 `permission_audit_log`（`operation_type=NODE_VISIBILITY_CHANGE`）；③ 最终授权动作始终由后端执行，agent 仅做推荐，不直接操作权限表

3. **建设单位用户的权限边界**：第 10 行只说"非建设单位用户只可读"，但第 5 行说"节点负责人选择文档设为节点可见"——节点负责人本身是建设单位人员。如果某个建设单位用户不是节点负责人，他能否：
   - 看到该节点的所有文件？（从第 5 行"默认参与者可见"推断，应该可以）
   - 编辑/删除该节点的文件？（未说明）
   - 将文件设为对其他企业可见？（未说明，这是一个权限放大风险点）

   建议明确：**只有节点负责人可以管理文件可见性**，其他建设单位用户仅有查看/编辑权。

4. **跨项目文件泄露**：第 5 行的"选择已入库的企业单位为参与单位"——如果有企业虽已入库但**不在本项目**参与（例如已退场的企业），节点负责人是否能将其选为参与单位？建议限定可选的单位范围为**本项目关联的履约中企业**（`CompanyInfo.status=active` 且在本项目有分配）。

## 四、替代方案

当前需求的核心模型（节点负责人 → 选文档 → 选企业 → 授权）简洁实用，且与现有 `NodeAccessibleFile` 表和全景节点体系高度契合，**整体方向无需替代**。

但在**接口方案**上有一个值得考虑的替代：

### 接口方案对比

#### 方案 A：当前方案 —— IM 自然语言 + Agent
- **思路**：用户通过 IM 说"把 XX 施工图设为节点可见给 XX 公司"，Agent 解析意图 → 搜索文件 → 展示清单 → 用户确认
- **优势**：与 Emily 的 IM 交互模式一致，无需额外前端开发
- **劣势**：LLM 解析文件描述存在歧义（"B3 区 2 层结构图"可能匹配多个文件）；批量操作时确认成本高；无法展示文件缩略图等富信息
- **适用场景**：文件量中等（<100/节点）、文件名规范的场景

#### 方案 B：补充最小 API（✅ 推荐作为补充）
- **思路**：保持 IM 自然语言入口的同时，增加一个简单的 `GET /api/v1/files/by-node/{node_id}` 查询端点，返回节点关联的文件清单（含文件名/类型/密级/上传时间），Agent 拿到结构化数据后做精确匹配和展示
- **优势**：Agent 选文件时不再依赖模糊的文本描述匹配；用户确认时看到的清单更准确；API 可复用于后续任何文件浏览场景
- **劣势**：需要开发一个新端点（工作量 ~2h）；不改变整体方案，是增强而非替代
- **适用场景**：所有场景，作为方案 A 的增强层

**建议**：采用 A+B 组合——IM 自然语言作为交互入口，API 作为 Agent 的内部查询依赖。不要求用户直接使用 API。
