## 1. 一句话定位

Emily 进化日志系统通过 `pipeline_run_id` 串联一次完整请求的"意图→规划→执行→反馈"全链路，8 张表各司其职，共享统一写入工具，非阻断持久化，为成本追踪、质量评估、行为审计提供结构化数据基础。

## 2. 架构全景

```
                            PipelineBUS.run()
                                  │
                    ┌─────────────┼─────────────┐
                    │  set_context()              │
                    │  (注入 pipeline_run_id 等)   │
                    ▼                             │
        ┌───────────────────────┐                │
        │    4 节点 Pipeline    │                │
        │  node1 → node2 →     │                │
        │  node3 → node4       │                │
        └───────┬──────┬───────┘                │
                │      │                         │
      ┌─────────┘      └──────────┐              │
      ▼                           ▼              │
  LLM 调用                     业务操作          │
  (trace callback)         (event/task/meeting)  │
      │                           │              │
      ▼                           ▼              │
  LLMInteractionLogger    BusinessEventLogger     │
  (callback 自动触发)      (Application 层调用)    │
      │                           │              │
      └───────────┬───────────────┘              │
                  ▼                              │
          EvolutionLogWriter                     │
          (非阻断·截断·异步)                      │
                  │                              │
                  ▼                              │
           PostgreSQL                           │
                                                │
        ┌───────────────────────┐               │
        │ finally:              │               │
        │  clear_context()      │◄──────────────┘
        └───────────────────────┘

  ──────────── 不经过 PipelineBUS 的日志 ────────────

  Session 生命周期 ──→ SessionLifecycleLogger ──→ EvolutionLogWriter
  RAG 检索       ──→ RAGRetrievalLogger     ──→ EvolutionLogWriter
  调度器作业     ──→ SchedulerJobLogger      ──→ EvolutionLogWriter.write_sync
  Hook 执行      ──→ AuditHook 直接写 DB（不走 EvolutionLogWriter）
  反馈信号       ──→ FeedbackSignalDetector  ──→ EvolutionLogWriter
```

## 4. 核心机制：pipeline_run_id 上下文注入

`pipeline_run_id` 是日志系统的"脊椎"，让 8 张表中 6 张的数据可按请求关联。

### 4.1 注入流程

```
PipelineBUS.run(context)
  │
  ├─ LLMInteractionLogger.set_context(
  │      pipeline_run_id=context.pipeline_run_id,
  │      conversation_id=context.message.conversation_id,
  │      user_id=context.user_id)
  │
  ├─ BusinessEventLogger.set_context(
  │      pipeline_run_id=context.pipeline_run_id,
  │      conversation_id=context.message.conversation_id)
  │
  ├─ try:
  │     └─ 4 节点执行循环
  │         ├─ LLM 调用 → trace callback → 从 _current_context 读取 → 写入 LLM 日志
  │         └─ 业务操作 → _log_business_event → 从 _current_context 捕获 → 写入事件日志
  │
  └─ finally:
        ├─ LLMInteractionLogger.clear_context()
        └─ BusinessEventLogger.clear_context()
```

### 4.2 两种上下文传递模式

| 模式 | 适用 Logger | 原理 | 时序要求 |
|------|-----------|------|---------|
| **类变量 `_current_context`** | LLMInteractionLogger, BusinessEventLogger | PipelineBUS 设置 → Logger 读取 | 必须在 Pipeline 执行期间读取 |
| **BusContext 直接传参** | PipelineExecutionLogger | `log(context, ...)` 直接读 `context.pipeline_run_id` | 无（同步调用） |

### 4.3 关键时序陷阱：ensure_future 竞态

**问题**：Application 层使用 `asyncio.ensure_future()` 调度日志写入，协程体在 `clear_context()` 之后才执行，此时 `_current_context` 已清空。

**解决**：`_log_business_event` 必须是**同步函数**，在调用时（上下文仍在）立即读取 `_current_context` 并固化到 kwargs，再调度异步写入：

```python
# ✅ 正确：同步函数 + 立即捕获上下文
def _log_business_event(**kwargs) -> None:
    from ..infrastructure.logging.business_event_logger import BusinessEventLogger
    ctx = BusinessEventLogger._current_context          # 立即读取
    kwargs.setdefault("pipeline_run_id", ctx.get("pipeline_run_id", ""))
    kwargs.setdefault("conversation_id", ctx.get("conversation_id", ""))
    asyncio.ensure_future(BusinessEventLogger.log(**kwargs))  # 异步写入

# ❌ 错误：async 函数 + ensure_future → 上下文在执行时已清空
async def _log_business_event(**kwargs) -> None:
    await BusinessEventLogger.log(**kwargs)  # 执行时 clear_context() 已调用
asyncio.ensure_future(_log_business_event(...))
```

## 5. EvolutionLogWriter：统一写入工具

**文件**：`emily-core/emily_core/infrastructure/logging/log_writer.py`

所有 Logger 的最终写入入口（AuditHook 除外，它直接操作 DB session）。

### 5.1 三原则

| 原则 | 实现 | 说明 |
|------|------|------|
| **非阻断** | 整体 try/except，异常只 `logger.warning` | 日志写入失败不影响业务主流程 |
| **截断** | `_truncate()`: Text ≤ 5000, String ≤ 500 | 防止超大 payload |
| **异步** | `async write()` → `asyncio.to_thread(_sync_write)` | 同步 DB 写入在线程中执行，不阻塞事件循环 |

### 5.2 两个入口

```python
# 异步入口（绝大多数场景使用）
await EvolutionLogWriter.write(PipelineExecutionLog, pipeline_run_id="abc", ...)

# 同步入口（Hook 内 / 调度器同步上下文）
EvolutionLogWriter.write_sync(HookExecutionLog, hook_name="auth_check", ...)
```

### 5.3 截断规则

| 字段特征 | 上限 | 示例 |
|---------|------|------|
| 后缀 `_json` / `_summary` / `_detail` / `_text` | 5000 字 | `tool_calls_json`, `results_summary`, `detail_json` |
| 特定长字段名 | 5000 字 | `params_json`, `context_summary`, `error_detail` |
| 其他 String 字段 | 500 字 | `summary`, `error_summary`, `abort_reason` |

### 5.4 自动填充

`write()` / `write_sync()` 会自动填充 `created_at`（UTC ISO8601），调用方无需手动传入。

## 6. 各 Logger 接口速查

### 6.1 PipelineExecutionLogger

**文件**：`infrastructure/logging/pipeline_logger.py`

```python
await PipelineExecutionLogger.log(context, started_at, node_timings)
```

| 参数 | 类型 | 说明 |
|------|------|------|
| `context` | BusContext | 含 WorkItem + 用户 + 意图 + Hook 决策 |
| `started_at` | str | Pipeline 执行开始时间 ISO8601 |
| `node_timings` | dict | `{"wi_node1": ms, "wi_node2": ms, ...}` |

**写入表**：`pipeline_execution_logs`

**调用方**：`PipelineBUS._log_execution()`（Pipeline 完成时自动调用，**无需手动调用**）

**特例**：接收完整 BusContext，从 WorkItem / intent / context 中采集所有字段，不需要 pipeline_run_id 注入。

---

### 6.2 LLMInteractionLogger

**文件**：`infrastructure/logging/llm_logger.py`

```python
# 初始化时注册（__init__.py 已自动完成）
llm_client.set_trace_callback(LLMInteractionLogger.make_callback())

# Pipeline 执行前注入上下文（PipelineBUS.run() 已自动完成）
LLMInteractionLogger.set_context(pipeline_run_id, conversation_id, user_id)
LLMInteractionLogger.clear_context()
```

**写入表**：`evolution_llm_interaction_logs`

**触发方式**：LLM 调用结束时，`LLMClient._trace_callback` 自动触发，**无需手动调用 `log()`**。

**call_category 推断逻辑**：

| call_type 包含 | 推断 category |
|----------------|--------------|
| `intent` 或 `json` | `intent` |
| `plan` | `planning` |
| 其他 | `execution` |

如 `set_context()` 时指定了 `call_category`，则优先使用显式值。

**文件**：`infrastructure/logging/business_event_logger.py`

## 7. Hook 执行日志（特殊路径）

**文件**：`emily-core/emily_core/workitem/pipeline/hook.py` — `AuditHook.execute()`

Hook 日志**不走 `EvolutionLogWriter`**，而是 `AuditHook` 在 `after` 阶段直接创建 `HookExecutionLog` ORM 对象并通过 `get_session()` 写入。

**写入表**：`hook_execution_logs`

**增强字段**（日志系统收束时新增）：

| 字段 | 来源 | 说明 |
|------|------|------|
| `user_id` | `context.user_id` | 操作用户 |
| `sop_id` | `context.intent.sop_id` | 关联 SOP |
| `block_reason` | `context.abort_reason` | BLOCK 原因 |
| `session_level` | `context.get_session_context().level` | 用户权限层级 |

**pipeline_run_id**：直接从 `context.pipeline_run_id` 获取（AuditHook 在 Pipeline 内执行，BusContext 始终可用）。

## 8. 新增 Logger 的检查清单

当需要新增一种日志采集时，按以下步骤操作：

### Step 1：定义 ORM 模型

在 `infrastructure/database/models.py` 中新增模型类，确保包含：

- [ ] `id = Column(String, primary_key=True, default=_new_uuid)`
- [ ] `pipeline_run_id = Column(String, index=True)` — 如果属于 Pipeline 请求链路
- [ ] `user_id = Column(String, default="")` — 如果有用户上下文
- [ ] `created_at = Column(String, default=_utc_now)` — 统一时间格式
- [ ] 适当的 `Index` 定义

### Step 2：创建 Logger 类

在 `infrastructure/logging/` 下新建文件，参考已有 Logger 的模式：

```python
class MyNewLogger:
    """XXX 日志采集器。"""

    @staticmethod
    async def log(*, key_field: str, pipeline_run_id: str = "") -> None:
        from .log_writer import EvolutionLogWriter
        from ...infrastructure.database.models import MyNewLog

        await EvolutionLogWriter.write(
            MyNewLog,
            key_field=key_field,
            pipeline_run_id=pipeline_run_id,
        )
```

### Step 3：如果需要 pipeline_run_id 上下文注入

1. 在 Logger 类中添加 `_current_context: dict[str, str] = {}` + `set_context()` / `clear_context()`
2. 在 `PipelineBUS.run()` 中添加对应的 `set_context()` / `clear_context()` 调用
3. 在 `log()` 方法中添加自动填充逻辑：
   ```python
   ctx = cls._current_context
   if not pipeline_run_id:
       pipeline_run_id = ctx.get("pipeline_run_id", "")
   ```

### Step 4：在业务代码中调用

- 如果在 Application 层且使用 `asyncio.ensure_future`，必须使用**同步包装函数**提前捕获上下文（见 §4.3）
- 如果直接 `await`，可在 `log()` 内部自动填充

### Step 5：验证

```sql
-- 检查 pipeline_run_id 是否正确填充
SELECT pipeline_run_id, * FROM my_new_logs ORDER BY created_at DESC LIMIT 3;

-- 端到端关联验证
SELECT pel.pipeline_run_id, mnl.*
FROM pipeline_execution_logs pel
LEFT JOIN my_new_logs mnl ON mnl.pipeline_run_id = pel.pipeline_run_id
ORDER BY pel.created_at DESC LIMIT 5;
```

## 9. 关联查询速查

### 9.1 用户完整交互链路

```sql
SELECT
  pel.matched_sop_id, pel.final_status, pel.elapsed_ms,
  lil.call_category, lil.total_tokens, lil.latency_ms AS llm_latency,
  bel.event_category, bel.event_action, bel.summary
FROM pipeline_execution_logs pel
LEFT JOIN evolution_llm_interaction_logs lil ON lil.pipeline_run_id = pel.pipeline_run_id
LEFT JOIN business_event_logs bel ON bel.pipeline_run_id = pel.pipeline_run_id
WHERE pel.user_id = 'user-dev1'
  AND pel.created_at >= '2026-07-10T00:00:00Z'
ORDER BY pel.created_at DESC;
```

### 9.2 LLM 成本追踪

```sql
SELECT
  call_category,
  COUNT(*) AS call_count,
  SUM(total_tokens) AS total_tokens,
  SUM(latency_ms) AS total_latency_ms,
  AVG(latency_ms) AS avg_latency_ms
FROM evolution_llm_interaction_logs
WHERE created_at >= '2026-07-10T00:00:00Z'
GROUP BY call_category
ORDER BY total_tokens DESC;
```

### 9.3 Hook 阻断分析

```sql
SELECT
  hook_name, decision, COUNT(*) AS cnt,
  array_agg(DISTINCT block_reason) AS reasons
FROM hook_execution_logs
WHERE created_at >= '2026-07-10T00:00:00Z'
GROUP BY hook_name, decision
ORDER BY cnt DESC;
```

### 9.4 业务事件审计

```sql
SELECT
  event_category, event_action,
  COUNT(*) AS cnt,
  array_agg(DISTINCT summary) AS examples
FROM business_event_logs
WHERE created_at >= '2026-07-10T00:00:00Z'
GROUP BY event_category, event_action
ORDER BY cnt DESC;
```

## 11. 已知局限与后续方向

| 局限 | 影响 | 后续方向 |
|------|------|---------|
| `RAGRetrievalLogger` 需显式传 `pipeline_run_id` | 调用方可能遗漏 | 接入 `_current_context` 自动填充 |
| `FeedbackSignalDetector.log_signals()` 传空 `pipeline_run_id` | 反馈信号无法关联到请求 | 在 SessionAgent 调用处补充上下文 |
| `_current_context` 是类变量，非线程安全 | 多线程场景可能覆盖 | 如需多线程，改用 `contextvars` |
| `AuditHook` 直接写 DB，不走 `EvolutionLogWriter` | 统一截断/日志风格不一致 | 可考虑统一走 `EvolutionLogWriter` |
| `repeat_request` 信号检测未实现 | 缺少重复请求检测 | 需 SessionAgent 历史上下文支持 |
| Session 确认路径绕过 PipelineBUS | 确认操作的 BusinessEventLog 无 `pipeline_run_id` | 可接受（确认不是独立 Pipeline 请求） |
