## 四、需求二：项目记忆模块 — 审查

### 4.1 优点
- **公共/私有分离正确**：边界清晰。
- **准确识别"私有记忆已部分实现，需合并"**：与代码现状吻合（`UserMemoryService` 存在但未接入）。
- **零散信息仓库定位准确**：正式信息走 DB+状态机，非正式信息走记忆——分工合理，例子（项目入口路线）贴切。
- **定时整理用计划任务、RAG 分阶段（先手动后自动）**：务实，且计划任务基础设施已就绪。

### 4.2 与现有代码的关系
- `UserMemoryService`（`services/user_memory_service.py`）：按用户 MD 文件 `{memory_dir}/{用户名}-长期记忆.md`，有 `save_memory`/`load_memory`/`load_memory_context`，自动截断 50 条。**这就是私有记忆的现成实现**，但挂在休眠的 `MasterAgent` 上，Session 主线未用。
- `write_user_memory` 工具（`tools/memory_tool.py`）：仅在 `MasterAgent` 路径注册，未进 Session 路径的 `BusinessFlowToolRegistry`。
- `SessionContext.user_preferences`/`history_summary`（[session_context.py:75-77](emily-core/emily_core/session/session_context.py#L75-L77)）：骨架字段，`SessionFactory._build_context`（[session_factory.py:77-114](emily-core/emily_core/adapters/session/session_factory.py#L77-L114)）不填充。
- `MaxKBRagProvider`/`LocalFileRagProvider` + `knowledge_search` 工具：RAG 查询链路已就绪。
- `PlanTaskScheduler`：定时触发能力已就绪。

### 4.3 问题与风险

1. **【高优先】"合并"的具体动作未列出**。需求说"现已一定程度实现，需要合并"，但合并即：①把 `UserMemoryService` 接入 `SessionFactory._build_context`（灌注 `user_preferences`/`history_summary`）；②把 `write_user_memory` 注册进 Session 路径工具表；③`emily-data/user_memory/` 启用。这是可立即推进的独立工作，不依赖权限系统。

2. **【高风险】对话摘要器不存在**。需求要"历史对话摘要，每次对话后由 session-agent 更新"。现有只有滑动窗口（`ConversationContext`），无摘要服务。需新建：session 进入 `ARCHIVING` 态时（`session_state.py` 已有该状态）触发 LLM 摘要并写回用户记忆文件。这是真正的新工作。见决策点 5。

3. **【高风险】"定时整理通过计划任务，系统自主发起 session 安排 session-agent"——执行模型与 `plan_task` 不匹配**。`plan_task` 是**人任务**系统（生产者-消费者，执行人提交成果）。记忆整理是**自主智能体任务**（系统自起 session，agent 自主完成）。`plan_task` 调度器可作**触发器**，但执行路径不同。见决策点 6。

4. **【中风险】公共记忆并发写入**。多个 session-agent 同时写公共记忆 MD 文件会冲突。`UserMemoryService` 按用户写无竞争，但公共记忆是共享写。见决策点 7。

5. **【中风险】三级分类（公开/私有/保密）与权限系统 `info_level`（public/internal/confidential）重复**。`PermissionSnapshot.info_level` 已有同概念（[session_context.py:53](emily-core/emily_core/session/session_context.py#L53)）。应复用，避免两套分类。见决策点 8。

6. **【中风险】"按权限查 RAG"未实现**。`knowledge_search` 工具做纯向量检索，不按 `info_level` 过滤。公共记忆含保密级时，需权限感知的 RAG 检索。

7. **【低风险】"通知管理员手动补充 RAG"可自动化**。`MaxKBRagProvider` 已用 MaxKB admin API（`hit_test`）。该 API 通常支持文档上传，后期可自动入库。手动作为 Phase 1 可接受。

8. **【低风险】"灌注如 session 的状态机"措辞**：应为"灌注入 SessionContext"。机制已存在（`SessionFactory`），只需填充字段。

### 4.4 关键决策点（方案对比）

#### 决策点 5：对话摘要生成
- **A. 会话归档时 LLM 摘要**：session 进入 `ARCHIVING` 时，一次 LLM 调用生成本次会话摘要，追加到用户记忆 MD。低频、低成本。
- **B. 逐轮增量摘要**：每 N 轮压缩一次。实时但 LLM 调用多。
- **C. 仅滑动窗口，不摘要**：最简，但无"远期记忆"，违背需求。
- **推荐 A**：与 `SessionState.ARCHIVING` 天然契合，低频低成本，满足"远期记忆参考"。

#### 决策点 6：定时整理的执行模型
- **A. `plan_task` 调度器触发 + 自主 SessionAgent 运行**：调度器到点起一个"系统 session"，`SessionAgent` 自主执行整理任务（非人提交）。需新增"系统自主任务"类型，与 `plan_task` 的人任务区分。
- **B. 独立系统调度器**：与 `plan_task` 平行新建一个轻量定时器，直接调记忆整理服务。不复用 `plan_task`。
- **C. `plan_task` 实例 + 系统作执行人**：把系统用户设为 executor，复用 `plan_task` 全流程。但 `plan_task` 流程（提交→确认→归档）对自主任务太重。
- **推荐 A**：复用 `PlanTaskScheduler` 的定时与分布式锁能力，但执行走 SessionAgent 自主路径；在调度器加"自主任务"分支。避免重造调度器，也避免把自主任务塞进人任务流程。

#### 决策点 7：公共记忆存储与并发
- **A. 纯 MD 文件 + 文件锁**：符合需求表述，但并发写需文件锁，脆弱。
- **B. DB 表存储**：新增 `project_memory` 表（主题/条目/级别/来源/时间），无并发问题，可审计。失去 MD 的可读性。
- **C. MD 文件 + 追加日志 + 每日合并**：session-agent 追加到按日日志，定时整理任务合并入主题 MD。并发安全（追加）+ 最终 MD 可读。
- **推荐 C**：兼顾需求想要的 MD 形态与并发安全；定时整理任务（决策点 6）天然负责合并。B 作为可选的索引层（DB 索引 → MD 全文）。

#### 决策点 8：三级分类对齐
- **A. 复用 `PermissionSnapshot.info_level`（public/internal/confidential）**：与权限系统统一，RAG 检索可直接按 `info_level` 过滤。
- **B. 记忆模块独立分类（公开/私有/保密）**：语义略不同（"私有"=用户私有 vs "保密"=保密级），但与权限系统术语不一致。
- **推荐 A**：统一用 `info_level`；"用户私有记忆"由"按用户归属"表达（`user_id` 字段），不与信息级别混淆。这样 RAG 权限过滤（4.3-6）也一并解决。

## 五、跨需求问题

1. **两份需求都不引用已有设计**：状态机不引 §12，记忆模块不引 `UserMemoryService`/`info_level`。合并/对齐是本次审查的最大动作。
2. **依赖序列**：auth（Phase III）→ 状态机（Phase IV）→ 记忆的权限感知部分（公共记忆三级、权限 RAG）。但**私有记忆合并（4.3-1）与对话摘要（4.3-2）不依赖权限，可立即推进**。
3. **Session 主线对齐**：所有记忆工作必须落在 Session 主线（`SessionFactory`/`SessionAgent`/`BusinessFlowToolRegistry`），不要碰休眠的 `MasterAgent`。
4. **术语统一**："状态机"在代码中已用于 workitem/plan_task/project 三处，建议项目级状态机统一称 `ProjectState`，避免与 `WorkItemState`/`PlanTaskInstance.status` 混淆。
5. **复用清单**（避免重造）：Repository 模式、`ALLOWED_TRANSITIONS` 状态机、JSON 快照审计日志、`UserMemoryService` MD 存储模式、Pipeline hooks、`PlanTaskScheduler`、RAG providers、`SessionFactory._build_context` 灌注、`PermissionSnapshot`。

## 七、推荐推进序列（轻量）

1. **立即可做（无权限依赖）**：
   - 私有记忆合并：`UserMemoryService` 接入 `SessionFactory`、注册 `write_user_memory` 工具到 Session 路径、填充 `SessionContext` 记忆字段。
   - 对话摘要器：`SessionState.ARCHIVING` 触发 LLM 摘要写回用户记忆。
2. **接口冻结（权限并行）**：与权限系统商定 `ProjectState` 权限接口（复用 §12 `project_state_permissions`），即便引擎未实现也先定接口。
3. **状态机落地（Phase IV，依赖 auth）**：按 §12 表结构建表，阶段目录用决策点 4-C 导入；触发用决策点 2-A；并发用决策点 3。
4. **公共记忆 + 权限 RAG（依赖 auth + 状态机）**：按决策点 7-C 建公共记忆，三级分类用决策点 8-A；定时整理用决策点 6-A；`knowledge_search` 增 `info_level` 过滤。
5. **RAG 自动化（后期）**：MaxKB admin API 自动入库替代手动。
