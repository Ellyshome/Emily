# 全景节点与计划任务模块拆分改造 — 需求文档

> **版本**：v2.0（吸纳审核 V1 意见修订）
> **日期**：2026-07-09
> **状态**：草案

---

## 1. 背景

当前 Emily 存在两个模块功能定位模糊：

- **计划任务模块（PlanTask）**：处理业务任务指派、成果提交确认、循环调度、提醒升级
- **全景节点模块（Node）**：处理项目 WBS 分解、依赖解锁、成果进度度量

两者在「业务任务追踪」维度上高度重叠，且通过合规链（`_validate_compliance_chain`）勉强桥接，导致：

1. 业务进度有两个数据源（`NodeDeliverable` 和 `PlanTaskDeliverable`），彼此不自动同步
2. 合规链逻辑复杂且脆弱（`VIRTUAL-NODE` 等补丁）
3. 用户认知混乱：同一个工作，是创建「任务」还是创建「节点」？

**改造方向**：

- **业务类任务** → 归入全景节点，用叶子节点细化到个人，复用 Node 的全部能力
- **系统类任务** → PlanTask 转型为系统调度器（晨报、巡检、自检等），成为系统工具而非业务工具

---

## 2. 改造原则

1. **业务任务 = 叶子节点**：一个 TASK 类型的节点就是当前 PlanTask 实例的等价物
2. **节点责任人必填**：所有节点（不论 MILESTONE / WORK_PACKAGE / TASK）必须有责任人，且 FK 关联 `users` 表中真实存在的用户
3. **责任人默认为创建者本人**：创建节点时若未指定责任人，自动设为 `creator_id`
4. **调度器不持有业务状态**：系统调度器只负责「在正确的时间触发正确的动作」
5. **调度器架构对齐 PipelineBUS**：采用 JobHandler 注册表 + 声明式配置 + Hook 拦截模式，方便模块化增加/移除计划工作
6. **向下兼容**：分阶段迁移，旧 PlanTask 数据在过渡期只读保留

## 3. Node 模块改造

### 3.1 ProjectNode 模型扩展

#### 3.1.1 新增字段

| 字段 | 类型 | 默认值 | 约束 | 说明 |
|------|------|--------|------|------|
| `responsible_user_id` | `VARCHAR(100)` | `''` | **NOT NULL, FK→users.id** | 责任人。创建时未指定则默认为 `creator_id` |
| `node_type` | `VARCHAR(20)` | `'WORK_PACKAGE'` | NOT NULL | 节点类型 |

**`responsible_user_id` 约束**：
- **必填**：所有节点（包括 MILESTONE、WORK_PACKAGE、TASK）的责任人字段均为必填项
- **外键约束**：必须关联 `users` 表中真实存在的用户记录，不允许空值或指向不存在的用户
- **默认逻辑**：创建节点时若未指定 `responsible_user_id`，系统自动填入 `creator_id`（创建者本人），且 `creator_id` 必须是 `users` 表中存在的用户
- **变更权限**：责任人变更需有权限校验（部门负责人或 L5+ 管理员可变更本部门节点的责任人）

**`node_type` 枚举**：

| 值 | 含义 | 典型示例 | 粒度 | 可否作为父节点 |
|---|---|---|---|---|
| `MILESTONE` | 里程碑 | 项目开工、竣工验收 | 阶段级 | ✅ 可以 |
| `WORK_PACKAGE` | 工作包（默认） | 基础施工、主体结构 | 条线级 | ✅ 可以 |
| `TASK` | 具体任务（叶子） | 提交验收报告、完成材料报验 | 个人级 | ❌ 不可——TASK 为叶子节点，不允许挂载子节点 |

**`node_type` 行为约束**：
- `TASK` 类型节点不允许作为父节点：`create_node()` 校验 `parent_node_id` 指向的节点类型，若父节点为 `TASK` 则拒绝创建
- `TASK` 类型节点自动设 `child_weight = "0.0000"`，不可变更

### 3.2 NodeDeliverable 增强：提交/确认工作流

当前 `NodeDeliverable` 只有量纲化进度（`target_amount` / `current_amount`），缺少人机交互的提交确认流程。

#### 3.2.1 新增字段

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `submission_status` | `VARCHAR(20)` | `'PENDING'` | 提交状态 |
| `submitted_by` | `VARCHAR(100)` | `''` | 提交人（FK→users.id） |
| `submitted_at` | `VARCHAR(50)` | `''` | 提交时间（ISO8601） |
| `confirmed_by` | `VARCHAR(100)` | `''` | 确认人（FK→users.id） |
| `confirmed_at` | `VARCHAR(50)` | `''` | 确认时间（ISO8601） |
| `return_reason` | `VARCHAR(500)` | `''` | 退回原因 |
| `attachment_file_id` | `VARCHAR(100)` | `''` | 提交附件（FK→files.id） |

#### 3.2.2 submission_status 状态机

```
PENDING ──(提交)──→ SUBMITTED ──(确认)──→ CONFIRMED
                        │
                        └──(退回)──→ RETURNED ──(重新提交)──→ SUBMITTED
```

**状态流转规则**：

| 当前状态 | 允许的目标状态 | 操作人 | 前置条件 |
|---|---|---|---|
| PENDING | SUBMITTED | 责任人或其同部门人员 | 节点状态为 IN_PROGRESS |
| SUBMITTED | CONFIRMED | 节点责任人上级或创建者 | 成果内容非空 |
| SUBMITTED | RETURNED | 同上 | 必须填写退回原因 |
| RETURNED | SUBMITTED | 责任人或其同部门人员 | 新提交内容非空 |
| CONFIRMED | _(终态)_ | — | 不可变更 |

#### 3.2.3 双重驱动模型

Node 的核心优势——量纲驱动——保留。新增确认驱动作为补充：

- **量纲驱动**（现有）：`current_amount / target_amount` → 自动计算进度百分比 → 触发节点状态流转
- **确认驱动**（新增）：`SUBMITTED → CONFIRMED` → 人工确认完成 → 也可触发节点状态流转

对于 TASK 类型节点，主要走确认驱动；对于 WORK_PACKAGE 类型节点，主要走量纲驱动。两者不冲突，且可同时生效。

**触发规则**：当成果的 `submission_status` 变为 `CONFIRMED` 时，自动将 `current_amount` 设为 `target_amount`（视同完成），进而触发进度重算和状态流转。

## 4. 系统调度器模块（替代 PlanTask）

### 4.1 重新定位

```
旧定位：业务任务管理（模板→实例→提交→确认→归档）
新定位：系统动作调度器（定时触发已注册的 JobHandler 动作）
```

**架构模式**：对齐 PipelineBUS，采用 **JobHandler 注册表 + 声明式配置 + Hook 拦截** 三层架构：

```
┌─────────────────────────────────────────────┐
│           SchedulerEngine（调度引擎）          │
│  · Advisory Lock 分布式调度                    │
│  · tick 循环 + 时间匹配                        │
│  · 执行生命周期管理                             │
├─────────────────────────────────────────────┤
│     JobHandlerRegistry（动作注册表）            │
│  · register(handler)  — 注册动作处理器          │
│  · get(action_type)   — 按类型查找             │
│  · list_all()         — 列出已注册动作          │
├─────────────────────────────────────────────┤
│     SchedulerHookRegistry（Hook 注册表）       │
│  · before:execute  — 执行前拦截（可阻断）       │
│  · after:execute   — 执行后处理（fire-and-forget）│
│  · on_error:execute — 执行异常处理             │
└─────────────────────────────────────────────┘
```

### 4.2 保留的核心能力

| 能力 | 当前用途 | 改造后用途 |
|---|---|---|
| Advisory Lock 分布式调度 | 防并发 | 保留（调度器核心） |
| tick 循环 + 时间匹配 | 调度 PlanTask 实例 | 调度 SchedulerJob 执行 |
| LLM 周期推算 | 推算业务截止时间 | 推算下次执行时间（CRON 模式的自然语言补充） |
| 自动归档 | 归档已完成业务任务 | 归档已执行系统动作日志 |

### 4.3 删除的业务能力

| 能力 | 原因 |
|---|---|
| 任务指派（initiator→executor） | 转入 Node 的 `responsible_user_id` |
| 成果提交/确认/退回 | 转入 Node 的 deliverable 工作流 |
| 合规链校验 | 不再需要 |
| 执行人升级（escalate_to_supervisor） | 转入 Node 或按权限模型处理 |
| 异常复核（ANOMALY_PENDING_REVIEW） | 系统动作无此概念 |
| 超时提醒/临期提醒（handle_overdue/handle_near_deadline） | 转为 `check_node_deadlines` handler（见 §4.5.3） |

### 4.4 JobHandler 注册表

#### 4.4.1 Handler 基类

```python
class SchedulerJobHandler(ABC):
    """调度动作处理器基类。

    每个 handler 对应一种可调度的动作类型。
    新增调度动作 = 写一个 Handler 子类 + 在 register_all 中注册，
    不改调度器核心代码。
    """

    @property
    @abstractmethod
    def action_type(self) -> str:
        """动作类型唯一标识，如 'generate_morning_report'。"""

    @property
    @abstractmethod
    def description(self) -> str:
        """一句话描述。"""

    @abstractmethod
    async def execute(self, params: dict) -> "JobResult":
        """执行调度动作。

        Args:
            params: 作业的 action_params（来自 SchedulerJob.action_params）

        Returns:
            JobResult(success, summary, data)
        """
```

#### 4.4.2 注册表

```python
class JobHandlerRegistry:
    """调度动作注册表。类似 BusinessFlowToolRegistry 的模式。"""

    def register(self, handler: SchedulerJobHandler) -> None:
        """注册一个动作处理器。"""

    def get(self, action_type: str) -> SchedulerJobHandler | None:
        """按 action_type 查找处理器。"""

    def list_all(self) -> list[dict]:
        """列出所有已注册动作（供 API/工具展示）。"""
```

#### 4.4.3 内置 Handler 列表

每个 Handler 独立文件，位于 `emily_core/scheduler/jobs/` 目录：

| 文件 | action_type | 说明 | 依赖注入 |
|---|---|---|---|
| `morning_report.py` | `generate_morning_report` | 生成晨报并推送 | `outbound_bus` |
| `session_cleanup.py` | `cleanup_expired_sessions` | 清理过期 Session | `session_pool` |
| `health_check.py` | `health_check` | 系统自检 | `llm_client`, `rag_provider` |
| `node_deadlines.py` | `check_node_deadlines` | 节点截止时间提醒 | `node_service`, `outbound_bus` |
| `periodic_node.py` | `create_periodic_node` | 定期创建叶子节点 | `node_service`（通过接口注入，非直接 import） |
| `data_sync.py` | `data_sync` | 数据同步 | `rag_provider` |
| `webhook.py` | `custom_webhook` | 调用外部 Webhook | `aiohttp` |

**依赖注入模式**：Handler 不直接 import Service 类，而是在注册时通过 `__init__` 接收依赖：

```python
class MorningReportHandler(SchedulerJobHandler):
    action_type = "generate_morning_report"
    description = "生成晨报并推送到指定群"

    def __init__(self, outbound_bus=None, llm_client=None):
        self._outbound_bus = outbound_bus
        self._llm = llm_client

    async def execute(self, params: dict) -> JobResult:
        push_group = params.get("push_to_group", "")
        # ... 组装晨报、推送 ...
        return JobResult(success=True, summary="晨报已推送")
```

### 4.5 Scheduler Hook 机制

#### 4.5.1 Hook 基类

```python
class SchedulerHook(ABC):
    """调度 Hook 基类。对齐 PipelineBUS Hook 三态语义。"""

    @property
    @abstractmethod
    def name(self) -> str: ...

    @property
    def priority(self) -> int:
        return 10

    @property
    def enabled(self) -> bool:
        return True

    @abstractmethod
    async def execute(self, context: "SchedulerContext") -> "HookResult":
        """执行 Hook 逻辑。

        Returns:
            HookResult(decision=ALLOW/WARN/BLOCK, message=...)
        """
```

#### 4.5.2 内置 Hook

| Hook | 挂载点 | 说明 |
|---|---|---|
| `ExecutionLogHook` | `after:execute` | 记录执行日志到 `scheduler_executions` |
| `FailureNotificationHook` | `on_error:execute` | 执行失败时通知管理员 |
| `RetryHook` | `on_error:execute` | 执行失败时自动重试（最多 N 次） |

#### 4.5.3 执行流程

```
SchedulerEngine.tick()
    ↓ 扫描 due 的 SchedulerJob
    ↓ for each job:
        ① fire before:execute hooks → BLOCK 则跳过此 job
        ② JobHandlerRegistry.get(action_type).execute(params)
        ③ fire after:execute hooks → 记录日志等
        ④ on error → fire on_error:execute hooks → 重试/通知
```

**与 PipelineBUS 的对照**：

| PipelineBUS | SchedulerEngine |
|---|---|
| 4 节点顺序执行 | 1 节点（execute）执行 |
| `before:{node}` hooks | `before:execute` hooks |
| `after:{node}` hooks | `after:execute` hooks |
| `on_error:{node}` hooks | `on_error:execute` hooks |
| HookDecision ALLOW/WARN/BLOCK | 同 |

#### 配置与代码的关联机制

`handler_module` 是配置与代码之间的显式桥梁，解决纯字符串隐式约定的脆弱性问题：

| 字段 | 作用 | 示例 |
|------|------|------|
| `action_type` | 语义标识（人可读，配置内唯一） | `"generate_morning_report"` |
| `handler_module` | 代码定位（Python 模块路径，自动 import） | `"scheduler.jobs.morning_report"` |

**启动时自动校验+注册**：

```python
# scheduler/engine.py 启动时
for job_conf in config["jobs"]:
    module_path = job_conf["handler_module"]
    action_type = job_conf["action_type"]

    # ① 自动 import Handler 模块
    module = importlib.import_module(f"emily_core.{module_path}")

    # ② 查找 action_type 匹配的 Handler 子类
    handler_cls = _find_handler_by_action_type(module, action_type)
    if handler_cls is None:
        raise StartupError(
            f"模块 {module_path} 中未找到 action_type='{action_type}' 的 Handler"
        )

    # ③ 注册到 JobHandlerRegistry
    registry.register(handler_cls(injected_dependencies...))
```

**启动校验保障**：
- `handler_module` 指向的模块不存在 → 启动报错
- 模块存在但 `action_type` 不匹配 → 启动报错
- 配置中 `action_type` 重复 → 启动报错
- 这三项校验确保配置与代码的一致性，避免运行时才发现关联断裂

**新增调度工作的流程**：
1. 编写 `SchedulerJobHandler` 子类（如 `scheduler/jobs/my_new_job.py`）
2. 在 `scheduler_config.json` 的 `jobs` 数组中添加条目（**含 `handler_module` 和 `action_type`**）
3. 重启容器时自动 import + 校验 + 注册

**移除**：从配置中删除条目或将 `enabled` 设为 `false`，无需改代码。

### 4.9 桥接场景：调度器触发业务动作

循环业务任务（如每周安全巡检）通过调度器触发 Node 创建：

```
SchedulerJob(action_type="create_periodic_node")
    ↓ 调度器 tick 匹配
    ↓ fire before:execute hooks
    ↓ PeriodicNodeHandler.execute(params)
        → 通过注入的 node_service 接口创建 TASK 叶子节点
        → responsible_user_id=指定人（必填且 FK 约束）
        → 节点进入 Node 正常生命周期
    ↓ fire after:execute hooks
```

调度器不持有业务状态，它只负责「在正确的时间触发正确的动作」。

**节点截止时间提醒**：

```
SchedulerJob(action_type="check_node_deadlines", interval_seconds=300)
    ↓ 每 5 分钟执行一次
    ↓ NodeDeadlineHandler.execute(params)
        → 调用 node_service.find_near_deadline(before_minutes=60)
        → 调用 node_service.find_overdue()
        → 通过 outbound_bus 推送提醒
    ↓ 不持久化提醒状态——无状态，每次查询当前数据
```

## 7. 迁移策略

### 阶段 1：Node 扩展（向下兼容，不破坏现有功能）

**数据库变更**：

1. `project_nodes` 加 `responsible_user_id`（**nullable，无FK**）+ `node_type`（默认 `WORK_PACKAGE`）
2. `node_deliverables` 加提交确认字段（默认 `PENDING`）

**数据回填**（三步迁移）：

*Step 1：回填 `responsible_user_id`*
```sql
-- 大部分情况：从 creator_id 回填
UPDATE project_nodes SET responsible_user_id = creator_id WHERE responsible_user_id IS NULL OR responsible_user_id = '';

-- 兜底：creator_id 无效时设为系统管理员 UUID
UPDATE project_nodes SET responsible_user_id = '{系统管理员UUID}'
WHERE responsible_user_id IS NULL
   OR responsible_user_id = ''
   OR responsible_user_id NOT IN (SELECT id FROM users);
```

*Step 2：回填 `submission_status`*（智能回填，非全默认 PENDING）
```sql
-- 节点已 COMPLETED → 成果 CONFIRMED
UPDATE node_deliverables d
SET submission_status = 'CONFIRMED',
    confirmed_at = (SELECT completed_at FROM project_nodes n WHERE n.node_id = d.node_id)
WHERE d.submission_status = 'PENDING'
  AND EXISTS (SELECT 1 FROM project_nodes n WHERE n.node_id = d.node_id AND n.status = 'COMPLETED');

-- 成果 current_amount >= target_amount → CONFIRMED
UPDATE node_deliverables
SET submission_status = 'CONFIRMED'
WHERE submission_status = 'PENDING'
  AND CAST(current_amount AS DECIMAL) >= CAST(target_amount AS DECIMAL);

-- 成果 current_amount > 0 且 < target → SUBMITTED
UPDATE node_deliverables
SET submission_status = 'SUBMITTED'
WHERE submission_status = 'PENDING'
  AND CAST(current_amount AS DECIMAL) > 0
  AND CAST(current_amount AS DECIMAL) < CAST(target_amount AS DECIMAL);

-- 其余保持 PENDING
```

*Step 3：加约束*
```sql
ALTER TABLE project_nodes ALTER COLUMN responsible_user_id SET NOT NULL;
ALTER TABLE project_nodes ADD CONSTRAINT fk_nodes_responsible_user FOREIGN KEY (responsible_user_id) REFERENCES users(id);
```

**代码变更**：
3. NodeService 加新方法
4. 新增工具注册（`create_task_node` 等），与旧 PlanTask 工具并存

### 阶段 2：业务流量切换

**切换条件**：`plan_task_instances` 表中 `WAITING` / `SUBMITTED` / `RETURNED` 状态记录数 = 0（所有活跃任务已迁移或归档）

1. SOP-009 指向新工具（`create_task_node` 替代 `record_plan_task`）
2. 新创建的业务任务走 Node 路径
3. 旧 PlanTask 工具降级为只读查询（仅 `query_plan_tasks` 保留）
4. 旧 PlanTask 数据只读保留

### 阶段 3：PlanTask 清理 + Scheduler 重写

1. 数据迁移脚本：将活跃的 `plan_task_instances` 转为 TASK 类型节点（`responsible_user_id` 从 `executor_id` 映射，需 FK 校验）
2. 删除旧 PlanTask 工具注册
3. 新建 `scheduler/` 模块（JobHandler 注册表 + Hook + 声明式配置）
4. 删除合规链相关代码 + `plan_task_match` hook
5. 删除 `plan_task_templates` / `plan_task_instances` / `plan_task_logs` / `plan_task_deliverables` 四张表

## 8. 风险评估

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 节点膨胀：业务任务全变叶子节点，节点数可能激增 | 中 | `node_type` 区分 + 分页查询 + 按责任人过滤 + `find_by_node_type()` 索引 |
| 现有节点 `responsible_user_id` 回填数据质量 | 中 | 三步迁移：先加列→回填（含兜底逻辑）→再加约束 |
| 现有 deliverable submission_status 回填 | 中 | 智能回填（按节点状态和成果进度），非全默认 PENDING |
| 循环业务任务（周报/月报）的调度 | 低 | 调度器通过 `create_periodic_node` handler 创建，Node 不感知调度 |
| 现有 PlanTask 数据迁移 | 中 | 阶段式迁移，量化切换条件 |
| 调度器 Handler 循环依赖 | 低 | Handler 通过 `__init__` 注入依赖，非直接 import Service |
| 退回/重新提交流程增加 Node 复杂度 | 低 | 逻辑集中在 deliverable 层，Node 状态机不变 |
| 前端适配工作量 | 中 | 「我的任务」API 简化前端对接，旧 API 兼容期过渡 |

## 9. 改造后架构总览

```

  │     ├── MorningReportHandler

  │     ├── HealthCheckHandler

  │     ├── DataSyncHandler
  │     └── WebhookHandler
  ├── SchedulerHookRegistry（before/after/on_error 拦截）
  │     ├── ExecutionLogHook
  │     ├── FailureNotificationHook
  │     └── RetryHook

  └── scheduler_config.json（声明式配置，新增/移除工作不改代码）
```
