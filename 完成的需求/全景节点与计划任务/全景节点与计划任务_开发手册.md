## 1. 模块概览

### 1.1 定位

全景节点与计划任务模块是 Emily 项目管理的核心，负责：

- **全景节点图**：以树形结构管理项目节点（里程碑 / 工作包 / 任务），追踪进度
- **任务成果管理**：节点下挂交付物，支持提交 → 确认 / 退回 → 重提交的完整审批流
- **计划任务调度**：基于 Tick 循环 + Advisory Lock 的轻量调度引擎，驱动定时作业

### 1.2 架构分层

```
api/routes/node.py          ← REST 端点（FastAPI Router）
        │
        ▼
services/node_service.py    ← 业务编排（权限校验、状态流转、事件记录）
        │
        ▼
repositories/node_repo.py   ← 数据访问（SQLAlchemy，每方法独立 session）
        │
        ▼
models.py                   ← ORM 模型（ProjectNode / NodeDeliverable / SchedulerJob / SchedulerExecution）
```

调度子模块：

```
scheduler/engine.py         ← SchedulerEngine：tick 循环 + Advisory Lock
scheduler/service.py        ← SchedulerService：作业 CRUD
scheduler/handler_registry.py ← JobHandlerRegistry：action_type → handler 映射
scheduler/jobs/*.py         ← 7 个内置 Handler 实现
```

### 1.3 关键设计决策

| 决策 | 说明 |
|------|------|
| **异步 Service + 同步 Repo** | Service 方法均为 `async def`，Repo 方法为 `@staticmethod` 同步方法；Service 通过 `await asyncio.to_thread(repo.method, ...)` 在线程池中执行 DB 操作 |
| **Command 模式** | Service 方法入参统一使用 `@dataclass` Command 对象，不直接接收零散参数 |
| **独立 session** | Repo 每个方法通过 `with get_session()` 获取独立 session，无跨请求污染 |
| **Advisory Lock** | SchedulerEngine 使用 PostgreSQL `pg_try_advisory_lock` 保证多实例互斥 |
| **auto_create_all** | 启动时 `Base.metadata.create_all()` 自动建表；**注意：若模型变更会重建全表导致数据清空** |

## 3. 状态机

### 3.1 节点状态

```
NOT_ACTIVATED ──审批通过──▶ CONDITIONS_NOT_MET ──条件满足──▶ IN_PROGRESS ──全部完成──▶ COMPLETED
       │                         ▲                                      │
       └──审批拒绝──▶ 废弃        └──────── 成果确认触发自动流转 ──────────┘
```

**流转规则**：
- 管理员（Level ≥ 5）创建的节点直接进入 `CONDITIONS_NOT_MET`，跳过 `NOT_ACTIVATED`
- 确认交付物时，若所有 `is_required=True` 的成果均已 `CONFIRMED`，节点自动 `IN_PROGRESS → COMPLETED`
- `TASK` 类型节点不能作为父节点（创建子节点时校验）

### 3.2 交付物提交状态

```
                    ┌──── 提交 ────▶ SUBMITTED ── 确认 ──▶ CONFIRMED
PENDING             │                    │
                    │                    ├── 退回 ──▶ RETURNED ── 重提交 ──▶ SUBMITTED
                    └── 提交 ────────────┘
```

**权限约束**：
- **提交**：仅节点责任人（`responsible_user_id`）或同部门人员（`owner_dept_id`）
- **确认 / 退回**：仅审批人（Level ≥ 5）

## 7. Scheduler 调度框架

### 7.1 架构

```
SchedulerEngine._loop()
    │ 每 tick_seconds 秒
    ├── pg_try_advisory_lock("scheduler_engine:global_tick")
    ├── SchedulerService.list_active_jobs()
    │       └── 扫描 scheduler_jobs WHERE status='ACTIVE'
    ├── 对每个到期作业: _execute_job(job)
    │       ├── SchedulerService.create_execution()  ← 创建执行记录
    │       ├── _fire_before_hooks()                 ← 可阻断执行
    │       ├── handler.execute(params)
    │       └── _fire_after_hooks()
    └── pg_advisory_unlock(...)
```

### 7.2 配置

```python
# 在 EmilyCore 初始化时设置
config.scheduler_enabled = True          # 是否启用
config.scheduler_tick_seconds = 60       # tick 间隔（秒）
```

| `session_cleanup` | `jobs/session_cleanup.py` | 会话清理 |

```python
    action_params='{"key": "value"}',

await scheduler_service.create_job(cmd)
# 然后将作业 status 改为 ACTIVE
```

## 8. 权限模型

### 8.1 用户等级

| Level | 角色 | 权限 |
|-------|------|------|
| 5-6 | 管理员 | 创建节点自动激活、变更责任人、确认/退回成果 |
| 3-4 | 普通用户 | 提交/重提交成果（仅自己的节点） |

### 8.2 权限校验规则

| 操作 | 规则 | 错误码 |
|------|------|------|
| 创建节点 | 仅建设单位人员 | `40301` |
| 激活节点 | 审批人 Level ≥ 5 且同部门 | `40302` |
| 变更责任人 | 操作人 Level ≥ 5 | `40302` |
| 提交成果 | 责任人或同部门 | `40303` |
| 确认/退回成果 | 确认人 Level ≥ 5 | 无（Service 层内部校验） |

```python
# 1. node_schemas.py — 定义 Request
class MyActionRequest(BaseModel):
    param1: str
    param2: str = ""

# 2. node_commands.py — 定义 Command
@dataclass
class MyActionCommand:
    param1: str
    param2: str = ""

# 3. node_service.py — 添加 Service 方法
async def my_action(self, cmd: MyActionCommand) -> NodeOperationResult:

async def my_action(node_id: str, body: MyActionRequest):
    svc = _get_service()
    cmd = MyActionCommand(param1=body.param1, param2=body.param2)
    result = await svc.my_action(cmd)
    if not result.success:
        raise HTTPException(status_code=400, detail=result.message)
    return ApiResponse(message=result.message)
```

## 10. 常见问题排查

### 10.1 容器启动后数据丢失

**原因**：SQLAlchemy `create_all()` 在模型变更时重建全表。

**解决**：
- 方案 A：数据持久化到 volume，启动后执行 seed 脚本
- 方案 B：使用 Alembic 迁移替代 `create_all()`

### 10.2 创建节点报 "责任人 XXX 不存在于用户表中"

**原因**：`PermissionRepository.get_user()` 查询条件 `is_deleted == False`，若该字段为 NULL 则不匹配。

**解决**：确保插入用户时设置 `is_deleted = false`。

### 10.3 `/my-tasks` 返回 404 "节点 my-tasks 不存在"

**原因**：FastAPI 路由匹配顺序，`/{node_id}` 先于 `/my-tasks` 匹配。

**解决**：确保 `/my-tasks` 路由在 `/{node_id}` 之前注册（当前代码已修复）。

### 10.4 `TypeError: object bool can't be used in 'await' expression`

**原因**：对同步方法使用了 `await`。

**检查**：`_check_submission_permission` 是 `def` 而非 `async def`，调用时不要加 `await`。

### 10.5 参数位置错位导致 SQL 类型错误

**原因**：Repo 方法参数较多时，调用方传参顺序与签名不一致。

**建议**：多参数方法使用 keyword arguments 显式传参：
```python
# 推荐
NodeDeliverableRepo.find_pending_by_responsible_user(
    responsible_user_id=user_id,
    node_status="IN_PROGRESS",
    limit=page_size,
    offset=offset,
)
```
