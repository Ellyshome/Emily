# 计划任务系统（Scheduled Task Module）代码编制计划

> 基于 [定时任务模块需求.md](定时任务模块需求.md) v2.0
> 编制日期：2026-06-25
> 版本：v2.1（含架构师审核意见修正）

---

## 一、Context

在建设工程项目管理中，存在两类信息上传模式：
1. **生产者-消费者模式**：管理者预先下达工作指标（"计划任务"），执行者在时效内上传成果，"收货销项"
2. **主动录入模式**：用户主动上报计划外工作（已有 SOP-002-REC 覆盖）

本模块实现第一类模式——计划任务系统的全部后端功能，包括：任务模板与实例管理、五态状态机流转、循环任务自动生成、超时提醒、审计日志、以及与现有 SOP 工作流系统的集成。

技术上下文：Emily 项目使用 Python 3.12 + SQLAlchemy + asyncio，遵循四层架构（Model → Repository → Service → Application → Tool Handler）。当前**不存在任何定时调度框架**（无 APScheduler、Celery 等），唯一的后台循环是 `SessionPoolManager._sweep_loop()`。

---

## 二、设计决策

### 2.1 调度引擎方案：asyncio 后台循环

**选择**：使用 `asyncio.create_task()` 启动后台调度循环（与现有 SessionPool sweeper 模式一致）。

**理由**：
- 零外部依赖，不引入 APScheduler/Celery
- 与现有架构完全一致
- 房地产项目场景下任务频率不会超过单进程压力上限（需求文档 §7.3 明确"暂不考虑高并发"）
- 调度间隔可配置（默认 60 秒），每次扫描：超时检测 + 循环任务下一轮生成 + 归档触发

**风险与应对**：
| 风险 | 应对措施 |
|------|---------|
| 进程重启时调度循环终止 | 调度循环在 EmilyCore 初始化时启动，每次扫描都基于数据库状态判定（不依赖内存），进程重启后自动恢复 |
| 多实例部署导致重复调度 | 使用 PostgreSQL Advisory Lock 实现分布式锁，确保同一时间只有一个进程在执行调度 |

### 2.2 提醒机制：通过 OutboundEventBus 推送 IM 消息

**选择**：提醒消息通过现有 `OutboundEventBus.publish("reply", data)` 发布，data 中携带 `user_id` + `content`，由 SSE/IM Adapter 层根据 `user_id` 路由到正确的用户会话。

**理由**：
- 复用现有消息投递基础设施
- 无需新增推送通道
- 离线用户的提醒消息由 Adapter 层处理（SSE 断连时消息丢弃，后续可扩展 `pending_notifications` 表实现离线补发）

**注意**：`OutboundEventBus` 是广播机制，不能定向投递。提醒消息通过 `publish()` 发布后，所有订阅的 SSE 连接都会收到，由各 Adapter 根据 `user_id` 自行判断是否投递到自己的会话。

### 2.3 状态机实现：纯数据状态机

**选择**：状态仅作为 `plan_task_instance.status` 字段存储，不包含行为逻辑。状态流转由 `PlanTaskService` 的方法驱动，每次流转写入 `plan_task_log` 审计记录。

**理由**：需求文档 §2.2 明确"状态机本质是仪表盘功能，不自主行动"。

### 2.4 循环任务实现：双触发机制（归档触发 + 主动补齐容错）

**选择**：采用双触发机制确保循环任务不丢失。

- **主触发（归档触发）**：上一轮任务归档后，调度机根据模板规则自动生成下一轮任务——对齐需求文档 §4.2 "一轮任务完成后自动生成下一轮"
- **容错触发（主动补齐）**：调度机每次 tick 时检查——如果上一轮已过期 N 天但未归档且未取消，用 LLM 判断是否应补齐当前周期。解决拖期提交导致后续周期任务丢失的问题
- **暂停/取消保护**：已 CANCELLED 或对应模板已 INACTIVE 的循环，不再生成新实例
- 使用 `template_id + period_key`（如 `tpl-001 + 2024-W25`）作为唯一幂等键，防止重复创建
- `deadline_rule` 存储为自然语言描述（非 Cron 表达式），由 LLM 推算具体截止时间
- **LLM 失败降级**：调用失败时不做自动推算，改为通知任务发起人人工处理（通过 `OutboundEventBus.publish("reply", data)` 投递，data 中携带 `user_id` 供 Adapter 层路由）

**理由**：需求文档 §4.2 明确"循环本质还是通过单次任务计划实现，由调度机根据需求描述记录，注销上次循环的时候，开启下次循环"。

### 2.5 计划外事件匹配机制

**选择**：用户上传成果时，先尝试匹配同项目、同阶段、同执行人、时间窗口内的挂起任务；匹配失败则自动创建"计划外"任务实例并标记 `is_unscheduled=True`。

**集成方式**：作为 Pipeline Hook（`before:execute` 钩子），对 `record_event` 和 `record_task` 工具执行前做匹配检查。匹配成功则关联到已有计划任务（自动 fill `plan_task_instance_id`），匹配失败则交由 SOP 正常流程处理（标记计划外）。

**匹配策略**（分层匹配）：
1. **精确匹配**：同一项目 + 同一阶段 + 同一执行人 + 时间窗口（±7天）
2. **模糊匹配**：LLM 判定上传内容与任务描述的相似度（可选增强）
3. **无匹配**：创建计划外实例或标记为计划外事件

**理由**：需求文档 §1.3 / §2.1 明确"一般工作流若无对应计划，则标记为计划外事件"。

### 2.6 归档策略：原地保留 + 强制不可变

**选择**：归档后依然在 `plan_task_instances` 表中，状态变为 `ARCHIVED`（终态）。不设独立归档表。

**强制约束**：Repository 层所有 update 操作前检查，归档后的数据不可修改。

**理由**：简单可靠，审计查询方便。

### 2.7 监控大盘：后端 SQL 视图 + 统计 API

**选择**：本阶段只交付后端——创建 PostgreSQL 视图 + 统计查询 API，供 Grafana 或前端后期消费。不实现 Web 页面。

## 三、数据库设计（v2.1 已补充缺失字段）

### 3.1 plan_task_template（任务模板表）

```python
class PlanTaskTemplate(Base):
    __tablename__ = "plan_task_templates"

    id = Column(String, primary_key=True, default=_new_uuid)
    template_no = Column(String(50), unique=True, nullable=False)   # 模板编号 TPL-YYYYMMDD-NNNN
    name = Column(String(200), nullable=False)                      # 模板名称
    description = Column(String, default="")                        # 模板描述

    # ── 任务定义 ──
    initiator_id = Column(String, ForeignKey("users.id"), nullable=False)  # 发起人
    executor_id = Column(String, ForeignKey("users.id"), nullable=True)    # 执行人（可为空=待指派）
    project_id = Column(String, ForeignKey("projects.id"), nullable=True)  # 关联项目

    # ── 调度规则 ──
    task_type = Column(String(20), nullable=False, default="ONCE")  # ONCE / WEEKLY / MONTHLY
    deadline_rule = Column(String(500), default="")                 # 自然语言截止描述，如"每周五17:00"、"每月20日"
    # 循环任务每次生成新实例时，由 LLM 解析 deadline_rule 推算具体的 deadline_at

    # ── 验收标准 ──
    verification_standard = Column(String, default="{}")            # JSON 核验规则

    # ── 工作流关联 ──
    workflow_definition_key = Column(String(100), default="")       # 关联工作流定义键

    # ── 状态与审计 ──
    status = Column(String(20), default="DRAFT")                    # DRAFT / ACTIVE / INACTIVE
    creator_id = Column(String, ForeignKey("users.id"), nullable=True)
    created_at = Column(String, default=_utc_now)
    updated_at = Column(String, default=_utc_now, onupdate=_utc_now)
    is_deleted = Column(Boolean, default=False)
```

### 3.2 plan_task_instance（任务实例表）

```python
class PlanTaskInstance(Base):
    __tablename__ = "plan_task_instances"

    id = Column(String, primary_key=True, default=_new_uuid)
    instance_no = Column(String(50), unique=True, nullable=False)   # 实例编号 PTI-YYYYMMDD-NNNN
    template_id = Column(String, ForeignKey("plan_task_templates.id"), nullable=True)

    # ── 幂等键 ──
    period_key = Column(String(100), default="")                    # "2024-W25", "2024-M06", "2024-07-15"
    # 唯一约束：(template_id, period_key) WHERE status != 'CANCELLED'

    # ── 任务核心字段 ──
    title = Column(String(500), nullable=False)
    description = Column(String, default="")
    initiator_id = Column(String, ForeignKey("users.id"), nullable=False)   # 发起人
    executor_id = Column(String, ForeignKey("users.id"), nullable=True)     # 执行人
    project_id = Column(String, ForeignKey("projects.id"), nullable=True)
    phase_code = Column(String(100), nullable=True)                         # 关联项目阶段编码

    # ── 时间字段 ──
    deadline_at = Column(String, nullable=True)           # 截止时间（ISO8601）
    reminded_at = Column(String, nullable=True)           # 最后提醒时间
    escalated_at = Column(String, nullable=True)          # 升级给上级的时间（v2.1 新增，P2）

    # ── 执行人升级（v2.1 新增，P2） ──
    original_executor_id = Column(String, ForeignKey("users.id"), nullable=True)  # 原执行人
    escalation_reason = Column(String, default="")       # 升级原因（离职/失能等）

    # ── 验收标准 ──
    verification_standard = Column(String, default="{}")  # JSON 核验规则

    # ── 状态机（含 ANOMALY_PENDING_REVIEW 状态，v2.1 新增，P2） ──
    # WAITING / SUBMITTED / RETURNED / CONFIRMED / ARCHIVED / CANCELLED / ANOMALY_PENDING_REVIEW
    status = Column(String(20), default="WAITING")

    # ── 时间戳 ──
    submitted_at = Column(String, nullable=True)          # 提交时间
    confirmed_at = Column(String, nullable=True)          # 确认时间
    archived_at = Column(String, nullable=True)           # 归档时间

    # ── 工作流关联 ──
    workflow_instance_id = Column(String, nullable=True)  # 关联工作流实例ID

    # ── 异常标记 ──
    is_unscheduled = Column(Boolean, default=False)       # 是否计划外事件
    anomaly_reason = Column(String, default="")           # 异常原因

    # ── LLM 推算失败标记（v2.1 新增） ──
    llm_calculation_failed = Column(Boolean, default=False)  # LLM 推算截止时间是否失败
    llm_failure_notified = Column(Boolean, default=False)    # 是否已通知发起人人工处理

    # ── 审计 ──
    created_at = Column(String, default=_utc_now)
    updated_at = Column(String, default=_utc_now, onupdate=_utc_now)
    is_deleted = Column(Boolean, default=False)
```

### 4.3 Service 层

#### `PlanTaskService` (`services/plan_task_service.py`)

核心业务逻辑方法：

| 方法 | 说明 | 触发的状态流转 | 优先级 |
|------|------|---------------|--------|
| `create_template(cmd) → PlanTaskTemplate` | 创建任务模板 | — | P0 |
| `activate_template(id) → PlanTaskTemplate` | 激活模板（DRAFT→ACTIVE） | — | P0 |
| `create_instance(cmd) → PlanTaskInstance` | 创建任务实例，鉴权检查，幂等检查 | → WAITING / **ANOMALY_PENDING_REVIEW** | P0 |
| `submit_deliverable(cmd) → PlanTaskInstance` | 提交成果 | WAITING → SUBMITTED | P0 |
| `confirm_task(cmd) → PlanTaskInstance` | 发起人确认成果 | SUBMITTED → CONFIRMED | P0 |
| `return_task(cmd) → PlanTaskInstance` | 发起人退回成果 | SUBMITTED → RETURNED | P0 |
| `resubmit_deliverable(cmd) → PlanTaskInstance` | 执行者修改后重新提交 | RETURNED → SUBMITTED | P0 |
| `archive_task(instance_id) → PlanTaskInstance` | 归档已确认任务 | CONFIRMED → ARCHIVED | P0 |
| `cancel_instance(instance_id, reason) → PlanTaskInstance` | 取消任务 | * → CANCELLED | P0 |
| `mark_unscheduled(instance_id, reason) → PlanTaskInstance` | 标记为计划外事件 | 不流转状态，设 is_unscheduled | P0 |
| `match_or_create_unscheduled(user_id, context, deliverable) → PlanTaskInstance` | 上传时匹配已有任务，失败则创建计划外实例（v2.1 新增） | → WAITING / SUBMITTED | P1 |
| `review_anomaly_task(cmd) → PlanTaskInstance` | 上级复核反向下达的异常任务（v2.1 新增，P2） | ANOMALY_PENDING_REVIEW → WAITING / CANCELLED | P2 |
| `escalate_to_supervisor(cmd) → PlanTaskInstance` | 执行人离职/失能，升级给顺位上级（v2.1 新增，P2） | 不流转状态，变更 executor_id | P2 |

每个状态变更方法内部：
1. 校验当前状态是否允许目标流转
2. 执行 `update_status()` 写入新状态（内部含归档不可变检查）
3. 创建 `PlanTaskLog` 记录（含 snapshot 快照）
4. 返回更新后的实例

```python
async def _authorize_task_creation(self, initiator_id: str, executor_id: str) -> AuthCheckResult:
    """检查发起人是否有权限向执行人下达任务。
    
    正常流程：发起人 permission_level >= 执行人 permission_level → WAITING
    异常场景：执行人 permission_level > 发起人 permission_level（如业务执行者向主管下达任务）
      → 标记 ANOMALY，状态设为 ANOMALY_PENDING_REVIEW，通知直接上级复核
    """
    initiator = await self._user_repo.get_by_id(initiator_id)
    executor = await self._user_repo.get_by_id(executor_id)
    
    if initiator.permission_level < executor.permission_level:
        return AuthCheckResult(
            allowed=True,
            anomaly=True,
            target_status="ANOMALY_PENDING_REVIEW",
            reason=f"发起人（{initiator.permission_level}）权限等级低于执行人（{executor.permission_level}），需上级复核",
            supervisor_id=initiator.supervisor_id,
        )
    return AuthCheckResult(allowed=True, anomaly=False, target_status="WAITING")
```

后台调度引擎，核心循环（**v2.1 已修正循环生成逻辑 + 新增分布式锁**）：

```python
class PlanTaskScheduler:
    """计划任务调度引擎 —— 后台 asyncio 循环。
    
    职责：
    - 分布式锁：多实例部署时确保只有一个进程在执行调度
    - 超时检测：扫描 deadline_at < now 且 status = WAITING 的任务
    - 临近提醒：扫描 deadline_at - now < 1h 且尚未提醒的任务
    - 循环任务补齐：扫描所有 ACTIVE 循环模板，主动补齐当前周期应有的实例（v2.1 修正，不再依赖上一轮归档）
    - LLM 失败通知：扫描推算失败的实例，通知发起人人工处理（v2.1 新增）
    - 自动归档：扫描 status = CONFIRMED 的任务，自动归档
    - 自动升级：超期 N 天未处理的任务，自动升级给顺位上级（P2）
    """
    
    def __init__(self, service: PlanTaskService, config: Config, outbound_bus: OutboundEventBus):
        self._service = service
        self._config = config
        self._outbound = outbound_bus
        self._task: asyncio.Task | None = None
        self._running = False
    
    async def start(self):
        """启动调度循环（在 EmilyCore 初始化时调用）。"""
        if not self._config.scheduler_enabled:
            return
        self._running = True
        self._task = asyncio.create_task(self._loop())
    
    async def stop(self):
        """停止调度循环。"""
        self._running = False
        if self._task:
            self._task.cancel()
    
    async def _acquire_distributed_lock(self, lock_key: str) -> bool:
        """获取 PostgreSQL 分布式锁，防止多进程重复调度。"""
        result = await self._db.execute(
            text("SELECT pg_try_advisory_lock(hashtext(:key))"),
            {"key": f"plan_task_scheduler:{lock_key}"}
        )
        return result.scalar()
    
    async def _release_distributed_lock(self, lock_key: str):
        """释放分布式锁。"""
        await self._db.execute(
            text("SELECT pg_advisory_unlock(hashtext(:key))"),
            {"key": f"plan_task_scheduler:{lock_key}"}
        )
    
    async def _loop(self):
        """主循环：每 scheduler_tick_seconds 秒执行一次。"""
        while self._running:
            try:
                await self._tick()
            except Exception as e:
                logger.error("Scheduler tick failed: %s", e, exc_info=True)
            await asyncio.sleep(self._config.scheduler_tick_seconds)
    
    async def _tick(self):
        """单次调度循环（含分布式锁保护）。"""
        # 先尝试获取全局锁，避免多进程重复调度
        if not await self._acquire_distributed_lock("global_tick"):
            return  # 其他进程已在处理，跳过
        
        try:
            now = datetime.now(timezone.utc).isoformat()
            
            # 1. 超时检测 + 发送提醒
            overdue_instances = await self._service.find_overdue(now)
            for inst in overdue_instances:
                await self._handle_overdue(inst)
            
            # 2. 临近截止提醒
            near_instances = await self._service.find_near_deadline(now)
            for inst in near_instances:
                await self._send_reminder(inst)
            
            # 3. 循环任务实例补齐（v2.1 修正核心逻辑）
            await self._ensure_cycle_instances_exist()
            
            # 4. LLM 推算失败通知发起人人工处理（v2.1 新增降级方案）
            await self._notify_llm_failure_to_initiators()
            
            # 5. 自动归档已确认任务
            await self._auto_archive_confirmed()
            
            # 6. 超期 N 天未处理自动升级给上级（P2）
            await self._auto_escalate_long_overdue()
            
        finally:
            await self._release_distributed_lock("global_tick")
    
    async def _ensure_cycle_instances_exist(self):
        """扫描所有 ACTIVE 循环模板，主动补齐当前周期应有的实例。
        
        v2.1 修正：不再依赖上一轮归档后才生成下一轮。
        不管上一轮状态如何，当前周期的任务必须存在。
        """
        active_cycle_templates = await self._service.get_active_cycle_templates()
        now = datetime.now(timezone.utc)
        
        for template in active_cycle_templates:
            # 调用 LLM 推算当前周期的 period_key 和 deadline_at
            try:
                current_period = await self._calc_current_period(
                    deadline_rule=template.deadline_rule,
                    reference_time=now,
                )
            except Exception as e:
                # LLM 推算失败：标记模板，通知发起人人工处理
                logger.warning("LLM failed to calculate period for template %s: %s", template.id, e)
                await self._mark_template_llm_failed(template.id, str(e))
                continue
            
            # 幂等检查：当前周期实例是否已存在
            existing = await self._service.get_by_period_key(
                template.id, current_period.period_key
            )
            if existing:
                continue  # 已存在，跳过
            
            # 创建当前周期的实例
            await self._service.create_instance_from_template(
                template, current_period
            )
    
    async def _calc_current_period(self, deadline_rule: str, reference_time: datetime) -> PeriodCalculationResult:
        """调用 LLM 推算当前周期的 period_key 和 deadline_at。
        
        异常不捕获，由上层处理降级逻辑。
        """
        return await self._llm_client.json_call(
            prompt=f"""
            请根据截止时间规则 '{deadline_rule}'，以参考时间 {reference_time.isoformat()} 为基准，
            推算"当前周期"的信息。返回 JSON 格式：
            {{
                "period_key": "2024-W25 或 2024-M06 格式",
                "deadline_at": "ISO8601 格式的截止时间",
                "cycle_type": "WEEKLY 或 MONTHLY"
            }}
            """,
            schema=PeriodCalculationResult,
        )
    
    async def _notify_llm_failure_to_initiators(self):
        """扫描 LLM 推算截止时间失败且尚未通知的实例，通知发起人人工处理。
        
        v2.1 新增降级方案：LLM 失败不做自动推算，通知人工处理。
        """
        failed_instances = await self._service.find_llm_failed_pending_notification(limit=50)
        
        for inst in failed_instances:
            # 通过 OutboundEventBus 发布提醒（Adapter 层根据 user_id 路由）
            self._outbound.publish("reply", {
                "user_id": inst.initiator_id,
                "content": (
                    f"【需要人工处理】计划任务「{inst.title}」（{inst.instance_no}）"
                    f"无法自动推算截止时间，请手动设定截止时间后继续执行。"
                ),
                "source": "plan_task_scheduler",
            })
            # 标记已通知，避免重复
            await self._service.mark_llm_failure_notified(inst.id)
```
