## 0. 实施前提：关键技术验证结果

### 0.1 主动推送通道可行性 ✅ 已验证

审阅意见指出"主动推送通道不通"为致命问题。经验证，**AstrBot 框架已原生支持主动发消息**：

```python
# star.Context.send_message() — 无需入站 AstrMessageEvent
async def send_message(
    self,
    session: str | MessageSesion,
    message_chain: MessageChain,
) -> bool:
    """根据 session(unified_msg_origin) 主动发送消息。"""
```

- **aiocqhttp 适配器（NapCat）已实现** `send_by_session()` → 内部调用 `bot.send_private_msg()` / `bot.send_group_msg()`，走现有 WebSocket 连接
- **无需启用 NapCat HTTP API**（当前 `httpServers: []`）
- **无需新增基础设施**

**session 字符串格式**：`"{platform_id}:{MessageType}:{session_id}"`

| 场景 | 示例 |
|------|------|
| 私聊 | `"aiocqhttp-xxx:FriendMessage:123456789"` |
| 群聊 | `"aiocqhttp-xxx:GroupMessage:group_987654321"` |

### 0.2 需要解决的问题

| 问题 | 根因 | 解决方式 |
|------|------|----------|
| SSEListener 无法主动推送 | `_handle_reply()` 依赖 `_event_registry[conv_id]` 中的 `AstrMessageEvent` | 新增 `"proactive_push"` 事件类型 + `_handle_proactive_push()` handler，走 `context.send_message()` |
| PlanTaskScheduler 通知丢失 | publish `reply` 事件时带 `user_id` 而非 `conversation_id`，且 registry 无对应 entry | 迁移到 NotificationService，走 `proactive_push` 通道 |
| Core 侧无 `user_id → IM session` 映射 | 现有架构以 conversation_id 路由 | UserConversationResolver 解析 user_id → IM session 字符串 |

## 1. 设计修正（相对需求 v2.0 的变更）

### 1.1 推翻 D06：新增 `proactive_push` 事件类型

| 项 | 需求 v2.0 | 修正后 |
|----|-----------|--------|
| SSE 事件类型 | 复用 `reply` | 新增 `proactive_push` |
| 插件侧改动 | "无需改动" | 新增 `_handle_proactive_push()` + `ProactiveSender` |
| 发送机制 | `event.set_result()` | `context.send_message()` |
| 依赖入站 event | 是 | **否** |

**理由**：`reply` 是对入站消息的响应（依赖 `AstrMessageEvent`），`proactive_push` 是系统主动推送（无入站上下文），语义和依赖链完全不同。强行复用会引入 `if/else` 分支和隐式依赖。

### 1.2 D03 增强：NotificationDispatcher 超时约束

在 `PlanTaskScheduler._tick()` 末尾追加通知扫描，`NotificationDispatcher.tick()` 内部加严格超时：

- 单次 tick 总耗时 ≤ 5s
- 单条投递 ≤ 500ms
- 超时未处理的通知留到下一轮

### 1.3 离线降级独立实现

Phase 1 不与尚未存在的 `agent_issues` 合并。`SessionAgent` 入口新增独立的 `_check_failed_notifications(user_id)` 方法。

### 1.4 数据模型补充

- `notification_queue` 增加 `dedup_key` 字段（通知去重）
- `notification_queue.target_conversation_id` 注释明确为 **IM 平台 conversation_id**（非 Core 内部 UUID）
- 离线降级用 `delivery_logs.result="DELIVERED_ON_LOGIN"` 代替 `metadata_json.delivered_on_login`（避免 JSON 并发写）

## 2. 修正后架构

```
┌───────────────────────────────────────────────────────────────────┐
│  业务模块层                                                        │
│  plan_task / agent_issue(远期) / permission(远期) / state_machine(远期) │
└───────────────────────┬───────────────────────────────────────────┘
                        ↓ NotificationService.enqueue(dedup_key=...)
┌───────────────────────────────────────────────────────────────────┐
│  NotificationService（统一入口）                                    │
│  · 校验 + 去重(dedup_key) + 落库 notification_queue (PENDING)     │
│  · 关联 source_module / source_id                                  │
└───────────────────────┬───────────────────────────────────────────┘
                        ↓
┌───────────────────────────────────────────────────────────────────┐
│  NotificationDispatcher（调度投递）                                 │
│  并入 PlanTaskScheduler._tick() 末尾，5s 超时上限                  │
│  · 扫描 PENDING 且 scheduled_at <= now（限 50 条）                 │
│  · UserConversationResolver 解析 user_id → im_session_str          │
│  · publish "proactive_push" 到 OutboundEventBus（非 "reply"）      │
│  · 标记 SENT / FAILED / EXPIRED                                    │
└───────────────────────┬───────────────────────────────────────────┘
                        ↓
┌───────────────────────────────────────────────────────────────────┐
│  出站层                                                            │
│  OutboundEventBus("proactive_push", {im_session, content})         │
│  → SSE /events/outbound                                           │
│  → SSEListener._handle_proactive_push()                            │
│  → ProactiveSender.send(context, im_session, content)              │
│  → context.send_message(im_session, MessageChain)                  │
│  → aiocqhttp → NapCat WebSocket → QQ                              │
└───────────────────────────────────────────────────────────────────┘
```

**关键变更**：出站层不再走 `_event_registry` 查找 + `event.set_result()`，而是走 `context.send_message()` 直接发送。

# data/plugins/emily_agent/adapters/astrbot/proactive_sender.py

class ProactiveSender:
    """主动消息发送器 —— 通过 AstrBot Context API 发送，不依赖 _event_registry。"""

    def __init__(self, context: "star.Context"):
        self._context = context

    async def send(self, im_session: str, content: str) -> bool:
        """
        通过 context.send_message() 主动发送文本消息。

        Args:
            im_session: IM 会话字符串，格式 "{platform_id}:{MessageType}:{session_id}"
                         如 "aiocqhttp-xxx:FriendMessage:123456"
            content: 消息文本

        Returns:
            True=发送成功, False=发送失败
        """
        from astrbot.core.message.components import Plain

        chain = [Plain(content)]
        try:
            return await self._context.send_message(im_session, chain)
        except Exception as e:
            logger.warning("ProactiveSender send failed: session=%s, err=%s", im_session, e)
            return False

    @staticmethod
    def build_private_session(platform_id: str, qq_number: str) -> str:
        """构建私聊 session 字符串。"""
        return f"{platform_id}:FriendMessage:{qq_number}"

    @staticmethod
    def build_group_session(platform_id: str, group_id: str) -> str:
        """构建群聊 session 字符串。"""
        return f"{platform_id}:GroupMessage:group_{group_id}"
```

class SSEListener:
    def __init__(self, outbound, event_registry, proactive_sender=None):
        self.outbound = outbound
        self._event_registry = event_registry
        self._proactive_sender = proactive_sender   # 新增
        self._handlers = {
            "reply": self._handle_reply,
            "progress": self._handle_progress,
            "file_send": self._handle_file_send,
            "session_closed": self._handle_session_closed,
            "proactive_push": self._handle_proactive_push,  # 新增
        }

    async def _handle_proactive_push(self, data: dict) -> None:
        """主动推送消息 —— 走 context.send_message()，不依赖 _event_registry。"""
        im_session = data.get("im_session", "")
        content = data.get("content", "")
        if not im_session or not content:
            logger.warning("proactive_push: missing im_session or content")
            return
        success = await self._proactive_sender.send(im_session, content)
        if not success:
            logger.warning("proactive_push: send failed for session=%s", im_session)

### 5.4 UserConversationResolver

# emily-core/emily_core/services/user_conversation_resolver.py

class UserConversationResolver:
    """解析 user_id → IM session 字符串（供插件 context.send_message() 使用）。"""

    def __init__(self, user_repo, conversation_repo, config):
        self._user_repo = user_repo
        self._conversation_repo = conversation_repo
        self._config = config

    def resolve(self, user_id: str) -> str | None:
        """
        解析优先级：
          1. 该用户的私聊会话（conversation_type='private'）
             → 构建 "{platform_id}:FriendMessage:{qq_number}"
          2. 该用户最近活跃的群聊（按 messages.created_at desc）
             → 构建 "{platform_id}:GroupMessage:group_{group_id}"
          3. 都没有 → 返回 None（降级上线提示）

        数据源：user_im_bindings (QQ号) + conversations (会话类型) + messages (最近活跃)

        Returns:
            IM session 字符串 或 None
        """
```

**关键映射路径**：

```
user_id → user_im_bindings(im_platform, im_user_id=QQ号)
        → conversations(im_platform, conversation_type='private', conversation_id~QQ号)
        → 拼接 "{platform_id}:FriendMessage:{QQ号}"
```

`conversations.conversation_id` 对于 QQ 私聊的格式为 `private_{QQ号}`（AstrBot 约定），需在 Resolver 中做格式解析以提取 QQ 号。

### 5.6 NotificationDispatcher

```python
# emily-core/emily_core/services/notification_dispatcher.py

import asyncio

class NotificationDispatcher:
    """通知投递调度器。"""

    MAX_BATCH = 50
    TICK_TIMEOUT = 5.0     # 单次 tick 总超时
    ITEM_TIMEOUT = 0.5     # 单条投递超时

    def __init__(self, repo, resolver, outbound_bus, config):
        self._repo = repo
        self._resolver = resolver
        self._outbound = outbound_bus
        self._config = config

    async def tick(self) -> int:
        """
        单次调度（带总超时 5s）：

          1. 过期扫描：PENDING + expires_at < now → EXPIRED
          2. 投递扫描：PENDING + scheduled_at <= now，按 priority 排序，限 50 条
          3. 对每条：
             a. resolve(user_id) → im_session（None → 标记 FAILED + 降级）
             b. publish "proactive_push" 到 OutboundEventBus
             c. 成功 → SENT；失败 → retry_count++ 或 FAILED
          4. 写 delivery_log

        Returns:
            本轮投递成功数
        """
        try:
            return await asyncio.wait_for(self._tick_inner(), timeout=self.TICK_TIMEOUT)
        except asyncio.TimeoutError:
            logger.warning("NotificationDispatcher tick timed out (%ss)", self.TICK_TIMEOUT)
            return 0

    async def _tick_inner(self) -> int:
        # 1. 过期扫描
        await asyncio.to_thread(self._repo.expire_notifications)
        # 2. 投递扫描
        notifications = await asyncio.to_thread(
            self._repo.scan_pending, limit=self.MAX_BATCH
        )
        sent = 0
        for n in notifications:
            im_session = await asyncio.to_thread(self._resolver.resolve, n.target_user_id)
            if im_session is None:
                # 无可用会话 → FAILED + 降级
                await asyncio.to_thread(
                    self._repo.mark_failed, n.id, "no_resolvable_session"
                )
                continue
            # publish proactive_push
            try:
                self._outbound.publish("proactive_push", {
                    "im_session": im_session,
                    "content": n.content,
                    "notify_no": n.notify_no,
                })
                await asyncio.to_thread(self._repo.mark_sent, n.id, im_session)
                sent += 1
            except Exception as e:
                # 重试逻辑
                retry_count = n.retry_count + 1
                max_retry = self._get_max_retry(str(e))
                if retry_count >= max_retry:
                    await asyncio.to_thread(self._repo.mark_failed, n.id, str(e))
                else:
                    await asyncio.to_thread(self._repo.increment_retry, n.id)
        return sent
```

async def _check_failed_notifications(self, user_id: str) -> list:
    """检查该用户的 FAILED 通知（无可用会话导致），返回未补推的列表。"""
    if not user_id:
        return []
    core = getattr(self, "_core_ref", None)
    if core is None or core._notification_repo is None:
        return []
    notifications = await asyncio.to_thread(
        core._notification_repo.find_failed_by_user, user_id
    )
    # 过滤已补推的（delivery_logs 中有 DELIVERED_ON_LOGIN 记录的跳过）
    return [n for n in notifications if not self._already_delivered_on_login(n.id)]

def _format_failed_notifications(self, notifications) -> str:
    """格式化上线补推提示。"""
    lines = [f"⚠ 您之前有 {len(notifications)} 条未送达通知："]
    for i, n in enumerate(notifications, 1):
        lines.append(f"{i}. {n.content}")
    return "\n".join(lines) + "\n\n"

### 6.1 新增事件类型 `proactive_push`

OutboundEventBus 新增第 5 种事件类型：

| 事件类型 | 数据载荷 | 用途 |
|----------|----------|------|
| `reply` | `{conversation_id, content, reply_to_message_id}` | 对入站消息的回复（依赖 event_registry） |
| `progress` | `{conversation_id, content}` | 处理进度（依赖 event_registry） |
| `file_send` | `{conversation_id, file_paths, caption}` | 文件发送（依赖 event_registry） |
| `session_closed` | `{conversation_id}` | 会话关闭（清理 event_registry） |
| **`proactive_push`** | `{im_session, content, notify_no}` | **系统主动推送（不依赖 event_registry）** |

SSE 帧示例：

```
event: proactive_push
data: {"im_session": "aiocqhttp-xxx:FriendMessage:123456", "content": "⚠ 任务「周报」已超时", "notify_no": "NTF-20260626-0001"}
```

## 9. 风险与对策

| 风险 | 概率 | 影响 | 对策 |
|------|------|------|------|
| `context.send_message()` 的 platform_id 不固定 | 中 | 构建的 session 字符串错误，投递失败 | 配置 `notification_platform_id`，运行时从 `_event_registry` 中的已有 event 自动探测 platform_id 并缓存 |
| UserConversationResolver 找不到用户私聊会话 | 高 | 用户从未与 Emily 私聊过，无法推送 | 降级为上线补推；同时可在用户首次交互时主动创建 conversation 记录 |
| NotificationDispatcher tick 超时影响 PlanTaskScheduler | 低 | 计划任务相关 tick 延迟 | 严格 5s 超时上限 + 放在 tick 末尾 |
| aiocqhttp 主动发消息频率限制 | 中 | NapCat/QQ 对主动消息有频率限制 | 单次 tick 限 50 条；远期加频率控制 |
| 通知表数据膨胀 | 低 | 大量 SENT/EXPIRED 记录 | 增加归档策略（90 天后清理终态记录） |

## 10. 与需求 v2.0 的变更汇总

| 项 | 需求 v2.0 | 本计划 | 变更原因 |
|----|-----------|--------|----------|
| SSE 事件类型 | 复用 `reply` | 新增 `proactive_push` | reply 依赖 event_registry，主动推送无入站 event |
| 插件侧改动 | "无需改动" | 新增 ProactiveSender + SSEListener 扩展 | 主动推送必须走 `context.send_message()` |
| target_conversation_id | 存储 conversation_id | 改为 `target_im_session`（IM session 字符串） | 语义更明确，直接用于 `context.send_message()` |
| 通知去重 | 无 | 新增 `dedup_key` 字段 | 防止 PlanTaskScheduler 重复入队 |
| 离线降级标记 | `metadata_json.delivered_on_login` | `delivery_logs.result="DELIVERED_ON_LOGIN"` | 避免 JSON 并发写风险 |
| REST 端点 | 4 个 | Phase 1 仅 2 个（列表 + 详情） | 精简首批交付 |
| PlanTaskScheduler 通知 | 未提及迁移 | Phase 1 优先迁移 | 修复现有 bug + 验证端到端通路 |
