> **V1.1 变更**：复盘周期从固定"日复盘"改为可变周期（默认 1 天，支持 N 天），以天为单位，最短 1 天。

## 一、模块定位与核心问题

Emily 已有 5+ 张进化日志表持续采集运行数据，但**零机制**将观察转化为自我改进。本模块建立三层进化知识体，形成完整的 **Observe → Reflect → Generalize → Mutate → Apply → Validate** 闭环：

```
日志采集层(已有) ──→ 周期洞察(Reflect) ──→ 进化规则(Generalize) ──→ 进化补丁(Mutate)
                                                                           │
                                                                     管理员审批(Apply)
                                                                           │
                                                                     效果验证(Validate)
```

**核心原则**：

| 原则 | 说明 |
|------|------|
| **Patch 安全边界** | 补丁只改 `emily-data/` 下的配置文件，绝不触碰 `emily-core/` 下的 Python 代码 |
| **全部人工审批** | 所有补丁需管理员（permission_level ≥ 5）审批后才能应用 |
| **复盘周期可变** | 洞察引擎的复盘周期以天为单位，默认 1 天（日复盘），支持 7 天、30 天等任意周期，最小 1 天 |
| **小步快跑** | 一条规则 = 一个补丁，避免大范围行为突变 |
| **可追溯** | 每个补丁记录 来源 Rule → 来源 Insight → 来源日志记录 |

## 二、架构设计

### 2.1 脚本优先架构

本模块采用**脚本优先**架构，与 Emily 其他模块（纯 Service 层 + API 触发）不同。设计动机：

1. 周期洞察的指标聚合和异常检测完全无 LLM 依赖，最适合先以脚本形态快速验证数据质量
2. 每个脚本可独立运行、独立验收、独立排错——无需启动整个 emily-core 容器
3. Service 层是脚本的薄封装，供调度器 Handler 和 API 复用

**调用关系**：

```
┌─────────────────────────────────────────────────────────────┐
│                    触发入口                                  │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐   │
│  │ CLI 脚本  │  │ 调度器    │  │ API 路由  │  │ 薄聚合    │   │
│  │ (独立运行) │  │ Handler  │  │ (管理员)  │  │ evolution │   │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘  └────┬─────┘   │
│       │              │              │              │          │
│       └──────────────┴──────┬───────┴──────────────┘          │
│                             │                                 │
│                             ▼                                 │
│                    ┌────────────────┐                         │
│                    │  Service 层     │  ← 薄封装，核心逻辑    │
│                    │  InsightGen    │     在脚本中             │
│                    │  RuleInductor  │                         │
│                    │  PatchGen      │                         │
│                    │  PatchApplier  │                         │
│                    │  PatchValidator│                         │
│                    │  MorningBuilder│                         │
│                    └───────┬────────┘                         │
│                            │                                  │
│                            ▼                                  │
│                    ┌────────────────┐                         │
│                    │  Repository 层  │                         │
│                    │  EvolutionRepo  │  ← 全 sync             │
│                    └───────┬────────┘                         │
│                            │                                  │
│                            ▼                                  │
│                    ┌────────────────┐                         │
│                    │  3 张进化表      │  + 9 张日志源表         │
│                    │  (新增)         │  (已有)                 │
│                    └────────────────┘                         │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 分层约定

| 层 | 文件位置 | 职责 | 模式 |
|----|---------|------|------|
| **CLI 脚本** | `scripts/evolution_*.py` | CLI 入口 + 人类可读输出 + 核心函数 | `argparse` + `if __name__` + `async def core_func()` |
| **Service** | `services/evolution/*.py` | 薄封装脚本核心逻辑，供 Handler/API 调用 | `async def` + `asyncio.to_thread()` |
| **Repository** | `repositories/evolution_repo.py` | 3 表 CRUD + 9 数据源聚合查询 | `@staticmethod` + `_impl` 内函数 + `get_session()` |
| **ORM** | `infrastructure/database/models.py` | 3 个新 ORM 类 | `Column(String)` + `_new_uuid` + `_utc_now` |
| **Prompt** | `emily-data/prompts/evolution_*.md` | LLM Prompt 模板 | `{var}` 占位符 + `load_prompt()` 加载 |

## 三、数据模型

### 3.1 新增 3 张进化表

#### `evolution_daily_insights` — 周期洞察

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | String PK | UUID |
| `insight_date` | String **UNIQUE** | 1天=`YYYY-MM-DD`，多天=`YYYY-MM-DD~YYYY-MM-DD` |
| `analysis_days` | Integer | 复盘天数（默认 1，最小 1） |
| `total_messages` | Integer | 本周期消息数 |
| `total_pipeline_runs` | Integer | 本周期 Pipeline 执行数 |
| `sop_hit_rate` | Float | SOP 命中率 0-1 |
| `fallback_rate` | Float | Fallback 率 0-1 |
| `top_sop_ids` | Text | JSON: `[{sop_id, count}]` Top 5 |
| `feedback_summary` | Text | 用户反馈信号汇总文本 |
| `anomaly_flags` | Text | JSON: `["high_fallback","low_rag_hit"]` |
| `insight_text` | Text | LLM 生成的完整 JSON 洞察 |
| `metrics_json` | Text | 完整指标快照 JSON（9 数据源聚合结果） |
| `health_score` | Integer | 健康评分 0-100 |
| `created_at` | String | ISO8601 |

**`insight_date` 存储格式**：
- 1 天复盘：`2026-07-09`
- 7 天复盘：`2026-07-03~2026-07-09`
- UNIQUE 约束确保同一周期范围不重复生成

**写入时机**：`evolution_insight.py` 脚本 / `InsightGenerator.generate()` / 每日 22:00 调度（默认 1 天）

#### `evolution_rules` — 进化规则

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | String PK | UUID |
| `rule_no` | String(20) **UNIQUE** | R-001, R-002, ... |
| `title` | String(200) | 规则标题 |
| `description` | Text | 规则详细描述 |
| `evidence_insight_ids` | Text | JSON: 支撑此规则的 Insight ID 列表 |
| `category` | String(30) | routing / prompt / sop / hook / user_memory |
| `confidence` | Float | 置信度 0-1 |
| `status` | String(20) | DRAFT → CONFIRMED → SUPERSEDED / DISCARDED |
| `superseded_by` | String(20) | 被哪条规则替代 |
| `suggested_action` | Text | 建议的具体改进动作 |
| `impact_estimate` | String(500) | 预计改进后的指标变化 |
| `created_at` | String | ISO8601 |
| `confirmed_at` | String | ISO8601 |

**状态机**：

```
DRAFT ──(管理员确认)──→ CONFIRMED ──(被新规则替代)──→ SUPERSEDED
  │
  └──(废弃)──→ DISCARDED
```

#### `evolution_patches` — 进化补丁

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | String PK | UUID |
| `patch_no` | String(20) **UNIQUE** | EP-001, EP-002, ... |
| `rule_no` | String(20) | 来源规则编号 |
| `target_type` | String(30) | prompt / sop / skill / hook / user_memory |
| `target_path` | String(500) | 目标文件路径（相对 emily-data/） |
| `patch_content` | Text | 变更内容 |
| `patch_type` | String(30) | append / replace_section / insert_after |
| `search_anchor` | String(500) | 定位锚点 |
| `risk_level` | String(10) | low / medium / high |
| `validation_criteria` | Text | 验证标准 |
| `status` | String(20) | DRAFT → APPLIED → CONFIRMED / ROLLED_BACK |
| `rollback_snapshot` | Text | 应用前原始内容（用于回滚） |
| `created_at` | String | ISO8601 |

**状态机**：

```
DRAFT ──(管理员审批)──→ APPLIED ──(7天后验证通过)──→ CONFIRMED
  │                       │
  └──(管理员拒绝)──→ REJECTED    └──(验证不通过)──→ ROLLED_BACK
```

**8 条硬规则**：

| 标识 | 检测规则 | 严重度 | 阈值(1天) | 多天均摊 |
|------|---------|--------|-----------|---------|
| `high_fallback` | Fallback 率 > 30% | 🔴 高 | 0.30 | 无需均摊 |
| `sop_correction_spike` | 纠正信号 > 3×days | 🔴 高 | 3 | **按天数均摊** |
| `low_rag_hit` | RAG 零命中率 > 50% | 🟡 中 | 0.50 | 无需均摊 |
| `slow_pipeline` | Pipeline 平均耗时 > 10s | 🟡 中 | 10000ms | 无需均摊 |
| `volume_anomaly` | 消息量同比 ±50% | 🟡 中 | 0.50 | 对比同长度前周期 |
| `tool_failure` | 单工具失败率 > 20% | 🔴 高 | 0.20 | 无需均摊 |
| `iteration_overflow` | max_iterations_reached > 3×days | 🟡 中 | 3 | **按天数均摊** |
| `node_overdue` | 存在逾期 IN_PROGRESS 节点 | 🔴 高 | 1 | 无需均摊 |

**返回结构**：
```python
[
    {
        "flag": "high_fallback",
        "severity": "high",       # "high" | "medium"
        "message": "Fallback 率 35.2% 超过阈值 30%",
        "detail": { "fallback_rate": 0.352, "threshold": 0.30 }
    },
    ...
]
```

**阈值配置**：在 `evolution_anomaly.py` 顶部的 `THRESHOLDS` 字典中集中定义，修改阈值只改此处。

#### `evolution_apply.py` — 补丁审批/应用/回滚

| 项目 | 说明 |
|------|------|
| **核心函数** | `approve_patch()`, `apply_patch()`, `rollback_patch()` |
| **LLM 依赖** | ❌ 无 |
| **写操作** | ✅ 写 DB + 修改 `emily-data/` 下的配置文件 |

```bash
uv run python scripts/evolution_apply.py list --status DRAFT                    # 列出待审批
uv run python scripts/evolution_apply.py approve --patch-no EP-001              # 审批
uv run python scripts/evolution_apply.py reject --patch-no EP-001               # 拒绝
uv run python scripts/evolution_apply.py apply --patch-no EP-001                # 应用
uv run python scripts/evolution_apply.py apply --patch-no EP-001 --dry-run      # 预览应用
uv run python scripts/evolution_apply.py rollback --patch-no EP-001             # 回滚
```

**应用流程**（`apply`）：
1. 读取 `evolution_patches` 中的 patch 记录
2. 读取目标文件当前内容 → 保存为 `rollback_snapshot`
3. 按 `patch_type` 执行变更：
   - `append`：在 `search_anchor` 定位的段落末尾追加
   - `replace_section`：替换 `search_anchor` 定位的完整段落
   - `insert_after`：在 `search_anchor` 定位后插入
4. 状态 → `APPLIED`

**回滚流程**（`rollback`）：
1. 读取 `rollback_snapshot`
2. 写回原始内容
3. 状态 → `ROLLED_BACK`

#### `evolution_validate.py` — 补丁效果验证

| 项目 | 说明 |
|------|------|
| **核心函数** | `async def validate_patches(patch_nos=None, *, dry_run=False) → list[dict]` |
| **LLM 依赖** | ❌ 无（纯指标对比） |
| **写操作** | ✅ 更新 patch 状态 + 可能自动回滚 |

```bash
uv run python scripts/evolution_validate.py --all                 # 验证所有已应用 ≥7 天的补丁
uv run python scripts/evolution_validate.py --patch-no EP-001     # 验证指定补丁
uv run python scripts/evolution_validate.py --all --preview       # 只看指标对比
```

**验证逻辑**：
1. 查找 `status=APPLIED` 且 `applied_at` ≥ 7 天前的补丁
2. 对比应用前后关键指标（根据 `validation_criteria` 中定义的标准）
3. 判定：
   - **CONFIRMED**：指标改善或无显著恶化
   - **ROLLED_BACK**：指标显著恶化 → 自动回滚

## 十、排错速查

| 现象 | 原因 | 解决 |
|------|------|------|
| `evolution_metrics.py` 全输出 0 | 当日无数据或表为空 | 正常——新部署系统无历史数据；用 `--source pipeline` 检查单源 |
| 脚本报 `import emily_core` 失败 | `sys.path` 未包含 `emily-core/` | 检查脚本顶部的 `sys.path.insert(0, ...)` |
| `__pycache__` 不刷新 | Docker bind-mount 不触发重编译 | `docker exec emily-core find /app/emily_core -name '__pycache__' -type d -exec rm -rf {} +` |
| Windows GBK 乱码 | PowerShell 默认 GBK 编码 | 脚本首行已含 `io.TextIOWrapper` 修复；或 `$env:PYTHONIOENCODING="utf-8"` |
| LLM 返回非 JSON | `chat_json` 解析失败 | 检查 `LLMClient._parse_json_response` 的 markdown 代码块回退逻辑 |
| 补丁应用失败：找不到锚点 | `search_anchor` 在目标文件中不存在 | 检查 `evolution_patch.md` Prompt 是否明确要求锚点精确匹配 |
| 补丁回滚后行为未恢复 | `rollback_snapshot` 为空 | 检查 `apply_patch()` 是否在应用前正确保存了原始内容 |
