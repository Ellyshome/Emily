## 一、模块定位与价值

### 1.1 解决什么问题

SessionAgent 对自身系统结构缺乏可操作的认知：

| 认知条目 | 当前状态 | 本模块交付 |
|----------|----------|-----------|
| 数据库有哪些表 | 仅 10/53 表名可见（硬编码） | 全量表名 + 可见表核心字段 + 表间关系 |
| 字段结构与含义 | 完全没有 | 核心字段名/类型/必填/含义 |
| 文件分类体系 | 仅有数量统计 | 7 类分类说明 + 访问规则 |
| 权限分级结构 | 仅一行标签"管理员(L5)" | 6 级树形继承 + 两线分叉 + 跨线机制 + 用户位置 |

**一句话**：当前 SessionAgent 的认知是**标签级**的——它知道自己能访问什么、叫什么名字，但**不知道为什么、怎么用、有什么关联**。系统自我描述模块将代码中已有的知识桥接到 LLM prompt。

### 1.2 一句话总结

**系统描述书**回答"我自己是什么结构"——数据库/文件/权限三域认知，代码驱动，偏差检测自动更新。

### 1.3 在元认知模块中的位置

```
元认知模块
├── 规则书     → 我应该怎么做事（规范层 / Ought）
├── 世界书     → 我服务的项目现在怎么样（经验层 / Is-External）
└── 系统描述书 → 我自己是什么结构（自省层 / Is-Internal）  ← 本模块
```

三种知识构成完整的认知三角：**规范知识 + 外部经验知识 + 内省知识**。

## 二、四层架构

### 2.1 总体结构

| 层 | 名称 | 存储位置 | 更新方式 | 生命周期 | 注入变量 |
|----|------|----------|----------|----------|----------|
| 第一层 | 规则书 | `emily-data/rules/规则书.md` | 人工编辑 → 热重载 | 系统级（全局一份） | `{rule_book}` |
| 第二层 | 世界书 | `project_world_books` 表 | 偏差检测 → 日级增量更新 | 项目级（每项目一份） | `{project_world_book}` |
| 第三层 | 系统描述书 | `system_descriptions` 表 | 代码 hash 偏差检测 → 周级更新 | 系统级（全局一份） | `{system_description}` |
| 编排层 | 元认知判断 | `project_world_books.initialization_*` | 初始化检查 | 项目级 | 世界书内嵌 |

### 2.2 各层对比

| 维度 | 规则书 | 世界书 | 系统描述书 |
|------|--------|--------|-----------|
| 认知对象 | 行为规范（Ought） | 项目业务现实（Is-External） | 系统自身结构（Is-Internal） |
| 真理来源 | 人类编写 | 业务数据内容 | 代码与配置 |
| 变化频率 | 人工编辑时 | 日级 | 部署/迁移时 |
| 作用域 | 全局 | per-project | 全局 |
| 偏差模式 | 无（无自动检测） | 数据 vs 记录 | 代码 hash vs 描述 hash |
| 更新触发 | 人工编辑 → 重载 | 调度器日级检测 | 启动校验 + 周级调度 + 迁移触发 |
| Token 预算 | ~100 | ~170 | ~400 |

## 三、数据结构

### 3.1 数据库表：`system_descriptions`

| 字段 | 类型 | 说明 | 分类 |
|------|------|------|------|
| `id` | String PK | UUID | 标识 |
| `version` | Integer | 整体版本号（递增） | 版本 |
| `content_json` | Text | 三域结构化 JSON（机器可解析） | 认知数据 |
| `content_text` | Text | 纯文本摘要（直接注入 prompt，~400 tokens） | 认知数据 |
| `domain_versions` | Text | JSON：每域独立版本号 `{"database":3,"file":1,"permission":2}` | 版本 |
| `schema_hash` | String(64) | `Base.metadata` 的 SHA-256 hash | 偏差检测 |
| `permission_hash` | String(64) | `PermissionLevel` + `INHERITANCE_CHAIN` 的 SHA-256 hash | 偏差检测 |
| `file_model_hash` | String(64) | `FileCategory` 枚举 + `files` 模型的 SHA-256 hash | 偏差检测 |
| `token_count` | Integer | 估算 token 数 | 统计 |
| `generated_at` | String | 最近生成时间 | 元数据 |
| `generated_by` | String(50) | 生成来源：`startup` / `scheduler` / `manual` | 元数据 |
| `created_at` | String | 首次创建时间 | 元数据 |
| `updated_at` | String | 最近更新时间 | 元数据 |

**关键设计决策**：
- 无 `project_id`——系统描述是全局唯一的，不因项目不同而改变
- 三个 hash 字段分别对应三域——支持单域偏差检测（虽然当前采用全量重建策略）
- `content_json` 与 `content_text` 分离——JSON 供程序解析和按权限裁剪，text 供 LLM 直接消费

### 3.3 content_text 格式规范

纯文本摘要控制在 ~600 字（~400 tokens），按域拼接：

```
📊 数据库资源（你有权访问的表）
· 事件表: 读写 — 记录项目现场发生的事件
  核心字段：title(标题,必填) / event_type(类型,必填) / event_date(日期)
· 任务表: 只读 — 跟踪工作任务的执行情况
  核心字段：title(标题,必填) / status(状态) / node_id(关联节点→节点表)
（另有 48 张系统表，共 53 张）

🔗 表间关系
events.project_id → projects.id / tasks.node_id → project_nodes.node_id

📁 文件分类体系
项目证照 / 承包合同 / 工作记录 / 阶段成果 / 过程文件 / 管理规程 / 其他文件
文件访问规则：confidentiality=0 公开文件所有用户可见；上传人始终可见；L5+ 管理员全部可见

🔐 权限分级体系
参建线: L1 访客 → L2 参建执行 → L3 参建管理
建设线: L1 访客 → L4 建设主管 → L5 管理员 → L6 系统管理员
⚠️ L4 不继承 L2/L3，两线在 L1 后分叉；跨线访问需临时/永久授权
你的位置：管理员(L5) 建设线，继承链 L5→L4→L1
```

**格式规则**：
- D1 数据库部分按用户 `db_perms` 动态裁剪（Strategy B）
- D2 文件部分全量显示，访问控制由运行时 `confidentiality` 检查执行
- D3 权限部分全量显示 + 动态注入当前用户位置
- 不可见表仅列数量，不列名

### 3.4 字段描述三层 fallback

| 优先级 | 来源 | 说明 |
|--------|------|------|
| 1 | `PublicFieldRegistry` 表 | 最权威，人工维护 |
| 2 | ORM `Column.comment` 属性 | 代码内联注释，开发时维护 |
| 3 | 空字符串 | 兜底（LLM 生成留作后续优化） |

## 六、三域构建详解

### 6.1 D1：数据库认知

**数据源与采集方式**：

| 数据 | 来源 | 采集方式 |
|------|------|---------|
| 表清单 | `Base.metadata.tables` | 反射 ORM 元数据 |
| 字段名/类型 | `Column` 属性 | 反射 ORM 元数据 |
| 字段含义 | `PublicFieldRegistry` 表 + `Column.comment` | 查询 DB + 反射 |
| 表间关系 | `ForeignKey` | 手工标注（`_KEY_RELATIONS`） |
| 用户权限 | `db_perms`（来自 `PermissionService`） | 注入时裁剪（非构建时） |

**可见表范围**：与 `db_perms` 实际返回对齐——project / events / tasks / meetings / files / financial，共 6 张表提取核心字段。

**字段筛选**：每张可见表仅提取 5-6 个核心字段（`_KEY_FIELDS` 映射），避免全量字段过载 prompt。

**注入时裁剪（Strategy B）**：
- 构建时生成全量描述（所有可见表 + 全部字段）
- `fetch_system_description._format_filtered_text()` 按 `db_perms` 过滤 D1 部分
- 用户无权限的表直接跳过，不显示
- 不可见表仅列数量，不列名

### 6.2 D2：文件认知

**7 类文件分类**（对应 `FileCategory` 枚举）：

| 枚举值 | 中文名 | 说明 |
|--------|--------|------|
| PROJECT_LICENSE | 项目证照 | 项目相关证照文件 |
| CONTRACT | 承包合同 | 各类合同文件 |
| WORK_RECORD | 工作记录 | 施工日志、检查记录等 |
| PHASE_DELIVERABLE | 阶段成果 | 阶段性验收成果 |
| PROCESS_DOC | 过程文件 | 审批单、签证单等过程性文件 |
| MANAGEMENT_SPEC | 管理规程 | 标准、规范、制度文件 |
| OTHER | 其他文件 | 不属于以上类别的项目文件 |

**文件访问规则**（基于 `confidentiality` 字段）：

| confidentiality 值 | 含义 | 可见性 |
|---------------------|------|--------|
| 0 | 公开 | 所有用户可见 |
| 1 | 内部 | 按权限级别控制 |
| 2 | 机密 | 仅授权人员可见 |
| 3 | 绝密 | 仅 L5+ 管理员可见 |

> ⚠ 需求文档假设的 `access_level ≤ info_level` 规则与实际代码不符。实际使用 `confidentiality` 整数字段（0-3）控制访问。

**files 表核心字段**（与需求文档假设不同）：

| 实际字段名 | 需求假设 | 类型 | 说明 |
|-----------|---------|------|------|
| `filename` | ~~original_name~~ | String(500) | 原始文件名 |
| `file_type` | — | String(100) | 文件类型 |
| `file_category` | ~~category~~ | String(50) | 文件业务分类（FileCategory 枚举值） |
| `confidentiality` | ~~access_level~~ | Integer | 密级 0=公开 1=内部 2=机密 3=绝密 |

### 6.3 D3：权限认知

**6 级树形继承结构**：

```
参建线: L1 访客 → L2 参建执行 → L3 参建管理
建设线: L1 访客 → L4 建设主管 → L5 管理员 → L6 系统管理员
```

**关键语义**：
- L4 不继承 L2/L3——两线在 L1 后分叉
- 跨线访问通过 `PermissionGrant`（临时/永久授权）实现
- 继承链存储在 `INHERITANCE_CHAIN` 常量：`{5: frozenset({5, 4, 1}), ...}`

**db_perms 实际覆盖的表**（仅 5 张，非需求假设的 10 张）：

| 级别 | 可见表 |
|------|--------|
| L1 | project:read |
| L2/L3 参建线 | project:read, event:rw, task:read/rw(视公司类型), meeting:rw |
| L4 建设主管 | project:rw, event:rw, task:rw, meeting:rw |
| L5+ 管理员 | project:rw, event:rw, task:rw, meeting:rw, financial:read |

## 七、偏差检测与进化闭环

### 7.1 三域 hash 偏差检测

| 检测域 | 检测方式 | 偏差信号 |
|--------|---------|---------|
| D1 数据库 | 计算 `Base.metadata.tables` 的 SHA-256 hash vs `schema_hash` | 新增/删除表、新增/删除/修改字段 |
| D2 文件 | 计算 `FileCategory` 枚举 + files 模型的 SHA-256 hash vs `file_model_hash` | 分类枚举变更、文件模型字段变更 |
| D3 权限 | 计算 `PermissionLevel` + `INHERITANCE_CHAIN` + `LEVEL_NAME` 的 SHA-256 hash vs `permission_hash` | 级别增删、继承链变更 |

### 7.2 Hash 计算方式

采用**ORM 元数据序列化**方式，不 hash 源文件（避免注释/空格变更误触发）：

```python
# D1 示例：序列化 Base.metadata.tables
for tbl_name in sorted(Base.metadata.tables.keys()):
    table = Base.metadata.tables[tbl_name]
    for col in table.columns:
        col_parts.append(f"{col.name}:{type(col.type).__name__}:{col.nullable}")
    parts.append(f"{tbl_name}({','.join(sorted(col_parts))})")
canonical = "|".join(parts)
return hashlib.sha256(canonical.encode("utf-8")).hexdigest()
```

### 7.3 更新策略

当前采用**全量重建策略**（与世界书一致）：

- **原因**：三域描述之间有交叉引用（如权限域引用表名，文件域引用权限规则）
- **实现**：检测到任何域偏差后，调用 `SystemDescriptionBuilder.build()` 重建全部三域
- **未来优化**：可改为只重建过时域，但需确保域间一致性

### 7.4 更新触发

| 触发时机 | 机制 | 说明 |
|----------|------|------|
| 容器启动 | `_init_meta_cognition()` 中检测 | 启动时自动检查，有偏差则重建 |
| 周级调度 | `SystemDescriptionUpdateHandler` | 比世界书的日级更宽松 |
| 手动触发 | CLI `build_system_description.py --force` | 开发/运维调试 |
| API 触发 | `POST /api/v1/meta-cognition/system-description/build?force=true` | 运维远程操作 |

### 7.5 与世界书偏差检测的差异

| 维度 | 世界书 | 系统描述书 |
|------|--------|-----------|
| 检测对象 | DB 数据内容 | 代码结构 hash |
| 检测频率 | 日级 | 周级 + 启动时 |
| 检测方法 | 查 DB 聚合值 vs 世界书记录 | 查 ORM 元数据 hash vs 存储的 hash |
| 需要连接 | 是（查业务数据） | 是（加载 ORM 元数据） |
| 需要 LLM | 有时（层1语义变更） | 否（纯代码结构对比） |

## 八、Session 注入方案

### 8.1 注入时裁剪（Strategy B）

```
构建（全量）→ 存 DB（content_json + content_text）
                                    ↓ fetcher 读取 content_json
                                    ↓ 按 db_perms 过滤 D1
                                    ↓ 重新格式化 content_text
                                    ↓ 返回裁剪后的文本
```

**裁剪规则**：
- D1 数据库：只显示 `db_perms` 中有权限的表；无权限表计入"另有 N 张表"
- D2 文件：全量显示（访问控制由 `confidentiality` 运行时检查执行）
- D3 权限：全量显示 + 动态注入当前用户位置（级别+继承链）

### 8.2 与现有变量的关系

| 现有变量 | 处理方式 | 理由 |
|----------|---------|------|
| `{visible_schema}` | **保留但降级为后备** | 系统描述书为空时降级显示 |
| `{visible_files}` | **保留但降级为后备** | 同上 |
| `{user_permission_level}` | **保留** | 用户身份标识，属于 Session 级上下文 |
| `{available_tools}` | **保留** | 工具列表是动态的，系统描述书是静态的 |

### 8.3 prompt 模板位置

`emily-data/prompts/session.md` 中，在 `### 规则书` 段之后：

```markdown
### 系统自我描述
{system_description}
```

## 九、Token 预算控制

| 场景 | 系统描述 | 世界书 | 规则书 | 总计 |
|------|---------|--------|--------|------|
| L5 管理员 | ~400 tokens | ~170 tokens | ~100 tokens | ~670 tokens |
| L2 参建执行 | ~300 tokens（可见表少） | ~170 tokens | ~100 tokens | ~570 tokens |
| L1 访客 | ~200 tokens（仅 project:read） | ~170 tokens | ~100 tokens | ~470 tokens |

**控制手段**：
- 每张可见表仅提取 5-6 个核心字段
- 不可见表不列名不列字段
- 表间关系仅标注最重要的 5-7 条
- `content_text` 控制在 ~600 字

## 十、开发指南

### 10.1 新增可见表

1. 打开 `system_description_builder.py`
2. 在 `_TABLE_DISPLAY_NAMES` 中追加中文标签
3. 在 `_TABLE_DESCRIPTIONS` 中追加表描述
4. 在 `_VISIBLE_TABLES` 集合中追加表名
5. 在 `_KEY_FIELDS` 中追加该表的核心字段列表
6. 在 `_KEY_RELATIONS` 中追加相关表间关系（如有）
7. 运行 `--force` 重建：`uv run python scripts/build_system_description.py --force`

### 10.2 新增文件分类

1. 修改 `models.py` 中 `FileCategory` 枚举（添加新成员 + DISPLAY_NAMES）
2. 运行 `--force` 重建——hash 变化自动触发偏差检测
3. 无需手动修改 builder——`_build_file()` 通过 `FileCategory.ALL` 自动采集

### 10.3 新增权限级别

1. 修改 `permission/level.py` 中 `PermissionLevel`、`INHERITANCE_CHAIN`、`LEVEL_NAME`
2. 修改 `system_description_builder.py` 中 `_build_permission()` 的 `line_map` 和 `capability_map`
3. 运行 `--force` 重建

### 10.4 新增字段描述

1. 向 `public_field_registry` 表插入记录：`model_name`、`field_name`、`description`
2. 无需重建——`_load_field_descriptions()` 每次构建时实时查询

```sql
INSERT INTO public_field_registry (id, model_name, field_name, description)
VALUES (gen_random_uuid()::text, 'Event', 'event_type', '事件类型（施工进展/质量安全/材料/设计变更/会议/其他）');
```

### 10.5 调试技巧

```powershell
# 预览系统描述（不入库）
uv run python scripts/build_system_description.py --dry-run
```

### 10.6 常见问题

| 问题 | 原因 | 解决 |
|------|------|------|
| 系统描述为空 | 首次启动未触发构建 | 手动 `--force` 重建 |
| 偏差检测全 False | 描述刚构建，代码未变 | 正常，代码变更后再检测 |
| 可见表与 db_perms 不一致 | `_VISIBLE_TABLES` 未包含新表 | 按本手册 §10.1 新增 |
| 字段描述为空 | `PublicFieldRegistry` 无记录且 `Column.comment` 未设置 | 向表中插入记录或给 ORM 列加 `comment=` |
| `__pycache__` 不刷新 | Docker bind-mount 不触发重编译 | `docker exec emily-core find /app/emily_core -name '__pycache__' -type d -exec rm -rf {} +` |
| content_text 中出现"施工图"等 | 参照了旧需求文档 | 实际分类是 7 类（项目证照/承包合同/...），见本手册 §6.2 |
| Token 占用过大 | 可见表字段过多 | 调整 `_KEY_FIELDS` 减少每表字段数 |
