# Emily 元认知模块 — 需求规格

> **版本**：V3
> **模块名称**：元认知模块（Meta-cognition Module）
> **前置文档**：[自检-冷启-世界书_审核_V1.md](../自检-冷启-世界书/自检-冷启-世界书_审核_V1.md)
> **核心变更**（V2→V3）：模块更名为"元认知"；新增"规则书"系统级行为约定；明确项目启动时元认知数据收集与判断流程

---

## 一、模块定位

### 1.1 核心问题

Emily 定位为"项目团队公共大脑"，但当前存在两个根本性缺失：

1. **认知断层**：SessionAgent 对项目缺乏全面认知——它只知道自己服务的项目名和状态，不知道项目的人员架构、节点进度、关键里程碑、当前风险。数据存在但未被组织成 AI 可理解的上下文。
2. **行为无约束**：Emily 没有系统级的行为约定——它不知道自己在组织中应该主动做什么、不该做什么、遇到边界情况如何处理。缺乏"组织共识"导致行为不可预期。

### 1.2 模块目标

元认知模块解决两个问题：**"我知道什么"** 和 **"我该怎么做"**。

- **世界书**回答"我知道什么"：对所服务项目的七层认知，通过认知进化闭环保持同步
- **规则书**回答"我该怎么做"：AI 与人的组织约定，系统级的行为宪法

```
项目实际数据变化 → 认知偏差检测 → 增量更新世界书 → Session 注入更新后的认知
项目启动/数据缺失 → 元认知判断 → 引导初始化 / 补充世界书
组织约定变更 → 规则书更新 → Session 注入更新后的行为规则
```

### 1.3 三层架构

```
┌─────────────────────────────────────────────────────┐
│                    规则书                              │
│   AI 与人的组织约定（系统级行为宪法）                    │
│   回答：我该怎么做、不该怎么做、边界情况如何处理         │
│   人类可读、逐条明文                                  │
├─────────────────────────────────────────────────────┤
│                    世界书                              │
│   项目七层认知（数据驱动的项目理解）                     │
│   回答：这是什么项目、谁负责、走到哪了、有什么风险       │
│   偏差检测 → 增量更新                                 │
├─────────────────────────────────────────────────────┤
│                  元认知判断                            │
│   项目启动时的数据收集与初始化判断                       │
│   回答：项目信息齐不齐、缺什么、是否可运转               │
│   不齐 → 引导补充；缺关键信息 → 阻断标记                │
└─────────────────────────────────────────────────────┘
```

### 1.4 设计原则

1. **独立脚本 + 薄聚合**：每个功能以独立可执行脚本交付，支持 `--dry-run` 独立运行观察；薄聚合脚本串联各独立脚本完成流程编排
2. **模块化实现**：按模块逐个实现、逐个验证。每个模块独立可用，模块间通过数据库和文件接口衔接
3. **初始化引导**：项目有"最小可运转信息集合"，Emily 能感知缺失项并主动引导管理员完成初始化
4. **规则书人类可读**：规则书是 Markdown 文件，人类可以直接阅读和编辑，Emily 读取后注入 prompt

### 1.5 与 V1 的关系

| 维度 | V1（自检-冷启-世界书） | V3（元认知模块） |
|------|----------------------|-----------------|
| 认知范围 | 系统级统计（用户数/项目数/事件数） | 项目级七层认知 + 系统级行为约定 |
| 认知形态 | 静态模板 + 一次性数据注入 | 持久化文档 + 增量更新 + 规则书 |
| 更新机制 | 仅冷启动时重建 | 偏差驱动增量更新 + 规则书人工编辑 |
| 注入方式 | 独立 prompt 模板 | 世界书 `{project_world_book}` + 规则书 `{rule_book}` |
| 行为约束 | 无 | 规则书明文约定 AI 处理原则 |

## 二、规则书

### 2.1 定义

规则书是 Emily 的**系统级行为宪法**——一份由人类编写和维护的 Markdown 文档，逐条明文约定 AI 的处理原则。类似于 AI Agent 的长期记忆文件，但是**整个系统级别**的。

### 2.2 与世界书的区别

| 维度 | 世界书 | 规则书 |
|------|--------|--------|
| 回答的问题 | 我知道什么（事实） | 我该怎么做（行为） |
| 内容性质 | 数据驱动、自动生成 | 人类约定、人工编辑 |
| 更新方式 | 偏差检测 → 自动增量更新 | 人工编辑 → 重载生效 |
| 生命周期 | 项目级（每个项目一份） | 系统级（全局一份） |
| 注入位置 | `{project_world_book}` | `{rule_book}` |

### 2.3 规则书内容

规则书全文见 [emily-data/rules/规则书.md](../../emily-data/rules/规则书.md)，包含八类条款：

| 章节 | 主题 | 条款数 | 核心约定 |
|------|------|--------|---------|
| 一 | 身份与边界 | 5 | 公共大脑非私人助手、信息对管理员可见、操作可审计、无审批权、超出能力如实告知 |
| 二 | 主动行为规则 | 5 | 初始化引导、风险提醒、不主动发起对话、T2以下阻断录入、偏差自动修补 |
| 三 | 信息处理原则 | 5 | 只记录事实、原始数据优先、不编造数据、区分确定与不确定、来源可溯 |
| 四 | 权限与安全 | 5 | 严格按权限、删除二次确认、敏感信息脱敏、操作留痕、异常批量操作告警 |
| 五 | 初始化与引导 | 6 | 首次启动自动收集、缺失项引导、一次一项、进度可查、允许跳过、**必备项可自定义** |
| 六 | 沟通风格 | 5 | 专业友好、简洁聚焦、禁用Markdown、emoji点缀、不确定时主动询问 |
| 七 | 数据完整与一致性 | 5 | 世界书与现实对齐、偏差自动修补、录入前校验、关联数据同步、定期复盘 |
| 八 | 错误与异常处理 | 4 | 诚实报告失败、不静默跳过、降级不崩溃、异常上报 |

> 📝 **自定义**：规则书是 Markdown 文件，项目管理者可直接编辑。第五章"初始化与引导"条款与初始化必备项清单联动——必备项定义"什么叫齐了"，规则书定义"不齐怎么办"。修改后保存，热重载或重启生效。

### 2.4 规则书文件

- **位置**：`emily-data/rules/规则书.md`
- **格式**：Markdown，人类可直接阅读和编辑
- **加载**：EmilyCore 启动时读取，注入到 Session prompt 的 `{rule_book}` 变量
- **热更新**：支持 API 触发重载（无需重启容器）

### 2.5 规则书与进化闭环的关系

规则书是**人工约定**，不在进化闭环的自动更新范围内。但进化闭环可以**建议**规则书更新：

- 当 DailyInsight 发现高频 Fallback 场景时，可建议新增对应规则
- 当 RuleInduction 归纳出行为模式时，可建议将其固化为规则书条款
- 建议以 DRAFT 补丁形式呈现，经人工审批后写入

## 三、七层认知模型

### 3.1 概述

SessionAgent 对项目的认知分为七层，每层有独立的数据源、变化节奏和过时判定标准：

| 层 | 名称 | 回答的问题 | 变化节奏 | 过时信号 |
|----|------|-----------|---------|---------|
| 1 | 本体认知 | 这是什么项目？ | 慢（月级） | lifecycle_stage 变了 / 新增参建单位 |
| 2 | 人员认知 | 谁负责什么？ | 中（周级） | 有人离开/加入 / 角色变更 |
| 3 | 结构认知 | 项目怎么拆的、走到哪了？ | 快（日级） | 节点进度变化 >5% / 新节点 / 状态流转 |
| 4 | 时间认知 | 时间线上过去和未来？ | 快（日级） | 新逾期 / 临近截止 / 事件流变化 |
| 5 | 关系认知 | 动了A会影响B？ | 中（周级） | 依赖链变化 / 新增阻塞 |
| 6 | 知识认知 | 知道什么、不知道什么？ | 慢（月级） | 新 SOP / 知识库更新 |
| 7 | 自省认知 | 自己几斤几两？ | 快（日级） | 初始化状态变化 / 能力边界变化 |

### 3.2 各层认知内容

#### 层1：本体认知

| 认知项 | 具体内容 | 数据源 |
|--------|----------|--------|
| 项目身份 | 名称、编号、地址、规模（面积/栋数/业态） | projects 表 |
| 生命周期 | 当前阶段（立项→规划→施工→交付）、阶段目标、阶段截止 | projects.lifecycle_stage |
| 参建方 | 建设单位/代建/总包/监理/设计…各是谁 | company_info + 关联 |
| 项目概述 | 一句话描述项目性质和当前阶段核心任务 | LLM 生成（阶段迁移时） |

**文本格式示例**：
```
📋 项目：生态城26#地（ECOCITY-26）
📍 XX市XX区 ｜ 阶段：工程施工 ｜ 代建：蓝城伟业
🏗 总包：XX建设 / 监理：XX监理 / 设计：XX设计院
```

#### 层2：人员认知

| 认知项 | 具体内容 | 数据源 |
|--------|----------|--------|
| 关键人员 | 项目经理/总监理/各条线负责人 | users + user_company |
| 职责边界 | 谁负责哪些节点、谁有权审批 | permission + node ownership |
| 联系关系 | 同一公司的人、上下级关系 | users.company_id + supervisor_id |

**文本格式示例**：
```
👥 张工(项目经理/蓝城伟业) / 李总(总监理/XX监理)
条线：土建→王工 / 安装→赵工 / 安防→孙工
```

#### 层3：结构认知

| 认知项 | 具体内容 | 数据源 |
|--------|----------|--------|
| 节点树拓扑 | 里程碑→工作包→任务，层级关系 | project_nodes (parent_node_id) |
| 整体进度 | 各层级进度百分比、加权汇总 | project_nodes.progress + child_weight |
| 里程碑状态 | 关键里程碑的完成情况 | project_nodes WHERE node_type='MILESTONE' |
| 流转状态 | 三态：条件未满足→进行中→完成 | project_nodes.status |

**文本格式示例**：
```
📊 120节点：35完成 / 45进行中 / 5逾期
🏁 基础工程✓ ｜ 主体封顶60%(8.30) ｜ 竣工验收(12.31)
```

#### 层4：时间认知

| 认知项 | 具体内容 | 数据源 |
|--------|----------|--------|
| 近期事件 | 关键事件流（决策/变更/里程碑达成） | events 表 |
| 即将到期 | 7天内截止的节点/任务 | project_nodes.deadline |
| 已逾期 | 超时未完成的事项 | project_nodes (deadline < now) |
| 周期节奏 | 晨报/周报/月度安全检查 | scheduler_jobs |

**文本格式示例**：
```
📝 近期：7.9样板段放线完成 / 7.8钢筋进场验收通过
⏰ 7天内截止：消防验收资料(7.15) / 主体封顶(8.30)
🔴 逾期：外墙保温施工(7.5) / 电梯安装(7.1)
```

#### 层5：关系认知

| 认知项 | 具体内容 | 数据源 |
|--------|----------|--------|
| 上下游依赖 | 完成节点X → 解锁节点Y的前置条件 | node_dependencies |
| 成果级联 | 成果A未交付 → 下游B/C/D无法启动 | node_deliverables + dependencies |
| 人员协同 | 条线A的节点交付物是条线B的前置 | node_dependencies (跨 owner_dept) |

**文本格式示例**：
```
🔗 依赖：施工图完成 → 解锁3节点(桩基/基坑/材料采购)
⚠️ 阻塞：设计院图纸未出 → 3节点等待中
```

> 注意：层5内容较长，不常驻 Session prompt，仅在用户问及相关节点时按需注入。

#### 层6：知识认知

| 认知项 | 具体内容 | 数据源 |
|--------|----------|--------|
| SOP 覆盖 | 哪些业务场景有 SOP、哪些没有 | SkillRegistry |
| 知识库地图 | 有哪些知识集合、覆盖什么领域 | MaxKB 元数据 |
| 文件资产 | 项目文件数量和类型分布 | files 表统计 |
| 认知盲区 | 哪些领域知识缺失、哪些 SOP 未覆盖 | 对比项目需求 vs 现有覆盖 |

> 注意：层6大部分信息已在 Session prompt 中通过 `{sop_catalog}` + `{rag_info}` + `{available_tools}` 注入。层6额外补充的是"认知盲区"识别。

#### 层7：自省认知

| 认知项 | 具体内容 | 数据源 |
|--------|----------|--------|
| 初始化状态 | 项目处于哪级初始化、缺失哪些必备项 | initialization_check（见第五章） |
| 能力边界 | 能做什么（工具+Skill）、不能做什么 | available_tools + skill_registry |
| 处理质量 | SOP 命中率、Fallback 率、用户反馈 | evolution_daily_insights |

**文本格式示例**：
```
🟢 项目已激活（可运转级，12/12 必备项完成）
🟡 项目未激活（有组织级，7/12 必备项，缺失：节点树/里程碑截止日期/…）
```

## 四、认知进化闭环

### 4.1 核心机制

认知不是静态快照，而是通过**认知偏差检测**驱动的增量更新闭环：

```
                    ┌────────── 复盘总结 ──────────┐
                    │                              │
                    │  DailyInsight 周期性执行      │
                    │         ↓                    │
                    │  采集10个数据源指标            │
                    │  (9个系统指标 + 1个认知偏差)    │
                    │         ↓                    │
                    │  LLM 生成洞察                │
                    │         ↓                    │
                    │  检测到认知偏差？              │
                    │    是 → 更新世界书            │
                    │    否 → 跳过                  │
                    └──────────────────────────────┘
```

### 4.2 认知偏差检测（新增第 10 个数据源）

在现有 `collect_metrics()` 的 9 个数据源基础上，新增第 10 个：`cognition_drift`。

**偏差检测逻辑**（纯数据对比，无需 LLM，非常轻量）：

```python
def detect_cognition_drift(project_id: str) -> dict:
    """检测项目世界书与实际数据的偏差。"""
    world_book = ProjectWorldBookRepo.get_by_project(project_id)
    if world_book is None:
        return {"status": "missing", "message": "项目无世界书，需首次生成"}

    drift = {}
    layers = json.loads(world_book.content_json)

    if _ontology_changed(project_id, layers.get("ontology", {})):
        drift["ontology"] = {"stale": True, "signals": [...]}
    if _personnel_changed(project_id, layers.get("personnel", {})):
        drift["personnel"] = {"stale": True, "signals": [...]}
    if _structure_changed(project_id, layers.get("structure", {})):
        drift["structure"] = {"stale": True, "signals": [...]}
    if _temporal_changed(project_id, layers.get("temporal", {})):
        drift["temporal"] = {"stale": True, "signals": [...]}
    if _relation_changed(project_id, layers.get("relation", {})):
        drift["relation"] = {"stale": True, "signals": [...]}
    if _introspection_changed(project_id, layers.get("introspection", {})):
        drift["introspection"] = {"stale": True, "signals": [...]}

    return drift
```

**每层的偏差检测条件**：

| 层 | 偏差信号 | 检测方式 |
|----|---------|---------|
| 1.本体 | lifecycle_stage 变了 / 新增参建单位 | 对比 projects + company_info vs 世界书记录 |
| 2.人员 | users 表有角色变更 / 新增删除用户 | 对比 users.last_updated vs 世界书 updated_at |
| 3.结构 | 整体进度偏差 >5% / 逾期数变化 / 新节点 | 对比 project_nodes 聚合 vs 世界书 layer3 |
| 4.时间 | 近 N 天有新事件 / deadline 逼近 | 对比 events + nodes.deadline vs 世界书 layer4 |
| 5.关系 | 依赖链变更 | 对比 node_dependencies 最后更新时间 |
| 6.知识 | SOP/知识库变更 | 对比 SkillRegistry 版本号 |
| 7.自省 | 初始化层级变化 | 对比 initialization_status 各项 |

### 4.3 更新路径

#### 路径 A：数据驱动更新（无需 LLM，快）

适用于纯数据性偏差（进度数字变了、逾期数量变了、近期事件更新了）：

```
cognition_drift.structure.stale == True
  → 重新计算 node_overview / milestone_status / overdue_count
  → 只更新世界书的第3层（结构认知段）
  → 版本号 +1，拼接 full_text
```

涉及的层：层2、层3、层4、层5、层7

#### 路径 B：LLM 驱动更新（需 LLM，慢但语义深）

适用于语义性偏差（阶段迁移的含义、人员变更的影响、新风险识别）：

```
cognition_drift.ontology.stale == True
  → lifecycle_stage 从 1→2（规划→施工）
  → LLM 重新生成项目概述文本
  → 更新世界书的第1层
  → 版本号 +1
```

**决策规则**：数据驱动优先。只有当偏差涉及语义理解时才调 LLM。

## 五、项目初始化清单

### 5.1 四层初始化模型

项目从"Emily 知道它的存在"到"Emily 能有效辅助它的运转"，分四个层级。每级有对应的最小信息集合，只有满足上一级才能有效进入下一级：

| 层级 | 含义 | Emily 能做什么 | 必备项数 |
|------|------|---------------|---------|
| **T1 可识别** | Emily 知道有这个项目，且能通知到管理员 | 在被问到时能说出项目基本信息；自检结果能送达管理员 | 7 |
| **T2 有组织** | 知道谁参与了 | 能回答"这事找谁"，能按人推送 | 6 |
| **T3 可运转** | 有工作结构 | 能跟踪进度、提醒截止、记录事件 | 5 |
| **T4 充分运转** | 完整数据闭环 | 能主动预警、识别风险、引导流程 | 5 |

> 📝 以下必备项为 AI 基于工程建设行业知识生成的初始版本。项目管理者应根据实际管理需要审核和修改。修改方式：编辑本文件或通过 CLI/API 更新。

### 5.2 T1 可识别 — 必备项（7项）

| # | 必备项 | 数据源 | 判定条件 |
|---|--------|--------|---------|
| T1-1 | 项目名称 | projects.name | 非空且非默认值 |
| T1-2 | 项目编号 | projects.code | 非空（如 ECOCITY-26） |
| T1-3 | 项目地址 | projects.address | 非空 |
| T1-4 | 项目类型 | projects.description 或业务字段 | 能区分住宅/商业/文旅/综合体 |
| T1-5 | 生命周期阶段 | projects.lifecycle_stage | 非0（0=未设定） |
| T1-6 | 项目管理员账户 | users (is_admin=True 或 project admin 角色) | 至少1个管理员用户关联到项目 |
| T1-7 | 管理员邮箱 | users.email 或通知配置 | 至少1个管理员有可用的邮箱地址 |

**T1-6/T1-7 的设计原因**：冷启动自检结果必须能通过邮件送达管理员。没有管理员账户→不知道通知谁；没有邮箱→通知无法送达。这两项是自检→邮件→引导这个闭环的**起点**，没有它们，整个元认知流程无法闭合。

**不满足 T1 的后果**：
- 缺 T1-1~T1-5：Emily 无法识别该项目，不会主动提及
- 缺 T1-6 或 T1-7：Emily 能识别项目但**无法通知管理员**，自检结果仅写入日志，无法送达

### 5.3 T2 有组织 — 必备项（6项）

| # | 必备项 | 数据源 | 判定条件 |
|---|--------|--------|---------|
| T2-1 | 建设单位（甲方） | company_info 关联 | 至少1个 type=建设单位 的公司关联到项目 |
| T2-2 | 项目管理/代建单位 | company_info 关联 | 至少1个 type=代建单位 的公司关联到项目 |
| T2-3 | 施工总承包单位 | company_info 关联 | 至少1个 type=施工单位 的公司关联到项目 |
| T2-4 | 监理单位 | company_info 关联 | 至少1个 type=监理单位 的公司关联到项目 |
| T2-5 | 项目经理 | users 关联 | 至少1个用户角色为项目经理且绑定到项目 |
| T2-6 | 总监理工程师 | users 关联 | 至少1个用户角色为总监理且绑定到项目 |

**不满足 T2 的后果**：Emily 无法回答"这事找谁"，按规则书第五章§4，阻断录入类操作，仅允许基本查询。

### 5.4 T3 可运转 — 必备项（5项）

| # | 必备项 | 数据源 | 判定条件 |
|---|--------|--------|---------|
| T3-1 | 节点树已创建 | project_nodes | 至少存在1个 MILESTONE 类型节点 |
| T3-2 | 关键里程碑有截止日期 | project_nodes.deadline | MILESTONE 节点 deadline 非空 |
| T3-3 | 关键节点有责任人 | project_nodes.responsible_user_id | MILESTONE + WORK_PACKAGE 节点 responsible_user_id 非空 |
| T3-4 | 至少1个适配SOP | SkillRegistry | 至少1个 Skill 的 sop_id 与项目匹配 |
| T3-5 | 项目经理已绑定IM | user_im_bindings | 项目经理有 napcat 平台绑定 |

**达到 T3 的意义**：Emily 全面启用——可跟踪进度、提醒截止、记录事件、引导SOP流程。`is_activated = True`。

### 5.5 T4 充分运转 — 必备项（5项）

| # | 必备项 | 数据源 | 判定条件 |
|---|--------|--------|---------|
| T4-1 | 全部参建单位已录入 | company_info 关联 | 无 type 对应的公司缺失（设计/分包等） |
| T4-2 | 全部节点有责任人 | project_nodes | 无 responsible_user_id 为空的活跃节点 |
| T4-3 | 节点依赖关系已建立 | node_dependencies | 至少50%的 WORK_PACKAGE 节点有依赖记录 |
| T4-4 | 知识库已填充项目资料 | RAG / files | 项目关联文件数 ≥5 |
| T4-5 | 晨报已成功发送至少1次 | scheduler_job_logs | morning_report handler 有成功记录 |

**达到 T4 的意义**：Emily 可主动预警风险、识别依赖阻塞、引导流程闭环——真正成为"项目团队公共大脑"。

### 5.6 初始化引导机制

Emily 感知项目当前初始化层级，在对话中主动引导管理员完成缺失项：

- 世界书 `content_text` 末尾标记当前层级和缺失项
- 当用户（尤其是管理员）与 Emily 交互时，Emily 可根据缺失项主动询问
- 调度器定期检查初始化层级变化，变更时通知管理员

**标记格式**：
```
🟡 T2 有组织级（13/23 必备项）
缺失：节点树未创建 / 里程碑无截止日期 / ...
→ 可对 Emily 说"帮我完成初始化"开始引导
```

## 六、项目启动时的元认知流程

### 6.1 触发时机

- EmilyCore 启动（`_ensure_initialized()` 末尾）
- 管理员手动触发（API / CLI）
- 新项目创建后

### 6.2 元认知数据收集与判断流程

```
项目启动
  │
  ├─ ① 加载规则书
  │     → 读取 emily-data/rules/规则书.md
  │     → 注入系统级行为约定
  │
  ├─ ② 查询 projects 表，获取所有 active 项目
  │
  └─ ③ 对每个项目执行元认知判断：
        │
        ├─ 世界书是否存在？
        │    否 → 调用 build_world_book.py 生成
        │    是 → 继续
        │
        ├─ 世界书与项目信息匹配度检查
        │    → 调用 detect_cognition_drift.py
        │    → 有偏差 → 调用 update_world_book.py 补充
        │    → 世界书不足 → 自动使用构建脚本补充
        │
        ├─ 项目初始化判断
        │    → 调用 check_initialization.py
        │    → 输出 T1-T4 层级和缺失项
        │
        └─ 自检结果邮件通知
             → 有管理员邮箱？→ 发送自检报告邮件
             │   邮件内容：项目状态 + 初始化层级 + 缺失项清单
             → 无管理员邮箱？→ 仅写入日志 + 世界书标记
             → 邮件发送失败？→ 仅写入日志 + 世界书标记（fail-open）
```

### 6.3 自检邮件通知

#### 触发时机
- EmilyCore 启动时（每个 active 项目）
- 管理员手动触发自检后
- 项目初始化层级发生变化时

#### 邮件内容

```
Emily 项目自检报告
═══════════════════════════════════
项目：生态城26#地（ECOCITY-26）
检查时间：2026-07-10 08:00:00+08:00
初始化层级：T2 有组织（13/23 必备项）
═══════════════════════════════════

✅ T1 可识别（7/7）
  ✓ 项目名称 / 编号 / 地址 / 类型 / 生命周期阶段
  ✓ 管理员账户 / 管理员邮箱

✅ T2 有组织（6/6）
  ✓ 建设单位 / 代建单位 / 总包 / 监理
  ✓ 项目经理 / 总监理

❌ T3 可运转（0/5）
  ✗ 节点树未创建
  ✗ 里程碑无截止日期
  ✗ 关键节点无责任人
  ✗ 无适配 SOP
  ✗ 项目经理未绑定 IM

⏳ T4 充分运转（0/5）
  （需先完成 T3）

═══════════════════════════════════
📋 下一步：对 Emily 说"帮我完成初始化"开始引导
```

#### 闭环保障

```
管理员账户 + 邮箱（T1-6/T1-7）
        ↓
冷启动自检 → 发现缺失项
        ↓
邮件送达管理员 ← 如果此环节断裂（无邮箱/发送失败），降级到日志+世界书标记
        ↓
管理员获知缺失项，与 Emily 交互补充
        ↓
下次自检 → 层级提升 → 新的邮件通知
```

**关键设计**：T1-6（管理员账户）和 T1-7（管理员邮箱）是整个闭环的起点。没有它们，后续所有通知和引导都无法送达。因此它们被放在 T1（最低层级），确保最早被检查。

### 6.4 关键行为

1. **世界书不足可自行补充**：检测到世界书缺失或偏差时，直接调用 `build_world_book.py` / `update_world_book.py` 补充，无需人工干预
2. **自检结果邮件送达**：自检完成后必须尝试邮件通知管理员。邮件发送失败不阻塞系统（fail-open），但世界书中标记"管理员未收到通知"
3. **初始化判断阻断**：关键信息缺失时标记为未激活，Emily 在对话中会主动提醒而非静默跳过
4. **规则书始终加载**：无论项目状态如何，规则书作为系统级行为约定始终注入

## 八、交付物：独立脚本 + 薄聚合

### 8.1 架构原则

- **每个脚本可独立执行**：支持 `--dry-run` 模式，输出到终端便于观察和排查
- **薄聚合脚本**仅串联各独立脚本的入口，不包含业务逻辑
- **数据库为接口**：模块间通过 `project_world_books` 表衔接，不直接 import 彼此

### 8.2 独立脚本清单

| # | 脚本 | 职责 | 关键参数 | dry-run 输出 |
|---|------|------|---------|-------------|
| 1 | `build_world_book.py` | 构建/重建单个项目的世界书 | `--project-id` `--layer` `--dry-run` | content_json 和 content_text 预览 |
| 2 | `detect_cognition_drift.py` | 检测项目世界书与实际数据的偏差 | `--project-id` `--all` `--dry-run` | 各层偏差检测结果 |
| 3 | `update_world_book.py` | 根据偏差增量更新世界书 | `--project-id` `--all` `--dry-run` | 将要更新的层和变更内容 |
| 4 | `check_initialization.py` | 检查项目初始化层级和缺失项 | `--project-id` `--all` `--dry-run` | T1-T4 各层必备项完成情况 |
| 5 | `generate_session_prompt.py` | 为指定用户生成 Session prompt（世界书+规则书） | `--user-id` `--dry-run` | 将注入的 prompt 段预览 + token 估算 |
| 6 | `self_check.py` | 系统级自检（复用 V1） | `--dry-run` | 用户/项目/业务量/知识库统计 |

### 8.3 薄聚合脚本

| # | 脚本 | 职责 | 串联逻辑 |
|---|------|------|---------|
| 7 | `cold_start.py` | 冷启动流程编排 | self_check → check_initialization → build_world_book → 邮件通知 |
| 8 | `cognition_cycle.py` | 认知进化周期执行 | detect_cognition_drift → update_world_book → 汇总日志 |

### 8.4 规则书文件

| 文件 | 说明 |
|------|------|
| `emily-data/rules/规则书.md` | 系统级行为约定，人类可读可编辑，Emily 启动时加载注入 |

### 8.5 脚本交互关系

```
cold_start.py（薄聚合）
  ├── self_check.py           → 系统级自检数据
  ├── check_initialization.py → 项目初始化层级
  ├── build_world_book.py     → 首次构建世界书
  └── 邮件通知                 → 发送启动报告

cognition_cycle.py（薄聚合）
  ├── detect_cognition_drift.py → 偏差检测
  └── update_world_book.py      → 增量更新

EmilyCore._ensure_initialized()（运行时集成）
  ├── 加载 emily-data/rules/规则书.md → {rule_book}
  ├── ProjectWorldBookService.init()
  │     └── 内部调用 build_world_book 逻辑
  └── SessionContext.create()
        └── 内部调用 generate_session_prompt 逻辑

SchedulerEngine._tick()（运行时集成）
  └── ProjectWorldBookUpdateHandler
        └── 内部调用 cognition_cycle 逻辑
```

### 8.6 独立脚本接口约定

每个独立脚本遵循统一模式（参照 `scripts/collect_session_data.py`）：

```python
# 1. 文件头 docstring：定位 + 用法 + 输出格式
# 2. sys.path 设置 + _init_db_if_needed()
# 3. 核心函数：xxx.run() → dict（结构化结果）
# 4. CLI 入口：--dry-run 预览模式
# 5. 永不崩溃：独立 try/except，失败记录 warnings
```

## 十、模块化实现清单

按模块逐个实现，每个模块独立可用：

| 模块 | 交付物 | 依赖 | 可独立验证 |
