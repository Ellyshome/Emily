## 一、模块定位与价值

### 1.1 解决什么问题

Emily 定位为"项目团队公共大脑"，但存在两个根本性缺失：

1. **认知断层**：SessionAgent 对项目缺乏全面认知——它只知道自己服务的项目名和状态，不知道项目的人员架构、节点进度、关键里程碑、当前风险。数据存在但未被组织成 AI 可理解的上下文。
2. **行为无约束**：Emily 没有系统级的行为约定——它不知道自己在组织中应该主动做什么、不该做什么、遇到边界情况如何处理。

### 1.2 一句话总结

**规则书**回答"我该怎么做"，**世界书**回答"我知道什么"，**元认知判断**回答"项目信息齐不齐"。

### 1.3 与系统其他模块的关系

## 二、三层架构

### 2.1 总体结构

| 层 | 名称 | 存储位置 | 更新方式 | 生命周期 | 注入变量 |
|----|------|----------|----------|----------|----------|
| 顶层 | 规则书 | `emily-data/rules/规则书.md` | 人工编辑 → 热重载 | 系统级（全局一份） | `{rule_book}` |
| 中层 | 世界书 | `project_world_books` 表 | 偏差检测 → 增量更新 | 项目级（每项目一份） | `{project_world_book}` |
| 底层 | 元认知判断 | `project_world_books.initialization_*` 字段 | 初始化检查 | 项目级 | 世界书内嵌 |

### 2.2 各层职责

**规则书**——AI 与人的组织约定（系统级行为宪法）：
- 8 章 41 条明文约定，涵盖身份边界、主动行为、信息处理、权限安全、初始化引导、沟通风格、数据一致性、错误处理
- 人类可直接阅读和编辑 `emily-data/rules/规则书.md`
- 规则书与初始化清单联动：清单定义"什么叫齐了"，规则书定义"不齐怎么办"

**世界书**——项目七层认知（数据驱动的项目理解）：
- 七层结构化 JSON（content_json）+ 纯文本摘要（content_text）
- 偏差检测驱动增量更新，保持与实际数据同步
- 纯文本摘要直接注入 Session prompt，目标 300-500 字（~100-170 tokens）

**元认知判断**——项目启动时的数据收集与初始化判断：
- 四层初始化模型（T1-T4，23 项必备项）
- 不齐 → 引导补充；缺关键信息 → 阻断标记
- 世界书不足可自行补充（调用构建脚本）

## 三、数据结构

### 3.1 数据库表：`project_world_books`

| 字段 | 类型 | 说明 | 分类 |
|------|------|------|------|
| `id` | String PK | UUID | 标识 |
| `project_id` | String FK→projects.id | 项目归属（**UNIQUE**，每项目一份） | 标识 |
| `version` | Integer | 整体版本号（递增） | 版本 |
| `content_json` | Text | 七层结构化 JSON（机器可解析） | 认知数据 |
| `content_text` | Text | 纯文本摘要（直接注入 prompt） | 认知数据 |
| `layer_versions` | Text | JSON：每层独立版本号 `{"ontology":3,"personnel":5,...}` | 版本 |
| `initialization_tier` | Integer | 当前初始化层级 0-4 | 元认知判断 |
| `initialization_status` | Text | JSON：各必备项完成情况 | 元认知判断 |
| `is_activated` | Boolean | 是否达到 T3 可运转级 | 元认知判断 |
| `token_count` | Integer | 估算 token 数 | 统计 |
| `generated_at` | String | 最近生成时间 | 元数据 |
| `generated_by` | String(50) | 生成来源：`startup` / `scheduler_data` / `scheduler_llm` / `manual` | 元数据 |
| `created_at` | String | 首次创建时间 | 元数据 |
| `updated_at` | String | 最近更新时间 | 元数据 |

**关键设计决策**：
- `project_id` 为 UNIQUE——每项目最多一份世界书
- `content_json` 与 `content_text` 分离——JSON 供程序解析，text 供 LLM 消费
- `layer_versions` 支持单层版本追踪——偏差检测后只更新过时层

### 3.3 content_text 格式规范

纯文本摘要控制在 300-500 字（~100-170 tokens），按层拼接：

```
📋 项目：生态城26#地（ECOCITY-26）
📍 XX市XX区 ｜ 阶段：工程施工 ｜ 代建：蓝城伟业
🏗 总包：XX建设 / 监理：XX监理

👥 张工(项目经理) / 李总(总监理)

📊 120节点：35完成 / 45进行中 / 5逾期 ｜ 整体29.2%
🏁 基础工程✓ ｜ 主体封顶60%(8.30)

📝 近期：7.9样板段放线完成
⏰ 7天内：消防验收资料(7.15)
🔴 逾期：外墙保温(7.5)

🟡 T2 有组织级 — 缺失：里程碑无截止日期 / ...
```

**格式规则**：
- 层5（关系）和层6（知识）不常驻，仅在检测到阻塞或盲区时追加
- 层7 初始化状态始终显示
- 日期只显示月.日（如 `7.15`），不显示年份
- 里程碑用 ✓ 表示完成，否则显示进度百分比

## 六、四层初始化模型

### 6.1 层级定义

| 层级 | 含义 | Emily 能做什么 | 必备项数 | is_activated |
|------|------|---------------|---------|-------------|
| T1 可识别 | 知道有这个项目 | 回答项目基本信息；自检结果能送达管理员 | 7 | False |
| T2 有组织 | 知道谁参与了 | 回答"这事找谁"，按人推送 | 6 | False |
| T3 可运转 | 有工作结构 | 跟踪进度、提醒截止、记录事件 | 5 | **True** |
| T4 充分运转 | 完整数据闭环 | 主动预警、识别风险、引导流程 | 5 | True |

### 6.2 23 项必备项详情

**T1 可识别（7 项）**：

| # | 必备项 | 数据源 | 判定条件 | 缺失影响 |
|---|--------|--------|---------|---------|
| T1-1 | 项目名称 | `projects.name` | 非空且非"未命名项目" | 无法识别项目 |
| T1-2 | 项目编号 | `projects.code` | 非空 | 无法唯一标识 |
| T1-3 | 项目地址 | `projects.address` | 非空 | 无法定位项目 |
| T1-4 | 项目类型 | `projects.description` 或 `lifecycle_stage` | 能区分项目类型 | 无法分类处理 |
| T1-5 | 生命周期阶段 | `projects.lifecycle_stage` | 非 0 | 无法判断项目阶段 |
| T1-6 | 管理员账户 | `users.is_admin=True` | 至少 1 个管理员关联项目 | **闭环起点**——无法通知 |
| T1-7 | 管理员邮箱 | `users.email` | 至少 1 个管理员有邮箱 | **闭环起点**——通知无法送达 |

**T2 有组织（6 项）**：

| # | 必备项 | 数据源 | 判定条件 |
|---|--------|--------|---------|
| T2-1 | 建设单位 | `company_info.type` | 含"建设单位" |
| T2-2 | 代建/管理单位 | `company_info.type` | 含"代建单位"或"建设单位" |
| T2-3 | 施工总承包单位 | `company_info.type` | 含"施工单位"或"总包" |
| T2-4 | 监理单位 | `company_info.type` | 含"监理单位"或"监理" |
| T2-5 | 项目经理 | `users.position` JSON | 含"项目经理" |
| T2-6 | 总监理工程师 | `users.position` JSON | 含"总监理工程师"或"总监理" |

**T3 可运转（5 项）**：

| # | 必备项 | 数据源 | 判定条件 |
|---|--------|--------|---------|
| T3-1 | 节点树已创建 | `project_nodes` | 至少 1 个 MILESTONE 类型节点 |
| T3-2 | 里程碑有截止日期 | `project_nodes.deadline` | MILESTONE 节点 deadline 非空 |
| T3-3 | 关键节点有责任人 | `project_nodes.responsible_user_id` | MILESTONE + WORK_PACKAGE 节点责任人非空 |
| T3-4 | 至少 1 个适配 SOP | `SkillRegistry` | 至少 1 个 Skill |
| T3-5 | 项目经理已绑定 IM | `user_im_bindings` | 项目经理有 napcat 平台绑定 |

**T4 充分运转（5 项）**：

| # | 必备项 | 数据源 | 判定条件 |
|---|--------|--------|---------|
| T4-1 | 全部参建单位 | `company_info.type` | 含建设/代建/施工/监理/设计 |
| T4-2 | 全部节点有责任人 | `project_nodes` | 活跃节点责任人非空 |
| T4-3 | 依赖关系覆盖 | `node_dependencies` | ≥50% 的 WORK_PACKAGE 有依赖记录 |
| T4-4 | 知识库已填充 | `files` | 项目关联文件 ≥5 |
| T4-5 | 晨报已发送 | `scheduler_job_logs` | morning_report handler 有成功记录 |

### 6.3 层级计算规则

```python
tier = 0
if T1_done >= T1_total:    # T1 全部完成
    tier = 1
if tier >= 1 and T2_done >= T2_total:   # T2 全部完成
    tier = 2
if tier >= 2 and T3_done >= T3_total:   # T3 全部完成
    tier = 3
    is_activated = True                  # 达到可运转级
if tier >= 3 and T4_done >= T4_total:   # T4 全部完成
    tier = 4
```

**关键规则**：层级是**累进**的——必须完成上一级全部项才能进入下一级。不存在"跳级"。

## 七、认知进化闭环

### 7.1 偏差检测机制

每层的偏差检测条件：

| 层 | 偏差信号 | 检测方式 | 更新路径 |
|----|---------|---------|---------|
| 1.本体 | lifecycle_stage 变了 / 新增参建单位 | 对比 projects + company_info vs 世界书 | **LLM 驱动**（语义理解） |
| 2.人员 | 用户数变化 | 对比 users.count vs 世界书 | 数据驱动 |
| 3.结构 | 进度偏差 >5% / 逾期数变化 / 新节点 | 对比 project_nodes 聚合 vs 世界书 | 数据驱动 |
| 4.时间 | 近期有新事件 | 对比 events.count vs 世界书 | 数据驱动 |
| 5.关系 | 依赖链变更 | 对比 node_dependencies.count vs 世界书 | 数据驱动 |
| 6.知识 | SOP/知识库变更 | 对比 SkillRegistry 版本 | 按需检测 |
| 7.自省 | 初始化层级变化 | 重新运行 InitializationChecker | 数据驱动 |

### 7.2 更新策略

当前实现采用**重建策略**（而非逐层修补）：

- **原因**：七层数据相互关联（如层3的逾期数依赖层4的时间数据），逐层修补可能导致层间引用不一致
- **实现**：检测到偏差后，调用 `ProjectWorldBookBuilder.build()` 重建全部七层，然后整体写入
- **未来优化**：可改为只重建过时层，但需确保层间一致性

### 7.3 数据源分类

| 更新路径 | 适用层 | 是否需要 LLM | 速度 |
|---------|--------|-------------|------|
| 数据驱动 | 层2/3/4/5/7 | 否 | 快（<1s） |
| LLM 驱动 | 层1（项目概述语义变更时） | 是 | 慢（2-5s） |

**决策规则**：数据驱动优先。只有当偏差涉及语义理解时才调 LLM。

### 8.1 文件加载路径

多级 fallback 路径查找：

- `RuleBookLoader.reload()` 重新读取文件
- 通过 `EmilyCore.reload_rule_book()` API 触发
- 规则书文件缺失时降级为空字符串（**不阻塞系统**，fail-open）

```

  └── 定义 T1-T4 各层的具体必备项和判定条件
```

## 十、冷启动流程

### 10.1 触发时机

- EmilyCore 启动（`_ensure_initialized()` 末尾的 `_init_meta_cognition()`）
- 管理员手动触发（`scripts/cold_start.py`）
- 新项目创建后

### 10.2 流程步骤

```
cold_start.py（薄聚合）
  │
  ├── [1/4] self_check.py       → 系统级自检数据
  │     统计：用户/项目/业务量/知识库/世界书
  │
  ├── [2/4] check_initialization → 项目初始化层级
  │     遍历所有 active 项目，执行 23 项检查
  │
  ├── [3/4] build_world_book     → 首次构建世界书
  │     仅对无世界书的项目构建
  │     已存在的项目跳过（由偏差检测机制维护）
  │
  └── [4/4] 邮件通知             → 自检报告送达管理员
        管理员有邮箱 → 发送自检报告
        无邮箱/发送失败 → 仅写日志（fail-open）
```

### 10.3 自检邮件闭环

```
管理员账户 + 邮箱（T1-6/T1-7）
        ↓
冷启动自检 → 发现缺失项
        ↓
邮件送达管理员 ← 如果此环节断裂，降级到日志+世界书标记
        ↓
管理员获知缺失项，与 Emily 交互补充
        ↓
下次自检 → 层级提升 → 新的邮件通知
```

**关键设计**：T1-6（管理员账户）和 T1-7（管理员邮箱）是整个闭环的起点。没有它们，后续所有通知和引导都无法送达。因此它们被放在 T1（最低层级），确保最早被检查。

## 十一、开发指南

### 11.1 新增偏差检测条件

1. 打开 `cognition_drift_detector.py`

### 11.5 常见问题

| 问题 | 原因 | 解决 |
|------|------|------|
| 世界书为空 | 项目无活跃用户/节点 | 先完成初始化再构建 |
| 规则书加载为空 | 文件路径不正确 | 检查容器内 `/app/rules/` 是否存在 |
| 偏差检测全 False | 世界书刚构建，数据一致 | 正常，等数据变化后再检测 |
| 初始化层级始终为 0 | 项目缺少基本信息 | 先填写项目名称/编号/地址等 T1 项 |
| `__pycache__` 不刷新 | Docker bind-mount 不触发重编译 | `docker exec emily-core find /app/emily_core -name '__pycache__' -type d -exec rm -rf {} +` |
