# Emily 元认知模块 — 系统自我描述需求规格

> **版本**：V1
> **模块名称**：系统自我描述（System Self-Description）
> **归属模块**：元认知模块（Meta-cognition Module）
> **前置文档**：[自我认知需求规格 V3](自我认知需求规格.md)
> **核心问题**：SessionAgent 对自身系统结构（数据库/文件/权限）缺乏认知，导致"知道自己能访问什么，但不知道为什么、怎么用、有什么关联"

---

## 一、问题定义

### 1.1 核心症状

SessionAgent 对以下条目缺乏可操作的认知：

| 认知条目 | 当前状态 | 缺失程度 |
|----------|----------|----------|
| 数据库有哪些表 | 仅 10/53 表名可见 | 🔴 严重缺失 |
| 数据库 Schema 架构（字段结构） | 完全没有 | 🔴 完全缺失 |
| 数据库各字段的功能与意义 | 完全没有 | 🔴 完全缺失 |
| 文件各字段的意义 | 完全没有 | 🔴 完全缺失 |
| 文件分类原则与意义 | 仅有分类名称统计 | 🟡 表面认知 |
| 人员权限分级原则与目的 | 仅有自身标签 + 规则书规则 | 🟡 结构性缺失 |

**一句话**：当前 SessionAgent 的认知是**标签级**的——它知道自己能访问什么、叫什么名字，但**不知道为什么、怎么用、有什么关联**。像一个拿到了图书馆门禁卡但完全看不懂索书号和分类法的读者。

### 1.2 现有机制逐项审查

#### 1.2.1 `{visible_schema}` — 可查询的数据库

**来源**：`SessionDataFetcher` → `fetch_visible_schema.py` → `db_perms` 权限过滤

**当前输出**：
```
· 事件表: 读写
· 任务表: 只读
```

**问题**：
- 硬编码 10 张表的中文映射（`fetch_visible_schema.py:39-50`），数据库实际有 53 张表
- 仅展示表名 + 权限级别（读写/只读），无任何字段信息
- 用户没有 `db_perms` 的表完全不可见

**硬编码的 10 表映射**：
```python
table_names = {
    "project": "项目表", "events": "事件表", "tasks": "任务表",
    "meetings": "会议表", "files": "文件表", "messages": "消息表",
    "users": "用户表", "financial": "财务表", "project_nodes": "节点表",
    "node_deliverables": "节点成果表",
}
```

#### 1.2.2 `{visible_files}` — 可访问的文件

**来源**：`fetch_visible_files.py` → `SessionAccessibleFileRepo.get_file_summary()`

**当前输出**：
```
共 23 个文件（施工图(8个), 报告(5个), 规范(3个), 其他(7个)），分类：...
```

**问题**：
- 只有数量统计和类型分布
- 无分类规则说明、无字段语义、无访问逻辑

#### 1.2.3 `{user_permission_level}` — 用户权限

**来源**：`level.py:level_label()` → 生成如"管理员(L5)"

**当前输出**（注入 session.md）：
```
权限：管理员(L5)
```

**问题**：
- 仅一行文字标签
- 6 级树形继承结构（参建线 L1→L2→L3 / 建设线 L1→L4→L5→L6）不注入
- 两线在 L1 后分叉的设计意图不注入
- 跨线访问通过 `PermissionGrant` 解决的机制不注入
- L4 建设主管不继承 L2 参建执行权限的业务语义不注入

#### 1.2.4 `{rule_book}` — 规则书

**来源**：`emily-data/rules/规则书.md` → `RuleBookLoader`

**已有内容**：八类行为约定（身份与边界、主动行为、信息处理、权限与安全、初始化、沟通风格、数据完整、异常处理）

**问题**：规则书解决的是"我该怎么做"（行为准则），不解决"我自身是什么结构"（系统知识）。它告诉 Emily"不越权"，但没告诉 Emily"越权的边界具体长什么样"。

### 1.3 根因分析

信息在代码/文档/数据库中已经存在，但**没有桥接到 Prompt**：

| 知识源 | 现状 | 是否被 LLM 消费 |
|--------|------|-----------------|
| `models.py`（53 表完整字段） | 代码存在 | ❌ |
| `docs/数据库设计.md` | 文档存在 | ❌ |
| `PublicFieldRegistry` 表 | 表结构存在 | ❌ 未采集注入 |
| `FileCategory` 枚举 | 代码存在 | ❌ 仅 display 名注入 |
| `PermissionLevel` + `INHERITANCE_CHAIN` | 代码存在 | ❌ 仅 level_label 注入 |
| `规则书.md` | 文件存在 | ✅ 全文注入 |
| `project_world_book` | 表存在 | ✅ 内容注入 |

**核心断裂**：数据库 schema 知识、字段语义、权限体系结构——这些信息在系统内部已经存在，但没有任何机制将它们转化为 LLM 可消费的 prompt 片段。

## 二、架构决策：归属元认知模块

### 2.1 决策结论

**系统自我描述应归属元认知模块统一管理，但作为独立的第三类知识（与规则书、世界书并列），而非塞进世界书。**

### 2.2 决策理由

#### 理由一：三类知识构成完整的自我认知

```
元认知模块
├── 规则书     → 我应该怎么做事（规范层 / Ought）
├── 世界书     → 我服务的项目现在怎么样（经验层 / Is-External）
└── 系统描述书 → 我自己是什么结构（自省层 / Is-Internal）
```

哲学上这是一个完整的认知三角：**规范知识 + 外部经验知识 + 内省知识**。拆出去反而破坏了概念的完整性。

#### 理由二：三阶段闭环机制可复用

元认知模块的核心模式是领域无关的：

```
构建表征（Build）→ 检测偏差（Detect）→ 增量更新（Update）
```

| 闭环阶段 | 世界书实现 | 系统描述书可复用 |
|----------|-----------|-----------------|
| 构建 | `ProjectWorldBookBuilder._build_*()` | `SystemDescriptionBuilder._build_schema()`, `_build_permissions()`, `_build_file_rules()` |
| 偏差检测 | `CognitionDriftDetector`（比对 DB 数据 vs 世界书快照） | `SchemaDriftDetector`（比对 `Base.metadata` hash vs 存储的描述快照） |
| 增量更新 | `ProjectWorldBookService.update_stale()` | `SystemDescriptionService.update_if_stale()` |
| 调度触发 | `WorldBookUpdateHandler`（日级） | `SystemDescriptionUpdateHandler`（启动时 + 迁移后） |

#### 理由三：进化闭环可以统一

现有的进化子系统：
```
DailyInsight → RuleInduction → PatchValidation → RuleBook 热更新
```

系统描述书加入后形成第二条闭环：
```
SchemaDrift 检测 → 描述书自动重建 → prompt 变量热更新 → Session 刷新
```

如果拆出去独立管理，就需要另起一套调度、检测、热重载基础设施——重复造轮子。

### 2.3 为什么不能塞进世界书

1. **作用域冲突**：世界书是 per-project 的，系统描述是 global 的。53 张表的描述不因项目不同而改变
2. **更新频率冲突**：世界书日级更新，系统描述月级甚至季度级更新。混在一起会导致：要么系统描述被日级全量重建（浪费），要么世界书被系统描述的重建拖慢
3. **偏差检测逻辑完全不同**：世界书偏差是"查 DB 数量/状态 vs 世界书记录"，系统描述偏差是"查 `Base.metadata.tables` 的 hash vs 存储的描述 hash"——强耦合会让两个检测器都变脏

### 2.4 元认知模块新三层架构

```
┌─────────────────────────────────────────────────────┐
│                    规则书                              │
│   AI 与人的组织约定（系统级行为宪法）                    │
│   回答：我该怎么做、不该怎么做、边界情况如何处理         │
│   变化频率：低（人工编辑）                              │
│   作用域：全局唯一                                     │
│   注入变量：{rule_book}                               │
├─────────────────────────────────────────────────────┤
│                    世界书                              │
│   项目七层认知（数据驱动的项目理解）                     │
│   回答：这是什么项目、谁负责、走到哪了、有什么风险       │
│   变化频率：高（日级数据驱动更新）                       │
│   作用域：按项目隔离                                   │
│   注入变量：{project_world_book}                      │
├─────────────────────────────────────────────────────┤
│                 系统描述书（新增）                       │
│   系统自身结构与能力描述（代码驱动的自我认知）            │
│   回答：我内部有什么资源、怎么用、为什么这样设计          │
│   变化频率：极低（仅在部署/迁移/配置变更时更新）          │
│   作用域：全局唯一                                     │
│   注入变量：{system_description}                      │
└─────────────────────────────────────────────────────┘
```

三种知识的对比：

| 维度 | 规则书 | 世界书 | 系统描述书 |
|------|--------|--------|-----------|
| 认知对象 | 行为规范（Ought） | 项目业务现实（Is-External） | 系统自身结构（Is-Internal） |
| 真理来源 | 人类编写 | 业务数据内容 | 代码与配置 |
| 变化频率 | 人工编辑时 | 日级 | 部署/迁移时 |
| 作用域 | 全局 | per-project | 全局 |
| 偏差模式 | 无（无自动检测） | 数据 vs 记录 | 代码 vs 描述 |
| 更新触发 | 人工编辑 → 重载 | 调度器日级检测 | 启动校验 + 迁移触发 |

## 三、系统描述书内容规格

### 3.1 概述

系统描述书包含三个知识域，每个域独立构建、独立版本、独立更新：

| 域 | 名称 | 回答的问题 | 变化触发 |
|----|------|-----------|---------|
| D1 | 数据库认知 | 我有什么表、每个表什么字段、字段什么意思 | `models.py` 变更 / 新增表或字段 |
| D2 | 文件认知 | 文件怎么分类、分类规则是什么、各字段含义 | `FileCategory` 枚举变更 / 文件模型变更 |
| D3 | 权限认知 | 权限怎么分级、为什么这样分、继承规则是什么 | `PermissionLevel` / `INHERITANCE_CHAIN` 变更 |

### 3.2 D1：数据库认知

#### 3.2.1 当前缺陷

- 仅 10/53 表名可见，且为硬编码
- 无字段级信息（名称、类型、含义、必填/可选）
- 无表间关系（FK、一对一、一对多）
- LLM 无法判断"遇到 X 问题该查哪张表的哪个字段"

#### 3.2.2 目标内容

**第一层：表清单 + 权限标注**

按 `db_perms` 分为用户可见和不可见两组。可见表标注权限级别（读写/只读），不可见表仅列名不暴露字段细节。

```
📊 数据库资源（你有权访问的表）
· 事件表(events): 读写 — 记录项目现场发生的事件
· 任务表(tasks): 只读 — 跟踪工作任务的执行情况
· 会议表(meetings): 读写 — 记录会议安排和纪要
...
📊 其他系统表（共 N 张，按权限不可直接查询）
```

**第二层：可见表的核心字段摘要**

每张可见表提取 5-10 个核心字段（非全部字段），格式：

```
事件表(events) — 记录项目现场发生的事件
  · title(文本,必填): 事件标题/简要描述
  · event_type(枚举,必填): 事件类型（施工进展/质量安全/材料/设计变更/会议/其他）
  · event_date(日期): 事件发生日期
  · created_by(关联→users): 记录人
  · project_id(关联→projects): 所属项目
```

**第三层：关键表间关系**

仅标注与业务查询最相关的关系：

```
🔗 表间关系
· events.project_id → projects.id（每个事件属于一个项目）
· tasks.node_id → project_nodes.node_id（每个任务关联一个全景节点）
· files.category → FileCategory 枚举（文件按分类体系归档）
· users.company → company_info.id（用户归属参建单位）
```

#### 3.2.3 数据源

| 数据 | 来源 | 采集方式 |
|------|------|---------|
| 表清单 | `Base.metadata.tables` | 反射 ORM 元数据 |
| 字段名/类型 | `Column` 属性 | 反射 ORM 元数据 |
| 字段含义 | `PublicFieldRegistry` 表 + ORM `comment` | 查询 DB + 反射 |
| 表间关系 | `ForeignKey` + `relationship` | 反射 ORM 元数据 |
| 用户权限 | `db_perms`（来自 `PermissionService`） | 已有机制 |

#### 3.2.4 字段含义的采集策略

当前 `PublicFieldRegistry` 表结构已定义但未被使用：

```python
class PublicFieldRegistry(Base):
    __tablename__ = "public_field_registry"
    model_name = Column(String(100))    # "Project" / "Event"
    field_name = Column(String(100))    # "name" / "area"
    description = Column(String(500))   # 字段含义描述
```

**采集策略（三层 fallback）**：

1. **优先**：`PublicFieldRegistry` 表中已登记的 `description`（最权威，人工维护）
2. **次选**：ORM `Column.comment` 属性（代码内联注释，开发时维护）
3. **兜底**：LLM 根据字段名 + 表名 + 类型生成一次性格式描述（首次构建时生成，后续缓存）

### 3.3 D2：文件认知

#### 3.3.1 当前缺陷

- 仅有数量统计（`共 23 个文件（施工图(8个)...）`）
- 无分类规则说明（为什么这样分、各分类的含义）
- 无 `files` 表核心字段语义
- 无文件访问逻辑（谁能看什么级别的文件）

#### 3.3.2 目标内容

**第一层：分类体系**

```
📁 文件分类体系
· 施工图: 施工过程中的图纸文件（蓝图、竣工图等）
· 报告: 各类检查/检测/验收报告
· 规范: 适用的国家和行业标准规范文件
· 变更: 设计变更通知、工程洽商记录
· 其他: 不属于以上类别的项目文件
```

**第二层：files 表核心字段**

```
文件表(files) — 项目文件归档
  · original_name(文本,必填): 原始文件名
  · file_type(枚举,必填): 文件类型（施工图/报告/规范/变更/其他）
  · category(枚举): 文件分类（对应 FileCategory 枚举）
  · access_level(整数): 访问级别（1=公开,2=内部,3=私密,4=机密）
  · project_id(关联→projects): 所属项目
  · uploaded_by(关联→users): 上传人
```

**第三层：访问规则**

```
🔒 文件访问规则
· access_level ≤ 用户 info_level 时可查看
· 上传人始终可查看自己上传的文件
· L5+ 管理员可查看所有文件
```

#### 3.3.3 数据源

| 数据 | 来源 | 采集方式 |
|------|------|---------|
| 分类枚举 | `FileCategory` 枚举类 | 反射枚举成员 + `display()` 方法 |
| 字段结构 | `files` 表 ORM 模型 | 反射 ORM 元数据 |
| 访问规则 | `row_security.py` 中文件相关逻辑 | 硬编码规则摘要 |
| 分类说明 | `PublicFieldRegistry` + LLM 兜底 | 同 D1 策略 |

### 3.4 D3：权限认知

#### 3.4.1 当前缺陷

- 仅注入 `权限：管理员(L5)` 一行文字
- 6 级树形继承结构不注入
- 参建线 vs 建设线的分叉设计不注入
- 跨线访问机制不注入

#### 3.4.2 目标内容

**第一层：6 级树形权限结构**

```
🔐 权限分级体系
参建线: L1 访客 → L2 参建执行 → L3 参建管理
建设线: L1 访客 → L4 建设主管 → L5 管理员 → L6 系统管理员

注意：L4 不继承 L2/L3 权限（两线在 L1 后分叉）
跨线访问通过临时/永久授权(PermissionGrant)实现
```

**第二层：各级别能力边界**

```
· L1 访客: 基本查询、公开信息查看
· L2 参建执行: 录入自己负责的事件/任务、查看项目公开信息
· L3 参建管理: 管理参建单位内人员、审核参建方提交
· L4 建设主管: 管理全景节点、审批跨单位事项
· L5 管理员: 全局管理、权限授予、数据脱敏规则配置
· L6 系统管理员: 系统配置、权限规则定义、强制撤销
```

**第三层：当前用户在体系中的位置**

```
你的权限：管理员(L5) — 建设线
继承链：L5 → L4 → L1（可访问 L5/L4/L1 级资源）
不可自动访问：L2 参建执行、L3 参建管理（需通过 PermissionGrant 授权）
```

#### 3.4.3 数据源

| 数据 | 来源 | 采集方式 |
|------|------|---------|
| 级别定义 | `PermissionLevel` 枚举 | 反射枚举成员 |
| 继承链 | `INHERITANCE_CHAIN` 常量 | 直接读取 |
| 级别名称 | `LEVEL_NAME` 常量 | 直接读取 |
| 各级能力 | `fetch_available_tools.py` 权限规则 + SOP 白名单 | 代码逻辑摘要 |
| 当前用户位置 | `SessionContext.level` + `INHERITANCE_CHAIN` | 动态计算 |

### 3.5 Token 预算

| 域 | 目标 tokens | 说明 |
|----|------------|------|
| D1 数据库认知 | 150-250 | 取决于用户可见表数量 |
| D2 文件认知 | 80-120 | 分类体系 + 字段摘要 + 访问规则 |
| D3 权限认知 | 80-120 | 6 级结构 + 用户位置 |
| **合计** | **310-490** | 与世界书（~170）+ 规则书（~100）合计 ~580-760 |

## 四、系统描述书数据结构

### 4.1 新增数据库表：`system_descriptions`

| 字段 | 类型 | 说明 |
|------|------|------|
| id | String PK | UUID |
| version | Integer | 版本号（递增） |
| content_json | Text | 三域结构化 JSON（机器可解析） |
| content_text | Text | 纯文本摘要（直接注入 prompt，~400 tokens） |
| domain_versions | Text | JSON：每域独立版本号 `{"database":3,"file":1,"permission":2}` |
| schema_hash | String(64) | `Base.metadata` 的 SHA-256 hash（用于偏差检测） |
| permission_hash | String(64) | `PermissionLevel` + `INHERITANCE_CHAIN` 的 SHA-256 hash |
| file_model_hash | String(64) | `FileCategory` 枚举 + files 模型的 SHA-256 hash |
| token_count | Integer | 估算 token 数 |
| generated_at | String | 最近生成时间 |
| generated_by | String | 生成来源：startup / migration / manual |
| created_at | String | 首次创建时间 |
| updated_at | String | 最近更新时间 |

### 4.2 content_json 结构

```json
{
  "database": {
    "total_tables": 53,
    "visible_tables": [
      {
        "table_name": "events",
        "display_name": "事件表",
        "description": "记录项目现场发生的事件",
        "permission": "read_write",
        "key_fields": [
```

## 五、偏差检测与自动更新

### 5.1 偏差检测机制

系统描述书的偏差检测与世界书不同：**不是比对数据内容，而是比对代码结构**。

| 检测域 | 检测方式 | 偏差信号 |
|--------|---------|---------|
| D1 数据库 | 计算 `Base.metadata.tables` 的 SHA-256 hash vs `schema_hash` | 新增/删除表、新增/删除/修改字段 |
| D2 文件 | 计算 `FileCategory` 枚举 + files 模型的 SHA-256 hash vs `file_model_hash` | 分类枚举变更、文件模型字段变更 |
| D3 权限 | 计算 `PermissionLevel` + `INHERITANCE_CHAIN` 的 SHA-256 hash vs `permission_hash` | 级别增删、继承链变更 |

```python
class SchemaDriftDetector:
    """系统描述偏差检测器——比对代码结构 hash vs 存储的描述快照。"""

    def detect(self) -> dict:
        """检测系统描述是否与当前代码结构一致。"""
        stored = SystemDescriptionRepo.get_latest()
        if stored is None:
            return {"has_description": False, "needs_build": True}

        current_schema_hash = self._compute_schema_hash()
        current_permission_hash = self._compute_permission_hash()
        current_file_hash = self._compute_file_hash()

        stale_domains = []
        if current_schema_hash != stored.schema_hash:
            stale_domains.append("database")
        if current_file_hash != stored.file_model_hash:
            stale_domains.append("file")
        if current_permission_hash != stored.permission_hash:
            stale_domains.append("permission")

        return {
            "has_description": True,
            "has_drift": len(stale_domains) > 0,
            "stale_domains": stale_domains,
        }
```

### 5.2 更新触发

| 触发时机 | 机制 | 说明 |
|----------|------|------|
| 容器启动 | `_init_meta_cognition()` 中增加检测 | 启动时自动检查，有偏差则重建 |
| DB 迁移后 | 调用 `POST /api/v1/meta-cognition/reload` | 迁移脚本或手动触发 |
| 调度器周期 | `SystemDescriptionUpdateHandler`（周级） | 比世界书的日级更宽松 |
| 手动触发 | CLI 脚本 `build_system_description.py` | 开发/运维调试 |

### 5.3 更新策略

与世界书相同：**有偏差时全量重建**（非逐域修补）。原因：

1. 三个域的描述之间有交叉引用（如权限域引用了表名，文件域引用了权限规则）
2. 系统描述总体积很小（~400 tokens），全量重建代价极低
3. 全量重建保证一致性

```python
def fetch() -> str:
    """获取系统自我描述纯文本摘要。"""
    try:
        from ...repositories.system_description_repo import SystemDescriptionRepo
        desc = SystemDescriptionRepo.get_latest()
        if desc is None:
            return "（系统自我描述未生成）"
        return desc.content_text or ""
    except Exception as e:
        logger.error("fetch_system_description failed: %s", e)
        return ""
```

### 6.5 注入层级

系统描述书为全局唯一，不随用户变化——**每个 Session 的 `{system_description}` 内容相同**。但其中 D1（数据库）部分会根据用户的 `db_perms` 动态裁剪可见表清单。

有两种实现策略：

| 策略 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A：构建时裁剪 | `SystemDescriptionBuilder.build()` 接收 `db_perms` 参数，仅生成用户可见部分 | 每用户描述精确 | 无法缓存共享，每次 Session 创建都重建 |
| B：注入时裁剪 | 构建全量描述，`fetch_system_description` 在返回时按 `db_perms` 过滤 | 全量描述可缓存共享 | 需要 fetcher 实现过滤逻辑 |

**推荐策略 B**：全量构建 + 注入时裁剪。理由：
1. 系统描述体量小（~400 tokens），裁剪逻辑简单
2. 全量描述可被多个用户共享，避免重复构建
3. 与世界书的模式一致（世界书也是全量构建，注入时不变）

### 6.6 与现有变量的关系

系统描述书注入后，现有的浅层变量如何处理：

| 现有变量 | 处理方式 | 理由 |
|----------|---------|------|
| `{visible_schema}` | **保留但降级为后备** | 当系统描述书为空时降级显示（与规则书/世界书一致的 fail-open 策略） |
| `{visible_files}` | **保留但降级为后备** | 同上 |
| `{user_permission_level}` | **保留** | 这是用户身份标识（姓名/职位/权限），属于 Session 级上下文，不属于系统描述 |
| `{available_tools}` | **保留** | 工具列表是动态的（随权限变化），系统描述书是静态的（代码驱动） |

## 十一、风险与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| 系统描述 token 占用过大，挤占对话空间 | 中 | 高 | 控制 ~400 tokens 上限；按 `db_perms` 裁剪可见表数量 |
| `Base.metadata` 反射无法获取字段含义 | 高 | 中 | 三层 fallback：`PublicFieldRegistry` → `Column.comment` → LLM 生成 |
| 首次构建时 `PublicFieldRegistry` 为空 | 高 | 中 | LLM 兜底生成字段描述，存入 `PublicFieldRegistry` 供后续使用 |
| 代码 hash 计算涉及动态 import 可能失败 | 低 | 低 | 仅计算 `models.py` + `level.py` + `FileCategory` 的文件 hash，非全量 import |
| 系统描述与 `visible_schema` 功能重叠 | 中 | 低 | `{visible_schema}` 降级为后备，系统描述为主；最终可废弃 `visible_schema` |
