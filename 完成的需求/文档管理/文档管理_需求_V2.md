# 文档管理 — 文件分类与检索需求规格

> **版本**：V2
> **状态**：待评审
> **最后更新**：2026-07-09
> **基于**：[文档管理需求.md](文档管理需求.md)（V1 原始需求）+ [文档管理_审核_V1.md](文档管理_审核_V1.md)（审核意见，采纳方案 A）
> **方案选择**：方案 A — `file_category` 枚举字段 + 扩展现有 FileService

---

## 1. 定位

### 1.1 一句话

为 Emily 已有的文件归档体系增加**业务分类维度**（`file_category`），使用户能通过 IM 对话按分类（证照/合同/工作记录等）检索和管理文件。

### 1.2 不是什么

- **不是独立的"文档管理模块"** — 不新建 Service / Application / Repo，扩展现有 `FileService` / `FileRepository` 即可
- **不是文件管理器** — 不做文件夹树、目录层级、拖拽移动等 Web 文件管理器功能
- **不是版本管理** — `files` 表已有 `version / is_latest / parent_file_id / change_log` 版本链，本需求不改动版本逻辑

---

## 2. 背景与动机

当前 Emily 的文件管理存在**"只管归档，不管分类"**的痛点：

| 现状 | 问题 |
|------|------|
| `files.file_type` 是自由文本（如"施工图"、"竣工验收报告"） | 无统一分类，`by_type` 统计结果零散不可用 |
| 归档时 LLM 只提取 `file_type`（内容描述），不提取业务分类 | 用户说"帮我查一下承包合同类的文件"无法精确过滤 |
| `SessionAccessibleFileRepo.get_file_summary()` 按 `file_type` 分组 | 分组粒度太细，"施工图"和"施工方案"被分成两组，用户更关心"阶段成果"这个大类 |

建筑工程项目中，文件按业务用途分为 7 大类是行业共识（证照/合同/工作记录/阶段成果/过程文件/管理规程/其他），覆盖了从前期到竣工的全周期文档分类需求。

---

## 3. 文件分类定义

### 3.1 分类枚举

| 枚举值 | 中文名 | 含义 | 典型文件示例 |
|--------|--------|------|------------|
| `PROJECT_LICENSE` | 项目证照 | 具有法律效力的项目正式文档 | 竣工备案证、预售证、建筑施工许可证、土地出让合同 |
| `CONTRACT` | 承包合同 | 参建单位合同文本与附件，具备多方约束法律效力 | 总包合同、界面划分协议、预算清单 |
| `WORK_RECORD` | 工作记录 | 施工过程的工作确认和检查记录 | 完工确认单、进场记录单、巡检报告、隐蔽工程验收单 |
| `PHASE_DELIVERABLE` | 阶段成果 | 各专业方案文本与设计成果 | 施工图、设计方案、专项施工方案 |
| `PROCESS_DOC` | 过程文件 | 行政/管理类过程文档 | 政府整改单、通知单、飞检评分表、年终总结 |
| `MANAGEMENT_SPEC` | 管理规程 | 企业操作手册和成果约束要求 | 报销规程、铺装工艺手册、外墙干挂要求、飞检评分标准 |
| `OTHER` | 其他文件 | 不符合以上分类的文件 | 用户上传的未分类文件、临时文档 |

### 3.2 分类规则

1. **7 类固定，应用层枚举** — 枚举值定义在 Python 代码中（类似 `WorkItemState`），不在 DB 层做 CHECK 约束，方便未来扩展
2. **一个文件只属于一个分类** — `file_category` 是单值字段，不是多选
3. **分类与 `file_type` 是独立维度** — `file_type` 描述文件内容类型（自由文本），`file_category` 描述业务归属（枚举）。例如 `file_type="竣工验收报告"`, `file_category="PHASE_DELIVERABLE"`
4. **默认值 `OTHER`** — 归档时 LLM 无法判断分类则默认归入"其他文件"，不阻塞归档流程
5. **分类可变更** — 用户可通过对话让 Emily 修改文件的分类（"把这个文件改到承包合同类"）

## 4. 数据模型变更

### 4.1 `files` 表新增字段

| 字段 | 类型 | 可空 | 默认值 | 说明 |
|------|------|------|--------|------|
| `file_category` | `String(50)` | ✅ | `"OTHER"` | 文件业务分类枚举值 |

**迁移方式**：手动 DDL（项目无 Alembic）

```sql
ALTER TABLE files ADD COLUMN file_category VARCHAR(50) DEFAULT 'OTHER';
CREATE INDEX idx_files_category ON files(file_category);
```

**已有数据回填**：提供一次性迁移脚本，对 `file_category = 'OTHER'` 的记录调用 LLM 根据 `filename + file_type` 推断分类。脚本路径：`scripts/migrate_file_category.py`

### 4.2 不新增表

本需求不引入新表。7 类分类通过 `file_category` 枚举字段实现，不需要 `file_folders` / `file_folder_items` 等关联表。

```json
  "file_category": {

    "description": "文件业务分类，取值范围：PROJECT_LICENSE(项目证照) / CONTRACT(承包合同) / WORK_RECORD(工作记录) / PHASE_DELIVERABLE(阶段成果) / PROCESS_DOC(过程文件) / MANAGEMENT_SPEC(管理规程) / OTHER(其他文件)",
```

```json
  "properties": {
    "file_category": {
      "type": "string",

    },
    "project_id": {

      "description": "项目 UUID（可选，默认取当前用户项目）"
    },
    "limit": {
      "type": "integer",
      "description": "返回数量上限，默认 10",
      "default": 10
    }
  }
}
```

**返回结构**：

```json
{
  "success": true,
  "reply": "📎 承包合同类文件（共 5 份）\n──────────────\n1. 总包合同.pdf (FIL-20260709-0001)\n2. 界面划分协议.docx (FIL-20260708-0003)\n...",
```

**用户对话示例**：

- "帮我查一下承包合同类的文件" → `query_files(file_category="CONTRACT")`

## 7. SOP / Prompt 变更

### 7.1 `record_file` SOP prompt

在文件归档 SOP 的结构化输出 prompt 中增加 `file_category` 字段说明，让 LLM 归档时自动分类：

```
文件分类决策规则（file_category 字段，必填）：
  - PROJECT_LICENSE：涉及政府许可、法律效力证书（如施工许可证、预售证、土地合同）
  - CONTRACT：涉及参建单位签约、合同文本、界面划分、预算清单
  - WORK_RECORD：涉及完工确认、进场记录、巡检、验收单
  - PHASE_DELIVERABLE：涉及设计方案、施工图、专项方案
  - PROCESS_DOC：涉及政府整改/通知、飞检、年终总结
  - MANAGEMENT_SPEC：涉及操作手册、工艺规程、标准规范
  - OTHER：无法归入以上分类

分类依据：根据文件名和用户描述判断业务用途，而非文件格式。
无法判断时默认 OTHER。
```

### 7.2 新增 SOP 路由规则

在 `emily-data/sops/` 目录下新增文件查询 SOP（或扩展现有 SOP），覆盖以下用户意图：

| 用户意图 | 路由目标 |
|---------|---------|
| "查一下XX类的文件" | `query_files(file_category=...)` |
| "有没有XX文件" | `query_files(keyword=...)` |
| "项目有什么证照" | `query_files(file_category="PROJECT_LICENSE")` |
| "把XX文件改到XX类" | `update_file_category(file_no=..., file_category=...)` |

## 8. 可见性与权限

### 8.1 分类不影响文件可见性

`file_category` 是文件的**元数据属性**，不影响文件可见性判定。文件可见性仍由 `SessionAccessibleFile` 三级机制决定（project_scope / node_linked / explicit），分类查询在可见性过滤之后执行。

查询流程：
1. `SessionAccessibleFileRepo` 确定用户可见文件集合
2. 在可见集合内按 `file_category` 过滤
3. 返回结果

### 8.2 分类变更权限

| 操作 | 最低权限 |
|------|---------|
| 按分类查询文件 | all（所有用户） |
| 修改文件分类 | write（level ≥ 3，参建管理及以上） |
| 删除文件（软删除） | admin（level ≥ 5，管理员） |

### 8.3 保密级别交叉

`file_category` 与 `files.confidentiality` 是独立维度：
- `file_category` = 业务分类（7 类枚举）
- `confidentiality` = 保密级别（0-公开 / 1-内部 / 2-机密 / 3-绝密）

查询时两者可以组合过滤："查一下承包合同类的公开文件" → `file_category=CONTRACT AND confidentiality<=0`

## 9. 与全景节点的关系

文件分类与节点关联是**独立维度**，互不冲突：

| 维度 | 字段 | 用途 |
|------|------|------|
| 业务分类 | `file_category` | 按文档用途检索 |
| 节点关联 | `NodeAccessibleFile` + `source_module_type` | 按工程节点追溯 |

一个文件可以同时有 `file_category="PHASE_DELIVERABLE"`（阶段成果）和 `source_module_type="NODE_DELIVERABLE_DOC"`（节点成果文档），两者描述的是同一文件的不同视角，不矛盾。

## 10. 数据迁移

### 10.1 已有文件分类回填

**脚本**: `scripts/migrate_file_category.py`

策略：
1. 查询所有 `file_category = 'OTHER'` 的文件
2. 对每个文件，用 `filename + file_type` 构建 prompt，调用 LLM 推断分类
3. 批量更新 `file_category`
4. 输出回填报告

```bash
# 执行回填（预览模式）
uv run python scripts/migrate_file_category.py --dry-run

# 执行回填（实际写入）
uv run python scripts/migrate_file_category.py
```

### 10.2 DDL 迁移

```sql
-- Step 1: 加字段
ALTER TABLE files ADD COLUMN file_category VARCHAR(50) DEFAULT 'OTHER';

-- Step 2: 加索引
CREATE INDEX idx_files_category ON files(file_category);

-- Step 3: 回填由 migrate_file_category.py 完成
```

## 12. 验收标准

| # | 验收项 | 验证方式 |
|---|--------|---------|

| 4 | 修改文件分类 | emy-test 发送"把 FIL-xxx 改到管理规程类"，验证分类更新成功 |
| 5 | 分类统计 | 调用 `get_category_summary()` 验证 7 类统计正确 |
| 6 | 未分类文件默认 OTHER | 不指定分类时归档的文件 `file_category = "OTHER"` |
| 7 | 分类变更权限 | level 2 用户尝试修改分类被拒绝，level 3 用户成功 |
