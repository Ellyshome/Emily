## 一、总体评价

需求文档正确识别了一个真实痛点：当前 Emily 的文件管理处于**"只管归档，不管分类"**的状态——`files` 表有 26 列、`file_type` 是自由文本、没有结构化的分类体系，文件之间也没有文件夹/目录关系。用户上传了文件，之后想按业务维度（证照、合同、工作记录等）检索就无能为力了。

## 四、替代方案

### 方案 A：`file_category` 枚举字段 + 扩展现有 FileService（✅ 推荐）

- **思路**：在 `files` 表新增 `file_category` 字段（String(50)，应用层枚举约束），7 类分类作为枚举值。扩展 `FileService` / `FileRepository` 增加按分类查询、更新分类的方法。注册 `query_files_by_category` / `update_file_category` BusinessFlowTool。更新 `record_file` SOP prompt 让 LLM 自动分类。
- **优势**：改动最小、与现有基础设施完全兼容、不需要新表/新 Service/新 Application、实现快
- **劣势**：7 类是扁平分类，不支持多级子目录（但 IM 场景不需要）
- **适用场景**：Emily 当前 IM 对话驱动的文件操作场景

### 方案 B：文件夹树表（`file_folders` + `file_folder_items`）

- **思路**：新建 `file_folders` 表（id, name, parent_id, project_id, ...）和 `file_folder_items` 中间表（folder_id, file_id），实现树状文件夹结构。
- **优势**：支持多级目录、支持文件夹级别的权限控制、类似传统文件管理器体验
- **劣势**：新增 2 张表 + 2 个 Repo + 可能需要新 Service/Application；与 IM 对话场景不匹配（用户不会说"帮我把文件放到第3级目录下"）；过度设计
- **适用场景**：未来如果需要 Web 端文件管理器界面

### 方案 C：不修改数据模型，纯 LLM 分类

- **思路**：不改表结构，查询时调 LLM 根据文件名和描述动态分类。
- **优势**：零改动
- **劣势**：每次查询都要调 LLM（成本高、延迟大）、分类结果不稳定、无法按分类做 SQL 索引查询
- **适用场景**：仅做临时 POC 验证
