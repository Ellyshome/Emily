## 探查结论（设计输入，均为实测）

1. **状态向上传播从未实现**——`node_repo.get_ancestor_chain` 的 docstring 写着"用于递归进度重算"，但**全仓无任何调用者做重算**，只被 `mount_child` 用于深度/循环校验。后果在数据里可见：子任务已是 `IN_PROGRESS`，其父工作包仍是 `CONDITIONS_NOT_MET`。**D3 允许嵌套后此缺陷会放大，必须在本计划内补齐。**

## M1：类型与归类规则

**依赖**：无　**实现**：D1, D2, C1　**层级**：Service / 常量

**设计决策（关键）**：`node_type` 列**保留**（不改表、兼容 console 与 API 展示），但**不再由调用方随意决定**——改由系统按结构**单向提升**：

- 挂了子节点 → 必为 `MILESTONE`（自动提升，不可逆向下沉）
- 无子节点 → 保持创建时声明的类型（默认 `TASK`；显式建为 `MILESTONE` 的叶子保留，代表"尚未分解的里程碑"）

理由：结构可保证"有子节点必为里程碑"，但"无子节点"不能反推为任务——里程碑登记后常尚未分解任务，而 D5 要求它此时显示「未启动」。已退场类型 `WORK_PACKAGE` 由 M5 按结构收敛。默认值由 `WORK_PACKAGE` 改为 `TASK`（新建节点默认是叶子）。

**改动点**：`models.py` L1109 注释与默认值、`node_commands.py` L24、`node_batch.py` L60/L228、`node_schemas.py` L40、`api/routes/node.py` L96、`node_service.py` L263；新增 `refresh_node_type(node_id)`，由 `mount_child` / `unmount_child` 触发。

**验收**

```bash
grep -rn "WORK_PACKAGE" emily-core/emily_core | grep -v "migrate_node_type"
→ 预期：0 命中

# 结构派生正确性
uv run python scripts/manage_nodes.py query --project-id EMR  # 任取一项目
→ 预期：有子节点的 node_type 全为 MILESTONE，叶子全为 TASK
```

**失败处理**：若 `node_service.py` 仍有 `node_type=getattr(cmd,...)` 形式的调用方传值残留，说明未收敛，回退重做。

## M2：状态引擎（删进度 + 新判据）

**依赖**：M1　**实现**：D4, D5, D6　**层级**：Service + 纯计算引擎

### 引擎变更（`node_state_machine.py` L141-L187）

任务（叶子）判定顺序：

| 条件 | 结果 |
|------|------|
| 前置依赖未满足 | 未启动 |
| 无成果定义 | 未启动 |
| **完成量 = 0** | **未启动（新增）** |
| 0 < 完成量 < 目标 | 运行中 |
| 完成量 ≥ 目标 | 已完结 |

里程碑（有子节点）：维持 `_determine_parent_status` 三态聚合，逐层递归，不新增规则。

**必须保留**：`completion >= 1.0 → COMPLETED`（任务完结的唯一自动路径）、`calc_deliverable_completion` 函数本体（被状态判定调用，仅删除其"进度"用途）。

### Service 变更（`node_service.py` L1166-L1184）

- 删除 `new_progress` 的计算与 `node_repo.update_progress` 调用
- `progress_changed` 分支一并删除，仅按 `status_changed` 判断是否写库
- `NodeOperationResult.progress` 字段保留（返回结构兼容），恒回 0.0 或现状值
- **保留** `determine_node_status` 调用与 `completed_at` 写入链

### 验收

# ② progress 列不再被系统写（上报前后值不变）
→ 预期：两次查询 progress 均为原值

# ③ 全仓确认进度写入路径已断
grep -rn "update_progress" emily-core/emily_core/services/node_service.py

**失败处理**：若任务在 0 量时仍显示 `IN_PROGRESS`，检查 `deliverables` 是否为空（空列表走"无成果定义→未启动"分支，勿混淆）。

## M3：祖先传播（补齐"有方法无调用"）

**依赖**：M2　**实现**：D2, D3　**层级**：Service + Repository 接线

**问题**：任何一层节点状态变化后，只有自身被重算，祖先不会更新（今日工作包状态陈旧即此因）。

**设计**：

- 新增 `_recalc_ancestors(node_id)`：自底向上逐层调用 `_recalc_node_status`，直到状态无变化或到达根
- 接线点：所有会改变状态的入口统一收口——`update_deliverable_progress`、`submit/confirm/return_deliverable`、`mount_child`、`unmount_child`、`create_node`（挂父时）
- 深度约束调整：`MAX_PARENT_DEPTH = 3` 不再作为业务硬上限，改由 `MAX_TREE_DEPTH = 10` 作**安全上限**（仅防脏数据成环）；`mount_child` 的循环校验保留。
  - "任务必须是叶子"无需额外校验——单向提升规则下，有子节点必然被提升为里程碑，任务（叶子）不可能有子节点，是规则的自然后果。
- `get_ancestor_chain` 的 `max_depth` 由调用方按实际深度传入，不再写死 3

**验收**

```bash
# 三级链路：施工总控(里程碑) → 景观绿化工程(里程碑) → 乔木种植(任务)
# 对任务上报 30/100
docker exec emily-postgres psql -U emily -d emily -c \
 "SELECT node_id,node_type,status FROM project_nodes
  WHERE node_id IN ('EMR-SG-01','EMR-SG-01-05','EMR-SG-01-05-01') ORDER BY node_id;"
→ 预期：三级均为 IN_PROGRESS（今日为「任务 IN_PROGRESS / 两级父 CONDITIONS_NOT_MET」）

# 接线可达性（宪法 Q6）
grep -rn "get_ancestor_chain" emily-core/emily_core
→ 预期：≥2 处（定义 + 重算调用点），仅 1 处 = 未接线
```

**失败处理**：跨级未同步时先确认收口点是否漏接（尤其 `create_node` 挂父路径）。

## 执行顺序与停损规则

1. M1 → M2 → M3 为主线，M4/M5/M6 可在 M1 完成后并行，M7 最后。
2. 每完成一个模块：清 `__pycache__` → 重启 `emily-core` → 执行该模块验收命令 → 记录输出。
3. 偏差 ≤1 个接口 → 直接改；2–4 个 → 追加本文件修订记录继续；**>4 个或架构方向变化 → 停，报告用户**。
4. **触发停损的典型情形**：M4 建任务带量做不通（说明 `add_deliverable` 契约与 `create_node` 不兼容），或 M3 祖先重算在场量下出现性能问题——两者都需回退基线重议，不得就地绕过。

## 风险与回滚

| 风险 | 影响 | 对策 |
|------|------|------|
| 迁移不可逆 | 存量类型分布错乱 | 迁移前 `pg_dump` 备份 `project_nodes`；脚本幂等可重跑 |
| 类型改由结构派生后与旧数据不符 | 旧 `MILESTONE` 节点若为叶子会被刷成 `TASK` | M1 的结构刷新**只对新挂载/卸载动作生效**，不回溯刷存量；存量由 M5 一次性迁移 |
| 祖先重算引入额外写库 | 上报延迟 | 深度受安全上限约束（`MAX_TREE_DEPTH = 10`）+ 仅状态变化时写库 + 某层未变化即提前终止 |
| console 未同步 | 类型标签显示空白 | M6 与 M1 同批发布 |
