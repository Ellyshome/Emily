### 3.5 分布式锁形同虚设——advisory lock 跨 session 失效

**证据**（`plan_task_scheduler.py:101-121`）：

```python
async def _acquire_distributed_lock(self, lock_key: str) -> bool:
    with get_session() as session:                    # ① 在此 session 内获取锁
        result = session.execute(text("SELECT pg_try_advisory_lock(...)"))
        return bool(result.scalar())
    # ② with 退出 → get_session commit + session.close()（session.py:117-122）
```

`pg_try_advisory_lock` 是**会话级锁**，绑定在获取它的数据库连接上。`get_session()` 的 `with` 块一退出就 `session.close()`，连接归还连接池（`pool_size=5`，非真断开）。随后 `_tick` 主体（`plan_task_scheduler.py:156-176`）的每一步又开**新的** `get_session()`，拿到的是池中**任意**连接——与持锁连接无关。`finally` 里的 `_release_distributed_lock`（`plan_task_scheduler.py:123`）同样开新 session，`pg_advisory_unlock` 跑在一条并不持有该锁的连接上，unlock 返回 false。

**后果**：锁在 `_tick` 主体执行期间**不提供任何保护**；多进程部署时各进程 `_tick` 并行执行，超时提醒、循环补齐、自动归档会**重复触发**。前序修正报告 P0-6 已指出但**未修复**。

**修复**：用一个**独立的、跨整个 `_tick` 生命周期保持打开**的 session 持锁（前序修正报告 P0-6 方案正确，需落地），或改用 `pg_advisory_xact_lock` 绑定到 `_tick` 的事务。

### 3.6 同步 Repository 阻塞 asyncio 事件循环

**证据**：Service 全部方法声明为 `async def`，但内部直接调用同步 Repository（`with get_session()` 为阻塞式 SQLAlchemy，`session.py:103`）。例如 `plan_task_service.py:117` `create_template` → `PlanTaskTemplateRepo.create` → 同步 `session.flush()`。调度循环 `_tick`（60s 一次，`plan_task_scheduler.py:149`）内的每次 DB 查询都阻塞事件循环。

**影响**：与 `handle_message` 共享同一事件循环，调度 tick 期间的阻塞查询会延迟消息处理。低频场景（60s tick）可容忍，但架构上 `async/await` 形同虚设。前序修正报告 P0-1 提出 `asyncio.to_thread` 包裹方案但**未落地**（全项目 Repository 均同步，改异步工作量另议）。

**建议**：至少将 Scheduler `_tick` 内的批量 Repository 调用用 `asyncio.to_thread` 包裹；或接受现状但在报告中标注为已知技术债。

## 四、🟠 重要问题（P1 — 功能缺失 / 偏离计划）

### 4.1 数据库唯一约束与索引全部未落地（计划 §3.6）

**证据**：`models.py` 中 4 张 plan_task 表**均无 `__table_args__`**，无 `UniqueConstraint`、无 `Index`（grep 确认仅 `users`/`conversations`/`sop_permission_bindings` 三张老表有约束）。建表走 `Base.metadata.create_all`（`session.py:94`），且项目**无 alembic 迁移**（glob 确认），故 §3.6 要求的约束/索引不会被任何途径补上。

| 计划要求 | 状态 | 影响 |
|----------|------|------|
| `uq_pti_period`（template_id+period_key 唯一，WHERE status≠CANCELLED） | ❌ | 幂等仅靠应用层"先查后插"（`plan_task_repo.py:174-190`），并发下可重复创建实例 |
| `idx_pti_status_deadline` | ❌ | 调度机核心查询 `find_overdue`/`find_near_deadline` 全表扫描 |
| `idx_pti_executor_status` / `idx_pti_project` / `idx_pti_unscheduled` / `idx_pti_llm_failed` / `idx_ptl_instance` / `idx_ptd_submitted` | ❌ | 查询性能退化 |

**修复**：在 `PlanTaskInstance` 加 `__table_args__`（`UniqueConstraint` + 各 `Index`）。注意：`create_all` 对已存在的表不会补字段/索引，需手动 DDL 或建迁移。

### 4.2 LLM 推算失败降级偏离计划（§2.4）+ 通知逻辑是死代码

**计划要求**（§2.4、§七.3）："LLM 失败降级：调用失败时**不做自动推算**，改为**通知任务发起人人工处理**"。

**实际实现**（`plan_task_scheduler.py:346-369`）：`_calc_current_period` 在 LLM 失败时 `except` 捕获并返回 `_fallback_period_calc`——硬编码"本周五 17:00"（`plan_task_scheduler.py:399-415`）；`_calc_next_period` 同理返回"+7 天"兜底（line 417-447）。即 LLM 失败时**仍自动创建实例**，与计划"不做自动推算"直接矛盾。

**死代码链**：
- 没有任何代码路径将 `instance.llm_calculation_failed` 置为 `True`（grep 确认仅有定义与 `set_deadline_manually` 清除它）。
- 因此 `find_llm_failed_pending_notification`（`plan_task_repo.py:377`）**永远返回空列表**。
- `_notify_llm_failure_to_initiators`（`plan_task_scheduler.py:451`）永不执行。
- 模板级 `llm_calculation_failed`/`llm_failure_notified`（`models.py:824-826`，前序修正 P1-1 已加字段）同样**无人设置、无查询方法**。

**后果**：计划承诺的"LLM 失败通知人工处理"机制完全不存在；取而代之的是用错误截止时间静默创建任务。

**修复**：`_calc_current_period`/`_calc_next_period` 失败时应抛异常或返回失败标记，由 `_handle_cycle_task_generation` 标记模板/实例 `llm_calculation_failed=True` 并 `continue`，交由 `_notify_llm_failure_to_initiators` 通知。

### 4.6 实例创建与日志写入跨 session，无事务边界

**证据**：Service 每个状态变更方法都用两次独立 `get_session()`——先 `update_status`（提交），再 `PlanTaskLogRepo.create`（另起 session 提交）。例如 `plan_task_service.py:294-307`：`update_status` 成功提交后，若 `PlanTaskLogRepo.create` 失败，**实例状态已变更但审计日志丢失**，违反"每次流转写审计记录"（§4.3）。

**修复**：合并到同一 session（前序修正 P1-3 方案：Repository 方法接受可选 `session` 参数复用）。前序已提但**未落地**。

### 5.1 `cancel_instance` 审计日志 `from_status` 丢失

`plan_task_service.py:401` `instance = update_status(..., "CANCELLED")` 返回的实例已是 `CANCELLED`，随后 line 405 `from_status=instance.status if instance.status != "CANCELLED" else None` 恒为 `None`——**原始状态被丢失**。应在调用 `update_status` 前用局部变量保存 `original_status`。

### 5.2 `update_status` 日志 "from → to" 失真

`plan_task_repo.py:429-432`：`instance.status` 在 line 412 已被赋为 `new_status`，故 `instance.status if instance.status == new_status else "-"` 恒等于 `new_status`，日志变成 `"X → X"`，丢失变更前状态。

### 5.4 时区不一致

- 编号生成用 `BEIJING_TZ`（`plan_task_repo.py:22,50,149`）。
- 时间戳与截止比较用 `timezone.utc`（`plan_task_service.py` / `plan_task_scheduler.py` 全局）。
- `find_overdue`/`find_near_deadline` 对 `deadline_at`（String 列）做**字符串比较**（`plan_task_repo.py:253,275-276`），若 `deadline_at` 存储格式带/不带时区后缀不统一，比较结果错乱。

### 5.5 `get_today_due_tasks` 逻辑错误

`plan_task_app.py:290-313`：`tomorrow_start` 实为当日 23:59:59（命名误导）；用 UTC 0 点过滤"今日"与业务本地时区不符；且依赖 `find_by_status`（见 3.1）必然抛错被 `except` 吞掉返回空。

### 5.6 缺统一异常类 + 重复 `_new_id`

- 全模块只抛 `ValueError`（`plan_task_service.py` 多处），无法区分"状态非法/归档不可变/不存在"，调用方难以精确处理（前序 P2-1 未落地）。
