# RAG 系统化改造 PRD（融合版）

> 本文为统一主文档，融合「可见范围改造」与「RAG 通用能力对标」两条线，同步设计、分层落地。
> 过程稿保留：《RAG可见范围改造PRD.md》《RAG改造技术对标清单.md》不删除，仅作历史参考。
> 参照仓库：`D:\app\charrystudio\cherry-studio`（AGPL-3.0，只抄设计、不抄代码）。

## 一、背景与问题

1. **越权风险**：Emily 当前 RAG 通道（`knowledge_search`）对任何用户执行全库向量检索，不区分用户、不设可见范围。
2. **现状简陋**：RAG 停在「切块 → 向量化 → 余弦 top_k」三段向量检索原型，缺工程化 RAG 的整条管线（分块质量、混合检索、去重、重排、状态机、溯源）。
3. 需求目标：所有搜索统一收敛到「用户对应的可见文件范围」内，访客仅能访问受限内容。

## 二、目标与总体思路

1. **范围化（正确性）**：建立统一「可见文件范围」模型，作为 RAG 检索（及后续所有搜索）的前置过滤器。
2. **能力对标（质量）**：对照 Cherry Studio 补齐 RAG 通用工程能力（抄设计不抄代码）。
3. **同步推进**：两条线共享同一条入库管线 / chunk 表结构 / 检索查询 / 工具层，串行会产生二次返工（迁移两次 schema、重写两次 search），故同步设计、分层落地。

## 三、核心范围模型（完整公式）

```
可见文件集合 = 上传者自有集 ∪ 公开文件集 ∪ 节点可见集

  ① 上传者自有集 = files.uploaded_by = user_id
                 （自传永可见，不受密级约束）
  ② 公开文件集   = files.confidentiality = 0
                 （不锚定任何节点，仅凭「密级=公开」纳入，全员可见）
  ③ 节点可见集   = 用户所属企业参与的全景节点共享文件并集
                 （node_participant_companies → node_accessible_files → files）
                 ∩ (files.confidentiality ≤ user.info_level)
```

访客落点：未关联节点、无企业 → ③ 为空，可见 = ① ∪ ②，即「自传文件 + 公开文件」，支撑基础问答。

## 四、已定约定（决策记录）

1. **doc_id 归一**：切片只锚定 `files.id`（file_id），不携带节点/scope 信息。
2. **过滤位置**：检索前 SQL WHERE 过滤（`doc_id IN 可见集`），排序前过滤；宁少答、不泄露。
3. **最小单元**：文件（files.id），切片不冗余 scope。
4. **公共文档**：不设全员节点/公共节点/虚企业；文件初始**零可见**，允许不被全员所见。
5. **公开文件**：以 `files.confidentiality = 0` 表达（方案 A），不设基础节点。
6. **上传者可见**：自传文件永远可见，**不受密级约束**。
7. **密级约束**：节点可见集需过 `confidentiality ≤ user.info_level`。
8. **零可见治理**：照常入库，后台定期扫描「零可见文件治理清单」做下架/补授权。
9. **范围外应答**：归 session-agent，不在本次范围。

## 五、功能需求

- **F1** 按用户 ID 返回其关联的全景节点列表（节点名 + ID）。
- **F2** 按节点 ID 返回节点内共享文件列表（文件名 + ID）。
- **F3** 按用户 ID 返回可见文件集合（= ① ∪ ② ∪ ③）。
- **F4** RAG 检索接入可见集：`knowledge_search` 在向量排序前按 `doc_id IN 可见集` 过滤。
- **F5** 密级过滤：节点可见集（③）内按 `confidentiality ≤ user.info_level` 过滤。

## 六、RAG 通用能力对标（抄设计、不抄代码）

Cherry 引擎功能完整，但范围维度是空的（全仓库无 user/tenant/ACL/文件级/节点级权限），故：通用能力对标其设计，范围能力必须自建。

| # | 能力 | Emily 现状 | Cherry 参考 | 落到本栈形态 |
|---|---|---|---|---|
| 1 | 文档解析 | 仅 UTF-8 纯文本 | 17 种格式 + anydoc 原生 + 降级链 | `pymupdf`/`unstructured`/`docling` 按类型路由 |
| 2 | 分块 | 固定长度/粗切 | 结构断点打分 + token 精修 + offset 不变量 | 重写同算法 |
| 3 | 去重 | 无 | content/embedding 双 sha256 | 哈希列入库前查重 |
| 4 | 向量化 | 手动调 embedding | 统一 embedMany，维度绑定 | 统一 embedding 服务 |
| 5 | 检索 | 纯余弦 top_k 无过滤 | BM25 + 向量 + RRF 混合 | pgvector + pg_trgm + RRF |
| 6 | 重排 | 无 | 可选 rerank，失败降级 | 可选 rerank 服务 |
| 7 | 入库可靠性 | 一次性脚本 | 5 类 job + 状态机 + 崩溃恢复 | 接入作业基建 |
| 8 | 引用溯源 | 无 | `[cite:id]` 溯源 | 工具返回来源 id + 标题 |

## 七、实施策略：同步设计、三里程碑落地

- **里程碑 1（正确性）**：doc_id 归一 + 范围过滤（F1~F5）。交付标准：越权已堵住，任何用户检索结果都落在可见集内。
- **里程碑 2（质量）**：对标表 1~6（文档解析、分块、去重、向量化、混合检索、重排）。交付标准：召回与排序质量提升。
- **里程碑 3（体验/可靠性）**：对标表 7~8（入库状态机、引用溯源）。

## 八、非目标 / 后置项

1. **访客能力限制**（只能受限 RAG 问答、其余工具拦截）：**后置**。范围化完成不会自然实现，需单独做工具白名单/拦截逻辑。
2. **范围外应答话术**：归 session-agent。
3. Cherry 的 AGPL-3.0 合规风险：不引入其代码/依赖，仅取其设计思路，规避传染性许可。

## 九、技术口径

- 可见性是「关系」而非「属性」：文件/切片不存节点归属，经 `node_accessible_files` 推导。
- 密级是正交维度：`confidentiality` 决定"够不够格看"，与"归属范围"分离。
- doc_id 归一是前提：当前目录扫描入库的 doc_id 为 uuid4（断链），需先改为锚定 files.id。
