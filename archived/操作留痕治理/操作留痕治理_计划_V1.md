## 一、落地策略

**一句话**：新建一个**留痕门面**（上下文 + 装饰器 + 写入 + 三态判定），把留痕挂到动作类 service 方法上；四类入口只负责注入上下文；数据层扩列并扩展补列机制以支持索引。

**三条已核实的关键事实决定了设计**（均来自本轮代码核查）：

| 事实 | 影响 |
|------|------|
| `EvolutionLogWriter` **已有 `write_sync()`**（`log_writer.py:49-63`），且已有先例（`scheduler_logger.py:32`、`llm_logger.py:100`） | 装饰器**不需要** `asyncio` 投递，同步写入即可，避开了"sync 方法里无处 await"的难题 |
| 105 个写方法中，**只有 35 个**返回可机械判定三态的结构（8 个 `dict含success` + 21 个 `NodeOperationResult` + 6 个 `list[dict]`）；services 层**几乎不 raise**（仅 3 处），失败普遍被吞成 `None`/`False` | **不做全区返回签名重构**（105 个方法、高风险）；改为「**统一解释层 + 分级判定**」，见 §2.2 |
| `_ensure_columns` **只补列与 UNIQUE 约束，不支持普通索引**（`session.py:47-207`） | 需要**扩展**该机制（新增 `_PENDING_INDEXES`），否则 `source` 索引在既有库上不存在 |

## 二、详细方案设计（逐条回答 PRD 附录 B）

### 2.1 留痕门面与挂载形态（回答附录 B.1、B.3）

**新增模块** `emily-core/emily_core/infrastructure/logging/audit.py`，提供三件东西：

| 组成 | 内容 |
|------|------|
| **上下文** | `AuditContext`（dataclass：`source` / `channel` / `channel_account` / `actor_id` / `actor_name`）+ `ContextVar` 载体 + `bind_audit_context()` / `reset_audit_context(token)` / `current_audit_context()` |
| **动作记录** | `record_action(category, action, target_type, target_id, target_no, summary, result, error_reason, actor)` → 同步调 `EvolutionLogWriter.write_sync(BusinessEventLog, ...)`，失败吞掉并计数 |
| **装饰器** | `@audited(category=..., action=..., target_type=..., actor_arg=..., target_arg=..., target_no_arg=..., summary=...)`，同时支持 sync 与 async 方法 |

**动作边界如何判定**（FR-15）：**以"是否显式挂装饰器"为准**，而非命名约定或全量扫描。理由：
- 显式声明可评审、可追溯（挂载清单见 §3 附录）；
- service 内部互调天然不重复留痕（内部方法不挂装饰器）；
- 满足约束 13（统一注册形态），不依赖逐方法手写写入代码。

**actor 从哪来**：装饰器 `actor_arg` 指定参数名（如 `operator_id` / `user_id`），从调用入参取。这样**入口只注入 source / channel**，不传 actor —— 少一层透传。取不到时记 `actor=unknown`（FR-4，不得静默不留痕）。

**写入方式**：`write_sync`（同步、单条 INSERT、非阻断）。代价与权衡：
- 事件循环内同步写一次（~ms 级）——与既有 `scheduler_logger` / `llm_logger` 同代价，可接受；
- 好处：不引入队列/后台线程，不依赖事件循环存在（脚本进程无循环）。

**失败可观测**（FR-12）：`audit.py` 内维护模块级计数（`write_failures` / `last_error`），暴露 `audit_write_stats()`，供 `scripts/self_check.py` 读取（需同步改 `self_check.py` 的 `result` 键 + `console_resources.py:1422-1429` 的 `stats` 白名单）。

### 2.2 结果判定（回答附录 B.2；FR-14 的落地解释）

**FR-14 原文要求"service 返回约定统一"，落地解释为**：**统一"解释"，不统一"签名"**。

理由：105 个写方法分布在 50 个模块，签名形态涵盖 ORM 对象 / `None` / `bool` / `dict` / `NodeOperationResult` / `list[dict]`；全量重构签名属独立大工程，且会触碰大量与留痕无关的调用方（高风险、非本需求目标）。改为在门面内提供**唯一判定函数** `_classify_result(ret)`：

| 优先级 | 返回形态 | 判定 |
|--------|---------|------|
| 1 | 抛异常 | `failed`，`error_reason=repr(exc)` |
| 2 | `NodeOperationResult`（21 个方法） | `success=True` → `succeeded`；`False` → 按 `error_code` 查拒绝码表 → `rejected` / `failed` |
| 3 | `dict` 含 `success`（8 个方法） | 同上，取 `error` / `reason_code` |
| 4 | `list[dict]` 逐项含 `success`（6 个函数） | 全部 `success` → `succeeded`；否则按失败项计数（`n_success/n_total` 记入 `summary`） |
| 5 | `bool` | `True` → `succeeded`；`False` → `failed` |
| 6 | `None` / ORM 对象 / 其他 | `succeeded`（无失败信号，按"未抛异常即已写库"处理） |

**"被拒"识别**：维护一张**拒绝码表**（`REJECT_CODES`），初始条目来自已核实的错误码：
`permission_denied`（`file_service.py:114`）、`40301`（`node_commands.NodeOperationResult` 权限不足）、`invalid_confidentiality`（`file_service.py:98`，动作已开始的校验拒绝，按基线 §四.5 口径计 `rejected`）。
表可扩，新增条目须在 PRD 约束 7 的口径下评审。

**已知局限（写入文档，不掩盖）**：约 2/3 的方法（返回 ORM / `None`）只能记"调用发生 + 是否抛异常"，**无法区分"失败"与"被拒"**。这些方法的三态完整化需要逐个补 `reason_code`，**列为后续可选工作**（按动作重要性排优先级），不在本批次强推。

### 2.3 上下文载体与回退链（回答附录 B.4）

`ContextVar` + **四级回退**，解决"脚本进程 / 线程 / 无注入路径"的取值：

```
1) contextvars 当前值（正常路径：入口已注入）
2) 若未绑定 → 读环境变量 EMILY_AUDIT_SOURCE / EMILY_AUDIT_CHANNEL_ACCOUNT（脚本 subprocess 通道）
3) 若仍无 → 'auto'
```

- **线程安全**：`asyncio.to_thread` 会复制调用时刻的 context（全仓 228 处，`run_in_executor` 零命中），故入口在 `to_thread` 之前注入即可传到工作线程；`repositories/` 全同步的设计不构成障碍。
- **不回流**：线程内 set 不回传事件循环，这正是我们要的隔离语义。
- **并发隔离**：`contextvars` 替代现有两处类级 dict（`business_event_logger.py:23`、`llm_logger.py:24`）中的前者；`llm_logger` 的改造不在本需求范围（另案）。
- **兼容桥**：沿用项目既有范式（`kernel/context.py:44` `bind_compat()`、`state.py:13`、`kernel_state.py:230`），不新造机制。

### 2.5 数据层变更（回答附录 B.7；约束 11）

| 表 | 新增列 | 落库 |
|----|--------|------|
| `business_event_logs` | `source` `VARCHAR(20)` default `''`、`channel` `VARCHAR(30)`、`channel_account` `VARCHAR(200)`、`result` `VARCHAR(20)`、`error_reason` `VARCHAR(500)` | `models.py` 加 `Column` + `session.py` `_PENDING_COLUMNS` 加条目 |
| `messages` | `source` `VARCHAR(20)` default `''` | 同上 |
| `scheduler_job_logs` | `source` `VARCHAR(20)` default `''`、`actor` `VARCHAR(200)` | 同上 |

**索引**：`_ensure_columns` 不支持普通索引 → **扩展机制**，新增 `_PENDING_INDEXES`（与既有 `_PENDING_CONSTRAINTS` 同构，用 `pg_indexes` 幂等检查 + 失败只 warning）：

```
_PENDING_INDEXES = {
    "business_event_logs": [("idx_bel_source_created", "(source, created_at)")],
    "messages":            [("idx_msg_source_created", "(source, created_at)")],
    "scheduler_job_logs":  [("idx_sjl_source_created", "(source, created_at)")],
}
```

同时在 `models.py` 的 `__table_args__` 里声明同样的 `Index`，使**全新库**经 `create_all` 也有索引（两条路径都覆盖）。

**兼容**：`BusinessEventLogger.log()` 透传 5 个新字段，并接上门面上下文（读 `current_audit_context()` 回填 `source`/`channel`/`channel_account`/`result`）；`conversation_id` 仍不落库（表无该列，本需求不扩，仅记录该事实）。

## 四、验收（对照 PRD §七）

第一批完成后可验证的项：

1. **补列与索引生效**：重启后启动报告出现 `数据库迁移：新增列 business_event_logs.source, ...`；`\d business_event_logs` 可见 5 个新列与 `idx_bel_source_created`。
2. **并发不串扰**：两个会话并发触发动作，`source` / `channel` / `actor` 不串（contextvars 载体）。
3. **console 与 IM 可分辨**：console 任一写操作留痕 `source='ops'`；console 模拟对话 `source='test'`；IM 消息链路的动作 `source='user'`。
4. **首挂动作留痕**：改密级的「成功 / 被拒（非上传人）/ 参数非法」三种情形分别产生 `succeeded` / `rejected` / 无留痕（口径见基线 §四.5）。
5. **同源同痕**：文件删除从 console 触发有痕（现状已有）、从 IM 触发**新增有痕**（首挂 `file_manager.soft_delete` 后）。
6. **非阻断**：人为制造留痕写入失败（如临时改表名）不影响业务返回。

## 五、风险与缓解

| 风险 | 缓解 |
|------|------|
| `ContextVar` 在 `BaseHTTPMiddleware` 的 `call_next` 子任务中可见性依赖 starlette 版本 | 中间件内 `set` 后用 token 复位；实施后立即用 console 端点实测验证（验收 3） |
| 装饰器同步写库在事件循环内阻塞 | 单条 INSERT；与既有 `scheduler_logger` 同代价；必要时后续换队列（不改接口） |
| 挂载范围蔓延（105 个写方法） | 只挂"业务可感知动作"，附录清单逐条评审；查询类与高频内部回填（如 `update_summary`）**明确不挂** |
| 三态在 Tier B 方法上不可判 | 已在 §2.2 显式声明局限；不假装有 `result='rejected'` |
| 存量回填误判 | `--dry-run` + 抽样 20 条人工确认；`result` 不回填 |
| 索引机制扩展影响启动 | `_PENDING_INDEXES` 失败只 warning 不阻塞（同 `_PENDING_CONSTRAINTS` 语义） |

### 第二批起的阻塞点（须先拍板）

`FR-8` 要求"先在 service 层补齐能力，再由 console 与 IM/Tool **同源调用**"。难点在**知识入库/检索**：这两件事目前只在 `tools/embed_tool.handle_embed_and_index` 与 `providers/rag/pgvector_provider.py` 里，且 `tei` / `repo` 依赖是**注册期经 `functools.partial` 注入**的（`tools/registry.py:363-371`）。两条可选路径：

| 方案 | 做法 | 代价 |
|------|------|------|
| **A. service 为唯一实现，tool 变薄壳** | 新增 `KnowledgeService.index_chunks / search`，`embed_tool` 与 console 都调它；tool 的 `tei`/`repo` 注入改为 service 内部获取 | 动到 tool 注册链与 `partial` 注入方式，风险中等；但真正满足"同源同痕" |

**建议 A**，但因为它动到工具注册注入链，先确认再实施。
