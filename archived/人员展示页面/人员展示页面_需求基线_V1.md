## 一、背景与问题

1. **现象（人员视图缺失）**——需求的首条即"人员列表"，而 console 今天没有这张表。
   - 全仓**唯一**"人员 + 企业 + 等级"的读取入口是 `GET /api/v1/console/users`（`api/routes/console_resources.py:430-440`），其实现是 `scripts/options.list_options("users")`（`emily_core/scripts/options.py:49-70`），返回仅四字段 `value`(id) / `label`(username) / `level` / `note`(company_name)。
   - 该入口的定位是**左侧栏"操作人"下拉的候选源**（`static/scripts_tool/console.js:889` `ensureGlobalUsers()`），不是人员视图：**上限 300 条**（`options.py:21,46`）、**无排序参数**、**无登记时间**、**无录入人**。
   - 另一条人员读取链路 `QueryService.query_users()`（`services/query_service.py:435-472`）返回 `user_id/username/display_name/status/created_at/node_names`，**同样不含 level / company / 录入人**。
   - 结论：需求要求的五个列中，**"登记时间""录入人"两列在现有任何入口都不存在**，其余三列也只在下拉候选里存在。
2. **现象（人员等级 / 企业归属"只能改库"）**：
   - 仓储层仅有**通用**写入方法 `UserRepository.update_user(user_id, **kwargs)`（`repositories/user_repo.py:217`）——裸 `setattr`，**无取值校验、无授权判定、无留痕**。
   - **service 层无专用方法**：`user_binding_service`（仅绑定/自注册）、`permission_service`（仅授权 grants，**不改 `users.level` / `users.company`**）、`company_resolver`（**只解析引用，不提供企业列表**）三者均无该能力。
   - **工具层无**：`tools/registry.py` 注册的全部工具中，与用户相关的只有 `write_user_memory`（仅写长期记忆）；**无任何人员/权限/企业类工具**。
   - **SOP 无**：`emily-data/sops/` 下无人员注册或权限调整 SOP（SOP-000 仅在缩写表中**举例**"人员登记"，SOP-007 是长期记忆）。
   - **脚本无**：`scripts/` 下无管理用户、改等级、改企业归属的脚本。
   - 与 `Issues/权限矩阵/权限表_fixed.csv`（注9）、`权限与能力缺口清单_V1.md:30-31`（G-2 / G-3）完全吻合：**该能力属"设计意向"，当前零落点**。
   - **企业侧同病**（G-1，本次一并纳入）：全仓**无企业清单能力**——`company_resolver` 只做"引用→ID"解析（`services/company_resolver.py:31`）、`permission_repo.get_company` 只按 id 单查（`:42`），**无 `list_companies` / 无创建 / 无删除**；`company_info` 仅由种子数据与个别脚本写入。故 FR-5 的归属候选、FR-11 的企业清单、FR-12 的增删**都缺件**。
3. **现象（长期记忆无条目级读取）**：
   - 项目里"人员长期记忆"的**唯一真实载体**是 `UserMemoryService` 的每用户 Markdown 文件（`services/user_memory_service.py:35`；文件名 `{用户名}-长期记忆.md`，:67-76；条目格式 `## [YYYY-MM-DD HH:MM] 标题`，:129；目录 `emily-data/user_memory/`，`docker-compose-napcat.yml` 挂载）。
   - 该服务现有方法只有：`save_memory`(:96) / `load_memory`(:146，**整篇原文**) / `load_memory_context`(:175，**压成 `- 标题: 内容` 的注入文本**) / `list_users`(:253，**只有用户名名单**)。
   - **没有任何"按用户返回条目列表"的方法**——而需求要的正是"各条目"。
   - 另有 DB 列 `users.long_term_memory`（`models.py:96`），但**无写入方**，`session_data_fetcher.py:107-108` 注释明确"仅为兼容历史数据保留"，仅作兜底读。
   - 结论：条目级展示**必须先补 service 能力**，不能靠现有 `load_memory` 硬解析文本。
4. **现象（session 初始化提示词无生成入口）**：
   - 真正的会话拉起提示词是**运行时装配**的：`SessionLoop._build_system_prompt(entries)`（`session/loop.py:325-339`）＝ `load_prompt("session_loop")` 模板 + `{capability_catalog}`（工具能力目录）+ `SessionContext.get_prompt_variables()`（`session_context.py:570-640`，含 `{user_memory}`:626）+ `{current_datetime}`，最后 `_strip_unfilled`。
   - 该方法是**实例私有方法**，输入依赖 `entries`（该用户等级下的可用能力目录）；**无任何 service 函数、无任何 API 端点**把它串起来（`api/routes/` 全目录搜 `session_prompt|generate_session` 零命中）。
   - `scripts/generate_session_prompt.py` 名字最接近，但**是降级版**：只取世界书 + 规则书做 token 统计（`:49` `generate_session_prompt()`，返回体 `:88-98` 只有长度/token 字段），**不加载 `session_loop.md` 模板、不渲染任何变量**。
   - 结论：需求要的"一键生成"，**能力本身尚不存在**（不是接线问题，是缺件）。
5. **现象（console 已具备承载条件，不必新造壳）**：
   - 前端：17 个模块面板 + 模块清单数组 `MODULE_ITEMS`（`console.js:977`）+ 面板隐藏清单 `MODULE_PANEL_SELECTORS`（`:854`）+ 点击分发 `bindListClicks`（`:95`）+ 切换刷新 `reloadActiveModule`（`:921`）；等级中文名常量 `USER_LEVEL_NAMES`（`:878`）已存在。
   - **排序先例已有两处**（文件管理、会话日志）：纯**前端客户端排序**，`data-sort-key` + `.sort-ind`（`console.js:1056/1184/1209/1223`；`console.css:267-269`），**后端不参与排序**。
   - 写操作安全件已有：写库二次确认模态 `#confirm-overlay`（`index.html:644`）；全局操作人锚点 `#global-operator-select`（`index.html:19`，标题即注明"控制所有右侧栏的可见范围与操作日志归属"）。
   - 后端：`/api/v1/console` 前缀**已在鉴权白名单**（`api/middleware/auth.py:30-37`），**无需改 auth**；且 `api/middleware/audit_context.py:31-42` 已对该前缀注入留痕上下文 `source=ops` / `channel_account=console`。
   - 结论：新增该模块**不需要新静态目录、不需要改 `server.py` / `auth.py`**，改动面收敛在既有 console 三件套与一个路由文件内。
6. **现象（写操作口径已定但未落地）**：`权限与能力缺口清单_V1.md` 已就本页面的写能力作出决策——
   - **D3**（:119）：企业/人员管理（G-1~G-3）**本期全做**（企业增删 + 人员等级调整 + 人员归属调整），落地要求"**新增工具（限 L5/L6）+ 审计留痕**"；
   - **D6**（:127）：等级调整——L6 可调至 L6、L5 最高 L4、L4 最高 L3、L3 仅可调"自己下一级"、L2/L1 不可调；企业归属调整——L4+ 可调、L3 可管理本企业人员进出、L2/L1 不可；
   - **D7**（:128）：纠错补救类能力本期不做，console 中依赖该特权的入口**先建后停**。
   - ✅ **该冲突已于 2026-09-17 裁决**（见 §十一 Q4 / §十 B11）：**以 D6 为业务口径**，D3 的"限 L5/L6"修正为"工具准入不得低于该能力实际可操作的最低等级"；判定在服务层、以操作人等级为准、fail-closed、被拒也留痕。已同步写入缺口清单（新增 D8 / V1.3）。
7. **现象（console 无认证，写能力因此受限）**：console 全部端点当前**完全放行**（`auth.py:30-37`），"操作人"由请求自述（GET 走 query `user_id`，POST 走 body `operator_id`），**服务端不校验身份**。此为既有已声明的限制（`操作留痕治理_需求基线_V1.md` Q17：console 认证立为独立后续项，本期不纳入）。本页面的写操作**继承该限制**，且**不得**借此把它包装成"有审计效力的操作"。
8. **定性**：这不是"给 console 加一张表"，而是**三条能力缺口的同一载体**——
   - 缺**人员视图**（读）；缺**人员维护**（写）；缺**记忆与提示词的可见性**（读）。
   - 三者共同的上游事实是：**人员相关的读写能力在 service 层从来没有建立过**（`users.company` / `users.level` 只能裸写，记忆没有条目级读取，提示词没有可调用的装配入口）。
   - 因此本需求的正确形态是：**先在能力层补齐（service / 工具），再由 console 同源接线**——而不是在路由层直接改库、直接解析记忆文本、直接复刻提示词装配。后者正是约束 14（console 不得自造功能）明令禁止的。
9. **影响**：
   - **人员视图不可得** → 无法回答"这个人是谁录的、什么时候录的、属于哪个企业"，人员档案的台账属性缺失。
   - **等级/企业调整走改库** → 无校验（可把 L1 提成 L6）、无留痕、无授权判定；一旦错改，无审计线索可回溯，且直接影响该人全量权限（等级是权限的唯一决定因素之一，`permission/level.py`）。
   - **长期记忆不可见** → 无法回答"Emily 到底记住了这个人的什么"，记忆写入（`write_user_memory`）成了一个**不可观测的黑箱**：写错了、写偏了都看不见。
   - **session 提示词不可见** → 无法回答"Emily 是以什么身份、什么项目上下文、什么权限视角面对这个人的"；提示词类问题只能靠读代码 + 翻日志定位，`{user_memory}` / `{project_brief}` / `{rule_brief}` 等变量的实际渲染结果**没有任何观测入口**。
   - **本页面还会放大一个既有隐患**：console 无认证（现象 7）下新增写能力，若不强制服务端等级判定，等于给"自述操作人"开了一条改全站权限的路。

## 二、目标

1. **G1 人员可看全**：以一张表回答"人员是谁、属哪家、何时录、谁录的"，并支持按列排序。
2. **G2 人员与企业可维护**：人员等级、企业归属可调整，**企业可增删**（L4+），且**均带校验、带授权判定、带留痕**——彻底终结"只能改库"。
3. **G3 记忆可见**：某人的长期记忆**按条目**可见（时间 / 标题 / 内容），把记忆从黑箱变为可观测对象。
4. **G4 提示词可现**：一键得到"Emily 面对此人时会真正用到的 session 初始化提示词"，并在页内框架展示，无需读代码或翻日志。
5. **G5 同源不另造**：本页面的每一项能力都**先存在于能力层（service / 工具）**，console 仅接线复用；路由层**零业务逻辑、零裸 SQL、零文本解析**（约束 14 / 宪法 C13）。
6. **G6 主链路零侵入**：不修改 Session 主循环、LangGraph 执行引擎或任何内核文件；不改变消息处理路径与权限模型。

## 三、范围

- **纳入**：
  - emy-console **人员模块面板**（前端面板 + 模块清单登记 + 一条路由文件的端点）；

  - **长期记忆条目列**（条目数 + 展开查看条目）；
  - **人员等级调整**（写）；
  - **人员企业归属调整**（写）；
  - **企业增删**（写，L4+）：企业列表 / 新增企业 / 删除企业（本次新增，见 §五 FR-11 / FR-12）；
  - 写操作的**服务层授权判定 + 参数校验 + 留痕**；
  - **长期记忆条目级读取**能力（service 层补齐）；
  - **session 初始化提示词生成**能力（service 层补齐）+ 页面内展示；
  - 上述能力按既有注册通道接入（工具注册 / schema 三步 / 一致性映射）。
- **不纳入**：
  - **人员新增与删除**（本页面不含增删人员；自注册链路现状不变）；
  - **企业档案的完整编辑**（仅增、删两项；企业的其余字段（统一社会信用代码、单位性质、承包范围、对接单位等）不在本期编辑范围——见 §五 FR-12 的"最小字段"口径）；

  - **console 认证 / 鉴权改造**（Q17：独立后续项）；
  - **长期记忆的编辑与删除**（本页面**只读**记忆；写入路径仍是 `write_user_memory`）；
  - **会话归档（`session_archives`）内容展示**（已有「会话日志」模块承载）；
  - **群级记忆（`group_memories`）/ 项目世界书（`ProjectWorldBook`）展示**（维度不同，非人员维度）；
  - **权限矩阵 / 行级安全的改造**（含 `permission/row_security.py` 的 fail-open 遗留问题 G-13）；
  - **Session 主循环与提示词装配的重构**（见 §七.4）；
  - 新增同级 CLI 脚本入口（能力落在工具层；脚本通道按需另行接线）。

## 四、术语

1. **人员**：`users` 表中的一行（`models.py:67-101`）。**不含**未登记的 IM 访客（访客在会话归档中 `is_guest` 标记，不在 `users` 内）。
2. **人员等级**：`users.level`，取值 **1–6**，语义与中文名以 `emily_core/permission/level.py` 为准（1 访客 / 2 参建执行 / 3 参建管理 / 4 建设主管 / 5 管理员 / 6 系统管理员；`level.py:20-28,44-51`）。
   > 注意：需求原文与部分文档写作"人员等级 / permission_level"，**实际列名是 `level`**，`users` 表**不存在** `permission_level` 列。命名口径以 `level.py` 为准（权限表注2）。
3. **所属企业**：`users.company`（**字符串外键** → `company_info.id`，**可空**，`models.py:94`）。展示值取 `company_info.company_name`；为空或悬空时展示为"未归属 / 未知"。
4. **录入人**：`users.creator_id`（`models.py:88`，非空）。**自注册路径下等于本人 id**（`user_repo.py:163-169`），此时展示为"本人（自注册）"。
5. **登记时间**：`users.created_at`（`models.py:99`）。注意该列类型为 **String**（ISO 串），展示时按既有 console 时间展示口径处理。
6. **长期记忆**：`UserMemoryService` 维护的**每用户 Markdown 文件**（`{用户名}-长期记忆.md`）。**不是** session 归档、**不是**世界书、**不是**群级记忆。其 DB 列 `users.long_term_memory` 为**无写入方的兜底历史数据**。
7. **记忆条目**：长期记忆文件中的一个 `## [YYYY-MM-DD HH:MM] 标题` 段（含时间戳、标题、正文）。当前**无独立字段、无条目 ID**，靠 `## ` 前缀界定；条数上限默认 50（超限裁最旧）。
8. **session 初始化提示词**：Emily 在一个用户会话拉起时装配的 system prompt，即 `session_loop.md` 模板经变量渲染后的成品（模板 + 能力目录 + 提示词变量 + 当前时间）。**不是** `scripts/generate_session_prompt.py` 的"世界书+规则书 token 统计"。
9. **操作人（console 全局操作人）**：页面左上 `#global-operator-select` 选定的人员，作为所有右侧面板的可见范围与操作归属锚点；其身份**由请求自述**，服务端当前不校验。
10. **模块面板**：console 右侧并列的 `<section>` 之一，由 `MODULE_ITEMS` + `MODULE_PANEL_SELECTORS` + `bindListClicks` 三处登记。
11. **后台视角**：console 相对 IM 的定位（D4）；本页面的写操作按"所选操作人等级"判定，不引入超级特权。
12. **企业**：`company_info` 表中的一行（`models.py:453-478`），人员归属的目标对象。本期只涉及**增**与**删**两个动作，且采用**最小字段**口径（§五 FR-12）：其余字段（统一社会信用代码 `unified_code`、单位性质 `type`、承包范围 `scope`、对接单位 `partners`、负责人 `project_leader_id` 等）均不在本期编辑范围。
    - ⚠️ **实现注意**：该表有多个 **NOT NULL 且无默认值**的列（`company_name` / `unified_code` / `project_leader_id` / `creator_id`），因此"最小字段"**不等于**"只填名称即可落库"——其余必填项的取值口径（自动生成 / 取操作人 / 允许留空）必须在计划阶段明确，否则 FR-12 无法落地。此条属"实现现状所施加的约束"，登记于此以免遗漏（口径本身留在计划阶段定）。
13. **删除企业**：本期的"删"采用何种语义（逻辑删除 vs 物理删除），以及**存在在职人员归属时是否允许删**，属规格决策——见 §十一 Q9。

## 五、功能需求

### A. 人员视图（只读）

1. **FR-1 人员列表**：提供人员表，列为 **人员ID / 姓名 / 所属企业 / 登记时间 / 录入人**（对应 §四.1–5 的字段）。
   - 录入人须解析为**可读姓名**（非 UUID）；解析不到时展示原始 ID 或"未知"。
   - 所属企业须解析为 `company_name`；空/悬空须有明确文案（不显示空白）。
   - 默认范围与**规模上限**须明确（见 NFR-3），超限行为可见（截断提示），不得静默丢数据。
   - 页面须能识别"当前无人员"与"加载失败"两种状态（沿用既有模块的加载中/失败/空态写法）。
2. **FR-2 按列排序**：列表支持**按列排序**（需求原文"可根据列参数排序"）。
   - 排序口径沿用 console 既有约定：**前端客户端排序**，表头可点、有升降序指示，不新增后端排序参数。
   - 至少覆盖需求列：姓名、所属企业、登记时间、录入人；排序语义须稳定（时间按时间序而非字符串序，等级如作为列则按数值序）。
3. **FR-3 长期记忆条目列**：列表中提供一列展示该人员的长期记忆。
   - 列内展示**条目数**；无记忆时明确显示"无"（需求原文"若有"）。
   - 可**展开查看条目**：每条含 时间 / 标题 / 内容（§四.7）。
   - 记忆取值口径须与 Emily 实际注入口径**一致来源**（同一 service），不得在 console 另写一份解析规则。
   - 记忆内容可能较长，展示须有折叠/截断策略且不丢失可读性。

### B. 人员维护（写）

4. **FR-4 人员等级调整**：可将某人员的等级调整为另一合法值。
   - 目标值取值域 **1–6**；非法值必须被拒（服务端校验，非仅前端下拉约束）。
   - 须有**授权判定**：操作人等级决定"能调到哪一级"，规则须收敛为**唯一口径**（见 §十一 Q4，D3 与 D6 冲突待裁决）。
   - 须为**幂等**语义：调成当前值不产生副作用记录（或明确标注为"无变化"）。
   - 失败须可区分原因（无权限 / 目标不存在 / 目标值非法 / 超出可调范围）。
5. **FR-5 人员企业归属调整**：可将某人员的所属企业改为另一企业（含改为"未归属"）。
   - 企业候选取自**真实企业表**，不得要求使用者手抄 UUID（下拉/搜索选择）。
   - 须校验目标企业**存在且有效**（非已删/已停用）。
   - 须有**授权判定**（规则同 Q4 裁决口径）。
   - 空值/清除归属须与"未设置"语义一致，不得与"设为某个空企业"混淆。
6. **FR-6 写操作的安全与留痕**：FR-4 / FR-5 均为**状态变更操作**，须满足：
   - **服务端授权判定**：不信任前端、不信任自述的操作人以外的一切；判定不通过须返回明确拒绝原因，且**被拒也要留痕**（沿用操作留痕治理的三态口径：动作已开始后的规则/权限拒绝属"被拒"，须记录）。
   - **留痕**：经既有唯一挂载点写入（`@audited` / `audit.record_action`），携带 操作人 / 目标人员 / 变更前后值 / 结果 / 来源；**禁止**在路由层或前端自行写留痕。
   - **二次确认**：改等级、改归属属高危写操作，前端须经写库二次确认（复用既有 `#confirm-overlay`）。
   - **变更可追溯**：留痕须能回答"谁把谁从什么改成什么"（新旧值入留痕），否则审计价值不成立。

### C. 记忆与提示词

7. **FR-7 长期记忆条目级读取能力**：在能力层提供"按人员返回记忆条目列表"（条目含 时间 / 标题 / 内容，及总条数）。
   - 这是 FR-3 的**前置能力**；不得在 console 侧用正则解析注入文本或整篇 Markdown 替代。
   - 须兼容"无记忆文件""文件存在但无条目""记忆功能被关闭"三种情形并各有明确返回。
   - **只读**：读取不得改动记忆文件（含不得触发裁剪）。
8. **FR-8 一键生成 session 初始化提示词**：
   - 对指定人员，**一键生成**其 session 初始化提示词，并在**页面下方的结果框架内**展示（需求原文）。
   - **口径要求（规格级）**：生成的提示词必须与"Emily 面对此人时会真正装配使用的那份"**同模板、同变量装配、同能力目录口径**——即包含 `{user_memory}` / `{project_brief}` / `{rule_brief}` / `{capability_catalog}` / `{current_datetime}` 等变量的实际渲染结果，而非其中任意片段的预览。
   - **无副作用**：生成**不得**发消息、不得调 LLM、不得写会话归档、不得创建会话、不得写留痕（纯只读渲染）。
   - 生成失败须可区分原因（人员不存在 / 模板缺失 / 上下文采集异常），并展示可诊断信息，不得只回"生成失败"。
   - 生成结果须可复制（供人工比对/取证）。
   - 展示须区分"提示词正文"与"生成元信息"（如人员、时间、token 规模），避免混排。

### D. 接线与注册

9. **FR-9 能力注册接入**：本需求新增的每一项能力按既有注册通道接入，不得裸文件/硬编码接线（约束 12 / 宪法 C11）：
   - 写能力（等级调整 / 企业归属调整）→ **业务工具注册**（`tools/registry.py`），且必须完成**参数 schema 三步**（源文件 `_XXX_SCHEMA` → 注册 `params=` → `tools_consistency.py` 的 `TOOL_SCHEMA_MAP`，约束 11 / 宪法 C10）；
   - 写工具必须声明 **`write_mode`** 并同步一致性映射（G-9 的教训：写工具未标写语义会被当作只读能力暴露）；
   - 只读能力（人员列表 / 记忆条目 / 提示词生成）→ **service 层能力**（必要时补 Repository 查询方法），console 只读端点复用之；**禁止**裸 SQL、禁止绕过 service 直查表。
10. **FR-10 console 模块接入**：作为 console 的第 18 个模块面板接入。
    - 前端三处登记必须同步（模块清单 / 面板隐藏清单 / 点击分发），缺一处即出现"面板残留"或"点不开"（既有代码注释已明示该约束）。
    - 切换"全局操作人"时本模块的刷新行为须与其他模块一致（可见范围 / 操作归属锚点）。
    - 后端端点沿用 console 既有契约（`{code,message,data}` 响应、`asyncio.to_thread` 包同步、异常不抛 500）。
    - 不新增静态目录、不改鉴权白名单、不改 `server.py` 的静态挂载。

### E. 企业管理（写，L4+）

11. **FR-11 企业清单**：提供企业清单，作为 FR-5 归属调整的**唯一候选来源**（也不得要求使用者手抄企业 ID）。
    - 清单取**真实企业表**，不得硬编码、不得前端静态枚举。
    - 须能反映企业当前状态：候选下拉只出现**有效**企业；已删除企业不得出现在候选内。
    - 清单须能显示每个企业的**当前归属人数**——这是 FR-12 删除前置判定的可见依据（"这家企业下面还有人"必须一眼可见）。
    - 口径"简单优先"：企业清单**不单开模块面板**，作为人员页面内的一个区块/下拉承载（用户明示"就简单点"）。
12. **FR-12 企业新增与删除**（权限口径：**L4 及以上**，L3/L2/L1 不可 —— D6 ③ / D8-b）：
    - **新增**：以**最小字段**创建企业（§四.12）；企业名称必填；其余必填项的取值口径在计划阶段明确。
    - **删除**：语义与前置条件（能否删除仍有在职人员归属的企业）见 §十一 Q9。
    - 两项均须：**服务层授权判定**（以操作人 `level` 为准，< L4 拒绝，取不到等级则拒绝）、**参数校验**（空名称、非法 ID、目标不存在）、**留痕**（含操作人、目标企业、结果；**被拒也留痕**）。
    - 两项均须经前端的**写库二次确认**（高危写操作）。
    - **失败可诊断**：无权限 / 名称非法 / 名称重复（若定唯一）/ 企业仍有人归属 / 企业不存在，各自返回明确原因并可区分。
    - **不提供**企业字段的编辑（改名、改性质等）——本期只增、删（§三 不纳入）。

## 六、非功能需求

1. **NFR-1 写操作不改链路**：新增能力不改消息处理路径、不加拦截、不影响 IM 侧任何行为；IM 侧权限模型与可见范围不变（D4 / 权限表注1、注3）。
2. **NFR-2 只读路径零副作用**：人员列表 / 记忆条目 / 提示词生成三条只读路径**不产生任何写入**（不写库、不写文件、不留痕、不调 LLM）。提示词生成尤其不得触发"会话创建"一类隐式行为。
3. **NFR-3 规模与性能**：人员列表须有明确规模上限与截断提示（既有列表端点截断值为 `_LIST_LIMIT=2000`，`console_resources.py:33`；现人员下拉上限 300）。首屏渲染不得因逐人读取记忆文件而阻塞——记忆条目数须**批量或惰性**获取，不得 N 人 × 全量读文件。
4. **NFR-4 权限 fail-closed**：写操作的等级判定在信息缺失时**默认拒绝**（取不到操作人等级 → 拒），不得 fail-open。
5. **NFR-5 留痕非阻断**：留痕失败不影响业务返回（沿用 `EvolutionLogWriter` 三原则：失败只告警、截断、异步）。
6. **NFR-6 无越界改动**：不顺带重构 console 既有模块；不引入新依赖；不修 `permission/row_security.py` 等既有遗留问题（G-13 另案）。
7. **NFR-7 展示不泄露**：提示词与记忆正文均含人员隐私与项目内部信息，展示仅限 console 后台视角；端口与放行口径维持现状（`127.0.0.1` 绑定 + 现有白名单），本期**不因本功能扩大暴露面**。
8. **NFR-8 可回退**：新模块可整体停用（前端入口下架 / 后端端点返回"暂未开放"）而不影响其余 console 模块——沿用 D7 的"先建后停"表达方式。

## 七、约束

1. **console 不得自造功能（约束 14 / 宪法 C13）**：本页面**每一项**读写能力都必须先在 `tools/`（写）或 `emily_core/services/`（读写）落地，再由 console **同源接线**。路由层出现业务逻辑、裸 SQL、直调 repo/provider、或在前端复刻解析规则，均视为违反。**能力缺失时先补能力层，不得 console 先行**。
2. **工具必须带参数 schema（约束 11 / 宪法 C10）**：新增写工具必须完成三步（源文件 schema → 注册 `params=` → 一致性映射），缺一即在启动日志报 SchemaGuard 警告并在 CI 报 error。同时必须登记 `write_mode`。
3. **能力注册接入（约束 12 / 宪法 C11）**：新增能力不得裸文件硬编码接线；若出现"实现文件无人调用 / 注册表挂 stub"，须停下并先定义注册点。
4. **不触碰 Session 主循环（约束 13 / 宪法 C12）**：本需求**不得**修改 `session/loop.py`（主循环文件）。FR-8 若要达成"与 Emily 实际使用的那份一致"，**只能**由能力层新建装配能力实现；
   - ⚠️ **必须显式登记的风险**：能力层新装配 + `loop.py:325` 内既有装配 = **同一逻辑两份实现**。这属于"内核自身的机制形态问题"，按 C12 **须以专项需求基线立项**才能收敛为唯一实现。本基线**不**把它塞进本期（否则即为以业务需求之名改内核）。
   - 本期的正确姿势：按期交付"同模板 + 同变量 + 同能力目录口径"的生成能力，并把"两份实现收敛"登记为遗留项（见 §十一 Q2）。
5. **写操作的授权口径必须唯一**：不得同一能力存在两套准入规则（D3 与 D6 的冲突必须收敛，§十一 Q4）。
6. **不动权限模型与可见范围**：人员可见范围由"单位性质 + 企业参与节点"推导（权限表注1），本页面不引入新的可见范围规则；console 为后台视角（D4），不把后台视角让渡给 IM，也不把 IM 权限用于后台越权。
7. **不新建重复层**：新能力复用 `emily_core/services/` 与 `tools/registry.py`，不新建独立的"人员服务层""提示词服务"等平行层。
8. **改动方式**：优先扩展既有结构与既有约定（前端排序约定、`{code,message,data}` 契约、`@audited` 挂载点、`_PENDING_COLUMNS` 补列机制），不新建重复表；**本需求原则上不需要新增表/列**（见 §十一 Q5 例外）。

## 九、验收方向

1. **人员视图完整**：人员列表同时呈现五列，且"登记时间""录入人"两列**经真实数据可见**（现状此二维度无任何入口）；录入人显示为姓名而非 UUID。
2. **排序可用**：点击姓名 / 所属企业 / 登记时间 / 录入人表头，顺序正确且指示可见；登记时间按时间序而非字符串序。
3. **记忆条目可见**：对**有**记忆文件的人员，列显示条目数并展开出 时间/标题/内容；对**无**记忆人员显示"无"；条目数与记忆文件中的 `## ` 段数一致（抽样核对）。
4. **记忆口径同源**：页面展示的条目与 Emily 实际注入的记忆**同源同内容**（同一 service 取值），非 console 侧自行解析的副本。
5. **等级调整生效且受控**：
   - 越权调整（按裁决口径不允许的组合）→ 被拒，返回明确原因，**且产生一条"被拒"留痕**；
   - 合法调整 → `users.level` 变化生效并产生留痕，留痕含**新旧值**与操作人；
   - 非法值（0 / 7 / 非数值）→ 被拒且不落库。
6. **企业归属调整生效且受控**：合法调整 → `users.company` 变化 + 留痕；目标企业不存在 → 拒绝；清空归属 → 落为空值且展示为"未归属"。
7. **企业清单可用**：清单取自真实企业表（非硬编码）；候选下拉只出现有效企业；每个企业可显示当前归属人数；不得要求手抄企业 ID。
8. **企业增删受控（L4+）**：
   - L4 及以上新增、删除 → 成功 + 留痕（含操作人、目标企业、结果）；L3 及以下 → **被拒 + 明确原因 + 一条"被拒"留痕**；
   - 新增空名称 → 拒绝；名称重复（若定唯一）→ 拒绝；
   - 删除仍有在归属人员的企业（若决策禁止）→ 拒绝并提示归属人数；
   - 删除语义与 Q9 裁决一致（逻辑删除则数据仍在、候选不再出现）。
9. **写操作留痕可答四问**：从留痕能回答"**谁**（操作人）+ **做了什么**（等级/归属/企业增删）+ **对象是谁**（目标人员或企业）+ **成没成（含新旧值）**"。
10. **提示词可生成且口径正确**：
    - 一键生成后，页面框架内出现完整提示词正文；
    - **口径核对**：与 Emily 实际装配的那份在**模板、变量集、能力目录口径**上一致（与 `session_loop.md` 模板段落逐段对照：长期记忆段、项目简述段、规则段、能力目录段均非"（无）"式空值时的实际内容）；
    - 含 `{user_memory}`、`{capability_catalog}`、`{current_datetime}` 的实际渲染结果，而非统计数字。
11. **生成无副作用**：连续生成 N 次后，`session_archives` / `messages` / `business_event_logs` **无新增记录**；记忆文件 mtime 与条目数不变。
12. **无认证限制如实呈现**：页面写操作在无认证前提下可用（现状），但**不宣称**具备对外审计效力（与 `操作留痕治理` Q17 的限制声明一致）。
13. **同源可达性（静态扫描）**：新写工具在 `tools/registry.py` 有注册、在 `tools_consistency.py` 有 schema 与 `write_mode` 映射；console 路由**不出现**裸 SQL / 直调 repo / 直调 provider；能力层新增的只读方法**有且仅有** console 一个消费方（或有其它消费方，但不得零消费方）。
14. **主链路不回归**：`session/loop.py`、LangGraph 引擎、消息处理路径**零改动**（以 diff 证）；IM 侧抽测一次常规对话无新增告警。
15. **前端登记三处同步**：模块面板可点开、切换模块后无面板残留、切换全局操作人时本模块刷新行为与其他模块一致。
16. **失败可诊断**：人员不存在 / 记忆功能关闭 / 模板缺失 / 企业不存在 / 企业仍有人归属，各类失败各有明确文案，不出现"操作失败"式模糊提示。
