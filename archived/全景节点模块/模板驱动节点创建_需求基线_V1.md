# 模板驱动节点创建 — 需求基线 V1

**一句话**：让全景节点模板从"文字预设"升级为"对象装配说明书"——模板声明要采集哪些对象（参与单位 / 成员 / 共享文件 / 前置成果），系统按描述解析成真实记录候选，经人确认后落库；同一套装配能力同时服务**控制台信息面板**与 **IM 文字对话**两个入口。

> **性质**：需求基线（讨论稿），确认后转计划
> **日期**：2026-09-22
> **范围**：模板的"对象声明"能力 + 对象采集器 + 两端（控制台 / IM）的装配与确认 + 落库编排。
> **关联**：
> - 模板库本身的存储/挂载/索引形态见 `Issues/全景节点参考模板模块/全景节点参考模板模块_需求基线_V1.md`（**与本基线有重叠，见 §十二 开放问题 1**）
> - 模板 → 三表映射契约见 `emily-data/node_templates/README.md`
> - 消费方（Atlas 归属判定）见 `Issues/全景节点维护者/全景节点维护者_需求基线_V1.md`
> - 节点创建口径见 `emily-data/sops/SOP-011-SYS-node_manage.md`

## 一、背景：现状与七个断点

### 1.1 已经打通的（本轮已完成，作为基线现状）

| # | 能力 | 锚点 |
|---|---|---|
| 1 | 模板索引在容器内真实可读 | `docker-compose-{minimal,wecom,napcat}.yml` 只读挂载 `/app/data/node_templates`；`emily-core/Dockerfile` 建 `/app/data` |
| 2 | 索引驱动的模板发现 + 详情 | `GET /api/v1/console/node-templates`（读 `index.yaml`）、`GET /api/v1/console/node-template?ref_id=`（按索引的 `file` 再读 md） |
| 3 | 节点本身的增 / 改 / 删 | `POST /console/node-create`、`/node-update`、`/node-delete`（软删） |
| 4 | 模板来源可溯源 | `project_nodes.template_ref_id` 列（自动补列，无手写迁移） |
| 5 | 信息交互面板 | 节点ID 可点开面板（改名称/截止/备注 + 删除）；表头「＋ 增加节点」；模板预填名称/类型/备注/成果清单 |
| 6 | **最小切片：前置条件 → 依赖候选** | `GET /console/node-draft`；模板 `## 前置条件` 的描述匹配项目内已有成果 → 面板可删候选 → 保存时随节点落库 |

### 1.2 尚未打通的七个断点

| # | 断点 | 证据锚点 |
|---|---|---|
| 1 | **系统内不存在"描述 → 集合"的解析器**。现有一律是"描述 → 单个记录"，且歧义即 `None`（fail-closed、拒绝猜测），与"先给一组候选让人挑"的范式相反 | `emily-core/emily_core/services/company_resolver.py::resolve`（单值、精确等值） |
| 2 | **企业匹配能力最弱**：`type` 是自由文本中文标签且写法不统一（`总包`/`施工单位`/`施工总承包`、`监理`/`监理单位`），`scope`（承包范围 JSON，如 `["景观","1标段"]`）**全仓无任何代码读取**，且无简写/别名字段。故「景观分包单位」这类描述目前**必然匹配不到任何企业** | `emily-core/emily_core/infrastructure/database/models.py::CompanyInfo`；`.../services/permission_service.py::_CONSTRUCTION_TYPES`（局部词表，非全局归一） |
| 3 | **模板没有承载"对象声明"的地方**：现只有 4 个 frontmatter 字段 + 4 个正文章节；README 的映射契约只覆盖「产物清单」与「前置条件」，无参与单位 / 成员 / 文件的声明位 | `emily-data/node_templates/README.md` §二~§四 |
| 4 | **创建期写不了参与人 / 共享文件 / 依赖**：`create_node` 只落「参与单位（多，`replace_all`）+ 成果」；参与人只有单个 `add`（无批量、无 `replace_all`），文件有 `batch_add`，依赖必须在节点落库后建 | `.../services/node_service.py::create_node`；`.../repositories/node_repo.py` 三个关联表 Repo |
| 5 | **IM 侧模板库完全不可达**：`ctx.node_template_catalog` 仍被加载，但已从 `get_prompt_variables` 的映射中移除（不再进 prompt）；无任何 list/read 模板的工具；SOP-011 全文未提模板；`create_node` 工具不收 `template_ref_id` | `.../session/session_context.py`（P1-1 移除说明）；`emily-core/emily_core/tools/`（无模板工具）；`emily-data/sops/SOP-011-SYS-node_manage.md` |
| 6 | **IM 建节点无写库前确认关卡**：SOP-011 未要求建节点前向用户确认；现存的 `ConfirmDialog`（事件拟录入单）与 `ConfirmQueue`（WorkItem `WAITING_CONFIRM`）均与节点创建无关 | `.../session/confirm_dialog.py`、`.../session/confirm_queue.py`、`.../tools/node_tool.py` |
| 7 | **模板"对象声明"的下游无人消费**：本轮已写入 `template_ref_id`，但目前只作溯源记录，无读取方按它取回模板蓝图 | `.../services/node_commands.py::CreateNodeCommand.template_ref_id` |

**结论**：模板的"文字字段预填"链路已经通了，但"对象采集"链路一处未通——既无声明位（断点 3），也无解析器（断点 1/2），更无创建期落库通道（断点 4）。IM 侧则是整条链都缺（断点 5/6）。

## 二、定位

- **是**：模板的一种新增能力（对象声明）+ 一组只读采集器 + 一条"两入口共用"的装配链 + 创建期的落库编排。
- **不是**：不是新的节点体系、不是新的权限规则、不是常驻服务；不改变既有节点工具与 SOP-011 的触发条件/权限映射。
- **不被本基线改动**：模板的存储形态（逐文件夹 + `template.yaml` 属「全景节点参考模板模块」线）；节点状态机与成果自证化口径；`CompanyResolver.resolve` 的既有语义（新增采集器而不改写它）。

## 三、目标

1. **G1 可声明**：模板能声明"要采集哪些对象"（参与单位 / 成员 / 共享文件 / 前置成果），声明是结构化的、可校验的、不依赖自然语言猜测。
2. **G2 可解析**：给定"描述 + 项目上下文"，系统能解析出**真实记录候选集合**（而非单值），并保留"依据哪条声明"的可解释性。
3. **G3 可确认**：候选一律先呈现给人，可增删调整；**未经确认不落库**。
4. **G4 两入口同源**：控制台信息面板与 IM 文字对话消费**同一条装配链**；IM 侧不重复实现解析逻辑。
5. **G5 不谎报**：解析不到的声明必须显式回显为"未解析项"，不得静默丢弃，也不得让人误以为模板已全部生效。
6. **G6 不阻断**：模板库不可用、采集器异常、单项落库失败，均不阻断节点创建主链路。

## 四、范围

**纳入**
- 模板的"对象声明"结构化承载位（含既有 `## 前置条件` 的结构化升级路径）
- 四类采集器：参与单位、成员用户、共享文件、前置成果（依赖）
- 统一装配产物（草稿：候选集合 + 未解析项）与控制台只读装配接口

- IM 侧：模板只读工具、装配预览（dry-run）工具、`create_node` 扩展入参、SOP-011 增补声明
- 企业类型同义词表（归一化）

**不纳入**
- 模板存储形态改造（文件夹 + `template.yaml`）与存量模板迁移 →「全景节点参考模板模块」

- 附件（成果约定 / 参考范例）的读取与下发：**由用户本地上传**，不经模板链路（已确认）

- 把模板蓝图（文件识别特征 / 典型文件名 / 流程位置）喂给 LLM 做文件匹配 →「资料驱动节点更新」

## 五、术语

1. **对象声明**：模板中声明"要采集哪类对象 + 匹配条件 + 是否必需"的结构化片段。
2. **采集器（Collector）**：把一条对象声明解析为真实记录候选集合的只读组件。
3. **装配（Assemble）**：采集器集合的编排，输入"模板 + 项目上下文"，输出"节点草稿"。
4. **节点草稿**：`{模板字段, 成果清单, 各类对象候选, 未解析项}`，只读、不写库。
5. **未解析项**：声明了但没匹配到真实记录的条目，必须回显。
6. **落库编排**：用户确认后，按依赖顺序把草稿写入 `project_nodes` / `node_deliverables` / `node_participant_companies` / `node_participants` / `node_accessible_files` / `node_dependencies`。

## 六、已确认决策（本轮拍定）

| # | 决策点 | 结论 | 影响 |
|---|---|---|---|
| D1 | 企业匹配判据 | **类型归一化 + `scope` 包含**（不用 LLM 语义挑选） | 需维护类型同义词表；要求企业台账 `type`/`scope` 填得规范 |
| D2 | 对象声明形态 | **结构化声明式**（非脚本式、非声明+脚本混合） | 模板作者需按格式填；换来实现可控、可校验、两入口天然共用 |
| D3 | IM 侧确认强度 | **轻量**：装配预览工具（只算不写）+ SOP 声明约束流程 | 不接入 `ConfirmQueue`，不做服务端 pending 草稿；可靠性依赖 LLM 遵守 SOP |
| D4 | 开工顺序 | **先切最小一刀** | 首刀 = 前置条件 → 已有成果 → 依赖候选（**已完成**，见 §九 批次 0） |
| D5 | 模板附件定位 | **不读不下发**，由用户本地上传 | 模板目录内的 `成果约定.md` / 参考范例 `xlsx` 不进索引、不经接口下发 |

**贯穿性硬原则（P1）**：**LLM 只转述候选，绝不生成 ID**；所有 ID 必须由服务端从声明解析得出，解析不出的丢弃并回报。此原则用于防止模型幻觉写入脏数据。

## 七、功能需求

### FR-1 对象声明的承载位

1. 模板内新增机器可读的对象声明区，按对象类型分节，每条声明至少含：`描述`（可读意图）、`匹配条件`、`是否必需`。
2. 匹配条件是**声明式**的，按对象类型取值域：
   - 参与单位：`type`（经同义词表归一）+ `scope` 关键词 + 名称关键词
   - 成员用户：来源单位（引用同模板的参与单位声明）+ 可选角色
   - 共享文件：文件名/类型关键词
   - 前置成果：成果名关键词（自然语言描述亦可，见 FR-4）
3. 声明区**不放进 `index.yaml`**——该索引会被注入 prompt，声明全部塞入会持续膨胀。声明随模板正文走，按需读取。
4. 既有 `## 前置条件`（自然语言条目）**继续有效**，作为"前置成果"声明的宽松形态；不得要求存量模板立刻改写。
5. 声明格式需可校验：声明语法错误、`type` 不在同义词表内、引用不存在的来源单位，均在读取时产出告警而非静默忽略。

### FR-2 采集器：参与单位

1. 输入一条参与单位声明 + `project_id`，输出候选企业集合（可 0..N 条）。
2. 候选池优先级：**项目内参建单位**（由 `node_participant_companies` 反推）优先，未命中再退全局企业。
3. 匹配口径（对齐 D1）：`type` 经同义词表归一后等值匹配；`scope` 按关键词包含匹配；`company_name` 按关键词包含匹配。多条件为"与"。
4. **与 `CompanyResolver.resolve` 的语义差异必须保留**：`resolve` 是"歧义即拒绝"的单值解析（供既有写入路径用），采集器是"多候选即返回全部"的候选收集。两者并存，不改前者。
5. 维护一份企业类型同义词表（如 `分包` / `专业分包` / `劳务分包` → 归一为同一类），并提供"未在词表内的 `type` 值"巡检能力，暴露企业台账的数据质量问题。

### FR-3 采集器：成员用户

1. 输入"来源单位集合"或直接描述，输出候选用户集合。
2. 主路径：由已确定的参与单位 → 该单位在职人员（`users.company ∈ 单位集`，且状态为在职）。
3. 可选路径：按姓名/岗位关键词匹配。
4. 候选需带出"来自哪个单位"，便于界面分组呈现与人工判断。

### FR-4 采集器：共享文件

1. 输入文件声明 + 当前操作人，输出候选文件集合。
2. 候选范围**必须限定在该操作人的可见文件集合内**（复用既有可见集口径，不新造可见性规则）。
3. 匹配方式：文件名/类型的包含匹配（复用既有检索能力）；不要求语义理解。
4. 候选需带出"文件名 + 文件编号"以便辨识。

### FR-5 采集器：前置成果（依赖）

> **本轮已完成**，此处固化口径，后续作为其他采集器的参照实现。

1. 输入模板描述 + `project_id`，在**该项目内已有成果**中匹配，输出候选依赖集合。
2. 匹配键两级：整句优先（更具体），整句无命中再退到"去掉『已…』状态尾句"的主体词；成果名侧同时尝试去掉通用尾词（`文件`/`报告`/`清单`…）后比对。
3. 双向子串匹配；名称长度低于下限不参与（避免噪声命中）；多命中取名称最长者。
4. 依赖只能指向**已存在的成果**，故落库必须发生在节点创建之后。
5. 未匹配的描述进入"未解析项"，如实回显。

### FR-6 统一装配与控制台消费

1. 提供一个只读装配接口：输入 `ref_id` + `project_id`，输出节点草稿（模板字段 + 成果清单 + 各类候选 + 未解析项）。
2. 装配**不写库、不产生副作用**，可被反复调用。
3. 控制台信息面板在"选模板"或"切项目"时重新装配；任一入参变化都要重算（前置成果类候选依赖项目）。
4. 面板呈现规则：候选为可删项（默认全选）；未解析项单列回显；改动仅在保存时生效。
5. 装配失败或模板库不可用时，面板降级为纯手工录入，不阻断创建。

### FR-7 创建期落库编排

1. 保存时，用户确认后的各类对象**随节点一次性提交**，由服务端按依赖顺序落库：节点 → 成果 → 参与单位 → 参与人 → 共享文件 → 依赖。
2. **不得**在落库前信任前端传入的 ID：服务端必须对每个 ID 做存在性与归属校验，校验失败的项丢弃并回报（对齐 P1）。
3. 单个关联项落库失败**不阻断**节点创建；失败明细回传界面显式提示。
4. 参与人、共享文件、依赖目前**无创建期入参**，需扩展创建链路或在创建成功后编排补写；文件类落库需同时满足既有可见性/密级约束。

### FR-8 IM 侧接入（模板驱动对话建节点）

1. **模板可达**：新增**只读业务工具**，供 LLM 列出模板清单、读取指定模板的对象声明与成果清单。不得用 `ScriptEntry`（subprocess CLI）作为 LLM 通道。
2. **先预览后落库**：新增装配预览工具（dry-run，只算不写），返回候选集合与未解析项；LLM 据此用**文字**向用户列候选、收调整。
3. **创建入参扩展**：`create_node` 工具需支持携带已确认的成果、参与单位、参与人、共享文件与依赖（或等价的确认后提交方式），并透传模板来源。
4. **SOP 声明**：在节点管理 SOP 增补"参考模板库"一节——位置、发现方式、使用方式、权限口径，并明确"建节点前先取候选、向用户确认后再落库"的流程要求。仅增一节，不改既有触发条件、工具清单与权限映射。
5. **权限**：沿用既有判定，本基线不新造权限规则。模板列出/读取的门槛与建节点引用模板的门槛需明确（见 §十二 开放问题 3）。

### FR-9 可解释性

1. 每条候选必须能回答"依据模板的哪一条声明、匹配到什么、为什么命中"。
2. 该信息需在控制台面板（对操作人）与 IM 回复（对对话用户）中可见。

## 八、非功能需求

1. **NFR-1 不阻断主链路**：模板库缺失、索引损坏、采集器异常、单关联项落库失败，均不影响节点创建/查询等既有流程。
2. **NFR-2 无新增常驻成本**：无常驻进程；采集只在"装配/预览"被显式触发时发生，不给普通对话引入额外 LLM 调用。
3. **NFR-3 只读安全**：装配链路全程只读；模板目录容器内只读挂载。
4. **NFR-4 可解释**：见 FR-9。
5. **NFR-5 零新增依赖**：复用既有 Service / Repository / 可见集能力，不引入新库。
6. **NFR-6 注册通道接入**：新增工具必须经 `tool_registry` 注册并带参数 schema（三步缺一不可）；新增能力不得裸接线。
7. **NFR-7 主循环冻结**：本需求**不得**改动 Session 主循环；IM 侧一律落能力层（新工具 / 新 SOP 声明）。
8. **NFR-8 控制台同源**：控制台的装配与落库必须复用 Emily 既有能力层，不得在路由层复刻业务逻辑。
9. **NFR-9 数据质量可见**：企业类型越出同义词表、`scope` 缺失等情况应可巡检，不以静默降级掩盖。

## 九、任务分解与批次

### 批次 0 — 前置成果采集（依赖）✅ 已完成

| 任务 | 验收 |

## 十一、验收口径

> 均为可执行命令；在**容器内**执行（镜像无 `curl`，统一走 `python -c`）。`PID` 取目标项目 ID。

1. **装配只读性**：调用一次装配接口，`project_nodes` / `node_dependencies` 行数不变。
   ```bash
   docker exec emily-core python -c "import urllib.request,sqlalchemy as sa
   from emily_core.infrastructure.database.session import get_session
   def c(sql):
       with get_session() as s: return s.execute(sa.text(sql)).scalar()
   q='select count(*) from project_nodes'; q2='select count(*) from node_dependencies'
   a1,b1=c(q),c(q2)
   urllib.request.urlopen('http://127.0.0.1:18080/api/v1/console/node-draft?ref_id=REF-CONST-DG-001&project_id=PID').read()
   a2,b2=c(q),c(q2)
   print('nodes', a1, a2, 'deps', b1, b2)"
   → 预期输出：`nodes N N deps M M`（两侧相等）
   → 实测（2026-09-22）：`nodes 42 42 deps 22 22`
   ```
2. **前置成果匹配（批次 0）**：三个存量模板的装配结果，匹配项与未解析项均可解释，且无假阳性。
3. **参与单位匹配（批次 1）**：项目内存在 `type=分包` 且 `scope` 含关键词的企业时，声明"某专业分包单位"能列出该企业为候选；项目内不存在时进入未解析项而非报错。
4. **成员用户匹配（批次 2）**：候选用户均属于已确定的参与单位；带出所属单位。
5. **共享文件匹配（批次 3）**：候选文件全部落在操作人可见集内（越界即 FAIL）。
6. **落库正确性**：保存后各类关联表行数与界面确认项一致；从界面移除的项**不入库**；越权/不存在的 ID 被服务端丢弃并回报。
   → 实测（2026-09-22，`REF-CONST-DG-001` + 2 条有效依赖 + 1 条伪造 ID）：`project_nodes` 42→43、`node_deliverables` 46→49（+3，与模板成果数一致）、`node_dependencies` 22→24（+2，仅有效项）；伪造项 `BOGUS-DELV-999` 未落库。
7. **失败不阻断**：人为让某项依赖落库失败（如指向已废弃成果），节点仍创建成功且界面显式提示失败明细。
   → 实测：返回 `dependencies_added=[2 条]`、`dependencies_failed=[{BOGUS-DELV-999, "成果 BOGUS-DELV-999 不存在"}]`，节点 `NODE-56CF` 仍创建成功；`project_events` 记 `node_created`×1 + `dependency_added`×2（伪造项无事件）。
8. **软删语义**：删除后节点从全景节点表消失（表内回到 42 条），`is_discarded=true`；**关联记录按设计保留**（成果 3 行 / 依赖 2 行 / 事件 6 条仍在库）。
9. **IM 可达性（批次 4）**：对话中可列出模板、可读到指定模板的声明；预览工具返回候选且不写库。
10. **接线闭合**：新增接口在前后端均有可达调用路径。
    ```bash
    # 限定文本类型，避免 __pycache__ 的 .pyc 命中干扰计数
    grep -rn --include=*.py --include=*.js --include=*.html "node-draft" emily-core/ | wc -l
    → 预期输出：≥2（后端定义 + 前端消费）；仅 1 处 = 未接线，FAIL
    → 实测（2026-09-22）：3 处 —— `api/routes/console_resources.py` 定义 1 处；`static/scripts_tool/console.js` 消费 2 处（模块命令提示 + 装配调用）
    ```

## 十二、开放问题（待评审确定）

1. **与「全景节点参考模板模块」基线的重叠归属**——《参考模板模块》的 FR-5（LLM 检索工具）、FR-6（SOP-011 声明）与本基线 FR-8 完全重叠；其 FR-3（容器挂载）已由本轮完成。
   **建议**：把 FR-5 / FR-6 并入本线（因为它们必须消费"对象声明"，单独做只能做一半），《参考模板模块》只保留 FR-1 / FR-2 / FR-4 / FR-8（存储形态 + 索引形态 + 存量迁移）。**需先确认，否则两条线会各建一半。**
2. **声明格式的落地形态**：是"新增独立小节（如 `## 对象声明`）"，还是升级 frontmatter 承载？前者可读性好、与既有正文章节风格一致；后者机器友好。需与《参考模板模块》的 `template.yaml` 形态一并决定，避免同一份信息两处。
3. **IM 侧权限门槛**：列出/读取模板定 L3+ 还是 L5+？与"谁能参考模板"的业务口径挂钩（建节点引用模板沿用 L5+）。
4. **工具粒度**：`list_node_templates` + `read_node_template` 两个工具，还是一个合并的 `query_node_template`；预览工具是否与之合并。
5. **成员用户的默认集**：模板声明"某单位应参与"时，是否默认把该单位**全部在职人员**加为成员？范围过大时会带来大量无关成员，需业务口径确认（或要求声明中显式指定角色）。
6. **依赖的阻塞语义**：模板采集出的依赖默认权重取多少？是否需要区分"阻塞型前置"（高权重）与"参考型前置"。
7. **规则派召回不足时的兜底**：若企业 `scope` 数据长期不规范导致召回不足，是否引入语义匹配兜底（本轮已决定不引入，保留为后续选项）。
