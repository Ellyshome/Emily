# 全景节点参考模板模块 — 需求基线 V1

**一句话**：把 `emily-data/node_templates/` 从"只有索引、无人消费的空壳"建成完整可用的全景节点参考模板模块——可挂载、可发现、可检索、可被 AI 在建节点时参考。

> **性质**：需求基线（讨论稿），确认后转计划
> **日期**：2026-09-22
> **范围**：仅"参考模板模块本身"（存储形态 + 挂载 + 索引 + 检索通道 + SOP 声明）；**不含** Atlas 的归属判定/提案/签认迁正（属「全景节点维护者」线）。
> **关联**：
> - 消费方设计见 `Issues/全景节点维护者/全景节点维护者_需求基线_V1.md`（FR-12 明确"参考系消费现有通用参考节点库"）
> - 填报格式来源见 `Issues/资料驱动节点更新/全景节点填报格式约定_V1.md`
> - 种子材料见 `Issues/节点成果手册-上传全景计划/`

---

## 一、背景：现状与四个断点

模块的位置与契约早已存在，但链路是断的：

| # | 现状 | 锚点 |
|---|---|---|
| 1 | **有位置**：`emily-data/node_templates/` 定义"模板 → `project_nodes` / `node_deliverables` / `node_dependencies` 三表"映射契约 | `emily-data/node_templates/README.md` |
| 2 | **只索引、不消费**：README §八 声称的 `infrastructure/node_template/parser.py`、`mapper.py` 不存在；全仓无代码读模板正文 | `emily-core/emily_core/infrastructure/`（无 `node_template/`） |
| 3 | **未进 prompt**：`ctx.node_template_catalog` 仍加载，但 `get_prompt_variables` 已按提示词第二刀移除该占位符，`session.md` 亦不含 | `emily-core/emily_core/session/session_context.py` |
| 4 | **未挂载、未打包**：三个 compose 变体均未挂 `node_templates`，Dockerfile 不 COPY `scripts/` 与 `emily-data/`；容器内 `/app/data/node_templates` 不存在，加载被 `try/except` 静默吞掉；bootstrap 的 `auto_run` 自检因脚本缺失而空转 | `docker-compose-{minimal,wecom,napcat}.yml`、`emily-core/Dockerfile`、`emily-core/emily_core/bootstrap.py` |
| 5 | **形态受限**：现约定为"单 `.md` + frontmatter"，承载不了参考范例（xlsx）与成果约定附件 | `scripts/maintain_node_template_index.py`（顶层 `glob("*.md")`） |

**结论**：位置有了但不可用——LLM 既不知道有模板库，也没有任何工具能读到它。需立一条独立需求线把该模块补成完整闭环。

---

## 二、定位

- **是**：一个"行业参考蓝图"的数据模块 + 一条 LLM 可调用的只读检索通道 + 一句 SOP 声明。
- **不是**：不是常驻服务、不是新 SOP 业务流、不承载节点写入（写入仍走既有 `node_templates` 消费方与节点工具集）。
- **不被本基线改动**：节点创建/更新/废弃的既有工具与权限口径（SOP-011 §3.3 / §3.5）。

---

## 三、目标

1. **G1 可挂载**：容器内模板库真实可读，三个 compose 变体口径一致。
2. **G2 可发现**：LLM 通过 SOP 一段说明即知"有模板库、在哪、怎么用"。
3. **G3 可检索**：存在一个业务工具，能列出模板清单、读取指定模板的清单与附件清单。
4. **G4 可承载附件**：模板可携带参考范例、成果约定等附件，且附件定位明确（谁读、怎么读）。
5. **G5 不破坏既有契约**：`README.md` 的"模板 → 三表"映射契约继续成立，存量 2 个模板迁移后行为不变。

---

## 四、范围

**纳入**
- 模板存储形态改造（逐文件夹 + 固定命名清单文件 + 附件）
- 容器挂载与路径统一（含 Dockerfile 目录准备）
- `index.yaml` 生成脚本改造（目录扫描 + 附件清单）
- LLM 检索通道（新增只读业务工具 + SOP 声明）
- 存量模板迁移（2 个 `.md` → 文件夹）

**不纳入**
- 模板 → 节点三表的**自动写入实现**（parser/mapper 落地属"资料驱动节点更新"或后续计划）
- Atlas 的判断与提案能力
- 模板的在线编辑/上传界面
- 模板内容的业务扩写（各专业填报，另行推进）

---

## 五、术语

1. **模板文件夹**：`node_templates/` 下的一个子目录，即一个节点模板。
2. **清单文件**：模板文件夹内固定命名的结构化入口文件（本基线定为 `template.yaml`）。
3. **附件**：模板文件夹内除清单文件外的所有文件（参考范例、成果约定、图纸样例等）。
4. **模板索引**：`index.yaml`，模板库的唯一发现入口。

---

## 六、功能需求

### FR-1 存储形态：一个文件夹 = 一个模板

1. 模板置于 `node_templates/<模板目录>/`，目录名建议等于 `ref_id`（如 `REF-CONST-DG-001`）；脚本按目录扫描，并校验"清单文件内 `ref_id` == 目录名"，不一致则告警。
2. 每个模板文件夹**必须**含固定命名的清单文件 `template.yaml`，承载需要入库的结构化字段（至少：`ref_id`、`node_name`、`node_type`、`stage_id`；可选：`deliverables[]`、前置条件、`remark` 摘要来源）。
3. **"任意文本格式"只开放给附件**，不开放给清单文件——避免破坏入库映射的抽取锚点（原契约依赖固定段落，逐文件夹后必须有一个稳定入口）。
4. 附件命名自由，推荐语义化固定名（`成果约定.md`、`范例-*.xlsx`），便于索引呈现与人工辨识。

### FR-2 附件定位

1. 附件是**给人看和给人下载的参考物**，不要求 LLM 直接解析。
2. 索引只登记附件**清单**（文件名 + 大小 + 类型），不索引正文；LLM 需要交付成果约定正文时，读的是文本类附件（`.md`/`.txt`/`.yaml`）。
3. 二进制附件（`.xlsx`/`.docx`/`.pdf`）**不走本模块的解析链路**；若后续需要 LLM 读懂，另立需求走既有文件解析/OCR 链路，不在本基线承诺。

### FR-3 容器挂载与路径统一

1. 挂载点统一为 `/app/data/node_templates`（与代码中 `resolve_data_path` 的容器路径一致）。
2. 三个 compose 变体（`minimal` / `wecom` / `napcat`）**均须**以只读方式挂载 `./emily-data/node_templates:/app/data/node_templates:ro`。
3. Dockerfile 补 `mkdir -p /app/data`——`resolve_data_path` 以 `container_path.parent.exists()` 判定，`/app/data` 不存在会静默回退到开发路径，容器内依然读不到。
4. **索引生成与消费分离**：`index.yaml` 在宿主机生成（维护脚本运行于开发环境），容器只读消费；容器内不承担索引写入。
5. 顺带核对既有漏挂：`company_policies` 仅在 `napcat` 变体挂载，`skills` 亦非三变体一致，一并对齐。

### FR-4 发现机制：索引与脚本

1. 保留 `index.yaml` 为唯一发现入口，数据结构调整：
   - 保留：`ref_id`、`node_name`、`node_type`、`stage_id`、`summary`
   - 变更：`file` → `dir` + `entry_file`
   - 新增：`attachments[]`（文件名清单）
2. `scripts/maintain_node_template_index.py` 同步改造：扫描 `*/` 子目录（不再顶层 `glob("*.md")`）、解析 `template.yaml`、汇总附件清单；`--check` / `--auto` 三种模式语义不变。
3. 索引中保持 `template_count` 与阶段/类型分布统计，便于人工巡检。

### FR-5 检索通道：LLM 可调用

1. 新增**只读业务工具**（`BusinessFlowTool`，进程内 async handler，登记进 `tool_registry`），提供：
   - 列出模板清单（按阶段/类型过滤，返回 `ref_id` + 名称 + 摘要 + 附件名）
   - 读取指定模板（返回清单文件内容 + 附件清单）
2. **不得**用 `ScriptEntry`（subprocess CLI）作为 LLM 通道——该形态的设计消费者是开发者而非 LLM。
3. 工具必须只读、幂等、不写库，失败 fail-open（模板库不可用时不阻断节点操作主链路）。
4. 工具名称与粒度（一个合并工具 vs 列出/读取两个工具）见"开放问题"。

### FR-6 声明：写入节点管理 SOP

1. 在 `emily-data/sops/SOP-011-SYS-node_manage.md` 增补"参考模板库"一节：**位置、发现方式、使用方式、权限口径**。
2. 声明口径：模板是"判断依据/参考蓝图"，**不是硬规则**（与「全景节点维护者」FR-12 一致）。
3. 方式上仅"新增一节声明"，不改 SOP-011 既有触发条件、工具清单与权限映射。

### FR-7 权限口径

沿用既有判定，本模块**不新造权限规则**：

| 动作 | 门槛建议 |
|---|---|
| 列出 / 读取模板 | L3+（待定，见开放问题） |
| 建节点时引用模板 | 沿用节点创建口径（L5+，见 SOP-011 §3.5） |

### FR-8 存量迁移

1. `REF-CONST-DG-001-施工图设计完成.md`、`REF-CONST-LC-001-建设工程规划许可证.md` 迁移为模板文件夹 + `template.yaml`。
2. 迁移后 `index.yaml` 的 `ref_id` / `node_name` / `node_type` / `stage_id` / `summary` 输出**与迁移前一致**（作为回归验收项）。

## 七、非功能需求

1. **NFR-1 不阻断主链路**：模板库缺失、索引损坏、工具异常一律不影响节点创建/查询等既有流程。
2. **NFR-2 无新增常驻成本**：无常驻进程，不给普通对话引入额外 LLM 调用（工具按需触发）。
3. **NFR-3 只读安全**：容器内模板目录只读挂载；工具无写入路径。
4. **NFR-4 可解释**：任何引用模板的建议，都能指出"依据哪个 `ref_id` 的哪一条"。
5. **NFR-5 零 schema 变更**：不新增数据库表/字段。

## 九、验收口径

1. 容器内 `/app/data/node_templates/index.yaml` 可读，Session 侧加载无异常日志。
2. 三个 compose 变体均完成只读挂载，重启后仍生效。
3. 新增/删除一个模板文件夹后运行维护脚本，`index.yaml` 正确反映；未运行脚本时 `--check` 报出差异。
4. 检索工具在 LLM 链路可被调用：能列出模板、能读到指定模板的清单与附件清单。
5. 存量 2 个模板迁移后，索引关键字段与迁移前一致。
6. SOP-011 含"参考模板库"一节，LLM 侧可见该 SOP 的目录摘要。

## 十一、开放问题（待评审确定）

1. **消费方优先级**：先服务"手工建节点的人"还是等 Atlas？——Atlas 规格已标注失效（见 `Issues/节点状态自证化/节点状态自证化_执行报告_V1.md`），若通道为 Atlas 而建，需先确认其落点是否变更。
2. **工具粒度**：`list_node_templates` + `read_node_template` 两个工具，还是合并为一个 `query_node_template`。
3. **读取权限**：列出/读取定 L3+ 还是 L5+（与"谁能参考"的业务口径挂钩）。
4. **目录命名**：目录名 = `ref_id`（稳定但不可读）还是 `{ref_id}-{node_name}`（可读但改名即变路径）。
5. **附件是否需要被 LLM 直接消费**：若需要，须指定走哪条解析链路（本基线默认不走）。
6. **是否保留旧契约兼容**：是否允许顶层单 `.md` 模板与文件夹模板短期并存（本基线默认不兼容，一次性迁移）。
