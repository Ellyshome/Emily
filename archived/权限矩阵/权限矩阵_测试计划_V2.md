## 一、目标与范围

### 1.1 目标

**把权限表当作目标态（to-be），逐格验收「是否已实现」；凡未达成的格子，落为待实现项并给出实现动作。**

三个层次：

| 层次 | 内容 |
|---|---|
| **L1 逐格达成** | 16 个能力行 × 6 档（共 96 格）的授权结论，是否与代码运行时行为一致 |
| **L2 注释口径** | 注1~注14 声明的口径（可见范围推导、通道差异、密级制度、已知取舍）是否成立 |
| **L3 通道闭合** | 每格在 **IM / REST / CLI / console** 各通道的结论是否一致（尤其标注了通道差异的格子） |

### 1.2 基准唯一性原则

> 判定冲突时**一律以权限表为准**。若权限表与清单/代码不一致，记为该格「未达成」，并在差距登记表中登记实现动作——**不得用"清单说这是有意为之"来豁免权限表目标**（已知取舍类除外，见 3.2）。

### 1.3 范围内

- 权限表全部 16 个能力行（人员类 3 / 企业类 1 / 节点类 6 / 文件类 6）的 96 格授权结论
- 注1~注14 全部条目
- 授权链路的四通路（P1 级别层 / P2 SOP 声明层 / P3 自由工具集护栏 / P4 兜底白名单）
- IM / REST / CLI / console 四通道的等价性与差异

### 1.4 范围外

| 项 | 原因 |
|---|---|
| 按单位维度真·行级隔离 | Q9 已决（不立项）；仅验证服务层过滤有效 |
| 纠错补救类**能力**本身（误删恢复等） | D7 已决（本期不做）；仅验证 console 入口是否停用 |
| 前端 UI 渲染 | 只验端点行为与判定同源 |
| 节点业务状态机正确性 | 属 `test/09_全景节点.md` 既有覆盖，本计划只做挂载影响的抽检 |

### 2.3 通道语义（每格可能多通道，须分别判定）

| 通道 | 判定位置 | 目标差异 |

### 2.4 判定语义关键（防误判）

| 语义 | 事实 | 影响 |
|---|---|---|
| P1 `permission_flag` 与 SOP 准入均为**线性「>=」** | `tool_registry_repo.get_available`、`permission/cache._compute_user_whitelist` | L4 会拿到 `write`(L3+) 工具与 `min_level<=4` 的 SOP；**不可用树形继承直觉断言 L4 看不到 L3 工具** |
| 工具**可见 ≠ 可执行** | `sop_only` 工具须匹配到承载 SOP 才能在 IM 执行 | 出现"能看到但跑不通"的空窗，是本计划 L3 层的重点 |
| `record_*` 四件套 permission_flag=`write`(L3+) | 但被 SOP-001/002/003/004（准入 L2）声明 | **L2 的 R9/R12 依赖 P2 并集**，不是 P1 |
| 兜底白名单无写业务工具 | `_ADVANCED_APPEND_TOOLS` 仅 4 个 `record_*` | 写能力不可靠兜底"救活" |
| 未登记用户快照降级 `{"level":1}` | `permission_service.build_permission_dict` | **禁止用假 sender-id**（Q3） |
